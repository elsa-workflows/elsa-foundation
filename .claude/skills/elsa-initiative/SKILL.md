## Outline

1. Read `docs/skills/catalog.md#initiative-coordination` and `docs/contributing/initiatives.md`.
2. Find the initiative: the issue given, or the parent of type Initiative (at any depth) or `Part of #N` of the work in hand. For an unlinked ADR or spec, check open initiative boards for its topic and add the missing link; ask if the scope is unclear. If there is no matching initiative, stop; this skill does not apply.
3. Find the user's role: the assignee (or the delegate the board records) is the coordinator, people in the board's **Approvers** list are approvers. Help with permitted contributions without requiring a role; decline actions reserved for a coordinator, recorded delegate or approver when the user lacks that role. Contribution, GitHub permissions or a bot's identity never grant approval authority.
4. Do the requested action as the catalog describes: check in, contribute an analysis, report work, reconcile a multi-point review or position, sync, reserve a number, merge an accepted proposal, start a spec's implementation, land (these five coordinator or recorded delegate only), track a side track, run the final round, prepare the meeting, process the meeting transcript, or start an initiative. Closing the review follows the guide: at most two review rounds, `Resolve in call` at any time, one final round in which approvers approve or record a `Meeting item` in their own words (a session helping an approver formats and fact-checks, never drafts positions or counter-arguments), a human meeting led on short spoken anchors (decision ID plus a two-to-three word handle), and a coordinator session that classifies the transcript, grills the coordinator to confirm, and applies the decisions itself; approvers then only verify. Proposal PRs target the initiative branch `initiative/<n>-<slug>` (stacked proposals target their parent's branch); authors cut their branch from it, and spec authors give `speckit-specify` the reserved folder via `SPECIFY_FEATURE_DIRECTORY`; the parent's author merges agreed stacked children, never the coordinator. Only the coordinator merges proposals (also their own; when the coordinator is away the delegate or an approver stands in, and a non-delegate stand-in reports board updates in a pointer comment instead of editing the board), and only once agreement is recorded in any form (a processed meeting read-back, a comment, a reconciliation row or a review; a GitHub approval is not required) and after the guide's pre-merge gate: merge `origin/main` in (never rebase), check main's changes, and in a local unpushed merge of the PR head with the branch check the proposal against the whole branch and run `python tools/initiatives/check_decision_docs.py`; verify every finding, post one gate comment, let the approvers decide contradictions, then squash-merge once no contradiction, number collision or check error is open. Phases apply per spec: a spec advances to implementation as soon as it is approved and every ADR and decision it applies is agreed and merged into the branch, without waiting for the other specs; it is implemented on the initiative branch (implementation PRs target it, run the full CI tiers, are reviewed and approved by Code Review, and are merged by the coordinator without the pre-merge gate) and lands on `main` with the initiative. Whoever merges a PR into the initiative branch closes the issues it fixes right after the merge (`closingIssuesReferences`), with a comment naming the PR and merge commit, because GitHub only auto-closes on merges into `main`; the sync closes any left open. At landing, an approver's attestation is a PR comment and Code Review approves and merges. When the gate's local merge conflicts, the author merges the initiative branch into the PR; the coordinator running the gate does not commit to it. A side-track fix is its own issue outside the initiative; the proposal it blocks waits until the fix is synced in. Follow the guide's final-commit agreement rule for ADRs and specs; the author makes status edits, and material changes — ones that could seriously alter a reviewer's decision, not trivial edits such as the status line — require fresh agreement, with the re-review request stating what changed and what it means for that reviewer's prior answers. A reconciliation never makes anything agreed. A finding that a document must change is handled only when its edit is **prepared** (a pushed draft commit named in the row), never left comment-only; the author drafts it, or the coordinator in that PR's scope deduces the verdict, applies it and asks the reviewers to verify. The sync and the pre-merge gate both check **surface consistency** (title, description and document agree on the current direction; the description is the live state and carries the open-questions checklist; no document-changing finding is comment-only), and the gate's deterministic checks fail a newly added ADR with no *Alternatives considered* section. The document stays **name-free and timeless** (no `@` mentions, attributed positions, dated headings, PR or issue links, provenance lines or open-questions section; the checker fails mentions and warns on the rest); routing lives on the board. When a session helps anyone take part in a proposal PR or issue, it offers to record their thoughts as a **forum comment** but offers to edit the document only to the PR's author or the coordinator in that PR's scope. During sync, open the required draft review PR for work merged without agreement and keep dependent work blocked.
5. Apply the size guard before every post: split into numbered comments or link a canonical record yourself; ask only when an alternative changes content, destination or access.

Only the coordinator, or the recorded delegate, edits the initiative's description. Do not touch `docs/program-goals/`.
