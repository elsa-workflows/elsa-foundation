# Extension points — DispatchWorkflow runtime

## `DispatchWorkflowRuntimeFeature`

- Shell feature: `ActivitiesDispatchWorkflowRuntime`.
- Depends on `WorkflowsRuntimeResumption`.
- Contributes `ChildStartExecutor` for the stable `Elsa.Activities.DispatchWorkflow.StartChild` post-commit intent kind with a finite host-configured total-attempt count and positive retry delay. Explicit rejection is permanent; infrastructure unavailability, non-forwarded deferral, and a duplicate answer with no child to show for it are transient, so the duplicate dead-letters through the ordinary delivery budget.
- Contributes `ChildCancelExecutor` for the stable `Elsa.Activities.DispatchWorkflow.CancelChild` kind with an unbounded, positive-backoff retry policy.
- Contributes `ParentResumeExecutor` for the stable `Elsa.Activities.DispatchWorkflow.ResumeParent` kind with an unbounded, positive-backoff retry policy. The aggregate dispatcher owns `DispatchAsync`; contributed handlers own `HandleAsync`, and each registration is the sole source of its kind and retry policy.

## Shared runtime contracts

The module stages `WorkflowDispatchCheckpointRequest` through the additive `IWorkflowDispatchStagingContext` capability implemented by the Foundation runtime context. The runtime engine, rather than the activity, owns folding the dispatch record and intent into the activity-completed checkpoint. Providers replace `IWorkflowDispatchStore` alongside their checkpoint persistence implementation; a provider must never ignore non-empty `WorkflowDispatches` state changes.

The activity has no transport selector. `ChildStartExecutor` atomically admits the dispatch through `IWorkflowDispatchAdmissionStore` before delegating to `IWorkflowStartDispatcher`, which retains authority over exact-source gating and actor-provider selection. `WorkflowDispatchCancellationEnricher` adds a provider-resolved cancellation request and cancel intent to a parent Cancel checkpoint; `IWorkflowDispatchCancellationStore` resolves that request in the checkpoint transaction. `ChildCancelExecutor` sends one deterministic Cancel command through the configured child actor. Runtime readiness rejects providers missing either atomic dispatch capability.

`IWorkflowTestScopeCleaner` is the internal close/reconciliation capability for test-run expiry and teardown. It pages only exact-scope live fire-and-forget dispatches: Pending is cancelled before admission; Started receives the existing deterministic child Cancel responsibility. It never treats ordinary parent completion as teardown and never directly cancels waited, production, legacy-unscoped, or other-scope dispatches. No public teardown route is contributed by this module.

`WorkflowDispatchDeliveryFailureProjector` supplies the feature-owned `IPostCommitFailureProjector`; registration fails clearly if another owning feature already selected that replacement contract. Exhausted child-start delivery reaches a provider completion boundary that checks the deterministic child execution first: durable child materialization or terminal evidence wins and acknowledges the start responsibility, while absence atomically finalizes the original outbox item as the dead letter and moves the dispatch to `DispatchFailed` with deterministic, allowlisted incident evidence. Wait mode also creates one deterministic parent-resume responsibility in that same completion; fire-and-forget creates none and can be reopened only through the separately authorized `IWorkflowDispatchRedriveStore` capability.
The committed child-start payload carries the parent's immutable retained pin and one replay-stable dispatch depth. Retained-pin starts may use the exact child after its source is replaced or unpublished, but still pass contributed runtime start policies and the configured depth limit before actor acquisition. Realized child inputs are checked against the declared-input snapshot before the dispatch checkpoint is staged.

Configure `DispatchWorkflowOptions.MaxNestingDepth` through the standard options surface. The default maximum child depth is 32, values must be positive, root and legacy starts begin at zero, and one DispatchWorkflow edge increments depth exactly once.

Wait mode stages a deterministic, non-expiring completion bookmark through the runtime checkpoint. `WorkflowDispatchCompletionEnricher` turns a Completed, Faulted, or Cancelled child terminal checkpoint into one deterministic parent-resume intent. Completed uses `IWorkflowOutputSource` so only policy-safe terminal outputs cross the execution boundary; redacted outputs retain metadata but never their value. Faulted exposes only a fixed diagnostic classification and at most 32 stable incident IDs; Cancelled exposes fixed classification only. If an intent was already committed, the enricher retrieves it through `IPostCommitOutboxLookupStore` and reuses the exact durable representation.

`ParentResumeExecutor` dispatches the replay-stable bookmark stimulus and then verifies the exact parent workflow, activity, and bookmark state. Missing state is acknowledged only when durable state proves the parent activity or workflow terminal; otherwise delivery remains retryable. The activity callback accepts only its deterministic target and identity tuple, then materializes Completed, Faulted, Cancelled, or delivery-caused `DispatchFailed` as an ordinary matching graph outcome without faulting the activity. `DispatchFailed` carries no child outputs or raw provider failure detail and is permanently non-redrivable in wait mode.

## IRuntimeWorkflowControlBoundary

- **Kind:** single-implementation replacement, scoped. DispatchWorkflow supplies the default. Register one scoped override before the feature, or explicitly replace its descriptor; startup rejects missing or multiple providers. Resolution never fans out.
- **Usage:** resolves an opted-in called root through its exact admitted waited dispatch, pinned caller/consumer/root and complete execution context. The workflow's retained lookup hint grants no authority. Legacy/no-hint execution returns null and keeps ordinary dispatch behavior. The declared control key/version is compiled from ActivityChildControlConsumerAttribute on a structural control consumer and admitted only from its exact child's scheduling provenance.
- **Failure:** WorkflowControlBoundaryException carries workflow/root identifiers and the original InnerException for inconsistent retained identity or store failure. Cancellation passes through.
- **Delivery boundary:** this service resolves authority only. Producer control staging, terminal batching, source-outbox validation, ordered inbox processing and consumer callbacks are separate responsibilities; no authored-control delivery or foreign incident absorption follows from a successful lookup alone.

## Root control checkpoint contribution

The scoped internal WorkflowControlProducerEnricher owns producer-state validation and the mandatory terminal barrier. It runs at phase75, after lifecycle projection (default phase0) and cancellation (50), before the existing single parent-resume/result enrichment (100). It reads the retained exact root with current-checkpoint overlay and includes the same terminal root projection on replay, preserving every other atomic participant and outer commit fence/work settings. A terminal outcome without authored data gets a fresh empty barrier; ordinary fault does not invent authored failure classification.

Failure is WorkflowControlBoundaryException with original cause and the exact root when known (null before identification); cancellation passes through. This contribution stages checkpoint data only. Nonterminal outbox transport, terminal result/source authority, ordered inbox and consumer delivery are separate phases; successful producer staging does not qualify them.

## Control source authority

IRuntimeChildControlAuthorizer is a single scoped replacement owned by DispatchWorkflow. Register an override before the feature or replace its descriptor; shell initialization rejects missing or multiple providers. It resolves the exact retained boundary and looks up the carried commit/intent/outbox identity directly, comparing the whole committed transport payload. It accepts retained source authority regardless of outbox delivery status and never infers an older batch from the root's latest projection. Inconsistent/missing source or store failures raise WorkflowControlBoundaryException with original cause; cancellation passes through.

The internal scoped WorkflowControlNotificationEnricher runs at90, between producer projection75 and terminal resume100. A nonterminal batch emits only for its own checkpoint source work; the root projection atomically retains that source commit ID so an unchanged projection never emits again, including another checkpoint from the same work. Exact original replay requires the anchored outbox authority. The source child workflow/root owns this outbox responsibility; the immutable payload carries the exact parent/call/consumer delivery address, preserving the generic checkpoint target invariant. One deterministic intent carries its whole ordered batch. Equivalent persisted intent is reused, conflicting content refuses. Terminal batches travel only in the existing single parent-resume result. DispatchWorkflow retains its original constructor and ordinary outcomes; the scoped `DispatchWorkflowResumeGuard` handles the named Core `ActivityResumeValidating` event and validates the exact source and complete result before trigger claim or activation; a missing admitted terminal barrier refuses. `DispatchWorkflowRuntimeFeature` requires Events and initialization requires its exact-source handler. Temporary dependency reads retain their original cause in an unavailable boundary exception and defer the owed resume; malformed or contradictory data fails closed. Fixed diagnostics and the actual child incident stay separate from authored control. The generic IRuntimeChildControlCompletion result projection copies validated terminal control onto the completed leaf in that same resume checkpoint; this data grants no dispatch or consumer authority.

Staging and immutable-source validation do not establish an ordered caller inbox or nonterminal callback delivery. Those use the subsequent generic callback/inbox path; no such delivery or recovery claim follows from this contribution alone.

## Control inbox delivery

`WorkflowControlNotificationExecutor` owns the one registered nonterminal intent kind, with UntilAcknowledged retry. It verifies its immutable source before enqueueing the exact consumer command and acknowledges only after durable inbox acceptance or target retirement. Delivery idempotency derives from the source outbox identity. Actor reply loss after buffered or consumed acceptance retries against retained cursor data without repeating the callback. This is engine delivery; BPMN alone interprets authored codes and failure precedence. Neither a completed DispatchWorkflow leaf nor an inbox acceptance absorbs the called workflow's actual fault incident.

The current in-process controls cover empty terminal barriers arriving before earlier notifications, ordered release, all returned decision branches, same-call cancellation, source read outage before activation, and reply loss after buffered/consumed acceptance. Both providers conservatively refuse whole-run deletion while linked control is owed, and late source retries require sticky caller retirement proof. Fresh-provider gap recovery and concurrent claims remain T045 gates; in-process controls do not qualify them.

Failed admission has no called root: the pre-resume validator permits ordinary `DispatchFailed` only against its exact opted-in waited dispatch and current generation's deterministic immutable failure resume receipt. It carries no authored batch or inbox. A forged failure result cannot use this route to omit an admitted terminal barrier.

### Called-control history retention (#2735)

`IWorkflowExecutionStateStore.IsDeletionTombstonedAsync` returns true only for sticky provider deletion proof in the current persistence scope. Its default is false; an absent execution does not establish proof. In-memory/EF implementations use retained ownership tombstones, and the coalescing wrapper delegates to the durable store. EF provider errors retain contextual persistence exceptions and original causes.

Run deletion returns `DependencyRetained` (API409) while opted-in waited-control history remains needed. Called history requires sticky caller deletion proof; terminal caller deletion requires terminal/pre-admission-failed called work and Delivered owed rows. FailedFinal is not resolution. Missing or inconsistent hinted-child authority refuses deletion. Checks run in existing provider deletion gates; EF probes incoming sticky proof before its candidate write lock and avoids a second-root lock. Parent identity currently lives in workflow payloads, so the rare deletion guard captures finite same-scope header pages before any write lock, then rechecks captured identities against current authority under the candidate lock. Supported terminal state admits no new called runs after that capture. This is not a throughput claim. Existing dispatch/source replay records remain retained outside run-owned purge.
