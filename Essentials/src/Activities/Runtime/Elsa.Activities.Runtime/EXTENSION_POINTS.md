# Extension points — Activities.Runtime domain

The per-domain catalog (framework §2.22.1). Anchored at `Elsa.Activities.Runtime`, which coordinates transient activation, pinned-input hydration, atomic transition handling, and CLR type discovery.

> Carries **no** `Elsa.*.Design.*` dependency (Elsa §E2.2). Runtime invocation consumes only the compiled `ActivityContract` and canonical bindings.

---

## Implementable contributor interfaces

### `WorkflowInvokeActivitySchedulerWorkHandler` *(Activities Runtime — `Elsa.Activities.Runtime`)*
- **Kind:** Scheduler work contributor.
- **Register:** `ActivitiesRuntimeFeature` registers it as an `IWorkflowSchedulerWorkHandler`.
- **Usage:** handles `WorkflowExecutionCommandKind.InvokeActivity` work by materializing or reusing the committed input snapshot, acquiring an `IActivityActivator` lease, executing one closed typed transition, and atomically recording completion or fault state. Structural activities are invoked through `IRuntimeStructuralActivity` and must return one `RuntimeStructuralContinuation` decision. When a faulted activity has a parent, it rides a child-fault parent-evaluation work item (`ChildFaultParentEvaluation`) on the fault incident checkpoint so a fork/join parent can resolve its join deterministically (#308). It does not load Design-owned authored workflow models.

### `WorkflowParentActivityCompletionSchedulerWorkHandler` *(Activities Runtime — `Elsa.Activities.Runtime`)*
- **Kind:** Scheduler work contributor.
- **Register:** `ActivitiesRuntimeFeature` registers it as an `IWorkflowSchedulerWorkHandler`.
- **Usage:** handles `ParentCompletionEvaluation` by reactivating the transient parent from its pinned snapshot and invoking `IRuntimeActivityChildCompletionHandler` for a completed child, or `IRuntimeActivityChildFaultHandler` for a faulted child (work items tagged `runtime.childFaulted`, #308). Each callback returns a `RuntimeStructuralContinuation` for the runtime to apply. For a faulted child whose parent does not implement `IRuntimeActivityChildFaultHandler` the handler no-ops, leaving the fault a blocking incident, unless an ancestor that implements `IRuntimeActivityDescendantFaultHandler` is in reach (spec 258 R-3), in which case the fault is also delivered there. It does not interpret workflow-level edges or load Design-owned authored workflow models.

### Delayed child schedules *(Activities Runtime — `Elsa.Activities.Runtime`, spec 261 R-7)*
- **Kind:** Staging rule shared by the structural evaluations; not an extension point of its own.
- **Usage:** the invoke, parent-completion and structural-callback (notification, intervention decision) evaluations call `RuntimeDelayedSchedules.Validate` on the staged child schedules, so a refused due time faults the evaluation with `runtime.delayed-schedule.too-far` or `runtime.delayed-schedule.unavailable` and commits none of its schedules. `SchedulerWorkItems.NewChildActivityScheduleWorkItems` stamps `runtime.scheduleNotBefore` on a child schedule whose due time is later than now and never lets a child inherit it through command metadata. The commit and delivery rules are in the [Workflows Runtime catalog](../../../Workflows/Runtime/Elsa.Workflows.Runtime/EXTENSION_POINTS.md) under `IRuntimeStructuralActivity`.

### `WorkflowNotifyParentActivitySchedulerWorkHandler` *(Activities Runtime — `Elsa.Activities.Runtime`)*
- **Kind:** Scheduler work contributor.
- **Register:** `ActivitiesRuntimeFeature` registers it as an `IWorkflowSchedulerWorkHandler`.
- **Usage:** handles `WorkflowExecutionCommandKind.NotifyParentActivity` (spec 126, seam C) by reactivating the target parent — the notifying child's committed parent — from its pinned snapshot and invoking `IRuntimeActivityChildNotificationHandler.OnChildNotifiedAsync`, applying the returned continuation and any staged seam-A subtree cancellations / child schedules / further parent notifications in one atomic checkpoint commit. A parent that does not implement the interface, or is no longer `Running`, silently acks the notification (late delivery is legal — a notifying child that has since completed or faulted still delivers). The notifying child keeps running throughout. Its `HandlerName` is a frozen wire value (persisted in scheduler poison/drain records). It does not interpret workflow-level edges or load Design-owned authored workflow models.

### `WorkflowInterventionDecisionSchedulerWorkHandler` *(Activities Runtime — `Elsa.Activities.Runtime`, spec 260 R-5)*
- **Kind:** Built-in scheduler work handler; not replaced by hosts.
- **Usage:** handles `WorkflowExecutionCommandKind.DeliverInterventionDecision`, the work item a `DecideIntervention/1` alteration checkpoint enqueues. It finds the requester's direct child on the path from the faulted activity, reactivates the requester from its pinned snapshot and invokes `IRuntimeActivityInterventionDecisionHandler.OnInterventionDecidedAsync`, then commits the continuation, child schedules, subtree cancellations and notifications in one checkpoint with `runtime.interventionDecisionProcessedWorkItemId` on the requester. A requester that is no longer `Running`, or that already processed the item, acks it without a callback. It shares `StructuralCallbackEvaluation` with `WorkflowNotifyParentActivitySchedulerWorkHandler`. Its `HandlerName` is a frozen wire value.

### `IRuntimeActivityInterventionDecisionHandler` *(Core — `Elsa.Workflows.Runtime.Core`, spec 260 R-5)*
- **Kind:** Engine-only opt-in structural callback.
- **Signature:** `OnInterventionDecidedAsync(IRuntimeActivityExecutionContext context, ActivityInterventionDecidedContext decision)` returns `ValueTask<RuntimeStructuralContinuation>`.
- **Usage:** a structural activity that offers decisions with `RequestChildFaultIntervention(incidentId, reason, metadata, decisions)` must implement it; it receives the operator's decision in its own evaluation and applies it by its own transition. It must accept any decision it offered while its wait stands and may ignore one for a wait it no longer has. The runtime never interprets the code. Known implementation: `CompensationScope` (`compensation.resolve.effect-absent`, `compensation.resolve.effect-accepted`, `compensation.abandon`).

### `ResumeTargetAttribute` *(Core — `Elsa.Activities.Runtime.Core`)*
- **Kind:** Declaration surface (activity author contract).
- **Signature:** `[ResumeTarget("stable-resume-target-id")]` on an activity handler method.
- **Usage:** declares a stable runtime resume target ID. Workflow compile/publish can copy the ID into a runtime executable artifact's resume-target table. Durable bookmarks store this ID, not the C# method name.
- **Related runtime seam:** `IBookmarkResumeResolver` in `Elsa.Workflows.Runtime.Core`.

### `ActivityAttribute` *(Core — `Elsa.Activities.Runtime.Core`)*
- **Kind:** Declaration surface (activity author contract).
- **Signature:** `[Activity(Icon = "Rocket" | "git-branch" | "asset:Package.Id/icons/name.svg" | "ext:slack")]` on an activity class.
- **Usage:** optional designer icon. CLR reconciliation copies a valid value onto an `elsa.activity-icon` design facet; the authoring catalog exposes it as `iconName`. Accepted forms are a lucide export or kebab name, `asset:<package>/<path>` for a static web asset in the extension package, or `ext:<name>` for a React icon registered on the Studio client via `registerActivityIcons`. An unknown, empty or unsafe value is ignored so the designer keeps its type/category fallback. The facet is presentation only and is excluded from the descriptor hash, so adding or changing an icon does not throw `ActivityVersionHashMismatchException`.
- **Related design seam:** `ActivityIconName` in `Elsa.Activities.Design.Core`; Studio `registerActivityIcons` in `@elsa-workflows/studio-sdk`.

### `TriggerActivityAttribute` *(Core — `Elsa.Activities.Runtime.Core`)*
- **Kind:** Declaration surface (activity author contract).
- **Signature:** `[TriggerActivity]` on an activity class that can start a workflow from an external stimulus.
- **Usage:** CLR reconciliation records the activity version as `Trigger`; publish-time compilation also reads the marker from the CLR construction descriptor so legacy catalog rows authored before the marker was persisted still compile into routable trigger nodes.
- **Related runtime seam:** `IActivityTriggerStimulusProvider` in `Elsa.Workflows.Runtime.Core`; a marked activity must have a provider contributed by its owning feature.

### `RefusesSecretBindingAttribute` *(Core — `Elsa.Activities.Runtime.Core`)*
- **Kind:** Declaration surface (activity author contract).
- **Signature:** `[RefusesSecretBinding("InputKey", SecretBindingRefusalReason.PersistedByActivity | FixedAtPublish | EchoedToOutput)]` on an activity class, once per input (`AllowMultiple`, inherited).
- **Usage:** an activity author must apply it to every input whose value the activity copies into its own persisted state (`PersistedByActivity`), that a publish-time reader needs as a literal (`FixedAtPublish`), or that the activity returns in its result, writes out of the workflow (for example to the console or an HTTP response) or copies into a fault (`EchoedToOutput`). Publication refuses a secret reference on such an input with `VF-ACT-012`, naming the node, the input and the reason. The marker is read by reflection over the activity's CLR type at publish and is never written into the activity catalog, so adding it changes no catalog hash.
- **Related runtime seam:** `SecretBindingDiagnostics` in `Elsa.Workflows.Runtime.Core` owns the `VF-ACT-012` message for each `SecretBindingRefusalReason`.

### `ActivityInputAttribute.Tier` *(Core — `Elsa.Activities.Runtime.Core`)*
- **Kind:** Declaration surface (activity author contract).
- **Signature:** `[ActivityInput(Tier = InputTier.Essential | Optional | Setting)]` on an activity input property. The three values are the only legal tiers. The property is a non-nullable enum (attribute parameters cannot be `InputTier?`); its CLR default `0` is not a defined member and means unset.
- **Usage:** optional designer disclosure group. CLR reconciliation copies a declared value onto `InputDefinition.Tier` as the camel-case string `essential`, `optional`, or `setting`. The authoring catalog exposes that string as `tier` on each input. Leave the property unset (or omit the JSON field) to store `null`; the client then applies its own default (today: show the first four inputs). JSON catalogs and the descriptor/version API set the same strings on `InputDefinition.Tier` (`ActivityInputTiers` in `Elsa.Activities.Design.Core`). An unknown stored string is dropped to `null` rather than echoed. The field does not change requiredness, browsability, or bindings. It is part of the descriptor hash: adding or changing a tier re-reconciles the stored version in place (same `(DefinitionId, Version)`) instead of throwing `ActivityVersionHashMismatchException`. Other content changes on that identity still throw. Shared engine properties (display name, commit strategy, incident strategy, and the like) are Studio-supplied settings and are not declared here.
- **Related design seam:** `InputDefinition.Tier` and `ActivityInputTiers` in `Elsa.Activities.Design.Core`; authoring catalog `ActivityInputDescriptorView.Tier`.

### `ActivityInputAttribute.IsSensitive` / `ActivityInputAttribute.IsCredential` *(Core — `Elsa.Activities.Runtime.Core`)*
- **Kind:** Declaration surface (activity author contract).
- **Signature:** `[ActivityInput(IsSensitive = true)]` or `[ActivityInput(IsCredential = true)]` on an activity input property. A credential is sensitive too.
- **Usage:** declares that every binding of the input is sensitive, or that the input holds a credential and accepts only a secret reference or no binding. CLR reconciliation copies the declaration into the input's `InputDefinition` (`IsSensitive`, `IsCredential`, each `true` or null) and refuses a credential declaration that could never be bound to a secret reference: one with a `DefaultValue`, one whose type is not `string`, one the type names in `[RefusesSecretBinding]`, and any on an `IRuntimeActivityCheckpointParticipant`. Publication compiles each binding's effective policy as the stricter of the declaration and the authored `ArgumentState.IsSensitive`, refuses an authored `IsSensitive: false` on a declared input with `VF-ACT-005`, and pins the declaration into the activity contract: the policy, and `ActivityInputContract.IsCredential`, an explicit flag that is never inferred from `RequiresEncryption` and is left out of the contract's serialized shape and fingerprint while false.
- **Related runtime seam:** `SecretBindingDiagnostics` in `Elsa.Workflows.Runtime.Core` owns the `VF-ACT-011` messages: an input whose effective policy requires encryption, which a credential declaration sets, accepts only a secret reference or no binding, so publication refuses a literal, an object, a value read, an expression or a declared default on it.

### `IActivityActivator` *(Activities Runtime — `Elsa.Activities.Runtime`)*
- **Kind:** Replacement activation boundary.
- **Signature:** `ActivateAsync(ActivityActivationRequest request, CancellationToken cancellationToken)` returns an async-disposable `ActivityActivationLease`.
- **Usage:** creates one fresh activity and owned service scope per invocation attempt, then hydrates plain annotated inputs from the committed snapshot. The shipped CLR implementation is `ClrActivityActivator` in `Elsa.Activities.Primitives`; it binds the owned scope to the partition of the scope it activates in, so services injected into the activity work in the execution's partition.
- **Secret-bound inputs:** `ActivityActivationRequest` carries the `WorkflowExecutionId` of the executing instance and the `ActivityExecutionId` being activated, and every caller sets both. For a strategy that hydrates inputs, `ActivityActivator` resolves each withheld secret reference through its `ActivitySecretInputResolver` collaborator (registered scoped by `ActivitiesRuntimeFeature`, with the partition accessor, the workflow execution state store and the registered `IRuntimeValueConversionExecutor` required and only `IRuntimeSecretResolver` (`Elsa.Workflows.Runtime.Core`) optional) for the execution's partition, after checking that the instance does not record a different tenant, registers the resolved value with `IRuntimeSecretMask` (`Elsa.Workflows.Runtime.Core`) under the request's `ActivityExecutionId`, converts it with the envelope's plan, and hydrates from a transient copy; the request's snapshot is never changed. The collaborator is a required constructor dependency of `ActivityActivator`, and the mask a required one of the collaborator; one composed without an `IRuntimeSecretResolver` refuses a secret input with the missing-resolver activation failure. See that contract's entry in the Workflows.Runtime catalog for the failure codes and the missing-resolver activation failure.
- **One secret resolver per host:** `ActivitiesRuntimeFeature` registers `RuntimeSecretResolverCompositionValidator` (`public sealed`), a CShells shell initializer in `LifecyclePhase.Prepare`, which reads the composed service collection and fails shell activation with `MultipleRuntimeSecretResolversException` (`Elsa.Workflows.Runtime.Core`), naming every registration, when it holds more than one non-keyed `IRuntimeSecretResolver`, in either registration order (framework §2.6.2: a replacement-contract conflict is detected at startup). It counts registrations and resolves none. A plain host that composes the runtime without CShells runs it only if it runs the registered shell initializers.
- **Masking at the fault boundaries:** the invoke, bookmark resume, parent completion and parent notification work handlers mask the failure text of the activity execution they handle with the scope's `IRuntimeSecretMask` (spec 188, FR-012), through `ActivityFaultMasking`: a recorded exception becomes `SecretMaskedException` while a value is registered for the execution (masked message, stack trace and inner exception chain; code and type name kept as they are), a returned `ActivityFault`'s message is masked once before `ActivityFaultProjection.ToNormalized` and its code, category and fault type are kept unmasked, and when a cancellation arm's disposal also failed, the aggregate it throws holds a masked copy of the cancellation (same token) and the masked disposal failures. With no disposal failure the cancellation is rethrown unchanged. Each releases the execution's values once it has recorded the outcome. `ActivitiesRuntimeFeature` also registers `RuntimeSecretMaskCompositionValidator` (`public sealed`), which fails shell activation with `MultipleRuntimeSecretMasksException` when the composed services hold more than one non-keyed `IRuntimeSecretMask`. See the Workflows.Runtime catalog's `IRuntimeSecretMask` entry for what is and is not masked.

### `IRuntimeStructuralActivity` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Engine-only structural execution protocol.
- **Signature:** `ValueTask<RuntimeStructuralContinuation> ExecuteStructureAsync(IRuntimeActivityExecutionContext context)`.
- **Usage:** implemented by composite activities that schedule and coordinate executable children. The runtime invokes this method instead of the ordinary `IActivity.ExecuteAsync` path, then applies exactly one immutable continuation decision: `Complete(outcome)`, `Defer`, `Faulted(fault)`, or `Cancel(reason)`. A terminal decision cannot also schedule children, and the initial `Defer` decision must schedule at least one child.

### `IRuntimeActivityChildCompletionHandler` / `IRuntimeActivityChildFaultHandler` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Engine-only structural re-evaluation protocols.
- **Signatures:** `OnChildCompletedAsync(ActivityChildCompletedContext context)` and `OnChildFaultedAsync(ActivityChildFaultedContext context)` each return `ValueTask<RuntimeStructuralContinuation>`.
- **Usage:** implemented by structural activities that own child completion or fault routing. The runtime invokes them only for parent-evaluation work after reconstructing the parent from the pinned executable artifact. A callback may return `Defer` while existing children are still running or after scheduling the next child; otherwise it returns one terminal continuation decision. A parent that does not implement the fault callback leaves the child's fault as a blocking incident.
- **Callback routing provenance:** completion, direct-fault and combined-outcome contexts expose immutable `ChildSchedulingMetadata` copied from the child's committed scheduling provenance. Descendant-fault contexts expose `ViaChildSchedulingMetadata` from the receiver's actual direct child, rather than from the faulted leaf or delivery command. Legacy context constructors remain available with empty metadata; direct callers must supply provenance explicitly to route an owned child.
- **Reporting metadata (spec 258):** the completion and child-fault work items an activity reports to its parent with carry the source work item's command metadata overlaid with the reporting activity's own scheduling provenance metadata. A structural activity that finishes from a child or notification evaluation therefore reports with what its parent stamped on it, not with what it stamped on its own children; a parent can route every child's outcome by the metadata it scheduled it with.
- **Child-subtree cancellation (spec 112):** during a callback the parent may also stage `RequestChildSubtreeCancellation(childActivityExecutionId, reason)` on the context for any of its live direct children. The runtime terminalizes the target's whole execution subtree to `Cancelled`/`ParentCancelled`, deletes its bookmarks/durable timers/queued scheduler work via `IActivityScopeCleanupStore`, and suppresses its non-terminal incidents — all inside the same checkpoint commit as the continuation. Honored with `Defer` and `Complete` only; a terminal target is skipped as a legal first-completion-wins race; unknown, non-child, or duplicate targets fault the evaluation.
- **Child-fault absorption (spec 115):** during a child-**fault** evaluation the parent may stage `RequestChildFaultAbsorption(incidentId, reason)` naming the evaluation's incident. The incident resolves with an internal `AbsorbFault` resolution outcome sourced from `StructuralFaultAbsorption`, and the faulted child's leftover subtree is reclaimed (live descendants `Cancelled`/`FaultAbsorbed`, resources cleaned, their other incidents suppressed) in the same commit as the continuation — the composite consumes the fault and keeps routing instead of re-faulting or leaving a blocking incident. Honored with `Defer`/`Complete`; at most one per evaluation; a wrong or missing incident id, a completion-evaluation staging, or a `Fault`/`Cancel` continuation faults the evaluation; an already-terminal incident skips as a legal redelivery race. Composes with spec-112 cancellations in the same evaluation. The request metadata is copied into the resolved outcome's metadata.
- **Child-fault intervention (spec 251):** during a child-**fault** evaluation the parent may stage `RequestChildFaultIntervention(incidentId, reason, metadata)` instead. The incident stays `Blocking` with a `WaitForIntervention` outcome from `StructuralIntervention` carrying the metadata, in the same commit as the parent's `Defer` continuation; no incident strategy acts on it, the run stays running, and the faulted child's subtree is left as it is for an operator's `RetryFaultedActivity/1`. At most one per evaluation, `Defer` only, never with absorption, and only for the evaluation's incident; misuse faults the evaluation. `ActivityChildFaultedContext.FaultCode`/`FaultCategory` carry the faulted child's committed fault code and category.

### `IRuntimeActivityDescendantFaultHandler` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Opt-in structural re-evaluation protocol (spec 258 R-3).
- **Signature:** `OnDescendantFaultedAsync(ActivityDescendantFaultedContext context)` returns `ValueTask<RuntimeStructuralContinuation>`.
- **Usage:** when a child faults under a composite that handles no child faults (Sequence, ForEach, While, For), that composite still suspends, and in the same checkpoint the runtime walks up from it and delivers the fault to the nearest ancestor implementing this interface, as a `CompleteActivity` child-fault evaluation marked `runtime.descendantFault`. The walk stops, and nothing is delivered, at a node that handles child faults (a Flowchart in between keeps today's suspend) and at an `elsa.graph-activity` boundary. Each node's fault handling is compiled into its metadata (`runtime.structuralFaultHandling`: `child` or `descendant`, absent otherwise), so the runtime decides without constructing ancestors. The context carries the faulted descendant's ids, incident, fault code and category, and the receiver's direct child it came through (`ViaChildActivityExecutionId`/`ViaChildExecutableNodeId`); the work item's command metadata carries that via child's scheduling provenance metadata. The receiver may absorb the fault, which cancels the **via child's** subtree, or request intervention, under the child-fault rules above. Combined fault-and-notification outcomes are not relayed. The delivery records `runtime.descendantFaultProcessedWorkItemId` on the faulted activity, beside the marker its direct parent set.

### `IRuntimeAcceptsRescheduledFaultedChild` *(Core — `Elsa.Workflows.Runtime.Core`, #3135)*
- **Kind:** Opt-in marker capability for structural parents; no members.
- **Usage:** a parent that keeps waiting for a child whose fault it was told about but did not consume implements it, so an operator's `RescheduleActivity/1` of that faulted child reaches it: the successor carries no parent-completion marker and its outcome arrives as that child's ordinary outcome. `ExecutableNodeCompiler` compiles it into node metadata (`runtime.acceptsRescheduledFaultedChild` = `true`, absent otherwise), and the reschedule preflight reads it from the pinned executable without constructing the parent. A faulted source whose parent deferred on its fault is refused with `ParentDoesNotAcceptRescheduledChild` when the parent's node lacks the capability. Any faulted source is refused with `SourceParentNotRunning` or `SourceAncestorNotRunning` while its parent or an ancestor is no longer running, and with `SourceFaultHandledByAncestor` when an ancestor already received its fault and deferred (spec 258 R-3). Only a newly compiled artifact carries the capability: node metadata is not part of the artifact hash, so republishing an unchanged definition reuses the stored artifact without it (as with `runtime.structuralFaultHandling`). A parent that absorbs child faults, or stops tracking a faulted child (a BPMN error boundary or late-fault guard), must not implement it.
- **Known implementations (shipped):** `Sequence` (its next step follows from the completed node alone) and `Parallel` (its join reads the durable branch states). Both are cross-domain contributions from their activity modules.

### `IRuntimeActivityChildNotificationHandler` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Engine-only structural re-evaluation protocol (spec 126, seam C — the child→parent counterpart of the parent→child seams above).
- **Signature:** `OnChildNotifiedAsync(IRuntimeActivityExecutionContext context, ActivityChildNotifiedContext notification)` returns `ValueTask<RuntimeStructuralContinuation>`.
- **Parent notification (spec 126):** a still-running structural child stages `RequestParentNotification(code, payload?)` on its own execution context during any of its evaluations (invoke, or a child-completion/child-fault evaluation of its own children). The notification commits atomically with the child's `Defer`/`Complete` state as a durable `NotifyParentActivity` work item and reaches — always and only — the child's committed parent (no target parameter; spoof-proof). A parent implementing this interface receives `OnChildNotifiedAsync` with the code, payload, and the notifying child's identity (aei, node, iteration id), and may return any continuation and stage seam-A subtree cancellations / child schedules exactly as in a child-completion evaluation (an interrupting consumer tears the notifying child down in the same commit; seam-B absorption stays child-fault-evaluation-only). The child keeps running throughout; a notification whose child has since completed or faulted still delivers, and only a non-`Running` (or non-implementing) parent acks it away. Staging from a root activity (no committed parent), an empty/oversized (>128) code, an oversized payload, or a `Cancel` continuation with staged notifications faults the evaluation deterministically. An intentional `Fault` with valid staged parent notifications uses the combined child-outcome protocol below; an exception or disposal failure discards the staging. One hop only — bubbling to a grandparent is the consumer's own recursion (it stages its own `RequestParentNotification`).
- **Ancestor notification (spec 237):** a structural activity may instead stage `RequestAncestorNotification(ancestorConsumerKey, code, payload?)` during an initial structural execution that completes it. The runtime walks the committed `ParentActivityExecutionId` chain to the **nearest** ancestor whose executable node descriptor has that consumer key and delivers the same `NotifyParentActivity` work item to it, so no composite in between sees or intercepts it. The item is enqueued ahead of the requester's own completion (and carries a lower sequence), so the ancestor evaluates it before the requester's direct parent sees the completion; a completed ancestor drops later items, so the first committed one wins. No matching ancestor faults the requester with `runtime.ancestor-notification.target-not-found`; staging one from any other evaluation, or with a `Defer`/`Fault`/`Cancel` continuation, faults the evaluation. A subtree cancellation staged by the ancestor in this evaluation commits atomically with its continuation. Used by the graph `Complete` activity to end its nearest `elsa.graph-activity` boundary.
- **Ancestor selector and via child (spec 258 R-1, R-2):** the `RequestAncestorNotification(RuntimeAncestorSelector selector, code, payload?)` overload addresses the nearest ancestor by `ConsumerKey` (what the string overload maps to) or by `ActivityTypeKey` (the executable node's activity type), optionally narrowed to one `AuthoredActivityId`. `StopAtGraphBoundary` ends the walk at a non-matching `elsa.graph-activity` ancestor; `Optional` sends nothing when no ancestor matches instead of faulting. It is also valid in a child-**completion** evaluation that completes the requester: the items commit with the completion and are enqueued ahead of its upward completion work item. A child-fault evaluation, and any continuation other than `Complete`, still fault the evaluation. `ActivityChildNotifiedContext.ViaChildActivityExecutionId`/`ViaChildExecutableNodeId` name the receiver's direct child on the path from the notifying activity (the notifying child itself for a direct notification).

### `IRuntimeActivityChildOutcomeHandler` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Opt-in structural re-evaluation protocol (spec 126 D6).
- **Signature:** `OnChildOutcomeAsync(ActivityChildOutcomeContext context)` returns `ValueTask<RuntimeStructuralContinuation>`.
- **Usage:** receives an intentional child fault and its ordered parent notifications in one callback. The runtime persists the masked fault, exact incident id and notifications in one versioned `RuntimeParentOutcome`, delivered as `CompleteActivity` / `ParentOutcomeEvaluation`. It does not invoke the legacy notification and fault callbacks sequentially. A fault-only parent retains its legacy fault callback; a parent with neither capability leaves the original blocking incident. A legacy notification consumer without this combined capability records `runtime.parent-outcome.handler-required` without invoking either callback.
- **Recovery:** a `Defer` or `Complete` callback may absorb the exact incident and reclaim descendants in the same checkpoint as its continuation and the exact processed-work marker. The child remains historically `Faulted`. A pending outcome holds automatic incident resolution while its committed parent remains `Running`; late delivery to a non-running parent is acknowledged. Exceptions, invalid staging and disposal failures discard the staged notifications. Upgrade readers before producers; see [spec 126 D6](../../../../../specs/126-runtime-child-parent-notification/spec.md) for the wire, retry and rollout contract.

### Existing structural consumers

These consumers do not yet implement the combined callback.

**Known implementations (shipped):**
- `Elsa.Activities.Flowchart` — `Flowchart` *(routes completed children through Flowchart-owned structure and child projection)*
- `Elsa.Activities.Sequence` — `Sequence` *(schedules child executable nodes in Sequence-owned slot order)*
- `Elsa.Activities.ControlFlow` — `Parallel` *(fork/join: counts branch completions toward the join threshold)* and the `If`/`Switch`/`For`/`ForEach`/`While`/`Do` control-flow composites

## Background leaf execution

- **Declaration:** `[BackgroundExecutionSafe]` pins type-level eligibility into `ActivityContract.SupportsBackgroundExecution`; authored `ActivityExecutionPlacement.Background` chooses this placement per node.
- **Composition:** `BackgroundActivitiesFeature` enables coordinator admission and optionally the tracked worker pump (`RunWorkers`). `BackgroundActivityWorkerOptions` bounds concurrency, polling, renewal and result size.
- **Worker host seam:** `BackgroundActivityWorker.ExecuteClaimAsync(PersistenceScope, BackgroundActivityWorkClaim, CancellationToken)` consumes a claim from `IBackgroundActivityWorkStore` in independently bound activation/renewal/receipt scopes. It validates the pinned implementation and typed result, and never directly changes native activity state.
- **Coordinator:** `WorkflowInvokeActivitySchedulerWorkHandler` commits admission, then later applies a ready result through native output/fault/completion handling. The checkpoint enricher includes receipt acceptance or cancellation in that same native commit.
- **Contract:** [Background activity execution](../../../../../docs/reference/background-activity-execution.md) describes eligibility, host composition, at-least-once physical effects, cancellation and rollback. No Runtime-to-Design dependency is introduced.

### `ActivityResumeValidating` *(Core — `Elsa.Workflows.Runtime.Core`, #2735)*

- **Kind:** Named validation event, published inline with Sequential delivery before bookmark trigger claim or CLR activation, including retry of an existing claim.
- **Register:** `AddEventHandler<ActivityResumeValidating, THandler>()`; scoped handlers run in registration order. Zero handlers preserves the ordinary path. Configured handlers require `IInlineEventPublisher`; missing event infrastructure fails closed. A handler skips activity families it does not own and validates without changing execution or delivery state.
- **Failure:** Conflicting data refuses. Temporary source unavailability throws `RuntimeSchedulerWorkUnavailableException` before the bookmark is consumed; the claim/fence stays governed by the existing scheduler. This gate is outside the activity callback fault conversion, so an infrastructure read does not become an authored activity fault.

### `IRuntimeActivityChildControlConsumer` *(Core — `Elsa.Workflows.Runtime.Core`, #2735)*

- **Kind:** Explicit structural callback capability, declared by the pinned consumer contract; no default interpretation.
- **Usage:** `OnChildControlAsync(RuntimeChildControlContext)` receives one contiguous exact-call prefix after immutable source authorization. Nonterminal command `DeliverChildControl=20` uses the frozen `WorkflowChildControlSchedulerWorkHandler` name. Terminal delivery enters through ordinary completed-child evaluation, including an empty terminal barrier. Future ordinals buffer without activation; consumed or identical pending duplicates acknowledge without repeating the callback. Conflicts refuse.
- **Atomicity:** The calling child's inbox and processed terminal-child receipt commit with the consumer's returned state and owed schedules/cancellations on Defer, Complete, intentional Fault and Cancel. Cancellation of the same call merges its cursor into the cancelled projection. Unexpected callback failure does not consume the prefix. `ActivityScopeCleanup` removes invocation-owned resources, preserving invocation projections and their inboxes. Whole-run deletion uses provider-atomic dependency refusal and sticky caller retirement proof; its finite controls are in [T043 evidence](../../../../../specs/1006-bpmn-library-adoption/evidence/control-inbox.md). Fresh-provider gap recovery remains a separate T045 gate.

### Activation claims and unavailable control dependencies (#2735)

Normal invocation and structural callback activation claims retain their scheduler source until the
final decision commits. A temporary control-source failure can retry before an accepted decision;
activation claims do not promise that callback code executes only once across such retries. The
existing consumed markers and fenced final commit prevent repeating accepted effects. Background
admission retains its separate atomic claim/publication path. Clean activation disposal preserves
the typed unavailable signal; disposal failure follows the ordinary fault path with both causes.

### Collection child-slot input metadata *(Core — `Elsa.Activities.Runtime.Core`)*

`ActivityChildSlotAttribute.ItemIdProperty` optionally names a stable collection-item identity and `ConditionProperty` names its structure-owned argument.
