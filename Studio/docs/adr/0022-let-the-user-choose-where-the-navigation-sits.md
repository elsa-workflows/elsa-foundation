# Let the user choose where the navigation sits

ADR 0021 made the top menubar part of the `workbench` layout, so the only way to get top navigation was to pick Schematic, and the only way to keep a sidebar was to avoid it. Navigation placement is now its own axis: the user picks **Theme default**, **Left** or **Top** in the theme menu, and the host publishes the result as `data-nav-mode` (`left` | `top`) on `<html>`, beside `data-theme-layout`. A theme's layout still supplies the default — `workbench` asks for `top`, every other layout for `left` — so Schematic looks exactly as it did until the user says otherwise, and the choice survives switching themes. This amends ADR 0021 on one point only: the menubar is no longer a property of a layout. A layout keeps everything else it decided (islands, density, the sheet, the designer's arrangement), and `data-theme-layout` and `useStudioThemeLayout()` are unchanged, so modules are unaffected and should not need to read the navigation mode.

The status bar travels with the navigation mode rather than staying with the workbench layout. It exists because a menubar has no sidebar footer, which is where backend status otherwise lives; tying it to `workbench` would leave top navigation in any other theme with no backend status at all, and leave Schematic with both a footer and a status bar when its navigation is on the left. The icon-rail collapse likewise applies only to left navigation and is ignored, not forgotten, under top.

The preference is device-local chrome state in `localStorage` (`elsa-studio-nav-mode`), like the sidebar collapse and the bottom-panel size, not a governed Studio Preference (ADR 0011). Where the navigation sits depends on the screen in front of the user, carries nothing an administrator needs to govern, and has to be readable before the backend is reachable, since the shell renders without one.

The menubar and status-bar rules are keyed only on `data-nav-mode` and never name a layout or a theme; layout and theme rules never name the navigation mode. That is the rule that keeps a 4 × 2 matrix from becoming eight designs. Where a layout's own rule assumes the sidebar is on the left, the remedy is to make that rule placement-agnostic, not to add a per-theme exception to the navigation rules. The editorial sheet is the one case so far: it omits its desk margin on the start side because the sidebar normally provides it. It now declares its inset once as `--shell-frame-inset` and takes `--shell-frame-inset-start` on that side, which is unset (0) beside a sidebar; the top mode sets it to the full inset of whatever layout is active, without naming one. A future layout that insets its frame follows the same two variables. Top navigation keeps the limits it had as part of the workbench layout: it applies at desktop widths only (below 1025px both modes share the responsive strip), a navigation too long for one row wraps to a second rather than collapsing into an overflow menu, and child navigation is a hover and `:focus-within` dropdown with no touch-specific affordance (the parent item remains a link to its own page).
