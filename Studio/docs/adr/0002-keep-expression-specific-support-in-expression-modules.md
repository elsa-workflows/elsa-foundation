# Keep expression-specific support in expression modules

Workflow authoring exposes Slots for activity property editing and supplies a language-neutral Expression Authoring Context, but expression-specific behavior belongs to expression modules. The backend side of each Expression Module is authoritative for its versioned, metadata-only Expression Symbol Catalog and applies Host Policy before returning symbols or resolving referenced Expression Value Shapes; authoring never evaluates expressions or retrieves live runtime values for code intelligence. Its client side combines that catalog with the shared context and projects both into the Expression Type's Expression Symbols. Editors provide immediate local syntax diagnostics, while the owning backend Expression Module provides authoritative semantic diagnostics asynchronously. Inline and expanded Expression Editor Surfaces share this tooling and differ only in presentation and interaction density; a compact surface preserves multiline expressions unchanged and routes their editing to the expanded surface. Expression Modules contribute their editors, metadata, validation diagnostics, Weaver Tools, and help instead of embedding language-specific behavior in the Workflows module. This keeps Workflows responsible for workflow visibility and typing facts, prevents frontend tooling from drifting from runtime capabilities, and allows expression languages to evolve independently.
