# Let a theme choose its layout

A Studio theme may choose a layout — `classic`, `floating`, `workbench` or `editorial` — alongside its palettes, typography and shape. The layout decides how the shell and the graph-authoring workbench are arranged: docked panels, floating islands over a full-bleed canvas, an IDE-like menubar with a status bar and dense panels, or a calm sheet where steps are added inline rather than from a toolbox. It is a property of the theme, not a separate user preference, because the signature themes were designed as a whole: Drift's soft islands, Schematic's workbench and Atelier's inline authoring are as much of each theme's identity as its colours. Any theme, including a custom one, may pick any layout.

The host publishes the layout as `data-theme-layout` on `<html>`, beside the mode attributes of ADR 0020, and modules adapt to it through two channels. Arrangement is CSS keyed on that attribute and styled only through tokens, so the token contract still governs every colour. Where a layout changes markup or behaviour — the editorial layout drops the activity toolbox and adds an Add step affordance; floating and editorial draw curved connections — modules read it with `useStudioThemeLayout()` from the SDK, which observes the same attribute. That keeps one source of truth: the attribute the host writes is what both CSS and code read, so a module never needs to know which theme is active.

A layout never removes a capability, only its presentation. The editorial designer keeps its contributed side panels, keeps the BPMN shape palette where events and gateways are authored, and routes Add step through the same activity picker and commit path as dragging a new activity off a port — so a step added inline is indistinguishable from one added any other way. Layouts apply at desktop widths only; below them the shell keeps its responsive strip. Layout rules for a surface ship with that surface (the workbench's rules load with the deferred designer), so a layout does not grow the landing paths every user pays for.
