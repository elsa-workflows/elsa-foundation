# Reporting a security vulnerability

Report suspected security vulnerabilities through [Elsa Foundation's private GitHub reporting page](https://github.com/elsa-workflows/elsa-foundation/security/advisories/new). Keep sensitive vulnerability details out of public issues, discussions, pull requests, and other public channels.

When safe and available, include the affected Elsa version and source commit SHA, the affected component and security impact, reproduction steps, and the smallest safe proof that demonstrates the issue. Do not include credentials, tokens, secrets, personal data, or customer data; redact them from logs and proof.

No response-time SLA is offered, and this guidance does not define supported versions. For ordinary contributor questions, use [Foundation Discussions Q&A](https://github.com/elsa-workflows/elsa-foundation/discussions/categories/q-a). For non-security bugs or feature requests, open a [Foundation issue](https://github.com/elsa-workflows/elsa-foundation/issues).

## Release dependency monitoring

Foundation release maintainers review the weekly [release inventory report](https://github.com/elsa-workflows/elsa-foundation/actions/workflows/release-monitor.yml). The report covers the latest published contributor compatibility checkpoint and designated stable Foundation releases. Each reviewed subject in [the release list](tools/release-monitor/supported.json) identifies a package archive or an image platform by digest. For a checkpoint, the source of membership is its published immutable image pair. Package computation examples and later evidence attachments do not add release members. A consuming application needs its own deployment inventory.

The monitor refreshes Grype's advisory database, verifies the publisher's signatures and inventories, and records its scanner version, database build time and checksum. A report lists matches by artifact digest, component and advisory. It distinguishes findings, no findings, unavailable historical evidence, missing expected inventories, and operational or verification errors. Findings are report-only. Missing or untrusted evidence for an expected modern release, an unregistered release, stale data or a scanner failure needs investigation. Each workflow attempt retains its report for 90 days. Maintainers can rerun the workflow on main after a transient failure.

For a new designated release, reconcile the full subject list with its published release manifest. Record each image's product, index, both Linux child digests, successful producer run ID and publisher commit. For a package, record the package ID, version, official feed service index and SHA-256 of the downloaded, attestable bytes. Use the Foundation publisher's signed package identity check. Incorporate the stable promotion and any registry-signing contract when the first stable release is cut under [#2085](https://github.com/elsa-workflows/elsa-foundation/issues/2085). A stable subject whose exact distributed bytes cannot yet be verified remains a coverage error. The October 2026 checkpoint remains listed as a historical coverage gap when a newer contributor checkpoint is designated. It predates published image SBOMs. Its immutable indexes are checked for absence of attached SPDX predicates and reported as unavailable.

Review new matches for the exact affected platform or package, upstream fixed versions and reachability. Record confirmed unaffected, under investigation or remediation pending in the maintainer's triage record, with rationale and a revisit condition. Coordinate the upstream update and retest, then record the first fixed digest. Route sensitive or actionable unpublished vulnerability details through the private reporting channel above. A clean scan covers the recorded database and subject only. This monitoring cadence does not change release support commitments or response times.
