# Elsa.Etl.RabbitMq

The RabbitMQ publisher for ETL message delivery with publisher confirms ([spec 1200](../../../../specs/1200-etl-rabbitmq-delivery/spec.md)), and the consumer for RabbitMQ ingestion with manual acknowledgements ([spec 1201](../../../../specs/1201-etl-rabbitmq-source/spec.md)). The feature registers one `IEtlRabbitMqPublisher` and one `IEtlRabbitMqConsumer` over RabbitMQ.Client 7; the ETL runtime owns the delivery protocol (one persistent JSON message per record, a stable message id and effect headers, and recording a batch only once every message is confirmed) and the ingestion protocol (a per-attempt snapshot, and acknowledging the messages only once the store has recorded it, so a message whose acknowledgement is lost is read again), and resolves this publisher and consumer for `EtlRuntimeFeature.RabbitMqBindings`.

- **Feature:** `EtlRabbitMq`, which depends on `EtlRuntime`. It registers no event handlers, contributes no fan-in events, and registers no tasks.
- **Publication:** each batch opens its own connection, without automatic recovery, and one channel with publisher confirmation tracking, so every publish completes only once the broker confirmed it. A `basic.return` (no queue matched the mandatory message) reports the batch as unroutable; a negative acknowledgement reports it as nacked, which the runtime retries.
- **Failures:** an unreachable broker, a closed connection or channel, an I/O error or a timeout is transient. Each confirm and protocol round trip waits at most 30 seconds, so a broker that blocks publishers under a disk or memory alarm yields the attempt instead of holding it until the alarm clears. A connection the broker blocks (it sends `connection.blocked`) ends its publication at once and is held, one per target, until the broker unblocks or drops it; while one is held, publications to that target yield without opening another, because a blocked broker stops reading and would never see further connections close. Any other publication that ends without the broker's answer, by the bound, a failure or the caller's cancellation, releases its connection in the background, because the client's abort and close wait out their own timeouts. Failed authentication and a channel or connection closed with access refused (403), not found (404), precondition failed (406), not allowed (530) or not implemented (540, such as `basic.get` on a stream queue) are rejections, except a 530 whose text, with the quoted virtual host and user names removed, reports a connection or channel limit (per virtual host, user or node), or a limit the broker could not query, and a 406 reporting that deliveries stayed unacknowledged past the broker's `consumer_timeout`, which are transient. Anything else is a rejection.
- **Targets:** `DescribeTarget` returns the host, the URI's port (or 5672, and 5671 for `amqps`, when it names none), the virtual host and the user name of the AMQP URI, never the password.
- **Consumption:** `RabbitMqEtlConsumer` opens a connection and one channel per preparation and takes messages with `basic.get`, without automatic acknowledgement, up to the run's maximum and byte bounds; a message that would not fit is rejected back to the queue at once. A run stops taking messages after five minutes, having taken at least one, well inside the broker's 30-minute default `consumer_timeout`; a channel the broker closes for that timeout (406 with "delivery acknowledgement … timed out") is transient. Its receipt acknowledges every taken message with one multiple acknowledgement, and disposing it unacknowledged closes the channel, so the broker requeues them.
