# Elsa.Rules.Persistence.EntityFrameworkCore

This project owns the EF Core mapping for Rules durable runs and their append-only receipt and fact history. The context depends on the Rules provider-neutral persistence contracts and shared EF persistence infrastructure; inference and receipt semantics remain in `Elsa.Rules.Runtime`.

Provider contexts and separate migration sets exist for SQLite, PostgreSQL, SQL Server and MySQL. Runtime registration accepts those providers; the host supplies its chosen engine package, while this package stays provider-neutral. Implementation availability is distinct from the real-engine qualification recorded in spec 999. Each provider uses its own live database clock for lease checks. MySQL uses utf8mb4 and large-text columns; ordinal comparisons and fixed-size indexed hashes preserve scope identity independently of database defaults.

The module declares its own migration-history identity and schema family, so migrations coexist with other EF modules. Schema creation goes through the shared migration lifecycle, never `EnsureCreated`. The nonpackable migration host lives in `Extensions/Rules/src/Tooling`; use `bash tools/rules/generate-rules-migrations.sh <MigrationName> [Sqlite|PostgreSql|SqlServer|MySql]` to add to one provider's retained history. SQLite remains the default for the command.

The run row keeps a lowercase digest as its indexed key and retains the complete framed identity for exact equality checks. `ModelRevision` tracks semantic progress; `ConcurrencyToken` is a provider-level optimistic concurrency token. Round receipts retain logical semantics separately from the first accepted physical attempt, and fact history uses an integer position rather than database atom collation.

The internal store implements the complete `IRuleRunStore` and `IRuleRunReader` contracts: admission/refusal/cancellation, database-time worker claim/reclaim/renew/release, bounded status/terminal/work/progress reads, separate receipt acceptance and consumption, and terminal delivery claim/read/acknowledgement. A compatible runtime validator verifies each complete new round; common retained receipts can be consumed and replayed without the old interpreter. Acceptance does not commit facts. Consumption atomically commits facts/history and the original transition confirmation, with terminal state and any frozen native delivery in the same transaction. Same-owner work reads refresh the semantic revision without renewing or mutating the lease.

`RulesRuntimeEntityFrameworkCoreFeature` registers the actual store and its reader, fresh per-transaction contexts, the shared provider binding/schema write gate and the normal migration lifecycle. It supports optional context pooling and separate work/delivery lease durations. The default reader follows the selected store; a store replacement must also implement `IRuleRunReader` or register a reader explicitly. Both defaults preserve earlier host replacements. No context or migration bypass becomes public API.

Progress cursors capture a model revision and validate the exact run/fingerprint and retained anchor. Pages are bounded to 256 entries in visibility-revision, kind and canonical-key order. Later facts are excluded and later consumption remains unconsumed in the captured view. Bounded ordering headers are selected first; receipt bodies are validated sequentially, not materialized as a multi-megabyte history.

Native delivery leases use their own fences and database-time expiry. Acknowledgement requires a registered durable-parent proof validator, full canonical result/address agreement and a fresh owner check before the atomic write. Missing proof remains retryable. Exact replay works after acknowledgement without rerunning the old native adapter. This store contract is exercised with synthetic proof validators; the actual native adapter and Sequence/Flowchart evidence remain pending. See [the persistence contract](../../../../../specs/999-durable-rules/contracts/persistence.md) for the authority, replay, sizing and transaction guarantees. SQLite tests do not establish separate-process, packaged-host or native-composite qualification.
