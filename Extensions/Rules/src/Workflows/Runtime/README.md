# Elsa.Rules.Workflows.Runtime

`RunRules` is an ordinary typed stateful activity. Its literal `Program` is compiled and pinned during publication by the sibling Design module. Initial facts and an optional round limit belong to each invocation. Execution reads the exact executable metadata and freezes the initial facts and resolved limit; it does not recompile the artifact, query design storage, or select the currently installed implementation. The model's later admission validator decides whether the frozen implementation is available.

The native checkpoint enricher captures both the actual bookmark and registration identity and records the frozen destination with the Start intent in one native checkpoint. Cancellation reuses that retained destination after trigger payload retirement. Only invocation and destination information belong in native state; Rules rounds, accepted receipts and result responsibility belong in the Rules persistence domain.

Resume validates the frozen destination, consumed typed receipt and delivery deduplication identity. A terminal payload must have the same canonical content as the Rules store's retained terminal result, including all facts. Succeeded and Refused return that complete result through normal native outcomes; Faulted and Cancelled use the existing native fault/cancellation transitions. Invalid nonpositive or excessive round limits have a native refusal path without constructing a Rules invocation or row.

The native intent handler validates the frozen route and retained invocation before admission or cancellation. An invalid round-limit intent stays pending until its exact native fault or terminal parent is proven; enqueue acknowledgement alone does not settle it.

An explicit temporary Rules-reader outage during resume retains the consumed trigger payload and source scheduler work. Bookmark resumes cross a durable queue boundary before execution; a live claim can be released with delayed visibility and retried through a fresh activation. A legacy queue without claim transitions preserves work but cannot provide that delay. Permanent identity/content mismatches and disposal failures retain their existing native fault behavior.

The terminal-delivery executor uses the existing Rules delivery lease, dispatches the frozen result through the ordinary bookmark dispatcher and inspects native state in fresh persistence scopes. It never treats enqueue or duplicate-command status as consumption. The acknowledgement validator independently rechecks the store-retained invocation and native outcome before the Rules store commits acknowledgement. Successful/refused results require full canonical content, an exact consumed receipt and the final completed resume attempt; a fault requires its exact terminal marker. A cancelled child alone is insufficient: the parent must be proven terminal. Missing proof or temporary native unavailability preserves the delivery for lease-expiry retry.

`RulesWorkflowsRuntimeFeature` depends on `RulesRuntime` and `WorkflowsRuntimeResumption`. It adds the checkpoint enricher, retry-until-acknowledged Start/Cancel handlers, delivery executor, inspector and default `IRuleDeliveryProofValidator`. The host supplies its normal workflow runtime and persistence composition, including bookmark dispatch, plus the Rules store/reader. The default proof validator is registered with `TryAdd`; a replacement must validate the complete trusted native outcome before the Rules store acknowledges delivery.

One delivery worker is shared by the shell's `IBackgroundTask` and the plain host's `IHostedService` registrations. It reuses the Rules-internal host lifecycle, while retaining its own concurrency limit (`MaxConcurrentDeliveries`, 1–64, default 2) and idle/error polling (`PollIntervalMilliseconds`, 10–60000, default 250). A plain host waits for application startup; shell Tasks startup already follows Prepare-phase migrations. Activation cancellation does not own an activated worker, and shutdown waits for its attempt loops. Each attempt uses a fresh service scope. The immutable options are captured during registration. Host registrations supplied before the feature can replace the default delivery proof validator; that implementation must honor the trusted validation contract.

Native state in the delivery-host tests is controlled; persisted-runtime results are recorded separately in the [native recovery checkpoint](../../../../../specs/999-durable-rules/evidence/native-recovery-acceptance-checkpoint.md), while package-backed REST journeys and restart readback are in the [package/Workbench checkpoint](../../../../../specs/999-durable-rules/evidence/package-workbench-checkpoint.md). The retained package upgrade proof is documented in the [retained-upgrade checkpoint](../../../../../specs/999-durable-rules/evidence/retained-upgrade-checkpoint.md). These receipts qualify the named same-machine journeys only: external effects remain at least once, the earlier full Workbench run's SQLite lock failure remains unexplained despite its isolated pass, and no multi-machine recovery claim is made.
