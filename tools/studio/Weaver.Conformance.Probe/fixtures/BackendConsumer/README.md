# Package-only backend application

`consumers.prepare_consumers(run)` replaces `__BACKEND_REFERENCES__` with exact PackageReferences from the retained candidate identities and `run.pin(...)` for public infrastructure. This baseline references both real provider adapters, the public Weaver/Identity/Preferences contracts and native authoring services. Neither resource package nor the protocol fixture is an application reference. The actual protocol archive is staged in the native runtime feed.

The application uses public CShells/Nuplane registration, native ModularityApi endpoints, normal Identity/SQLite module wiring and a separate application-owned SQLite/OpenIddict TokenDb. It contains no Workbench helpers or private management mapping. The root Nuplane ingress/coordinator/admin instances are shared into shell scopes. Native-loaded factories share the baseline provider implementation assemblies, in addition to Core/CShells contracts, so they replace the actual adapter's public factory interface.

Normal CLR catalog provisioning uses Workflows Publishing/API/EF and its declared runtime prerequisites, with the public artifact-only EF feature. ActivitiesRuntime registers real CLR contracts; the source-owned publisher creates their native catalog/template records. It does not publish or run a user workflow. The artifact feature's required private recovery signing key is generated by `configure_runtime` and retained across restarts; it is never put in provider traces or public receipts. The earlier catalog-only EF startup tenant failure remains unqualified evidence, with no global-access or tenant-guard override.

Root service validation has application-owned feature-store/reload guards that throw on use. The selected ModularityApi feature replaces these with its real shell-owned implementations. The generation observation requires those exact owning types, records their assembly identities and refuses any root guard invocation; these guards never simulate configuration reads or writes.

Preparation builds/publishes only. Before starting the published applications, the integration driver calls:

```python
configure_runtime(run, backend_url=owned_backend_origin,
                  studio_url=owned_studio_origin,
                  admin_username=private_username, admin_password=private_password,
                  provider="copilot", enroll=True)
```

This writes exact CORS/return origins, native initial-admin seed settings and the first-party issuer into private runtime JSON. No password is written to a public receipt. `enroll=True` authorizes the separate Studio protected store's enrollment. The backend uses a fresh ordinary Nuplane store, matching Foundation.Host/Workbench and its existing manifest contributor; it performs no enrollment or cutover. The only native credentials are obtained later through normal login cookie and `/_elsa/identity/token`; the consumer does not mint fixture tokens.

The ordinary shell selects `WeaverEffects` for its in-memory Weaver store. `configure_runtime` explicitly enables
all three fixture privilege classes under `Elsa:Weaver:Privileges`, matching Workbench's base policy without changing the
product's default-off options. Later operator controls can call
`configure_weaver_privileges(run, administrative=False, irrecoverable=False, activation=False)` (or another explicit
boolean combination). It atomically replaces only those host options in private backend JSON and preserves unrelated
configuration, credentials and the Studio file. It returns only the three booleans. A file update is not proof of a live
policy change: the driver must observe the actual sessionless bootstrap after the configuration provider reloads.

`select_protocol_profile(run, "copilot" | "anthropic")` changes only JSON after the driver has stopped its own backend. Exactly one actual provider feature and one corresponding native-loaded fixture feature are enabled; both adapter binaries remain unchanged. CommandFile and provider TraceFile are distinct absolute paths under the published private protocol directory. The driver atomically updates `{commandId,toolName,arguments}` before each new explicit request and keeps it fixed throughout review/continuation.

The application starts on its ordinary isolated store, using real blocking native startup reconciliation with explicit `FailHost`, then activates its selected shell through public `IShellRegistry.GetOrActivateAsync` before printing `WEAVER_BACKEND_CONSUMER_READY`. A listening HTTP server alone is not readiness. Permission-protected `POST /__qualification/reconcile` uses the actual shared Nuplane admin service. `GET /__qualification/generation` reports the actual shell identity, scoped context/tool contributors and shared contract identities/locations. These are fixture observations; native services still own feature configuration, installed-package state and effects. Studio retains its separately required coordinated protected-asset profile. The earlier coordinated-backend serving failure remains unqualified evidence; this recipe does not claim a general native-admission concurrency fix.

Private `Qualification:Principals` entries contain exactly `subject`, `tenant`, `username`, `password` and `exactDirectPermissions`. Before readiness, the optional bootstrap creates/checks actual password-backed users through the configured native Identity authority, then saves and rereads the exact direct grants. Each tenant gets a fresh persistence-bound shell scope. Existing disabled users, conflicting password identities, roles and membership grants are refused. Omit the array or use `[]` for a baseline without extra principals. Credentials remain private; the fixture emits no claims or tokens.

Private `Qualification:GrantProfiles` maps predeclared profile names to arrays of unique, concrete permission keys, without wildcards. Principal selections and profiles are captured before startup; request bodies and later configuration reloads cannot supply new subjects, tenants or grants. `GET /__qualification/principals/{index}/authority` requires native ModuleManagement read permission and returns the owning IAM revision and observed direct grants. `POST /__qualification/principals/{index}/grant-profile` requires native ModuleManagement manage permission and accepts exactly `{ "profile": "<predeclared name>", "revision": "<observed IAM revision>" }`. It passes that revision to the real revision-aware user store, refuses conflict, rereads the owning record and verifies the exact saved revision/grants with no role or membership extras. These admin-only fixture routes inspect/change only the configured Identity principal; they do not inspect another user's domain resources or issue authorization claims. After selecting a profile, the driver obtains a fresh cookie/token through normal login for the same subject/tenant; existing bearer claims are not refreshed by changing IAM data. Restoration is an explicit selection of a predeclared profile using a newly observed revision.

The optional `Qualification:DiagnosticGateDirectory` pauses immediately before startup and on a startup exception, before application disposal. It must be a fresh absolute directory below the owned content root. Each stage writes `<stage>.ready.json` and waits for `<stage>.release`, for at most 60 seconds. It records a typed admission failure without touching native locks; backend enrollment observation is absent for this ordinary profile. `configure_runtime` clears this setting; ordinary qualification runs with the gate off.

`run.profiles["backend"]` exposes `published`, `assembly`, `env`, `audit`, `runtimeFeed`, `nativeStore`, `appsettings`, `shells`, `commandFile` and `traceFiles` to the integration driver. `freeze_consumer_baseline` runs after real startup and before resource installation. `capture_consumer_after` runs after final restored observations; it refuses changed/missing common DLL/browser files. Build/lock/asset/audit receipts remain separate from runtime case acceptance.

An optional profile `contentRoot` selects an existing absolute runtime directory under the owned run root. Without it,
the published directory remains the content root and working directory as before. A separate content root must have no
symlink component under the run root and must not overlap any published binary directory. Initialize it from fresh,
normal owned configuration and key/state generation; these helpers never copy historical private configuration or
credentials. Generate database connections for that root (using `backend_features(content_root)` for the ordinary
feature settings), and point `runtimeFeed`, `nativeStore`, `appsettings`, `shells`, `commandFile` and `traceFiles` there.
`configure_runtime`, protocol selection, privilege configuration and durable-store selection write only that runtime
root, refusing linked configuration files. They do not relocate existing data or rewrite database connection strings.
The driver still launches the exact DLL from `published` with the same published working directory and passes the
selected root explicitly to ASP.NET. Process and restart receipts retain both paths, the executable hash and runtime
directory identity. Generation closeout rejects a changed executable or replaced runtime directory. Switching binary
profiles belongs only in `RestartableServer.restart(..., while_stopped=...)`, after normal closeout; each new generation
gets a separate receipt and empty runtime package caches. This capability alone is not upgrade qualification.

The current consumer references the normal `Elsa.Attention.Api` package, discovers its assembly and selects
`AttentionApi` plus `ModularityAttention` beside `ApiCapabilities` and `ModularityApi`. Attention keeps its ordinary
`attention:read` endpoint permission and the modularity contributor's ModuleManagement read permission. The normal
Identity administrator seed converges the catalog's permissions through its existing administrator role; no claims,
permission bypass or additional fixture grant is added here. Explicit non-admin qualification principals still need
their exact native grants and fresh normal login. Package/feature selection is not evidence of an available endpoint:
the native held/finalized matrix must observe the catalog, Attention and capabilities with the actual signed-in user.

The application also discovers `WeaverEntityFrameworkCore`, `WeaverEfEffects` and `Secrets` from their
existing package assemblies; the baseline shell does not select them. For the #3441 restart inventory,
`consumers.enable_durable_weaver_store(run, database, key)` removes common effects and selects EF effects alongside the store
and Secrets in runtime `shells.json` while the driver's own backend is stopped: SQLite over a new database file under the
run's output root, a private Secrets key that is never returned or retained in a receipt, and the store's 15-second lease.
The helper refuses missing/already-durable effects selection rather than composing two siblings or guessing a store.
The driver then starts a new generation of the same published application through `runtime.RestartableServer`. This
configuration does not itself establish schema finalization or feature availability; the real composed-host gates remain.

`QualificationWorkflowAuthority.cs` is a test-only host feature for the spec 1193 workflow-authorization-unavailable
inventory. No baseline shell selects it. `authorization_journeys.py` selects it through the ordinary native feature
apply with a private absolute `ModeFile`, and deselects it before anything later runs. It replaces the single
`IWorkflowDefinitionAuthorizer` registration with a wrapper that reads that file on every decision: `native` delegates to
the host's actual authorizer, `deny` refuses, and `throw` raises `WorkflowDefinitionAuthorizationException` with the
file's private `cause` canary as its inner cause. A missing, malformed or unknown mode is a fixture error, never a
decision. The seam supplies no other service and changes no product code.

`QualificationTenantActivity.cs` is a test-only host feature for the spec 1193 workflow-truth-seams inventory. No
baseline shell selects it. `truth_seam_journeys.py` selects it through the ordinary native feature apply with one
`Tenant`, and deselects it afterwards. The host's CLR-reconciled catalog is tenant-agnostic, so the seam replaces the
single `IActivityAuthoringCatalogReader` registration with a wrapper over the host's actual `ActivityAuthoringCatalogReader`
that adds one activity, first, for requests whose principal is in that tenant. The designer's catalog GET and Weaver's
`IActivityAuthoringCatalog` both read through it, so the driver compares each tenant's two answers. The seam supplies no
other service and changes no product code.

`QualificationBatchCatalog.cs` is a test-only host feature for the spec 1193 workflow-batch and workflow-explain
inventories. No baseline shell selects it. `batch_journeys.py` and `explain_journeys.py` each select it through the
ordinary native feature apply and deselect it afterwards. The
host's CLR-reconciled catalog has no credential input, no password-hinted input and no activity its availability policy
excludes, so the seam replaces the single `IActivityAuthoringCatalogReader` registration with a wrapper over the host's
actual `ActivityAuthoringCatalogReader` that adds activities first: one with a credential input (`apiKey`), one with a
password-hinted input (`passphrase`, neither sensitive nor a credential, which the designer masks only for its hint;
named so that no probe redactor rewrites it), and,
only when every entry is requested, one that is listed but not addable. The designer's catalog GET and Weaver's
`IActivityAuthoringCatalog` both read through it. The seam supplies no other service and changes no product code.

`QualificationLibraryResponses.cs` is a test-only host feature for the spec 1193 workflow-library inventory (SC-008). No
baseline shell selects it. `library_journeys.py` selects it through the ordinary native feature apply with a private
absolute `ModeFile` and `LogFile`, and deselects it afterwards. It replaces the single `IWorkflowLibraryCommands`
registration with a wrapper over the host's actual commands. With the mode `{"drop":"create-tag"}` (or `"save-view"`) a
keyed tag (or view) creation is committed by the actual library, then its response is lost once per operation key: the
wrapper appends `{kind, operationKey, committedId}` to the log and throws. The Weaver tool must then resolve the outcome by
rereading the key, and the driver proves exactly one tag (or view) exists with the logged identity. `{"drop":"none"}`
delegates every call unchanged. Only Weaver's library writes reach it: the HTTP library endpoints keep the built-in
decisions whatever `IWorkflowLibraryCommands` is installed, so the driver's own owner writes and reads never pass through
the seam. The seam changes no product code.

Spec 1193 slice F adds `Elsa.Weaver.Workflows.Runtime` to the packaged references and selects its shell feature
`WeaverWorkflowsRuntime` in the baseline shell, beside `WeaverWorkflows`; its assembly is listed with the
other Weaver assemblies. `inspection_journeys.py` adds no seam: it deselects each Weaver feature once, through the ordinary
native feature apply, for its deployment-shape control and selects it again.

`QualificationRunCapture.cs` is a test-only host feature for the spec 1193 workflow-run inventory (T045). No baseline shell
selects it. `run_journeys.py` selects it through the ordinary native feature apply before seeding its Runs, and deselects it
afterwards. The runtime's default `IRuntimePayloadCapturePolicy` never captures a sensitive payload, so a canary authored
into a sensitive input would never reach execution evidence. The seam replaces the single capture policy registration with
a wrapper over the host's actual policy that captures sensitive activity inputs as full payloads and delegates every other
decision unchanged; the canary is then in the run's value evidence, and Weaver's withholding of it is a real control. The
seam changes no product code.
