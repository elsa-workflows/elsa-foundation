# Toolbox renewals demo

This lane replaces the Notes/Workbench demonstration with packaged renewal activities and an authenticated Foundation.Host composition. Feature implementations and the demo identity bootstrap arrive through Nuplane. `Composition/Composition.csproj` is a preparation-only build graph; Foundation.Host never references it or its feature implementations.

The local React cockpit lives in `/Users/sipke/Documents/Codex/2026-10-03/modules-without-restart/demo-cockpit`, with a presentation alongside it. The cockpit owns its Foundation.Host processes on 5311/5312 and Studio on 5313. It refuses occupied ports and stops only child processes it started. It uses `prepare.py` through a fixed allowlist rather than accepting browser commands or filesystem paths.

Preparation builds source packages, derives their closure from NuGet's actual restored project graph, and copies external package archives from the restored cache. Both demo releases are staged before the presentation. Each host keeps a private bootstrap/baseline feed and an independent `.nuplane` install store. Both hosts also watch the same initially empty `artifacts/demo/renewals/feed` update directory, and both share the isolated renewal database. Source-built host EF metadata is shared rather than loaded a second time.

Nuplane `0.0.11-preview.95` resolves overlapping desired requests through explicit `Nuplane:DesiredState:SourcePriorities`: shared `renewal-demo-updates` has priority 0, private `renewal-demo-baseline` has priority 100, and `closure` has priority 200. Lower numbers win. While the shared directory is empty, only the private baseline feed requests those renewal packages. The baseline name sorts first alphabetically, so tests and the live rehearsal exercise the fixed priority policy rather than a naming workaround.

Release 1.0.0 is acquired through each host's private baseline feed. One release 1.1.0 publication then places both matching packages in the shared update directory. Both Nuplane stores install the update automatically, while both applications continue serving 1.0.0 until the presenter explicitly reloads each shell. Validate blocks host A's reload until its migration is applied; after A switches, host B continues serving 1.0.0 and the premium endpoint reports the pending schema state until B reloads. The cockpit reads each installed release from its independent store and each served release from the sample's actual release endpoint. HTTP 404 alone is never called a served release.

The API rehearsal uses bounded client waits: ordinary authenticated API requests default to 30 seconds, and module-management requests default to 10 minutes; an explicitly supplied per-request timeout overrides either default. After the one shared publication, it polls both independent Nuplane stores under one 15-minute deadline. Premium endpoint readiness gets a separate five-minute polling window. A timeout retains the last observed store or HTTP evidence and fails the rehearsal; it is never reported as installation or readiness success. The separate prepare subprocess deadline remains 15 minutes.

Automatic reconciliation remains disabled: rapid scheduled cycles can accumulate in its FIFO during busy baseline setup and delay an explicit request. The cockpit's single Publish action invokes authenticated reconciliation for both running hosts and waits for both installed package versions. Directory watching also remains enabled, so the shared package update reaches each store automatically without another host-specific publication.

Reset stops owned processes, refuses occupied demo ports, then archives the isolated runtime directories and database files. It retains prepared packages. Archived files can be recovered; reset never deletes user data or signals unrelated processes.
