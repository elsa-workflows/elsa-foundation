The owned acceptance runner builds normal Workbench/Studio from one clean commit and runs 16 primary cases followed by two diagnostics cases. Each phase stops all its processes before the next begins. Existing listeners and stores are never reused.

`diagnostics.py` creates a private enabled store per diagnostics project. Normal authenticated authoring, publishing, execution, task and diagnostics-settings APIs create the repeated/parallel/completed, structurally resolved fault, metadata-capture and 10,000-event fixtures. The browser uses bounded pages and indexed bookmark identities. It never downloads the long history to seed or sort the UI.

One supervised stop/preparation/restart is allowed per diagnostics project. `HistoryDiagnosticsFixture.cs` is compiled in a temporary directory against the freshly built normal Workbench binary closure; it adds no product project or endpoint. Before any store operation, both controllers validate the private root, live owner, nonce, source and non-linked existing database. A deliberate invalid-owner invocation must leave store byte hashes unchanged. The valid invocation uses ordinary IAM user/role/password ports, `IRuntimeHistoryRetentionStore.PurgeThroughAsync`, and the normal fenced checkpoint/CreateBookmark paths. It never constructs history events/batches or writes query rows. Requests containing the private demo passwords are deleted; public receipts contain identities, grants, boundaries and product hashes.

The passive-expiry fixture is explicitly a lower-level native legacy-continuation fixture. Its exact artifact is normally published, its native owner is created through a fenced checkpoint, and the ordinary CreateBookmark handler suspends that owner with an actual future expiry. No stock authorable expiry, activity activation, timeout or callback result is claimed. The source records must remain unchanged when a later normal inspection observes the expired handle.

After captured-store inspection, the supervisor closes that profile and creates a separate fresh store with `WorkflowsRuntimeHistory.Enabled=false` before admission. It does not flip the setting for existing captured runs. The diagnostics profile switch is a separate owned host/store, while the same-store restart guard remains one per project.

The two diagnostics projects cover desktop light and 320px dark, alongside the primary journey's four layout/theme combinations. Their receipts distinguish real cross-run exact-target refusal from the backend's independent cross-tenant/partition authorization controls. The existing value viewer is reused without changing its contracts or presentation. Assertions and fixture ports remain supporting evidence until the exact-source screenshots and experience receive independent inspection under [Studio UX acceptance](../../docs/contributing/studio-ux-acceptance.md).
