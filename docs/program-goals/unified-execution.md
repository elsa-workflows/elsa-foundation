## Owner clarification — 9 November 2026

[Decided in session after the independent architecture review](https://github.com/elsa-workflows/elsa-foundation/issues/2892#issuecomment-6737964981); the review itself is on [#3987](https://github.com/elsa-workflows/elsa-foundation/pull/3987#issuecomment-6734169085).

1. **What "unified execution" means.** A shared durable host with model-owned semantics, joined by a small set of ports. The ports are the shared abstraction: `IRuntimeExecutionProtocolDriver` with `IRuntimeExecutionProtocolSource`; `IRuntimeCheckpointCommitStore` with `RuntimeCheckpointCommit` and the fence (`IRuntimeExecutionOwnershipService`, `RuntimeExecutionFence`); `IBookmarkResumeDispatcher`; and the post-commit intent contracts (`IRuntimeCheckpointCommitEnricher`, `IRuntimePostCommitIntentHandler` and the durable-source variant). A neutral extracted kernel is not the destination and is not a deferred deliverable; it is out of scope.
2. **ETL and Rules are separately owned execution domains** ([ADR 0087](../adr/0087-etl-owns-its-execution-domain.md), [ADR 0088](../adr/0088-rules-owns-its-execution-domain.md)) with first-class native integration through those ports. They are not co-equal execution models of the shared host and are not migrated onto the host's lease, fence or outbox. The only convergence in scope is host plumbing with no state or contract change: the two polling loops onto `BackoffSweepWorkerTask` and one shared heartbeat helper, as a later leaf.
3. **The shared ports are locked only after a second real protocol driver exists.** Decisions durable runs ([ADR 0095](../adr/0095-decisions-owns-business-decision-semantics.md)) was named as that second driver; on 9 November the owner [withdrew it from the schedule](https://github.com/elsa-workflows/elsa-foundation/issues/2892#issuecomment-6739699681) because durable Decisions runs have no concrete requirement and no wait state. Locking means PublicAPI analyzer opt-in for the projects that declare the ports, not a redesign; the opt-in itself (#4008) proceeds as a surface declaration, and the ports stay unlocked until a second real driver exists.
4. **Priority order for the remaining work** (as [revised on 9 November](https://github.com/elsa-workflows/elsa-foundation/issues/2892#issuecomment-6739699681)): native and BPMN journeys first; ETL and Rules native-parent restart witnesses; the PublicAPI opt-in; Agents native collaboration; ETL connectors last and only from the approved list below. Existing deferrals stand.
5. **Working method tightened:** see [Working method](#working-method).

## Approved scope and boundaries

- Keep the existing EF checkpoint/outbox authority. The shared abstraction is the set of ports named in the owner clarification; lock them only after a second real protocol driver exists (Decisions is [no longer scheduled](https://github.com/elsa-workflows/elsa-foundation/issues/2892#issuecomment-6739699681) as that driver), and never extract a neutral kernel. Actors address whole executions, not every activity or record.
- BPMN foundation APIs: task claim/completion, external work, correlation, timers, incidents/retry, cancellation and inspection. Arbitrary token alteration, live-instance migration and a full operator console are deferred, not demonstrated.
- ETL connectors: CSV/JSON Lines files; paginated JSON HTTP ingestion and JSON delivery; PostgreSQL and SQL Server snapshot/watermark reads and transactional keyed writes; RabbitMQ JSON with manual acknowledgement and publisher confirms. Include local mapping, filtering, validation, routing and lookups. Log CDC, distributed shuffle, windows/stream joins and general analytics are deferred.
- ETL uses partition cursors, bounded batches, byte limits and durable admission budgets. Lease expiry does not prove physical memory reclamation or worker shutdown. External effects remain at least once unless destination guarantees are verified.
- Agent delivery includes typed routes/rounds, scoped memory/knowledge/tool bindings, durable accepted decisions, exact authorized tool approval, budgets before dispatch and deterministic/provider-protocol tests. Live model smoke tests are opt-in; no unexecuted live behavior claim.
- Preserve existing definitions and saved executions with explicit versioning. Rollback stops new capability admission while retaining readers/workers for accepted instances.
- Complete the existing presentation's offline/direct-file, keyboard, reduced-motion and responsive checks through an authorized browser harness.

## Follow-up after current delivery: durable task runner

[Owner intent recorded on 20 October 2026](https://github.com/elsa-workflows/elsa-foundation/issues/2892#issuecomment-6299076556):
discuss a horizontally scalable durable task runner after this program is delivered. This is outside the current
acceptance and active implementation queue. Preserve durable work acceptance separately from dispatch eligibility;
distinguish pausing a workflow's jobs on a shared queue from pausing the entire queue, and define what happens to
already running work. A pause must not imply rollback of external effects or proof of worker termination.

Evaluate an out-of-the-box runner and third-party adapters against those semantics before choosing a provider or
stabilizing a public contract. Keep actor placement separate from computational work. Current ETL qualification
does not establish workflow/queue pause support; no new runner implementation lane is authorized by this note.

The finite ETL worker keeps durable admission, fenced work claims and terminal delivery separate. Its private
polling loop can later be replaced without selecting a runner framework now. Future pause design must explicitly
decide whether completed results may advance a paused workflow, and enforce eligibility durably at the relevant
claim/continuation boundary. Preserve pending results and proof-before-acknowledgement; process-local worker
capacity is not a distributed per-workflow in-flight limit.

A candidate pause contract is to stop issuing new dispatch permits after the durable pause commits,
while previously permitted work counts as in flight. Intake and receipt retention remain available;
whether those receipts may advance the workflow is a separate continuation policy. Workflow-scoped
eligibility must work on shared queues without requiring one physical queue per workflow. Evaluate
provider adapters against these semantics; do not equate stopping a host polling loop with a durable
pause guarantee. These are follow-up design criteria, not implemented capabilities.

Define how pause affects retry deadlines and timers, including permitted work that has not physically
started. Current bounded HTTP attempts use absolute deadlines; a future workflow pause must not silently
extend an already-issued request timeout or treat a lease expiry as proof of termination.

## Working method

One active implementation leaf, one integration lane and a small prepared successor queue; no parallel workers or supervisors. Reuse matching PRs and honor claims. Use a concise contract for substantial behavior, executable acceptance tests, focused changes, bounded self-review under the owner’s standing authorization, CI/maps and post-merge evidence. Review is independent lenses on the exact diff with findings recorded as PR comments; it does not create an independent-approval gate. Evidence is the PR comment and CI artifacts, never private manifests or hash receipts. Do not create a parallel backlog in this file or duplicate existing native proofs. Progressive elaboration follows real integrations.

BPMN library changes, refactoring, upgrades and necessary releases are explicitly authorized. Use the relevant GitHub App identity and normal review/publication gates. This authority does not extend to unrelated releases/deployments, permission changes, live model costs or overriding active claims.
