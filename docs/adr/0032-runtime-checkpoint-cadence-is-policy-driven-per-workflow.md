# Runtime Checkpoint Cadence Is Policy-Driven Per Workflow

Status: accepted (2026-07-20; ratified with orchestrator approval. Resolves all in-ADR open questions — R1 contract-level SideEffectProfile with fail-safe External default, R2 marker-conditional pre-activation flush (spec-095 FR-019 amendment ships with WU-marker), R3 cadence/inspection-granularity read-model projection, R4 ActivityCancelled confirmed mandatory, R5 per-workflow authored cadence over host default — see Ratification resolutions and the sequenced Follow-up.)

Runtime checkpoint durability will be **policy-driven, not per-activity-mandatory**. Checkpoints stay *mandatory* only at **semantic boundaries** — suspend/bookmark, external side-effect, workflow finish/fault/cancel, and the recovery and inspection-integrity points — and become **relaxable** between those boundaries, where a configurable cadence ("commit every N activities / every T milliseconds") decides whether an intermediate checkpoint is flushed immediately, deferred, or skipped. Recovery is replay from the last committed checkpoint; the existing per-work-item idempotency keys make the redelivered span safe. Cadence is **configurable per workflow (or per section)**, because for long-running human-in-the-loop workflows per-activity durability is often the right default, while hot loops and compute pipelines want a relaxed cadence. This is the second of two independent dials on the runtime's per-activity cost; the first is burst execution ([ADR 0031](0031-runtime-burst-execution-sticky-single-writer-drain-with-in-process-fast-path.md)). It extends the checkpoint-commit contract ([ADR 0020](0020-runtime-checkpoint-commit-post-commit-work.md)) and is orthogonal to the pipeline spine ([ADR 0029](0029-runtime-execution-flows-through-the-pipelines.md)).

**The problem this fixes.** The checkpoint model is already designed for policy-driven cadence — `RuntimeCheckpoint`'s own summary reads "Named runtime boundary describing what changed. **Persistence policy decides when it is flushed**" (`src/Elsa/Workflows/Runtime/Core/Models/RuntimeCheckpoint.cs`), and the decision type already carries three modes: `RuntimeCheckpointPersistenceMode.{Immediate, Deferred, Skip}`. But the *only* registered policy is `ImmediateRuntimeCheckpointPersistencePolicy`, whose `DecideAsync` returns `Immediate` unconditionally. So in practice every checkpoint flushes immediately, and the handlers reinforce this by stamping their completion checkpoints `CheckpointRequirement = Mandatory` (the commit builders in `WorkflowInvokeActivitySchedulerWorkHandler` and `WorkflowParentActivityCompletionSchedulerWorkHandler`, and `ActivityFaultIncidentRecorder`). `RuntimeCheckpointCommitter.CommitAsync` then enforces that a `Mandatory` checkpoint *cannot* be skipped (`IsMandatoryCheckpoint` → `throw`). The net effect: the `Deferred` mode is defined but unreachable, and durability cadence is hard-wired to per-activity-immediate. That is the correct default for durability-critical workflows and a large, unavoidable cost for hot loops — the same cost [ADR 0031](0031-runtime-burst-execution-sticky-single-writer-drain-with-in-process-fast-path.md) quantifies (1–3 mandatory commits per activity). Cadence and burst are complementary: burst removes the *hop* cost, cadence removes the *commit* cost; neither subsumes the other.

**Semantic-boundary taxonomy — which checkpoints are inherently mandatory versus relaxable.** Grounding this in the actual names (`RuntimeCheckpointNames`, `src/Elsa/Workflows/Runtime/Core/Constants/RuntimeCheckpointNames.cs`), the boundary classes are:

- **Inherently mandatory — externally observable or recovery-defining. Never relaxable.**
  - `WorkflowSuspended`, `BookmarkCreated`, `BookmarkConsumed`, `ActivitySuspended` — the workflow is about to stop executing and wait for the outside world; the durable record *is* the resume point. Skipping it means a resume has nothing to resume from.
  - `WorkflowCompleted`, `WorkflowFaulted`, `WorkflowCancelled` — terminal status is externally observable (queries, siblings stop draining on it per the drainer's `#293` terminal check) and must be durable exactly once.
  - `IncidentRecorded` — fault/incident evidence; already stamped mandatory by `ActivityFaultIncidentRecorder`, and relaxing it would lose the diagnostic record of a failure.
  - `DurableValueCaptured` when it accompanies an **external side-effect** — a value published for another party (an emitted event, an external reference other systems read) must be durable before the effect is observable.
  - `PostCommitIntentRecorded` — the outbox continuation ([ADR 0020](0020-runtime-checkpoint-commit-post-commit-work.md)); if post-commit work is folded into a checkpoint, that checkpoint inherits the mandatory requirement, because dropping it silently drops continuation work (the committer already fails a `Skip` that carries post-commit intents: `RuntimeCheckpointCommitFailureCodes.SkipHasPostCommitWork`).

- **Relaxable — intra-run progress markers with no external observer between boundaries.**
  - `ActivityScheduled`, `ActivityStarted`, `ActivityCompleted` — per-activity progress. Between two mandatory boundaries these exist to shorten replay, not to define correctness: if the run crashes, replay from the previous mandatory checkpoint re-derives them. This is the bulk of the hot-loop cost.
  - `ActivityInspectionCaptured` — currently stamped mandatory to keep per-activity inspection evidence exact ([ADR 0001 checkpoint-gated inspection](0001-checkpoint-gated-activity-execution-inspection.md)). This is the **primary tension**: relaxing cadence necessarily coarsens inspection granularity between boundaries. The policy must treat inspection fidelity as a *configured* property (see per-workflow configurability), not a silent casualty.
  - `WorkflowStarted`, `ActivityRecovered` — start/recovery markers; recoverable by replay.
  - `ActivityCancelled` — the ADR provisionally placed this as relaxable, but ratification **confirms it MANDATORY** (see [Ratification resolutions](#ratification-resolutions), R4): the shipped `ActivityCancellationCheckpointService` stamps it `Mandatory` and atomically schedules workflow cancellation, so an authored cancellation is externally consequential (it terminates the surrounding run) and is exactly the compensation-hook case that belongs in the mandatory set. It is already in the shipped `MandatoryFlushCheckpointNames`.

The rule of thumb the policy encodes: **a checkpoint is mandatory iff skipping it would make a later resume, a terminal-status query, an external side-effect, an outbox continuation, or a fault record incorrect or unobservable.** Everything else is a replay-shortening progress marker and is a candidate for deferral.

**Policy surface — extend the existing seam, add a cadence-aware policy.** The seam is already the right shape and should **not** be replaced: `IRuntimeCheckpointPersistencePolicy.DecideAsync(RuntimeCheckpoint, …)` returns a `RuntimeCheckpointPersistenceDecision(Mode, Reason)`, the committer already honours all three modes, and `Mandatory` metadata already overrides any attempt to skip. The concrete recommendation, after reading the seam:

1. **Add a `CadenceRuntimeCheckpointPersistencePolicy`** implementing the existing `IRuntimeCheckpointPersistencePolicy`. It reads the checkpoint's `Name` and `Metadata` (specifically `RuntimeMetadataKeys.CheckpointRequirement`): if `Mandatory`, return `Immediate` (never override a mandatory boundary — the committer would throw anyway, and the policy should not even try). Otherwise consult the configured cadence and return `Immediate`, `Deferred`, or `Skip` for the relaxable classes above.
2. **Keep `Deferred` distinct from `Skip`.** `Skip` means *never persist this checkpoint's state* (the committer already forbids skipping a checkpoint that carries post-commit work). `Deferred` means *do not flush now; fold this checkpoint's state into the next flushed commit* — a coalesced write that preserves the state changes but batches the I/O. `Deferred` is the mode hot loops want (progress is retained, just written in batches); `Skip` is for truly disposable markers. Making `Deferred` reachable is the core new behavior, and it requires the committer/store to accumulate deferred state changes and fold them into the next `Immediate` commit — the same atomic-fold mechanism already used for post-commit intents and durable-value write-back in `RuntimeCheckpointCommitter.CommitAsync`.
3. **Do not weaken the mandatory guardrail.** `IsMandatoryCheckpoint` stays; the cadence policy operates strictly *below* it. This keeps the safety property that a semantic boundary can never be relaxed by misconfiguration.

A new interface is *not* recommended — the existing `IRuntimeCheckpointPersistencePolicy` is exactly the decision seam, and adding a second contract would fragment it. The only new type is the cadence-aware implementation plus its configuration. **This recommendation has since shipped:** the cadence-aware policy landed as `CoalescingRuntimeCheckpointPersistencePolicy` (E3-6/RT-10) with `RuntimeCheckpointFold` making `Deferred` reachable and the `WorkflowsRuntimeCheckpointPersistence` shell feature selecting it — so points 1–3 above describe live code, and the [Ratification resolutions](#ratification-resolutions) refine it (the marker-conditional `ActivityAttemptClaimed` decision of R2 is the one behavioral change to the shipped policy).

**Replay and recovery semantics — what redelivery means for side-effecting activities.** With relaxed cadence, recovery replays the span of activities executed since the last *flushed* checkpoint. That span is re-dispatched from the durable queue, and safety rests on the `IdempotencyKey` carried on every `RuntimeSchedulerWorkItem` and command envelope ([ADR 0031](0031-runtime-burst-execution-sticky-single-writer-drain-with-in-process-fast-path.md)): a redelivered work item is recognizable, and a handler that has already produced a committed effect can no-op (the invoke handler already short-circuits `if (state.Status == ActivityExecutionStatus.Completed)`). The load-bearing constraint is therefore: **any activity with an externally observable side-effect must sit behind a mandatory checkpoint boundary** so its effect is durable-once and never re-run on replay. Pure/deterministic activities (compute, variable transforms, in-workflow routing) are freely replayable and are exactly the ones a relaxed cadence targets. This makes the taxonomy above not just an optimization classification but a *correctness* classification: the mandatory set is precisely the set whose re-execution or loss would be observable. The runtime does not yet have a general "this activity performs an external side-effect" marker; the cadence policy needs one so it can force a mandatory boundary around side-effecting activities rather than relying on authors to configure cadence correctly. This was the ratification blocker; it is now **resolved** — a pinned-contract `SideEffectProfile` flag with a fail-safe `External` default (see [Ratification resolutions](#ratification-resolutions), R1). Until a workflow's activities are marked, an unmarked activity is treated as side-effecting and its boundary stays mandatory, so a relaxed cadence degrades to extra durability, never to data corruption.

**Per-workflow (and per-section) configurability.** Cadence is not a global switch. A long-running approval workflow that waits days between human steps should keep per-activity `Immediate` durability (the durability *is* the product, and the cost is negligible against the wait); a nightly compute pipeline over a hot loop should relax to "commit every N activities / T ms." The policy therefore resolves cadence from configuration keyed by workflow (and, where the executable exposes it, by section/region of the graph — e.g. a loop body relaxed while the surrounding orchestration stays immediate). The `RuntimeCheckpoint` already carries enough context to resolve this (`WorkflowExecutionId`, `Name`, `Metadata` including executable-artifact identity and node id), so the cadence-aware policy can look up per-workflow configuration without a new carrier. The default cadence remains **per-activity immediate** — the current, safe behavior — so relaxed cadence is strictly opt-in per workflow.

**Interaction with burst execution ([ADR 0031](0031-runtime-burst-execution-sticky-single-writer-drain-with-in-process-fast-path.md)).** The two dials compose cleanly, and the **burst boundary is a natural checkpoint boundary**: a burst drains a workflow's ready work in-process and ends when the queue empties, the workflow suspends, or it reaches terminal status — every one of those is already a mandatory semantic boundary. So the ideal cadence for a bursting hot loop is "defer intermediate `ActivityCompleted` checkpoints, flush at the burst boundary," which turns N per-activity commits into one coalesced commit at burst end while keeping the resume point exactly at the boundary the burst already stops on. Burst removes the per-hop JSON/scope cost; cadence removes the per-hop commit cost; together they approach Elsa-3 burst throughput while the last-boundary checkpoint preserves crash recovery. Neither depends on the other: cadence works without burst (batched commits on the hop-by-hop durable path), and burst works without cadence (fast hops, still per-activity commits).

**Constitution alignment.** The cadence policy is entirely Runtime-owned, reads only runtime state (the checkpoint, its metadata, per-workflow configuration) and the pinned executable identity, and introduces no `Elsa.Workflows.Design.*` dependency, so §E2.2 (no Runtime→Design dependency) and §E2.6 (artifact-only runtime) are preserved. No new constitution gate is required. If the team wants "checkpoint durability is policy-driven with a fixed mandatory semantic-boundary set" pinned as a durable rule, that single item routes through [Constitution Readiness](../program-goals/constitution-readiness.md); this ADR does not depend on it.

**Consequences.** Hot loops and compute pipelines can trade fine-grained durability for throughput by opting into a relaxed cadence, while durability-critical and human-in-the-loop workflows keep per-activity immediacy as the default; the `Deferred` mode that already exists in the model becomes reachable. The costs: (1) **inspection granularity coarsens** under relaxed cadence — per-activity inspection evidence between boundaries is no longer guaranteed exact, so inspection fidelity becomes a configured trade-off the UI/observability layer must surface, not assume ([ADR 0001](0001-checkpoint-gated-activity-execution-inspection.md)); (2) **replay re-executes a wider span**, so the side-effect-behind-a-boundary rule becomes a hard correctness obligation, and mis-relaxing cadence around a side-effecting activity is a data-integrity bug — this is why the side-effect marker was a ratification blocker for unattended use (now resolved, R1); (3) the committer/store must implement deferred-state accumulation and atomic fold-forward into the next flushed commit, extending the fold mechanism [ADR 0020](0020-runtime-checkpoint-commit-post-commit-work.md) established — **this is now substantially built.** The cadence-aware policy this ADR proposed as `CadenceRuntimeCheckpointPersistencePolicy` shipped as `CoalescingRuntimeCheckpointPersistencePolicy` (`src/Elsa/Workflows/Runtime/Services/Coalescing/CoalescingRuntimeCheckpointPersistencePolicy.cs`), selected by the `WorkflowsRuntimeCheckpointPersistenceFeature` shell feature (`Immediate` default vs `Coalesced`, with `MaxSegmentCheckpoints` default 50); `Deferred` is reachable, `RuntimeCheckpointFold.Fold` collapses buffered change-sets to last-writer-per-`StateId` and folds them into one atomic commit at a flush boundary (`RuntimeCoalescingSession` owns the working set, the whole runtime store stack is decorated to pass through byte-for-byte when no session is active). The resolutions below are therefore refinements on a live mechanism, not greenfield design. The default-immediate behavior is unchanged, so nothing regresses until a workflow (or its host) opts in.

**Alternatives considered.** *Keep per-activity immediate checkpointing everywhere (do nothing)* was rejected for the same reason as in [ADR 0031](0031-runtime-burst-execution-sticky-single-writer-drain-with-in-process-fast-path.md): the per-activity commit cost is an unacceptable hot-loop tax at GA, and the model already anticipates cadence (`Deferred` mode, "policy decides when it is flushed") — leaving that seam inert is a false affordance of the same class [ADR 0029](0029-runtime-execution-flows-through-the-pipelines.md) fixed for the pipeline. *A global cadence switch* was rejected: the right cadence is workflow-shaped (human-in-the-loop wants immediate, hot loops want relaxed), and a global setting forces one to subsidize the other. *Replace `IRuntimeCheckpointPersistencePolicy` with a new seam* was rejected: the existing interface already returns the exact decision (`Immediate/Deferred/Skip` + reason) and the committer already honours it with a mandatory-override guard; a new seam would fragment a correct contract. *Drop the mandatory-checkpoint concept and let the policy decide everything* was rejected: the mandatory set encodes correctness (resume points, terminal status, external effects, outbox), not preference, and must remain non-relaxable by any configuration. *Make cadence a burst-only feature* was rejected: cadence has independent value on the hop-by-hop durable path (batched commits without burst affinity), and coupling it to burst would deny that benefit to workflows that never form a burst.

## Ratification resolutions

These resolutions close the three open questions flagged above and were folded in at acceptance (mirroring how [ADR 0031](0031-runtime-burst-execution-sticky-single-writer-drain-with-in-process-fast-path.md) folded its two open questions into an accepted status). They land against a *live* mechanism: the coalescing policy, session, fold, decorated stores, and the `WorkflowsRuntimeCheckpointPersistence` shell feature already exist under `src/Elsa/Workflows/Runtime/Services/Coalescing/` and `.../Api/Coalescing/`. The remaining design surface is the side-effect marker, the pre-activation-flush relaxation it unlocks, the inspection-fidelity read-model contract, and the per-workflow authoring carrier.

**R1 — the external side-effect marker (the ratification blocker). Resolved: a contract-level flag, source-of-truth on the pinned contract, transported as checkpoint metadata; fail-safe default `External`.** Add a `SideEffectProfile { External, ReplaySafe }` to `ActivityContract` (`src/Elsa/Activities/Runtime/Core/Models/ActivityContract.cs`) — the immutable, fingerprinted contract already pinned into the executable at publish and read by the runtime without reflection, which is exactly the artifact-only-runtime discipline (§E2.6) and the publish-time contract gate (PR #785) the runtime already trusts. The activity author declares it (attribute or contract-builder call), it is compiled into the executable and covered by the contract fingerprint (so a profile change is a contract-version change, not a silent mutation). Candidate (b), a pure runtime checkpoint-reason discriminator, was rejected: it throws away the author's design-time knowledge and forces the policy to re-derive intent per checkpoint from heuristics. The chosen shape is a disciplined variant of the hybrid (c): the **contract flag is the source of truth**, and because `IRuntimeCheckpointPersistencePolicy.DecideAsync` decides on a `RuntimeCheckpoint` (name + metadata) rather than on the contract object, the claimer/handlers stamp the resolved profile onto the checkpoint as a `RuntimeMetadataKeys.CheckpointSideEffectProfile` key — contract is source, metadata is transport. **Default for unmarked activities: `External` (fail-safe).** Argue it explicitly: the marker gates whether a boundary may relax; mis-declaring a side-effecting activity as `ReplaySafe` is a data-integrity bug (its external effect re-fires on replay), whereas leaving a genuinely pure activity unmarked merely forgoes throughput. The failure modes are asymmetric, so the default must fail toward durability — unmarked ⇒ mandatory boundary — and `ReplaySafe` is the deliberate, auditable opt-in whose blast radius is one activity contract. Worked classification of shipped built-ins:

| Activity class | Externally observable? | Profile | Rationale |
| --- | --- | --- | --- |
| `WriteLine` / console output | Yes (console/log sink) | `External` by default, author-declarable `ReplaySafe` | The write is observable, but a console line is idempotent-enough that an author who accepts duplicate lines on replay may opt in; the runtime must not assume it. |
| HTTP call / outbound request / send message / publish event | Yes (remote system) | `External` (mandatory) | Re-execution re-sends; must sit behind a mandatory boundary so the effect is durable-once. |
| `SetVariable`, `If`, `Flowchart`/`Sequence` routing, pure compute/transform | No (in-workflow state only) | `ReplaySafe` | Deterministic, in-workflow; re-derived identically by replay from the last flushed boundary. This is the class a relaxed cadence targets. |

**R2 — spec-095 interplay (the real cost floor). Resolved, and this is the load-bearing decision: for `ReplaySafe` activities the pre-activation flush relaxes to `Deferred`; for `External`/unmarked it stays mandatory.** The measured coalesced floor is ≈ (CLR activity count + terminal) commits because `RuntimeCheckpointNames.ActivityAttemptClaimed` sits in `CoalescingRuntimeCheckpointPersistencePolicy.MandatoryFlushCheckpointNames` and `ActivityAttemptActivationClaimer.ClaimAsync` stamps it `CheckpointRequirement = Mandatory` for every transient CLR activity — the pre-activation flush that realizes spec-095 **FR-019** ("Durable execution MUST commit a logical invocation identity and complete materialized input snapshot before constructing or invoking user activity code", `specs/095-value-flow-redesign/spec.md`). What that boundary protects: **at-most-once attempt visibility, crash attribution, and poison/retry accounting** — the durable claim (state metadata `ActivityAttemptActivationClaim` + `...ClaimWorkItemId`) is what lets a redelivered work item be recognized as the *same* attempt (FR-020's distinct-attempt-identity, FR-022's no-re-execution-after-committed-completion) instead of being blindly re-run as a fresh attempt. For an activity whose pinned contract declares `SideEffectProfile.ReplaySafe`, re-running the body on segment replay is harmless *by declaration*, so FR-019's pre-activation flush protects **diagnostic fidelity** (per-activity attempt/poison precision), not correctness — and may therefore relax to `Deferred` (the claim state is still written into the coalesced working set and folded forward atomically at the next flush; `Deferred` ≠ `Skip`, so nothing is lost, only batched). For `External`/unmarked activities it stays `Immediate`. **Verdict, stated plainly: without this relaxation ADR 0032 cannot reach sub-activity-count commits.** Coalescing already removes the `ActivityScheduled`/`ActivityStarted`/`ActivityCompleted` flushes, but `ActivityAttemptClaimed` pins the floor at one mandatory flush per CLR activity; making that one boundary conditional on the marker is the *only* lever that reaches "commit every N activities" for a hot loop of pure activities. Mechanism: promote `ActivityAttemptClaimed` out of the unconditional `MandatoryFlushCheckpointNames` set into a conditional decision keyed on the `CheckpointSideEffectProfile` metadata the claimer stamps (`External`/absent ⇒ `Immediate`, `ReplaySafe` ⇒ `Deferred`), leaving the terminal/suspend/bookmark/incident names unconditionally mandatory. **This requires amending spec-095 FR-019** to make the pre-activation flush conditional on the contract's side-effect profile; that is permissible under the repo's pre-release / no-back-compat rule, and the amendment ships *with* the implementation unit (WU-marker), not as a separate retroactive edit.

**R3 — inspection fidelity. Resolved: project effective cadence and inspection granularity into the instance read model.** Under coalescing, inspection projections fold with their carrier checkpoints — `RuntimeCheckpointFold` merges `activityExecutionInspections` last-writer-per-`StateId` within a segment — so between two flushed boundaries per-activity inspection rows are coalesced rather than each independently durable ([ADR 0001](0001-checkpoint-gated-activity-execution-inspection.md)). Rather than let that surface as silent loss, the instance/inspection read model exposes two projected properties: `checkpointCadence` (`Immediate` | `Coalesced { maxSegmentCheckpoints, … }`, resolved from the same feature/executable configuration the policy reads) and an `inspectionGranularity` badge (`activity-level` | `boundary-level`). This is a **contract statement, not a UI design**: Studio (and any observability consumer) reads these fields to render "inspection is boundary-level for this run" and to explain why intra-segment per-activity evidence is coalesced. It costs nothing when cadence is `Immediate` (granularity is `activity-level`, the current behavior).

**R4 — `ActivityCancelled`. Resolved: MANDATORY, correcting the ADR's provisional "relaxable" classification.** The shipped code already settles this: `RuntimeCheckpointNames.ActivityCancelled` is in `CoalescingRuntimeCheckpointPersistencePolicy.MandatoryFlushCheckpointNames`, and `ActivityCancellationCheckpointService.CommitAsync` (`src/Elsa/Activities/Runtime/Services/ActivityCancellationCheckpointService.cs`) stamps it `Mandatory` and *atomically schedules workflow cancellation* through a post-commit intent (`NewWorkflowCancelWorkItem`) — i.e. an authored activity cancellation is externally consequential: it terminates the surrounding run and its live work. That is precisely the "externally observable ⇒ mandatory" test, and it is the compensation-hooks escape hatch the ADR anticipated made concrete: authored cancellation *is* a compensation trigger, so it correctly belongs in the mandatory set and is never relaxable by cadence.

**R5 — configuration surface. Resolved: authored on the workflow, compiled into the executable, with a host-level default; per-workflow wins.** The host-level default already exists as `WorkflowsRuntimeCheckpointPersistenceFeature` (`src/Elsa/Workflows/Runtime/Api/Coalescing/`), configured through shells.json (`Mode` = `Immediate` | `Coalesced`, plus `MaxSegmentCheckpoints`). The per-workflow carrier is `WorkflowStrategyOptions` (`src/Elsa/Workflows/Design/Core/Models/WorkflowStrategyOptions.cs`, which already carries `CommitStrategyType` as a stable type alias): add a checkpoint-cadence selection there so it flows design → publish → executable and the Runtime reads it off the pinned artifact identity already present in checkpoint metadata (`ExecutableArtifactId`/`Version`/`Hash`) — no Runtime→Design dependency (§E2.2), no new carrier. **Precedence:** the mandatory-boundary set overrides everything and can never be relaxed by any configuration; below that, a per-workflow authored cadence overrides the host default; the host default applies only where the workflow authors none. A runtime-side per-definition policy store was rejected as the *primary* carrier: an executable's replay-safety is a property of its pinned graph and must travel with the versioned artifact, not live in mutable host state that can drift from the graph it governs — though a host may still supply the default when a workflow is silent.

## Follow-up

Sequenced implementation plan (bounded work units, Runtime Execution Seam bucket):

- **WU-marker — side-effect profile on the contract (R1) + the pre-activation-flush relaxation (R2).** (a) Add `SideEffectProfile { External, ReplaySafe }` to `ActivityContract` with an author-facing declaration (attribute / contract-builder), fingerprinted, default `External`; (b) stamp the resolved profile onto activity checkpoints as `RuntimeMetadataKeys.CheckpointSideEffectProfile` (notably in `ActivityAttemptActivationClaimer.ClaimAsync`); (c) make `ActivityAttemptClaimed` a conditional decision in `CoalescingRuntimeCheckpointPersistencePolicy` (mandatory for `External`/absent, `Deferred` for `ReplaySafe`), removing it from the unconditional `MandatoryFlushCheckpointNames` set while leaving the terminal/suspend/bookmark/incident names mandatory; (d) amend spec-095 FR-019 to make the pre-activation flush conditional on the profile. *Tests:* extend `RuntimeCheckpointCoalescingPolicyTests` for the conditional `ActivityAttemptClaimed` decision; `GroundworkCoalescingCrashConvergenceTests` to prove a `ReplaySafe` hot loop recovers byte-identically after a mid-segment crash replays the deferred claims, and an `External` activity still flushes its claim before the body; the relevant spec-095 attempt/poison tests to prove `External`/unmarked attribution is unchanged.
- **WU-cadence-policy — effective-cadence read-model projection (R3).** Project `checkpointCadence` and `inspectionGranularity` into the instance/inspection read model from the feature/executable configuration; ensure `Immediate` runs report `activity-level` unchanged. *Tests:* `RuntimeCheckpointCommitTests` / inspection read-model tests asserting the badge reflects the active policy and that folded inspections are surfaced as boundary-level, not dropped.
- **WU-config-surface — per-workflow cadence authoring (R5).** Add the cadence selection to `WorkflowStrategyOptions`, compile it into the executable, resolve it in the policy from pinned-artifact metadata with the R5 precedence rule; keep the `WorkflowsRuntimeCheckpointPersistence` feature as the host default. *Tests:* `RuntimeCheckpointCoalescingTests` for per-workflow override vs host default vs mandatory-override precedence; a guardrail test asserting a mandatory checkpoint is always flushed regardless of configured cadence, and that a relaxed-cadence run recovers correctly by replay from the last flushed boundary.

Sequence: WU-marker first (it unlocks the cost floor and carries the spec-095 amendment), then WU-cadence-policy and WU-config-surface, which are independent of each other.
