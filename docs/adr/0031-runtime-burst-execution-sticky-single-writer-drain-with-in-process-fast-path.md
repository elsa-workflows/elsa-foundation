# Runtime Burst Execution Uses A Sticky Single-Writer Drain With An In-Process Fast Path

Status: accepted (2026-07-19; ratified with orchestrator approval. Resolves both in-ADR open questions — redelivery de-duplication is a mandated queue-provider contract, and the single-writer-per-execution model is the intra-workflow parallelism ceiling — see the resolutions inline and under Follow-up.)

The runtime will keep the durable, message-driven work-item model as the **source of truth** and add **execution locality as an optional optimization layer on top of it**: a sticky single-writer *burst* that drains one workflow execution's ready work items in a tight in-process loop, inside one ambient DI scope, skipping the JSON serialize/deserialize round-trip on in-process hops and letting activities share heavy in-memory objects for the duration of the burst through a reconstructible best-effort cache. The load-bearing invariant is that **durable state is the truth and in-process memory is only a cache — never a correctness dependency**: a burst that crashes, is evicted, or never forms at all recovers by replaying from the last committed checkpoint, and every result is identical to the fully-durable path. This decision is one of two independent dials on the same problem; the other is checkpoint cadence ([ADR 0032](0032-runtime-checkpoint-cadence-is-policy-driven-per-workflow.md)). It composes with, and does not alter, the pipeline spine ([ADR 0029](0029-runtime-execution-flows-through-the-pipelines.md)) or the checkpoint-commit contract ([ADR 0020](0020-runtime-checkpoint-commit-post-commit-work.md)).

**The problem this fixes — the honest per-activity cost.** Elsa 4 replaced Elsa 3's in-memory "burst of execution" (one long-lived shared `WorkflowExecutionContext` per run, all activities executing against shared heap state in a single call stack) with a durable, message-driven scheduler. Each activity invocation is now a discrete `RuntimeSchedulerWorkItem` (`src/Elsa/Workflows/Runtime/Core/Models/RuntimeSchedulerWorkItem.cs`) that flows through a sequence of command kinds — the enum values reached from the runtime core are `ScheduleActivity`, `StartActivity`, `InvokeActivity`, `CompleteActivity` (routing) and `CreateBookmark`, `ResumeBookmark`, `Checkpoint`, `Cancel`, `Start` — each a separate enqueue/peek/dequeue/dispatch hop through `WorkflowSchedulerCommandProcessor.ProcessAsync` → `IWorkflowSchedulerWorkQueue` → `WorkflowSchedulerDrainer.DrainAsync`. Concretely, for one ordinary leaf activity that schedules no children, the runtime pays:

- **Per-hop JSON serialization.** The work item's `Payload` is a `JsonElement` (`RuntimeSchedulerWorkItem.Payload`), and the command processor serializes each command payload into it (`WorkflowSchedulerCommandProcessor` builds the item from `envelope.Command.Payload`); the handler deserializes it back (`DeserializeInvokePayload` in `WorkflowInvokeActivitySchedulerWorkHandler`). Every hop is a serialize-on-enqueue / deserialize-on-dispatch round-trip, plus the JSON round-trips implied by durable-value capture and checkpoint state changes.
- **A durable-value `ListAsync` per invocation.** `WorkflowInvokeActivitySchedulerWorkHandler.InvokeActivityAsync` calls `durableValueStateStore.ListAsync(workItem.WorkflowExecutionId, …)` to project workflow variables, inputs, workflow identity, and upstream activity outputs (`RuntimeInputBindingStateProjection.Project*`) before the activity can even bind its inputs. Against a real store this is a query per activity.
- **A drain-loop state read per dispatched item.** `WorkflowSchedulerDrainer.DrainAsync` re-reads the workflow-execution state via `IsWorkflowTerminatedAsync` after every dispatched item to stop draining post-terminal siblings (the `#293` comment); on a durable provider this re-loads and deserializes the state document. (The drainer already fights this cost: the terminal check is deliberately *not* per-peek, and the execution-time identity carrier was moved off a per-invocation state read onto the durable-value projection the `ListAsync` above already rebuilds — see the correction below.)
- **Mandatory checkpoint commit(s) at semantic points.** The activity-completed / workflow-completed checkpoint is stamped `CheckpointRequirement = Mandatory` (the commit builders in `WorkflowInvokeActivitySchedulerWorkHandler`; likewise the parent-completion handler and the fault-incident recorder), and `RuntimeCheckpointCommitter.CommitAsync` folds durable-value write-back and post-commit scheduler intents into that commit. An activity that schedules children commits an additional mandatory `ActivityInspectionCaptured` checkpoint (`CommitChildSchedulingActivityAsync`) that carries the child work items as post-commit intents.

Rolled up, an ordinary activity costs on the order of **5–7 work-item hops, 1–3 checkpoint commits, one durable-value `ListAsync`, at least one execution-state read, and several JSON serialize/deserialize round-trips** — every one of them a potential I/O crossing on a durable provider. This is the price of what the durable model buys — crash recovery, resume-anywhere, per-activity observability, and scale-out — and for long-running human-in-the-loop workflows it is the *right* price. But for hot loops and compute pipelines it is orders of magnitude slower than an Elsa 3 burst, and activities have lost the ability to share a heavy in-memory object (a loaded model, an open client, a large parsed document) across a run: everything that must survive a hop has to become durable value state and round-trip through JSON.

**The decision: burst is locality, not a second execution model.** A burst is a *sticky single-writer drain*: while one workflow execution has ready work, the drainer processes its queued items in a tight in-process loop under a single ambient DI scope, without returning control to the durable dispatch fabric between hops. `WorkflowSchedulerDrainer.DrainAsync` **already is** this loop — it dequeues and dispatches ready items for one `WorkflowExecutionId` until the queue drains, it pauses on terminal status, and it honours a pause gate. The burst optimization is the set of fast-path shortcuts layered onto that existing loop; it does not introduce a parallel executor. Two shortcuts are in scope:

1. **In-process hop fast path (skip the JSON round-trip).** When the drainer enqueues a follow-on work item and then immediately dequeues and dispatches it within the same burst, the payload never needs to leave the process. The burst may hand the in-memory command payload object directly to the next handler instead of serializing it to a `JsonElement` and deserializing it back. The serialized form remains the wire/durable contract and is still produced whenever the item is genuinely persisted (any mandatory-checkpoint boundary, any hand-off to a durable queue provider, any hop that crosses the process); the fast path is a same-process, same-burst shortcut only. Handlers keep their existing `JsonElement`-payload signature as the durable contract; the fast path supplies the already-materialized payload alongside it.

2. **Burst-scoped reconstructible cache for heavy objects/services.** Within one burst, activities may publish and read shared in-memory objects (a warmed client, a parsed document, a compiled model) through a burst-scoped cache keyed to the workflow execution. The cache contract is **best-effort and reconstructible-only**: an entry may vanish at any burst boundary and the workflow must still be correct. Anything that must survive across a suspend, a crash, a burst eviction, or a scale-out hop is a **durable value** — inline `DurableValueState` for small payloads, or a `DurableValueStorage.External` / `DurableValueExternalReference` for large ones (`src/Elsa/Workflows/Runtime/Core/Models/DurableValueState.cs`). The cache never becomes the home of record for any value; it is a lifetime-bounded accelerator over the durable projection that `ListAsync` already rebuilds.

**The load-bearing invariant.** *Durable state is truth; memory is cache; memory is never a correctness dependency.* Every fast-path shortcut must be a pure optimization of a path that is already correct without it. If the burst never forms (cold start, provider without in-process affinity, a host that dispatches each command remotely), execution falls back hop-by-hop through the durable model with byte-identical results. This is the same discipline the runtime already applies elsewhere: the ambient-services accessor is optional and no-ops to a fresh DI scope when absent (below), and the pipeline dispatcher is optional so direct-construction paths are unaffected ([ADR 0029](0029-runtime-execution-flows-through-the-pipelines.md)).

**What already exists versus what is new.** The seam for a sticky single-writer burst is largely built; this ADR ratifies its purpose and adds the fast paths, rather than inventing the machinery.

- *Already built — the single-writer agent.* `IWorkflowExecutionAgentProvider` resolves a provider-owned `IWorkflowExecutionAgent` that is "an active execution mailbox for one workflow execution id" and "providers enforce one active mailbox per workflow execution id" (`IWorkflowExecutionAgent.cs`, `IWorkflowExecutionAgentProvider.cs`). `WorkflowExecutionStartDispatcher` and `BookmarkResumeDispatcher` both activate an agent (`GetAgentAsync(activationRequest, …)`) before enqueuing. `PassivateAsync` is *defined* to release that agent, but no production path triggers passivation yet — activation and the single-writer mailbox are wired; agent release/eviction is not, so the live agent registry currently grows unboundedly (tracked as [#542](https://github.com/elsa-workflows/elsa-foundation/issues/542); the burst work unit below is the natural owner of agent lifetime/eviction). Single-writer-per-execution — the precondition for a safe sticky burst — is therefore already the contract on the activation side.
- *Already built — the drain loop.* `WorkflowSchedulerDrainer.DrainAsync` is the burst loop: peek → pause-check → dequeue → dispatch, repeated for one execution id until the queue empties or a terminal status is reached, honouring `MaxWorkItems`.
- *Already built — the ambient-scope seam.* `IWorkflowExecutionAmbientServicesAccessor` is "async-flow scoped access to non-durable services supplied by an in-process request-affine dispatch." `DrainAsync` opens the burst's ambient frame with `_ambientServicesAccessor.Push(request.AmbientServices)`, and `WorkflowInvokeActivitySchedulerWorkHandler.HandleAsync` uses it as the fast path today: `if (_ambientServicesAccessor.Current is { } ambientServices)` it runs against the *ambient* services (reusing the burst's scope), else it opens a fresh `_serviceScopeFactory.CreateAsyncScope()`. That branch is the exact optimization seam this ADR builds on — the ambient scope is the natural home for the burst-scoped cache, and the accessor is `AsyncLocal`-backed (`AsyncLocalWorkflowExecutionAmbientServicesAccessor`) with a no-op fallback (`NoopWorkflowExecutionAmbientServicesAccessor`) that guarantees the burst-absent path stays correct.
- *New.* (a) The in-process-hop fast path that skips serialize/deserialize when an item is enqueued and dispatched within the same burst; (b) the burst-scoped reconstructible cache contract (publish/read API, reconstructible-only semantics, eviction-at-boundary, the "must-survive ⇒ durable value" rule); (c) an explicit burst-lifetime boundary tied to the ambient scope so cache entries are disposed deterministically at burst end; (d) a guardrail asserting that disabling the fast path (no burst) produces identical committed state, so the cache can never silently become a correctness dependency.

**Prior art.** This is the shape the durable-workflow field converged on. **Temporal** keeps event-sourced history as truth but adds *sticky execution* (a workflow task is routed back to the worker that holds the cached, replayed workflow object) and batches state transitions into one workflow task rather than persisting each command — locality over a durable log. **Orleans** pairs virtual actors (single-threaded-per-grain, in-memory state, single-writer by activation) with periodic persistence; the grain is the cache, storage is truth. **Durable Task Framework (DTFx)**, which Elsa 3 drew on, uses *extended sessions* to keep the orchestration instance in memory across multiple dispatches so it need not replay history from scratch each turn. All three keep a durable source of truth and treat in-memory locality as a reconstructible accelerator that can be dropped without affecting correctness — exactly the invariant above.

**Constitution alignment.** The burst is entirely Runtime-owned. It operates over runtime state (the scheduler queue, durable values, execution state) and the pinned executable artifact, and introduces no `Elsa.Workflows.Design.*` dependency, so §E2.2 (no Runtime→Design dependency) and §E2.6 (executable-always-runs / artifact-only runtime) are preserved — the burst-scoped cache holds only runtime objects and never reaches back to design-side data. No new constitution gate is required for this decision. If the team later wants "in-process locality is optimization-only; durable state is the sole source of truth" pinned as a durable rule, that single item routes through [Constitution Readiness](../program-goals/constitution-readiness.md); this ADR does not depend on it.

**Failure semantics.** A burst is at-least-once and crash-safe by construction. If the burst faults or the host dies mid-loop, recovery replays from the last committed checkpoint ([ADR 0020](0020-runtime-checkpoint-commit-post-commit-work.md)); any work item that was dispatched in-process but not yet checkpoint-committed is simply re-dispatched from the durable queue. Redelivery is made safe by the `IdempotencyKey` carried on every `RuntimeSchedulerWorkItem` and on the command envelope (`WorkflowExecutionCommandDeliveryMode.AtLeastOnce` in `BookmarkResumeDispatcher`): a redelivered item is recognizable and a handler that has already produced a committed effect can no-op — the invoke handler already guards this (`if (state.Status == ActivityExecutionStatus.Completed) { EnqueueCompletionWork…; return; }`). The burst-scoped cache needs no recovery handling at all: its entries are reconstructible, so a lost cache is refilled by the same `ListAsync` projection the durable path already performs. **Resolved at ratification — redelivery de-duplication is a mandated queue-provider contract.** `IWorkflowSchedulerWorkQueue.EnqueueAsync` MUST be idempotent by work-item identity: re-enqueueing an item whose `WorkItemId` already exists for that workflow execution returns (and keeps) the already-queued item and never appends a duplicate. This is now the *primary* redelivery-safety guarantee — the in-process fast path (WU-2) and the outbox redelivery sweeps both rely on it — with per-handler idempotency (the `state.Status == ActivityExecutionStatus.Completed` no-op above) retained as defense-in-depth rather than the sole line of defense. Both shipped providers already conform: `InMemoryWorkflowSchedulerWorkQueue` and `GroundworkWorkflowSchedulerWorkQueue` implement create-only-by-identity enqueue keyed on `(WorkflowExecutionId, WorkItemId)`. The requirement is pinned in the `IWorkflowSchedulerWorkQueue` XML docs and covered by provider conformance tests.

**Consequences.** Hot loops and compute pipelines regain Elsa-3-class throughput (no per-hop JSON round-trip, no fresh DI scope per activity, shared heavy objects within a run) while keeping the durable guarantees; the burst-absent path is unchanged and byte-identical, so nothing regresses for workflows that never form a burst. The costs: (1) two representations of a work item can coexist within a burst (the live payload object and its serialized form), and the fast path must guarantee they are equivalent — the serialized form stays authoritative at every persistence boundary; (2) the burst-scoped cache adds a lifetime the runtime must bound and dispose deterministically at burst end, and a misuse where a caller treats the cache as durable is a correctness bug the guardrail must catch; (3) burst affinity interacts with scale-out — a workflow can burst on only one node at a time, which the single-writer agent already enforces. **Ratification pins this as the intended ceiling** (see the resolved parallelism decision under Follow-up): the single-writer-per-execution model is the deliberate intra-workflow concurrency bound — there is no concurrent drain of one workflow execution — and fork/join activities interleave *within* that single writer's drain loop rather than on parallel threads. Parallelism scales horizontally *across* workflow executions, not within one. This transitional coexistence of fast and durable paths is acceptable but must be documented so contributors never assume a cached object is a source of truth.

**Alternatives considered.** *Revert to the Elsa 3 shared `WorkflowExecutionContext` (one long-lived mutable context per run)* was rejected: it would surrender crash recovery, resume-anywhere, per-activity observability, and scale-out — the entire reason Elsa 4 adopted the durable work-item model — and it makes in-memory state the source of truth, the exact inversion of the invariant here. The runtime seam explicitly retired that model (the program-goal notes forbid resurrecting `WorkflowExecutionContext`), and [ADR 0030](0030-runtime-expression-evaluation-uses-a-parameter-threaded-live-carrier.md) already refused to bring back a DI-registered live context. *Do nothing — accept the per-activity cost as the price of durability* was rejected: against any real store the benchmark gap versus Elsa 3 on hot loops is a GA/reputation risk, and "activities cannot share a heavy in-memory object across a run" is a real capability regression users will hit, not a micro-optimization. *Make the burst the primary model and treat the durable hop as the fallback* was rejected as an inversion of the invariant: it would make correctness depend on burst formation, reintroducing the shared-memory correctness coupling; locality must remain the optimization, never the contract. *Cache heavy objects durably instead of in-memory* was rejected for the hot path: forcing every shared object through `DurableValueStorage.External` reintroduces the serialization/I/O cost the burst exists to avoid — durable external storage remains the right home for values that must survive, but not for a within-run accelerator.

## Follow-up

- **Speckit unit** (Runtime Execution Seam bucket): the burst fast path — (a) in-process-hop payload short-circuit in `WorkflowSchedulerDrainer` that skips serialize/deserialize when an enqueued item is dispatched within the same burst, preserving the `JsonElement` contract at every persistence boundary; (b) the burst-scoped reconstructible cache contract (publish/read API on the ambient scope, reconstructible-only + evict-at-boundary semantics, the must-survive ⇒ durable-value rule, deterministic dispose at burst end); (c) a guardrail test asserting that a run with the fast path disabled commits byte-identical checkpoint state to a run with it enabled (memory-is-never-correctness); (d) documented burst-affinity / single-writer interaction with scale-out. Sequence after this ADR is accepted.
  - **Items (a), (c), (d) implemented — [spec 109](../../specs/109-runtime-inprocess-hop-fast-path/spec.md) (WU-3).** The in-process-hop payload short-circuit is realized at the WU-2 live-drain delivery seam rather than inside `WorkflowSchedulerDrainer`: the checkpoint committer publishes the already-materialized continuation `RuntimeSchedulerWorkItem` onto a drain-scoped carrier on `RuntimeLiveDrainDeliveryScope` (keyed by post-commit intent id, evicted when the scope is popped at drain end), and `RuntimeSchedulerPostCommitIntentDispatcher` takes it instead of deserializing the durable intent payload. The serialized `Payload` stays authoritative at every persistence boundary (`[JsonIgnore]` in-process conduit; durable stores strip it → deserialize path). Guard (c) is a byte-identical ENABLED-vs-DISABLED end-to-end run plus dispatcher/committer/carrier seam tests (crash-window, absence fallback, single-use take, exec-id validation, toggle). (d) burst-affinity/single-writer/scale-out interaction is documented in the spec. **Evidence-first note (Step 0):** profiling found the per-hop JSON round-trip is only ~2% of an in-memory hop and ~0.36% of a durable hop, so the short-circuit is a **small, byte-identical** cut whose benefit scales with payload size — the dominant hot-loop costs are hop count, durable checkpoint-commit fsync ([ADR 0032](0032-runtime-checkpoint-cadence-is-policy-driven-per-workflow.md), shipped), and the durable claim/outbox round-trips ([spec 106](../../specs/106-runtime-live-drain-delivery/spec.md), shipped). Scope/context reuse is already handled by the ambient burst scope, so no further scope work was warranted.
  - **Item (b) remains open for the next unit** — the burst-scoped reconstructible cache for shared heavy in-memory objects (warmed clients, parsed documents, compiled models), with the reconstructible-only + must-survive⇒durable-value contract and deterministic dispose. The drain-scoped carrier spec 109 introduced is a private single-purpose payload carrier, not that general cache.
- **Ratification decisions** (resolved 2026-07-19, replacing the two open questions flagged above):
  1. *Redelivery de-duplication is a mandated queue-provider contract.* `IWorkflowSchedulerWorkQueue.EnqueueAsync` MUST be idempotent by work-item identity — re-enqueueing a `WorkItemId` already present for a workflow execution returns/keeps the existing item and adds no duplicate. The in-process fast path (WU-2) and the outbox redelivery sweeps depend on this as the *primary* guarantee; per-handler idempotency remains defense-in-depth, not the primary line of defense. Both shipped providers (`InMemoryWorkflowSchedulerWorkQueue`, `GroundworkWorkflowSchedulerWorkQueue`) already conform via create-only-by-identity enqueue; the contract is pinned in the interface XML docs and covered by provider conformance tests.
  2. *The single-writer-per-execution model is the intra-workflow parallelism ceiling.* No concurrent drain of one workflow execution is permitted; parallelism scales horizontally across executions. Fork/join activities interleave within the single writer's drain loop. The live agent already enforces one active mailbox per execution id ([#542](https://github.com/elsa-workflows/elsa-foundation/issues/542) owns agent lifetime/eviction).

## Correction from the code

Two points in the brainstorming background did not match the working tree and are corrected here:

- **The per-invocation execution-state read has already been eliminated for the common case.** The background implies a state read "per activity"; in the current `WorkflowInvokeActivitySchedulerWorkHandler`, the execution-time identity carrier (correlation id / instance name) is projected from the durable-value `ListAsync` the invocation already performs rather than read from workflow-execution state, and the control-leaf state load is lazy (only a mutating `Finish`/`Correlate`/`SetName` leaf pays it). The drainer's terminal-status re-check is likewise deliberately post-dispatch-only, not per-peek (the `#293` comment). The durable-value `ListAsync` per invocation and the drainer's post-dispatch state read remain, so the hop-cost arithmetic above still holds, but the runtime is already actively trimming these reads — the burst extends that direction rather than opening it.
- **The identity carrier itself settled on durable state as truth while this ADR was drafted.** The spec-083 review first threaded identity as per-hop command-metadata keys, then — after review found that per-branch-lineage metadata cannot broadcast a `Correlate`/`SetName` to an already-scheduled concurrent sibling branch — replaced the channel with a single `RuntimeMetadataKeys.IdentityName` (`runtime.identityName`) durable-value slot (commit `487465c5`): the assigning leaf upserts `identity:*`-tagged durable values on its completion commit, and every invocation (any branch, and the resume path) re-lists them through the same `ListAsync` projection. This is noted because it *reinforces* this ADR's invariant: even the identity accelerator moved onto durable state as the source of truth, with per-hop copies demoted to cache — the same "memory is cache, durable is truth" direction the burst formalizes.
