# Runtime Execution Flows Through The Workflow And Activity Pipelines

Status: proposed

The runtime scheduler will dispatch every work item **through the runtime pipeline appropriate to its kind** — the workflow-execution pipeline for workflow-tick and lifecycle work, the activity-execution pipeline for per-activity-execution work — with the existing scheduler work handler running as the pipeline's `Invoke`-slot body. This makes the already-defined pipeline contract (`IWorkflowRuntimeMiddleware` / `IActivityRuntimeMiddleware`, the pipeline builders, `RuntimeWorkflowPipelineSlots` / `RuntimeActivityPipelineSlots`, `RuntimePipelinePlan`) the **real execution spine**: a module that registers runtime middleware against a slot now actually runs during execution. This decision settles the "make the pipeline real" move (Move 1) and states the direction for, but does not commit, the larger handler-decomposition move (Move 2).

**The problem this fixes.** The pipeline contract exists today but nothing invokes it. The built-in middleware are empty placeholders whose base `InvokeAsync` only calls `next(context)`; the builders and `BuildPlan()` are exercised solely by `RuntimePipelineContractTests`; the pipeline is registered in no feature and no DI container; and there is no invoker that composes middleware into a chain and runs it. Real execution is inlined in scheduler work handlers: `WorkflowSchedulerCommandProcessor` enqueues a `RuntimeSchedulerWorkItem`, the drain coordinator dequeues it, and `IWorkflowSchedulerWorkHandler.HandleAsync` performs every phase as hardcoded sequential code (`WorkflowInvokeActivitySchedulerWorkHandler` alone is ~970 lines). A module that registers an `IActivityRuntimeMiddleware` is therefore **silently never run** — a false affordance, and the same failure class as the JS expression pre-processors whose unregistered dependency makes them dead code. It also blocks the framework's modular charter from reaching runtime execution (tracing, tenanting, authorization, domain-retry policy, custom persistence policy) and duplicates cross-cutting phase logic across handlers.

**Scheduler and pipeline are complementary, not alternatives.** The scheduler — the durable work-item queue, the drain coordinator, and the checkpoint machinery — is the correct *dispatch* layer and is retained unchanged; it is conformant with the runtime-state and checkpoint decisions and is well tested. The pipelines are the *execution spine*: the workflow pipeline is how one workflow tick runs, the activity pipeline is how one activity execution runs. In a correct design the scheduler work handler's body **is** an invocation of the activity (or workflow) pipeline. This mirrors elsa-core, where a scheduler/burst loop runs inside a workflow-execution pipeline and each activity runs through an activity-execution pipeline. The current foundation code collapsed that spine into the handler; this decision re-establishes it without discarding the scheduler.

**Mechanism: wrap, do not replace (Move 1).** A pipeline executor is invoked at the single handler-dispatch point in the drain coordinator: `pipeline.InvokeAsync(context, () => handler.HandleAsync(workItem, cancellationToken))`. The built-in slots remain pass-throughs and the handler stays intact as the `Invoke`-slot body, so the change is **behavior-preserving**: with no non-placeholder middleware registered, execution is byte-for-byte what it is today. The pipeline kind (workflow vs activity) is selected from the work item's command kind — the same discriminator the handlers' `CanHandle` already uses — and the pipeline context is built from the work item's loaded state before invocation. This is the minimum change that flips the pipeline from dead scaffolding to a live, extensible spine.

**Context shape and pipeline selection.** The workflow pipeline context carries the `WorkflowExecutionState` and the optional `SchedulerState`; the activity pipeline context additionally carries the `ActivityExecutionState` — the shapes the contract already defines. Workflow-lifecycle command kinds (workflow start, checkpoint, cancel, and the complete-activity routing step) run under the **workflow** pipeline; per-activity-execution kinds (schedule activity, start activity, invoke activity, resume bookmark, create bookmark, parent-activity completion) run under the **activity** pipeline. The exact handler-to-slot correspondence is recorded in the [pipeline wiring sizing](../reports/runtime-execution-pipeline-wiring-sizing.md); the executor only needs the kind→pipeline selection, not that per-slot detail, for Move 1.

**What is committed here, and what is deferred.** This decision commits **Move 1**: register the two pipelines in DI, build the contexts, invoke the executor at the dispatch point, and add a guardrail (below). It **does not commit Move 2** — relocating the handlers' inlined phases into slot-bound built-in middleware. Move 2 is endorsed as the eventual direction (built-in phase behavior should ultimately live in its named slot, not inline in a handler), but it is explicitly out of scope of this ADR because each phase carries hazards that demand case-by-case design: atomic checkpoint-commit folding of durable-value write-back (#310, #286, #260), transactional fault arms that must not be split across slots, control-leaf intents (`Finish` / `Correlate` / `SetName` / `SetOutput`, #260/#308), container scope-completion capture that fires only on composite completion (#210, [ADR 0027](0027-scoped-variable-references-include-declaring-scope.md)), and the inspection-accumulator toggle that selects checkpoint-commit vs direct-persist. Until a later, separately-approved slice moves a given phase, its behavior stays in the handler. Move 2 proceeds incrementally, easiest handler first, with `WorkflowInvokeActivitySchedulerWorkHandler` last.

**Guardrail against re-orphaning.** Because the failure that motivated this ADR is precisely "types that look wired but are not," the executor lands with a test that asserts a registered marker middleware is **actually invoked during a real work-item dispatch** — not merely that the builder registers it. This mirrors the guardrail planned for the JS expression pre-processors and prevents a future change from silently regressing the pipeline back to dead scaffolding.

**Ordering and inspectability.** Middleware target stable named slots and coarse order rather than concrete neighboring middleware, and the resolved `RuntimePipelinePlan` is inspectable. This directly answers the original brainstorm concern (Decision 6): Elsa 3's pain was behavior-critical ordering encoded through implicit linked middleware; the slot model makes ordering explicit and the plan introspectable. Move 1 exposes the plan and the slot ordering even before any built-in phase is relocated.

**Constitution alignment.** The pipeline is entirely Runtime-owned and introduces no `Elsa.Workflows.Design.*` dependency, so §E2.2 (no Runtime→Design dependency) and §E2.6 (artifact-only runtime) are unaffected — the pipeline operates over runtime state and the pinned executable, never over design-side data. No new constitution gate is required for this decision. If the team later wants "runtime-execution extensibility is pipeline-mediated" pinned as a gate, that single item routes through Constitution Readiness; this ADR does not depend on it.

**Consequences.** Modules gain a real runtime-execution extension surface, the false affordance is removed, and the pipeline plan becomes inspectable — all with no behavior change on day one. The costs: a thin executor plus context construction is added to the hot per-work-item dispatch path (a single delegate chain over no-op slots; expected to be negligible), and the kind→pipeline selection must stay in sync with the handlers' `CanHandle` command kinds. Until Move 2 runs, built-in phase behavior remains duplicated in concept between the handlers (where it actually executes) and the empty slots (where it will eventually live); this transitional state is acceptable but must be documented so contributors do not assume a placeholder slot is where behavior resides.

**Alternatives considered.** *Option A — replace handler internals with per-slot middleware as the first move* was rejected for Move 1 because it forces the hazardous decomposition up front with no incremental safety net; it is adopted as the Move 2 direction instead. *Delete the pipeline types and keep execution handler-inlined* was rejected: it contradicts the modular charter and the steward's confirmed intent that runtime execution be pipeline-mediated. *A single unified pipeline for both workflow and activity execution* was rejected: the contract test and the two context types already separate the concerns, and collapsing them weakens workflow-vs-activity context clarity (Decision 6's caution against one generic pipeline).

## Follow-up

- **Move 1 Speckit unit** (Runtime Execution Seam bucket): pipeline executor + context construction + DI registration of both pipelines + the invocation-guardrail test. Behavior-preserving; low risk.
- **Move 2** (per-handler slot decomposition) sequences after, easiest handler first and `WorkflowInvokeActivitySchedulerWorkHandler` last, each handler its own approved change, per the [pipeline wiring sizing](../reports/runtime-execution-pipeline-wiring-sizing.md).
