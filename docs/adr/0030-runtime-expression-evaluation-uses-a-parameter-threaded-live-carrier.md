# Runtime Expression Evaluation Uses A Parameter-Threaded Live Carrier

Status: accepted

Runtime expression evaluation will obtain its workflow state — identity, inputs, variables, and activity outputs — from a **carrier passed as the `IExpressionExecutionContext` parameter**, never from a DI-registered live context. Two carriers exist along the same parameter-threading seam: the **materialization-time** carrier `IMaterializationExpressionState` (already built and working) for expressions evaluated when activity inputs materialize, and a **new execution-time live carrier** for expressions evaluated mid-activity against post-seed state. The five currently-dead `IWorkflowExecutionContext` JavaScript pre/post-processors are **re-pointed onto the live carrier**, not revived through dependency injection. This decision settles the expression-context edge of the Runtime Execution Seam (the "edge A" left open by the [source reconciliation](../reports/runtime-expression-context-source-reconciliation.md)); it is independent of, and composes with, [ADR 0029](0029-runtime-execution-flows-through-the-pipelines.md).

**The problem this fixes.** `JavaScriptWorkflowsRuntimeFeature` registers six pre/post-processors as `AddScoped`. Five of them — `WorkflowInputFunctionsPreProcessor`, `WorkflowFunctionsPreProcessor`, `VariableFunctionsPreProcessor`, `ActivityOutputFunctionsPreProcessor`, and `CopyVariablesToWorkflowContext` — take `IWorkflowExecutionContext` by constructor injection, but `IWorkflowExecutionContext` is registered nowhere in `src/` (it is `new`'d only under `tests/`). Because `PreProcessScript` resolves `IEnumerable<IScriptPreProcessor>`, MS DI eagerly constructs every registered implementation, so a single missing dependency throws for the **whole enumerable** — taking the one working processor (`MaterializationAccessorsPreProcessor`) down with it — on first script evaluation *if the feature is enabled*. No test enables the feature, so the throw is unguarded: turning the JS runtime feature on in a host today would silently break all JavaScript evaluation. This is the same failure class ADR 0029 addresses for the execution pipeline — types that advertise a capability that is not wired — here manifesting as a live resolution landmine rather than a silent no-op.

**Mechanism: parameter-thread, do not DI-inject (D1).** The runtime already proved the correct shape. `MaterializationAccessorsPreProcessor` takes **no** constructor dependencies: it casts the passed `IExpressionExecutionContext` to the narrow marker `IMaterializationExpressionState` and reads `variables`/`input`/`output` from it. That carrier is populated by `RuntimeActivityInputMaterializer` from the runtime's own resolution context (workflow variables, workflow inputs, activity outputs) — all state the scheduler work handler already holds. This decision **ratifies parameter-carrying as the single expression-state mechanism** for the runtime and rejects constructing or DI-registering a live `IWorkflowExecutionContext`. Parameter-threading keeps expression state request-scoped by construction, avoids a captive-dependency hazard, and stays Design-free.

**A live execution-time carrier is in scope (Q2).** Materialization-time evaluation is not the only evaluation point: a *Run JavaScript*-style activity evaluates arbitrary script at execution time and must read — and write — workflow state after inputs are seeded. Materialization-time-only would have let us delete the live context outright; because live mid-execution evaluation **is** a required surface, the runtime needs a live carrier. The decisive constraint is *how* it is obtained: it is **built and populated by the scheduler work handler at execution time and passed as the `IExpressionExecutionContext` parameter**, exactly like the materialization carrier — not resurrected as a DI service. `IWorkflowExecutionContext` as a DI-injected dependency is therefore **retired**; whether the concrete type is renamed or reworked into the live carrier is an implementation naming detail for the Speckit unit, but it MUST NOT return as a registered service.

**Accessor surface: keep all four, re-pointed onto the carrier (D3).** The generic `getVariable`/`getInput`/`getOutput` accessors already resolve at materialization time and are unaffected. The four behaviors that are dead today are all confirmed **required product surface** and are ported onto the live carrier:

- **Execution-time identity functions** (`getWorkflowInstanceId`, `getCorrelationId`, workflow name, …) — unobtainable through the generic accessors; sourced from `WorkflowExecutionState` / the pinned executable identity.
- **Named pascalized accessors** (e.g. `getGreeting()` for a variable named `greeting`) — sugar over the generic path, generated per declared name.
- **Execution-time activity-output accessors** — reading upstream outputs during execution, where execution-time timing (not just materialization-time) matters.
- **JS-side variable write-back** — script mutations to workflow variables that persist. This is the highest-risk surface: the carrier accumulates variable mutations during evaluation, and the handler folds them into the **existing durable-value write-back on the checkpoint-commit boundary** (`WorkflowInvokeActivitySchedulerWorkHandler.BuildWorkflowScopeWriteBackChanges`, the same path that already persists `SetOutput` and workflow-scope variable changes, per #310/#286/#260 and [ADR 0020](0020-runtime-checkpoint-commit-post-commit-work.md)). Write-back MUST NOT introduce a second persistence route; it reuses the atomic checkpoint fold.

**Carrier shape: narrow markers, not a general bag (Q3).** The live carrier is a **narrow, purpose-named marker interface** (mirroring `IMaterializationExpressionState`), not elsa-core's general `TransientProperties` bag on `IExpressionExecutionContext`. A general transient-properties carrier is deferred until a second consumer proves the seam (§2.17/§2.20 — do not extract shared abstraction before the second use). The two narrow carriers can be unified behind a general bag later without changing the parameter-threading model, so nothing here forecloses parity.

**Guardrail against re-orphaning (D4).** The unit lands with a test that **enables `JavaScriptWorkflowsRuntimeFeature`, resolves `IEnumerable<IScriptPreProcessor>`, and runs a smoke JS evaluation** — asserting that every registered pre/post-processor constructs and the pipeline evaluates end-to-end. This is what no current test does, and its absence is exactly why the landmine went unnoticed. It mirrors ADR 0029's invocation guardrail and prevents a future change from silently re-orphaning a processor behind an unregistered dependency.

**Relationship to spec 064.** [Spec 064 "Runtime Workflow Execution Context"](../../specs/064-runtime-workflow-execution-context/spec.md) is **superseded as a mechanism but its intent is carried forward**: its three scenarios (workflow identity without loading authored models; inputs/variables/outputs readable from a runtime-owned context; JS updates to correlation/name/variables visible on re-read) are precisely the identity, read, and write-back surfaces kept above. 064 modelled this as a mutable runtime-owned `WorkflowExecutionContext` object; this ADR re-expresses the same behavior on the parameter-threaded live carrier and forbids the DI-service form. The implementation spec re-bases 064's FR-001…FR-005 onto the carrier rather than starting fresh.

**Constitution alignment.** Both carriers are Runtime-owned and read only runtime state (execution state, durable values, the pinned executable) — no `Elsa.Workflows.Design.*` dependency — so §E2.2 (no Runtime→Design dependency) and §E2.6 (artifact-only runtime) are preserved. No new gate is required. If the team wants "runtime expression-state is parameter-threaded and Design-free" pinned as a durable rule, that single item routes through [Constitution Readiness](../program-goals/constitution-readiness.md); this ADR does not depend on it.

**Consequences.** Enabling the JS runtime feature becomes safe; the dead processors become live behavior; the identity/named/output/write-back surfaces work at execution time; and a guardrail prevents regression. The costs: the scheduler work handler gains live-carrier construction on the execution path (it already assembles the same state, so the marginal cost is a projection, not new I/O); JS variable write-back adds a mutation-accumulation step that must fold into the checkpoint boundary correctly (the primary implementation hazard, and the reason write-back reuses the existing durable-value path rather than inventing one); and two narrow carriers coexist until a general bag is justified. `IWorkflowExecutionContext` must be prevented from re-entering DI — the guardrail plus a structural check cover this.

**Alternatives considered.** *Construct/DI-register `IWorkflowExecutionContext` to revive the processors as written* was rejected (D1): it reintroduces the live-service coupling the runtime already moved away from and risks captive-dependency and lifetime bugs; the working materialization path already demonstrates the parameter-carrier is sufficient. *Drop the five processors and ship only the generic materialization accessors* was rejected (D3/Q2): identity functions and JS write-back are required product surface and a Run-JavaScript activity needs live mid-execution evaluation, so materialization-time-only is insufficient. *Add a general `TransientProperties` carrier now for elsa-core parity* was rejected (Q3): speculative surface with no second consumer; the narrow marker is adequate and widenable later.

## Follow-up

- **Speckit unit** (Runtime Execution Seam bucket): the live execution-time carrier (narrow marker + handler-side population); re-point the five processors onto it and strip their constructor deps; port the identity / named-accessor / exec-time-output / variable-write-back behaviors; fold write-back into the checkpoint-commit durable-value path; retire `IWorkflowExecutionContext` as a DI dependency; and the enable-feature resolve-and-evaluate guardrail. Re-base spec 064's FR-001…FR-005 onto the carrier.
- **Sequencing vs ADR 0029:** independent. The carrier is populated by the scheduler work handler regardless of whether execution is pipeline-mediated (0029 Move 1) or handler-inlined; if 0029 Move 2 later relocates input materialization into slot middleware, the carrier construction moves with it.
