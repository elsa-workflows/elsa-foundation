# ReplaySafe Activities Execute As Fused Hops With Precomputed Routing

Status: accepted (2026-07-20; ratified with orchestrator approval. Extends [ADR 0031](0031-runtime-burst-execution-sticky-single-writer-drain-with-in-process-fast-path.md) and [ADR 0032](0032-runtime-checkpoint-cadence-is-policy-driven-per-workflow.md); amends the 5–7-hops-per-activity execution model, the spec-095 FR wording that assumes per-stage work items, and the scheduler handler set. All four decisions (D1–D4, including D4's deferral) are ratified; the three in-ADR open questions are resolved under Ratification resolutions in the Follow-up. Nothing is implemented yet — implementation sequences as Speckit units per the Follow-up.)

The runtime will let a burst execute a `ReplaySafe` activity's scheduler stages — schedule, start, invoke, and the completion-propagation cascade — as **fused in-process handler passes** instead of discrete queue hops, and will move the routing knowledge those stages need from runtime graph walks to **publish-time routing tables** pinned into the executable. The durable work-item model remains the source of truth exactly as ADR 0031 ratified it: fusion is a dispatch-level locality optimization available only inside a live burst, only for activities whose pinned contract declares `SideEffectProfile.ReplaySafe`, and a run with fusion disabled commits byte-identical durable state. The justifying logic is the same one ADR 0032 R2 ratified for the pre-activation flush: **the per-stage split buys redrive granularity that a `ReplaySafe` activity has declared away.** For `External`/unmarked activities every hop, flush, and attempt boundary is unchanged.

## The problem — hop count is the last big lever, and the evidence says so

After ADR 0031 (burst + in-process fast path) and ADR 0032 (coalesced cadence + R2 claim relaxation) shipped, the spec-109 Step-0 profile ([research](../../specs/109-runtime-inprocess-hop-fast-path/research.md)) shows where the remaining cost lives: **dispatch machinery is ~55% of a durable hop and ~78% of an in-memory hop** (claim/ack, pipeline, tracer, handler dispatch), JSON round-trips are ~0.4–2% (already short-circuited by spec 109), scope construction is ~0 (ambient burst scope), and the fsync floor is owned by coalescing. The cost that remains is the **number of hops**, and the runtime pays a lot of them. Per ordinary leaf activity inside a routing composite, today's chain is:

1. `ScheduleActivity` — `WorkflowScheduleActivitySchedulerWorkHandler`: deserialize payload, pinned-executable read, activity-state find, create the `Scheduled` state, build a mandatory `ActivityScheduled` commit with an inspection projection, post-commit intent → hop 2.
2. `StartActivity` — `WorkflowStartActivitySchedulerWorkHandler`: deserialize, executable read, state find, **materialize the input snapshot** (durable-value `ListAllDurableValueStatesAsync` + runtime-view `ListAllAsync` + visible variable frames), create the `Running` state, `ActivityStarted` commit, intent → hop 3.
3. `InvokeActivity` — `WorkflowInvokeActivitySchedulerWorkHandler`: attempt claim (`ActivityAttemptClaimed`, already `Deferred` for `ReplaySafe` per R2), run the body, `Completed` commit, intent → hop 4.
4. `CompleteActivity` (`ActivityCompleted`) — `WorkflowCompleteActivitySchedulerWorkHandler`: parent-state find, re-enqueue as → hop 5.
5. `CompleteActivity` (`ParentCompletionEvaluation`) — `WorkflowParentActivityCompletionSchedulerWorkHandler`: load parent state + executable, walk the graph to route the child's outcomes to successors, re-enqueue as → hop 6.
6. `CompleteActivity` (`ContinuationScheduling`) — re-enqueue as → hop 7.
7. `Checkpoint` work item — commit `ActivityCompleted`/`WorkflowCompleted` with the downstream `ScheduleActivity` intents, which start the next activity's chain at hop 1.

Seven-plus dispatches per graph edge, each paying the drain loop's claim/pause/dispatch/ack machinery and (durably) a claim round-trip, so that any single stage can be independently redriven after a crash. For an `External` activity that granularity is the product: it is what makes at-most-once attempt visibility, crash attribution, and poison accounting per-stage precise. For a `ReplaySafe` activity, ADR 0032 R2 already ratified the counter-argument — re-running the whole span is harmless *by declaration*, the claim flush is already `Deferred`, and the checkpoints already fold into one segment flush. The runtime currently keeps paying full per-stage dispatch for granularity that the flush cadence no longer preserves anyway: after coalescing, a mid-segment crash replays the whole segment regardless of how many hops it took. **The hops now buy nothing for `ReplaySafe` activities except CPU.**

## Decision D1 — fused schedule→start→invoke pass for ReplaySafe activities

When the drainer dispatches a `ScheduleActivity` work item inside a live burst, and the target node's pinned contract declares `SideEffectProfile.ReplaySafe`, the handler pass runs the **schedule, start, and invoke stage cores in one dispatch**: create the `Scheduled` state, transition to `Running` with the materialized input snapshot, claim the attempt, run the body, and stage all of the stage checkpoints (`ActivityScheduled`, `ActivityStarted`, `ActivityAttemptClaimed`, the completion commit) into the coalescing working set in the same order the discrete hops would have produced them. The `StartActivity` and `InvokeActivity` work items for that span are **never enqueued** — the fused pass subsumes them.

- **Mechanism.** Extract each handler's stage core (the `ExecuteAsync` bodies, which are already cleanly separated from their dispatch plumbing) into stage services callable both by the existing per-kind handlers (the durable path, unchanged) and by a new fused pass selected by `RuntimeSchedulerPipelineSelector` when burst + `ReplaySafe` + toggle allow. No new command kinds; the durable wire contract is untouched.
- **Crash semantics.** If the host dies mid-fusion, the durable queue holds only the original `ScheduleActivity` item (plus whatever the last flush pinned). Redelivery re-dispatches it; the existing idempotency ladder — queue-level enqueue-by-identity (ADR 0031 ratification decision 1), status-based handler no-ops, and fold-forward claim state — resolves it exactly as a mid-segment coalescing crash resolves today: either the segment flushed (the redelivered item sees `Completed` state and no-ops) or it did not (the span replays from the last flushed checkpoint, harmless by declaration). The crash-convergence suites extend to fused spans.
- **What is NOT fused.** `External`/unmarked activities (their pre-activation flush and per-stage attempt visibility are correctness, per R2); any stage that suspends (bookmark creation exits the fusion and falls back to discrete hops); intrinsics with mutating state loads (`Finish`/`Correlate`/`SetName`) in the first iteration; anything outside a live burst. The fallback at every exit point is the existing discrete chain — fusion is an optimization of a path that stays correct without it (the ADR 0031 invariant, verbatim).
- **Observability.** The same checkpoint documents, states, and inspection projections are produced — fewer dispatches, identical durable history. `DurableRoundTripDiagnostics` gains a fused-pass counter so the benchmark can attribute the win. Poison attribution coarsens from per-stage to per-span for `ReplaySafe` activities only; this is the R2 trade restated at dispatch granularity, and the fail-safe default (`External` ⇒ never fused) keeps the asymmetry pointing at durability.

## Decision D2 — inline completion propagation within a burst

The completion cascade (hops 4–7 above) collapses symmetrically: when a child completes inside a live burst and its **parent is a `ReplaySafe` routing composite** (`Flowchart`/`Sequence` and other pure-routing containers, which the ADR 0032 worked classification already pins as `ReplaySafe`), the fused completion pass runs parent-completion evaluation, outcome routing, continuation scheduling, and the completion checkpoint **in the same handler pass**, emitting the successor's `ScheduleActivity` intent directly. Four hops per edge become part of one pass; combined with D1, an ordinary `ReplaySafe` leaf costs ~1–2 dispatches instead of ~7.

The same guards apply: `External` parents keep the discrete cascade; fan-in joins that must observe sibling branches fall back to discrete evaluation whenever the join's semantics require cross-branch state it cannot see inline (first iteration: fuse only single-predecessor edges, the straight-line case the hot-loop benchmark measures); the single-writer drain (ADR 0031 ratification decision 2) already serializes the cascade, so inlining it changes cost, not ordering.

## Decision D3 — publish-time routing tables in the pinned executable

`WorkflowParentActivityCompletionSchedulerWorkHandler` routes outcomes by walking the executable graph at runtime, per completion. The outcome→successor relation is fully determined at publish time; compile it into the pinned executable (an `ExecutableNode`-level `outcome → successor executable-node ids` table, alongside the existing node metadata) so runtime routing is a dictionary lookup. This is pure compile-time work with zero runtime risk, it benefits `External` activities too (the discrete cascade does the same lookup), and it ships independently of D1/D2 — it is also the piece D2 wants, since an inline pass should not pay a graph walk either. Interaction with [ADR 0038](0038-artifact-hash-is-purely-behavioral-and-executables-are-content-addressed.md): the table is derived deterministically from the same graph the hash already covers, so it adds no new behavioral surface; whether it participates in the content hash or is recomputed on materialization is an implementation detail the spec resolves (recomputed-on-load keeps the hash untouched and is the conservative default).

## Decision D4 — completion batching at quiescence (deferred unless evidence demands it)

The third idea from the campaign — folding straight-line completion cascades into the segment flush the way checkpoints already fold — is **subsumed by D1+D2 for the burst case** (a fused chain already reaches quiescence in one pass) and only adds value if fusion cannot form (no burst) yet cascades still dominate, a shape no current measurement shows. Record it as deferred; re-open it only if the Unit-C throughput instrument or container traces surface a non-burst cascade cost worth cutting. Ratifying D4 as *deferred* is intentional — it keeps the unit bounded and honest.

## Guardrails (the non-negotiables, same discipline as 0031/0032)

1. **Byte-identical durable state**: a run with fusion disabled (or no burst) commits byte-identical checkpoint/state documents to a fused run, proven by the same guardrail harness spec 109 used (ENABLED-vs-DISABLED end-to-end comparison).
2. **Crash convergence**: the coalescing crash-convergence suites extend to kill points inside a fused span, for both D1 and D2 shapes, plus the `External`-parent and suspend fallback exits.
3. **`External` untouched**: the spec-095 attempt/poison/attribution tests prove `External`/unmarked behavior is bit-for-bit unchanged.
4. **Toggle**: fusion ships behind a feature toggle (like the spec-109 fast path) so any regression is a config rollback, and the benchmark A/B stays runnable forever.

## Consequences

Hot loops of `ReplaySafe` activities drop from ~7 dispatches per activity-edge to ~1–2, cutting the 55–78% dispatch-machinery share — the projected 2–3× on in-memory hot-loop CPU and a proportional cut to the durable drain's claim round-trips (each elided hop is an elided durable claim/ack on Groundwork providers). Costs: the stage cores get a second caller, so their extraction must be behavior-preserving (the handler test suites pin this); the scheduler's mental model gains a second dispatch shape that contributors must learn (mitigated by the fallback rule: *fused = the same stages, same order, same documents, one pass*); and poison/attempt attribution for `ReplaySafe` spans coarsens as ratified in R2. The spec-095 FR wording that presumes one work item per stage needs the same style of amendment R2 shipped (amendment travels with the implementing unit, per the pre-release rule).

## Alternatives considered

*Keep per-stage hops and optimize the dispatch machinery instead* (cheaper claim/ack, leaner pipeline) was rejected: it shrinks the per-hop constant but keeps the ~7× multiplier, and spec 109 already proved the constant's biggest components (serialization, scope) are gone — the multiplier is the cost. *Fuse for everything, not just `ReplaySafe`* was rejected on the R2 asymmetry: for `External` activities per-stage redrive granularity is correctness-adjacent (attempt visibility, at-most-once effect placement), and the fail-safe direction must remain durability. *Bring back an Elsa-3-style long-lived execution context to host the fused pass* stays rejected for the reasons ADR 0031 already documents; fusion runs entirely inside the existing drain loop, ambient scope, and checkpoint committer. *Runtime-cached routing tables* (memoize the graph walk per executable) was rejected in favor of D3's publish-time compilation: the artifact is immutable and content-addressed, so computing routing at publish (or deterministically on load) is strictly simpler than managing a runtime cache.

## Follow-up

- **Speckit unit(s)** (Runtime Execution Seam bucket), sequenced after ratification: D3 first (independent, zero-risk, benefits both paths), then D1+D2 as one unit or two depending on review appetite — D1 without D2 still pays the 4-hop completion cascade, so measuring D1 alone understates the ceiling; the spec should A/B all three combinations with the existing benchmark harness (commits/run and executable-reads/run stay the deterministic evidence; wall-time claims follow the run-order-swap discipline).
  - **D3 implemented — [spec 119](../../specs/119-publish-time-routing-tables/spec.md)** (publish-time routing tables, recomputed on materialization per resolution #2: the `ExecutableNode.GetOrAddRoutingStructure<T>` memo + Flowchart outbound/inbound indexes; no schema/hash change).
  - **D1 + D2 implemented — [spec 123](../../specs/123-replaysafe-hop-fusion/spec.md)** (fused schedule→start→invoke pass and the inline single-predecessor completion pump both shipped). The spec (design + FR set + guardrail/A-B/crash test plan) and the ADR 0031 cross-reference note + spec-095 FR amendment travelled with this unit and are in place. **Shipped:** the stage-core extraction refactor (schedule/start/invoke-completion), `RuntimeReplaySafeFusionOptions` (default ON, resolution #3; `FuseCompletionCascade` dial for the D1-only A/B column), per-run dispatch/fused-span/inline-cascade/join-fallback counters (`RuntimeSchedulerDispatchDiagnostics`, surfaced on `DurableRoundTripDiagnostics`), the **D1 fused schedule→start→invoke driver** (`ReplaySafeFusionDriver`), and the **D2 inline completion pump**: `IReplaySafeSuccessorRoutingProbe` (Runtime.Core) with Flowchart/Sequence implementations resolves the cross-assembly single-predecessor check off the spec-119 memo (D3), and the driver pumps the completion cascade inline in drain-loop FIFO order via the coalescing session's peek/consume pair — a fusable successor re-enters the D1 pass (re-entrancy-guarded, iterative), while join edges (single-predecessor-only per resolution #1), child-fault evaluations, non-ReplaySafe parents, and the workflow tail keep the discrete cascade. Byte-identical guardrails (incl. multi-outcome branch and fan-in join with the join fallback proven via counters) and an 8-kill-point Groundwork crash-convergence suite (inside the inline completion pass and across the D2→D1 recursion boundary) confirmed the coalescing-session invariants empirically. A/B (ReplaySafe hot-loop×10, coalesced): dispatches **58 (none) → 36 (D1) → 5 (D1+D2)**; commits stay folded to 1 by coalescing.
- **Spec-095 FR amendment** travels with the D1 implementing unit (the FRs that enumerate per-stage work items and the 5–7-hop model).
- **ADR 0031 cross-reference update**: its follow-up list gains a pointer here; its "5–7 work-item hops" arithmetic gets a "see ADR 0047 for the ReplaySafe fusion that removes most of them" note when D1 ships.
- **Ratification resolutions** (resolved 2026-07-20, replacing the three open questions flagged at drafting):
  1. *D2 fan-in scope: single-predecessor edges only in the first iteration.* Joins keep the discrete cascade until a measurement shows inline join evaluation is worth its complexity — the hot-loop shapes the campaign optimizes are straight-line, and the fallback rule already keeps joins correct. Re-open as its own unit only with evidence.
  2. *D3 table placement: recomputed on materialization.* The routing table is derived deterministically from graph content the artifact hash already covers, so recomputing it when the executable is materialized keeps the content hash byte-stable, avoids a schema change to the persisted artifact, and preserves ADR 0038's hash semantics untouched. If profiling ever shows materialization-time computation matters, moving it inside the hashed content is a compatible later change (pre-release, no back-compat burden).
  3. *Toggle default: ON at ship.* Consistent with how coalescing shipped; the byte-identical guardrail plus the config-flip rollback bound the risk, and each implementing unit's PR must carry the benchmark A/B (fused off/on, commits + executable-reads as deterministic evidence) at the QA gate.
