# Elsa Glossary

These are Elsa-specific terms and bindings. Framework-level terms live in [root.md](root.md).

| Term | Canonical meaning |
|---|---|
| Elsa foundation workspace | The repository role where foundation libraries, architecture gates, maps, skills, and glossary knowledge make Elsa navigable and verifiable. |
| Elsa host | An ASP.NET Core application instance that composes selected Elsa features. In this repository that is `Elsa.Workbench`, a development and demo host; the shipped host is not yet built. |
| Elsa application | The Elsa application defined by the domain tree in the Elsa constitution. |
| Elsa foundation repo | `elsa-foundation`, this repository: the transitional baseline for Elsa foundation libraries, architecture knowledge, maps, specs, and default implementation work. |
| Weaver | The user-facing AI assistant experience in Elsa Studio. It is implemented through provider-neutral agent contracts, but Weaver is not the AI provider, SDK adapter, or workflow execution agent. |
| Provider SDK binding | An adapter from Elsa's AI-provider-neutral agent facade to one model or provider SDK, such as the GitHub Copilot SDK. |
| Agent harness provider | An adapter from Elsa's AI-provider-neutral agent facade to a higher-level agent runtime that can own long-running runs, skills, tools, artifacts, memory, sandbox execution, and sub-agent progress. |
| Agent run | One long-running harness execution inside an agent session. A run may produce progress, tool activity, artifacts, and proposals without redefining the user-visible conversation boundary. |
| Elsa.Primitives | The primitives domain replacing the historical `Elsa.Common`; it carries truly cross-cutting primitive abstractions without becoming a dumping ground. |
| Workflow design | The authoring side of workflows: definitions, drafts, versions, design-time validation, design-time persistence, and read models. |
| Design command recovery | Resolving an ambiguous design-command outcome by rereading authoritative design state rather than replaying the command's original response. A recoverable command exposes a stable target identity or deterministic lookup by which its committed outcome can be found. |
| Workflow graph operation | A provider-neutral workflow-design edit intent, such as adding an activity, connecting activities, setting the root, changing a property, or setting designer metadata. Agent providers may generate graph operations, but workflow design owns their meaning and the designer owns their application to working state. |
| Workflow runtime | The execution side of workflows: executable artifacts, instances, runtime state, bookmarks, logs, and execution integrations. |
| Bookmark | A durable runtime resume handle owned by one activity execution. It identifies the stimulus and pinned-artifact resume target that may continue that execution; it is not a timer or a workflow-control command. |
| Bookmark expiration | The optional `BookmarkState.ExpiresAt` admissibility cutoff for a resume handle. `null` means the bookmark remains matchable indefinitely; a finite value makes it unmatchable at or after that instant. By itself, expiration does not schedule work, select an outcome, cancel an activity or workflow, delete the bookmark, or emit a timeout event. See [bookmark expiration](../bookmark-expiration.md). |
| Execution Evidence domain | The Elsa domain that captures, stores, and exposes committed workflow-runtime facts for deterministic verification. Its planned module family begins with `Elsa.Workflows.ExecutionEvidence.Core`, `Elsa.Workflows.ExecutionEvidence`, and `Elsa.Workflows.ExecutionEvidence.Api`, followed by the durable `Elsa.Workflows.ExecutionEvidence.Persistence.Groundwork` provider. Existing Elsa domains do not receive Execution Evidence concepts; adapters owned by the Execution Evidence domain consume their generic extension seams. |
| Execution evidence | An immutable, structured record of a committed semantic workflow-runtime fact, suitable for deterministic automated verification. It includes the causation and durability facts needed to interpret that semantic fact, but excludes implementation-level mechanics such as middleware traversal, scheduler loops, actor callbacks, and method invocations. Authoritative evidence is recorded with its runtime checkpoint and delivered after commit with at-least-once semantics; stable evidence identity and workflow-local sequencing support deduplication and gap detection. Attempted or uncommitted behavior and implementation mechanics belong to diagnostic telemetry and are not execution evidence. |
| Evidence session | An explicitly opened capture scope identified by an `EvidenceSessionId`. On a host where the Execution Evidence module is enabled, only workflows associated with an evidence session produce execution evidence. The association propagates through scheduling, stimuli, child workflows, and resumed execution. Test frameworks may associate the session with a test-run identifier, but testing terminology is not part of the runtime contract. |
| Evidence kind | The stable string identity and schema version of a typed execution-evidence payload. The Execution Evidence `.Core` module defines the baseline catalog; optional modules may register additional kinds by referencing that contract. Unregistered ad hoc payloads are not execution evidence. |
| Evidence capture profile | The value-capture request attached to an evidence session. It uses explicit subject allowlists and is constrained only by module-wide operational limits and pre-persistence sanitizers, not by a generalized host policy matrix. Metadata evidence remains available when a value is not captured. |
| Evidence value disposition | The explicit state of a value field in execution evidence: `captured`, `redacted`, `omitted`, or `truncated`. Consumers must not infer why a value is absent from a null or missing payload. |
| Evidence cursor | An opaque position returned by the Execution Evidence API for ordered continuation of a session query or wait. It lets a consumer resume without interpreting storage offsets or workflow-local sequence implementation details. |
| Evidence completeness boundary | A committed position through which an evidence range is known to be settled and gap-free, established by terminal workflow evidence, an explicit settled barrier, or completed evidence-session lifecycle. Only absence within such a boundary can support a definitive negative assertion; a timeout is inconclusive. |
| Evidence retention | The lifecycle policy that retains and deletes execution evidence as one complete evidence session. The retention period begins when the session completes; record-by-record expiry and automatic storage-pressure eviction are not part of the contract. |
| Evidence ordering | The ordering guarantee for execution evidence: a strict monotonic sequence per workflow instance and a stable ordinal within one checkpoint. Relationships across workflows use explicit causation references; session query order and timestamps are not a global semantic order. |
| Baseline evidence catalog | The Execution Evidence `.Core` catalog of committed workflow lifecycle, activity lifecycle, state mutation, bookmark lifecycle, incident lifecycle, stimulus and causation, scheduling, and checkpoint/barrier transition kinds. It excludes state reads, heartbeats, polling, middleware traversal, ordinary logs, and uncommitted exceptions. |
| Workflow alteration | An authorized, typed operator-requested change to an existing workflow execution. It is distinct from ordinary workflow progression and from changing workflow design. |
| Workflow alteration envelope | The persisted and wire-safe description of one workflow alteration: a stable kind, schema version, and data payload resolved by a trusted host-registered handler. It never persists a CLR implementation type or carries client-supplied executable code. |
| Alteration plan | A durable operator submission that groups an ordered set of workflow alterations with sealed tenant and execution-authority scope plus submitting-operator provenance. It captures matching workflow execution identities through durable keyset pagination, persists and deduplicates the complete cohort, seals that immutable target snapshot, and only then dispatches jobs; the API imposes no fixed target-count limit. |
| Alteration job | The deterministically identified per-workflow-execution application and result record produced from an alteration plan. It applies the plan's ordered alterations atomically: a failure leaves the workflow execution unchanged and later alterations unapplied. At-least-once delivery is reconciled against durable checkpoint evidence rather than blindly reapplying an uncertain command. |
| Workflow execution migration | An atomic workflow alteration that replaces an operationally suspended, fully quiescent execution's pinned executable with an exact, compatibility-validated artifact of the same workflow definition. Operational suspension can be represented by a suspended workflow aggregate or, for a parked Elsa execution, a suspended wait/root activity under a still-running aggregate; quiescence separately proves that no activity or delivery lane remains active. Incompatible nodes, activity contracts, bookmarks, scopes, or variable declarations reject the migration without changing the execution. |
| Fault | A failed execution transition: an activity attempted work but did not complete it successfully. A fault remains part of execution history even when a structural parent later handles its consequences. |
| Incident | A durable runtime issue record created from an activity fault or another operational anomaly so that its attention and handling lifecycle can be tracked. Changing an incident's status or resolution outcome does not rewrite the execution event or state that caused it. |
| Fault absorption | A structural parent's meaningful handling of a child fault, usually by routing alternate control flow. Absorption resolves the associated incident while preserving the child activity's faulted state as historical truth. |
| Incident suppression | Neutralizing an open or blocking incident because cancellation or subtree reclamation made its owning execution scope irrelevant. Suppression prevents a stale incident from blocking execution; it does not claim that the original fault was successfully handled. |
| Incident strategy | A host-contributed runtime policy applied automatically to activity-fault incidents that remain blocking after structural parent propagation and absorption finish. Publication resolves the authored strategy reference or host default, pins its alias and version into the workflow executable, and includes that identity in executable identity; Elsa Foundation’s parity baseline provides `Fault/1` and `ContinueWithIncidents/1`. |
| Incident strategy descriptor | Safe discovery and publication metadata contributed atomically with an incident strategy implementation: its stable alias and version, display name, and description. Publication and read-only APIs consume descriptors without constructing executable strategy services. |
| Incident resolution action | An extensible, runtime-only result object returned by an incident strategy or system resolution flow and executed by the workflow runtime, analogous to an MVC action result. Every action exposes a stable kind for durable classification, but the runtime executes the returned object rather than dispatching through that kind or a persisted CLR type. Initial built-in kinds are `FaultWorkflow`, `ContinueWithIncidents`, `WaitForIntervention`, `AbsorbFault`, and `SuppressIncident`; an absent outcome means no action has executed, while undefined retry/suspension behavior has no placeholder action type. |
| Incident resolution outcome | Optional durable evidence created only after an incident resolution action executes. It records the stable action kind and application time, the applicable incident-strategy alias and version, any system-resolution source, and policy-safe metadata; strategy and system provenance may both be present when the runtime substitutes a fallback action. It is data rather than an executable CLR object, operator command, or REST mutation surface. |
| Continue with incidents | An incident resolution action that leaves the failed activity and its incident intact while allowing already-scheduled independent work to continue. It stops propagation of that fault; it does not convert the failed branch into success or synthesize activity outcomes. |
| Wait for intervention | An incident resolution action that leaves the incident blocking, stops work causally dependent on its failure, and schedules no automatic retry. It preserves the workflow's existing lifecycle status rather than representing ordinary workflow suspension. |
| Activity catalog | The persisted source of truth for activities visible to design-time consumers. Picker visibility comes from catalog rows, not live scanning. |
| Activity definition | Stable provider-neutral identity and authoring/catalog metadata for one reusable activity type. It is not a CLR type record and not a workflow definition. A definition may be Design-owned or source-owned and has immutable versions. |
| Activity definition version | One immutable version of an activity definition, carrying stable provider and runtime-consumer key/schema identities, opaque provider-owned descriptor payload, I/O contract, facets, source identity, lifecycle, and content hash. Runtime never dispatches by a CLR type name stored in this universal contract. |
| Activity provider | A producer of activity definitions or versions. A provider identifies its persisted contract with a stable provider key and provider schema version; it may be CLR scanning, graph authoring, JavaScript, C#, or another future shape. |
| Runtime activity consumer | Runtime implementation that recognizes a stable consumer key and schema version and constructs or executes the opaque descriptor payload. Provider identity and consumer identity are separate so multiple authoring sources can target one runtime capability without using CLR type identity as a wire contract. |
| Source-owned activity definition | An activity definition whose canonical version content is owned by an external provider source, such as CLR assembly reconciliation. Its catalog identity and immutable runtime template are committed together; editing/customizing it requires a fork into a new Design-owned definition. |
| Graph activity | A reusable composite activity authored as an activity graph. At runtime its children execute inside the same workflow execution and ordinary activity execution hierarchy; crossing the composite boundary does not create a child workflow. |
| Workflow-as-activity | Historical Elsa 3 concept imported into Elsa 4 reusable activity definitions. It is not an Elsa 4 runtime model. Starting another workflow is the separate, explicit `ExecuteWorkflow` behavior; reuse through a graph activity stays within the current workflow execution. |
| Activity availability policy | The design-time rule that determines whether an activity type can be offered for new selection in the workflow definition editor. It operates at the activity type key level, not the activity definition version level, and does not by itself invalidate existing workflow definitions or decide whether runtime execution is allowed. |
| Activity addability | Whether an activity can be newly selected from the workflow definition editor's picker. Addability does not control whether an already-authored activity node is rendered when an existing workflow definition is opened. |
| Non-addable activity node | An already-authored workflow definition node whose activity type is no longer available for new picker selection. The designer may surface this as a non-blocking warning, but addability alone does not prevent viewing, editing unrelated workflow content, saving, or publishing. |
| Host activity availability baseline | An optional host configuration boundary that constrains which catalog activities may ever be offered by design-time surfaces. When omitted, all non-removed catalog activities are eligible for selection before narrower management or user-context policy is applied; include rules narrow the eligible set, and exclude rules always remove matches from that set. |
| Activity availability policy stack | The ordered filtering model for activity selection: catalog rows, then optional host include rules, host exclude rules, management settings, and later user-context policy such as role-based access. Later layers may narrow the visible set but cannot re-add activities removed by an earlier host boundary. |
| Activity availability settings | Optional persisted management policy data that narrows which baseline-eligible activities are offered for new selection in design-time surfaces. Settings use one mode, such as all-except or only, with explicit activity keys and set names; when no settings exist, every baseline-eligible activity remains available. Settings are stored separately from the activity catalog so catalog reconciliation remains a fact update, not a policy edit. |
| Activity availability scope | The context key for activity availability settings. Version 1 uses a single host-default scope, but the model keeps the scope explicit so later tenant, workspace, role, or user-specific policies do not require redefining the settings contract. |
| Activity availability state | A diagnostic result that explains why an activity is or is not offered for new selection after the policy stack is evaluated, such as available, blocked by the host baseline, hidden by management settings, or removed from the catalog. |
| Unresolved activity availability reference | An activity key or activity set name referenced by host baseline configuration or management settings that is not currently resolvable from the catalog or registered host-defined sets. Unresolved references are retained and surfaced through diagnostics rather than silently discarded or treated as startup failures. |
| Activity set | A host/developer-defined named group of activity type keys used by activity availability policy. Sets are explicit collections rather than wildcard patterns, so adding a new activity to a package does not silently make it available through an existing set. |
| Workflow root activity | The single activity a workflow definition/executable runs. It may be a primitive activity or a composite activity such as `Sequence`, `Flowchart`, or `StateMachine`; composition details belong to that activity. |
| Workflow executable | The runtime-owned artifact produced from design-time source and consumed by runtime execution. It carries one compiled root activity plus runtime identity, source reference, resume targets, timestamps, and compatibility metadata. |
| Workflow definition state | The authored workflow document stored with drafts and versions in the design domain. It owns authored content, including one root activity, not runtime state. |
| Workflow definition compiler object | A short-lived code-first authoring object that emits a workflow executable when its build contract runs during compilation or publication. It is not a workflow instance, does not own runtime activity objects, and is never persisted. |
| Workflow-scoped variable | A variable declared by the workflow definition and visible throughout the workflow unless shadowed by a narrower variable scope. |
| Workflow variable alteration | A workflow alteration that replaces an existing workflow-scoped variable value by stable variable reference key, guarded by the expected root variable-frame revision. It does not address container or iteration variable frames. |
| Container-scoped variable | A variable declared by a container activity and visible only within that container activity's child execution scope, including nested descendant activities; when nested containers declare a variable with the same name, the nearest containing scope wins. |
| Variable reference key | The stable identity used by authored variable expressions to reference a variable within its declaring scope. Variable names are display and convenience access names, not the durable identity of a reference. |
| Type alias | The stable, frozen string identifier under which a CLR type is registered in `IWellKnownTypeRegistry` and referenced by authored arguments (e.g. `String`, `Elsa.Http.HttpRequest`). The CLR type behind an alias may be renamed or moved freely; the alias must never be renamed. Bare (dot-less) aliases are reserved for framework primitives; module types use dotted/reverse-DNS aliases. |
| Collection kind | The shape applied to an authored argument's element type: `Single`, `Array`, `List`, or `HashSet`. Combined with a type alias it forms a type reference and resolves to `T`, `T[]`, `List<T>`, or `HashSet<T>`. Replaces the former boolean "is array" flag. |
| Type reference | The two-field value object `{ Alias, CollectionKind }` that is the sole persisted representation of an authored Variable/Input/Output's type. It carries no namespace, assembly name, or assembly version. |
| Type descriptor catalog | The design-time, module-contributed catalog of selectable argument types (keyed by alias, each carrying display name, category, and a default-editor hint), aggregated from `IVariableTypeDescriptorProvider` contributions and served to the designer. Distinct from the runtime resolution registry per the §2.6.4 design-time/runtime split, but keyed by the same alias and sharing one `TypeDescriptor` shape record. |
| Argument descriptor | The uniform notion that a workflow Variable, Input, and Output each carry the same `{ Alias, CollectionKind }` type reference, so collection-ness round-trips identically for all three (the records themselves remain standalone per FR-030). |
| Facet | A module-owned, kinded, schema-versioned design metadata fragment attached to a broader model. Core stores, hashes, validates generic shape, and round-trips facets without owning their payload semantics. |
| Artifact-only runtime | The rule that runtime execution must be able to load and run from the published artifact without requiring design documents. |
| Runtime checkpoint commit | The atomic runtime operation that applies a named checkpoint's state changes and records any post-commit delivery work. Delivery of recorded work is handled by a separate post-commit delivery module. |
| Reconciliation | A process that updates persisted design/catalog state from authoritative sources such as CLR activities, JSON import, or workflow definitions. |
| Content authority | The role of holding the canonical content of a versioned entity. Content identity is defined over a **canonical serialization** (deterministic key ordering and formatting), not a raw stored blob, so the same logical state hashes identically regardless of storage encoding. For a reconciled version, the external source is content-authoritative: for a given `(id, version)` the source's canonical content is the version's content, and the catalog never rewrites it. Distinct from retention authority; the two never conflict because a version is immutable, so a fixed `(id, version)` is single-valued everywhere and same-`(id, version)`-different-canonical-content is a broken-source error, not a merge (surfaced diagnostically — logged in v1, enforced as a hard throw once a persisted content hash exists; see spec 085 FR-006). |
| Retention authority | The role of deciding which versions exist and persist. The catalog is retention-authoritative: it is an append-only, write-once ledger that a source can add to but can never mutate or delete from (a source disappearing is informational only). Distinct from content authority. |
| Activity construction | The runtime-side process that turns a descriptor type, descriptor payload, and argument bags into a live `IActivity`. |
| Activity contract | Versioned activity metadata describing stable input, result, outcome, activation, and policy schemas. A workflow executable pins the contract identity, version, stable member keys, and compatibility fingerprint it requires. |
| Activity input binding | An immutable executable instruction that supplies one activity input from a literal, workflow-request member, variable read, causally available activity-result projection, or explicit expression. It has no writable address or runtime memory-block identity. |
| Activity execution | One logical runtime invocation of an executable activity node within a workflow execution, with identity and pinned inputs stable across retries and resumptions. Multiple activity executions may reference the same authored activity when loops, composite slots, cycles, or repeated scheduling revisit that activity. Also called an activity invocation when contrasting it with an activation attempt. |
| Activity rescheduling alteration | A workflow alteration that supersedes an eligible scheduled, waiting, suspended, or faulted activity execution and schedules a distinct logical activity execution with explicit lineage to it. It does not rewrite the original execution, reuse its identity, or represent ordinary retry or resumption. |
| Activity scheduling alteration | A workflow alteration that schedules a fresh execution of an authored activity node under an explicitly selected active parent activity execution. The runtime derives scope, provenance, pinned executable, execution identity, and authored inputs; the caller cannot supply those runtime-owned facts or an arbitrary input payload. |
| Activity activation attempt | One transient CLR activity object and service-activation lifetime used to attempt an activity execution. Retry or resumption creates a fresh attempt while retaining the logical activity execution identity, pinned inputs, and committed private state. |
| Activity completion result | The single immutable typed payload committed atomically when an activity execution completes successfully. Named activity outputs are projections from this payload, not independently writable slots. |
| Activity execution scope | The runtime scope owned by an ordinary activity invocation, including a reusable or third-party activity. The framework does not distinguish a “custom activity invocation scope”; all activities participate in the same execution, checkpoint, cancellation, incident, and inspection rules. A graph-backed composite may add a boundary scope for its nested activity executions without creating a workflow execution. |
| Activity execution inspection projection | A runtime-owned read model for inspecting one activity execution, separate from continuation state and keyed by activity execution identity. It may include captured evidence such as outcomes, value snapshots, bookmarks, incidents, and scheduling provenance. |
| Activity execution value snapshot | Policy-governed inspection evidence for an activity input or output observed during one activity execution. A value snapshot may contain metadata only or include payload when runtime payload capture policy allows it. |
| Activity scheduling provenance | Runtime-owned correlation data that explains why and from where an activity execution was scheduled, including structural parent, temporal scheduler, optional branch or iteration identity, optional execution path or scope identity, and scheduling cause. |
| Publishing/compile bridge | The domain that reads design-side state and produces runtime artifacts without making Runtime depend on Design. |
| Runtime checkpoint | The workflow runtime commit boundary where continuation state, inspection projections, outbox intents, and related runtime changes become durable together according to runtime checkpoint policy. |
| Scheduler-boundary checkpoint | A runtime checkpoint that must persist before scheduler work can safely continue, such as scheduling an activity execution, starting invocation, suspending on a bookmark, completing, faulting, or canceling. |
| Elsa 3 import | Compatibility strategy for Elsa 3 assets. The boundary is import into Elsa 4-native models, not running Elsa 3 behavior in place. |
| Composition feature | An internal host-composition unit that registers services, endpoints, middleware, tasks, settings, or dependencies in an Elsa shell. Features describe how a host is assembled; their names and dependency graph are not a stable client contract. |
| API capability | A stable, versioned, client-visible promise that an active shell exposes a supported API contract, advertised with canonical shell-relative links. Capabilities are declared explicitly rather than inferred from composition-feature names, are caller-permission-neutral, and may have a many-to-many relationship with features: one feature can provide several capabilities and one capability can require several features. |
| Endpoint security disposition | The single inspectable access classification attached to a first-party endpoint: Foundation permission, intentional public access with a category and reason, host credential, or an explicitly owned host ASP.NET Core policy for a dynamic/integration surface. The host-policy form carries selected named policies when present; an empty policy set records authenticated-principal/default-policy compatibility without inventing a policy name. It declares how access is enforced without moving permission semantics or provider-specific claim mapping into the endpoint framework. |
| Route ownership metadata | Immutable ASP.NET Core endpoint metadata identifying whether a route is host-, module-, or dynamic-shell-owned, its stable owning module/feature identifier, and, for dynamic shell routes, the shell and exact generation. Routing inventory, collision diagnostics, and lifecycle binding use this identity; display names and route paths are not ownership identities. |
| Dynamically unloadable endpoint module | An endpoint-owning module whose assembly is promised to become collectible after its routes, services, serializers, and generation state are removed. It uses explicit endpoint mapping, cannot depend on FastEndpoints, and requires repeatable collectible-`AssemblyLoadContext` weak-reference evidence rather than process-memory observation alone. |
| Feature composition | Selecting and activating composition features and their dependencies in a shell/API host. Composition determines which API capabilities can be advertised but is not itself the client-visible discovery contract. |
| Elsa host management key | A server-side credential for host-control surfaces such as module management and Extension Builder operations. It is not a user authorization token and should not be exposed to browser code; browser calls should be user-authorized, while server-side bridges may attach the host management key when invoking another Elsa host. |
| Studio management bridge | A Studio-owned server-side surface that lets browser clients request host-control operations without learning backend host topology or carrying an Elsa host management key. The bridge authorizes the user-facing request, then invokes the target Elsa host with server-side credentials where needed. |
| Host-control permission | A user authorization permission for requesting Studio-mediated host-control operations. Use coarse read/manage permissions per host-control area, such as `module-management.read`, `module-management.manage`, `extension-builder.read`, and `extension-builder.manage`; possessing a Studio session alone is not enough. |
| Seam | In Elsa docs, a published contract boundary between sub-domains, normally represented by `.Core` contracts. See [seams and bridges](../seams.md). |
| Bridge | Code that connects two contract boundaries from above, depending on both contracts without making either side depend on the other. See [seams and bridges](../seams.md). |
| Extension Builder workspace | A logical Git-backed authoring space for one repository. It contains one or more .NET solutions, projects, source files, and related repository metadata. It is the source-control boundary first; build, package, and promotion behavior are downstream concerns. Multiple users may work in the same workspace through separate working copies. |
| Extension Builder working copy | A server-side Git checkout/clone for a specific user, session, or branch within an Extension Builder workspace. Source editing happens in a working copy, while the workspace remains the logical repository boundary visible in Studio. |
| Extension Builder working branch | The Git branch selected for an Extension Builder working copy. New edit sessions default to an explicit working branch rather than silently editing the repository default branch. |
| Extension Builder managed repository | The default Extension Builder workspace creation mode where Elsa Server initializes and owns a local Git repository first, creates an automatic initial commit for generated starter files, then lets the user connect or change the remote origin and push to their own repository later. |
| Extension Builder server-local repository | An existing Git repository on the Elsa Server filesystem that is registered as an Extension Builder workspace instead of being created or cloned by Extension Builder. |
| Extension Builder solution | A .NET solution file inside an Extension Builder workspace. It is the primary coordination boundary for solution-level build/test/package commands in the Studio UX. |
| Extension Builder project | A .NET project file inside an Extension Builder workspace or solution. It may produce packages or runtime contributions, but package identity is output metadata rather than the primary authoring boundary. |
| Extension Builder package artifact | A package output produced from an Extension Builder project or solution. It can be promoted to package feeds or module catalogs, but it is downstream from repository authoring. |
| Extension Builder solution explorer | The authoring navigation surface for a Git-backed Extension Builder workspace. It is repository-rooted, auto-focuses the only solution when exactly one solution exists, and uses a solution picker when multiple solutions exist. It shows repository, solution, project, folder, and file structure; build, promotion, runtime, and source-control details belong in contextual inspectors rather than as primary tree nodes. |
| Extension Builder repository workbench | The primary Extension Builder screen for selecting a Git-backed workspace, opening its active working copy, navigating solutions and files, editing source, and inspecting source-control/build state. |
| Extension Builder editor intelligence | The code understanding available inside Extension Builder. The first implementation target is build-backed intelligence: syntax-aware editing plus build/test diagnostics mapped to files. The UX may reserve space for future Roslyn/LSP-backed capabilities without implying they exist. |
| Extension Builder v1 editor scope | The first useful online .NET editor slice: source editing, repository navigation, file operations, build/test diagnostics, Git operations, and templates, without full IDE features such as debugger, terminal, semantic refactoring, or full NuGet management. |
| Extension Builder source-control inspector | The contextual source-control surface for a Git-backed Extension Builder workspace. It exposes real Git status, diffs, staging, unstaging, commit, and push flows; staged changes are the commit boundary, with stage-all as a convenience. |
| Extension Builder template | A scaffold applied at a specific authoring level: repository templates create managed workspaces, solution templates add .NET solutions, project templates add .NET projects to a solution or repository, and item templates add files to compatible projects. |
| Extension Builder build worker | The isolated execution boundary that runs restore, build, test, and pack operations for Extension Builder repositories outside the Elsa Server host process. |
| Execution liveness state | The runtime facet that tracks a workflow execution's ownership and liveness — lease, heartbeat, drain, and interruption. Named `ExecutionLivenessState` (W14, was `OperationalState`; NM-4/R5). Distinct from workflow hold state and scheduler state (R6). Its persisted document kind wire value remains `"operationalState"`. |
| Workflow hold state | The runtime facet holding an administrative pause/hold that sits outside normal workflow continuation state. Named `WorkflowHoldState` (W14, was `ControlPlaneState`; R5). Its persisted document kind wire value remains `"controlPlaneState"`. |
| Workflow execution actor | The in-process single-writer mailbox that serializes all command dispatch for one workflow execution id, enforcing the single-writer ownership contract. Named `IWorkflowExecutionActor` (W14, was `IWorkflowExecutionAgent`; R8) so that `Agent` is reserved for the AI-assistant domain. |
| Distributed actor provider | The opt-in clustered `IWorkflowExecutionActorProvider` (`DistributedWorkflowExecutionActorProvider`, leaf `Elsa.Workflows.Runtime.Distributed`; W20/E3-3) that layers per-execution *placement* over the in-process provider: when this node owns the execution's placement it returns the local in-process actor, otherwise a `ForwardingWorkflowExecutionActor` routes the command to the owning node via the durable command transport and returns `Deferred`. Placement is best-effort **routing** (which node drains); it is never the safety boundary. Double-execution is prevented by the unchanged W5 single-writer **fencing** token checked at checkpoint commit, which rejects a superseded node's late write (`RuntimeStaleFencingTokenException`). This placement-is-routing / fencing-is-safety split is the heart of the unit. A leaf-only provider per §2.7 — Runtime.Core gains zero references. |
| Execution placement lease | The per-execution ownership record (`ExecutionPlacementLease`, leaf `Elsa.Workflows.Runtime.Distributed`; W20) that says which cluster node currently drains a workflow execution. Acquired/renewed by a compare-and-swap that issues a strictly greater placement token (`IExecutionPlacementStore.TryClaimAsync`), expires on a `TimeProvider`-driven lease duration, and is renewed each pump sweep while the owner keeps draining. A placement lease is a routing hint, distinct from the W5 execution (fencing) lease that guards durable commit; losing placement mid-drain does not by itself corrupt state — the fencing token does that. |
| Execution command transport | The durable cross-node command inbox (`IExecutionCommandTransport`, leaf `Elsa.Workflows.Runtime.Distributed`; W20) that carries commands for an execution owned by another node. Ack-based/at-least-once: `SendAsync` appends, `LeaseAsync` hides an item under a visibility lease for one owner, `AckAsync` removes it only if the caller still holds a live lease. If the owning node dies after leasing but before acking, the lease expires and the survivor re-drives the item on failover claim — re-drive is safe because the fencing token, not the transport, prevents a second durable execution. The persisted document kind `executionCommandTransport` and its v1 golden-fixture wire shape are frozen (§E6); a durable Groundwork implementation is a named follow-up that must reuse them unchanged. |
| Workflow drain | The runtime process of draining queued commands for a workflow execution to a settled state. A `Drainer` runs the per-execution drain loop; a `WorkflowDrainOrchestrator` (was `…DrainCoordinator`) sequences the command-triggered multi-step drain (R4). |
| Recurring-trigger schedule | The runtime facet for Timer/Cron **start** triggers: a durable `RecurringTriggerSchedule` record (persisted document kind `recurringTriggerSchedule`) holding a schedule's next occurrence, drained by a hosted pump (`RecurringTriggerPumpTask`) that fires the trigger stimulus through `IStimulusRouter` to *start* a workflow (W16). Distinct from a **durable timer**, which resumes an *existing* execution (it has a `WorkflowExecutionId`); a start trigger has none. Missed-occurrence policy: after downtime a schedule fires at most once and advances to the next future occurrence — the backlog is never replayed. Occurrences are claimed with a compare-and-swap advance (`TryAdvanceAsync`) so at most one worker fires a given occurrence, which is also the seam a future clustered store keeps to make the pump cluster-safe (W20). |
| Groundwork | Codename for the provider-neutral, document-oriented persistence library family (`Groundwork.Core`/`.Documents`/`.PostgreSql`/`.Sqlite`) that backs Elsa's runtime persistence seams as an opt-in lane. Portable but equality-index-only, so it serves runtime stores rather than the `IQueryable`-bound design persistence. Kept as a codename with this entry rather than renamed (NM-11/R5). |
| Nuplane | Codename for Elsa's modular dynamic-loading strategy layer (`Elsa.Modularity.Nuplane`): loading Layer-3 implementations, helper libraries, and optional features at composition time. Elsa adopts the host-pins-`.Core`, Nuplane-loads-implementations model (constitution §E5). Kept as a codename with this entry (NM-11/R5). |
| Quiesce / quiescence | Bringing a workflow execution to a safe, settled state with no in-flight work — e.g. at end-of-drain, where the buffered checkpoint segment is folded and flushed through the checkpoint committer. Documented jargon (NM-12/R5). |
| Passivation | Deactivating a workflow-execution actor at a defined boundary (after checkpoint commit, entering durable suspension, registering a volatile wait, or host drain), releasing its in-memory mailbox while durable state is preserved. Documented jargon (NM-12/R5). |
| Control plane | Historical infra metaphor for the administrative/out-of-band command surface over a workflow execution. The persisted runtime facet it named is now **workflow hold state** (`WorkflowHoldState`); the term survives only in preserved wire strings and the `ControlPlaneCommand` activation reason. Documented for provenance (NM-12/R5). |
| Secret key-ring | The secrets rotation seam (`ISecretKeyRing`): one active encryption key plus zero or more additional decryption keys, each identified by a validated key id. The value protector tags ciphertext with the active key id (`v2:<keyId>:nonce:tag:ciphertext`) and still reads legacy `v1:` payloads, so rotating the master key adds a new active key without making existing data unreadable. Key ids are validated at startup (non-empty, no `:`, unique, active key present). See [secrets key rotation](../secrets-key-rotation.md). |
| Durable identity store | The Groundwork-backed persistence provider for the Foundation identity domain (`IdentityGroundworkPersistence` shell feature). It replaces the in-memory identity stores so users, roles, external identities, and tenant memberships survive restarts, using the identity domain's own storage manifest (`elsa-identity`) with wire-safe document kinds (`identityUser`, `identityRole`, `identityExternalIdentity`, `identityTenantMembership`) frozen by golden fixtures. |
| Engine telemetry | The workflow runtime engine's own distributed-tracing self-instrumentation (MS-9): `ActivitySource`-based spans for the four hot-path phases (drain, dispatch, activity execution, checkpoint commit) emitted from source `Elsa.Workflows.Runtime`. It **emits** spans a host's OpenTelemetry SDK or `ActivityListener` subscribes to; it is off by default (no-op `IWorkflowEngineTracer`) and enabled by the `WorkflowsRuntimeTracing` feature. Distinct from the OpenTelemetry ingestion domain. See [engine telemetry](../reference/engine-telemetry.md). |
| OpenTelemetry ingestion domain | The `Elsa.Diagnostics.OpenTelemetry(.Core)` backend that **receives** OTLP telemetry pushed by *other* processes (OTLP/HTTP protobuf collector + in-memory store + query/live-feed API), composed as the `DiagnosticsOpenTelemetry` feature. It is a telemetry *sink*, not engine self-instrumentation — the engine never pushes its own spans into it. Contrast with engine telemetry. See [engine telemetry](../reference/engine-telemetry.md) and [diagnostics-observability-readiness](../program-goals/diagnostics-observability-readiness.md). |
| Engine tracer contract | `IWorkflowEngineTracer` (`Elsa.Workflows.Runtime.Core.Diagnostics`): the single-implementation replacement contract whose `Start*` methods return `Activity?` for each engine phase. The runtime composition root registers the allocation-free `NullWorkflowEngineTracer`; the tracing feature replaces it with `ActivitySourceWorkflowEngineTracer`. Instrumentation is behaviour-preserving: no new awaits in fenced sequences, tags set only via `activity?.SetTag` after values exist. |
| Not-found error contract | The shared API rule (MS-14, issue #393) that a missing entity surfaces as `404` ProblemDetails rather than a generic `500`. `EntityNotFoundException` (`Elsa.Primitives.Exceptions`) is thrown by definition/version store lookups and caught in the FastEndpoints handler base classes (`ElsaRequestHandlerEndpoint`, `ElsaCommandHandlerEndpoint`), which map it to `404`. The global `ProblemDetailsFastEndpointConfigurator` gives every Elsa endpoint an RFC 7807 error shape. |
| Value representation | The declared form in which an activity result exists at a value-flow boundary, independent of the activity that produced it. Initial forms are `TypedValue`, `StructuredValue`, `TextValue`, `FormattedContent`, `BinaryContent`, `DurableReference`, and `TransientResource`; media type is optional metadata of formatted content, not the general value-flow concept. |
| Output binding coercion | The target-aware conversion of an activity result into the declared type and representation of a workflow variable or consuming activity input. Coercion is validated and pinned during publication and applied at runtime through a persistence-safe, deterministic conversion profile. |
| Conversion profile | A stable, versioned converter declaration describing supported source representations, target aliases, and conversion options. Elsa-built-in and module/host-registered profiles are available at publication; runtime applies only the profile pinned in the executable. |
| Transient result flow | Explicit in-memory activity-to-activity value flow for a `TransientResource` that cannot cross checkpoint, suspension, retry, migration, or worker boundaries and cannot be captured into durable workflow state. |
