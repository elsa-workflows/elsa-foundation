# Elsa Glossary

These are Elsa-specific terms and bindings. Framework-level terms live in [root.md](root.md).

| Term | Canonical meaning |
|---|---|
| Elsa foundation workspace | The repository role where foundation libraries, architecture gates, maps, skills, and glossary knowledge make Elsa navigable and verifiable. |
| Elsa host | The `Elsa.Server` ASP.NET Core application instance that composes selected Elsa features. |
| Elsa application | The Elsa application defined by the domain tree in the Elsa constitution. |
| Elsa foundation repo | `elsa-foundation`, this repository: the transitional baseline for Elsa foundation libraries, architecture knowledge, maps, specs, and default implementation work. |
| Weaver | The user-facing AI assistant experience in Elsa Studio. It is implemented through provider-neutral agent contracts, but Weaver is not the AI provider, SDK adapter, or workflow execution agent. |
| Provider SDK binding | An adapter from Elsa's AI-provider-neutral agent facade to one model or provider SDK, such as the GitHub Copilot SDK. |
| Agent harness provider | An adapter from Elsa's AI-provider-neutral agent facade to a higher-level agent runtime that can own long-running runs, skills, tools, artifacts, memory, sandbox execution, and sub-agent progress. |
| Agent run | One long-running harness execution inside an agent session. A run may produce progress, tool activity, artifacts, and proposals without redefining the user-visible conversation boundary. |
| Elsa.Primitives | The primitives domain replacing the historical `Elsa.Common`; it carries truly cross-cutting primitive abstractions without becoming a dumping ground. |
| Workflow design | The authoring side of workflows: definitions, drafts, versions, design-time validation, design-time persistence, and read models. |
| Workflow graph operation | A provider-neutral workflow-design edit intent, such as adding an activity, connecting activities, setting the root, changing a property, or setting designer metadata. Agent providers may generate graph operations, but workflow design owns their meaning and the designer owns their application to working state. |
| Workflow runtime | The execution side of workflows: executable artifacts, instances, runtime state, bookmarks, logs, and execution integrations. |
| Activity catalog | The persisted source of truth for activities visible to design-time consumers. Picker visibility comes from catalog rows, not live scanning. |
| Activity availability policy | The design-time rule that determines whether an activity type can be offered for new selection in the workflow definition editor. It operates at the activity type key level, not the activity definition version level, and does not by itself invalidate existing workflow definitions or decide whether runtime execution is allowed. |
| Activity addability | Whether an activity can be newly selected from the workflow definition editor's picker. Addability does not control whether an already-authored activity node is rendered when an existing workflow definition is opened. |
| Non-addable activity node | An already-authored workflow definition node whose activity type is no longer available for new picker selection. The designer may surface this as a non-blocking warning, but addability alone does not prevent viewing, editing unrelated workflow content, saving, or publishing. |
| Host activity availability baseline | An optional host configuration boundary that constrains which catalog activities may ever be offered by design-time surfaces. When omitted, all non-removed catalog activities are eligible for selection before narrower management or user-context policy is applied; include rules narrow the eligible set, and exclude rules always remove matches from that set. |
| Activity availability policy stack | The ordered filtering model for activity selection: catalog rows, then optional host include rules, host exclude rules, management settings, and later user-context policy such as role-based access. Later layers may narrow the visible set but cannot re-add activities removed by an earlier host boundary. |
| Activity availability settings | Optional persisted management policy data that narrows which baseline-eligible activities are offered for new selection in design-time surfaces. Settings use one mode, such as all-except or only, with explicit activity keys and set names; when no settings exist, every baseline-eligible activity remains available. Settings are stored separately from the activity catalog so catalog reconciliation remains a fact update, not a policy edit. |
| Activity availability scope | The context key for activity availability settings. Version 1 uses a single host-default scope, but the model keeps the scope explicit so later tenant, workspace, role, or user-specific policies do not require redefining the settings contract. |
| Activity availability state | A diagnostic result that explains why an activity is or is not offered for new selection after the policy stack is evaluated, such as available, blocked by the host baseline, hidden by management settings, or removed from the catalog. |
| Unresolved activity availability reference | An activity key or activity set name referenced by host baseline configuration or management settings that is not currently resolvable from the catalog or registered host-defined sets. Unresolved references are retained and surfaced through diagnostics rather than silently discarded or treated as startup failures. |
| Activity set | A host/developer-defined named group of activity type keys used by activity availability policy. Sets are explicit collections rather than wildcard patterns, so adding a new activity to a package does not silently make it available through an existing set. |
| Workflow root activity | The single activity a workflow definition/executable runs. It may be a primitive activity or a composite activity such as `Sequence`, `Flowchart`, or `StateMachine`; composition details belong to that activity. |
| Workflow executable | The runtime-owned artifact produced from design-time source and consumed by runtime execution. It carries one compiled root activity plus runtime identity, source reference, resume targets, timestamps, and compatibility metadata. |
| Workflow definition state | The authored workflow document stored with drafts and versions in the design domain. It owns authored content, including one root activity, not runtime state. |
| Workflow-scoped variable | A variable declared by the workflow definition and visible throughout the workflow unless shadowed by a narrower variable scope. |
| Container-scoped variable | A variable declared by a container activity and visible only within that container activity's child execution scope, including nested descendant activities; when nested containers declare a variable with the same name, the nearest containing scope wins. |
| Variable reference key | The stable identity used by authored variable expressions to reference a variable within its declaring scope. Variable names are display and convenience access names, not the durable identity of a reference. |
| Type alias | The stable, frozen string identifier under which a CLR type is registered in `IWellKnownTypeRegistry` and referenced by authored arguments (e.g. `String`, `Elsa.Http.HttpRequest`). The CLR type behind an alias may be renamed or moved freely; the alias must never be renamed. Bare (dot-less) aliases are reserved for framework primitives; module types use dotted/reverse-DNS aliases. |
| Collection kind | The shape applied to an authored argument's element type: `Single`, `Array`, `List`, or `HashSet`. Combined with a type alias it forms a type reference and resolves to `T`, `T[]`, `List<T>`, or `HashSet<T>`. Replaces the former boolean "is array" flag. |
| Type reference | The two-field value object `{ Alias, CollectionKind }` that is the sole persisted representation of an authored Variable/Input/Output's type. It carries no namespace, assembly name, or assembly version. |
| Type descriptor catalog | The design-time, module-contributed catalog of selectable argument types (keyed by alias, each carrying display name, category, and a default-editor hint), aggregated from `IVariableTypeDescriptorProvider` contributions and served to the designer. Distinct from the runtime resolution registry per the §2.6.4 design-time/runtime split, but keyed by the same alias and sharing one `TypeDescriptor` shape record. |
| Argument descriptor | The uniform notion that a workflow Variable, Input, and Output each carry the same `{ Alias, CollectionKind }` type reference, so collection-ness round-trips identically for all three (the records themselves remain standalone per FR-030). |
| Facet | A module-owned, kinded, schema-versioned design metadata fragment attached to a broader model. Core stores, hashes, validates generic shape, and round-trips facets without owning their payload semantics. |
| Artifact-only runtime | The rule that runtime execution must be able to load and run from the published artifact without requiring design documents. |
| Runtime checkpoint commit | The atomic runtime operation that applies a named checkpoint's state changes and records any post-commit delivery work. Delivery of recorded work is handled by a separate post-commit delivery module. |
| Reconciliation | A process that updates persisted design/catalog state from authoritative sources such as CLR activities, JSON import, or workflow definitions. |
| Activity construction | The runtime-side process that turns a descriptor type, descriptor payload, and argument bags into a live `IActivity`. |
| Activity execution | One concrete runtime invocation of an executable activity node within a workflow execution. Multiple activity executions may reference the same authored activity when loops, retries, composite slots, or repeated scheduling revisit that activity. |
| Activity execution inspection projection | A runtime-owned read model for inspecting one activity execution, separate from continuation state and keyed by activity execution identity. It may include captured evidence such as outcomes, value snapshots, bookmarks, incidents, and scheduling provenance. |
| Activity execution value snapshot | Policy-governed inspection evidence for an activity input or output observed during one activity execution. A value snapshot may contain metadata only or include payload when runtime payload capture policy allows it. |
| Activity scheduling provenance | Runtime-owned correlation data that explains why and from where an activity execution was scheduled, including structural parent, temporal scheduler, optional branch or iteration identity, optional execution path or scope identity, and scheduling cause. |
| Publishing/compile bridge | The domain that reads design-side state and produces runtime artifacts without making Runtime depend on Design. |
| Runtime checkpoint | The workflow runtime commit boundary where continuation state, inspection projections, outbox intents, and related runtime changes become durable together according to runtime checkpoint policy. |
| Scheduler-boundary checkpoint | A runtime checkpoint that must persist before scheduler work can safely continue, such as scheduling an activity execution, starting invocation, suspending on a bookmark, completing, faulting, or canceling. |
| Elsa 3 import | Compatibility strategy for Elsa 3 assets. The boundary is import into Elsa 4-native models, not running Elsa 3 behavior in place. |
| Feature composition | Selecting and activating a set of Elsa features and their dependencies into a shell/API host. |
| Seam | In Elsa docs, a published contract boundary between sub-domains, normally represented by `.Core` contracts. See [seams and bridges](../seams.md). |
| Bridge | Code that connects two contract boundaries from above, depending on both contracts without making either side depend on the other. See [seams and bridges](../seams.md). |
| Extension Builder workspace | A logical Git-backed authoring space for one repository. It contains one or more .NET solutions, projects, source files, and related repository metadata. It is the source-control boundary first; build, package, and promotion behavior are downstream concerns. Multiple users may work in the same workspace through separate working copies. |
| Extension Builder working copy | A server-side Git checkout/clone for a specific user, session, or branch within an Extension Builder workspace. Source editing happens in a working copy, while the workspace remains the logical repository boundary visible in Studio. |
| Extension Builder working branch | The Git branch selected for an Extension Builder working copy. New edit sessions default to an explicit working branch rather than silently editing the repository default branch. |
| Extension Builder managed repository | The default Extension Builder workspace creation mode where Elsa Server initializes and owns a local Git repository first, creates an automatic initial commit for generated starter files, then lets the user connect or change the remote origin and push to their own repository later. |
| Extension Builder server-local repository | An existing Git repository on the Elsa Server filesystem that is registered as an Extension Builder workspace instead of being created or cloned by Extension Builder. |
| Extension Builder solution | A .NET solution file inside an Extension Builder workspace. It is the primary coordination boundary for solution-level build/test/package commands in the Studio UX. |
| Extension Builder project | A .NET project file inside an Extension Builder workspace or solution. It may produce packages or runtime contributions, but package identity is output metadata rather than the primary authoring boundary. |
| Extension Builder package artifact | A package output produced from an Extension Builder project or solution. It can be promoted to package feeds or module catalogs, but it is downstream from repository authoring. |
| Extension Builder solution explorer | The authoring navigation surface for a Git-backed Extension Builder workspace. It is repository-rooted, auto-focuses the only solution when exactly one solution exists, and uses a solution picker when multiple solutions exist. It shows repository, solution, project, folder, and file structure; build, promotion, runtime, and source-control details belong in contextual inspectors rather than as primary tree nodes. |
| Extension Builder repository workbench | The primary Extension Builder screen for selecting a Git-backed workspace, opening its active working copy, navigating solutions and files, editing source, and inspecting source-control/build state. |
| Extension Builder editor intelligence | The code understanding available inside Extension Builder. The first implementation target is build-backed intelligence: syntax-aware editing plus build/test diagnostics mapped to files. The UX may reserve space for future Roslyn/LSP-backed capabilities without implying they exist. |
| Extension Builder v1 editor scope | The first useful online .NET editor slice: source editing, repository navigation, file operations, build/test diagnostics, Git operations, and templates, without full IDE features such as debugger, terminal, semantic refactoring, or full NuGet management. |
| Extension Builder source-control inspector | The contextual source-control surface for a Git-backed Extension Builder workspace. It exposes real Git status, diffs, staging, unstaging, commit, and push flows; staged changes are the commit boundary, with stage-all as a convenience. |
| Extension Builder template | A scaffold applied at a specific authoring level: repository templates create managed workspaces, solution templates add .NET solutions, project templates add .NET projects to a solution or repository, and item templates add files to compatible projects. |
| Extension Builder build worker | The isolated execution boundary that runs restore, build, test, and pack operations for Extension Builder repositories outside the Elsa Server host process. |
| Execution liveness state | The runtime facet that tracks a workflow execution's ownership and liveness — lease, heartbeat, drain, and interruption. Named `ExecutionLivenessState` (W14, was `OperationalState`; NM-4/R5). Distinct from workflow hold state and scheduler state (R6). Its persisted document kind wire value remains `"operationalState"`. |
| Workflow hold state | The runtime facet holding an administrative pause/hold that sits outside normal workflow continuation state. Named `WorkflowHoldState` (W14, was `ControlPlaneState`; R5). Its persisted document kind wire value remains `"controlPlaneState"`. |
| Workflow execution actor | The in-process single-writer mailbox that serializes all command dispatch for one workflow execution id, enforcing the single-writer ownership contract. Named `IWorkflowExecutionActor` (W14, was `IWorkflowExecutionAgent`; R8) so that `Agent` is reserved for the AI-assistant domain. |
| Workflow drain | The runtime process of draining queued commands for a workflow execution to a settled state. A `Drainer` runs the per-execution drain loop; a `WorkflowDrainOrchestrator` (was `…DrainCoordinator`) sequences the command-triggered multi-step drain (R4). |
| Groundwork | Codename for the provider-neutral, document-oriented persistence library family (`Groundwork.Core`/`.Documents`/`.PostgreSql`/`.Sqlite`) that backs Elsa's runtime persistence seams as an opt-in lane. Portable but equality-index-only, so it serves runtime stores rather than the `IQueryable`-bound design persistence. Kept as a codename with this entry rather than renamed (NM-11/R5). |
| Nuplane | Codename for Elsa's modular dynamic-loading strategy layer (`Elsa.Modularity.Nuplane`): loading Layer-3 implementations, helper libraries, and optional features at composition time. Elsa adopts the host-pins-`.Core`, Nuplane-loads-implementations model (constitution §E5). Kept as a codename with this entry (NM-11/R5). |
| Quiesce / quiescence | Bringing a workflow execution to a safe, settled state with no in-flight work — e.g. at end-of-drain, where the buffered checkpoint segment is folded and flushed through the checkpoint committer. Documented jargon (NM-12/R5). |
| Passivation | Deactivating a workflow-execution actor at a defined boundary (after checkpoint commit, entering durable suspension, registering a volatile wait, or host drain), releasing its in-memory mailbox while durable state is preserved. Documented jargon (NM-12/R5). |
| Control plane | Historical infra metaphor for the administrative/out-of-band command surface over a workflow execution. The persisted runtime facet it named is now **workflow hold state** (`WorkflowHoldState`); the term survives only in preserved wire strings and the `ControlPlaneCommand` activation reason. Documented for provenance (NM-12/R5). |
| Secret key-ring | The secrets rotation seam (`ISecretKeyRing`): one active encryption key plus zero or more additional decryption keys, each identified by a validated key id. The value protector tags ciphertext with the active key id (`v2:<keyId>:nonce:tag:ciphertext`) and still reads legacy `v1:` payloads, so rotating the master key adds a new active key without making existing data unreadable. Key ids are validated at startup (non-empty, no `:`, unique, active key present). See [secrets key rotation](../secrets-key-rotation.md). |
| Durable identity store | The Groundwork-backed persistence provider for the Foundation identity domain (`IdentityGroundworkPersistence` shell feature). It replaces the in-memory identity stores so users, roles, external identities, and tenant memberships survive restarts, using the identity domain's own storage manifest (`elsa-identity`) with wire-safe document kinds (`identityUser`, `identityRole`, `identityExternalIdentity`, `identityTenantMembership`) frozen by golden fixtures. |
| Engine telemetry | The workflow runtime engine's own distributed-tracing self-instrumentation (MS-9): `ActivitySource`-based spans for the four hot-path phases (drain, dispatch, activity execution, checkpoint commit) emitted from source `Elsa.Workflows.Runtime`. It **emits** spans a host's OpenTelemetry SDK or `ActivityListener` subscribes to; it is off by default (no-op `IWorkflowEngineTracer`) and enabled by the `WorkflowsRuntimeTracing` feature. Distinct from the OpenTelemetry ingestion domain. See [engine telemetry](../reference/engine-telemetry.md). |
| OpenTelemetry ingestion domain | The `Elsa.Diagnostics.OpenTelemetry(.Core)` backend that **receives** OTLP telemetry pushed by *other* processes (OTLP/HTTP protobuf collector + in-memory store + query/live-feed API), composed as the `DiagnosticsOpenTelemetry` feature. It is a telemetry *sink*, not engine self-instrumentation — the engine never pushes its own spans into it. Contrast with engine telemetry. See [engine telemetry](../reference/engine-telemetry.md) and [diagnostics-observability-readiness](../program-goals/diagnostics-observability-readiness.md). |
| Engine tracer contract | `IWorkflowEngineTracer` (`Elsa.Workflows.Runtime.Core.Diagnostics`): the single-implementation replacement contract whose `Start*` methods return `Activity?` for each engine phase. The runtime composition root registers the allocation-free `NullWorkflowEngineTracer`; the tracing feature replaces it with `ActivitySourceWorkflowEngineTracer`. Instrumentation is behaviour-preserving: no new awaits in fenced sequences, tags set only via `activity?.SetTag` after values exist. |
| Not-found error contract | The shared API rule (MS-14, issue #393) that a missing entity surfaces as `404` ProblemDetails rather than a generic `500`. `EntityNotFoundException` (`Elsa.Primitives.Exceptions`) is thrown by definition/version store lookups and caught in the FastEndpoints handler base classes (`ElsaRequestHandlerEndpoint`, `ElsaCommandHandlerEndpoint`), which map it to `404`. The global `ProblemDetailsFastEndpointConfigurator` gives every Elsa endpoint an RFC 7807 error shape. |
