# Workbench-owned startup context boundary (#2070)

Status: source and rebuilt-host investigation on 2026-09-26, following the [deployer receipt boundary](deployment-source-receipt-boundary.md). This is a design gate, not a production receipt or a verified candidate match.

## Decision

**No-go for claiming one host-owned, immutable complete-artifact context in the current Workbench.** The first viable capture point for Elsa's explicit root registrations is immediately after the final environment-variable and command-line providers are added in [Program.cs](../../../src/apps/Elsa.Workbench/Program.cs). The value there is the live `ConfigurationManager`, not an owned snapshot of the complete artifact. Root CORS is bound once; CShells and EF preparation can read the same mutable object later. The [rebuilt Workbench reload probe](../../../tests/essentials/Workbench/Tests/CompositionHostAttestationProbeTests.cs) changes the source after startup, promotes a shell with the new setting, and observes the old root CORS policy. The existing [test-owned deployer receipt](../../../tests/essentials/Workbench/Tests/CompositionHostAttestationProbeTests.cs) refuses changed files and overrides before launch, but the child never receives or independently checks that receipt. These are measured blockers, so this spike does not add a partial startup-context implementation or a new verified-match branch.

A bounded future seam is a **named startup configuration lane**, separately owned by Workbench and used by both the selected shell's blueprint construction and its startup-bound root consumers. It must be created from a retained immutable release, not from an after-the-fact directory scan or a caller-supplied receipt label. An intentionally live lane may remain for settings such as management-key rotation, but its values must not be included in a claim that one startup snapshot governs all configuration.

## Earliest source boundary and consumers

`WebApplication.CreateBuilder(args)` reads its default appsettings/environment/arguments before Workbench code runs. Workbench then adds `shells.json`, `shells.{Environment}.json` with `reloadOnChange: true`, and re-adds environment and command-line providers so their effective precedence is selected shell overlay, environment variables, then arguments. Default ASP.NET Core sources and any host-provided sources also participate. The first explicit Elsa root consumer follows the final provider at [Program.cs](../../../src/apps/Elsa.Workbench/Program.cs): `AddWorkbenchOpenIddictVendor(configuration)`. A snapshot made only after `CreateBuilder` cannot retrospectively attest host settings that `CreateBuilder` already consumed, or the byte identity and provenance of each provider.

| Consumer | Present behavior | Startup-context implication |
| --- | --- | --- |
| OpenIddict vendor store, boot switches, CORS, Nuplane setup and options | Root registrations receive the live configuration or sections; CORS origins are read into a policy during startup. Some options can bind again through configuration change tokens. | Classify each setting as startup-bound or intentionally live. Pass the same startup view to every startup-bound root registration. A one-time CORS read alone is not a complete root snapshot. |
| CShells `WithConfigurationProvider(configuration)` and deferred `ConfigureAllShells` | The shell provider and Workbench EF tooling defaults receive the live root. [CShells' blueprint provider](../../../specs/177-file-deployed-activation/research.md) composes from that source later; the callback reads the runtime-fault section on shell construction. | The selected default shell must build from the captured startup view. Reusing a live provider after capturing a marker would create a false binding. Other shells and reload policy need explicit scope. |
| EF resource preparer and migration guard | [EfPersistenceShellSettingsPreparer](../../../src/essentials/Modularity/EntityFramework/EfPersistenceShellSettingsPreparer.cs) snapshots the **current** root view on each preparation, with a reload-token guard for that invocation. [EfPendingMigrationActivationGuard](../../../src/essentials/Modularity/EntityFramework/EfPendingMigrationActivationGuard.cs) can resolve host policy through DI `IConfiguration`. | A copy made during each activation prevents torn values within that activation, but is not the process-start view. The guard and DI fallback must receive or resolve the correct lane before database access. |
| Nuplane package assembly provider | [Program.cs](../../../src/apps/Elsa.Workbench/Program.cs) binds Nuplane feed/loading sections at registration and CShells discovers assemblies through a [catalog-backed provider](../../../src/apps/Elsa.Workbench/NuplaneAssemblyProvider.cs). | A configuration snapshot does not prove package content or which assembly cohort an active generation used. Preserve that as a separate gate. |
| Management API key | [ManagementApiKeyAuthentication](../../../src/apps/Elsa.Workbench/ManagementApiKeyAuthentication.cs) reads DI `IConfiguration` per request. | Freezing root DI configuration wholesale would change key-rotation behavior. Decide and document its live policy separately before replacing DI registrations. |

The six-file base/Development/Staging set in the [host fixture](../../../tests/essentials/Workbench/Tests/CompositionHostAttestationProbeTests.cs) is a useful complete *test* artifact. It is not a discovery rule for arbitrary Workbench deployments. The host must receive an explicit source manifest or retained artifact handle for all included base, selected and unselected siblings. `IConfiguration.AsEnumerable()` can freeze effective values for an invocation, as the EF preparer demonstrates, but loses the file byte set and provider-level provenance; it is insufficient as a deployed-source receipt.

## Private contract for a later proof

The deployer owns publication and retains a complete immutable release while the selected process opens and captures it. Workbench owns a private process-start record with: an opaque process instance and release correlation; selected host, shell and environment; an inventory and private integrity evidence for every included base, selected-overlay and unselected file; the ordered configuration-provider set and effective environment/argument winners with provenance; and an immutable effective startup view actually passed to the root and selected-shell consumers. Values, file paths, credentials and reusable secret-bearing digests stay private. The record remains available for the lifetime of that process and its relevant shell generation; the deployer keeps its release through the process-start read and any recovery window its deployment contract promises. A directory that can change between check and read is not retained immutable evidence.

Missing or changed files, an unknown provider, source change during capture, unaccounted overrides, an unselected sibling omitted from the manifest, or a consumer still using the live provider must produce an **unknown/refused** source-binding result, not a claimed match. Process exit, a failed shell activation, or a later shell reload also requires a distinct state. The safe outward projection may contain a fresh opaque correlation ID, process instance, selected shell, generation, readiness and refusal class. It must not contain source bytes, connection values, raw paths, hashes of secret-bearing content, or an untrusted deployer label echoed as host proof.

An external deployer can later compare its private retained-release evidence with the host-held record. A generation-bound marker can be attached only after the selected shell is composed from that record and successfully promoted. Those comparisons remain insufficient for `candidateMatch=verified` until reviewed-candidate equality, applied package cohort and separate provider/migration prerequisites are proven. The [existing safe observer](../../../src/apps/Elsa.Workbench/Composition/CompositionActivationObservationEndpoints.cs) therefore continues to report `candidateMatch=unverified`.

## Reproducible host evidence and next gate

The existing rebuilt-host probe passed 6/6 with `dotnet test tests/essentials/Workbench/Tests/Elsa.Workbench.Tests.csproj --no-restore --filter FullyQualifiedName~CompositionHostAttestationProbeTests`. `Shell_reload_can_advance_while_startup_bound_host_configuration_stays_old` is the negative source mutation: a new shell generation reads the changed setting while root CORS retains the old one. `Fresh_process_uses_one_staged_bundle_for_root_and_shell_configuration` is a positive *external-copy* control and a negative mixed-copy control. `Test_deployer_can_bind_a_complete_retained_copy_to_one_child_without_claiming_candidate_match` checks the environment-override winner in the child, while `Test_deployer_refuses_changed_artifact_override_and_arbitrary_receipt_label` varies source, environment and override before launch. None proves the child captured the deployer's receipt. Environment and command-line values of a running child are process-start inputs; mutating the test launch inputs after it starts does not rewrite that process's provider, so such a test would not prove source ownership.

Before a production implementation story, prove in a **disposable rebuilt Workbench** that a host-opened retained artifact and effective override record are captured before binding; that root and selected shell use exactly that immutable view despite subsequent source edits; that a reload cannot silently rebind startup-only inputs; and that intentionally live keys retain a documented policy. The proof must refuse incomplete/mutable artifacts and disclose no private values. Until then, the host ownership seam remains unproven and spec 177 US2/US3 stay open.
