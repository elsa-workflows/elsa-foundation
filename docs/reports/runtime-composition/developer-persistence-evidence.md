# Developer persistence evidence boundary

Status: investigation in progress for [#2172](https://github.com/elsa-workflows/elsa-foundation/issues/2172), under developer composition epic [#1962](https://github.com/elsa-workflows/elsa-foundation/issues/1962) and program [#1959](https://github.com/elsa-workflows/elsa-foundation/issues/1959). Source audit baseline: verified main `d18ee00a9e9bb6908718571a348d4303a8695e54`. The production-path probe is integrated and root verification passed the full affected migrations project (382/382, including all 10 probe cases) and architecture guard (599/599). Independent correctness/report review is complete; PR and exact-main delivery gates remain pending. This report does not amend a public API, protocol, export policy or constitution.

Elsa constitution §E4 remains deferred. This investigation follows the existing accepted tooling and file-bridge contracts; it does not ratify a general configuration policy by implication.

## Question and outcome

How can a developer inspect each selected feature's effective persistence target and its source before generation, activation or database access, using the same persistence owner as the host? The existing planner explains exact feature selection. It does not resolve arbitrary authored settings or establish effective persistence targets. This spike must identify a viable integration seam and reproduce its limits before an implementation contract is approved.

The earlier [configuration-integration discovery](effective-configuration.md), [persistence boundary](persistence-boundaries.md), [developer planning contract](developer-plan-command-contract.md) and [import/export boundary](import-export-boundary.md) remain the historical decision inputs. [Spec 176](../../../specs/176-composition-file-bridge/spec.md) governs the delivered local file bridge. Do not substitute this discovery report for those contracts.

## Input context and capture boundary

The context must identify the selected host closure, shell, environment, source mode and supported source layers. `workbench-json-v1` reads `appsettings.json`, `appsettings.<environment>.json`, `shells.json`, then `shells.<environment>.json`. Later providers win. `workbench-json-environment-v1` explicitly includes inherited process environment. Neither mode means that the invoking process has captured a deployed host's environment, command-line arguments or arbitrary external provider.

[CompositionFileSource](../../../src/essentials/Cli/CompositionFileSource.cs) freezes its own host-file byte bundle and rechecks it before publishing a candidate. `EfToolingConfigurationContext.Create` separately reads JSON providers into a frozen configuration root. There is no shared snapshot identity between those two production readers. An unchanged source check performed before and after a second read cannot prove that the second reader consumed the first reader's bytes. A proposed integration must consume one frozen context or establish an explicit host-private correlation mechanism. Public hashes derived from secret-bearing sources are not an acceptable substitute.

The resolver's internal provenance currently distinguishes generic `root`, `shell-composed` and `shell-authored` scopes. The adapter constructs a generic runtime context; these records do not identify the exact file/provider which won, the selected environment, or a deployed-host observation. The v2 response's explicit context source/environment labels come from the tooling context. Do not infer file-level or external-provider provenance from the adapter's scope labels.

The existing tooling context verifies the host assembly's name and location before constructing its declared defaults. A temporary directory of configuration files cannot satisfy that check against an assembly loaded elsewhere. A test using the internal memory-backed constructor and the actual test assembly layout can demonstrate resolution agreement over an equivalent frozen value set. It cannot demonstrate that the production file readers consumed the same bytes. Keep those proofs separate.

The proposed first slice should use captured file-only inputs. The environment-enabled context adds process environment after file loading; those values are outside a file-byte bundle and can change independently. Capturing environment, command-line or custom-provider values would require a separately reviewed input and precedence contract. Until then, show those sources as unavailable/unverified. This limits evidence coverage, not the original program's eventual configuration scope.

## Existing-host versus candidate selection

`PrepareShell` applies host defaults and `FromConfiguration` to the selected shell's authored features. The [target-selection helper](../../../src/essentials/Persistence/EntityFramework/Tooling/EfToolingTargetSelection.cs) filters EF modules after that preparation. The v2 request cannot supply the planner's proposed `SelectedFeatureIds`. Therefore identical host/candidate fixtures may establish existing-shell agreement, but cannot establish target resolution for an edited composition which enables or removes consumers.

The next developer-visible slice must evaluate the edited candidate, rather than relabel existing-host facts as its effective targets. Prefer reusing the file bridge's in-memory `CompositionCandidateBuilder.Build` result without publishing files, then supplying those captured candidate bytes. It already uses the authoritative planner and verifies exact selection readback. Its existing acceptance and supported-shape requirements still apply: do not invent acceptance or silently promote an unresolved edited plan. A host-owned candidate-preparation context taking proposed IDs is an alternative if the specification proves the bridge cannot meet the required actor journey. Either approach must preserve explicit removals and unknown/local data without a second selection algorithm. Choose and prove the contract before implementation; current candidate targets remain unresolved when selections differ.

## Secret, trust and evidence boundary

Public output may contain reviewed feature/module/resource/provider identities, logical connection references, available selection kinds, context selectors, refusal codes and explicit unresolved prerequisites. Never project, log or publicly serialize an `IConfiguration`, composed shell settings, opaque authored JSON, whole operation request, or validator target object. Those can contain inline connection values or unknown secrets. A versioned private local worker request may transport captured inputs under the explicit trust boundary below; that does not authorize a public dump of that request. The [resolver models](../../../src/essentials/Persistence/EntityFramework/ResourceResolution/PersistenceResourceModels.cs) retain legacy connection-string **presence**, not its value. The EF validator may compare actual values privately; that does not authorize their export.

The [current v2 response](../../../src/essentials/Persistence/EntityFramework/Tooling/EfToolingContextContract.cs) projects per-feature resource, provider, connection reference and selection kind. Offline `list`/`plan` mark target verification `not-performed` and runtime parity `unobserved`. Live operations may report `matched` after comparing the supplied connection to configured values; that remains configuration matching, not physical target or readiness proof. The response does not expose per-participant source-file provenance, resource-definition layer or general feature-setting provenance. Even an observed test comparison must not silently rewrite those production response claims.

A closed response shape is not sufficient content validation. `BuildFacts` copies resource names and connection references from resolved configuration, but the production [adapter](../../../src/essentials/Persistence/EntityFramework/ResourceResolution/PersistenceConfigurationAdapter.cs) first enforces identifier-like reference names. The executable negative controls independently place inline connection syntax in the selected resource and connection-reference fields. Runtime preparation and v2 `list` both refuse with `resource-selection-invalid` and `resource-definition-invalid`, respectively; private-buffer checks confirm the inline content is absent from their diagnostics and responses. This disproves the initial suspected inline-reference leak for these production entry points. The [worker response validator](../../../src/essentials/Cli/Worker/HostContextInspectionResponse.cs) itself does not impose that identity grammar, so a new producer/consumer projection must preserve or explicitly validate the existing producer boundary, with bounds and value-free refusals. Valid logical names are intentionally visible; placing a canary in an ordinary valid name is not evidence of secret leakage.

Runtime can compare two differently named configured connections for a shared-context constraint. Tooling deliberately skips that lookup. Equal values under distinct names may therefore pass runtime while tooling remains `target-affinity-unverified`; different values may make runtime refuse while tooling still reports an unresolved target. `expected-connection-unchecked` is expected for applicable offline tooling. Same-reference cases need not produce an affinity warning. Configuration agreement is distinct from physical database identity: equal configured values are neither connectivity nor database/migration evidence.

[ADR 0076](../../adr/0076-persistence-tooling-runs-inside-the-host-closure.md) keeps the front end free of EF and places execution inside an explicitly selected host closure. Reuse that boundary. Do not silently load an arbitrary host or execute its composers during file-only planning. The configuration-only claim applies to inspected production resolution/preparation/list paths; an arbitrary custom composer may execute user code. Unknown/custom host defaults need an explicit trust and applicability contract before generalizing the proof.

## Unknown settings and export fidelity

The original [#1962](https://github.com/elsa-workflows/elsa-foundation/issues/1962) criterion remains broader than the delivered portable import lane. Preserve that criterion and distinguish these existing paths:

- The authored v1 reader clones nested opaque `settings` and `resources`. Same-catalog acceptance preserves values already in that authored document while omitting them from public preview. This does not classify them as safe to share.
- Import exports reviewed safe setting leaves and logical resource references. Unknown local values are masked in preview and omitted from portable authored output; the original local source files/captured snapshot retain them, as required by spec 176 FR-005/006.
- Generation preserves unknown/raw values in copied local host files while patching reviewed paths and leaving unrelated source data intact. That is local migration fidelity, not portable export of arbitrary unknown data.

Sources: [authored reader](../../../src/essentials/Modularity/Planning/Json/SelectionJsonReader.cs), [importer](../../../src/essentials/Modularity/Planning/Bridge/CompositionImporter.cs), [accept command](../../../src/essentials/Cli/CompositionAcceptCommand.cs), [candidate builder](../../../src/essentials/Modularity/Planning/Bridge/CompositionCandidateBuilder.cs), and [spec 176](../../../specs/176-composition-file-bridge/spec.md).

A safe portable round-trip contract for unknown local values is not yet approved. Unknown nonempty data may be a secret, and source layers or sibling nodes do not fit the authored v1 model. Retain this as an explicit epic gap. A later contract must define reviewed classification or external-reference mapping, handling of unavailable owners, source association, fidelity, disclosure and refusal. Do not solve it by copying arbitrary values into a shareable JSON file or silently narrowing the epic to local preservation.

## Next vertical slice to specify

Enable a developer to inspect an edited candidate against an explicitly selected host context alongside the pinned selection and see, for each supported persistence consumer, its logical target, selection reason and available provenance. Use a distinct `configurationResolution` projection; leave [Planning.PersistenceEvidence](../../../src/essentials/Modularity/Planning/Models/HostInventory.cs) and physical/layout/activation claims separate.

Before this becomes Ready for implementation, specify and review:

1. One file-only source capture and a defined candidate-selection/settings context consumed by the host-owned resolver, with differing-selection and drift/adverse capture proof. Ambient environment, CLI and external providers remain unverified until separately captured and specified.
2. Host-closure/defaults ownership and invocation through the existing EF-free front end/host worker boundary. The tooling operation must perform no host activation, package acquisition or database action; the caller separately trusts the declared composer's code to run.
3. A versioned, closed projection with content validation and value-free refusals, distinguishing selector source from resource-definition source. If exact source-file or general setting provenance is unavailable, report that absence rather than inventing it.
4. Exact refusal/exit/compatibility behavior for unsupported host inputs, legacy mode and known constraints. Configuration resolution may succeed while physical readiness remains unresolved.
5. A real developer journey from an existing selected host and pinned composition through inspect/plan/redacted output, including defaults, diagnostics override, legacy/refusal and drift controls, with canaries absent.

The preferred capture direction is for the front end to freeze the selected file bundle once and supply the defined candidate's source bytes privately to the existing host worker. A versioned host-owned context factory would compose those captured inputs without rereading live paths; the worker would return only the content-validated safe projection. The front end would retain its original source association for drift checking. Raw configuration bytes may cross this private local request boundary; they must never appear in public output, logs or diagnostics. Selecting the host also explicitly trusts its declared composer to run; this is not an arbitrary-code sandbox. Private stdin transport is compatible in principle with ADR 0076's credential boundary, but the exact candidate/context protocol, size limits, redacted failure behavior, assembly/configuration location distinction and legacy capability negotiation still require specification and producer-consumer proof.

Do not replace this requirement with two independent readers which happen to agree in an unchanged fixture. Such a fixture is useful baseline evidence; it does not establish the shared-input contract needed for the effective preview. The next specification should choose the capture protocol and projection together as one developer-visible slice, rather than ship an apparently effective preview against independently read files.
