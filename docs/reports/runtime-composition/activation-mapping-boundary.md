# Activation mapping for the first Embedded profile (#2053)

Status: proposed bounded contract on 2026-09-25. This is a prerequisite decision for [#2052](https://github.com/elsa-workflows/elsa-foundation/issues/2052), not an implemented feature-selection writer or a live-host guarantee.

## Why the current bridge stops

The [pure selection planner](../../../src/essentials/Modularity/Planning/Services/SelectionPlanner.cs) expands pinned profiles/groups plus additions/removals into exact IDs. The [file candidate builder](../../../src/essentials/Modularity/Planning/Bridge/CompositionCandidateBuilder.cs) then refuses whenever those IDs differ from the selected source: `bridge-selection-drift`. It only patches reviewed **existing** setting paths and named resource references. This is the deliberate [spec 176 boundary](../../../specs/176-composition-file-bridge/spec.md), so adding a reviewed profile to the catalog alone cannot generate its feature selection. The [Embedded host proof](embedded-lock-host-proof.md) establishes a 16-ID target and also shows that raw CShells activation can re-add a required dependency that a user explicitly disabled. The writer must therefore preserve planner intent before handing a candidate to CShells.

## Observed configuration behavior

The pinned-package [Workbench configuration tests](../../../tests/essentials/Architecture/WorkbenchConfigurationTests.cs) and the [bridge source tests](../../../tests/essentials/Modularity/Planning/Tests/CompositionBridgeSourceTests.cs) give these cases:

| Source and proposed edit | Pinned CShells result | v1 mapping recommendation |
|---|---|---|
| Object-map base contains `A` with settings; selected overlay adds `B:true` | `B` is enabled. | Allow an explicitly reviewed addition in the selected overlay when its ID is absent from both selected layers. |
| Object-map base contains `A` with settings; selected overlay writes `A:false` | `A` is disabled and its effective setting data is absent. The base object remains in the source file. The new characterization test proves this. | Allow a selected-environment removal by writing `false` in the overlay, retaining the base object and its unknown local values. The bridge reader currently refuses this object/scalar pairing and must be updated in the implementation slice. |
| Base contains `A:false`; selected overlay supplies an `A` object | The base scalar still wins; `A` remains disabled. | Refuse an attempted enable from this selected overlay. Changing the base would affect other environments and needs a separately reviewed mapping. |
| An array-shaped feature list receives an overlay | Entries merge by numeric index, and an object member named `Enabled` is a setting, not a disable switch. | Refuse activation-set edits to array-shaped sources in v1. Retain the existing array import/setting behavior. |
| Base and overlay change between object-map and array, or create case-equivalent duplicate IDs | The pinned package refuses or the bridge reports an ambiguous source. | Refuse before writing. |

The new object-map test covers both addition and disabling a base object in one selected overlay. Existing tests cover scalar/object precedence, array index replacement, duplicate IDs, and cross-shape rejection. [#2050's generic-host test](../../../tests/essentials/Workflows/Runtime/Persistence/EntityFrameworkCore/Tests/EmbeddedFixtureHostEvidenceTests.cs) remains the separate 16-ID positive runtime proof; it does not imply that the Workbench file bridge can currently materialize those IDs.

## Proposed narrow writer contract

1. Begin with an accepted, pinned composition and a frozen base/selected-overlay source snapshot. Run the shared planner before any patch. Refuse catalog/definition pin drift, unaccepted selection changes, known absent/incompatible features, and every **known required edge** whose target is absent after an explicit removal. The existing planner requires supplied host dependency evidence to emit `required-dependency-missing`; reviewed definition explanations alone currently become evidence, not a blocking finding. **For this first profile, extend the planner to emit the same unresolved finding from a pinned reviewed required edge when no loaded descriptor for that feature is supplied.** A supplied loaded descriptor remains authoritative under spec 174; a disagreement with reviewed metadata stays visible. This avoids making a manually assembled inventory a prerequisite for generating a candidate while keeping missing host evidence explicitly unverified. An absent inventory must never be presented as runtime readiness.
2. For v1, edit only the selected shell's object-map `Features` in its selected environment overlay, and only for cases whose merged semantics are proven. Add a missing feature as `true`; disable a base object or scalar feature with `false` in that overlay. Preserve the base file, other shells, unselected overlays, and unknown settings. Refuse a requested enable when base `false` wins, an overlay-only object removal that would discard its settings, array-shaped sources, or a feature whose source layer cannot be mapped without ambiguity. This is a **proposed subset**, not a claim those edits are implemented.
3. Re-read the generated base plus selected overlay with the bridge reader (extended for the proven object-to-`false` case), and compare the exact effective IDs to the planner's accepted IDs before publishing the fresh candidate. The redacted diff must identify each added/disabled feature and its source layer. Interactive acceptance remains bound to the unchanged frozen source; no in-place edit or partial output is allowed.
4. Keep host-specific settings separate. The current bridge cannot add a new setting path, so selecting `FileSystemDistributedLocking` does not configure `LocksFolderPath` by itself. Candidate generation must show that prerequisite as unresolved unless a separately reviewed host-local setting source supplies it. The profile catalog cannot carry lock paths, connection strings, signing keys, or migration authorization. Process environment and command-line overrides remain outside this file-only observation, as [spec 176](../../../specs/176-composition-file-bridge/spec.md) already states.

Do not gate on *every* unresolved planner finding indiscriminately: this file-only bridge intentionally reports inventory and persistence as unchecked. The critical distinction is between a known invalid exact selection, which refuses generation, and evidence that has not been supplied, which remains visible and prevents a runtime-ready claim. Before any actual host activation, revalidate against that host's current runtime descriptors; source-file equality alone cannot prove package loading or the live feature closure.

## Implementation handoff

[#2052](https://github.com/elsa-workflows/elsa-foundation/issues/2052) can proceed as a sequence: ratify this bounded mapping in a spec 176 follow-on contract; implement source-reader/candidate-writer changes with positive object-map and negative array/base-disabled tests; add the planner required-edge gate and post-write exact-set comparison; then publish the immutable `embedded-runtime@1` definition and exercise the CLI-to-generic-host path. Keep setting insertion, live/in-place apply, shell hot reload, package delivery, and other starting profiles out of that first slice. The [Workbench source-snapshot no-go](workbench-source-snapshot.md) still applies to claims about one complete live process/file snapshot.
