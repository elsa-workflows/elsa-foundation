# First runtime starting-profile decision (#2048)

Status: proposed first delivery direction on 2026-09-25 under [#1961](https://github.com/elsa-workflows/elsa-foundation/issues/1961). This chooses an evidence-backed **candidate**, not a published profile or a claim that all three fixture hosts are production ready.

## Decision

**Work toward `embedded-runtime@1` first.** Present it as an in-process runtime starting point, with its exact feature closure and host prerequisites visible. Do not call it “API-free”: the current required dependency graph includes `WorkflowsRuntimeApi` and `ApiCapabilities` even when the selected host creates no HTTP listener. A versioned profile should name all 15 closure IDs explicitly so the pure planner does not report three missing required edges that CShells would later auto-resolve. The final definition must also settle how a deployable lock provider is selected. Persistence stays a separate named-resource choice; no connection value belongs in the profile definition.

This is the smallest useful profile path supported by the [Embedded rebuilt-host proof](embedded-host-proof.md): a generic, non-ASP.NET host activated the selection and completed start, suspend, bookmark resume, and completion through a named SQLite EF store. That proof supplied a process-local `IDistributedLockProvider` from the [test harness](../../../tests/essentials/Workflows/Runtime/Persistence/EntityFrameworkCore/Tests/EmbeddedFixtureHostEvidenceTests.cs), so the next host proof must replace it with a reviewed deployable lock choice. The existing [`FileSystemDistributedLocking` feature](../../../src/essentials/Locking/FileSystem/FileSystemLockingFeature.cs) is a concrete candidate, with an explicit locks directory and single-host filesystem assumptions to verify; this report does not assume it works in the generic fixture. Until then, `embedded-runtime@1` remains a candidate, not a shipped preset.

Decide whether the product intentionally offers Authoring plus runtime endpoints or first changes the Publishing dependency; then prove authenticated authoring/publishing behavior. |

The pragmatic path treats these as **host shapes**, not claims that a role has perfectly isolated module dependencies. Strict isolation remains an explicit later option: Embedded would need a host-agnostic runtime-root feature and trigger dependency change; Authoring would need a narrower Publishing dependency. Those are published feature-contract changes with compatibility costs. Merely hiding the extra IDs in a builder would violate the [planner's exact-selection contract](../../../specs/174-profile-selection-planner/spec.md).

## Candidate contract for `embedded-runtime@1`

The 15 exact IDs in the proven CShells closure are `Primitives`, `Serialization`, `Mediator`, `Events`, `Expressions`, `ActivitiesRuntime`, `ActivitiesPrimitives`, `ActivitiesControlFlow`, `ActivitiesSequence`, `WorkflowsRuntimeEntityFrameworkCore`, `WorkflowsRuntimeResumption`, `WorkflowsRuntimeTriggers`, `ApiCapabilities`, `Tasks`, and `WorkflowsRuntimeApi`. The last three were previously auto-resolved in the [fixture host test](../../../tests/essentials/Workflows/Runtime/Persistence/EntityFrameworkCore/Tests/EmbeddedFixtureHostEvidenceTests.cs); making them explicit in a reviewed profile is a planning choice, not a change to CShells' dependency semantics. A profile/group expansion with a pinned catalog must show why each appears, and an advanced user can remove any ID and see the resulting required-edge refusal rather than a silent re-add. The host-proof spike decides whether `FileSystemDistributedLocking` becomes an explicit sixteenth default member or whether a documented host-owned provider is the supported contract.

Suggested user-facing description: **“Embedded runtime: execute and resume workflows in your own process. The demonstrated host does not start an HTTP listener. Review the included Runtime API feature before using this selection in a web host.”** The setup flow asks separately for a supported persistence resource, required signing keys, a lock provider, and the host's assembly/inventory evidence. It reports unverified package/host compatibility when that evidence is unavailable. The profile itself carries no database provider, connection string, signing secret, HTTP binding, or migration authorization.

The versioned definition follows the existing [Foundation-owned catalog contract](profile-catalog-contract.md): stable ID, immutable version and digest, exact members, and reviewed rationale. An authored composition pins that definition and the accepted expansion. New membership requires a new version and explicit re-resolution; profile upgrades never silently change an existing composition. The [pure planner](../../../specs/174-profile-selection-planner/spec.md) remains the decision engine for both the CLI and a later web builder, and host activation remains separate evidence.

## Next gates and issue boundaries

1. **Host-proof spike, ready to file:** run the explicit 15-ID closure in a disposable generic host with `FileSystemDistributedLocking` and a configured locks directory, rather than the test's process-local provider. Determine whether the locking feature belongs in the profile or remains a required host service. Keep the named SQLite resource, one real suspend/resume path, and a negative case for missing lock/service or incomplete dependency selection. Inspect the actual `EndpointDataSource`/host type so documentation can say exactly when HTTP routes do or do not exist. This is a proof of one supported example, not all providers or packages.
2. **Profile publication story, conditional on that proof:** add one immutable Foundation-reviewed `embedded-runtime@1` definition with the proven complete membership and rationale; use the existing planner/CLI contract to show exact IDs, provenance, required-edge findings, host prerequisites, and a safe persistence prompt. Verify no silent upgrade and no secret in the catalog/export. Do not publish Worker or Authoring in this story.
3. **Separate later decisions:** Worker needs a production identity/authorization and lock owner. Authoring needs an intentional runtime-endpoint scope and an authenticated operation proof. A strict API-free Embedded route, if desired, requires a separately reviewed feature-dependency change. The builder [interaction research](builder-ux/) still needs real-user task evaluation before a production screen is selected.

The first host-proof spike has enough detail to implement now. The publication story should be written against its result. No package loader, generic settings framework, production builder UI, or activation attestation is implied by this decision.
