# Source-to-generation attestation spike (#2042)

Status: investigated on 2026-09-25 against Workbench and CShells `0.0.30-preview.159`. This is a design gate for [spec 177](../../../specs/177-file-deployed-activation/spec.md), not a runtime contract or an implementation of verified candidate matching.

## Decision

**No-go for `candidateMatch=verified` in the current Workbench.** A custom CShells blueprint can carry immutable metadata into a promoted generation, and an activation participant can participate in the promotion/rollback boundary. Neither supplies a trustworthy identity for the bytes and process settings Workbench actually used, nor for the assembly cohort Nuplane actually made available. The [safe default-shell observation](../../../src/apps/Elsa.Workbench/Composition/CompositionActivationObservationEndpoints.cs) must continue to report `unverified`.

**Conditional go for a later, narrower design:** A Workbench-owned snapshot coordinator could construct one immutable candidate context from the complete deployed file set, effective process overrides, and a pinned package cohort. A custom blueprint provider would compose *only* from that context and place its safe marker in an immutable metadata map. A root activation participant would bind an accepted marker to the promoted shell generation and restore the previous binding on failure. The host would expose only a sanitized, authenticated readback. This needs implementation and host-level proof before any verified-match story can be accepted.

## Where the current seams sit

| Seam | What it can establish | Missing authority |
|---|---|---|
| `IShellBlueprintProvider.GetAsync` plus `IShellBlueprint.ComposeAsync` | A custom provider can capture one immutable candidate and use it for settings and descriptor metadata. | Workbench uses the built-in configuration provider and a live root `IConfiguration`; a metadata value inferred from a later file scan is not the loaded input. Only one blueprint provider is registered, so this requires replacing the current provider, not adding a second one. |
| `ShellDescriptor.Metadata` | The selected blueprint's metadata follows the constructed generation. | The descriptor retains the dictionary reference; the provider must pass an immutable map. Metadata is made before initializers succeed, so its presence on a candidate descriptor is not proof of promotion. |
| `IShellGenerationActivationParticipant` | `Commit` runs after the active pointer is set; a failure rolls back to the former active shell. This is the appropriate synchronous in-process acceptance hook. | It cannot make file switching, Nuplane reconciliation and shell promotion one transaction. No slow external deployment or network receipt operation belongs in `Commit`. |
| `IShellLifecycleSubscriber` | Useful for telemetry. | Its notification precedes active-pointer publication and exceptions are swallowed, so it cannot authorize an accepted-generation marker. |
| Nuplane package reconciliation | A package state can be observed independently of shell reload. [`Elsa.Foundation.Host`](../../../src/apps/Elsa.Foundation.Host/Shells/ShellReloadOnPackagesChanged.cs) refreshes its feature catalog and reloads active shells from `OnPackagesReconciledAsync`, after reconciliation. | [Workbench](../../../src/apps/Elsa.Workbench/Program.cs) currently has Nuplane loading and [admin reconcile](../../../src/apps/Elsa.Workbench/ElsaModuleManagementApi.cs), but no equivalent callback. A package ID/version or private store-state record is not a content-integrity proof of the assemblies supplying a generation. |

The pinning and rollback claims above are exercised by [`CompositionGenerationSeamProbeTests`](../../../tests/essentials/Modularity/Tests/CompositionGenerationSeamProbeTests.cs), a disposable in-process CShells host using the same pinned package as Workbench. It varies two shells and changes the candidate source while one activation is paused. The test also demonstrates mutable metadata aliasing as a negative control. The earlier [Workbench host probe](../../../tests/essentials/Workbench/Tests/CompositionHostAttestationProbeTests.cs) varies all six base/overlay sibling files and a process override, and checks failure and safe readback. Its package variation across two host starts does not establish same-process correlation. [Registry failure and observer-timeout tests](../../../tests/essentials/Modularity/Tests/ServerReadinessTests.cs) establish retention and uncertainty separately.

**Same-process package attempt:** In a rebuilt disposable Workbench, an initial local `1.0.0` package was recorded active; the probe then added `2.0.0` and called the authenticated `POST /_elsa/module-management/reconcile`. The call did not complete: the first run reached the `HttpClient` 100-second timeout, and a second run with a 25-second request budget also timed out. Machine load was modest (about 4.65 on an eight-core host). The host log showed successful initial shell activation but no completed reconciliation. This neither proves a Nuplane deadlock nor establishes which package supplied later assemblies; the experimental failing test was removed from the checked-in suite. The package-to-generation proof remains open and is a hard prerequisite for `verified`.

## Snapshot owner and ordering required for a future design

1. The external deployment owner publishes a complete immutable artifact and retains the previous release. Workbench's snapshot coordinator opens that *one* artifact identity and verifies all included base, selected overlay, and copied unselected sibling files against the deployment receipt. Unselected files belong to artifact integrity even when they do not contribute to the selected shell's effective settings.
2. At candidate creation the coordinator captures the effective environment and command-line inputs and the host-owned configuration that was bound at startup. If a proposed change alters startup-bound services, reject hot reload and require a new process; a shell-only reload cannot retroactively rebind those root services. Snapshot reads must be stable under concurrent writes: use immutable deployed directories/handles or revalidate the complete input after capture, refusing drift rather than mixing revisions.
3. Nuplane must supply a content-integrity identity for the **applied assemblies**, not just package names and versions. Acquire and retain a package cohort lease while composing/activating the shell; reconciliation must either finish before that lease is captured or wait until promotion ends. Reconciliation and promotion need an explicit ordering protocol, even if they cannot share a transaction. Recheck that the cohort which supplied assembly discovery is the cohort recorded in the candidate context.
4. The custom blueprint provider uses the captured context for *all* settings it composes; its metadata is an immutable, nonsecret marker with snapshot schema, opaque deployment ID and private verification reference. A generation must never inherit a marker merely because the current directory later resembles a candidate.
5. The activation participant accepts the marker only for the just-promoted shell/generation. Failed composition, initializer, prepare or commit retains the prior accepted marker and prior active generation. The safe root GET reads the active descriptor and accepted binding together, and reports `unverified` on absence, mismatch, uncertainty or a stale package lease. Multiple shells each have separate generation bindings; a complete artifact need not mean simultaneous multi-shell promotion.

CShells obtains a blueprint before its per-shell reload semaphore. Therefore overlapping reloads can queue different captured candidates; the implementation must label each request/candidate independently and compare the final active generation, never assume request arrival order identifies the winner.

## Secret-safe deployer and host comparison

The local handoff's random candidate ID is a label, not integrity evidence. A viable private protocol would canonicalize the complete byte manifest and context (schema, file roles, selected host/environment/shell, effective override identity, package cohort, release ID, expected-current release, operation nonce and expiry), then authenticate it with an HMAC key held by the trusted deployment/host verification boundary. Only an opaque release/operation ID and key ID need appear in shareable receipts. Do not export the HMAC over low-entropy settings as a public per-file digest; keep the authenticated manifest and comparisons server-side. A host that cannot access the trusted comparison key or independently establish the loaded snapshot must refuse verification.

Key ownership and rotation must be explicit: the deployment owner provisions the comparison key to the selected host's trusted verifier; the browser never receives it. New receipts use the current key ID, while the verifier retains the old key only as long as an accepted generation or recovery receipt requires readback. Bind each receipt to host, environment, expected prior release and unique operation nonce, with bounded validity and replay tracking; a receipt for a different host or an old expected-current state cannot authorize a new promotion. The root API returns safe status, shell, generation, opaque release ID and verification class. It does not return raw file values, paths, package manifests, MACs, private override values, blueprint configuration, provider exceptions or the management key. Any receipt comparison requires a separate authorization design beyond the current server-side management-key route.

## Proof still required before a verified-match implementation issue

- A disposable **rebuilt Workbench**, not only a tiny CShells host, composes exclusively from the captured immutable context while selected and unselected files and process overrides vary. Change files during a held activation and show refusal or a consistent old/new snapshot, never a mixture.
- A content-changing package replacement in **one running process** proves which assemblies were actually selected, how Nuplane reconciliation is ordered with reload, and how package-integrity identity survives promotion and rollback. A state-file version transition alone is insufficient.
- Two shells using one artifact have independent accepted markers; failed initializer/participant commit leaves the prior default-shell marker and generation active. A lost HTTP response and overlapping reloads resolve only by safe readback and deployment receipt, with explicit uncertainty where correlation is unavailable.
- Canary scans of all outward responses and key-rotation/replay cases prove the private comparison never leaks a secret or accepts a stale receipt.

Until those proofs pass, [spec 177's contract](../../../specs/177-file-deployed-activation/contracts/activation-v1.md) correctly separates deployment switched, active generation observed, and candidate match unverified. Package/provider/connection/migration readiness and source rollback remain independently owned; this spike supplies none of those guarantees.
