# Runtime-builder interaction study

Issue [#2029](https://github.com/elsa-workflows/elsa-foundation/issues/2029), under builder UX epic [#1963](https://github.com/elsa-workflows/elsa-foundation/issues/1963). Open [the three interactive mocks](index.html) in a browser. These are independent research screens over one synthetic fixture. They make no network call, contain no connection value, do not use the production planner, and do not generate a deployable CShells file. Their JSON download illustrates a review shape only.

## What is known, and what is hypothesized

The real [Workbench shell](../../../../src/Apps/Elsa.Workbench/shells.json) selects many individually named features and includes `WorkflowsRuntimeEntityFrameworkCore.WorkflowExecutableCacheCapacity`, plus distinct diagnostics EF features. The [proposed profile/group contract](../profile-catalog-contract.md) defines a Worker fixture with 14 authored IDs; the [host proof](../worker-host-proof.md) observed 15 effective IDs because Resumption requires `Tasks`. Those names are not released product profiles or groups. The [pure planner](../../../../src/essentials/Modularity/Planning/Services/SelectionPlanner.cs) and [CLI](../../../../src/essentials/Cli/CompositionPlanCommand.cs) handle supplied intent and evidence without starting a host. The [file bridge](../../../../specs/176-composition-file-bridge/spec.md) imports local source snapshots and writes reviewed candidates to a fresh directory, preserving unknown content and refusing changed sources. Its result is not a running-host observation.

The prototype's default and explicit diagnostics resource bindings are a proposed UI over the reviewed persistence direction in [#1968](https://github.com/elsa-workflows/elsa-foundation/issues/1968) and [#1969](https://github.com/elsa-workflows/elsa-foundation/issues/1969). The mock's `AcmeAuditSink` and `FuturePolicy` are invented external-content examples; no connection values exist in the mock. The shown cache-capacity path is real, but a UI review mapping for that path is a design assumption here. The mock's tiny dependency resolver models the named Worker fixture only. It cannot validate packages, host identity, actual configuration precedence, transaction topology, migrations, or database access.

The current Workbench [HTML entry point](../../../../src/Apps/Elsa.Workbench/wwwroot/index.html) loads a demo bundle, while [Workbench host management](../../../../src/Apps/Elsa.Workbench/Program.cs) is protected by a server-side management key. Read-only inspection of the separate Studio repository at `67cf888c3cc7` found a [Modules route](https://github.com/elsa-workflows/elsa-foundation-studio/blob/67cf888c3cc7fabbcd373cef512af081833d0fe5/src/Elsa.Studio.Web/Client/src/app/App.tsx) and [module registry page](https://github.com/elsa-workflows/elsa-foundation-studio/blob/67cf888c3cc7fabbcd373cef512af081833d0fe5/src/Elsa.Studio.Web/Client/src/app/modules/ModuleManagementPage.tsx), which manage host/module/package visibility rather than composition drafting; its App code explicitly keeps the management key out of browser requests. No builder-to-host API or browser-held key is proposed here. A later Studio/Workbench surface would need an authenticated server bridge and a separate apply/recovery contract under [#1964](https://github.com/elsa-workflows/elsa-foundation/issues/1964) and [#584](https://github.com/elsa-workflows/elsa-foundation/issues/584). The file-only developer workflow is the credible first integration point; the product home remains a decision.

## One fixture, four tasks

Personas: a developer composing a local host from source-controlled files, and an IT operator reviewing a candidate for an existing deployment. Both need an exact resolved view; the operator also needs provenance and explicit unchecked evidence. The sample import is synthetic: the proposed Worker selections, cache capacity `128`, plus unknown `AcmeAuditSink.FuturePolicy`. It represents a local source snapshot, never a live host.

1. **Start:** Choose the provisional Worker starter, or import the sample shell. Inspect its 14 requested feature IDs and required `Tasks`. No profile is certified for production identity.
2. **Persistence:** Choose `primary` as PostgreSQL / `ConnectionStrings:Elsa`; add the provisional diagnostics group and route its two EF consumers to `ConnectionStrings:Diagnostics`. The group gesture becomes two explicit feature bindings, not a persistent group-precedence layer. References are shown; values are not present.
3. **Refusal:** Open exact features and try to disable `Tasks`. The mock refuses because `WorkflowsRuntimeResumption` requires it and the Runtime EF feature depends on Resumption. Keep `Tasks`, or explicitly remove the affected chain. The draft is unchanged until recovery is selected.
4. **Import, edit, reopen:** Import the sample, change `WorkflowExecutableCacheCapacity` from `128` to `256`, export the illustrative JSON, then reopen that mock draft. The unknown external feature/setting is shown as preserved and unchecked. In the production bridge, unknown source content must be copied unchanged; this prototype does not perform that operation.

Each concept supports the same actions. With the provided shortcuts, the designed minimum to select Worker + diagnostics + primary + separate diagnostics is four choices in every concept. A refusal-and-keep sequence is two choices. Import, setting edit, export, and reopen is four choices. These are interface action counts, not observed user effort or task time; navigating, reading, and mistakes were not measured.

## Comparison from an internal walkthrough

| Criterion | Profile ledger | Work order | Expert workbench |
|---|---|---|---|
| Entry model | Pick a versioned starter and flat groups. | State a task through ordered source/outcome/infrastructure questions. | Search exact feature IDs and edit a pending change set. |
| Likely comprehension | Starter is quick, but “Worker” needs a clear boundary and provisional label. | Plain-language question order helps unfamiliar users; answer mappings must be trusted. | Exact state is obvious to experts; IDs and filters demand prior knowledge. |
| Designed shortcut choices for task 1–2 | 4 | 4 | 4 |
| Refusal and recovery | Adjacent to exact feature drawer; impact ledger remains visible. | Occurs in exception step; may require backtracking to the outcome answer. | Occurs at the row being edited; review ledger keeps the blocked edit visible. |
| Provenance | Strong: always-visible ledger and per-feature reason. | Good in review, less immediate during early questions. | Strongest for exact edits; dense for a new user. |
| File-versus-host risk | Persistent candidate label and unchecked list. | Explicit export step and unchecked preview. | Candidate label and edit ledger; experts may still infer that “workbench” is live. |
| Accessibility risk | Sticky ledger may become long; feature drawer must retain keyboard access. | Conditional steps must keep focus and announce changed questions. | Dense panes and search syntax need a table/list alternative and visible keyboard path. |

**Recommendation for the next product design iteration:** Use the profile ledger as the default shell, with the exact searchable workbench as its advanced view. Its always-visible impact and provenance fit a configuration tool that must make hidden feature expansion inspectable. Keep the task-led work order as a candidate onboarding flow only after real users show they need it; otherwise it adds another maintained mapping. Treat the three screens as alternatives for testing, not product components to combine wholesale. None of the profiles should be released until the Embedded API, Authoring authorization, and Worker production-identity decisions are resolved under [#1961](https://github.com/elsa-workflows/elsa-foundation/issues/1961).

## Real-user evaluation before implementation

Run six short moderated sessions: three developers who have used Elsa configuration, and three IT/operators who review deployment changes but are less familiar with feature IDs. Randomize the order of the three concepts. Give each person the four tasks above without naming the intended controls. Ask them to explain, before export, which exact features will run, why `Tasks` is present, where diagnostics will persist, what will be preserved from the imported file, and whether a running host has changed. Record completion, wrong turns, recovery path, elapsed time, confidence (1–5), and any mistaken live-host assumption. Do not coach except to unblock a session, and record each intervention.

Decision threshold proposed for that test: every participant must correctly identify export as file-only and the two diagnostics bindings; at least five of six should resolve the dependency refusal without losing their intended feature set. Use action/time observations to choose between the ledger and work order, and to decide whether the expert view should be a separate mode. The internal walkthrough above is **not** human usability validation.

## Review and implementation boundaries

The visual models need a real catalog/planner contract before production wiring: stable profile/group versions and ownership; a validated feature dependency explanation; reviewed setting paths; preserved unknown-source behavior; and a resolved resource plan. A browser-backed builder also needs its own authenticated server endpoint and draft/revision policy. A preview must never imply package availability, provider connectivity, safe migration, or live activation solely from a source snapshot. These are follow-up decisions, not claims made by this spike.
