# Workbench restart-scoped source boundary (#2060)

Status: bounded rebuilt-host proof on 2026-09-25, based on main `f04ecdca8c9a7f3bdc3fd85f6590bc9da3062742`. This follows the [hot-reload no-go](workbench-source-snapshot.md) and refines [spec 177](../../../specs/177-file-deployed-activation/spec.md). It does not implement a production deployment owner or candidate attestation.

## Decision

**Conditional go for a fresh-process *file* boundary; no-go for a captured source/override context or verified candidate matching in the current host.** In the six-file test bundle, a process started with root and default-shell values from one retained copy. A mutable source switched *after* that copy but before the child started did not alter the process's CORS policy or shell blueprint. A second process started from a new complete copy saw the new values. By contrast, changing the source between individual file copies produced a process with root and shell values from different source revisions. Restart alone is therefore insufficient: an external deployment owner must switch or retain a complete immutable artifact before Workbench starts. The probe does not capture effective environment/argument overrides or a private source identity at process start; the full #2060 source/override seam remains unproven.

The current Workbench does not own that immutable artifact, record a private source/override identity at process start, or correlate it with a shell generation. Its root and shell registrations share an `IConfiguration` reference but consume it at different times. `candidateMatch` remains `unverified`; a startup from files that happen to match a candidate on a later scan is not an attestation.

## Executed host evidence

The [reproducible Workbench test](../../../tests/essentials/Workbench/Tests/CompositionHostAttestationProbeTests.cs) starts built Workbench child processes, not an in-memory substitute. The new probe stages all six base, selected, and unselected `appsettings`/`shells` files. It copies the set to a private content root, changes the handoff source before the child starts, and observes the old CORS origin and `MaxSegmentCheckpoints=774001` in the first process. A second fresh process from the changed set observes the new origin and `774002`. The copied unselected siblings are present but are not effective inputs in the selected Development environment.

The same probe then simulates a file-at-a-time deployment: it copies the old selected appsettings overlay, changes both source overlays, and copies the new selected shell overlay. The resulting fresh process accepts the old CORS origin while its shell blueprint contains `774003`. This is a concrete mixed-source counterexample even without hot reload. The earlier [hot-reload probe](../../../tests/essentials/Workbench/Tests/CompositionHostAttestationProbeTests.cs) independently shows a new shell generation while startup-bound CORS remains old. The existing six-file/override probe shows an environment-supplied feature setting wins over selected JSON and that current public readiness/reload responses carry no generation-bound source marker.

The new host test passed 1/1, and the full attestation probe class passed 4/4. It demonstrates local processes and a test-owned retained copy. It does **not** prove that the repository has a production atomic deployment switch, that all source bytes were copied atomically under concurrent writes, or that root and shell attach a trustworthy candidate identity. The negative copy sequence is intentionally constructed to show the missing guarantee. No database, package-cohort integrity, deployed IdP, or recovery topology is exercised.

## Ownership and lifecycle contract for the next slice

1. An operator/deployer owns the complete configuration artifact, including unselected siblings. It must publish a new immutable directory or equivalent retained handles atomically; copying mutable files one by one into a live source directory is not a supported consistency boundary. The reviewed handoff ID and deployed artifact identity have different authority until that owner compares them.
2. A fresh Workbench process starts only after the artifact switch. Its selected environment, effective environment variables and command-line arguments are captured for that process. Root registrations, `ConfigureAllShells`, EF settings preparation, and blueprint composition must be tied to this same retained context. Current Workbench behavior relies on the external immutability assumption; it does not yet enforce or attest it.
3. Treat any changed input that may affect a root service as restart-required. This includes at least CORS, host-owned OpenIddict persistence, console streaming, Nuplane loading, eager activation, and root EF enrollment. A shell-only reload is eligible only after every relevant callback and preparer is audited against an unchanged startup-bound projection; otherwise refuse or require restart. A new process's shell generation number is not comparable to the previous process's number without a separate process identity.
4. After restart, an authorized observer may report the new process and default-shell readiness. It must keep candidate matching unverified until a trusted deployed-artifact receipt, private process-start source/override identity, applied-package cohort, and generation correlation are all available. Startup failure cannot be described as preserving the previous process unless the external deployment topology actually retained it. Database migration and rollback state are separate.

The next implementation boundary is a deployer/host handshake around a retained complete artifact and a private process-start receipt, followed by applied-package evidence. A shell-only blueprint marker or later directory scan would repeat the false-attribution risk found in [#2046](workbench-source-snapshot.md).

## Follow-up observation (#2062)

Workbench now returns an opaque process instance ID beside the default-shell generation in its management-key-protected GET and POST responses. That ID stays stable across shell reloads within one process and changes for a separately started process, so two equal generation numbers no longer imply the same host instance. The ID does not identify the deployment artifact, selected environment, effective overrides, or package cohort. The no-go for verified candidate matching above remains unchanged.
