# Selected-host evidence for composition planning

Status: investigation for [#2003](https://github.com/elsa-workflows/elsa-foundation/issues/2003), under [#1962](https://github.com/elsa-workflows/elsa-foundation/issues/1962). Source baseline: `59086262ca932fc3c80affa0556090f803608985`. This is a decision input, not a host-check implementation or a released profile.

## Decision

**No-go for presenting a deployment-directory scan as a checked host inventory or effective runtime configuration.** A selected directory is useful as a reproducible *source snapshot*, but the exact loaded feature graph and the running process's configuration cannot be established from its JSON and package manifests alone. Keep the shipped [`composition plan`](../../../src/essentials/Cli/CompositionPlanCommand.cs) file-only and explicitly unverified. The next implementation contract must distinguish a static, selected-source inspection from an authenticated host-produced observation. It must not turn `HostInventory.Source` or `PersistenceEvidence.Status` into an authority claim just because a local tool filled them in.

The positive finding is narrower: the existing EF tooling [configuration context](../../../src/essentials/Persistence/EntityFramework/Tooling/EfToolingConfigurationContext.cs) already composes a selected shell with the host's feature descriptors and resolves *resource identities* before feature activation. It can be reused as a design seam for a host-closure worker, with explicit source selection and an unchanged no-database guarantee. It does not by itself prove a running host has the same environment, command-line overrides, package generation, or connection target.

## What each source can actually observe

| Source | Supported observation | Limit |
|---|---|---|
| `shells.json` plus selected overlay | Authored feature names, disabled entries, and selected scalar settings. The existing [CLI reader](../../../src/essentials/Cli/ShellConfiguration.cs) intentionally retains only names and provider labels. | It omits required dependency expansion, root appsettings, environment/CLI overrides, package state, and connection equality. |
| Selected host configuration snapshot | Root and shell resource declarations, shell-default/feature bindings, and source mode, as in [EF tooling](../../../src/essentials/Persistence/EntityFramework/Tooling/EfToolingConfigurationContext.cs). | It must name the host, shell, environment, and exact source mode. The `workbench-json-environment-v1` mode reads the **tool process's** environment, which is not proof of the running host's environment; neither mode includes an arbitrary host's original command-line arguments. |
| Installed Nuplane package manifest | Package identity, digest, and declared feature/dependency hints via the [manifest contributor](../../../src/essentials/Modularity/Nuplane/Services/PackageManifestFeatureCatalogContributor.cs). | Installation is not loading. Manifest dependencies can differ from runtime descriptors, and a feed/package catalog may have changed after the snapshot. |
| Host-loaded descriptors | Exact descriptor dependencies, including an observed empty list, via the [runtime contributor](../../../src/essentials/Modularity/Nuplane/Services/RuntimeFeatureCatalogContributor.cs). | Acquiring them requires the host's loaded assembly closure or an authenticated host-produced snapshot. Loading assemblies is not a passive file scan and may execute package/module initialization code. |
| EF metadata preparation | Ordered feature closure and redacted resource names/selection kinds via [`EfPersistencePreparation`](../../../src/essentials/Persistence/EntityFramework/ResourceResolution/EfPersistencePreparation.cs). | Requires the selected host's descriptors and composer. With `verifyConnectionValues: false`, target affinity stays unresolved; no database operation occurs. |

The pure [planner](../../../src/essentials/Modularity/Planning/Services/SelectionPlanner.cs) deliberately preserves exact authored IDs; it never auto-adds a dependency. Its [host assessment](../../../src/essentials/Modularity/Planning/Services/HostAssessment.cs) treats loaded descriptors as governing and manifests as fallback evidence. A directory reader must therefore emit `installed`/unknown with `runtimeDependencies: null`, not `loaded` with a guessed descriptor list. `observedAt` would date the local inspection, not the runtime generation. Even a syntactically valid `HostInventory` can be caller asserted; the type carries no authentication or signed provenance.

## Concrete mismatch and source-precedence proof

The rebuilt [Worker fixture proof](worker-host-proof.md) authored 14 feature IDs, while CShells activated 15: `Tasks` was added by the required dependency of `WorkflowsRuntimeResumption`. A directory scan of the authored `Features` section would have returned 14 and incorrectly called it the complete host closure. That proof used a real host and a named SQLite resource; it did not establish static package inspection or live host drift. Its focused host test passed **1/1** on this baseline with no skips.

The Workbench [startup code](../../../src/apps/Elsa.Workbench/Program.cs) adds base shell JSON, environment overlay, then environment variables and command-line arguments. [Foundation Host startup](../../../src/apps/Elsa.Foundation.Host/Program.cs) instead adds only base shell JSON after the default builder. A generic `--host <directory>` reader cannot claim identical effective precedence for both. The existing [EF tooling context](../../../src/essentials/Persistence/EntityFramework/Tooling/EfToolingConfigurationContext.cs) freezes file-only versus file-plus-tool-environment sources and refuses an invalid host/shell selection; it does not silently inherit a live host's process state.

Focused existing EF tooling tests exercised this selected-source boundary: file and environment modes produced different expected connection targets; a frozen context did not follow a later file change; `Context_list_selects_the_named_resource_from_the_composed_shell_without_reading_its_connection` reported `primary`/`Shared` with target verification `not-performed`; and an unrelated resource was refused. The selected test class passed **39/39** on this baseline with no skips. These tests use disposable configuration files and source assemblies, rather than a newly built Nuplane deployment; they establish the EF seam, not full host-inventory generation.

No new directory-to-runtime snapshot comparator was built in this spike. The missing source is the result: a static scan cannot observe whether package assemblies were loaded, which descriptor generation a running host uses, or its private process overrides. A new comparator would be useful only after defining the host-produced observation it compares against. The existing Worker rebuilt-host proof supplies a known example of the authored-versus-effective mismatch.

## Safe next contract

1. Define a selected-source mode with explicit host directory, host identity, shell, environment, and configuration-source policy. It may read local JSON and already-installed manifests without feed access, activation, or database I/O. Its output says `source-snapshot`, distinguishes `installed` from `loaded`, and keeps persistence `unchecked`. Missing/ambiguous package or source facts produce unresolved findings, not an empty-green inventory.
2. For exact descriptor and effective-resource evidence, define a separate **host-produced** snapshot from the selected loaded closure. A host-closure worker may reuse the EF preparation seam, but its package-loading and code-execution boundary, authorization, versioning, generation/freshness, and output sanitization need review first. A live API also needs an authentication and replay contract. Do not infer live status from `--host` path syntax.
3. Reuse the existing planner result and redacted projection. A checked persistence claim requires reviewed provider, connection-name/value equality, schema, migration, and shared-context/transaction scope; [`EfPersistenceResourceValidator`](../../../src/essentials/Persistence/EntityFramework/Tooling/EfPersistenceResourceValidator.cs) with value checks disabled explicitly reports target affinity unverified. Resource names and selection kinds may be shown after safe-label validation; connection values, secret-store keys, raw provider exceptions, and untrusted rationale may not.
4. Before an implementation issue, test one disposable deployment with base/overlay/environment precedence, a dependency closure that expands beyond authored IDs, pinned package/manifest identities, resource override, missing manifest, and a canary credential. Compare the snapshot with the same host generation's observed descriptors and EF preparation. Refuse or mark unresolved any missing source, package drift, or unsafe output. The current EF tests cover only parts of this matrix.

The existing [persistence worker](../../../src/essentials/Cli/Worker/WorkerRunner.cs) is not yet a drop-in composition-inspection path: it loads the selected host and packages, can optionally restore packages, and emits package-load warnings from exception messages. A new read-only mode must close those side effects and sanitize failure output before sharing that boundary. Export/import and live drift remain separate decisions in the [developer command contract](developer-plan-command-contract.md).
