# Composition import and export boundary

Status: investigation for [#2005](https://github.com/elsa-workflows/elsa-foundation/issues/2005), under [#1962](https://github.com/elsa-workflows/elsa-foundation/issues/1962). Source baseline: `dcfa3ec9061def1b042896aa0290ac645fe9cc07`. This is a proposed contract for specification review, not a delivered importer, exporter, or management save path.

## Result

**Use three distinct artifacts:** portable authored intent, a redacted plan, and generated host files. Import from existing CShells files needs a *local source context* that keeps the original files and their layer identities available. A bare `AuthoredComposition` cannot replace that context without dropping other shells, unrelated nodes, and environment overlays. An exporter must derive a reviewed candidate into a new output directory by patching copies of the source files; it must not rewrite the live host or call the feature-management `SaveAsync` API in this first slice.

The first useful implementation is a file-only migration path for one selected host, shell, and environment, with an explicit catalog pin. It should preview imported exact feature IDs/settings/resources and show a diff before writing. It may write an authored document only when a developer explicitly accepts that baseline; missing package locks, host inventory, source overrides, and resource checks remain unresolved. It should then generate host files from that accepted document and the same local source context, preserving all unedited source material. The [shared planner](../../../src/essentials/Modularity/Planning/Services/SelectionPlanner.cs) remains the only feature-selection engine. The future builder UI should consume these same draft, plan, acceptance, and generated-output contracts.

## Source comparison

| Concern | Current source behavior | Contract consequence |
|---|---|---|
| Authored selection | [`AuthoredComposition`](../../../src/essentials/Modularity/Planning/Models/SelectionDocuments.cs) stores a catalog pin, optional profile, groups, additions/removals, previously accepted exact IDs/locks, and opaque `settings`/`resources` objects. | An imported legacy selection must not invent a released profile or package locks. Before developer acceptance it is a draft; after acceptance, a no-profile v1 document can record explicit IDs and empty locks, still showing inventory and persistence as unverified. |
| Strict reader | [`SelectionJsonReader`](../../../src/essentials/Modularity/Planning/Json/SelectionJsonReader.cs) rejects unknown top-level fields and duplicate keys, while cloning unknown nested fields under `settings`/`resources`. | Do not embed source layers into the v1 authored document or silently discard future top-level fields. Keep a separate local source context and version it if persisted. Semantic JSON round-trip, not byte-for-byte formatting, is the meaningful authored guarantee. |
| Plan output | [`composition plan`](../../../src/essentials/Cli/CompositionPlanCommand.cs) projects only reviewed, safe facts; opaque settings/resources are deliberately omitted. | Never implement export by serializing the plan. `plan` stays redacted and file-only; authored export and generated host output have different disclosure rules. |
| Existing editor | [`FeatureManagementService`](../../../src/essentials/Modularity/Nuplane/Services/FeatureManagementService.cs) restores masked values and validates a full feature request, then [`JsonShellFeatureConfigurationStore`](../../../src/essentials/Modularity/Api/Services/JsonShellFeatureConfigurationStore.cs) replaces the selected shell's `Features` node while preserving other JSON nodes. | Its save API cannot atomically write shell resource bindings and root resource definitions. Its HMAC revision covers `Features`, not the entire source bundle. Do not treat it as the import/export commit protocol. Whole-document apply/recovery belongs to [#1964](https://github.com/elsa-workflows/elsa-foundation/issues/1964). |
| Secret masking | [`SecretSettingMask`](../../../src/essentials/Modularity/Nuplane/Services/SecretSettingMask.cs) masks secret or undeclared feature settings in catalog responses, but the authored reader does not classify its opaque JSON. | Portable authored output should contain external references, not copied inline credentials. Unknown nonempty values remain in local source files until reviewed; there is no safe generic rule that converts arbitrary unknown values into public JSON. |

The committed Workbench fixture makes this concrete. [`shells.json`](../../../src/apps/Elsa.Workbench/shells.json) has **81** object-map feature entries, **12** with nonempty settings, plus `Name` and a shell `Configuration` node. [`shells.Production.json`](../../../src/apps/Elsa.Workbench/shells.Production.json) overlays **7** feature entries, 4 with nonempty settings; it also has a non-feature operational annotation that must be preserved. [`appsettings.json`](../../../src/apps/Elsa.Workbench/appsettings.json) holds root `ConnectionStrings` and `Elsa:Persistence:Resources` (currently empty) beside logging, CORS, and Nuplane configuration. Workbench startup loads base shell JSON, selected environment overlay, then environment variables and command-line arguments; [Foundation Host](../../../src/apps/Elsa.Foundation.Host/Program.cs) has a different layering path. A direct `shells.json -> AuthoredComposition -> shells.json` conversion would lose at least the other source layers and unrelated host settings, even if opaque feature values survived.

## Proposed first-slice semantics

1. **Select sources.** Require a host directory, explicit shell and environment, a pinned selection catalog, and an explicit file-source mode. Read base and selected overlay shell files plus relevant appsettings files as a frozen local source bundle. Record file identities and private change tokens; do not inherit the CLI process's environment or claim the running host's command-line values. If a selected source is missing, malformed, duplicated, or changes during inspection, refuse with a safe code and no partial output.
2. **Import preview.** Read CShells object-map and array feature shapes using the host's configuration semantics, distinguishing disabled entries, explicit false/zero/null/empty settings, shell `Configuration`, root resource definitions, and per-feature bindings. Show exact authored IDs and the identity, type, or presence of unclassified fields, but mask their raw values until reviewed; an unknown field may contain a secret. Preserve unknown IDs and fields in the local source context. Do not silently rebind host-owned/vendor stores or infer that an inline connection belongs in a shared resource.
3. **Accept authored intent.** Present the candidate and redacted findings. A developer can explicitly accept an initial no-profile selection pinned to the supplied catalog; accepted feature IDs record that human decision, not a verified runtime closure. Keep package locks absent unless a separately supplied, trusted inventory justifies them. The portable authored document contains only reviewed settings/resource references. Unknown or inline sensitive values need an explicit mapping to an external reference or remain anchored locally and unavailable in portable output. Never put the raw source bundle in the plan or a shareable authored export.
4. **Generate output.** Create a fresh destination directory, never overwrite by default. Patch copies of the selected source files with the accepted exact feature IDs and reviewed settings/resources, leaving other shells, overlays, unknown nodes, and unrelated appsettings semantically intact. Preserve untouched files byte-for-byte where possible. Show a redacted source-to-output diff and unresolved checks; success means files generated, not that the host can load packages, start, migrate, or reach the selected connection. An in-place apply and revision conflict protocol is separate [#1964](https://github.com/elsa-workflows/elsa-foundation/issues/1964) work.

The proposed source context is a local association with existing files, not a new portable settings-precedence layer. The authored v1 `settings`/`resources` fields can retain reviewed logical references and unknown nested JSON semantically, but they cannot by themselves carry the base/overlay split or arbitrary sibling nodes. A specification should choose whether that source association is an on-disk sidecar or an invocation-scoped context before an implementation story is filed. Any persisted sidecar should contain source paths and opaque revision tokens, not copies of secret-bearing documents.

## Inspectable before/after fixture

Use a disposable two-shell source bundle in addition to the committed Workbench files. Its base `shells.json` contains:

```json
{"CShells":{"Shells":{"default":{"Features":{"A":{"Flag":false,"Limit":0,"Future":{"x":null}},"B":false},"Configuration":{"Elsa":{"Persistence":{"DefaultResource":"primary","Bindings":{"A":"primary"}}}}},"tenant-b":{"Features":{"TenantOnly":{"Keep":"unchanged"}}}}},"CustomRoot":{"Keep":true}}
```

In `appsettings.json`, `Elsa:Persistence:Resources:primary` selects `PostgreSql` plus `ConnectionName: Shared`; `ConnectionStrings:Shared` stays in that local host file and is never copied into portable intent. In `shells.Production.json`, override only `A:Flag` to `true` and include an unrelated root key. Importing `default` for `Production` must show `A` selected, `B` disabled, the effective `Flag=true` with overlay provenance, `Limit=0`, `Future.x=null`, and resource reference `primary`; it must also say the target connection and package/runtime readiness are unverified. Generating output after an explicit edit to `A:Limit=1` must leave `tenant-b`, `CustomRoot`, and the unrelated overlay key unchanged; it must retain the disabled `B` entry or an equivalent explicit disabled state, rather than silently enabling it. A canary credential in `ConnectionStrings:Shared` and a canary value in an unknown feature field must each occur zero times in stdout, stderr, plan JSON, and any shareable authored file. The local generated host file may retain the existing values without printing them.

This fixture comparison is a **contract**, not a claim that a converter exists today. The current focused tests passed **13/13** selection-document cases and **42/42** store/secret-mask cases on this baseline. They establish parser preservation, feature-only save behavior, and masking, not import/export behavior. Before implementation review closes, a first converter must run the fixture end to end, compare parsed JSON subtrees after export, and assert no source file changed or database/package/host path was called.

## Decisions and readiness gate

| Decision | Recommendation / owner |
|---|---|
| Portable versus local data | Portable authored intent holds references and reviewed values; local source files retain unknown/raw values. #1962 specification must define the exact reference syntax and import review gesture. |
| Source association | Separate sidecar or invocation context, not an unknown top-level field in schema v1. Choose in the next specification using the two-shell fixture. |
| Initial accepted state | Import preview is not accepted. Explicit adoption creates a pinned no-profile authored baseline; package locks remain absent unless evidenced. |
| Generated-output writes | Fresh destination only in the first implementation. In-place apply, whole-bundle revision, and recovery remain #1964. |
| Unresolved features/settings | Preserve and show as unresolved; do not make up package availability or setting schema. Coordinate runtime unknown-feature behavior with [#1159](https://github.com/elsa-workflows/elsa-foundation/issues/1159). |
| Source layers and runtime claims | Inspect explicit files only; env/CLI and live host equality are not checked. The [selected-host boundary](selected-host-evidence-boundary.md) remains authoritative. |

**Go for a dedicated specification of this first file-only bridge; no-go for a direct implementation story yet.** The spec must resolve the source-association shape, secret/reference syntax, import acceptance action, output layout, and exact refusal codes. It should then split a thin end-to-end import-preview/accept/export story from later in-place apply. A trivial authored-file pretty-printer would not satisfy the existing-host migration task or the future builder's shared model.
