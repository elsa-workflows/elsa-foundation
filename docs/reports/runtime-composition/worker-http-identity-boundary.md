# Worker HTTP identity boundary (#2057)

Status: **no-go for a released Worker profile** on 2026-09-25. This is a source and existing-host-test finding, not a completed external-issuer integration. It refines the [Worker fixture proof](worker-host-proof.md) under [profile epic #1961](https://github.com/elsa-workflows/elsa-foundation/issues/1961).

## What is already proven

The [Worker HTTP fixture](../../../tests/essentials/Workflows/Runtime/Persistence/EntityFrameworkCore/Tests/WorkerHttpFixtureHostEvidenceTests.cs) starts a minimal CShells web host, resolves 14 authored Runtime feature IDs plus required `Tasks`, and completes HTTP execute, persistence, bookmark suspension, stimulus resume, and completion with one named SQLite resource. Its 401/403/200 assertions are useful permission-path evidence. They rely on `WorkerAuthenticationHandler`, a test scheme that accepts an `X-Worker-Permission` header and directly creates a principal with Elsa's internal normalized marker and permission claim. The host also injects a process-local lock provider. Neither is a deployable Worker identity/lock selection.

The focused Worker fixture test passed 1/1 on the current main-derived branch. Focused Foundation Identity OIDC registration and OpenIddict bearer tests passed 17/17. Those tests establish their own contracts; there is no test in this set that sends an externally minted JWT through the Worker shell and its Runtime permission endpoints.

## Available identity paths

| Path | Current capability | Worker consequence |
|---|---|---|
| External bearer via `FoundationIdentityOidc` | The [OIDC feature](../../../src/essentials/Foundation/Identity/Oidc/OidcAuthenticationFeature.cs) registers ASP.NET Core JWT validation. Its [named bearer options](../../../src/essentials/Foundation/Identity/Oidc/ConfigureOidcOptions.cs) set `Authority`, audience from `ClientId`, and HTTPS-metadata policy. `FoundationIdentityAbstractions` supplies shell authentication/authorization middleware and permission services. | A plausible single-host bearer authentication choice. Issuer, audience, and any secret remain host settings, outside immutable profile content. A valid JWT is **not yet** proof of an Elsa permission grant. |
| First-party tokens via `FoundationIdentityOpenIddict` | The [feature](../../../src/essentials/Foundation/Identity/OpenIddict/OpenIddictIdentityFeature.cs) issues and validates Elsa tokens; [bearer integration tests](../../../tests/essentials/Foundation/Identity/Tests/OpenIddict/OpenIddictBearerAuthenticationTests.cs) prove a validated grant, denial, anonymous refusal, and token rejection. | Adds an issuer, signing keys, and a token store to the Worker. Production vendor/store configuration is separately owned by [#1895](https://github.com/elsa-workflows/elsa-foundation/issues/1895). It is not the smallest external-issuer Worker prerequisite. |
| Host-owned authentication | The Worker fixture already composes the root host separately from its shell. | A host can supply its own provider, but it must deliver a *trusted normalized* principal through a reviewed contract. Merely selecting a bearer scheme or forwarding raw permission claims is insufficient. |

`FoundationIdentityAbstractions` and `FoundationIdentityOidc` are separate feature IDs. The [abstractions feature](../../../src/essentials/Foundation/Identity/FoundationIdentityAbstractionsFeature.cs) installs middleware within the shell; the OIDC feature registers the handlers. Workbench's [host composition](../../../src/apps/Elsa.Workbench/Program.cs) illustrates that root and shell middleware placement is deliberate. A future Worker proof must inspect the actual selected shell and mounted routes rather than infer them from feature names.

The current [OIDC registration](../../../src/essentials/Foundation/Identity/Oidc/Extensions/OidcAuthenticationServiceCollectionExtensions.cs) also registers the interactive handler whenever `ClientId` is present, while that same value supplies the bearer audience. A Worker marketed as bearer-only must verify this combined registration is harmless and disclosed, or separate those settings in a reviewed follow-up. It must not silently promise an API-only identity surface from this feature name.

## Blocking trust boundary

The [normalized-principal validator](../../../src/essentials/Foundation/Identity/Authorization/NormalizedPrincipalValidator.cs) accepts exactly one authenticated identity whose runtime authentication type is registered as trusted and which carries one valid normalized marker. The trust set starts empty in [Foundation Identity options](../../../src/essentials/Foundation/Identity/FoundationIdentityOptions.cs). The [normalizer](../../../src/essentials/Foundation/Identity/Authorization/AuthorizationServices.cs) strips incoming internal claims before it maps provider/tenant-scoped authority and creates that marker. This keeps an externally supplied marker or permission claim from self-authorizing.

The OIDC registration path does not invoke `IClaimsNormalizer` for an authenticated request or register its JWT identity type as trusted. The current source has no shipping external request-authentication adapter that performs the strip, map, mark, and trust sequence; [spec 151's FR-024](../../../specs/151-foundation-identity-permission-policy-bridge/spec.md) explicitly names that gap. Registering an OIDC issuer and audience can validate a token, but cannot currently establish the normalized principal that Elsa's `RequirePermission` runtime endpoints require. We therefore cannot honestly claim the Worker fixture's 403 and authorized execute/stimulus behavior with the existing OIDC feature. This conclusion is source-derived; a real-JWT Worker endpoint test is the follow-up gate.

## Decision and smallest next proof

Keep Worker as a planning fixture. Prefer an external-issuer, bearer-only path for the first Worker candidate rather than requiring it to issue tokens, but do not publish a `worker-http@1` profile yet. A separate bounded implementation must adapt validated OIDC bearer requests into the Foundation normalized-principal contract using reviewed provider/tenant mapping. It must fail authentication on normalization error; registering a trusted type alone or accepting an IdP-supplied internal marker is not enough. Coordinate scoped session grants with [#835](https://github.com/elsa-workflows/elsa-foundation/issues/835) rather than importing that whole Server/Studio RBAC program into this Worker slice.

The acceptance gate for that implementation is a minimal from-source Worker web host with the real JWT bearer handler and an isolated local issuer/key. It must show anonymous, tampered, wrong-issuer, and wrong-audience tokens receive 401; a validated caller without `workflow-runtime.execute` receives 403; a mapped caller with that permission executes and resumes the existing SQLite workflow over HTTP. It must reject raw internal marker/permission claims without the adapter's trusted mapping, report exact selected IDs and mounted route families, and keep issuer/key material outside the profile catalog. A local issuer proves validator and mapping wiring, not interoperability with a deployed IdP.

The [Embedded file-lock proof](embedded-lock-host-proof.md) supports one process/host with an isolated filesystem lock directory. It does not establish a multi-host Worker topology. Lock ownership and deployment topology remain explicit prerequisites for any later Worker publication, even after the identity gate passes.
