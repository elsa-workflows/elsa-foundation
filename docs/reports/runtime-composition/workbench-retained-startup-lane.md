# Retained startup lane proof (#2072)

Status: bounded, disposable Workbench proof. It establishes a viable host-owned configuration lane for the declared JSON artifact and process overrides. It does **not** establish complete deployment attestation, package identity, reviewed-candidate equality, or `candidateMatch=verified`.

## Result

**Go for a small production implementation story; no-go for an exact-candidate claim.** The opt-in `ELSA_WORKBENCH_STARTUP_ARTIFACT_PROBE=1` path in [Program.cs](../../../src/apps/Elsa.Workbench/Program.cs) makes Workbench open a private [declared artifact](../../../src/apps/Elsa.Workbench/WorkbenchStartupArtifactContext.cs) before its explicit Elsa root registrations. The context validates each listed source file against a private manifest, refuses undeclared top-level configuration siblings, retains the selected and unselected file bytes, and builds one non-reloading configuration root from the captured base and selected overlays followed by environment variables and arguments. It records the winning provider index for each effective key without publishing values, paths, or reusable digests.

The `configuration` passed to the root OpenIddict vendor registration, boot switches, CORS, Nuplane feed/loading, options, EF resource preparers, CShells blueprint provider and deferred Workbench shell defaults is the same immutable view in this probe path. The [rebuilt-host tests](../../../tests/essentials/Workbench/Tests/CompositionHostAttestationProbeTests.cs) prove command-line precedence over a conflicting environment value and refuse a file modified after manifest creation or an omitted unselected sibling. They then mutate selected and unselected source files and reload the shell: root CORS and the selected shell's blueprint keep their captured values. The test-owned receipt binds the six declared files, environment settings and argument sequence before launch; its label is never treated as host proof. The host's retained byte arrays and provider record belong to the child process that read them. The affected probe suite passed 10/10 tests; the architecture suite passed 277/277 and generated-map freshness passed.

This improves on [#2070's live split](workbench-startup-context.md): in the normal path, CShells can read a changed file during reload while root CORS stays at its process-start value. The probe path demonstrates that an owned snapshot can remove that specific split. It is deliberately opt-in, host-private and not an outward attestation API.

## Exact boundary

`WebApplication.CreateBuilder(args)` already reads its default appsettings, environment, arguments, host settings and development user secrets before Workbench can open this artifact. `ConsoleLogStreamingSetup.InstallConsoleStreamHookIfEnabled(args)` also runs earlier. The proof therefore covers the explicit Elsa configuration lane created **after** builder construction; it cannot claim that ASP.NET Core's own early host decisions (content root, environment, URLs, logging, user secrets or any host-provided source) came from retained bytes. A production design needs an earlier deployment/bootstrap seam or an explicit exclusion and separately checked host-input record.

The current private manifest is a test contract, not an authoritative deployment receipt. Its digest is used only to refuse a mismatch while Workbench opens the file; a mutable directory and mutable manifest could both be replaced before launch. A deployer must retain an immutable complete release and pass an authenticated handle or equivalent source identity that Workbench can open. Package binaries, Nuplane's assembly cohort and EF provider/migration prerequisites need independent evidence. No generated marker can equal a reviewed candidate yet.

The probe leaves root DI `IConfiguration` live so [management-key validation](../../../src/apps/Elsa.Workbench/ManagementApiKeyAuthentication.cs) keeps its per-request rotation behavior. This also leaves consumers that resolve DI configuration later outside the startup-lane completeness claim: [eager activation](../../../src/apps/Elsa.Workbench/Boot/EagerShellActivationHostedService.cs) reads it when the hosted service starts, and the [EF pending-migration guard](../../../src/essentials/Modularity/EntityFramework/EfPendingMigrationActivationGuard.cs) can use it as host-policy fallback. Provider-specific options that reread host DI configuration, and host/framework behavior bound during `CreateBuilder`, require a complete consumer audit before production use. Other shells are not generation-attributed by this proof. A failed shell promotion, process exit and recovery are separate outcomes; the [observer](../../../src/apps/Elsa.Workbench/Composition/CompositionActivationObservationEndpoints.cs) still reports an unverified candidate match.

## Smallest production story

Implement a first-class Workbench startup source contract backed by an externally retained immutable release, with a bootstrap boundary early enough to account for host inputs. Define which settings are startup-bound and which are intentionally live. Make the selected shell, all startup-bound root consumers, eager activation and EF migration-policy fallback use one typed startup context; keep the management key in a named live lane. Preserve selected and unselected source evidence and effective provider precedence privately, and refuse undeclared files, unknown providers, mixed artifacts and drift before activation. Expose only a fresh opaque process/source correlation and refusal class, attached to a successfully promoted shell generation; never return bytes, paths, connection values or reusable hashes. Test source mutation, override mismatch, omitted siblings, reload, process restart, failed activation and management-key rotation in a rebuilt host. Candidate verification remains blocked on reviewed-candidate equality, applied package cohort, provider/migration gates and recovery semantics.
