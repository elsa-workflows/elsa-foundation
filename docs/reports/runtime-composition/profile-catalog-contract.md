# Profile and feature-group catalog contract

Status: proposed decision record for [#1982](https://github.com/elsa-workflows/elsa-foundation/issues/1982), under [#1961](https://github.com/elsa-workflows/elsa-foundation/issues/1961). This is architecture discovery, not a shipped profile catalog or an activation guarantee. Source baseline: `57d791bd8a65a5d8045911487cdea2732eb5c2fd`. The generated maps passed `dotnet run --project tools/maps/Elsa.Maps.Generator -- check` on this baseline.

## Boundary and current evidence

The existing management [feature catalog](../../../src/essentials/Modularity/Core/Models/FeatureCatalogItem.cs) describes individual features, their source, installed package identity/version, settings, and dependencies. It has categories for display and a `Group` hint for individual **settings**; neither is a feature-group or starting-profile definition. [FeatureManagementService](../../../src/essentials/Modularity/Nuplane/Services/FeatureManagementService.cs) seeds enabled shell features, enriches them from runtime descriptors and installed package manifests, then masks secrets. Its `Revision` belongs to the authored shell feature snapshot. It is not an immutable revision of all catalog metadata or package availability.

The [runtime contributor](../../../src/essentials/Modularity/Nuplane/Services/RuntimeFeatureCatalogContributor.cs) uses loaded CShells descriptor IDs and their dependency graph. All runtime descriptor dependencies are mandatory, including when the graph is empty. The [manifest mapper](../../../src/essentials/Modularity/Nuplane/Services/PackageManifestCatalogMapper.cs) uses `cshellsFeatureName` when present and otherwise the manifest feature ID; it supplies dependency optionality only when a runtime descriptor did not resolve the list. It strips a same-package prefix from manifest dependencies to align them with CShells IDs. An installed manifest is metadata for an installed package, not evidence that another package version exists in a feed or can load on this host. Read errors are represented in catalog entries by the [package contributor](../../../src/essentials/Modularity/Nuplane/Services/PackageManifestFeatureCatalogContributor.cs).

The [fresh feature dependency map](../../maps/feature-dependency-map.md) reports 105 feature classes, one concrete feature without an explicit `ShellFeature` ID, and zero duplicate explicit IDs. The missing ID is Workbench-local `RuntimeFaultStackTraceFeature`; it is not evidence that the distributable Elsa feature set lacks stable IDs. The older [composition evidence report](../cshells-composition-evidence.md) says zero concrete IDs were missing and must be read as a previous snapshot. The map contains project/package-reference evidence but does not classify those edges as required feature activation. The report's dependency-kind and settings-kind vocabulary remains provisional planning guidance, not generator policy.

The accepted [shared-persistence specification](../../../specs/173-shared-persistence/spec.md) and [#1968](https://github.com/elsa-workflows/elsa-foundation/issues/1968)/[#1969](https://github.com/elsa-workflows/elsa-foundation/issues/1969) establish effective provider/connection resolution for reviewed consumers. A profile may select persistence features, but provider, connection reference, schema, migration policy, and physical-layout validation remain a separate configuration concern. A group-wide database choice is a bulk editor action that writes explicit feature bindings, not another runtime inheritance level.

## Proposed v1 decision

| Ownership/distribution option | Assessment |
|---|---|
| Foundation-reviewed catalog bundled with developer tooling | **Select for v1.** One reviewable source can pin profile/group versions and be used by both command and UI. It requires explicit maintenance as features evolve. |
| Package-contributed profile/group definitions | Retain package manifests as feature metadata and installed-package evidence. Letting an installed or third-party package change a reviewed starting profile would make membership depend on what happened to load. |
| Separately hosted catalog service | Defer. It adds a network/availability and trust boundary before the first offline developer workflow has been proven; immutable pinning would still be required. |

Use two evidence layers with different authority:

1. **A Foundation-owned, reviewed selection catalog** defines immutable starting profiles and flat groups using stable CShells feature IDs. Keep its source in this repository and distribute a versioned, content-addressed snapshot with the developer planner. The builder UI consumes the same planner contract. It does not require a hosted catalog service or package execution to show the choices. Only reviewed metadata may declare profile/group membership and dependency rationale; package-contributed labels, categories, or settings hints may enrich display, but cannot silently change a reviewed group.
2. **A host inventory** supplies what is actually loaded or installed for a specific target host, including runtime descriptor dependencies, package ID/version, manifest hash/read errors, and current shell selections. The planner compares its pinned selection catalog to this inventory and reports availability. It must not treat a local installed-package list as a remote feed search, or assume a package with the right name satisfies a host compatibility floor. [#1145](https://github.com/elsa-workflows/elsa-foundation/issues/1145) and [#1951](https://github.com/elsa-workflows/elsa-foundation/issues/1951) own those loading/floor guarantees.

The v1 authoring contract has zero or one starting profile, zero or more **flat** groups, explicit feature additions, and explicit feature removals. Groups may be recorded as pinned selection intent in the authoring document, but never become a third runtime settings-precedence layer. Expansion is set algebra in this order: profile members, union of group members, additions, removals, then dependency validation. Removal of a required dependency produces an unresolved explanation; the planner does not quietly restore it. Optional companions are suggestions, never automatic required additions. The expanded explicit feature set is what a future export materializes for CShells.

Pin each profile/group by stable ID, immutable version, and content digest. A published version is never edited in place; a changed membership receives a new version and digest. The authored composition also records the exact expanded feature IDs and the catalog digest used to compute them. For each resolved feature, a lock records the observed package ID/version and manifest hash, or marks it as host-bundled; missing identity stays unresolved rather than receiving an invented pin. This freezes existing compositions when catalog metadata changes and makes package drift visible. Re-resolution is an explicit operation showing added/removed features, changed dependency rationale, package drift, and settings/resource impact before acceptance. A custom profile is a user-owned, source-controlled authoring document in the developer workspace in v1, with the same version/digest rules. The server's current feature-management JSON store and its feature-only revision are not suitable as a global custom-profile registry. A future hosted builder needs its own draft/revision storage decision under [#1964](https://github.com/elsa-workflows/elsa-foundation/issues/1964).

Only the known CShells feature ID is a selection key. A duplicated ID blocks catalog publication. Unknown IDs, absent packages, unreadable manifests, unresolved dependency edges, and incompatible package/host versions remain preserved in the authored document and explicitly unresolved in a plan. The planner must not announce a runtime ready merely because an ID occurs in a manifest; live activation/readiness retains its own checks. [#1159](https://github.com/elsa-workflows/elsa-foundation/issues/1159) owns the existing runtime behavior for unknown requested features. Source categories are navigation metadata, not dependency or membership authority. Host-loading and package availability stay separate from feature selection, as the [composition evidence boundary](../cshells-composition-evidence.md#assembly-scanning-and-loading) requires.

The content digest should cover a canonical serialization of the owned profile/group definitions, including IDs, versions, members, and reviewed dependency explanations. It should not include configuration secret values, host-specific connection strings, mutable enabled state, or the live catalog response's shell revision. The exact file format and digest algorithm are an implementation detail for the first planner story; this record fixes the semantic boundary.

The [runtime catalog contributor](../../../src/essentials/Modularity/Nuplane/Services/RuntimeFeatureCatalogContributor.cs) can explain mandatory edges for loaded features, while the [manifest mapper](../../../src/essentials/Modularity/Nuplane/Services/PackageManifestCatalogMapper.cs) can preserve optionality for unloaded features. If these sources disagree, the plan records the loaded descriptor as runtime evidence and the manifest as divergent metadata; a reviewer decides whether a group definition should change. The examples do not infer required activation from project references. API claims above come from the named `IWebShellFeature` registration methods, not from synthetic feature counts; they name API areas, not a verified route inventory. An executable plan should use the host's API-capability evidence for the latter.

The later [Authoring host proof](authoring-host-proof.md) closes this fixture's specific evidence gap: its 16 explicit IDs resolve to 18 effective features, including `WorkflowsRuntimeApi` and `WorkflowsRuntimeTriggers`, and the raw selection lacks the Workbench's identity substrate for HTTP requests. The table remains a planning example, not a released authoring-only profile. Embedded, Worker, and Custom still need separate host evidence.

## Delivery boundary and follow-on work

The next specification task can define a pure, file-backed catalog/profile/group **planner** with pinned definitions, deterministic expansion, unresolved results, and fixture tests. Its later implementation should consume a supplied host-inventory snapshot and the reviewed persistence effective-plan contract, and perform no package fetch, database access, shell activation, or save. It should expose the same plan result to a developer command and later UI without generating a form for every property. Before filing the live profile story, verify the Embedded/Authoring/Worker fixture closures in rebuilt hosts, exact API surfaces, host-loading needs, and any missing dependency metadata. That is a separate acceptance gate, not a claim this report has already met.

This belongs to the [Feature Composition Readiness program](../../program-goals/feature-composition-readiness.md) as an architecture/report finding. It does not ratify framework-wide settings classification, alter the constitution, or replace package loading, module layout, or the runtime-builder UX epic.
