# Composition apply and recovery boundary

Status: bounded investigation for [#2034](https://github.com/elsa-workflows/elsa-foundation/issues/2034), under [#1964](https://github.com/elsa-workflows/elsa-foundation/issues/1964). Source baseline: `6489afb3b8773ef58a1c9ed002ee7f3333a6c529`. This recommends the next contract; it does not ship an apply API or promise an atomic deployment.

## Decision

Start with a **file/deployment activation contract for one selected Workbench-style shell**, using the delivered file bridge's accepted authored document, redacted diff, and fresh generated candidate. Keep the actual promotion under an explicit deployment/operator action and use the existing authenticated root shell reload, followed by active-generation and readiness verification. The first supported flow should expose separate `candidate generated`, `deployment accepted`, `reload attempted`, and `generation active` outcomes, plus a route back to a known previous deployment. A generated file is never an activation result.

Do not widen the legacy `POST /modularity/features/apply` endpoint into a resource-aware whole-bundle editor. Its revision and save operate on one shell's `Features` node, while shared persistence spans root definitions, shell bindings, environment overlays, connection references, and potentially host process overrides. An endpoint that writes only `Features` cannot provide a truthful whole-composition conflict or recovery guarantee. A later server-side apply API may be justified after the file/deployment contract proves the bundle, revision, host-observation, and recovery semantics.

The first contract should *specify*, then test on a disposable host, the exact promotion mechanism. It must not assume that replacing several JSON files one by one is atomic or that a directory-to-directory rename is available in every deployment. Immutable release directories with a host/deployment-controlled switch are a candidate mechanism, not an existing Foundation capability. If the selected host cannot activate a complete bundle from one controlled generation, the flow must stop at reviewable candidate output and documented operator deployment rather than advertise in-place apply.

The Foundation Host module-management refresh route is a different surface: it refreshes a catalog and reloads active shells, returning aggregate counts. It should not be inferred to provide the Workbench root endpoint's per-shell activation proof or a bundle commit protocol.

## Failure matrix and focused probes

The [service fault probes](../../../tests/essentials/Modularity/Tests/FeatureManagementServiceTests.cs) use an in-memory recording store and controlled refresher/reloader. They pin the ordering, not disk durability. The [real registry test](../../../tests/essentials/Modularity/Tests/ServerReadinessTests.cs) supplies the actual previous-generation behavior. The file bridge's source-change and publication tests cover a separate, pre-deployment boundary.

Focused verification on this branch: `FeatureManagementServiceTests` and `ServerReadinessTests` passed **38/38** (including all three new fault probes and the real-registry reload failure); `EfPersistenceActivationContextPreparerTests` passed **18/18**; `CompositionBridgeSourceTests` passed **12/12**; `CompositionFileSourceTests` and `CompositionGenerateCliTests` passed **15/15**. These runs use focused, container-free suites; they are not a claim about the full CI matrix or a production database.
After the repository's Release/Debug restore preparation, the architecture guard passed **276/276**. `Elsa.Maps.Generator -- check` reported that generated maps still describe the tree.

| Event | Authored/candidate state | Catalog/reload state | User-visible implication |
|---|---|---|---|
| Stale `Features` revision at legacy save | Save refuses; no new feature selection | No refresh or reload | Conflict applies only to the feature node. Re-read and re-review. |
| File-bridge source changes before candidate publication | Original source untouched; no candidate published | No host call | Re-preview exact sources. A previous invocation's acceptance cannot be replayed as a revision token. |
| Resource applicability or guard refuses before legacy save | No save | No refresh or reload | Safe pre-save refusal for the supported guard scope; it says nothing about other source layers. |
| Catalog refresh throws after legacy save | New feature selection remains in store | Reload is not called | API failure does not mean no mutation. An automatic client retry using the old revision will conflict. |
| Reloader throws after legacy save/refresh | New feature selection remains in store | Refresh happened; reload attempted | API failure again hides a persisted desired change. Active generation must be read separately. |
| Reloader reports a CShells error | New feature selection remains in store | `ReloadedShellCount=0`; `ApplyAsync` returns normally | A returned apply result can mean saved-but-not-active. The previous generation can remain ready; verify it from the registry/host, not the count alone. |
| Final catalog construction throws after reload | New feature selection remains in store | Reload may already have promoted the candidate | The caller sees an error although activation may have succeeded. Read the active generation before any retry. This is a source-order implication, not a separately injected probe. |
| Candidate initializes and is promoted | Deployment source and active generation need separate identities | Prior shell drains only after promotion | Success requires matching selected shell, expected new generation, and readiness. Database migration/data movement remains a separate claim. |

These tests do **not** prove a combined saved-file-plus-registry failure in a real Workbench instance, interruption during `File.WriteAllTextAsync`, atomic multi-file publication, or an authenticated builder-to-host API. Those are next-contract acceptance cases. The immediate risk is the indistinguishable `failure after save` versus `failure before save` response, and the normal response with a zero reload count.

## First contract to specify

1. **Review identity.** Pin the accepted authored selection/catalog, exact candidate bundle digest and each included source layer, selected host/shell/environment, and a redacted diff. Keep physical paths, connection values, unknown raw fields, and private file tokens out of shareable output. The bridge's invocation token is not a durable apply token. The deployment system must supply its own expected-current generation or compare-and-swap boundary; if absent, require a fresh operator review at deployment time.
2. **Preflight without side effects.** Check supported host layout, complete source bundle, package/descriptor availability where an authenticated host observation exists, resource names, and migration prerequisites. Label database target and package claims `unverified` when the evidence is unavailable. Refuse known resource-managed edits through the legacy feature editor. Do not open a database merely to decide whether a local file candidate can be generated.
3. **Promotion and verification.** Deploy a complete reviewed candidate with an explicit host-specific mechanism, invoke only the authorized root reload, then observe per-shell reload success, active generation, and readiness. Treat save/deployment completion and runtime activation as distinct states. Preserve the previous complete deployment and active generation until new promotion is verified. No browser-held management key; follow [ADR 0037](../../adr/0037-studio-management-bridge-keeps-host-management-key-server-side.md) for a future server bridge.
4. **Failure and retry.** Expose `refused-before-change`, `candidate-only`, `deployment-changed-not-active`, and `active` as distinct outcomes with safe codes and a redacted correlation/operation ID. After an uncertain response, read back both deployed bundle identity and active generation before retrying. A retry must not blindly replay a stale candidate; a repair or revert creates a freshly reviewed operation against the observed current state. If promotion fails, keep serving the previous active generation and offer operator rollback of the deployed source. Do not claim database rollback or undo migrations.
5. **Scope gate.** Prove one Workbench-style base/selected-overlay host and one shell first. Test changed unselected files, package/config drift, missing migrations under `Validate`, process overrides, a failed initializer after deployment, reload timeout/interruption, and a successful recovery with the old generation still serving during the failed attempt. Other hosts, multi-shell transactions, resource writes, and a hosted UI remain separate decisions.

## Dependencies and product choices

The [connection guard #1902](https://github.com/elsa-workflows/elsa-foundation/issues/1902) still has provider-validation and shared-context gaps; a green static check is not a connection or migration guarantee. [OpenIddict #1895](https://github.com/elsa-workflows/elsa-foundation/issues/1895) remains host-owned and SQLite-bound in Production, so it cannot silently inherit the shared EF resource claim. [Secrets policy #1900](https://github.com/elsa-workflows/elsa-foundation/issues/1900) remains an exception to host-wide `Validate`; preflight must identify it rather than label the whole deployment migration-safe. [Package loading #1145](https://github.com/elsa-workflows/elsa-foundation/issues/1145) and [host compatibility #1951](https://github.com/elsa-workflows/elsa-foundation/issues/1951) retain their own guarantees. The [selected-host evidence boundary](selected-host-evidence-boundary.md) explains why a directory scan is not a live inventory. This spike neither resolves nor reparents those issues.

For v1, choose **externally deployed bundle plus observed activation**. The operator or existing deployment pipeline owns the complete-bundle switch and its source rollback; Foundation owns candidate identity, safe preflight findings, an explicit reload invocation recipe, and observation of the resulting shell generation. The specification must define how the deployment passes an immutable bundle identity and expected-current identity into that observation; it cannot reuse the bridge's private invocation token. A managed server-side store, Foundation-owned switch/rollback, and browser apply each require later proof of an atomic complete-bundle switch, authorization, and recovery. The first implementation issue should be cut only after the v1 contract and disposable-host fixture are specified.
