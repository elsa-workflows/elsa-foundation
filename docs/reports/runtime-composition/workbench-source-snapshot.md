# Workbench source snapshot boundary (#2046)

Status: investigated on 2026-09-25 against Workbench and CShells `0.0.30-preview.159`. This is a source/override seam decision for [spec 177](../../../specs/177-file-deployed-activation/plan.md), not a candidate-match implementation.

## Decision

**No-go for a complete file-and-process snapshot on a Workbench shell hot reload as currently constructed.** A shell reload can publish a new generation while a root service continues using a value bound at process startup. The [rebuilt-host regression probe](../../../tests/essentials/Workbench/Tests/CompositionHostAttestationProbeTests.cs) demonstrates this with a selected shell overlay and root CORS setting: the generation advances and the private blueprint read shows the new overlay value, but the HTTP CORS policy still accepts the old origin and rejects the new one. This does not prove the exact overlay bytes used by that generation; that missing correlation is part of the no-go. The result is a split between a shell generation and its host, not one effective host snapshot that could be given a single source marker.

A custom blueprint provider is technically available, but replacing only the current provider cannot close this seam. Workbench's [`WithConfigurationProvider(configuration)` and `ConfigureAllShells(...)`](../../../src/apps/Elsa.Workbench/Program.cs) are separate inputs: the latter runs during blueprint composition and binds `WorkbenchEfToolingShellDefaults` from the live root configuration. Root OpenIddict vendor persistence, CORS, console streaming, Nuplane feed/loading, and eager-activation choices are configured outside the shell provider. A second scan of the files would identify what is present *later*, not necessarily the bytes or overrides consumed by those earlier registrations. Attaching that scan's identity to a blueprint would make a false attestation possible.

**Conditional go for a restart-scoped host snapshot:** A later implementation can make one immutable deployment artifact and captured process override set the sole source of a newly started Workbench. The host must construct its root services and its shell blueprint from that same frozen context and reject any startup-bound change on shell-only reload. A narrower shell-only reload is possible only after every participating callback and preparer is audited and bound to the candidate context. Neither path is implemented by this spike. `candidateMatch` remains `unverified`.

## Actual input boundary

[`Program.cs`](../../../src/apps/Elsa.Workbench/Program.cs) first calls `WebApplication.CreateBuilder(args)`, which loads `appsettings.json`, the selected `appsettings.{Environment}.json`, Development user secrets when applicable, environment variables, and arguments. It then adds `shells.json` and selected `shells.{Environment}.json` with change reload enabled, and adds environment variables and arguments again so they win over the shell files. Thus the effective precedence is framework defaults and appsettings layers, then selected shells layers, then the final environment and command-line layers. The selected environment is fixed when the process starts.

The copied unselected `appsettings.*.json` and `shells.*.json` siblings are **not** loaded by this Workbench process. They still matter to the externally deployed artifact and its integrity, as the [CLI bundle source](../../../src/essentials/Cli/CompositionFileSource.cs) demonstrates, but changing an unselected sibling cannot be inferred from the shell's `IConfiguration`. A complete artifact snapshot must enumerate and validate those bytes separately before a trusted owner switches the artifact. The CLI's source reader does not own Workbench's root configuration, and merely calling it from Workbench after startup would not establish equality with what the root services loaded.

Environment values and command-line arguments are effective inputs, including per-feature overrides. The existing [host attestation probe](../../../tests/essentials/Workbench/Tests/CompositionHostAttestationProbeTests.cs) verifies that an environment-supplied feature setting beats a selected overlay and that all six copied base/overlay files can change without producing a generation-bound source marker. Process environment and command-line values must be captured privately at process start; a file-only identity cannot represent them. Their raw values, physical paths, and hashes of secret-bearing settings must never be put in shareable output.

## Why a provider prototype cannot safely claim the whole snapshot today

The pinned CShells [`CShellsBuilder.AddBlueprintProvider`](https://www.nuget.org/packages/CShells/0.0.30-preview.159) permits one external provider. Its built-in `ConfigurationShellBlueprintProvider` obtains live configuration sections; `ConfigurationShellBlueprint.ComposeAsync` re-reads its section. A replacement can capture immutable settings and metadata for *its own* blueprint, as [#2042's in-process generation probe](../../../tests/essentials/Modularity/Tests/CompositionGenerationSeamProbeTests.cs) proves with two shells, a paused activation, and initializer/commit rollback. CShells then wraps the provider's blueprint with the host's `ConfigureAllShells` callbacks. Those callbacks currently read the live root again. A custom provider therefore cannot make the assembled shell settings immutable while this callback remains. It also has no authority to rebind already constructed root services or prove that their startup reads came from the same bytes. A disposable-host provider that claims a complete marker without changing these boundaries would prove only that the provider can label its own partial input.

The [Workbench EF settings preparer](../../../src/essentials/Modularity/EntityFramework/EfPersistenceShellSettingsPreparer.cs) copies current configuration values and checks a reload token around its own work. That is a useful local drift guard, but it does not own file bytes, root registrations, unselected siblings, or the other stages of shell activation. A JSON file change is observed asynchronously by each reloadable provider; a sequence of per-file atomic renames is not a complete-bundle transaction. Pausing activation while replacing files could therefore mix observed layers unless one artifact is frozen and all consumers use it. #2042's paused in-process test proves the CShells metadata and rollback mechanism, not that Workbench currently has this source owner.

## Safe next design boundary

1. Define one deployment owner that publishes an immutable complete directory or equivalent retained file handles, including unselected sibling bytes. Validate the full file set before handing an opaque release identity to the host. The host must not infer this identity by scanning mutable live files after reload.
2. At process start, capture the selected environment and effective environment/argument winners together with that artifact. Construct root services, shell defaults, preparers, and the custom blueprint from this *same* context. Remove every deferred read of a separate live root from the shell path. The host privately retains the full context; outward responses contain only a safe opaque ID and status.
3. Classify settings by lifecycle. Any changed input used by OpenIddict's root store, CORS, console streaming, Nuplane feed/loading, eager activation, or another startup-bound service requires a new Workbench process. For a shell-only change, compare the startup-bound projection with the current host baseline and refuse on difference before attempting reload.
4. Only after this source/override seam is executable in a rebuilt Workbench should the provider attach immutable, nonsecret metadata to each generation. A failed initializer or participant commit must retain the prior active generation and marker; two shells must keep separate generation bindings. [#2042](source-generation-attestation.md) proves the CShells-level mechanism, but the Workbench-level proof remains open.

This decision says nothing about Nuplane's applied package cohort, a private deployer/host receipt comparison, recovery, or database/migration readiness. Each is a separate gate in [#2042](source-generation-attestation.md) and [spec 177](../../../specs/177-file-deployed-activation/plan.md). Until all relevant gates pass, the [root observation endpoint](../../../src/apps/Elsa.Workbench/Composition/CompositionActivationObservationEndpoints.cs) must keep reporting `candidateMatch=unverified`.
