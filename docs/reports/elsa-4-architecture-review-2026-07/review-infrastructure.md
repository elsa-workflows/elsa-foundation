# Elsa 4 Infrastructure Substrate — Architecture Review

**Scope reviewed:** `src/Elsa/Events`, `src/Elsa/Mediator`, `src/Elsa/Pipelines`, `src/Elsa/Tasks`, `src/Elsa/Caching`, `src/Elsa/Serialization`, `src/Elsa/Locking`, `src/Elsa/Primitives`, `src/Elsa/Foundation`, plus root and per-domain `EXTENSION_POINTS.md`/`README.md`. Elsa 3's `src/common/Elsa.Mediator` (elsa-core repo) used as comparison baseline.

> **Note on delivery:** My operating constraints prohibit writing to files. The report below is the complete deliverable in place of the requested `review-infrastructure.md`.

## Executive Summary

Elsa 4's infrastructure substrate is a deliberate, well-documented attempt to replace Elsa 3's single broad `INotificationHandler<T>`/`ICommandHandler<T>` mediator with three narrower primitives: an `IEvent`/`IEventHandler<T>` pub-sub substrate with pluggable dispatch strategies, a parallel `ICommand`/`IRequest` mediator with its own pipelines, and a repo-wide "contributor interface + single aggregating handler" convention for fan-in extension points. The documentation discipline (root + per-domain `EXTENSION_POINTS.md`) is genuinely good and the *contributor-interface-for-contribution, `IEventHandler<T>` for independent-subscription* rule (§2.24.2) is a real, valuable clarification over Elsa 3's undifferentiated notification broadcast.

However, the implementation has real cracks that undercut the redesign's stated goals:

- The **Mediator half duplicates and gets wrong** the exact anti-pattern the Events half explicitly documents avoiding (resolving the non-generic handler marker forces every handler in the container to be instantiated on every dispatch) — see **IN-1**.
- The three pipeline builders (Command/Request/Event) are **copy-pasted, not shared**, and have diverged in both capability and behavior (accumulate vs. replace semantics) — see **IN-6/IN-7**. The only genuinely shared code is a small reflection helper in `Pipelines.Core`.
- **Command vs. Request is a distinction without a mechanical difference** — two complete, parallel sets of contracts/pipelines/builders/senders/contexts (≈30 types combined) for what is functionally one request/response shape (à la MediatR's single `IRequest<T>`).
- Two concrete correctness/performance bugs sit in hot paths: `JsonPayloadSerializer` rebuilds `JsonSerializerOptions` from scratch on every call (**IN-3**), and `BackgroundEventPublisher` can silently misreport failures because it links the *original caller's* (already-disposed) cancellation token into "fire-and-forget" dispatch (**IN-2**).
- `IBackgroundTask.StopAsync` is a **dead contract member** — implemented, documented, never called (**IN-5**); a `[SingleNodeTask]` on a secondary node can block startup for the full 10-minute default lock timeout and then crash it (**IN-4**).

None of this is fatal, and much of it is fixable with local, mechanical changes. But it means the "slimmer, stronger-typed successor" narrative is only half realized: **the events substrate is the disciplined half; the mediator half re-introduces the sloppiness (reflection-heavy, uncached, marker-resolving dispatch) that the events design explicitly calls out as wrong.**

## Per-Domain Assessment

### 1. Events (`src/Elsa/Events`)

The substrate is small and readable: `IEvent` (marker) → `IEventPublisher.Publish` → `EventPipeline` (one middleware: `EventHandlerInvokerMiddleware`) → `IEventPublishingStrategy` (Sequential/Parallel/Background) → `IEventHandler<T>`.

- `EventHandlerInvokerMiddleware` (`src/Elsa/Events/Middleware/EventHandlerInvokerMiddleware.cs:17-31`) resolves handlers via the **closed generic** `IEventHandler<TEvent>` only, and caches the closed-generic `Type` per event type in a `ConcurrentDictionary`. The code comment (lines 24-27) explicitly explains *why* this matters: resolving the non-generic marker would force every handler in the container to construct on every publish. This is correct, disciplined design.
- Full middleware pipeline for in-process events (`EventPipelineBuilder` + `IEventMiddleware`) is arguably heavier than needed for what is, by default, a single fixed middleware (`EventHandlerInvokerMiddleware`, see `EventPipeline.cs:28-31`) — but it is cheap (a builder + a `Func` chain) and gives a genuine seam (cross-cutting concerns like tracing/metrics could be added as middleware without touching the publisher). Verdict: reasonable, not over-engineered, given it's reused by 3 domains.
- Three strategies (Sequential/Parallel/Background) are clean, singleton, allocation-light (`EventPublishingStrategy.cs:8-18`). `BackgroundProcessingStrategy` just enqueues (`BackgroundProcessingStrategy.cs:13-20`) — no allocation beyond the channel write.
- **Reflection cost per publish is not fully cached.** `EventHandlerHelper.GetHandleAsync` (`Strategies/EventHandlerHelper.cs:9-13`) calls `typeof(IEventHandler<>).MakeGenericType(eventType)` + `GetMethod(...)` **fresh on every `Publish` call** (unlike the middleware's own `Type` cache) and then invokes every handler via `MethodBase.Invoke` (reflection) rather than a cached compiled delegate. For the default (Sequential, synchronous, can-break-the-caller) path this is avoidable per-call reflection overhead. See **IN-10**.

### 2. Mediator (`src/Elsa/Mediator`)

This is where the "shared engine" claim breaks down and where the worst correctness/perf issues live.

- `CommandHandlerInvokerMiddleware.cs:25-28` and `RequestHandlerInvokerMiddleware.cs:20-23` both call `serviceProvider.GetServices<ICommandHandler>()` / `GetServices<IRequestHandler>()` — the **non-generic marker** — then filter with `.Where(handlerType.IsInstanceOfType)`. This instantiates **every command/request handler registered anywhere in the application** on **every single dispatch**, which is precisely the anti-pattern the Events domain's own code comment (`EventHandlerInvokerMiddleware.cs:24-27`) warns against. See **IN-1** (High).
- No caching of `MethodInfo`/generic-type lookups at all in either invoker middleware (contrast with Events' `ConcurrentDictionary<Type,Type>` cache). Every command/request executes 2+ reflection lookups plus a reflection-based `Invoke` (`CommandHandlerInvokerMiddleware.cs:43-49`, `RequestHandlerInvokerMiddleware.cs:33-36`).
- Dead/commented-out code referencing an abandoned `ICommandStrategy` concept sits directly in the invoker (`CommandHandlerInvokerMiddleware.cs:38-41`) — a half-migrated design left in place. See **IN-13**.
- **Command and Request are mechanically identical** (`ICommand`/`ICommand<T>` vs `IRequest`/`IRequest<T>`, `ICommandHandler`/`ICommandHandler<,>` vs `IRequestHandler`/`IRequestHandler<,>`) — two fully parallel contract/pipeline/builder/sender/context/invoker/logging-middleware stacks for what is, in MediatR terms, a single `IRequest<TResponse>` concept. This roughly doubles the Mediator domain's type count for a distinction (`Send` vs. implicit query) that isn't enforced anywhere in the mechanism.
- The three pipeline builders (`CommandPipelineBuilder`, `RequestPipelineBuilder`, `EventPipelineBuilder`) are near-identical but **not DRY** — they are hand-copied and have diverged:
  - `CommandPipelineBuilder.cs:20-27` stores `ApplicationServices` via a `Properties["mediator.Services"]` round-trip; `EventPipelineBuilder.cs:17` stores it as a direct property. Same for `RequestPipelineBuilder.cs:20-27`.
  - `CommandPipelineBuilder` alone exposes `Use(index, ...)`, `Remove(...)`, `RemoveAt(...)`, `Clear()` (`CommandPipelineBuilder.cs:37-62`); `RequestPipelineBuilder`/`EventPipelineBuilder` don't.
  - `CommandPipeline` (`Commands/CommandPipeline.cs:16-31`) builds one `CommandPipelineBuilder` in its constructor and **reuses the same builder instance** across `Setup()` calls, so repeated `Setup()` calls **accumulate** middleware onto the existing list. `RequestPipeline`/`EventPipeline` (`Requests/RequestPipeline.cs:19-25`, `Events/Services/EventPipeline.cs:15-21`) construct a **brand-new builder** on every `Setup()` call, so `Setup()` **replaces** wholesale. Same method name, same conceptual role, opposite semantics.
  - `ICommandPipeline`/`IRequestPipeline` don't even expose `Setup`/`Pipeline` on the interface (implementation detail only); `IEventPipeline` does. See **IN-6/IN-7** (Medium).

### 3. Pipelines.Core (`src/Elsa/Pipelines/Core`)

This is genuinely small and does one thing well: `IMiddleware` marker + `MiddlewareExtensions.BuildMiddlewareDelegate` (reflection-based `Invoke`/`InvokeAsync` binding, `MiddlewareExtensions.cs:47-64`) + `HandlerRegistrationExtensions.AddHandlersFromAssembly` (assembly scan, `HandlerRegistrationExtensions.cs:13-40`). Both are legitimately reused by all three call sites (`Events/Core/Extensions/MiddlewareExtensions.cs:11-14`, `Mediator/Core/Extensions/MiddlewareExtensions.cs:12-22`). **This part of the "shared engine" claim is true.** What is *not* shared is the higher-level `PipelineBuilder`/`Pipeline` types (see §2) — those are copy-pasted per message kind rather than being, say, a generic `PipelineBuilder<TContext, TDelegate>`. Given C#'s lack of generic delegate covariance tricks this would need, a shared generic builder is achievable (a `Func<Delegate,Delegate>` composition core parameterized on the delegate type) but wasn't built — a missed DRY opportunity, not a structural impossibility.

### 4. Tasks (`src/Elsa/Tasks`)

Overall the best-engineered domain in scope: `TaskStateManager.Stop()` (`Services/TaskStateManager.cs:28-35`) carefully sequences cancellation → recurring-task stop → scheduled-execution dispose → background-task await → CTS dispose, with per-step `try/catch` around `ObjectDisposedException` for concurrent-shutdown races. `TopologicalTaskSorter` is a correct DFS-based Kahn/Tarjan-style sort with cycle detection (`Services/TopologicalTaskSorter.cs:58-94`).

Two real defects:
- **`IBackgroundTask.StopAsync`/`IBackgroundTaskStarter.StopAsync` is dead code.** It's declared (`Core/IBackgroundTask.cs:10`, `Core/IBackgroundTaskStarter.cs:6`) and implemented (`TaskExecutor.cs:20-23`), but grepping the whole scope shows **zero call sites** other than its own definition. `TaskStateManager.DisposeBackgroundRunningTasks` (`Services/TaskStateManager.cs:77-97`) only `Task.WhenAll`s the already-running execution tasks — it never calls `StopAsync` on the `IBackgroundTask` instances. Shutdown for background tasks is therefore 100% dependent on the task's own cooperative cancellation-token checking; any implementation that expects `StopAsync` to be its graceful-drain hook (as the interface's shape implies) will never be signalled. See **IN-5** (High).
- **`[SingleNodeTask]` can hang and then crash startup on secondary nodes.** `TaskExecutor.ExecuteInternalAsync` (`Services/TaskExecutor.cs:30-37`) calls `distributedLockProvider.AcquireLockAsync(...)`, which **throws `TimeoutException`** if the lock isn't acquired within the configured window (`Locking/Core/IDistributedLockProvider.cs:27-33`). The default timeout is **10 minutes** (`FileSystemLockingFeature.cs:23-25`). `RunStartupTasks` (`Services/TaskManager.cs:74-92`) has no per-task try/catch, so a secondary node running a `[SingleNodeTask]` startup task blocks for up to 10 minutes and then the `TimeoutException` propagates out of `StartExecutingRegisteredTasks` (caught only by the top-level `catch (Exception e)` at `TaskManager.cs:51-56`, which logs and **rethrows**) — aborting shell initialization on that node, rather than the "runs on one node, others skip" semantics the attribute's own doc comment implies (`Core/Attributes/SingleNodeTaskAttribute.cs:4-5`, Tasks `EXTENSION_POINTS.md:31`). See **IN-4** (High).

### 5. Caching, Serialization, Locking

- **Locking**: thin, correct adaptor around `Medallion.Threading.FileSystem` (`Locking/FileSystem/DistributedLockProviderAdaptor.cs`, `DistributedLockHandleAdaptor.cs`) — delegating stale-lock/cross-process correctness to a proven third-party library is the right call; no home-grown lock-file logic to audit. Good.
- **Caching**: `ICacheManager → IChangeTokenSignaler → IChangeTokenSignalInvoker` is a 3-contract stack for what is really 2 concerns. `ChangeTokenSignaler` (`Memory/Services/ChangeTokenSignaler.cs:7-19`) is a byte-for-byte pass-through of `IChangeTokenSignalInvoker` — identical two-method signature, zero added behavior — an overridable seam that exists only to exist. See **IN-9** (Low).
- **Serialization**: the `IJsonConverterSource` contribution flow (`Serialization/SystemText/Handlers/RegisterJsonConverters.cs`) is the **cleanest real-world example of the sanctioned contributor pattern in the whole review** — one small interface (`GetConverters()`), one owner-written aggregator, one registry, one startup task; a new contributor pays exactly 1 file + 1 registration line. See it praised in the verdict below.
  - But `JsonPayloadSerializer.GetOptions()` (`Serialization/SystemText/Services/JsonPayloadSerializer.cs:68-84`) **allocates and populates a brand-new `JsonSerializerOptions` on every single `Serialize`/`Deserialize` call**, looping the registry's converters into a fresh list each time. `System.Text.Json` caches `JsonTypeInfo`/reflection metadata *per `JsonSerializerOptions` instance*; rebuilding options every call means that cache is thrown away every call. For a type documented as serializing "execution log record payloads" (i.e., likely called once per activity/log entry during workflow execution), this is a genuine hot-path performance defect. See **IN-3** (High).
  - `PolymorphicObjectConverter.Read`/`Write` also call `options.Clone()` on every invocation (`PolymorphicObjectConverters/PolymorphicObjectConverter.cs:30,153`), compounding the above.

### 6. Primitives & Foundation

- **Primitives** is mostly a legitimate "no-dependency utility" layer (identity generators, `SemVer`, `Page`/`PageArgs`, `Entity`/`TenantEntity`, `Result`) — cohesive as a concept, but the `Extensions` folder is a classic grab-bag: `ObjectExtensions`, `CollectionExtensions`, `StringExtensions`, `StringArrayExtensions`, `TypeExtensions`, `QueryableExtensions`, `PropertyAccessorExtentions` (**typo in filename** — "Extentions", see `Primitives/Extensions/PropertyAccessorExtentions.cs`). `ObjectExtensions.ConvertIEnumerableToArray` (`Primitives/Extensions/ObjectExtensions.cs:17`) matches on the **literal string** `"AsyncIListEnumerableAdapter\`1"` — a magic-string coupling to an EF-Core/LINQ-internal type name inside what's meant to be a dependency-free primitives layer. See **IN-12**.
- **Foundation**, within the reviewed scope, is 100% Identity (`Foundation/Identity/{Abstractions,Api,AspNetCoreIdentity,Oidc,OpenIddict}`). Two sibling directories exist (`Foundation/Workflows`, `Foundation/Agent`) but contain **zero files** — either abandoned scaffolding or index drift versus the root `EXTENSION_POINTS.md`, which places "Agent" and "Workflow Agent" catalogs under `src/Elsa/Agent/*`, not `Foundation/*`. Within Identity itself, "contract bundling" files like `IamContracts.cs` (30 type declarations in 257 lines) and `AuthorizationContracts.cs` (320 lines) group many small interfaces/records per file — a defensible style choice for cohesion, not a defect, but worth flagging as a documented convention rather than an implicit one.

## Verdict: Is the contributor pattern over-complicated?

**Short answer: the *contributor-interface* half of the redesign is sound and worth its ceremony; the *parallel command/request mediator* half is where unjustified ceremony and real bugs concentrate. They shouldn't be judged as one thing.**

**Where it shines (contributor interfaces, `IEventHandler<T>` substrate):**
- The `IJsonConverterSource` flow (`Serialization/SystemText/Handlers/RegisterJsonConverters.cs`) is the pattern working as designed: the *ceremony* (event + aggregator + registry + startup task, ~4 types) is paid **once**, by the domain owner, and every subsequent contributor pays a **flat, small cost**: one interface implementation (`GetConverters()`) + one DI registration line. This is objectively less error-prone than Elsa 3's equivalent (`SerializationOptionsConfiguratorBase`, which already existed in Elsa 3 for this exact purpose — see `elsa-core/src/modules/Elsa.Workflows.Core/Activities/Flowchart/Serialization/FlowchartSerializationOptionConfigurator.cs`). So this specific pattern isn't new to Elsa 4 — Elsa 4 generalizes and names a convention Elsa 3 already used *inconsistently* for some seams while using raw notification broadcast for others.
- The naming vocabulary (Source/Contributor/PreProcessor/PostProcessor/Validator/Handler, root `EXTENSION_POINTS.md:24-32`) and the "exactly one aggregating handler per contribution flow" rule (§2.24.2) genuinely solves a real Elsa 3 problem: in Elsa 3, N features could each register their own `INotificationHandler<SomeEvent>` for the *same* conceptual contribution, with no visible, compile-time-discoverable "who can contribute to X" surface and no enforced single point of truth for how contributions combine (order, dedup, aggregation semantics were ad hoc per feature). The typed contributor interface (`IJsonConverterSource.GetConverters()`, pull-based) makes the contract's *shape* explicit and removes ordering ambiguity for read-back scenarios, which a shared generic `Handle(T, ct)` signature cannot.
- **DX cost for a contributor is genuinely low**: 1 file + 1 registration line, matching Elsa 3's equivalent effort. The claim that this pattern is "over-complicated" doesn't hold for the common case — the person adding a feature.

**Where it's bureaucracy / where the redesign didn't pay for itself:**
- The *plumbing* cost (what the domain owner pays once) is not small: to understand the Events substrate end-to-end requires learning ~26 types (`IEvent`, `IEventHandler`/`IEventHandler<T>`, `IEventPublisher`, `IEventContext`, `IEventStrategyContext`, `IEventPublishingStrategy` + 3 impls, `IEventChannel`, `IEventMiddleware`, `IEventPipeline`, `IEventPipelineBuilder`, `EventMiddlewareDelegate`, plus 6+ concrete classes). Elsa 3's equivalent (`INotification`, `INotificationHandler<T>`, `INotificationSender`, `NotificationPipeline`, 3 strategies) is comparably sized — so the Events substrate isn't meaningfully *heavier* than Elsa 3's notification stack, just reorganized and better commented.
- The **Mediator's** doubling of Command vs. Request (**IN-15**) is ceremony that doesn't earn its keep: it is two complete parallel stacks (contracts, handlers, contexts, pipelines, builders, senders, invoker middlewares, logging middlewares — roughly 30 types combined) for a distinction (fire-and-forget vs. response-returning) that MediatR and Elsa 3's own `IRequest`/`ICommand` split already modeled with **less** duplicated machinery by sharing pipeline infrastructure more aggressively. Elsa 4 had the opportunity to collapse this — or at minimum share one generic pipeline engine parameterized by context type — and didn't (**IN-6/IN-7**).
- The Mediator invoker middlewares reintroduce marker-resolution (**IN-1**), which is precisely the failure mode the Events documentation calls out — meaning **the redesign's own stated principle isn't uniformly applied even within the new infrastructure**, which is a stronger criticism than "the pattern is over-complicated": *the pattern is right, but only half-implemented consistently.*
- Caching's 3-layer stack (**IN-9**) is a small but clear example of "contract for the sake of a contract" — a pass-through interface with the exact same shape as the one below it, present purely so `Replace(...)` has a name to hang on, when one fewer contract would have been equally overridable.

**Simplification options (ranked by leverage):**
1. **Fix IN-1 first** (Mediator resolves closed generic directly, same as Events) — this is a one-line-per-middleware change with an immediate, measurable perf win and removes the biggest philosophical inconsistency in the review.
2. **Unify Command and Request** into a single `IRequest<TResponse>`-style hierarchy (optionally keep `ICommand` as a thin marker/alias for `IRequest<Unit>` for naming ergonomics) and **one** pipeline/builder/sender, collapsing ~30 types to ~15 without losing any capability. This is the single biggest ceremony reduction available.
3. **Extract one generic `PipelineBuilder<TContext, TDelegate>`** in `Pipelines.Core` that `Command`/`Request`/`Event` builders wrap, eliminating IN-6/IN-7's drift risk permanently instead of relying on developers to keep 3 copies in sync by hand.
4. **Merge `IChangeTokenSignaler` into `IChangeTokenSignalInvoker`** (or vice versa) — drop the pass-through layer.
5. Keep the contributor-interface convention as-is for genuine fan-in extension points (Serialization is the model to replicate) — this part does not need simplifying, and diluting it (e.g., going back to "just implement `IEventHandler<OnX>` yourself") would reintroduce the exact ordering/discoverability problems Elsa 3 had.

**Bottom line:** the contributor-interface pattern itself is a good, proportionate design decision, evidenced by its cheapest, cleanest instance (`IJsonConverterSource`). The complaint that should actually be raised isn't "contributor interfaces are over-engineered" — it's "the mediator/pipeline substrate underneath the contributor interfaces is under-shared and inconsistently disciplined," which is a narrower, more fixable problem.

3. Is the 10-minute default lock-acquisition timeout (IN-4) actually meant to gate `[SingleNodeTask]` semantics, or was `[SingleNodeTask]` designed assuming a `TryAcquireLock` (skip-if-unavailable) call that got swapped for `AcquireLockAsync` (block-then-throw) during implementation?
