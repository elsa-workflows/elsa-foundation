## Release ordering and evidence

1. Land and validate the upstream source work for extraction and host adoption, including the optional integration and Foundation readability consumer. Keep interim previews available for qualification; they do not satisfy stable release acceptance. Foundation's exact public-preview readability consumer proof qualifies the delivered upstream lease seam. Coordinating CShells Feature #145 remains open for final stable Foundation proof, but its closure is not a prerequisite for publishing the stable packages that proof must consume. Under [D18](../plans/modular-hosting-upstream/decisions.md), safe pruning is a separate later M3 outcome and does not block this extraction release/adoption sequence. Review the exact final source and resulting-main checks before each tag.
2. Prepare version metadata and release notes in reviewed organization branches where changes are needed. Tag exact validated commits, using the existing unprefixed `0.0.N` convention. Publishing a GitHub release triggers package publication; pushing a tag alone is insufficient for these workflows.
3. Release Nuplane `0.0.11` first from exact reviewed main through its existing `Publish packages` workflow. Verify the terminal workflow jobs, the expected eight-package family, package/source commit identity, dependencies and availability from a clean cache. Do not infer publication from the planned version or a successful prior qualification run.
4. In a reviewed CShells organization PR, update its three Nuplane preview dependency pins to stable Nuplane `0.0.11` and validate that dependency before the CShells release.
5. Release CShells `0.0.30` through its existing `Packages` workflow. Its publisher explicitly enumerates all ten packages, including `CShells.Nuplane`; verify the complete family, exact source identity and NuGet.org/Feedz availability. Do not claim symbol-feed publication from local `.snupkg` output alone.
6. After both stable families are available, reuse existing Foundation PR #2530 for stable package adoption. Change every CShells and Nuplane central pin together, add the optional integration package where adopted, remove superseded local glue and preserve host defaults and Elsa policy. The inspected pre-adoption baseline had seven CShells IDs at `0.0.30-preview.159` and five Nuplane IDs at `0.0.11-preview.94`. The isolated startup-preparation candidate pins eight CShells IDs, including `CShells.Nuplane`, at `.173` with Nuplane `.99`; it is not a main or stable-adoption update. Intended final versions remain CShells `0.0.30` and Nuplane `0.0.11`, subject to the release-time refresh above.
7. Follow [NuGet lock files](../reference/nuget-lock-files.md): restore the affected project graph to update every reached lock file, review dependency/content-hash changes, then deliberately regenerate and review the affected maps. Verify a clean-cache locked restore of the actual published packages and inspect package-source mapping: Foundation currently maps CShells to Feedz and Nuplane to NuGet.org/Feedz. Both release workflows publish to Feedz, so a feed migration is not implied.
8. Run the Foundation extraction/adoption gate through PR #2530: affected modularity, host/Workbench, cluster/EF, architecture, maps, package and relevant real-process E2E suites, including package change, overlapping generation drain, failure/recovery and preserved reload defaults. Review and merge the Foundation update and verify resulting-main checks. This is the scoped extraction/adoption acceptance that #2509 can record; it does not complete the whole #2500 goal.
9. Record exact release tags, source SHAs, workflow runs, feed/package identities, lock-file hashes and consumer evidence on #2500/#2509. The M3 safe-pruning outcome remains separately required under #108 before the full #2500 goal is complete; retain all of its existing safety gates.

No release is created by this plan. Production deployment and customer package-store mutation remain outside authorization. The M3 shared-root admission/deletion-safety gate remains required as a later separate outcome; this sequence does not bypass or weaken it.
