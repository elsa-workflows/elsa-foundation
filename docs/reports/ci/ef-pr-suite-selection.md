# Select EF container suites on pull requests

Issue: [#1993](https://github.com/elsa-workflows/elsa-foundation/issues/1993). The 18 EF matrix legs remain distinct tests. The fast `Build & test` lane excludes projects that reach Testcontainers, so removing the legs would remove PR coverage. Running all 18 for a documentation or narrow feature PR is unnecessary; the full matrix remains on every push to `main` and manual dispatch.

## Selection and failure boundary

The suite manifest is [`tools/ci/ef-suites.json`](../../../tools/ci/ef-suites.json). For a PR, the selector diffs the recorded base and head commits, treats renames as delete/add, maps source and test files to every containing solution project plus any static linked-source owners, and selects suites whose transitive `ProjectReference` closure reaches a changed project. It uses the validated [solution-filter graph](../../../tools/maps/Elsa.Maps.Generator/SolutionFilterGenerator.cs), so missing or unresolved project references cannot become a false no-impact result. The selector also checks that all Testcontainers solution roots are accounted for by the 18 matrix entries plus the separate Secrets host proof, and that all test projects are solution-listed. A newly added or newly container-dependent project missing from the manifest fails the selection gate instead of disappearing from coverage. With a valid suite inventory, an added/deleted project, unowned code file, shared EF infrastructure, build configuration, CI/selector change, or failed graph/diff calculation selects **all** existing suites. A malformed suite manifest or selector self-test fails the stable aggregate gate instead of reporting no impact. A docs-only diff selects **none** of the matrix legs.

The workflow retains `Build & test` and all other gates. `Select EF suites` publishes the mode and names in the run summary. Matrix legs run only for a nonempty selection; the stable `EF container suites` job passes only when selection succeeded, the always-run Secrets host proof passed, and every selected matrix leg succeeded (or when an explicit no-impact selection skipped the matrix). GitHub documents that [job-level `if` is evaluated before matrix expansion](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idif), which permits the empty selection. Main/manual runs must select the full manifest. A PR-level concurrency group cancels superseded heads; main/manual runs have unique groups and are never cancelled by a newer PR.

## Reading the checks

The separate suite rows identify a failing test family and keep its provider setup isolated. The stable `EF container suites` result answers the review question: did the selected container coverage pass? On a documentation-only PR, `Select EF suites` reports `none`, the 18-leg matrix is skipped, and the aggregate can pass after the always-run Secrets EF composition proof succeeds. This keeps useful test granularity without presenting every unrelated EF suite as queued work on every PR.

## Local comparison before live rollout

The selector contract tests cover documentation-only, Publishing, a shared dependency, indirect references, linked source files, unowned and new projects, shared build inputs, and selector/workflow changes. Replaying docs-only PR #2006's exact base/head returns `none` and zero matrix legs versus the observed 18. Replaying the Authoring proof PR #1992's base/head selects `cli-acceptance`, `publishing`, and `shared-persistence-fixture` rather than all 18; its changed Publishing test project is also consumed through Workbench/CLI test references. Those three suites sum to **11.04** median runner-minutes versus **37.52** for all 18, before the selector job and the separate Secrets host proof. This is a local impact estimate; the live docs-only comparison below measures the actual check count.

## Live rollout measurement

Before the selector, documentation-only [PR #2006](https://github.com/elsa-workflows/elsa-foundation/pull/2006) showed **29 check rows**, including **18 runnable named EF legs**. After rollout, documentation-only [PR #2008](https://github.com/elsa-workflows/elsa-foundation/pull/2008) at `6fa02c2104de68ce00712f9fb969d9696d5a8e82` showed **14 check rows** and **zero runnable named EF legs** in [CI run 36086515732](https://github.com/elsa-workflows/elsa-foundation/actions/runs/36086515732). The matrix appeared as one skipped placeholder; `Select EF suites`, the separate Secrets host proof, and the stable `EF container suites` aggregate all passed. This is 15 fewer check rows for that PR; it is not a wall-clock or total billing comparison. The first [main CI run after merge](https://github.com/elsa-workflows/elsa-foundation/actions/runs/36086425852) passed with all 18 named legs and the aggregate.
