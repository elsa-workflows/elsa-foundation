# Studio Preferences Minimal API canary — August 2026

## Recommendation

**Proceed** with the next bounded migrations in the First-party REST API Consolidation program. The Studio Preferences canary migrated its complete GET/PUT surface from FastEndpoints to an explicit module-owned Minimal API mapper with no unapproved HTTP or consumed OpenAPI differences. Minimal APIs and an unrelated FastEndpoints route operated in one host through the same Foundation Identity evaluator, and the production API assembly no longer references or registers FastEndpoints.

Proceed with two constraints:

1. Dynamically unloadable endpoint assemblies must not use typed Minimal API handler signatures that cause `RequestDelegateFactory` to retain collectible parameter types in process-wide caches. Use an explicit `RequestDelegate` boundary and explicit endpoint metadata until the framework behavior changes or a proven framework-neutral helper replaces the module-local pattern.
2. Each migration must capture its own before evidence. This canary proves the target architecture and the shared gates; it does not prove that every FastEndpoints feature uses only the same capabilities.

## Scope and implementation

`StudioPreferencesApiFeature` now implements CShells `IWebShellFeature` and delegates to `StudioPreferencesApi.MapStudioPreferencesApi(IEndpointRouteBuilder)`. The mapper owns exactly:

| Method | Route | Foundation policy |
|---|---|---|
| GET | `/_elsa/studio/preferences/{namespace}` | any of `*`, `studio.preferences.read` |
| PUT | `/_elsa/studio/preferences/{namespace}` | any of `*`, `studio.preferences.write` |

Both endpoints carry module ownership, Minimal API authoring, and permission-security metadata. The legacy endpoint classes, their two transition-exception records, and the production `Elsa.Api.FastEndpoints` reference were removed. FastEndpoints remains test-only for mixed-host evidence.

## Findings

### Feasibility

Minimal APIs can replace FastEndpoints for this production module without changing its route, wire, authorization, or consumed API-description contract. Explicit `IEndpointRouteBuilder` mapping fits the existing CShells feature lifecycle and does not require a new endpoint registry or Elsa-specific routing DSL.

Foundation authorization is already the correct common boundary. Both authoring models emitted the same encoded permission policy and reached the same dynamic policy provider, implication expansion, normalized-principal gate, wildcard handling, and resource evaluator.

### Compatibility costs discovered by the canary

The legacy OpenAPI surface described the route namespace through request schemas instead of path parameters, including a required GET request body. Because that description is externally observable, the canary preserves it with explicit metadata and an operation transformer. A future contract version should correct the description through a deliberate approved difference rather than silently changing generated clients during framework migration.

FastEndpoints' configured ProblemDetails representation was also observable. The Minimal implementation uses module-local result translation for the exact legacy status, title, type URI, error extension, and trace field. This is compatibility code, not a recommendation for a new shared endpoint framework.

### Collectibility trap

The first honest materialized-route test failed: typed handler signatures caused ASP.NET Core `RequestDelegateFactory` process-wide binding caches to retain collectible API types after route removal. Counting unmaterialized route registrations made the test green but did not model CShells publication and was rejected.

The production mapper now maps explicit `RequestDelegate` handlers, resolves services and route values from `HttpContext`, and publishes explicit binding/response metadata. Materialized routes then released cleanly in all repeated cycles while preserving HTTP and OpenAPI evidence. This is the canary's most important reusable finding for dynamically loaded Elsa modules.

## Remaining risks

- The collectible tests materialize routes and feature services but do not generate OpenAPI or execute JSON body binding inside the collectible context before unload. Those exercised-then-unload paths should become a follow-up gate before claiming that arbitrary dynamic endpoint modules are collectible after traffic and documentation generation.
- The in-memory preference store makes status, concurrency, and no-mutation behavior deterministic, but this canary does not add a persistence-provider integration matrix.
- Explicit metadata and compatibility translation make this mapper more verbose than a greenfield Minimal API. That cost is concentrated in the module and is driven primarily by legacy contract preservation.
- Framework constitution §2.24 remains provisional; this canary relies on accepted ADR 0068 and the existing CShells `IWebShellFeature` seam instead.

## Proposed follow-up

1. Continue with #1348 using the same before/after compatibility and Foundation authorization gates, inventorying the Secrets API's actual FastEndpoints capabilities first.
2. Add an exercised-then-unload compatibility case that performs one request and one OpenAPI generation inside a collectible context before route/service release.
3. Carry the explicit-`RequestDelegate` collectibility finding into #1349's migration playbook and architecture guard guidance.
4. Plan a versioned correction for the legacy Studio Preferences OpenAPI request-body/path-parameter description; do not mix it into this framework-neutral migration.
