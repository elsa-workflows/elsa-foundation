How the clean-slate Elsa kernel fits together

A walk through the new execution kernel, from the three layers down to the rows a commit writes. The diagrams with step buttons can be played through; every step is also written out beside them.

01

The kernel in one picture

The kernel is three layers and one storage contract. The actor runtime decides where things run. The durable layer makes every guarantee: nothing is lost, nothing applies twice, and a stale node can never write. The actor types on top do the actual work, and a workflow instance is one of them. Click a layer to see what it owns.

1 · Actor runtime

Owns
Placing actors on nodes, running each scope one pass at a time, wake-ups between nodes.
Not
Any guarantee about messages or state.
Swap
Built in: partitions. Integrators: Orleans, Proto.Actor, Akka.NET, Dapr actors.

2 · Durable actors

Owns
The durable inbox; a turn's new state and sent messages committed atomically; the fence against a stale owner; timers; background jobs; events; poison handling; the journal.
Not
Where an actor runs.
Swap
Never. Its storage can be swapped.

3 · Actor types

Owns
What an actor does with its messages. A workflow instance holds what all workflows share and runs an execution model for the rest.
Not
Persistence, placement.
Swap
Extended by adding actor types and execution models.

Persistence provider

Owns
Nine core guarantees: atomic commit, a fence inside it, conditional take, create-only inserts, an order key, reads in key order, reads by key, its own clock, failures told apart. The prototype's store also carries the node heartbeat, start subscriptions, held messages, delete and the projector's rows, each tested by the conformance suite.
Not
Any SQL in the kernel.
Swap
Any store that passes the conformance suite.
Why layer 2 is ours on any runtime. Orleans grain calls are at most once, a grain saves its state on its own, and saving state and sending a message are never one atomic act; when the network splits Orleans can briefly run two activations of one grain. Proto.Actor's messages are not durable. So the runtime only places and wakes; the guarantees come from layer 2 and its fence, which catches a second activation.

The idea in five sentences

  1. The durable layer knows nothing about workflows. It runs durable actors that own a piece of state and react to messages.
  2. An execution model turns an instance's state and incoming messages into new state and outgoing messages. It is the only extension point.
  3. Everything that crosses an instance boundary is a message: a start, a child finishing, a timer, an external event, a cancel, an alteration. No code reads another instance's state.
  4. Under the built-in runtime, actors are grouped into partitions. One node owns a partition at a time and is its only writer, so the hot path needs no reads, no per-instance lease and no read before a turn.
  5. A commit writes everything a turn changed in one transaction, and the owner batches the commits of many instances into one.
The inbox alone says what is owed. Anything the kernel still has to do for an instance after a commit (continue, start a background job, look for events) is a message written in that commit. A new owner needs nothing but the rows. The simulation forced this rule three times.
02

Words used here

Actor
Something with its own state that handles one message batch at a time. A workflow instance is one kind.
Turn
An instance's turn to run: it takes the messages in its inbox, runs as many activities as its persistence mode allows, changes its state and sends messages. Temporal calls this a workflow task. One turn is not one activity.
Pass
The runtime's call into a partition it hosts: it runs the turns that are due and commits them in batches. One pass holds many turns.
Partition
A fixed bucket of instances (64 on server databases, 1 on SQLite). Its owner is the only node that writes its instances.
Epoch
A counter on the partition row, raised every time a node takes the partition. Work started under an older epoch is thrown away.
Position
How many journal rows a partition has written (a turn at the Minimal history level writes none). The commit checks it, so two commits can never land at the same position.
Fence
The conditional update inside every commit: it lands only while the epoch and position are still the ones the owner expects.
Lease
How long the owner may hold the partition without writing (10 s). It decides who should write; the fence decides who can.
Message
A row in the inbox table: target, kind, payload, an order key seq, optionally a due time (a timer) and a start spec (create the target if missing).
Job
A background job: something slow an instance starts during a turn, whose result comes back later as a message while the instance keeps taking other messages.
Journal
One compact row per instance commit, written in the commit: the record of what happened. The viewer's tables are built from it.
Persistence mode
Where a workflow ends its turns: Ephemeral (only at a wait, if ever), Balanced (at each wait), Durable (after each activity). Chosen per workflow.
03

The seam between the runtime and the durable layer

Layer 2 hands the runtime a set of ownership scopes, one per partition, and the runtime decides which node hosts each one. The runtime runs a scope one pass at a time; a pass runs the turns that are due. Layer 2 does not trust it to be right: the fence catches a second activation on another node.

public interface IActorRuntime
{
    ScopeId ScopeOf(ActorId actor);                  // the actor's partition
    ValueTask StartAsync(IScopeHost host, CancellationToken ct);
    ValueTask WakeAsync(ActorId actor, CancellationToken ct);   // a hint: there is work
    ValueTask StopAsync(CancellationToken ct);
}

public interface IScopeHost                       // implemented by layer 2
{
    ValueTask<IScopeActivation?> ActivateAsync(ScopeId scope, CancellationToken ct);  // takes the fence, or declines
}

public interface IScopeActivation : IAsyncDisposable
{
    ValueTask WokenAsync(ActorId actor, CancellationToken ct);
    ValueTask<TimeSpan?> RunAsync(CancellationToken ct);        // one pass: turns until idle; when to call again
}

The prototype was split this way in round 4 stage A.

04

What is stored

Eight record kinds, shown as tables; a document store keeps the same records as documents. The instance row is the truth about the present, the journal the truth about the past. There is no outbox, dispatcher, scheduler queue, per-run lease, commit marker or timer table. Click a table.

partition

id, owner, epoch, lease_until, position

The fence. epoch changes only on a take; position counts journal rows. Times are in milliseconds; under the default fence lease_until is written from the owner's clock and compared with database time at a take.

node

id, seen_at

A heartbeat, so nodes can count each other and take a fair share of partitions. Liveness only, never correctness.

instance

id, partition, model, definition, status, sub_status, state, state_version, jobs, revision, parent, root, correlation, tenant, created, updated

state is opaque, owned by the model. jobs lists background jobs in flight. Lists and counts read this row directly.

message

seq, id, partition, target, kind, payload, headers, sender, reply_to, start, due, seen, trial, attempts, keep_until, done

The inbox. seq from the database gives the order; the unique id makes adding idempotent; a future due makes it a timer or a retry; start creates the target if missing.

subscription

key, instance, wait, partition, kind

Routes external events to waiting instances (kind wait) or to a definition that starts one (kind start).

event

key, id, payload, keep_until

A published event. By default it reaches only waits committed before it; a wait that asks for kept events also gets events published within their window before it.

journal

partition, position, instance, entries

One row per instance commit, written in that commit, according to the history level (Full by default). At Minimal no row is written.

projection

partition, position

How far the projector has got. Its own row, so the projector never touches the fence row and never slows a commit.

05

Life of a turn

Follow one message from the moment someone adds it until its effects are durable, handed on and visible in the viewer. Use the buttons or click a step below the diagram.

  1. Add a message.

    Anyone may insert one: the API, an event router, another partition's commit. The unique id makes it idempotent. A message from outside carries keep_until, so a retried command gets a duplicate-key answer instead of a second effect.

  2. Wake the owner.

    The adder signals the owner, in process or through a notifier between nodes. It is only a hint; the poll is the guarantee.

  3. Poll.

    A plain read: rows of the partition not seen at this epoch, not done, due within the horizon, in seq order. No locks and no watermark, so a row whose insert commits late is found next time.

  4. Mark it seen.

    A message that came by poll is not acted on until a fenced commit marks it seen = 8. If this node dies, the next owner knows exactly which messages it was holding. Messages sent inside a partition are written as seen and skip this.

  5. Run the turn.

    The execution model gets the state from memory and the inbox in order. It changes state, sends, subscribes, starts jobs, records journal entries and emits live output. Nothing is read from the database.

  6. Commit.

    The committer takes every finished turn of the partition: fence, instance rows, consumed messages deleted, sent messages inserted, journal rows. One transaction, 2 to 3 round trips on PostgreSQL, measured at 100 instances; rows per flush are capped (500 by default in the prototype); SQLite's calls grow with the rows.

  7. Hand over and release.

    Only after the commit lands: a message to an instance in the same partition goes over in memory, and a held HTTP response is released to the caller. A caller never sees a response for work that was then lost.

  8. Project.

    Later, the projector reads journal rows in position order per partition and writes the viewer's tables. The hot path never waits for it. The run view stays current by reading the journal tail past the projector (decided, not built); lists over projected rows lag it slightly.

06

The commit

The owner of partition p at epoch e, which believes the position is n, commits a batch of instance turns in one transaction, k of which write a journal row. Two ways to send it were built and measured; switch between them.

  1. Fence. UPDATE partition SET position = n + k, lease_until = … WHERE id = p AND epoch = e AND position = n. Also renews the lease, so a busy partition needs no heartbeat.
  2. Exactly one row changed? If not, roll back and reset. This check must come before COMMIT is sent.
  3. Insert or update the instance rows the batch changed, each update WHERE revision = r.
  4. Delete the consumed messages, or mark them done when they carry keep_until. Check the count.
  5. Mark seen = e on messages held in memory and not consumed.
  6. Insert the sent messages. Each id is derived from the sender and its revision, with a fixed-width ordinal, so a repeat is refused and order holds.
  7. Insert and delete subscriptions.
  8. Insert k journal rows at positions n + 1 … n + k.
  9. COMMIT.

Why not one round trip? A commit sent in the same packet as a fence that matched nothing would still land. The owner has to learn the fence held before it lets COMMIT go.

When a commit fails

What happenedWhat the owner does
Unknown outcome: the connection broke mid-commitReset: drop everything in memory for the partition and take it again. Recovery is the start-up path.
The fence matched nothingReset. Another node owns the partition now, or this node's memory is stale.
Deadlock victim, SQLITE_BUSY (transient)Retry the batch as it is.
Definite error: a value too long, a key violationNo reset. Commit the batch's instances one by one and park the one that fails (faulted, with the error). The rest go on.
07

Ownership and takeover

Leases decide who should write. The fence decides who can. Play through a takeover where the old owner was only paused, the case that breaks most designs.

  1. A takes the partition.

    The take succeeds only if the partition is free, its lease has expired, or A already owns it. Every take raises the epoch: now 7.

  2. A commits.

    The fence checks epoch 7 and position 40 and moves the position to 43. The same update renews the lease. An idle owner sends an empty fenced commit as its heartbeat.

  3. A stops.

    A long GC pause or a network split. A still believes it owns the partition and still holds instances in memory.

  4. The lease runs out.

    Nobody has written, so nothing is wrong yet. A wrong lease costs availability, never correctness.

  5. B takes the partition.

    Epoch 8, position 43. In the same transaction every message A had on trial gets one more attempt: that is how a message that kills its owner gets counted.

  6. B polls everything.

    Every row with seen < 8 comes back, so B finds all A was holding. B builds memory from rows alone, and hands nothing over in memory until a poll comes back short.

  7. A wakes and tries to commit.

    Its commit is fenced on epoch 7. It matches no row, so nothing lands. A resets and drops its memory. This is the Orleans two-activations case, caught.

  8. B carries on.

    B commits position 43 to 44. No two commits ever landed at the same position, and nothing prepared under epoch 7 got in.

  • Fair share. A node counts the others from the node heartbeats, holds its share of partitions and releases the surplus.
  • Reset is start-up. After any doubt the owner drops its memory and takes again. The take waits behind a commit still in flight, so it reads the true position.
  • Failover takes about one lease (10 s by default): the price of never having two writers.
08

Messages, timers and poison

The inbox is the outbox: a message to another instance is a row inserted in the sender's own transaction, and nothing is relayed afterwards.

Order

A target handles its messages in seq order. A sender's commits are serial, so messages from one sender to one target arrive in the order sent.

Once in state

A state change and the delete of the message that caused it are one transaction. A message changes state exactly once, though a turn's code may run more than once after a crash.

Outside commands

Carry keep_until. The consuming commit marks them done and a sweep deletes them later, so a client retrying a handled command gets a duplicate-key answer, not a second effect. Messages between instances need no window: a repeat cannot exist.

Timers

A message with a future due. The poll returns database time; the owner anchors it and schedules on a monotonic clock. Cancel a timer by deleting its message, whose id the sender knows.

Creating instances

A message may carry a start spec: if its target does not exist, the owner creates it on delivery. Starting a child, starting on an event and signal-with-start are all this one mechanism.

Placement

A start without a caller's key goes into a partition the starting node owns and runs there, with no hop. A keyed start hashes the key to a partition. A child goes into its parent's partition, so a call tree commits together.

Poison

A new owner puts its predecessor's held messages on trial, one at a time by default (an optional larger group halves with every attempt). If that owner is lost too, the next take adds one attempt to exactly the messages on trial, so a poison message ends up alone and a death stops counting against its neighbours. Past the threshold it is parked and its instance faulted, so a message that kills its process cannot walk the cluster.

Edge cases

A message to an instance that does not exist and carries no start spec is dropped and journalled. A message to a finished instance is consumed and dropped. A turn that throws parks its instance at once; retries are the model's business.

Execution models

A workflow instance runs an execution model. The model is a plug-in with one job: given the state and the inbox, produce new state and outgoing messages. Everything else is the kernel's.

A persistence mode is just where a turn ends

A turn commits at its end and only there. A model that wants a durable boundary ends the turn and sends itself a "continue" message, which the owner hands over in memory. That is all a persistence mode is. Here are ten activities with no wait, measured on PostgreSQL:

How the known models sit on the contract

Only Native is built, as a spike; the others are the planned fit.

Native (Elsa)

State is the live activity frames, variables and scheduled work. Slow activities are jobs. Each container brings its own semantics (below). Built as a spike; it passes its own simulation checks.

BPMN

Hosted on Bpmn.Semantics, a pure interpreter: definition, token state and one event in; next state and commands out. A turn feeds it the message; its commands become jobs, timers, subscriptions and sends. State is tokens and scopes. A task is a job, so an interrupting boundary event can cancel it. A call activity is a start. A message that arrives early waits in event.

ETL

State is stage cursors and references to data held elsewhere. Partitions of work are children spread over partitions. Backpressure is a credit protocol between instances.

Agents

State is the conversation checkpoint (a Microsoft Agent Framework thread). A tool call is a job; streamed output is emitted; another agent is another instance; a human approval is a subscription.

Standalone jobs

Elsa.Jobs rebuilt on the kernel: a job is an actor type next to the workflow instance, so a .NET app gets durable jobs without workflows. A workflow's job is the same thing, in the same commit, with no bridge between stores.

Durable entities

State is the entity's value; operations are messages with a reply-to. The reviewers' test of a fifth model: it fits with no change.

Replay-style authoring

Temporal and Durable Task style code, or Restate's journaled awaits, fit as models on the same contract. The kernel imposes neither.

Background jobs

Models compose through messages only. A parent of any model starts a child of any model and gets a message when it finishes. A cancel goes to the children the parent itself started, so admitting a child and cancelling the parent cannot race. The kernel owns suspend and resume, terminating a tree, tenant checks on sends and trace headers.

Events and correlation

An external event (an approval, a payment notice, a BPMN message) must reach every instance waiting for its key, even when the event and the wait are committed at nearly the same moment. Each side checks for the other after its own commit.

The alternative: correlation as an ordinary instance per key

Built as a 50-line model with no kernel change: subscribing and publishing are messages to the key's instance, which holds the waits and the kept events. It passed every run. It costs a hop, measured on PostgreSQL for one waiter, one event:

11

Synchronous HTTP

A workflow handles a request and writes the response itself. The response travels on the live Emit channel, not as a durable message: if it cannot reach the caller, the caller gets an error and the workflow is unaffected. Pick a case.

  1. The request arrives.

    Any node can take it. The route table is built when definitions are published, so finding the workflow reads nothing.

  2. It runs inline.

    The node places the new instance in a partition it owns and runs it in the request, with the request as Ambient. No hop.

  3. Respond and finish.

    The workflow writes the response and ends without waiting. In Ephemeral mode nothing is committed: zero database calls.

  1. The request arrives.

    Same as before: the route table is in memory.

  2. It runs inline.

    The instance is placed locally and runs in the request.

  3. The turn commits.

    The response is held until the commit of the turn that wrote it lands: 2 to 3 round trips of latency on PostgreSQL. A caller never sees a response for work that was then lost.

  4. The response is released.

    Writing the response does not end the workflow; the request returns and the workflow goes on. A route can opt out and respond before the commit.

  1. A resume arrives at node A.

    The workflow it resumes is waiting, and node B owns its partition.

  2. A adds a resume message.

    It carries a reply address, node A and the request's id, and A keeps the request open.

  3. B runs the turn.

    B finds the message by poll or wake hint, marks it seen and runs the turn.

  4. B commits.

    The turn that wrote the response commits, so the response may now be released.

  5. B replies to A.

    Over the runtime's transport between nodes, the same one wake-ups use. It is not durable. On one node this is all in process.

  6. A answers the request.

    One hop paid, because B owns the instance. Moving the instance to the receiving node is left out unless measurements show the hop matters.

  1. A resume arrives at node A.

    Node B owns the waiting workflow.

  2. A adds the resume message

    and holds the request open with a reply address.

  3. Node B dies.

    After its lease runs out another node takes the partition and resumes the workflow from the rows, as usual.

  4. The request ends with 503.

    By default, never a hang and never two responses. The workflow's later output is not sent to a caller that is gone. In the prototype an owner lost on another node is noticed only at the deadline (504): that signal is not built yet.

  • Waiting before responding (a background job, a short timer): the instance stays in memory on the receiving node and the request waits, up to the route's timeout.
  • Client disconnect and timeout end the observation. They do not cancel the workflow, unless the route maps them to a cancel message.
  • Streaming (chunked responses, server-sent events, an agent's tokens) uses the same channel. Large bodies stay out of state; the workflow holds a reference.

Three things vary independently, each behind its own seam. There is no fourth "runtime" plug-in: a deployment profile is a named preset of the last two. A workflow behaves the same under every profile, and synchronous HTTP works on all of them. Pick a profile.

14

How it is tested

The model is attacked by a deterministic simulation: several nodes against one store, one random action at a time (takes, polls, turns, commits, crashes, a paused owner that wakes with stale memory, commits whose answer is lost, retried commands, clocks that disagree). After every action it checks these invariants. A failing seed replays exactly.

1 · One writer

No two commits land at the same position; nothing prepared under an old epoch lands.

2 · Atomic turn

State, consumed and sent messages, subscriptions and journal row: all or none.

3 · No lost message

A committed message reaches a turn that consumes it while any node owns the partition.

4 · Once in state

A message changes state at most once, including a retried outside command.

5 · Timers

Never delivered early, never lost.

6 · Journal order

Rows present plus rows removed by deletes equal the position; the projector never passes an unwritten position.

7 · Takeover

After a take at e + 1 nothing from e commits, and the new owner sees all that did.

8 · Index matches state

An instance's subscriptions are exactly the waits in its committed state.

9 · Memory matches rows

What an owner holds equals the committed row plus its own uncommitted turn.

10 · Create once

Two messages that would create one instance create one, in any order, across takeovers.

11 · Order

One sender's messages to one target are handled in the order sent.

12 · Jobs

A job's result is applied once; a cancelled job's result never.

13 · Events meet

An event and a wait for its key, both committed in the window, meet exactly once.

14 · One bad instance

A failing instance is parked and its partition goes on; a message is parked for killing processes only after the threshold.

The simulation passes at 200,000 runs of 300 actions and 20,000 of 1,000, also with native instances in the mix; mutation checks break the kernel one rule at a time and each is caught, except two rules that another rule covers, which are caught when that rule is broken too; the store conformance suite (57 cases) runs on the in-memory store, SQLite, PostgreSQL, SQL Server, MySQL and MongoDB; a stress test with killed connections holds on all five engines and fails on every one with the fence broken on purpose. The figures and seeds are in the prototype's FINDINGS.md (sections 22 to 24); the engine findings, among them E9 (SQL Server deadlocks with the fence in the batch), in ENGINES.md.

Decided 12 November

Built in the prototype: the fence in the batch, the event tables and job poison counting. Partly: the wake signal (an in-process implementation, round 4). Not built yet: the Orleans adapter, short waits in memory, reply deadlines, the recreate rule, set-based projector rounds, parking a poisoned job, values by reference and the viewer's tail read.

  • Commit fence in the batch by default (2 round trips on PostgreSQL); fence first stays an option
  • A pluggable wake signal between nodes; polling remains the guarantee
  • Short timers and jobs of an Ephemeral instance stay in memory, up to the route timeout or a few seconds
  • Events: subscription and event tables are the one kernel mechanism
  • Reply addresses expire at the route's timeout, then the instance is unpinned
  • Recreate after delete: generated ids never return; caller keys may after keep_until
  • The projector batches each round into set-based writes, off the hot path
  • Jobs are counted for poison like messages
  • Large values stored by reference; segments only if measurements need them
  • The viewer reads projected rows plus the journal tail, so it is always current
  • Orleans hosts partitions as grains; no grain per instance, no sweep
  • 13 November: SQL Server defaults to the fence as its own statement (E9); the architecture section goes in docs/architecture/, published at the switch

To answer in the design proposal

  • Migrating running instances: a hook per container engine, and versioned activity state
  • Data lifecycle: retention, the right to erasure in an append-only journal, encryption at rest
  • Fairness, per-tenant quotas, admission control and bounded inboxes
  • Fan-out and fan-in over 100,000 children without flooding the parent
  • Job workers outside the process, in any language, with leases and heartbeats, built from Elsa.Jobs's worker protocol
  • Observability: trace context, stable metrics, operator actions on parked work
  • Write volume and bloat: bytes per commit and PostgreSQL dead rows, measured

Release 1 scope (decided 12 November)

In release 1

  • The kernel, the built-in runtime, the Embedded and Cluster profiles
  • The native model: structured containers and the Flowchart on the graph engine
  • Synchronous HTTP
  • PostgreSQL, SQL Server and SQLite, tuned; MySQL supported, not tuned
  • Studio on the new core
  • Basic trace context and metrics, retention and delete, admission control, simple instance migration
  • StateMachine, unless its design milestone is late; then 1.1
  • Agents as native activities, agent calls as background jobs

After release 1

  • BPMN, the Orleans adapter and ETL, each proven by a spike now
  • MongoDB in 1.1; proven in CI against a replica set from release 1
  • The aggregating fan-out pattern, with ETL; release 1 caps a parallel ForEach
  • The out-of-process job worker protocol (1.x); its contract designed now
  • A dedicated agent execution model

Standalone jobs (Elsa.Jobs on the kernel) are in neither column: their release is decided in the design proposal.
