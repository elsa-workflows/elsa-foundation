07

Ownership and takeover

Leases decide who should write. The fence decides who can. Play through a takeover where the old owner was only paused, the case that breaks most designs.

  1. A takes the partition.

    The take succeeds only if the partition is free, its lease has expired, or A already owns it. Every take raises the epoch: now 7.

  2. A commits.

    The fence checks epoch 7 and position 40 and moves the position to 43. The same update renews the lease. An idle owner sends an empty fenced commit as its heartbeat.

  3. A stops.

    A long GC pause or a network split. A still believes it owns the partition and still holds instances in memory.

  4. The lease runs out.

    Nobody has written, so nothing is wrong yet. A wrong lease costs availability, never correctness.

  5. B takes the partition.

    Epoch 8, position 43. In the same transaction every message A had on trial gets one more attempt: that is how a message that kills its owner gets counted.

  6. B polls everything.

    Every row with seen < 8 comes back, so B finds all A was holding. B builds memory from rows alone, and hands nothing over in memory until a poll comes back short.

  7. A wakes and tries to commit.

    Its commit is fenced on epoch 7. It matches no row, so nothing lands. A resets and drops its memory. This is the Orleans two-activations case, caught.

  8. B carries on.

    B commits position 43 to 44. No two commits ever landed at the same position, and nothing prepared under epoch 7 got in.

  • Fair share. A node counts the others from the node heartbeats, holds its share of partitions and releases the surplus.
  • Reset is start-up. After any doubt the owner drops its memory and takes again. The take waits behind a commit still in flight, so it reads the true position.
  • Failover takes about one lease (10 s by default): the price of never having two writers.
08

Messages, timers and poison

The inbox is the outbox: a message to another instance is a row inserted in the sender's own transaction, and nothing is relayed afterwards.

Order

A target handles its messages in seq order. A sender's commits are serial, so messages from one sender to one target arrive in the order sent.

Once in state

A state change and the delete of the message that caused it are one transaction. A message changes state exactly once, though a turn's code may run more than once after a crash.

Outside commands

Carry keep_until. The consuming commit marks them done and a sweep deletes them later, so a client retrying a handled command gets a duplicate-key answer, not a second effect. Messages between instances need no window: a repeat cannot exist.

Timers

A message with a future due. The poll returns database time; the owner anchors it and schedules on a monotonic clock. Cancel a timer by deleting its message, whose id the sender knows.

Creating instances

A message may carry a start spec: if its target does not exist, the owner creates it on delivery. Starting a child, starting on an event and signal-with-start are all this one mechanism.

Placement

A start without a caller's key goes into a partition the starting node owns and runs there, with no hop. A keyed start hashes the key to a partition. A child goes into its parent's partition, so a call tree commits together.

Poison

A new owner puts its predecessor's held messages on trial, one at a time by default (an optional larger group halves with every attempt). If that owner is lost too, the next take adds one attempt to exactly the messages on trial, so a poison message ends up alone and a death stops counting against its neighbours. Past the threshold it is parked and its instance faulted, so a message that kills its process cannot walk the cluster.

Edge cases

A message to an instance that does not exist and carries no start spec is dropped and journalled. A message to a finished instance is consumed and dropped. A turn that throws parks its instance at once; retries are the model's business.

A persistence mode is just where a turn ends

A turn commits at its end and only there. A model that wants a durable boundary ends the turn and sends itself a "continue" message, which the owner hands over in memory. That is all a persistence mode is. Here are ten activities with no wait, measured on PostgreSQL:

How the known models sit on the contract

Native (Elsa)

State is the live activity frames, variables and scheduled work. Slow activities are jobs. Each container brings its own semantics (below). Built as a spike; it passes its own simulation checks.

BPMN

Hosted on Bpmn.Semantics, a pure interpreter: definition, token state and one event in; next state and commands out. A turn feeds it the message; its commands become jobs, timers, subscriptions and sends. State is tokens and scopes. A task is a job, so an interrupting boundary event can cancel it. A call activity is a start. A message that arrives early waits in event.

ETL

State is stage cursors and references to data held elsewhere. Partitions of work are children spread over partitions. Backpressure is a credit protocol between instances.

Agents

State is the conversation checkpoint (a Microsoft Agent Framework thread). A tool call is a job; streamed output is emitted; another agent is another instance; a human approval is a subscription.

Standalone jobs

Elsa.Jobs rebuilt on the kernel: a job is an actor type next to the workflow instance, so a .NET app gets durable jobs without workflows. A workflow's job is the same thing, in the same commit, with no bridge between stores.

Durable entities

State is the entity's value; operations are messages with a reply-to. The reviewers' test of a fifth model: it fits with no change.

Replay-style authoring

Temporal and Durable Task style code, or Restate's journaled awaits, fit as models on the same contract. The kernel imposes neither.

Containers and their semantics

The native model is one activity tree. Each container brings its own semantics, runtime state and kind of diagram, and containers nest freely. The kernel sees none of this; it sees turns. Decided 12 November.

Models compose through messages only. A parent of any model starts a child of any model and gets a message when it finishes. A cancel goes to the children the parent itself started, so admitting a child and cancelling the parent cannot race. The kernel owns suspend and resume, terminating a tree, tenant checks on sends and trace headers.

Events and correlation

An external event (an approval, a payment notice, a BPMN message) must reach every instance waiting for its key, even when the event and the wait are committed at nearly the same moment. Each side checks for the other after its own commit.

11

Synchronous HTTP

A workflow handles a request and writes the response itself. The response travels on the live Emit channel, not as a durable message: if it cannot reach the caller, the caller gets an error and the workflow is unaffected. Pick a case.

  1. The request arrives.

    Any node can take it. The route table is built when definitions are published, so finding the workflow reads nothing.

  2. It runs inline.

    The node places the new instance in a partition it owns and runs it in the request, with the request as Ambient. No hop.

  3. Respond and finish.

    The workflow writes the response and ends without waiting. In Ephemeral mode nothing is committed: zero database calls.

  1. The request arrives.

    Same as before: the route table is in memory.

  2. It runs inline.

    The instance is placed locally and runs in the request.

  3. The turn commits.

    The response is held until the commit of the turn that wrote it lands: 2 to 3 round trips of latency. A caller never sees a response for work that was then lost.

  4. The response is released.

    Writing the response does not end the workflow; the request returns and the workflow goes on. A route can opt out and respond before the commit.

  1. A resume arrives at node A.

    The workflow it resumes is waiting, and node B owns its partition.

  2. A adds a resume message.

    It carries a reply address, node A and the request's id, and A keeps the request open.

  3. B runs the turn.

    B finds the message by poll or wake hint, marks it seen and runs the turn.

  4. B commits.

    The turn that wrote the response commits, so the response may now be released.

  5. B replies to A.

    Over the runtime's transport between nodes, the same one wake-ups use. It is not durable. On one node this is all in process.

  6. A answers the request.

    One hop paid, because B owns the instance. Moving the instance to the receiving node is left out unless measurements show the hop matters.

  1. A resume arrives at node A.

    Node B owns the waiting workflow.

  2. A adds the resume message

    and holds the request open with a reply address.

  3. Node B dies.

    After its lease runs out another node takes the partition and resumes the workflow from the rows, as usual.

  4. The request ends with 503.

    By default, never a hang and never two responses. The workflow's later output is not sent to a caller that is gone. In the prototype an owner lost on another node is noticed only at the deadline (504): that signal is not built yet.

  • Waiting before responding (a background job, a short timer): the instance stays in memory on the receiving node and the request waits, up to the route's timeout.
  • Client disconnect and timeout end the observation. They do not cancel the workflow, unless the route maps them to a cancel message.
  • Streaming (chunked responses, server-sent events, an agent's tokens) uses the same channel. Large bodies stay out of state; the workflow holds a reference.
