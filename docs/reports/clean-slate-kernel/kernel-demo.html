Elsa's new kernel

A new engine for running your business processes: it keeps going when a server fails, asks far less of the database, and can run many kinds of process.

Three parts, each with one job: where it runs · keeping it safe · your processes.

Correct

If a server dies, its workflows carry on from their last save on another server, and a server that is no longer the owner can never write.

one writer per partition, fenced in the database

Lean

One save carries many workflows, and a workflow kept in memory runs its next step without reading the database.

a turn reads nothing; one commit carries many instances

Open

Different kinds of workflow plug in: Elsa's own workflows, BPMN, and more.

execution models: native (Flowchart and StateMachine are its containers, each on its own engine), BPMN, …

Partition: a fixed group of actors, the things the kernel runs, such as running workflows; one server owns each group.
Turn: one burst of work by one actor, run in memory.
Commit: one save to the database, in one transaction.
Fence: a check inside every save that refuses a server which is no longer the owner.

04 · Persistence modes

You choose where a workflow saves

The same workflow three times, one instance per mode, stepping together. Each saved envelope is one commit.

Ephemeral writes nothing while it sends nothing to others and its waits are short enough to stay in memory: up to the request's timeout, else 5 s (the prototype's short wait, FINDINGS 25.6). A longer wait commits like Balanced. Round trips: the prototype's PostgreSQL counts with the fence in the batch.

05 · Database commands

How many database commands one workflow run costs

Same three workflows, same kind of count. In the default mode the new kernel issues far fewer commands for the straight run and the request, even adding the few it spends later writing history; for the fork and resume it is about level with Elsa 3 once its history is added — and every save is one atomic, fenced transaction.

What is counted: the run's own EF Core commands (reader, non-query, scalar) on SQLite (for Elsa 3, background queue polls excluded). Elsa 4: its runtime database context; Elsa 3: both of its contexts. Elsa 3 writes its history during the run, and it is counted: 25 of 29, 11 of 15 and 12 of 25 commands in the default mode; how much of Elsa 4's count is history is not broken out here; the kernel writes one journal row in the commit and expands it later, off the hot path, which is not counted. Kernel: the prototype's native model, not product code. Commands, not time.

06 · Safe, and next

A server that is no longer the owner cannot write

If a server pauses and another takes over its workflows, the database refuses the paused server's late save. Two servers never both write the same workflows.

Leases decide who should write. The fence decides who can.
