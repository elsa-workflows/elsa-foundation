## Lock order (criterion 5; slice 3, #4812)

`experiments/K1.LockOrder`: one owner holds partitions 1, 2 and 3. Commit X lists its fences 1, 2, 3 and commit Y lists
them 3, 2, 1, at the same picture. An outside transaction holds row 2 until both sessions wait, so each interleaving is
forced.

| Engine | Fence | Ascending (as built) | Batch order (`unordered=1`, the negative) |
|---|---|---|---|
| PostgreSQL 17 | batch | X landed, Y not landed, 0 deadlocks, 123 ms | deadlock (1), broken after about 1 s; the victim "not landed" (E1) |
| PostgreSQL 17 | checked | X landed, Y not landed, 0 deadlocks, 128 ms | deadlock (1); the victim Transient 40P01 |
| SQL Server 2022, RCSI | batch | X landed, Y not landed, 0 deadlocks, 179 ms | deadlock (1), broken after about 3 s; the victim Transient 1205 |
| SQL Server 2022, RCSI | checked | X landed, Y not landed, 0 deadlocks, 154 ms | deadlock (1); the victim Transient 1205 |
| MySQL 8.4, REPEATABLE READ | batch | X landed, Y not landed, 0 deadlocks, 121 ms | deadlock (1), broken at once; the victim "not landed" (E1) |
| MySQL 8.4, REPEATABLE READ | checked | X landed, Y not landed, 0 deadlocks, 102 ms | deadlock (1); the victim Transient 1213 |

In every run, the negatives included, one commit's three rows were written and the positions were 1 1 1. MongoDB has
no deadlock form: a second writer of a document fails at once with `WriteConflict` (slice 4). The in-memory store has
a lock-order conformance case. Provider qualification is K4.

## The decisive witness (criterion 2; slice 7b, #4820)

The setup: one owner holds {a, b, c}, and a flush with a turn, a Seen mark and a Trial mark in each of the three is
held. b moves to another owner, by lease expiry or by a cooperative release. The held flush then tries to land.

| Where | Outcome |
|---|---|
| Store conformance `OwnedSetChecks.Witness`, both variants: in-memory store | passed (7b, `9a4f915eb` and `8e0cbb7e1`) |
| EF on SQLite, `--checked-fence` and `--fence-in-batch` | passed in both modes (7b) |
| MongoDB 8.0 single-node replica set, both fence modes | passed in both modes (7b) |
| EF on PostgreSQL 17, SQL Server 2022 and MySQL 8.4, both fence modes | passed: the owned-set cases with both witness variants, 9 passed and 2 skipped (not applicable to EF) on each engine in each mode (slice 8) |
| `semantic-flaw FenceSubset "the K1 witness" "the held flush landed"` (in-memory, the mutation on) | 2 of 2 fail with that text, exit 0; the PR gate requires it |
| The kernel simulation: W1 with `FenceSubset` | caught at seed 23 |

In each passing run the flush is refused whole: no row, journal row, position or mark is written in any of the three.
The old owner retakes a and c at new epochs, and its retake of b is refused. The poll at the new epochs reads back
everything it had marked there, so no mark is stranded, and every journal starts at 1 with no hole. The simulation's
set worlds reach the witness on their own: in 10,000 seeds, 289,891 commits over several partitions landed fenced,
242 had part of their fences stale and 38 all of them, and each was refused.

## Costs (criterion 6; slice 8)

Measured in the integrated Worker (`EngineRun x setcost`, `x setidle`): 1,024 virtual partitions, four nodes of 256,
PostgreSQL 17.11 in Docker, round trips on the TCP stream, statements as Execute frames, the fence rows written, wall
time as the median of five. The full tables, SQLite, SQL Server, MySQL and 4,096 are in PARTITIONS.md, "K1 costs".

| Operation | Experiment (i) | Scattered: tcp / stmt / rows / ms | Contiguous: tcp / stmt / rows / ms |
|---|---|---|---|
| One set take of 256 | 2 / 1 / 256 | 2 / 1 / 256 / 3.4 | 2 / 1 / 256 / 1.2 |
| Start-up through the per-node host (256 activations) | | 512 / 256 / 256 / 195 | 512 / 256 / 256 / 83 |
| Beat of 256 | 1 / 1 / 256 | 2 / 2 / 256 / 3.6 | 2 / 2 / 256 / 1.4 |
| Takeover, one set take of a dead node's 256 | 2 / 1 / 256; 3.8 ms (median of 5 takes of 128 rows) | 3 / 2 / 256 / 2.6 | 3 / 2 / 256 / 1.8 |
| Takeover through the runtime (three survivors' rounds) | | 786 / 530 / 256 / 138 | 1,041 / 700 / 341 / 212 |
| Release of 128, one set release | 2 / 1 | 1 / 1 / 128 / 0.9 | 1 / 1 / 128 / 0.8 |
| Release of 128 through the host, one scope each | | 128 / 128 / 128 / 34 | 128 / 128 / 128 / 27 |
| Rebalance on join, 3 to 4 nodes | another workload: half a range (128) moved between two nodes, set release plus set take, 4 / 2 | 796 / 540 / 256 moved / 160 | 1,567 / 1,054 / 513 moved / 328 |
| Rebalance on leave: the stop, then the others' rounds | | 256 / 256 / 256 / 52, then 530 / 274 / 256 / 99 | 256 / 256 / 256 / 55, then 785 / 444 / 341 / 150 (341 moved: the leaver's 256 and 85 that `ContiguousOnlyBalancer` shifts) |
| 100-instance flush, new instances | 2 / 381 (k = 81) | the mark 2 / 3, the turns 2 / 5 (k = 74 to 91) | the same |
| The same 100 again | 2 / 281 | the mark 2 / 3, the turns 2 / 104 | the same |

What is above the experiment is explained in PARTITIONS.md: the beat and the set takeover add one statement and one
round trip (the lock order and the death count); the runtime moves partitions one row at a time (D1); and a polled
message is marked Seen in a commit of its own before its turn. SQL Server's commands match PostgreSQL's commands;
MySQL's set operations match, and its one-row paths send more commands (a read-back after each one-row take). No figure
showed a correctness defect.

- **The beat on PostgreSQL over 120 idle seconds (D3, observed):** 44.7 kB of WAL a second, 161 MB an hour (153.5 MiB), for an idle
  four-node cluster at 1,024; 96 % of it on the partition rows, 41 % of that lock records; 307 row updates a second,
  95 % HOT; autovacuum kept the table at 385 kB.
- **Orleans idle polls at 1,024, quiet machine (load 3.1 to 3.5):** 107 to 117 set polls a second per silo, against 1.0
  for the built-in loop (55 to 73 before the suites' set-poll fix below).
- **SQL Server** caches a new ad hoc plan of the set poll per take (20 takes: 1 plan before, 21 after).
- **The runtime suite's crash case at 4,096** (built-in runtime) took minutes before the kill, in the suite's own holder
  read, which was cubic in the count. Fixed in slice 8: the case takes 14 s at 1,024, 2,048 and 4,096, and its
  takeover 6.2 to 7.5 s, the lease.
- **Turn throughput across a large set:** the suites' store wrappers sent a set poll as one poll per partition, each a
  scan of the in-memory inbox. Fixed in slice 8 (the suites only): a burst of 4,096 tokens over 4,096 partitions went
  from 21.0 s to 0.92 s (one run each). The built-in suite at 4,096 went from 215 s (7b's PR body, [#4820](https://github.com/elsa-workflows/elsa-foundation/pull/4820)) to 50 s with the holder-read fix,
  and to 46 s with the set-poll forwarding as well.

## For decision (none blocks K1)

1. **Batched gain and give-up** in the built-in runtime: one set take and one set release per balancing round. It would
   cut a join at 1,024 from about 800 round trips to a few.
2. **The beat's WAL (D3):** a node-level beat, or a beat statement without its locking read.
3. **The silo-level poll for Orleans:** 107 to 117 set polls a second per idle silo at 1,024; a seam decision (one wake covers a node's set).
