# Consolidated Studio publisher cutover

This runbook describes a future, explicitly approved cutover from the standalone Studio repository to the consolidated Foundation repository. The consolidation change only stages the workflows and their gates. It does not change repository settings, secrets, feeds, images, or either live source publisher.

## Publisher ownership and identities

The root Foundation publisher remains `.github/workflows/packages.yml` (`Packages`). It owns the Foundation `Elsa.*` package plan, the `elsa-foundation-nuget-packages` artifact, and the `publish-state` branch. The root Docker Images workflow consumes that exact artifact from the `Packages` run. Keep this path and its state untouched during the Studio cutover.

The staged Studio replacement is `.github/workflows/studio-packages.yml`, named `Studio Packages (consolidated gated)`. It preserves the Studio artifact names `elsa-foundation-studio-nuget-packages` and `elsa-foundation-studio-npm-packages`, the existing Studio NuGet package identities, and these four npm identities in dependency order: `@elsa-workflows/studio-sdk`, `@elsa-workflows/studio-ui`, `@elsa-workflows/studio-code-editor`, and `@elsa-workflows/studio-workflows`. The NuGet artifact also contains a provenance manifest; package consumers must continue selecting `*.nupkg` rather than treating every artifact file as a package.

The Studio workflow has only `workflow_dispatch`. Its default target is `none`, which builds and uploads packages without publishing. A preview publish requires the repository variable `ELSA_STUDIO_CONSOLIDATED_PUBLISHING=true`, an explicit `feedz-preview` target, and a manual run from `main` or a reachable prerelease tag. A stable public release requires the same variable, an explicit `public-release` target, and a stable `v4.x.y` tag reachable from `main`. No push, branch, or GitHub Release event publishes automatically. The imported `Studio/.github/workflows/packages.yml` remains unchanged as provenance and is not an active root workflow.

Studio does not use the Foundation `publish-state` branch or the Foundation fingerprint calculator. Its current preview version form is `4.0.0-preview.N`; release versions come from Studio tags. Feedz is `https://f.feedz.io/elsa-workflows/elsa-4/nuget/index.json` for NuGet and `https://f.feedz.io/elsa-workflows/elsa-4/npm/` for npm; public destinations are NuGet.org and npmjs.org. Feedz npm publishes use dist-tag `preview`; stable npm releases use the registry's default `latest` tag. The legacy NuGet push commands retain `--skip-duplicate`, but that flag is not evidence that a version is new, complete, or monotonic.

The staged Studio image workflow is `.github/workflows/studio-docker.yml`, named `Studio Docker (consolidated gated)`. It accepts only a successful manual run of `Studio Packages (consolidated gated)`, downloads `elsa-foundation-studio-nuget-packages` from that exact run, and checks the manifest, commit, run, package versions, and repository before building. Its `publish` input defaults to `false`. A push additionally requires the repository variable to remain `true` and a Studio package run that completed its selected publication successfully. Main images keep `latest`, an explicitly floor-checked `4.0.0-preview.N`, and the short SHA tag. A prerelease tag adds only its exact version and short SHA, so it cannot move stable aliases. A stable tagged release keeps the version, major.minor, major, and short SHA tags. The existing image identity stays `elsaworkflows/elsa-studio`.

## Before changing publishers

1. Confirm the consolidation PR is reviewed and merged, Studio CI passes on the merge commit, and the root `Studio Packages (consolidated gated)` and `Studio Docker (consolidated gated)` workflows are present on `main`. Before any publisher opt-in, configure the `studio-publish` GitHub environment with required reviewers and deployment refs limited to `main`, `4.*` tags, and `v4.*` tags. Keep `ELSA_STUDIO_CONSOLIDATED_PUBLISHING` unset or `false` throughout this stage; the build-only Docker qualification uses a separate `studio-validation` environment.
2. Record the exact source Studio publisher workflows and their last successful run, commit, package versions, and image tags. Confirm no publish run is in progress or queued. This check must include the standalone Studio repository; imported files under `Studio/.github/` do not disable workflows in that separate repository.
3. Disable the standalone Studio `Packages` and `Docker Image` workflows before enabling any consolidated publisher. Wait for in-progress runs to finish or stop them through the repository’s normal release procedure, then verify that no old-source publisher remains eligible to write.
4. Run the new root Studio Packages workflow from `main` with target `none`. Review both preserved artifact names, every expected NuGet package ID/version, all four npm identities/versions, tarball verification, and the provenance manifest. This is a build-only rehearsal.
5. Before a Feedz preview, inspect the highest published preview version for every Studio NuGet package and each of the four npm packages. Choose a `preview_version` of the form `4.0.0-preview.N` whose numeric `N` is strictly greater than every existing floor. The root repository has a different Actions run-number sequence than the standalone Studio repository, so its run number is not evidence that the package version is monotonic. The workflow requires this explicit version on a main preview publish.
6. Before a public release, verify that the intended stable `4.x.y` or `v4.x.y` tag is reachable from `main`, that its exact version is above the published floor for all Studio packages, and that the same version is available for all four npm packages. Do not use `--skip-duplicate` or a failed/partial publish as a substitute for this comparison.
7. Before any prerelease image push, inspect Docker Hub’s existing Studio tags and verify the exact prerelease version will not collide with an already-published version. For a first image push from `main`, inspect Docker Hub’s current Studio preview tag floor and choose a strictly higher `preview_image_tag` in the form `4.0.0-preview.N`. Image and package workflow run numbers are separate counters. For a stable release image, pass the successful package run for the exact release tag; verify the four expected release aliases before publishing.
8. Only after the old source publisher is confirmed disabled and the build-only rehearsal and version-floor checks are reviewed, set `ELSA_STUDIO_CONSOLIDATED_PUBLISHING=true` in the root repository. Dispatch one Studio package publication at a time and verify NuGet plus npm feed state before dispatching the matching image workflow. The GitHub Release event itself remains non-publishing.

## Relocated Foundation inputs

Moving Foundation projects changes source fingerprints used by its existing package calculator. The first main dry-run may therefore report a broad affected set even though package identities and version policy are unchanged. Before any Foundation publish, inspect the exact `plan.json`, `computation.json`, package-version props, and affected project list against the `publish-state` record and current feed. Reconcile every package and version; do not bootstrap, force-advance, or treat the broad set as routine. This consolidation does not authorize a Foundation publisher or `publish-state` transition.

## Rollback

If a consolidated Studio publication behaves unexpectedly, first unset or set `ELSA_STUDIO_CONSOLIDATED_PUBLISHING=false` so the staged package and image publishers fail closed. Stop any queued consolidated dispatches, inspect the per-feed and Docker Hub state for partial writes, and reconcile the exact versions before retrying. Keep run logs, artifacts, and the package provenance manifest for diagnosis.

Re-enable the standalone Studio publisher only after the consolidated root publisher is confirmed stopped and the root opt-in is false. Never let both repositories publish the same Studio package identities concurrently. Leave the Foundation `Packages` workflow and its `publish-state` branch alone during a Studio rollback.
