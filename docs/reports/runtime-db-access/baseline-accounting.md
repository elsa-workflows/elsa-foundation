## Attribution protocol and limits

Use the current runtime tracing surface when the host listener is active; the tracer returns no span when no listener subscribes. `ActivitySourceWorkflowEngineTracer` emits drain, dispatch, activity-execution and checkpoint-commit spans. Existing tags include `elsa.workflow.execution_id`; dispatch/execution tags include `elsa.work_item.id` and `elsa.command.kind`; dispatch sets `elsa.handler.name`; checkpoint spans include `elsa.checkpoint.id`, `elsa.checkpoint.persistence_mode`, mandatory-boundary state and post-commit-intent count. Carry TraceId and SpanId/parentage from the incoming W3C request through EF event 20101 where the active logger/exporter supplies it. See [telemetry names/tags](../../../src/essentials/Workflows/Runtime/Diagnostics/WorkflowEngineTelemetry.cs#L21) and [span creation](../../../src/essentials/Workflows/Runtime/Diagnostics/ActivitySourceWorkflowEngineTracer.cs#L45).

For the REST census, EF event scope SpanId-to-ParentId edges were merged with exported engine-span parent edges per exact TraceId; each command was walked to the ASP.NET `RequestStarting` root and classified by its nearest engine-span ancestor. All 269 REST commands reached their matching request root, with zero scope-parent conflicts. A request-root/no-engine-span bucket is therefore causally inside the request but lacks an engine phase span. This ancestry still does not identify the exact repository method or provider call, nor an `ActivityExecutionId`/outbox-item join for arbitrary EF commands. Captured engine spans expose selected workflow execution, work-item, command-kind, handler, and checkpoint identity attributes; participant-name mapping is not present in the curated engine evidence. Keep the 16 companion commands after `RequestFinished` distinct from its 86 pre-response commands; timestamp or TraceId association alone does not prove settled work or outbox causality. See the [sanitized census](evidence/coalesced-rest-census-2026-10-06.json).

For EF `Microsoft.EntityFrameworkCore.Database.Command` event 20101, the census retains counts, TraceId, span ancestry, response boundary, table-token classification, and one leading SQL verb per command. It does not retain SQL text or parameters. The exact REST traces contain no `elsa_otel` diagnostic-table command. Group by request phase and source API/handler only where the source caller is known; keep inspection GETs, database initialization, unrelated pollers, and commands after transport completion separate. Exact source-method attribution remains **Pending**. The bounded raw-log filter also found structured EF transaction/savepoint messages: begin/began/commit/dispose templates and savepoint create/release templates are counted in the linked evidence. These logger observations do not give a SaveChanges-to-checkpoint mapping, statement count, round trips, or atomicity proof.

Keep these units separate in the ledger:

- EF event 20101 **command executions**;
- SQL statements parsed from command text, if separately counted;
- provider network round trips, only with provider-level evidence;
- EF transaction/savepoint lifecycle log events, as observed event groups;
- provider transaction count and atomicity, only with provider-level evidence;
- logical runtime checkpoints and immutable marker records;
- scheduler work items, claims, retries and acknowledgements;
- outbox items/intents and their delivery transitions.

They do not have a fixed one-to-one mapping. In particular, an EF command can carry multiple statements, batching can combine writes, and one checkpoint spans multiple participant operations. The checkpoint-store source has two `SaveChangesAsync` calls inside its new-commit transaction. The captured EF logs report transaction lifecycle events separately, but neither the source call count nor those lifecycle groups prove a SaveChanges-to-checkpoint mapping, statement count, provider round trips, or atomicity in the measured run.
