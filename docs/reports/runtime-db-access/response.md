# Response to the Elsa checkpoint latency findings

Prepared from the supplied report and a read-only source review. The measurements below are the report's measurements; I have not reproduced its workload. Source was checked against the reported commit `f97d7f614fd57115fd94916f13fa6c3e3ae7ef10` and local HEAD `6c3a9fe59f25c48cfef1e8fd8b8b742e674043ee`. The coalescing merger, activity invocation handler, and instance-detail projection discussed below are unchanged between those commits.

**Suggested response**

Thanks for separating the successful response path, faults, and background work. These findings give us a useful basis for investigating the runtime's database access.

My reading is that the main cost comes from how often the runtime persists and coordinates small execution steps. Four authored activities produce many more runtime transitions: scheduling, starting, claiming an attempt, invoking, completing, and propagating completion through the parent. Those transitions can each involve state, inspection, queue, outbox, and checkpoint-marker operations. Immediate persistence makes that amplification especially visible.

That explains the shape of the cost, but it does not establish that 533 operations is an acceptable budget. Coalescing already removes a large part of it. More importantly, the source contains an avoidable read-amplification pattern that is a strong candidate for the 81 durable-value reads under Coalesced mode. I would investigate that first, then assess the remaining queue, state, and checkpoint costs with the same workload.

I would treat 30 ms as a target to evaluate after those changes, rather than promise it from the existing measurements. We should preserve the crash recovery, ownership, and external-effect boundaries while reducing the database work needed to implement them.

**What the database work represents**

The report's component breakdown describes three related costs:

- Execution data: workflow/activity state, inputs and outputs, variable frames, and inspection evidence.
- Durable progression: queue admission, FIFO claiming, consumed-item deletion, outbox continuation, and checkpoint commit proof.
- Execution authority: liveness, ownership fences, and executable coordination.

A checkpoint is an atomic group of operations, not a single row write. The EF adapter checks whether its immutable commit marker already exists, stages the participating changes in a transaction, saves the participants, and writes the marker before committing. Twenty-four checkpoints therefore plausibly explain the reported 24 marker reads and 24 marker inserts. They also multiply the other participant operations. [Checkpoint adapter at the measured commit](https://github.com/elsa-workflows/elsa-foundation/blob/f97d7f614fd57115fd94916f13fa6c3e3ae7ef10/src/essentials/Workflows/Runtime/Persistence/EntityFrameworkCore/Stores/EfRuntimeCheckpointCommitStore.cs#L64).

Coalescing also reduces queue and outbox work: intermediate work can execute through the session's memory overlay, and the flush preserves remaining continuation work rather than durably recording continuation already consumed within the segment. Its benefit is broader than fewer marker inserts. [Checkpoint fold](https://github.com/elsa-workflows/elsa-foundation/blob/f97d7f614fd57115fd94916f13fa6c3e3ae7ef10/src/essentials/Workflows/Runtime/Services/Coalescing/RuntimeCheckpointFold.cs#L14).

One measurement distinction matters: an EF `Executed DbCommand` log entry counts a command execution. A command may contain multiple SQL statements, and EF can batch statements into fewer round trips. Unless the SQL text was also parsed, I would label these counts **database command executions** and separately count statements, round trips, transactions, and durable checkpoint commits. The reported reduction remains meaningful. [EF batching documentation](https://learn.microsoft.com/en-us/ef/core/performance/efficient-updating).

**Responses to the open questions**

1. **Is 533 the intended Immediate cost?** It is consistent with the current architecture's amplification, but the exact count is workload-specific and has not been independently reproduced here. The 24 checkpoints and 23 work items remain observed counts; they are not a general one-to-one invariant. The W9 report's 3→1 result is not a comparable budget: it used an in-memory substrate, and the reproducer at the measured commit uses a single `Finish` intrinsic rather than a CLR HTTP workflow. Its assertions enforce fewer commits and exactly one coalesced commit, not an Immediate count of three. [W9 reproducer](https://github.com/elsa-workflows/elsa-foundation/blob/f97d7f614fd57115fd94916f13fa6c3e3ae7ef10/tests/essentials/Workflows/Runtime/Tests/RuntimeCheckpointCoalescingTests.cs#L396), [intrinsic workload](https://github.com/elsa-workflows/elsa-foundation/blob/f97d7f614fd57115fd94916f13fa6c3e3ae7ef10/tests/essentials/Workflows/Runtime/Tests/RuntimeCheckpointCoalescingTests.cs#L1114).

2. **Why 81 durable-value reads?** `FindAsync` misses are possible, but the stronger source finding is in `ListPageAsync`. The shared coalesced page merger calls the inner store with a page size of **one**, repeatedly. It can re-read an unconsumed candidate while emitting earlier overlay values. When the inner store returns an empty page, that exhaustion is not propagated to the caller's cursor, so emitting buffered values can repeat the same empty query. Activity invocation loads the full durable-value set through this path; parent-completion paths can load it again. These are confirmed code patterns, but attributing the exact 81 requires the SQL and caller trace. [Merger](https://github.com/elsa-workflows/elsa-foundation/blob/f97d7f614fd57115fd94916f13fa6c3e3ae7ef10/src/essentials/Workflows/Runtime/Services/Coalescing/CoalescingRuntimeStateStores.cs#L177), [invocation traversal](https://github.com/elsa-workflows/elsa-foundation/blob/f97d7f614fd57115fd94916f13fa6c3e3ae7ef10/src/essentials/Activities/Runtime/Services/WorkflowInvokeActivitySchedulerWorkHandler.cs#L125). This merger also serves activity-state pages.

3. **Why several scheduler reads per item?** The source has an enqueue idempotency lookup, a FIFO lookup to claim work, and another identity/ownership check before the checkpoint transaction consumes that work. There are also empty-queue probes and possible retries. These explain why several reads per item are plausible; they do not prove the exact 85. Some of these reads enforce different guarantees and cannot simply be deleted. [Enqueue and claim](https://github.com/elsa-workflows/elsa-foundation/blob/f97d7f614fd57115fd94916f13fa6c3e3ae7ef10/src/essentials/Workflows/Runtime/Persistence/EntityFrameworkCore/Stores/EfSchedulerWorkQueueStore.cs#L29), [atomic consumption](https://github.com/elsa-workflows/elsa-foundation/blob/f97d7f614fd57115fd94916f13fa6c3e3ae7ef10/src/essentials/Workflows/Runtime/Persistence/EntityFrameworkCore/Stores/EfRuntimeCheckpointParticipantStaging.cs#L346).

4. **Can inspection be coarsened per workflow?** Yes, via authored checkpoint cadence when the host has coalescing enabled. The authored setting is compiled into the pinned executable, and the effective cadence is stamped per run. An authored Coalesced workflow on a host without coalescing machinery runs Immediate. This folds inspection projections at durable boundaries; it does not disable inspection capture. The instance-detail read model exposes `checkpointCadence`, `maxSegmentCheckpoints`, and `inspectionGranularity`; the documented endpoint is `GET /runtime/workflows/instances/{workflowExecutionId}`, subject to the host's API prefix and authorization. [Resolver](https://github.com/elsa-workflows/elsa-foundation/blob/f97d7f614fd57115fd94916f13fa6c3e3ae7ef10/src/essentials/Workflows/Runtime/Services/Checkpoints/RuntimeCheckpointCadenceResolver.cs#L27), [detail projection](https://github.com/elsa-workflows/elsa-foundation/blob/f97d7f614fd57115fd94916f13fa6c3e3ae7ef10/src/essentials/Workflows/Runtime/Api/Handlers/WorkflowInstanceDetailsService.cs#L58). No live API call was made in this review.

5. **Should the transform declare ReplaySafe?** If the whole activity is safe to re-execute from persisted inputs, yes. That includes its script, dependencies, and any I/O or observable effects. The profile lets its attempt-claim checkpoint defer under Coalesced mode. The declaration becomes part of the pinned contract at publication, so the workflow needs to be republished. One fewer forced flush is plausible, not yet a measured result. Also audit first-party activities: `WriteHttpResponse` constructs a response instruction that the transport delivers after the drain, but it has no explicit ReplaySafe annotation in this source. That is worth reviewing rather than assuming every existing External classification is necessary. [Profile contract](https://github.com/elsa-workflows/elsa-foundation/blob/f97d7f614fd57115fd94916f13fa6c3e3ae7ef10/src/essentials/Activities/Runtime/Core/Attributes/ActivitySideEffectProfileAttribute.cs#L5), [policy](https://github.com/elsa-workflows/elsa-foundation/blob/f97d7f614fd57115fd94916f13fa6c3e3ae7ef10/src/essentials/Workflows/Runtime/Services/Coalescing/CoalescingRuntimeCheckpointPersistencePolicy.cs#L57), [response activity](https://github.com/elsa-workflows/elsa-foundation/blob/f97d7f614fd57115fd94916f13fa6c3e3ae7ef10/src/essentials/Activities/Http/Activities/WriteHttpResponse.cs#L8).

6. **Is 30 ms realistic?** The evidence does not establish that yet. The best supplied measurement is 71 ms. Avoidable reads make further improvement plausible, but the observed 0.3 ms per operation is an aggregate ratio that includes other work, not a constant we can multiply into a latency promise. After reducing reads, profile the transform, materialization, serialization, and remaining persistence. The health endpoint is a useful transport baseline, not an equivalent durable workload.

7. **Are untraced background statements request follow-up?** Possibly. Missing request trace context does not establish causality either way. Correlate workflow execution, work item, outbox item, and checkpoint IDs across foreground and background scopes, and measure until the instance's follow-up work settles. Response latency and total database work per completed instance are separate metrics. Keep the unexplained HTTP 202 as a separate correctness investigation: the middleware falls back to 202 when no response has been written or committed instruction delivered after dispatch. That identifies the branch, not why this valid request took it. [HTTP response delivery and fallback](https://github.com/elsa-workflows/elsa-foundation/blob/f97d7f614fd57115fd94916f13fa6c3e3ae7ef10/src/essentials/Activities/Http/Middleware/HttpEndpointMiddleware.cs#L302).

**Proposed order of work**

1. **Make the workload reproducible and reconcile attribution.** Obtain the workflow/export, transform code, shell composition, and raw traces. Retain the pinned-image baseline, then repeat on a current build: ownership-heartbeat isolation and outbox completion fixes landed after the measured commit. Read back cadence and published side-effect profiles. Group commands by operation and caller, including page size, repeated identities, checkpoint name/flush reason, queue claim, and outbox delivery. Resolve the unexpected 202 from its instance and incident records. Collect diagnostic traces separately from low-logging timing runs.

2. **Fix coalesced pagination first.** Read bounded batches, retain the current persisted candidate while overlay values are emitted, and propagate exhausted-cursor state. Preserve ordering, overlay replacement/deletion, and continuation semantics. Verify overlay-only pages against an empty database, mixed pages, suppressed persisted rows, page boundaries, and multiple pages. Assert store-call counts scale with fetched pages rather than emitted values. This is the clearest source-supported change and benefits both durable-value and activity-state reads.

3. **Use cadence and replay classification deliberately.** For this workload, validate Coalesced mode, declare the transform ReplaySafe if justified, republish, and audit safe first-party computations. Keep normal SQL logging at Warning for timing runs. Verify crash replay, terminal persistence, bookmark boundaries, and unchanged response/output behavior. Do not remove a mandatory boundary merely to lower a number.

4. **Reduce remaining repeated access based on the new trace.** Consider a drain-scoped durable baseline cache, including misses, merged with staged updates and invalidated at flush. Review repeated full-set value materialization. Then assess checkpoint participant pre-reads and queue/outbox operations for batching or conditional provider operations that preserve concurrency, corruption detection, fencing, and atomicity. Avoid broad caching across executions or owners. Inspection already has a scoped durable-baseline memo in coalesced mode; inspect its remaining writes before introducing another cache.

5. **Evaluate the resulting cost.** Compare Immediate, Coalesced, and optimized Coalesced using the same successful workflow, payload, and environment. Report command executions, actual SQL statements, checkpoints, response latency, and total settled-instance database work. Include representative concurrency and a longer workflow so gains are not confined to four activities. Set a concrete latency target after that evidence; retain focused correctness and query-count regression coverage.

I would prioritize step 2 over index tuning, durability changes, or removing analytics. The report demonstrates a large cadence effect, a smaller logging effect, and no demonstrated improvement from `synchronous_commit=off`. It does not prove storage or analytics costs are zero, but neither currently has comparable evidence as the main lever.
