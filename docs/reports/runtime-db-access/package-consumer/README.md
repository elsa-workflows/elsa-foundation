## Apply the supported composition

1. Select the pinned Linux/amd64 Foundation Host image and obtain the exact packages listed in the artifact manifest from Elsa 4 Feedz and NuGet. Verify every archive against its recorded SHA-256 before loading it.
2. Mount the Elsa and NuGet local-feed directories read-only at `/app/package-feed/elsa-4` and `/app/package-feed/nuget.org`, the external lock at `/app/.nuplane/nuplane.lock.json`, and the included appsettings and shell configuration at `/app/appsettings.json` and `/app/shells.json`. Provide writable Nuplane state at `/app/.nuplane` and writable ancillary SQLite state at `/data`.
3. Extract the two DLL members named in the curated scan manifest into a read-only `/app/curated-clr-scan` mount. Configure `ConnectionStrings__ElsaRuntime2412` for the owned PostgreSQL database; use separate SQLite state for the ancillary connections. Set both .NET environment variables to `Development` for this fixture composition.
4. Publish and execute the [primary HttpEndpoint fixture](../../../../e2e-tests/http/Capture-RuntimeDbPaging2392Reference.ps1) and [valid REST companion](../../../../e2e-tests/http/Capture-RuntimeDbRest2386Control.ps1) from fixture commit `b9f854cb493c2945c14790bab75c991f46f9307a`. The preserved fixture adapter changes only the authentication helper health probe from `/` to the Foundation Host endpoint `/health/live`.
5. Require the expected HTTP response/output, Completed state and zero incidents for both exact execution IDs. Verify those records in PostgreSQL, then compare the active Nuplane package identities with the external lock. Host readiness and a correct response alone do not prove the intended persistence provider.

These are the composition and acceptance steps, not a replacement for the retained complete fixture runner. Preserve each run and its owned databases. The [cadence guide](../../../runtime-durable-resumption.md) covers choosing and reading back Immediate or Coalesced; this package verification used Immediate and changes no default.

## Verified package-consumer result

[Sanitized evidence](evidence/foundation-host-v9-package-consumer.json) records the v9 package-consumer run: 199 active package identities matched the external lock with zero Nuplane failures; the required CLR/intrinsic catalog passed; primary HTTP and valid REST passed; and PostgreSQL read-only readback found one `Completed` persisted row with zero incidents for each unique actual fixture execution ID. A separate root PostgreSQL-only posthoc query corroborated the stored/payload identities while the host stayed stopped. All three owned containers are stopped and their data volumes retained. This accepts the package-consumer outcome; [final joined accounting and program acceptance](../delivery-response.md) remain open.

Earlier attempts remain retained evidence: Production correctly refused the Development seed; the Generate path did not write its lock; the first external-lock run lacked the Sequence descriptor; and v7 passed the fixtures but persisted to SQLite because the named-resource configuration did not enroll those Foundation Host features. V9 uses the explicit CLR scan and four direct provider bindings. These configuration corrections do not repair the upstream lock writer or claim a runtime query reduction.

The external lock is operator-prepared because [Nuplane lock-writer issue #111](https://github.com/valence-works/nuplane/issues/111) remains open. Archive SHA-256 is checked outside Nuplane; this evidence does not claim Nuplane package-byte enforcement. The root lock has 230 rows and 184 direct roots; the pinned image's active closure has 199 packages (109 `elsa-4`, 90 `nuget.org`), with 17 root-lock/image version differences (12 active and 5 not active).

The evidence JSON is a sanitized projection, not a source config, executable sample, or raw receipt. It omits raw fixture IDs, generated env values, response bodies, cookies, SQL, and logs. Hashes below apply to the exact files copied into this folder, not to redacted examples.
