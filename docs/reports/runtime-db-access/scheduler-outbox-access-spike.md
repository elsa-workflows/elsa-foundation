# Scheduler and outbox access spike

Program [#2382](https://github.com/elsa-workflows/elsa-foundation/issues/2382), issue [#2407](https://github.com/elsa-workflows/elsa-foundation/issues/2407), 8 October 2026. Source under review: `9a472affde60978cb15743fbc0e5ce22ee0581a9`.

## Decision

No production change is selected. The only bounded trial, removing the enqueue identity pre-read, trades one command saved for a new identity against one extra command and a changed `SaveChanges` boundary on a duplicate. It keeps the winner reload and corruption check, but fails the existing-key/shared-context guard. A `ChangeTracker.HasChanges` fallback to read-first is a possible design, not a tested result; it would not preserve the no-`SaveChanges` boundary for a clean-context duplicate. Current post-M2 queue/outbox volume does not establish that a guarded variant is worthwhile.

This is a scoped no-change disposition for #2407, not a claim that every access is optimal. Historical empty polls remain recovery/liveness work without a demonstrated target-execution owner. No poll, fence, partition check, idempotency behavior, corruption detection, or retry path is selected for removal.

## Bounded SQLite trial

A temporary command interceptor in the existing `EfSchedulerWorkQueueStoreTests` SQLite shared-memory fixture counted EF Reader/NonQuery attempts during only each enqueue call. It recorded sanitized SQL verbs and marked failed commands; setup and readback assertions were outside each window. The trial removed only the four-line identity pre-read at queue-store lines 47–50. The unique-conflict catch, attempted-entity detach, winner reload, `ReadChecked`, cancellation handling and remaining assertions stayed in place.

| Source/run | New identity | Duplicate replay with changed payload in a fresh context | Focused store class |
|---|---|---|---:|
| Baseline | `SELECT`, `INSERT` (2 attempts) | `SELECT` (1) | 13 passed, 0 failed |
| Naive insert-first | `INSERT` (1) | `INSERT[failed]`, `SELECT` winner (2) | 12 passed, 1 failed |
| Restored | `SELECT`, `INSERT` (2) | `SELECT` (1) | 13 passed, 0 failed |

The two-call pair totals three attempts both before and during the trial. The duplicate returned the original sequence across a fresh context. The temporary probe also added an enqueue-replay corruption assertion to the existing `Projection_drift_fails_closed_on_visible_row` case after corrupting `WorkOrderKey`; the committed test itself covers `ListAsync`. The added enqueue assertion passed on baseline and candidate, and the candidate still failed closed through `ReadChecked`. These fixture results describe SQLite EF command attempts, not physical wire round trips or elapsed time.

The one candidate failure was `Duplicate_enqueue_does_not_flush_pending_sibling_or_invoke_save_interceptor`. With a pending sibling scheduler-state entity and an armed `SaveChangesInterceptor`, replay threw `DbUpdateException: Injected queue save failure` from candidate `SaveChangesAsync`. This precisely demonstrates that the duplicate now crosses the shared `SaveChanges`/interceptor boundary. The injected exception occurs before SQL, so this run does **not** show that the sibling reached the database. Because the enqueue call threw, the test's following returned-winner, interceptor-count-zero, sibling-still-Added, separate-context sibling-absence and persisted-winner assertions did not run. The baseline guard passed. The probe-added enqueue replay corruption assertion passed on baseline and trial, and the original `ListAsync` corruption assertion remained in the test.

A fallback such as retaining the read-first branch when the context already has pending changes was not implemented or tested. It might protect the demonstrated pending-sibling case, but a clean-context duplicate would still invoke `SaveChanges`, and contexts with pending changes would retain the pre-read cost. No current workload distribution establishes the tradeoff. Ambient-transaction/savepoint behavior and PostgreSQL behavior were not trialed. No native-provider, RTT, latency or post-M2 net-gain claim is made.
