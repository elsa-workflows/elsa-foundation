# Remaining command families and their disposition

The accepted extended captures account for **1,647 EF command executions**: 420 Coalesced and 1,227 Immediate, each with one successful HttpEndpoint request, one valid REST companion and separately counted resumption sweeps. **931 commands join an observed repository-method span; 716 have no method ancestor.** This offline review reconciles those 716 commands without inventing caller, row, outcome or savings attribution. It uses the [accepted checkpoint/queue packets](checkpoint-queue-accounting.md) and publishes the full [45-group matrix](evidence/residual-disposition-2026-10-07.json).

Every residual group retains the complete table-token array, observed trace/boundary, provider, context and verb. Each command belongs to one group. None of these residual groups contains multiple tables. Hierarchy commands are not absent from the capture; there are simply no hierarchy commands left in this no-method-ancestor subset. Transaction/SaveChanges boundaries, combined checkpoint flushes and exact typed identities stay in the original packets.

## Root decisions and handoffs

The program permits causal accounting **or explicitly owned residual uncertainty**. The root lead adopts the following bounded dispositions after root and independent review; this does not mark an unknown caller as explained or pass a downstream issue. Numeric reconciliation has separate root and independent review. Each unresolved group has an owner and a concrete acceptance/reopen condition in the JSON.

Own post-response/work-item/outbox correlation and the separately measured 28/24 residual sweep reads. Explain the historical 25–695 range only as far as evidence permits. Flat identity sets are not item-to-execution mappings, and source-compatible recovery reads do not prove ownership. No second baseline harness is required.
2. **T07 / [#2395](https://github.com/elsa-workflows/elsa-foundation/issues/2395):** own the relevant upstream caller, repeated unchanged baseline and freshness question for activity-state/durable-value materialization before T08/#2396 and #1306. The M2 HTTP-after observation is **8 durable-value and 12 activity-state commands**. The earlier 80 Coalesced durable-page operation joins include HTTP and REST and predate the paging fix; they are not remaining avoidable work or another 80-query saving. A reviewed no-change decision remains valid if no useful safe reuse is shown.
3. **Checkpoint [#1239](https://github.com/elsa-workflows/elsa-foundation/issues/1239):** consume the exact checkpoint scopes and requested participant vectors before choosing a reduction. Inputs are not affected rows, combined flushes are not per-participant commands, and the four observed missing marker lookups are not automatically removable. Respect the separately owned #2286 lease seam. Inspection/incident residuals enter this lane only if a selected proposal actually touches them; table names alone do not establish checkpoint ancestry.
4. **Queue/outbox T14 / [#2407](https://github.com/elsa-workflows/elsa-foundation/issues/2407):** consume T02 and T04 results after its dependencies are accepted. Empty polling results are not evidence that the durable recovery backstop is redundant. No safe query reduction is selected from those counts alone.
5. **Program lead, accepted through T18 / [#2413](https://github.com/elsa-workflows/elsa-foundation/issues/2413):** retain the remaining request/admission, state, inspection, diagnostics, placement and IAM residuals in the final response and final count comparison. No change is selected for them from this aggregate. Before a proposed change touches any such store, or a claimed saving relies on that family, prove the relevant caller/identity boundary. Investigate unexplained final group deltas before assigning savings. This is an explicit owned uncertainty, not a finding that the work is necessary, optimized, or fully attributed.
