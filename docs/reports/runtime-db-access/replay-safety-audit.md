# ReplaySafe and fusion audit

**Audit pin:** `c2dc3ac28c19e1c288697b885607a542b5def500` (7 October 2026). This is a source review of the selected fixture and bounded first-party candidates. Its Set intrinsic means the historical custom transform is not needed for this audit. No source behavior, profile, host default or published executable was changed, and no new build, execution or replay test was run for this audit. ## Decision

Keep `Immediate` as the host default for this program. The selected fixture's `SetVariable` compiles to the `Set` intrinsic and is already classified fusable; its exact JavaScript expressions read workflow-variable values through the `BindingPureV1` expression sandbox. `HttpEndpoint` remains `External`. `WriteHttpResponse` is a conditional T10 candidate for the exact fixture, not yet approved for a blanket type-level annotation: its body constructs a typed response instruction and HTTP delivery follows committed completion, and the retained artifact confirms the selected response inputs are inline literals or a pure variable expression. Full replay and binding-contract verification remains the gate before a type-level change. No latency or dispatch saving is claimed here.

## Selected graph and current declarations

The pinned reference fixture is a root `Sequence` with synchronous `HttpEndpoint`, `SetVariable`, and `WriteHttpResponse` children. `HttpEndpoint` is a CLR trigger activity with an injected `IHttpRequestBodyParser`. Its start/resume path consumes a trigger request or creates registrations, and its result parses the request body into `HttpEndpointResult` ([source](https://github.com/elsa-workflows/elsa-foundation/blob/c2dc3ac28c19e1c288697b885607a542b5def500/src/essentials/Activities/Http/Activities/HttpEndpoint.cs#L24-L35), [execution](https://github.com/elsa-workflows/elsa-foundation/blob/c2dc3ac28c19e1c288697b885607a542b5def500/src/essentials/Activities/Http/Activities/HttpEndpoint.cs#L71-L119)). ### Replay stability of the input snapshot

The start handler materializes the complete input snapshot before creating the `Running` state and its `ActivityStarted` commit ([materialization and transition](https://github.com/elsa-workflows/elsa-foundation/blob/c2dc3ac28c19e1c288697b885607a542b5def500/src/essentials/Workflows/Runtime/Services/WorkHandlers/WorkflowStartActivitySchedulerWorkHandler.cs#L275-L303)). In Coalesced cadence, that checkpoint is a replay-shortening marker, not a mandatory boundary: the source policy defers non-mandatory checkpoints, and ADR 0032 explicitly lists `ActivityStarted` among those replayable progress markers ([policy](https://github.com/elsa-workflows/elsa-foundation/blob/c2dc3ac28c19e1c288697b885607a542b5def500/src/essentials/Workflows/Runtime/Services/Coalescing/CoalescingRuntimeCheckpointPersistencePolicy.cs#L46-L66), [ADR 0032](https://github.com/elsa-workflows/elsa-foundation/blob/c2dc3ac28c19e1c288697b885607a542b5def500/docs/adr/0032-runtime-checkpoint-cadence-is-policy-driven-per-workflow.md#L18-L24)). If the segment has not flushed, recovery rematerializes the snapshot from the last flushed state. The profile therefore covers deterministic inputs as well as a pure `ExecuteAsync` body.

For canonical expression inputs, runtime materialization requires `BindingPureV1`; the first-party JavaScript evaluator enforces that profile and removes time, randomness, locale, and environment access ([runtime profile gate](https://github.com/elsa-workflows/elsa-foundation/blob/c2dc3ac28c19e1c288697b885607a542b5def500/src/essentials/Workflows/Runtime/Services/Values/RuntimePortableExpressionEvaluator.cs#L25-L48), [JavaScript restrictions](https://github.com/elsa-workflows/elsa-foundation/blob/c2dc3ac28c19e1c288697b885607a542b5def500/src/essentials/Expressions/JavaScript/Jint/Services/JintPortableJavaScriptEvaluator.cs#L30-L72), [evaluator contract](https://github.com/elsa-workflows/elsa-foundation/blob/c2dc3ac28c19e1c288697b885607a542b5def500/src/essentials/Expressions/Core/Contracts/IPortableExpressionEvaluator.cs#L6-L12)). This rules out arbitrary time/random JavaScript through the canonical binding path. The selected response body expression reads `referenceText`, which the preceding Set computes from the persisted `content` variable; it uses no request object, clock, random source, or injected activity service. The retained executable below confirms that binding and capability profile. T10 must still verify its candidate host composition and replay behavior. The evaluator contract describes pure evaluation over immutable declared values; this audit does not assume an implementation that deliberately violates that contract.

Secrets are withheld from the persisted snapshot and resolved afresh on every activation ([secret snapshot path](https://github.com/elsa-workflows/elsa-foundation/blob/c2dc3ac28c19e1c288697b885607a542b5def500/src/essentials/Workflows/Runtime/Services/Values/RuntimeActivityInputMaterializer.cs#L161-L165), [activation path](https://github.com/elsa-workflows/elsa-foundation/blob/c2dc3ac28c19e1c288697b885607a542b5def500/src/essentials/Activities/Runtime/Services/ActivitySecretInputResolver.cs#L53-L68)). `WriteHttpResponse` explicitly refuses secret bindings for `Body` and `ContentType`. Its remaining fields are `StatusCode: int` and `Headers: IDictionary<string, string[]>` ([activity inputs](https://github.com/elsa-workflows/elsa-foundation/blob/c2dc3ac28c19e1c288697b885607a542b5def500/src/essentials/Activities/Http/Activities/WriteHttpResponse.cs#L18-L32)); the contract compiler represents a dictionary input as a dictionary collection shape ([type decomposition](https://github.com/elsa-workflows/elsa-foundation/blob/c2dc3ac28c19e1c288697b885607a542b5def500/src/essentials/Primitives/Primitives/Models/TypeReferenceFactory.cs#L52-L76)). The numeric and collection-shape rules reject text-to-integer and text-to-dictionary Auto bindings, and [explicit profiles require formatted content](https://github.com/elsa-workflows/elsa-foundation/blob/c2dc3ac28c19e1c288697b885607a542b5def500/src/essentials/Workflows/Publishing/Services/ValueConversionPlanResolver.cs#L93-L106); I found no source-supported `SecretRead` binding for these fields. ## Claim, fusion, and publication semantics

`SideEffectProfile` governs the typed activity's pre-activation `ActivityAttemptClaimed` checkpoint. The claimer stamps the resolved profile into checkpoint metadata ([claim record](https://github.com/elsa-workflows/elsa-foundation/blob/c2dc3ac28c19e1c288697b885607a542b5def500/src/essentials/Activities/Runtime/Services/ActivityAttemptActivationClaimer.cs#L341-L360)). In Coalesced mode, a ReplaySafe claim is deferred and folded forward; External or missing profile remains immediate, and terminal, suspend, incident, cancellation, and bookmark boundaries stay immediate ([policy](https://github.com/elsa-workflows/elsa-foundation/blob/c2dc3ac28c19e1c288697b885607a542b5def500/src/essentials/Workflows/Runtime/Services/Coalescing/CoalescingRuntimeCheckpointPersistencePolicy.cs#L26-L71), [ADR 0032 R2](https://github.com/elsa-workflows/elsa-foundation/blob/c2dc3ac28c19e1c288697b885607a542b5def500/docs/adr/0032-runtime-checkpoint-cadence-is-policy-driven-per-workflow.md#L57-L60)). This is a claim-visibility/recovery declaration, not exactly-once delivery. `Set` is an intrinsic and does not take the CLR attempt-claim path; it has its own intrinsic completion commit.

A profile alone does not grant fusion. D1's `ShouldFuse` requires the option, a live coalescing session, and a ReplaySafe typed contract or fusable intrinsic ([driver](https://github.com/elsa-workflows/elsa-foundation/blob/c2dc3ac28c19e1c288697b885607a542b5def500/src/essentials/Workflows/Runtime/Services/WorkHandlers/ReplaySafeFusionDriver.cs#L69-L96)); `WorkflowScheduleActivitySchedulerWorkHandler` calls it for each `ScheduleActivity` dispatch ([call site](https://github.com/elsa-workflows/elsa-foundation/blob/c2dc3ac28c19e1c288697b885607a542b5def500/src/essentials/Workflows/Runtime/Services/WorkHandlers/WorkflowScheduleActivitySchedulerWorkHandler.cs#L115-L125)). The ReplaySafe-parent and single-inbound-edge checks apply separately to D2's inline completion pump when it considers a successor schedule ([D2 classifier](https://github.com/elsa-workflows/elsa-foundation/blob/c2dc3ac28c19e1c288697b885607a542b5def500/src/essentials/Workflows/Runtime/Services/WorkHandlers/ReplaySafeFusionDriver.cs#L303-L347), [ADR 0047 D1/D2](https://github.com/elsa-workflows/elsa-foundation/blob/c2dc3ac28c19e1c288697b885607a542b5def500/docs/adr/0047-replaysafe-activities-execute-as-fused-hops-with-precomputed-routing.md#L21-L35)). In the selected graph, `Sequence` schedules every child with the Sequence execution as parent ([first and next child](https://github.com/elsa-workflows/elsa-foundation/blob/c2dc3ac28c19e1c288697b885607a542b5def500/src/essentials/Activities/Sequence/Activities/Sequence.cs#L25-L45), [successor scheduling](https://github.com/elsa-workflows/elsa-foundation/blob/c2dc3ac28c19e1c288697b885607a542b5def500/src/essentials/Activities/Sequence/Activities/Sequence.cs#L47-L81)); its probe recognizes the linear child chain ([probe](https://github.com/elsa-workflows/elsa-foundation/blob/c2dc3ac28c19e1c288697b885607a542b5def500/src/essentials/Activities/Sequence/Internal/SequenceReplaySafeSuccessorRoutingProbe.cs#L7-L30)). Those facts support D2 continuation when the pump evaluates the sequence; they are not extra D1 preconditions. Thus `Set` can fuse as-is after the External `HttpEndpoint`; a ReplaySafe `WriteHttpResponse` could enter D1 if its profile changes. The trigger itself remains discrete. Outside an active Coalesced burst, the D1 path remains discrete ([options](https://github.com/elsa-workflows/elsa-foundation/blob/c2dc3ac28c19e1c288697b885607a542b5def500/src/essentials/Workflows/Runtime/Core/Models/RuntimeReplaySafeFusionOptions.cs#L3-L30)).

Fused typed invocation still passes through the ordinary activity activation strategy: `WorkflowInvokeActivitySchedulerWorkHandler` performs the claim, calls `IActivityActivator`, then invokes the activity ([invoke path](https://github.com/elsa-workflows/elsa-foundation/blob/c2dc3ac28c19e1c288697b885607a542b5def500/src/essentials/Activities/Runtime/Services/WorkflowInvokeActivitySchedulerWorkHandler.cs#L172-L221)); `ActivityActivator` resolves the consumer/schema strategy and `ClrActivityActivator` creates a fresh DI scope ([strategy selection](https://github.com/elsa-workflows/elsa-foundation/blob/c2dc3ac28c19e1c288697b885607a542b5def500/src/essentials/Activities/Runtime/Services/ActivityActivator.cs#L19-L89), [CLR activation](https://github.com/elsa-workflows/elsa-foundation/blob/c2dc3ac28c19e1c288697b885607a542b5def500/src/essentials/Activities/Primitives/Activation/ClrActivityActivator.cs#L13-L82)). Fusion does not bypass activation or DI dependencies. D1 eligibility is the node's ReplaySafe contract plus option and active session; the D2 parent/edge checks govern only inline completion-cascade successors.

The activity compiler resolves an unmarked type to External and places an explicit attribute value in the pinned `ActivityContract` ([resolution](https://github.com/elsa-workflows/elsa-foundation/blob/c2dc3ac28c19e1c288697b885607a542b5def500/src/essentials/Workflows/Publishing/Services/ExecutableNodeCompiler.cs#L346-L367)). The profile participates in the contract fingerprint when non-default; External remains omitted for byte-stable old contracts ([fingerprint](https://github.com/elsa-workflows/elsa-foundation/blob/c2dc3ac28c19e1c288697b885607a542b5def500/src/essentials/Activities/Runtime/Core/Models/ActivityContract.cs#L85-L123)).
