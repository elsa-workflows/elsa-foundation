## Assessment

There are two contributors to the high database count. First, the runtime implements durable execution through state transitions, ownership checks, scheduler work, outbox delivery, inspection and checkpoint commit proof. One authored activity can cause several such operations. Second, we found avoidable access patterns within that design: coalesced pagination amplified reads, and repeated traversals could fetch the same durable-value pages again within one eligible owner and segment. The program has delivered bounded read corrections. The accepted clean-source Coalesced HTTP control records 277→134 request-associated EF commands (PostgreSQL 195→84; ancillary SQLite 82→50). That combined-source observation does not isolate one correction or count all settled-instance work. [Final clean-source command account](final-clean-ef-accounting.md).

Coalesced execution already supports accumulating eligible work in memory and committing at durable boundaries. It is an existing way to choose a wider replay interval, subject to mandatory boundaries and the activity's pinned replay contract. This program keeps Immediate as the default. It does not establish that all remaining SQL is necessary, or that durability must be removed to improve performance. [Paging specification](../../../specs/193-bounded-coalesced-pagination/spec.md), [page-reuse evidence](../../../specs/197-bounded-durable-value-page-reuse/evidence/nonempty-ef-baseline.md), [cadence verification](cadence-verification.md).

The accounting units must remain distinct. EF command executions, command attempts that fail, SQL statements, provider protocol cycles, physical network round trips, transactions, durable checkpoint commits and scheduler dispatches are different measurements. A batched command can contain multiple statements. A protocol cycle is not itself a measured physical round trip. Request latency and all database work owned by a settled execution are also different quantities. [Accounting boundaries](joined-request-settlement-accounting.md).

## Responses to the supplied questions

**Q1 — Is 533 accesses / 24 checkpoints intended?** The architecture explains why four authored activities can produce many more persistence operations; it does not make 533 a required or acceptable budget. Those numbers belong to the supplied historical workload. The original counting method observed EF command events, so it does not independently establish 533 SQL statements or round trips. The selected HTTP fixture records 635→635 request-associated EF commands and 22→22 persisted checkpoint markers under Immediate, versus 277→134 commands and 3→2 markers under Coalesced. Valid REST records 556→556 commands / 18→18 markers and 101→73 commands / 1→1 markers respectively. Capture-wide SQL/protocol counts, typed queue operations and retained state are published separately; deleted dispatch history and physical RTT remain unmeasured. No general one-work-item/one-checkpoint invariant is assumed. [Original analysis](response.md), [observed operation joins](joined-request-settlement-accounting.md).

**Q2 — Why 81 durable-value reads under Coalesced?** The investigation found a stronger explanation than an assumed high point-lookup miss rate: the old shared merger read inner pages one item at a time and could repeat an exhausted-source probe while emitting overlay values. Full-value traversals at several runtime stages could amplify that further. The program corrected paging and delivered bounded page reuse. Those mechanisms do not attribute every one of the historical 81 reads. The six-to-two SQLite fixture result proves the selected reuse behavior; the final Coalesced HTTP/REST controls separately record 277→134 and 101→73 request-associated commands. The final diagnostic account separates request traces, global polling and point-in-time settlement; it does not assign all global work to an execution. [Final clean-source command account](final-clean-ef-accounting.md). [Historical mechanism](response.md), [selected reuse and its limits](materialization-reuse-spike.md), [delivered proof](../../../specs/197-bounded-durable-value-page-reuse/evidence/integration-verification.md).

**Q3 — Why about 85 scheduler reads for 23 work items?** Enqueue identity checks, FIFO claiming, fenced consumption, renewals and empty probes serve different purposes. The captured operation joins distinguish some of these paths, but they do not allocate the historical 85 reads completely. The tested insert-first shortcut did not preserve the duplicate-operation contract and is not shipped. This leaves opportunities to investigate with future evidence; it does not justify deleting ownership or replay checks based on an aggregate ratio. [Scheduler/outbox account and rejected trial](scheduler-outbox-access-spike.md).

**Q4 — Can inspection or persistence be less granular per workflow?** The existing authored checkpoint cadence provides this choice when the host composes Coalesced support. Verified cases demonstrate host fallback, workflow override, effective cap and persisted `activity-level` versus `boundary-level` inspection granularity. All six HTTP controls completed with the expected body and zero incidents, and earlier executions retained their original stamps across host reconfiguration. This coalesces durability; it does not disable inspection capture. Independent inspection decoupling remains [#1237](https://github.com/elsa-workflows/elsa-foundation/issues/1237). This program does not introduce a general persistence-off mode. [Live cadence verification](cadence-verification.md), [operator guide](../../runtime-durable-resumption.md).

**Q5 — Should a deterministic transform be ReplaySafe?** The declaration requires the whole supported activity contract to be safe to execute again from persisted input, including its evaluator, dependencies, payload references and observable effects. The selected reference computation is an already-fusable SetVariable intrinsic, so the original transform implementation is not required. HttpEndpoint remains External. The response activity has accepted contract, normal publication, process-loss and causal-count evidence supporting ReplaySafe; PR #2518 is merged and final integrated correctness passed. The reproduced profile-identity failure was corrected by #2515/#2517. Foundation is unreleased and unused, so the owner excluded a legacy-export compatibility layer. Historical failures remain documented. [Audit and erratum](replay-safety-audit.md), [current decision and limits](../../../specs/198-response-replay-safety/evidence/decision.md).

**Q6 — Is 30 ms realistic?** The final bounded measurements do not support that promise. For the selected four-activity Coalesced HTTP workflow, the final source observed a median of 149.5 ms, mean 200.5 ms and exploratory p95 of 368.1 ms, compared with before values of 239.4 / 303.0 / 493.8 ms. These are 60-sample observations on the recorded Azure/Debug/provider composition, with one window per source. They support using that measured range as the immediate engineering baseline; the final account still contains checkpoint, scheduler, inspection, state, liveness and configured telemetry work. Use roughly 150–200 ms central latency and the observed exploratory p95 near 370 ms as the baseline for this exact recipe, not a portable commitment. A lower product target needs a separately agreed Release/production-topology measurement and evidence identifying the next removable cost. The reported historical 0.3 ms per operation is an aggregate ratio, not a fixed price. No 30 ms gate or production SLA is adopted. [Final bounded comparison and limitations](final-timing.md).

**Q7 — Is untraced work after the response scheduler/outbox follow-up?** That remains unproven for the supplied 25–695 range. Missing TraceId does not establish ownership. The accepted extended handoff reconciles 1,647 commands, including 931 exact method joins and 716 commands assigned to explicit residual groups. It lacks an HTTP response-finished timestamp, so its after-drain commands cannot be relabelled post-response. Independently observed global sweeps are not automatically work owned by the measured execution. The final four-case account has its own calibrated client-response boundary. Before Coalesced, 263 HTTP-associated commands completed before client receipt, 8 started afterward and 6 overlap the uncertainty band. After Coalesced, all 134 completed before receipt. All HTTP-associated commands precede their later settled snapshots. Separately observed global polls remain unowned; they cannot explain the historical 25–695 range. These are client-receipt boundaries, not server response-finished events. [Final joined account](final-joined-accounting.md). [Joined account](joined-request-settlement-accounting.md), [residual disposition](residual-accounting.md).

## Remaining cost and owned uncertainty

The final Coalesced HTTP trace contains **134 commands: 84 PostgreSQL and 50 ancillary SQLite**. Its 47 exact method-ancestor joins comprise 33 checkpoint commands, 10 scheduler-queue commands, two durable-value commands and two outbox commands. The other 87 commands lack exact method ancestry: parsed table tokens identify 48 telemetry, two placement and 37 runtime-state commands. The last group includes nine activity-state reads, eight workflow-state reads, six inspection reads, six liveness commands and eight commands across trigger/bookmark, hold, incident, dispatch and executable-reference tables. This fully conserves the trace count; table classification does not prove the missing caller, affected rows, necessity or latency share. [Detailed counts and provenance](final-joined-accounting.md).

This explains why a simple activity graph still accesses the database: durable coordination and the configured host services operate below the authored activities. It also identifies concrete remaining families without pretending every access is unavoidable. The selected safe reductions are delivered. The rejected checkpoint-save and insert-first queue experiments remain rejected; no generic cache, persistence-off mode or weaker recovery policy is introduced.

## Operator guidance already supported

Use the [existing cadence guide](../../runtime-durable-resumption.md) to compose host support, author a per-workflow choice, publish the changed definition and read back the effective mode/cap/inspection granularity on the actual execution. Keep Immediate for workflows that require that durability granularity. Keep mandatory boundaries and External classifications unless a reviewed activity contract supports replay.

Use the primary HttpEndpoint fixture for response latency and the companion REST definition for valid REST admission/output checks. Do not substitute a workflow waiting at an HttpEndpoint bookmark for a completed REST control. Use separate diagnostics and timing runs, retain failed attempts, and inspect committed output, incident state and settlement before treating a response as a passing control. [Workload protocol](workload-reproduction-plan.md).
