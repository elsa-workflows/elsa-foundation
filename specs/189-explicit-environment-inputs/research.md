# Phase 0 Research: Explicit Private Environment Inputs

**Feature**: [Explicit private environment inputs](./spec.md)

**Status**: Research decisions and Phase 1 contracts reviewed; implementation proof remains planned

**Scope**: Resolve the source and policy choices needed to plan the first lane. This records design decisions, not production behavior or an executed proof.

## Constitution pre-check

The proposal is compatible with the current gates, subject to the planning decisions called out below:

- **Framework §2.1**: the capability is additive at the host/tool boundary and must keep implementation dependencies behind the existing host closure. It must reuse the existing composition and preparation path rather than introduce a second resolver.
- **Framework §2.11**: selection and required-dependency reconciliation must fail clearly before preparation. The input must not create a silent fallback or a second source of runtime truth.
- **Framework §2.12 and Elsa §E4**: configuration and settings classification remains deferred. This lane is a narrow, explicitly supplied overlay for one inspection operation; it does not ratify a general configuration taxonomy.
- **Framework §2.19**: existing feature identities remain the stable logical names used by composition, diagnostics, and tooling. The frozen candidate's accepted and removed feature identities therefore remain part of the compatibility boundary.
- **Framework §2.21**: existing candidate inspection subjects and objectives must continue to be proven. Research does not claim that tests have run, add a test cadence, or authorize deleting existing tests.
- **Framework §4**: the new capability is an additive public host capability. Its package placement and SemVer consequence belong in PLAN; the existing candidate contract and method remain closed.
- **ADR 0076 D1/D4/D7**: execution stays inside the selected host closure, provider disagreement is refused rather than inferred, and private values do not enter arguments or exported evidence.

The pre-check passes for research. The deferred status of Framework §2.12 and Elsa §E4 is material: a later plan must keep this feature-specific policy separate from any future general configuration model.

## Decisions

### D1. Add an independent candidate-environment capability

**Decision.** Add `EfCandidateEnvironmentInspectionContract.Version = 1` and an additive host entry point named `EfToolingHost.RunCandidateEnvironmentInspectionAsync(Stream, Stream, CancellationToken)`. Keep `EfCandidateInspectionContract.Version = 1` and `RunCandidateInspectionAsync(Stream, Stream, CancellationToken)` unchanged and closed.

**Rationale.** The existing candidate path is already a versioned, closed capability. [`EfCandidateInspectionContract.cs`](../../src/essentials/Persistence/EntityFramework/Tooling/EfCandidateInspectionContract.cs) defines its literal version, while [`EfToolingHost.cs:49-69`](../../src/essentials/Persistence/EntityFramework/Tooling/EfToolingHost.cs#L49-L69) exposes the existing host operation. [`ToolingEntryPoint.cs:139-162`](../../src/essentials/Cli/Worker/ToolingEntryPoint.cs#L139-L162) binds the existing version and exact method signature and deliberately has no legacy fallback. A separate versioned capability preserves candidate-v1 compatibility and lets a host advertise support independently.

**Alternatives considered.** Extending the old candidate payload or changing its method would silently widen a closed contract. Reusing the existing live-worker environment operation would import ambient process state and would not represent a supplied intended snapshot. Both alternatives violate the compatibility and determinism boundary.

### D2. Use a separate private worker command and host envelope

**Decision.** Add a private `inspect-candidate-environment` command while retaining outer `WorkerContract` version 2. Its host request conceptually contains the frozen old candidate payload and a separately bound environment-input payload. The old `inspect-candidate` request shape and validator continue to reject external fields.

**Rationale.** [`WorkerContract.cs:108-121`](../../src/essentials/Cli/Worker/WorkerContract.cs#L108-L121) rejects candidate-shaped requests sent through the ordinary path. [`WorkerContract.cs:635-706`](../../src/essentials/Cli/Worker/WorkerContract.cs#L635-L706) validates the existing candidate command and payload as a closed shape, and [`WorkerContract.cs:824-964`](../../src/essentials/Cli/Worker/WorkerContract.cs#L824-L964) shows the candidate fields that must remain stable. The new operation can share the outer worker transport and owned lifecycle while using its own capability and closed inner request. The host entry point should receive both parts together so that the selected host cannot accidentally inspect a candidate with a different environment binding.

**Alternatives considered.** Adding an `environment` field to the old candidate payload, accepting external fields in the old validator, or routing through the existing `inspect-candidate` operation would change the old contract. A new standalone transport would duplicate the worker boundary and its limits. These alternatives are rejected.

### D3. Capture one explicit private input document

**Decision.** The first lane accepts `--environment-input <privateJSONfile>`. The file is one closed raw document of the form `{ "version": 1, "entries": [ { "key": "...", "value": "..." } ] }`. Values are strings, and an empty string is valid. `null`, tombstone/removal entries, omitted values, and user binding IDs are not part of this lane. “Complete snapshot” means the complete explicitly supplied overlay document, not the full ambient, deployed, or effective environment.

The capture reads the operator-owned regular file once under the applicable size bound, makes immutable defensive copies for the private request, and verifies the source has not changed before and after the owned inspection. The original private source file remains the operator's source of truth; the privacy rule forbids extra generated copies and public exposure, not the values already present in that source file.

Capture creates random correlation values and binds the same private capture to the frozen candidate files, selected host, shell, environment, and invocation. Correlation is capture-owned rather than user supplied. No value digest, path digest, or per-key winning provenance is emitted.

**Rationale.** [`CompositionInputSnapshot.cs`](../../src/essentials/Cli/CompositionInputSnapshot.cs) captures file bytes once and verifies them again. [`CompositionInspectionCapture.cs`](../../src/essentials/Cli/CompositionInspectionCapture.cs) creates capture and invocation identifiers, freezes the selected files, and verifies the capture without publishing their contents. The proposed inspection extension preserves ADR 0076 D7's credential and exported-evidence boundaries; a private configuration file for this new inspection lane does not broaden apply/validate connection admission.

**Alternatives considered.** Importing caller ambient variables, custom providers, command-line values, deployment attestation, physical readiness, or an unknown portable export would make the result dependent on state the user did not explicitly supply. Rereading a mutable file during execution, accepting user binding IDs, or silently accepting a changed external selection would break capture integrity. These alternatives are rejected.

### D4. Apply the input at the Workbench environment stage

**Decision.** Treat explicit entries as the environment overlay at the supported Workbench stage: after appsettings base/environment and shells base/environment, before command-line. The first lane imports no caller ambient environment, custom provider, or command-line provider. Enrollment is an explicit host declaration as described in D9; it is not inferred from a host name or from method presence.

Normal `ConnectionStrings__<name>` keys are supported through the ordinary double-underscore normalization described in D5. Standard service-connection expansions are explicitly refused in D6. The lane therefore offers a deterministic supported subset of environment-stage behavior rather than claiming parity with every process-level provider.

**Rationale.** [`Elsa.Workbench/Program.cs:91-104`](../../src/apps/Elsa.Workbench/Program.cs#L91-L104) shows `WebApplication.CreateBuilder(args)` establishing the default appsettings layers, then adds `shells.json` and its environment variant, then environment variables, then command-line. [`EfCandidateInspectionOperation.cs:395-422`](../../src/essentials/Persistence/EntityFramework/Tooling/EfCandidateInspectionOperation.cs#L395-L422) shows the candidate file-only builder and its deterministic file order. The new operation can represent the explicit environment stage without importing the worker's live process environment or command line.

**Alternatives considered.** Letting command-line or live ambient state win would make the captured intent incomplete. Using the current worker environment would reintroduce caller ambient state. Enrolling a host without a reviewed configuration policy would overclaim portability. All are rejected.

### D5. Admit raw keys before lossy normalization

**Decision.** A key must be nonempty and comprise valid Unicode scalar values. Reject Unicode control characters, `=`, and unpaired UTF-16 surrogates. Do not trim, case-fold, or Unicode-normalize keys; a nonempty whitespace key remains a literal key. Values are JSON strings, may be blank, and may contain valid Unicode including escaped newline and tab; reject `null`, NUL, and unpaired surrogates. Normalize accepted keys by replacing `__` with `:`. Compare normalized keys using `StringComparer.OrdinalIgnoreCase` before any provider is invoked. Refuse duplicate raw keys and every normalized collision, including case-only differences and `__`/`:` aliases. Omission contributes nothing; there is no removal or tombstone semantic.

The selected first-lane admission limits are at most 1,024 entries, at most 1,024 UTF-8 bytes per raw or normalized key, and at most 65,536 UTF-8 bytes per value, in addition to the raw document limit in D7. These are new design choices within the existing transport budget, not limits already implemented in the source.

Admission rejects invalid Unicode scalar sequences in both keys and values before provider construction. Values may retain controls other than NUL, including newline and tab. Key controls are refused. No strict ASCII allowlist or Unicode normalization is introduced; these explicit first-lane rules are proposed production requirements, not claims of current implementation.

**Rationale.** The .NET environment provider uses the double-underscore-to-colon transform and a case-insensitive dictionary; once provider processing begins, raw identities and the distinction between colliding spellings are lost. The discovery report records the same behavior in [`external-environment-inputs.md:57-63`](../../docs/reports/runtime-composition/external-environment-inputs.md#L57-L63). Failing before provider admission makes a collision observable and deterministic instead of inheriting enumeration order.

**Alternatives considered.** Provider enumeration order/last-wins, allowing duplicate winners, rejecting every non-ASCII key, or applying a strict ASCII grammar would either be lossy or add an unsupported restriction. These alternatives are rejected pending evidence.

### D6. Refuse all standard service-connection prefixes in the first lane

**Decision.** Before `__` normalization, refuse raw keys with any of these prefixes, case-insensitively:

`MYSQLCONNSTR_`, `SQLAZURECONNSTR_`, `SQLCONNSTR_`, `CUSTOMCONNSTR_`, `POSTGRESQLCONNSTR_`, `APIHUBCONNSTR_`, `DOCDBCONNSTR_`, `EVENTHUBCONNSTR_`, `NOTIFICATIONHUBCONNSTR_`, `REDISCACHECONNSTR_`, `SERVICEBUSCONNSTR_`.

Ordinary `ConnectionStrings__<name>` remains supported. Reproducing service-prefix expansion is deferred work; a planning worker must not silently add it to the first lane.

**Rationale.** The pinned .NET 10.0.10 [`EnvironmentVariablesConfigurationProvider`](https://github.com/dotnet/runtime/blob/v10.0.10/src/libraries/Microsoft.Extensions.Configuration.EnvironmentVariables/src/EnvironmentVariablesConfigurationProvider.cs) defines the eleven families in its constants (source lines 16-26 in the repository view), checks them case-insensitively, and maps recognized values to `ConnectionStrings:<name>` and provider metadata (source lines 76-118). The provider's ordinary normalization also replaces `__` with `:`. Because these expansions carry additional semantics and erase the raw identity, a first lane that claims to carry only explicit intended values should refuse them as a complete class.

**Alternatives considered.** Refusing only the four commonly encountered prefixes would leave an incomplete negative boundary. Reproducing all provider mappings now would expand scope into provider semantics. Passing prefixes through would let a later provider reinterpret the value. All are rejected for this lane.

### D7. Preserve existing transport bounds and state the byte arithmetic

**Decision.** Preserve the existing candidate limits: each selected file is at most 1 MiB decoded, the selected-file aggregate is at most 4 MiB decoded, the serialized worker request is at most 8 MiB, the response is at most 4 MiB, and JSON depth is bounded at 64. The environment document has a 1 MiB raw UTF-8 bound. Its captured raw bytes are transmitted in a bounded base64 field so ordinary JSON escaping cannot expand its contents unpredictably.

The final serialized request remains authoritative. With binary MiB units, each 1 MiB selected file encodes to 1,398,104 base64 bytes. Four such files consume 5,592,416 bytes, and the 1 MiB environment document consumes another 1,398,104 bytes, for 6,990,520 bytes before the host envelope, feature selections, names, and JSON framing. That leaves 1,398,088 bytes of the 8,388,608-byte request ceiling. Therefore the per-part maxima do not guarantee that their combination fits; a request can be refused at the final bounded serialization even when each individual source passes. Use at most 1,024 entries, 1,024 UTF-8 bytes per raw or normalized key, and 65,536 UTF-8 bytes per value. These independent caps do not replace the raw-document or final-request limits. Exact-limit and one-over proof for every cap belongs in the existing fixtures.

Admission must count encoded and decoded bytes before allocation. No larger request cap, unlimited document, compression fallback, or new transport budget is proposed here.

**Rationale.** [`WorkerContract.cs:19-30`](../../src/essentials/Cli/Worker/WorkerContract.cs#L19-L30), [`WorkerContract.cs:673-706`](../../src/essentials/Cli/Worker/WorkerContract.cs#L673-L706), [`CandidateWorkerProcess.cs:9-18`](../../src/essentials/Cli/CandidateWorkerProcess.cs#L9-L18), and [`EfCandidateInspectionOperation.cs:16-24`](../../src/essentials/Persistence/EntityFramework/Tooling/EfCandidateInspectionOperation.cs#L16-L24) establish the current request, response, file, aggregate, depth, and selection bounds. The new input should fit the existing bounded worker rather than create an unbounded private path.

**Alternatives considered.** Increasing the transport cap, accepting an unlimited raw document, or relying on compression would create new operational and proof obligations. These alternatives are rejected.

### D8. Reuse host composition, reconciliation, and preparation

**Decision.** The additive host operation combines the frozen candidate files with the explicit environment overlay, then uses one host-owned configuration builder, composition/selection reconciliation, and EF persistence preparation path. Reconciliation occurs before preparation. Valid authored feature removals are preserved; the operation refuses divergent external selection, inconsistent removal intent, and required-dependency conflicts. It does not silently rewrite the authored selection.

If the external selection diverges, the achievable recovery is to edit the authored input, use the existing `composition accept` behavior where appropriate, and capture a fresh immutable input. There is no ambient “accept” magic and no assumption of a new recovery command.

The redacted projection retains existing safe candidate fields, use source `captured-workbench-json-explicit-environment-v1`, and identify `externalInputs` as `supplied-intended`. The old response validator remains closed and bound to the old source; the additive lane needs its own response-aware validation for the new source and fields. It must not claim deployment, readiness, physical state, or per-key winning provenance.

**Rationale.** [`EfCandidateInspectionOperation.cs:54-127`](../../src/essentials/Persistence/EntityFramework/Tooling/EfCandidateInspectionOperation.cs#L54-L127) and [`EfCandidateInspectionOperation.cs:153-239`](../../src/essentials/Persistence/EntityFramework/Tooling/EfCandidateInspectionOperation.cs#L153-L239) show bounded parsing, reconciliation before preparation, and value-free refusal/projection behavior. [`CompositionInspectionCapture.cs`](../../src/essentials/Cli/CompositionInspectionCapture.cs) supplies the existing edit/capture lifecycle. The existing authored-edit and `composition accept` behavior is documented in [`edited-selection-acceptance.md:19-30`](../../docs/reports/runtime-composition/edited-selection-acceptance.md#L19-L30); that file-only recovery evidence does not prove the new external-environment toggle journey, which remains a required future proof. Reusing those seams preserves one runtime configuration policy and candidate-v1 behavior.

**Alternatives considered.** A second resolver, a separate frontend interpretation, silently changing authored removals, or exporting exact winning file/key provenance would either create competing policy or disclose private configuration. These alternatives are rejected.

### D9. Require explicit host enrollment, not hostname inference

**Decision.** The new EF capability is carried by the shared EF assembly and is therefore available to more than one host assembly. Method existence alone must not enroll a host. Add an additive `EfCandidateEnvironmentInputsAttribute` declaration with version 1 and the literal policy `workbench-json-explicit-environment-v1`; ship that declaration only on the reviewed Workbench host for the first lane. A reviewed test fixture or replica may declare the same policy when it is intentionally enrolled. An unenrolled Foundation Host refuses before composition. The worker verifies the declaration on the actual matching host assembly that it loaded, rather than inferring eligibility from an assembly or host name. Existing composer and dependency-path guards remain in force.

**Rationale.** The shared capability boundary and the selected host closure mean that a host can expose the same method without having the reviewed Workbench source ordering or enrollment policy. An explicit, versioned declaration makes the supported policy inspectable and gives an unenrolled host a deterministic refusal. This also leaves room for a future reviewed host policy without silently widening the first lane.

**Alternatives considered.** Checking only for `RunCandidateEnvironmentInspectionAsync`, matching a host name, or assuming every host using the shared EF assembly has Workbench semantics would over-enroll Foundation Host and any future host. These alternatives are rejected.

### D10. Keep trust, privacy, and side-effect boundaries explicit

**Decision.** Selected host composition code is trusted host code and runs in the existing owned worker/child boundary. This is an isolation and lifecycle boundary, not a general sandbox promise. Inspection must not start services, activate a runtime, connect to a database, apply migrations, publish, persist, or otherwise change the host. Private values must not enter logs, arguments, public output, exception excerpts, generated/public artifacts, or fingerprints derived from private inputs. Explicit CLI file locations and assembly-loader paths may remain where existing host loading requires them; private input paths and captured values must not be copied into diagnostics or public results.

The operator-owned input file necessarily contains the supplied values. The prohibition is on extra persisted copies and disclosure of those values, including SHA256 or other derived fingerprints, while preserving the original input file and allowing safe existing loader metadata.

**Rationale.** The existing inspect command requires explicit `--trust-host-code` and uses the owned worker lifecycle; [`CompositionInspectCommand.cs`](../../src/essentials/Cli/CompositionInspectCommand.cs), [`CandidateWorkerProcess.cs`](../../src/essentials/Cli/CandidateWorkerProcess.cs), and ADR 0076 D1/D7 establish this boundary. The source capture verifies files without publishing their contents. This keeps the operation useful for host-specific inspection without claiming safety properties that the worker does not provide.

**Alternatives considered.** Claiming a general sandbox, importing command-line or ambient values, using deployed attestation or physical readiness, and emitting any private-input fingerprints would contradict the existing trust and privacy boundary. These alternatives are rejected.

## D11. Closed contract choices for Phase 1

**Decision.** The CLI option is `composition inspect --environment-input <path>`, admitted once and only for inspect. Omission retains the old file-only lane. No inline-value flag, stdin ambiguity, restore, ambient reader, or file generation is added. The capture creates one request bound to the selected installed host, shell/environment and accepted composition; callers cannot inject their own public capture receipt. The raw private document has exactly `version` (integer 1) and `entries` (array), with each entry having exactly string `key` and string `value`. Duplicate object properties, unknown fields, non-string values and nested/tombstone forms refuse. Zero entries is a valid explicit empty overlay. The document is strict UTF-8 JSON, allowing an optional leading UTF-8 BOM that counts against its 1 MiB cap; parsing may remove that prefix, but transport and drift comparison retain the original captured bytes. No Unicode normalization, trimming or value transformation is performed.

The new worker request remains outer version2 and has exactly `version`, `command`, `hostDirectory`, `hostName`, `depsFile`, `packageRoots`, `candidate`, and `environmentInput`. The new command is `inspect-candidate-environment`. Its nested candidate stays exactly the existing v1 payload with file-only source `captured-workbench-json-v1`. The separate `environmentInput` has exactly `version:1`, `captureId`, and canonical `content` base64 of the original raw document. Its capture ID must match the nested candidate, whose capture-owned invocation ID binds the whole operation. The host request has exactly `version:1`, `host:{name,directory}`, `candidate`, and `environmentInput`. Both processes check closed shape, limits and binding independently. Existing commands must still reject the additional field, including explicit null; no old parser is broadened merely because the shared request DTO gains an optional field.

Enrollment is `[assembly: EfCandidateEnvironmentInputs(1, "workbench-json-explicit-environment-v1")]`. The additive public attribute lives beside existing EF tooling declarations, has readonly `Version` and `Policy` properties from that constructor, targets assemblies and allows duplicate declarations to be detected and refused. Only exactly one supported declaration on the actual path-matched selected host assembly enrolls the first policy. Shared EF-method presence alone does not enroll Foundation Host. The host operation checks enrollment before building configuration or constructing the composer; the EF-free worker checks metadata using the loaded host's declaration and selected EF assembly identity, without adding an EF reference or invoking arbitrary attribute constructors. The worker obtains the actual assembly from an additive `HostClosure.LoadHostAssemblyForInspection(string hostDirectory, string hostName): Assembly` helper, verifies its name and actual location against the validated layout, and reads `CustomAttributeData` on that exact assembly. Preserve the existing public `LoadHostAssembly(...): void` signature; share the internal load implementation instead of changing its return type or scanning loaded assemblies by name. The declaration type identity must belong to the selected persistence assembly, with exactly two supported constructor arguments (integer1 and the exact policy string) and no extra named arguments. New capability binding requires the exact public static method, literal integer1, non-generic `Task<int>` return and stream/stream/cancellation parameters. No guessed package-version minimum: report the fixed unavailable-capability code and advise upgrading to a host carrying the declared capability.

New fixed safe codes are `candidate-environment-input-invalid`, `candidate-environment-input-too-large`, `candidate-environment-key-collision`, `candidate-environment-prefix-unsupported`, and `candidate-environment-host-unenrolled`. Shape/entry/character failures use invalid; any raw/per-entry bound exceeded uses too-large; duplicate raw or normalized entries use collision; a listed service prefix uses prefix-unsupported; absent/duplicate/wrong host declaration uses host-unenrolled. Input refusals exit2; unenrolled/capability/host-closure failures exit3. Retain existing source-drift, selection/EF conflict, response-invalid, cancellation/timeout and cleanup classifications and fixed local messages. No key, index, value, path, fingerprint or remote exception text appears in new diagnostics. Uncorrelatable direct host input exits2 with no invented response, preserving the existing missing/invalid-response treatment at the worker boundary.

The new response remains a separately validated host envelope version1 with existing correlation/status/exit and exactly one resolution/error. It retains existing safe resolution fields but requires source `captured-workbench-json-explicit-environment-v1` and `externalInputs:supplied-intended`. All target/connection/schema/migration/package/activation and runtime-parity states retain their existing unverified, not-performed or unobserved values. Exact-file/key/provider provenance remains unavailable. These are configuration-overlay semantics, not installation of a process environment or proof of host bootstrap/deployment behavior. Private correlation is removed from public rendering. A new lane-specific validator must refuse old-source, wrong-mode, stale-token, additional-field and readiness-promotion responses; the existing v1 validator remains closed.

Capture extends the existing source/input ownership rather than creating a second resolver: include the environment file in the supplied-input snapshot, make defensively owned copies, share one detached configuration for selection reconciliation and the actual EF preparer, and recheck all source/intent/private-input files before launch and after any result/refusal. Dispose invocation-owned buffers and roots, clear owned byte buffers where applicable, and reject disposed/reused private capture state; do not promise physical erasure of retained managed strings or constrain malicious trusted composer code. No additional persisted private copy is allowed. Source policy/enrollment and safe response state are constants verified at the actual host, never inferred from final values.

**Rationale.** These choices make the first actor slice implementable while preserving the existing ownership and transport budgets. The numeric byte arithmetic was independently reviewed: summing each file's base64 encoding differs by eight bytes from encoding their 4 MiB aggregate. The existing final serialized cap remains authoritative. The independent source review confirms the existing accept/edit flow is viable; the explicit-overlay divergence-to-recovery journey remains a future assigned proof, not evidence already executed.

**Alternatives considered.** A new worker envelope version, a second transport, a widened v1 candidate payload, hostname enrollment, unbounded/implicitly captured process inputs, or new accept semantics would add unnecessary compatibility or ownership mechanisms. Claiming numeric host-version support or observed deployment identity without evidence is rejected.

## Phase 0 disposition

No material architectural or product decision remains unresolved for this bounded first lane. Root accepts D1–D11 as planning choices under #2277's authorization. Phase 1 must turn them into exact contracts and an acceptance matrix, review ADR0076 D1/D4/D7's additive boundary extension and recheck the constitution. This disposition does not unblock production implementation: complete authoring, independent/root review, maps/diff and hosted delivery gates are still required. The eleven service-prefix families remain refused; supporting their expansions is separate future work. Existing projects and providers are reused, with no new permanent project, provider matrix or cadence; meaningful additions to existing fixtures remain required.

Independent Phase 0 audit identified the already-repaired D5 surrogate wording, command-specific old-field rejection (including explicit null), and the need for an exact loaded-host assembly seam. Root verified `HostClosure.LoadHostAssembly` currently returns void and selected an additive returning helper that preserves that public signature. Per-file base64 arithmetic, source order, ownership, response separation, service-prefix coverage and recovery boundaries otherwise agree with the audit. No future behavioral proof has run.

Phase 1 root and independent review clarified the implementation split without changing enrollment policy: `LoadHostAssemblyForInspection` only loads/name-and-location-checks the actual host. The worker resolves the selected persistence assembly, binds the new capability first, then uses `ToolingEntryPoint.ValidateCandidateEnvironmentEnrollment(Assembly, Assembly)` for metadata-only checks. Missing capability takes precedence over absent enrollment. The EF-owned host repeats equivalent metadata checks before configuration/composer construction and does not reference the CLI helper. The empty success example inherits Spec 187 semantics (`participants:[]`, `unresolved:[]`). All Phase 1 proof rows remain planned; no production behavior was tested during authoring.
