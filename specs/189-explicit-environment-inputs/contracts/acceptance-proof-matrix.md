# Acceptance and proof matrix

This matrix assigns every actor-facing requirement and success criterion to existing authoritative projects, fixtures, or source-backed journeys. Every row is **planned evidence**; no row is a passed implementation result in this planning artifact.

## Proof boundaries and harness

The public end-to-end harness is `tests/essentials/Cli/Tests/Elsa.Cli.Tests.csproj`, using `DotnetElsa.cs` to launch the public `Elsa.Cli.dll` in a separate process. The Workbench enrollment and public-wrapper proof must use the built output of `src/apps/Elsa.Workbench/Elsa.Workbench.csproj`; the existing fixture hosts are companion controls and cannot establish Workbench enrollment on their own.

The host-side contract and real EF-preparation parity use `tests/essentials/Persistence/EntityFrameworkCore/Migrations/Tests/Elsa.Persistence.EntityFrameworkCore.Migrations.Tests.csproj`, especially `tests/essentials/Persistence/EntityFrameworkCore/Migrations/Tests/EfCandidateInspectionTests.cs` and `tests/essentials/Persistence/EntityFrameworkCore/Migrations/Tests/EfToolingHostTests.cs`. CLI-side candidate/worker cases use the actual `tests/essentials/Cli/Tests/CandidateInspectionTests.cs` and related files. Planning/candidate acceptance uses `tests/essentials/Modularity/Planning/Tests/Elsa.Modularity.Planning.Tests.csproj`; architecture boundaries use `tests/essentials/Architecture/Elsa.Architecture.Tests.csproj`. The existing provider/database journey in `tests/essentials/Persistence/EntityFrameworkCore/CliAcceptance/ProviderTests/Elsa.Persistence.EntityFrameworkCore.CliAcceptance.ProviderTests.csproj` remains a separate already-proven persistence surface and must not be counted as proof that inspection accessed a database.

No new project, provider, permanent test cadence, or standalone ambient-environment matrix is proposed. New cases belong in these existing projects and fixtures.

## Numeric boundary cases

The implementation proof must include the exact admitted value and the first refused value where each is reachable under the closed shape; compound and redundant bounds are identified below:

- raw document: exactly 1 MiB and one byte over;
- each selected candidate file: exactly 1 MiB decoded and one byte over;
- selected candidate aggregate: exactly 4 MiB decoded and one byte over;
- each key: exactly 1,024 UTF-8 bytes raw and one byte over; also assert that normalized length is measured and cannot exceed the raw length under `__` replacement, documenting the unreachable “normalized longer than raw” combination rather than inventing an impossible input;
- each value: exactly 65,536 UTF-8 bytes and one byte over;
- entries: exactly 1,024 and 1,025;
- combined participant-plus-finding rows: baseline 1,022 participants plus 2 findings is accepted at 1,024; 1,023 participants plus 2 findings is refused at 1,025;
- selection IDs: existing 4,096-set boundary and one over;
- serialized worker request: exactly 8 MiB and one byte over after all base64/envelope metadata;
- host response: exactly 4 MiB and one byte over;
- JSON depth: existing depth 64 and one over;
- timeout option: existing 1 and 300 second endpoints plus invalid adjacent values.

With at most four selected files and a 1 MiB cap per file, the 4 MiB aggregate cap is redundant: a one-over aggregate specimen also violates a per-file or file-count guard. Record that compound refusal without claiming an independently valid aggregate-only input or a mutation proof of that redundant guard. Likewise, use existing valid selected-JSON cases for the depth-64 boundary; the explicit document and envelopes have shallow closed shapes, so nested invalid objects cannot be called valid exact-depth overlays.

The test must calculate encoded bytes before allocation and retain the final serialized request/response ceilings as authoritative. A per-part pass is not evidence that a combined maximum fits.

## Evidence discipline

The matrix is a plan-to-proof assignment, not a test report. Until implementation and gates run, every row remains unchecked. Root review must distinguish config-only inspection evidence, public Workbench closure evidence, old file-only compatibility evidence, and real database/provider persistence evidence. No skipped or fixture-only case may be reported as a passed end-to-end Workbench result.
