# User Tasks research — 2 November 2026

## Comparative evidence

Primary sources reviewed: [Camunda 8.8 lifecycle](https://docs.camunda.io/docs/8.8/apis-tools/frontend-development/task-applications/user-task-lifecycle/), [8.8 assignments and forms](https://docs.camunda.io/docs/8.8/components/modeler/bpmn/user-tasks/), and [task application layout](https://docs.camunda.io/docs/apis-tools/frontend-development/task-applications/introduction-to-task-applications/).

Camunda separates assignment from work state, permits self-claim and manager reassignment, and exposes lifecycle operations through an API. Candidate groups use stable IDs. Its task application pairs a work list with a form/detail view. Elsa adopts those interaction patterns, adds explicit named workflow outcomes, and keeps its initial lifecycle smaller: no pause/draft/reminder/SLA subsystem. Forms are pinned for a task; external form systems sit behind declared integrations. These are design choices, not assertions that Camunda guarantees Elsa's delivery semantics.

## Source assessment and decisions

1. **Runtime owns human work.** Existing `Elsa.Tasks` schedules host startup/background work, so do not put business tasks there. Add task contracts/models under `Essentials/src/Workflows/Runtime/Core/UserTasks/`, implementation under `Elsa.Workflows.Runtime/UserTasks/`, persistence to the existing Runtime EF family, API under Runtime API and an optional Studio module. No new root domain or provider stack.
2. **Typed native activity.** `Delay` demonstrates idempotent external staging before suspension. `StatefulActivity` and `ActivityTriggerRegistration<T>` retain typed private state/waits. Use a deterministic concrete-invocation task identity, with a non-actionable Staged state until the matching committed bookmark is observed. Same-invocation crash replay reuses it. Explicit boundary retries are successor invocations, with separate work only after old work retires; never retarget an accepted response.
3. **Journal plus reconciliation.** `RuntimeCheckpointCommit` has explicit participants and no generic extra-row hook. A separate CAS task aggregate is smaller than enlarging the entire checkpoint family. State, accepted response/delivery responsibility and history commit together. `BookmarkResumeDispatcher` durably queues a command but Dispatched/Duplicate does not establish task completion.
4. **Validate before consuming.** `ActivityResumeValidating` is Sequential before trigger claim/deletion. Validate the journal's immutable completion ID/payload and exact invocation/bookmark there. Transient reads throw `RuntimeSchedulerWorkUnavailableException`, preserving owed work. The existing `HumanReviewResumeGuard` is an independent example, not a runtime dependency on the Agent domain.
5. **Committed acknowledgement.** A fresh operation reads `IActivityExecutionStateStore`: Completed + matching invocation/outcome + canonical `ActivityCompletion.Result` equal to the accepted typed response establishes completion. Read inline or external values using `IExternalPayloadStore`. Private state is cleared, and `OnBookmarkConsumed` runs too early. Balanced coalescing requires a fresh external recovery scope after flush.
6. **Cancellation authority.** Check committed completion first, then explicit terminal execution, cancelled/faulted/superseded activity or sticky deletion tombstone. Missing rows/bookmarks alone are uncertain. Retain pending responsibility under uncertainty; do not label it successful or cancelled.
7. **Trusted eligibility.** `IdentityClaimTypes.UserId` is the persisted Elsa ID; generic subject claims may be external IDs. Normalize/validate the principal, reload active tenant user/membership and current role IDs, verify roles exist, and use current-subject permission authorization. Unsupported authority fails closed. API-supplied actor/groups/tenant are never authoritative. Reassignment validates destination in the same tenant.
8. **Forms.** Basic provider supports a closed typed field set and server validation. Immutable form versions and task snapshots preserve authored rules; prefill is evaluated workflow input. An explicit `IUserTaskFormProvider` identifies provider/version, materializes a safe display definition and validates responses. Duplicate/missing provider ownership refuses. A custom integration witness must actually validate and render, not just register an interface.
9. **Outcome authoring.** `ActivityValueOutcomesAttribute`, CLR scanner and executable compiler already pin literal collection outcomes. Studio `workflowAdapter.ts/getActivitySourcePorts` does not consume `dynamicOutcomes.valuePerItem`; extend this generically with literal-only parsing and parity tests.
10. **BPMN reuse.** Existing direct BPMN claim commands lack full release/reassignment/form response semantics. Bind a published native workflow containing Create User Task through `BpmnNativeServiceBinding`, using the existing service-child lifecycle. Do not fork human-task state or change BPMN token semantics.
11. **Studio composition.** Optional module under `Extensions/UserTasks/studio/Elsa.Studio.UserTasks`. Shared module UI, capabilities, permissions and property-editor contributions; no imports from private Workflows code. `HumanReviewPage.tsx` provides stable request ID, pending/conflict and stale-refresh patterns. An assignment-target endpoint avoids requiring identity-administrator permissions for task authors.

## Rejected shortcuts

In-memory-only acceptance; trusting cookie roles after revocation; caller-supplied tenant or actor; completion marked when queued; bookmark absence treated as completion; validating only inside ResumeAsync; rereading mutable form drafts for open tasks; external HTML/scripts embedded in Studio; a second BPMN human lifecycle. None is an acceptable substitute for the qualification matrix.

## Review corrections

Physical wait replacement requires a captured `StimulusResumeRecipient` and provider-enforced `ExpectedBookmarkResume` at initial consumption, not only a bookmark ID or a guard-time observation. Extend the dispatch request narrowly and preserve saved-source authority. A nonterminal task also retains its owning execution/activity completion evidence through a provider deletion fence, so a crash before acknowledgement cannot erase a completed response. These are mandatory tests before delivery acceptance.
