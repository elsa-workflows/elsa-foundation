# Feature Specification: Activity Identity & Catalog as Source-of-Truth

**Feature Branch**: `001-activity-identity-catalog`
**Created**: 2026-05-27
**Status**: Draft
**Input**: User description: Unit B of the Elsa entity-design refactor. Decouple activity identity from CLR types (Sipke 2026-05-26 item 1) and pin the activity catalog as the single source-of-truth for picker visibility (Sipke item 7). Works against constitution v2.0.0 (draft).

## Clarifications

### Session 2026-05-27 (second pass)

- Q: `ArgumentState` — where does it live, what does it carry, and what's the distinction between the factory's `inputs` and `outputs` parameters? → A: `ArgumentState` is a **design-time filled-in canvas** for an `ArgumentDefinition` (not a runtime value). It carries `ReferenceKey` (FK to the `ArgumentDefinition.ReferenceKey`) and an `ArgumentValue` value object (`{ object? Value, ExpressionType ExpressionType }`). At construction time the factory transforms each `ArgumentState` into a runtime `IExpression` and sets the corresponding `Input` / `Output` property on the produced `IActivity`. Two derived sealed records carry the same shape but distinct types: `InputState : ArgumentState` and `OutputState : ArgumentState`. The factory signature is **`Create(IImplementationDescriptor, IEnumerable<InputState>, IEnumerable<OutputState>, CancellationToken)`** — distinct types prevent accidentally swapping inputs / outputs at the call site. Lives in `Elsa.Activities.Design.Core.Models` alongside `ArgumentDefinition` (the canvas template). The slight naming tension (Activities.Design.Core hosting a model that's also consumed at runtime) is acknowledged; this is consistent with how `ArgumentDefinition` itself is already shared across design and runtime consumers, and is left as-is for Unit B.
- Q: Provisioning module — keep `.Provisioning.*` naming, or rename? Who supplies the immutable creation provenance fields, and what's the seed concrete source? → A: **Rename `Elsa.Activities.Design.Provisioning.*` → `Elsa.Activities.Design.Reconciliation.*`** (module + feature). The verb "to provision" stays on the *field* names (`ProvisionedAt`, `ProvisionedBy`, `LastProvisionedAt`, `LastProvisionedBy`, `ProvisioningHash` — they describe the moment / artefact of a provisioning operation) but the *module* is named for the higher-level idempotent-reconciliation lifecycle (per Sipke item 6). Service rename follows: `IActivityVersionProvisioner` → `IActivityVersionReconciler`; domain event rename: `OnActivityVersionsProvisioning` → `OnActivityVersionsReconciling`. The reconciliation source supplies `SourceKind`, `SourceId`, `ProvisionedAt`, `ProvisionedBy` on the contributed `IActivityDefinitionVersion.Definition` — the source *knows* its own identity. The reconciler invokes a new `IActivityDefinitionHasher` interface (in `Reconciliation.Core`, default implementation in the feature) to compute `ProvisioningHash` and writes the reconciliation-state row. **Seed source for Unit B:** a JSON-file reconciler reading from a file like `elsa-core-activities.json`: `SourceKind = SourceKind.Json`, `SourceId = <assembly name from the JSON entry>`, `ProvisionedBy = Environment.MachineName`.
- Q: Who owns the `OnEntitySaving` / `OnEntityModelCreating` event type definitions? → A: Unit B introduces them, in the appropriate persistence module (`Elsa.Persistence.Core` for the type declarations; instrumentation in `Elsa.Persistence.EFCore` / `ElsaDbContextBase`). The events are the natural complement to Unit B's fold-in of the activity-catalog handler migration (FR-017). Other features' handler migrations from `IGlobalEntitySavingHandler` / `IEntityModelCreatingHandler` happen later (remainder of Unit A's open code-checklist item), but inherit ready-to-use event types defined by Unit B.
- Q: `IArgumentDefinition` interface — retire, keep, or defer? → A: Retire. The sealed `ArgumentDefinition` record is the read contract; consumers reference the record directly. Eliminates the interface-record duality. Same call as for `InputDefinition` / `OutputDefinition` / `ActivityDesignFacet` (no read-only siblings introduced).

### Session 2026-05-27 (third pass — post-tasks)

- Q: `IEntityModelCreatingHandler` — migrate to `OnEntityModelCreating` event, or keep as-is? → A: **Keep as-is.** Model-creating is a sync side-effect chain on `ModelBuilder` — each handler customizes the shared builder; nothing flows back to a sender. Framework §2.6.1 prescribes async domain events for *contribution flows* (where handlers contribute data the sender collects). Model-creating is structurally different and the existing provider-interface pattern in `ElsaDbContextBase.ApplyEntityModelCreatingHandlers` is the right tool. No `OnEntityModelCreating` event is introduced. Only `OnEntitySaving` migrates; `IEntityModelCreatingHandler` survives unchanged.
- Q: Storage of `IImplementationDescriptor` — custom polymorphic JsonConverter, or explicit registry + reflection-driven deserialise? → A: **Explicit `IImplementationDescriptorRegistry` following the canonical §2.6.1 Registry + StartUp Task sub-pattern** (revised at session 4 below). The loading handler resolves the descriptor's CLR type from the registry by `ImplementationKind`, then calls `IPayloadSerializer.Deserialize(json, type)` via reflection-constructed generic method invocation. No custom `JsonConverter`.
- Q: Entity surface — `[NotMapped] ImplementationDescriptor` rich property + separate `*Source` string column, or shadow column with same name? → A: **Shadow column with same name.** `ActivityDefinitionVersion` exposes one CLR property: `[NotMapped] IImplementationDescriptor ImplementationDescriptor`. The persisted form is an EF Core *shadow column* named `ImplementationDescriptor` (string), accessed only via `EntityEntry.Property("ImplementationDescriptor")` in handlers. No `*Source` suffix; one name on the entity surface. The descriptor's runtime CLR type IS the kind binding — the rich projection inherently carries the kind information.
- Q: Hasher canonicalisation — native .NET or third-party library (JCS / RFC 8785)? → A: **Native .NET only.** Use `System.Text.Json` with a `JsonTypeInfoResolver` whose modifier sorts properties alphabetically by name (ordinal). Serialise the (definition + version) tuple with the resolver; SHA-256 over the resulting bytes. The default `IActivityDefinitionHasher` implementation in `Elsa.Activities.Design.Reconciliation` uses this. Stable across structurally-equivalent inputs that differ only in property order.

### Session 2026-05-27 (fourth pass — descriptor type registry)

- Q: How does the EF loading handler know which CLR type to deserialise the descriptor payload into? Derive from the resolver registry's generic argument (reflection over `IActivityImplementationResolver<TDescriptor>`), or use an explicit dedicated registry? → A: **Explicit dedicated registry** following the canonical §2.6.1 Registry + StartUp Task sub-pattern (worked example: Elsa §E3.3). Specifically:
   1. **`IImplementationDescriptorRegistry`** lives in `Elsa.Activities.Design.Core` with `void Register(ImplementationDescriptorRegistration registration)`, `void RegisterAll(IEnumerable<ImplementationDescriptorRegistration> registrations)`, and `Type? Resolve(ImplementationKind kind)` methods. A thin default implementation `ImplementationDescriptorRegistry` (dictionary-backed) ships in the same `.Core`.
   2. **`ImplementationDescriptorRegistration(ImplementationKind Kind, Type DescriptorType)`** is a sealed record carrying one registry entry.
   3. **`OnImplementationDescriptorsInitializing(ICollection<ImplementationDescriptorRegistration> Registrations) : IDomainEvent`** is the contribution event, also in `Elsa.Activities.Design.Core`.
   4. **`ImplementationDescriptorRegistryStartupTask`** in the activities runtime feature publishes the event and flushes contributions into the registry.
   5. The activities runtime feature handles its own event to register `new ImplementationDescriptorRegistration(ImplementationKind.Clr, typeof(ClrImplementationDescriptor))`. Unit G will register the `Workflow` mapping from its bridge module; future features register their kinds analogously.
   6. The EF loading handler consumes `IImplementationDescriptorRegistry.Resolve(entity.ImplementationKind)` → CLR type, then `IPayloadSerializer.Deserialize(json, type)`.

   Why explicit: the registry concern (kind → CLR type) is semantically distinct from the resolver concern (descriptor → IActivity). Deriving one from the other via reflection muddles two registries' lifecycles and surfaces. Symmetric application of the same §2.6.1 pattern keeps each registry's contract clear: own contract, own event, own startup task.

### Session 2026-05-27

- Q: Storage shape of `ImplementationDescriptor` in EF Core — JSON column with discriminator, per-kind tables, or hybrid? → A: Single shadow-JSON column on `ActivityDefinitionVersion` with the `ImplementationKind` discriminator driving polymorphic deserialisation. *(Revised in sessions 3 + 4: shadow column is named `ImplementationDescriptor` — no `*Source` suffix; deserialisation goes through `IImplementationDescriptorRegistry` per the §2.6.1 Registry + StartUp Task pattern, not a custom `JsonConverter`. See later session entries.)*
- Q: `ActivityTypeKey` vs `UniqueName` — same field or two distinct fields? → A: Same field. The current `UniqueName` column / property is renamed to `ActivityTypeKey` (one immutable column carrying the stable logical key). The `UniqueName` term is retired throughout this spec and the code in favour of `ActivityTypeKey`.
- Q: Concrete shape of the open discriminators (`ImplementationKind`, `SourceKind`) — plain string, smart-enum value-record, or extensible attribute-enum? → A: Smart-enum value-record. `public sealed record ImplementationKind(string Value) { public static readonly ImplementationKind Clr = new("Clr"); public static readonly ImplementationKind Workflow = new("Workflow"); }`. Persisted as the string `Value`; consumed as the typed wrapper. Same pattern applies to `SourceKind`. Compile-time safety for known kinds; open for new kinds via `new ImplementationKind("...")`.
- Q: Uniqueness on `(SourceKind, SourceId)` — globally unique, no constraint, or composite-with-`ActivityTypeKey`? → A: Composite uniqueness on `(SourceKind, SourceId, ActivityTypeKey)`, plus a non-unique lookup index on `(SourceKind, SourceId)` for the "what did this source produce?" reconciler query. Works for 1:N sources (CLR scanner, package manifest — one `SourceId` like an assembly can produce many `ActivityTypeKey`s) and for 1:1 sources (workflow, script).
- Q: Is the runtime `IActivityResolver` registry in Unit B's scope? → A: Yes — but split into two interfaces (revised mid-session). `IActivityFactory` is the dispatch + construction entry point (`ValueTask<IActivity> Create(IImplementationDescriptor descriptor, IEnumerable<ArgumentState> inputs, IEnumerable<ArgumentState> outputs, CancellationToken ct)`). `IActivityImplementationResolver<TDescriptor>` (kind-typed) declares `string Kind { get; }` and `Type Resolve(TDescriptor descriptor)` — its only responsibility is to return the CLR `Type` that backs the descriptor. The factory uses the resolver to obtain the `Type` and constructs the `IActivity` instance with the provided argument state. Resolvers are contributed via `IDomainEventSender` per framework §2.6.1 (Registry + StartUp Task sub-pattern). Unit B ships the CLR resolver as the seed; non-CLR resolvers (Workflow → Unit G; Remote / Script / … per consuming unit) plug into the same registry.
- Q: `ImplementationDescriptor` — abstract class or interface? → A: Interface (`IImplementationDescriptor`). `TypeInformation` stays a pure primitive value object in `Elsa.Primitives`. A new `ClrImplementationDescriptor` in `Elsa.Activities.Design.Core` implements `IImplementationDescriptor` and wraps `TypeInformation` as the payload for `ImplementationKind.Clr`.
- Q: `IsBrowsable` — keep as coarse default, or remove and rely on policy layer? → A: Remove entirely. Catalog row existence IS the picker visibility signal in Unit B. The context-aware visibility policy (deferred) is the only mechanism for "hide from this user / context" semantics. To hide an activity, remove it from the catalog (hard delete or `RemovedAt` on the reconciliation-state sibling). The picker shows every catalog row whose reconciliation state does not mark it removed.
- Q: `TenantId` index — declare per-entity or centralize? → A: Centralize. `ElsaDbContextBase.OnModelCreating` MUST scan entities inheriting from `TenantEntity` and declare the `TenantId` index automatically — same centralization pattern as the existing immutability enforcement. No per-entity index declarations.
- Q: Index on `ActivityDefinitionReconciliationState.IsStale`? → A: Yes. Needed for the reconciler's stale-removal sweep. (Index on `ImplementationKind` is NOT needed for Unit B.)
- Q: Read-only sibling interfaces for `InputDefinition` / `OutputDefinition` / `ActivityDesignFacet`? → A: No. These become `public sealed record`s — structurally immutable. No interface needed; structural immutability is enough.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Logical activity identity survives normal refactors (Priority: P1)

A workflow designer placed a `Elsa.Http.SendRequest` activity in a workflow definition six months ago. Since then, the implementation team has renamed the CLR type, moved it to a different namespace, and repackaged the assembly. The workflow definition still references the same logical activity, and the designer can still open, edit, and execute it without any data fix-up.

**Why this priority**: This is the load-bearing reason Unit B exists. The current model ties the durable identity of an activity to its CLR `TypeInformation`, which makes routine refactors data-breaking events. Every other goal in this spec is downstream of fixing this.

**Independent Test**: Persist an activity definition, then change the CLR type's namespace/assembly identity in code, then re-run provisioning. The stored row remains resolvable by its logical key; no foreign key from a consuming workflow needs to be rewritten. Verified by a test that mutates a stored `ImplementationDescriptor` (CLR form) while leaving the `ActivityTypeKey` intact and demonstrating that consumer-side resolution still succeeds.

**Acceptance Scenarios**:

1. **Given** an `ActivityDefinition` row with `ActivityTypeKey = "Elsa.Http.SendRequest"` and a CLR `ImplementationDescriptor` pointing at type `Foo.SendRequest` in assembly `Foo`, **When** the descriptor is updated to point at `Bar.SendRequest` in assembly `Bar` (same logical activity, refactored CLR layout), **Then** the `ActivityTypeKey` remains stable and any consumer that resolved the activity by key continues to resolve it.
2. **Given** a workflow definition that references an activity by `ActivityTypeKey`, **When** the catalog row's descriptor is updated as above, **Then** the workflow definition does not require a data migration.
3. **Given** an activity catalog row with `ImplementationKind = Clr`, **When** code attempts to set the `ActivityTypeKey` on the parent `ActivityDefinition` to a new value after creation, **Then** the change is rejected by the immutability mechanism (catalog identity is stable).

### User Story 2 — The picker shows exactly what the catalog contains (Priority: P1)

A workflow designer opens the activity picker. The list of activities shown is exactly the set of `ActivityDefinition` rows in the catalog whose reconciliation-state sibling does not mark them removed. No background process inspects loaded CLR assemblies, scans plugin directories, or queries live providers to populate the picker. Adding a row makes it visible; removing it (hard delete, or `RemovedAt` set by the reconciler) hides it.

**Why this priority**: This is the second load-bearing rule. Today the picker can drift from the catalog because live providers can surface activities the catalog does not know about. The rule "if it is in the picker, it has a catalog row" is the precondition for tenant filtering, indexing, large-catalog support, and reproducible designer behaviour across deployments.

**Independent Test**: Insert / delete a row directly into the activity catalog store and confirm the picker's response changes accordingly without re-running provisioning or restarting the host. Confirm that a CLR activity type that has *not* been provisioned into the catalog does NOT appear in the picker, even when its CLR assembly is loaded into the process.

**Acceptance Scenarios**:

1. **Given** a CLR activity type that is loaded into the host process but has no `ActivityDefinition` row, **When** a designer opens the picker, **Then** the activity does NOT appear.
2. **Given** an `ActivityDefinition` row whose reconciliation-state sibling is absent or does NOT mark it removed, **When** the picker is queried, **Then** the row appears.
3. **Given** an `ActivityDefinition` row whose `ActivityDefinitionReconciliationState.RemovedAt` is set, **When** the picker is queried, **Then** the row does NOT appear.
4. **Given** an `ActivityDefinition` row whose `ImplementationKind` is non-CLR (e.g. Workflow), **When** the picker is queried, **Then** the row appears alongside CLR rows with no distinction in visibility behaviour.

### User Story 3 — Non-CLR activities are first-class catalog entries (Priority: P1)

A workflow author exposes a published workflow version as an activity. The mechanism that performs the exposure writes an `ActivityDefinition` row whose `ImplementationKind = Workflow` and whose `ImplementationDescriptor` carries the workflow definition + version identifiers. From that point on, the workflow appears in the picker, can be selected from other workflows, and is executed through the same runtime activity contract as any CLR activity.

**Why this priority**: This is the catalog's reason for being polymorphic. Without it, the descriptor abstraction is theoretical; with it, workflow-as-activity (Unit G) and future kinds (JavaScript, Remote, Script, Host method, Package-manifest) all become straight rows in the catalog rather than special-case branches in the picker code.

**Independent Test**: Construct and persist an `ActivityDefinitionVersion` with `ImplementationKind = Workflow`, read it back through the design-domain interfaces, and confirm that the loaded value carries a structurally-correct non-CLR descriptor. Unit B does NOT ship the bridge module that actually creates such rows from a workflow version — that is Unit G.

**Acceptance Scenarios**:

1. **Given** an `ActivityDefinitionVersion` written with `ImplementationKind = Workflow` and a workflow-shaped `ImplementationDescriptor`, **When** the row is loaded through the design-domain interfaces, **Then** the descriptor round-trips structurally and the `ImplementationKind` is preserved.
2. **Given** the catalog contains rows of mixed `ImplementationKind`, **When** the picker enumerates the catalog, **Then** all rows are returned with no kind-specific filtering at the catalog query layer.
3. **Given** the codebase does NOT include the workflow-as-activity bridge module (Unit G), **When** a non-CLR row is constructed directly in a test, **Then** it persists and re-loads cleanly. (Unit B proves the schema is correct; Unit G ships the bridge.)

### User Story 4 — Provisioning carries provenance + reconciliation state, split across two entities (Priority: P2)

When an activity source provisions a row into the catalog, the **immutable creation provenance** (which source produced it, when, by whom) is recorded on the catalog row itself and never changes. The **operational reconciliation state** (which source-side version was last seen, what its hash was, when it was last touched, whether it has gone stale) lives on a sibling entity `ActivityDefinitionReconciliationState` with a 1:0..1 relationship to `ActivityDefinition`. Unit F (later) uses the reconciliation-state row to drive idempotent reconciliation, drift detection, conflict resolution, and stale-row removal. Unit B adds the storage shape (both entities) and exposes them through dedicated read contracts; Unit F refines the lifecycle behaviour that *uses* the reconciliation-state row.

**Why this priority**: Adding provenance + reconciliation state later is a schema change that ripples through migrations, EF mappings, interfaces, and DTOs. Adding them now — while the entity is already being reshaped — is the cheap move. Splitting them across two entities now (rather than one fat row) protects Sipke item 9 / framework §2.9's persistence-only-churn argument: reconciliation churn must not cascade through `IActivityDefinition`'s consumers.

**Independent Test**: Write a row through the reconciliation path, read it back, confirm the immutable creation provenance is populated on `ActivityDefinition` *and* the operational reconciliation fields are populated on `ActivityDefinitionReconciliationState`. Confirm a row created outside the reconciliation path (admin API / test) has *no* reconciliation-state sibling. Unit B does not assert specific reconciliation behaviour (drift detection, stale removal) — those tests land with Unit F.

**Acceptance Scenarios**:

1. **Given** a provisioning operation writes a new `ActivityDefinition`, **When** the row is read back, **Then** `SourceKind`, `SourceId`, `ProvisionedAt`, `ProvisionedBy` are populated on `ActivityDefinition` and are immutable.
2. **Given** a provisioning operation re-runs against an existing row, **When** the reconciliation-state sibling is updated, **Then** `LastSeenAt` is refreshed and `ProvisioningHash` reflects the latest projection — and `ActivityDefinition`'s own row is NOT rewritten unless its own (identity / display) fields changed.
3. **Given** the design-domain read contract `IActivityDefinition`, **When** a consumer reads it, **Then** operational reconciliation fields are NOT visible on it; they are reachable only through the separate `IActivityDefinitionReconciliationState` read contract.
4. **Given** an `ActivityDefinition` row created via the admin API rather than through provisioning, **When** the row is queried, **Then** it has no `ActivityDefinitionReconciliationState` sibling (the 1:0..1 relationship permits absence).

**Independent Test**: Run the existing saving handler tests (per framework §2.21.1 golden rule). Confirm they pass without changes to the test cases themselves. Confirm the activity-catalog saving handler is registered as an `IDomainEventHandler<OnEntitySaving>` (not a provider-interface instance) by inspecting the feature class registrations.

2. **Given** the activity catalog feature class, **When** the feature is registered, **Then** the saving / loading behaviour is wired through `OnEntitySaving` event handlers, not through `IGlobalEntitySavingHandler` / `IEntitySavingHandler<,>`.

### Edge Cases

- **A consumer asks for a CLR activity that loaded into the process but was never provisioned.** The catalog returns nothing; the picker does not show it; the runtime refuses to instantiate it through the activity contract. The CLR type may still be invoked through code paths that bypass the catalog, but the design-time surface ignores it.
- **A provisioning source produces a row whose `ActivityTypeKey` collides with an existing row of a different `SourceKind`.** Conflict resolution policy is Unit F's responsibility. Unit B records both rows (or throws — exact semantics deferred) and surfaces the collision through the `SourceKind` + `SourceId` provenance fields so Unit F has the data it needs to decide.
- **An `ImplementationDescriptor` is loaded for an `ImplementationKind` the current process does not recognise.** The row still loads (the descriptor is a structured payload). Attempts to *execute* such an activity fail through a runtime path — but cataloguing and reading remain unaffected. (This preserves the §E2.6.1 executable-always-runs contract for the kinds the process *does* recognise, and treats unknown kinds as a domain gate, not a system failure.)
- **A descriptor's stored payload diverges from the `ImplementationKind` enum value** (e.g. row says `Workflow`, payload structurally looks like `Clr`). Treated as a data-integrity failure surfaced at load time. Concrete diagnostic: schema validation on the descriptor against the declared kind.
- **A picker query against a tenant-scoped catalog returns rows for the wrong tenant.** Out of scope for Unit B. The catalog has a `TenantId` (inherited from `Entity`); a context-aware visibility layer (deferred) will use it. Unit B's queries are tenant-agnostic.
- **A previously-persisted CLR descriptor refers to a CLR type whose assembly is no longer loaded.** The catalog row loads (descriptor is a value payload). Attempts to instantiate the implementation fail through a runtime path; the design-side surface continues to function.

## Requirements *(mandatory)*

> **2026-06-11 design-domain cleanup:** `IActivityDefinitionVersion.Ports` and the core `ActivityPortDefinition` model were superseded by `DesignFacets`. Flowchart ports/connections, StateMachine transitions/triggers, and custom visual design shapes are module-owned facet payloads, not core activity catalog fields.

### Functional Requirements

**Identity, provenance & schema**

- **FR-001**: `ActivityDefinition` MUST expose a stable logical identity `ActivityTypeKey` (renamed from the current `UniqueName`) that is immutable after creation. One field, not two.
- **FR-002**: `ActivityDefinition` MUST expose **immutable creation provenance** — `SourceKind`, `SourceId`, `ProvisionedAt`, `ProvisionedBy`. These fields are immutable after creation and answer *"where did this catalog row come from?"* They are part of the catalog row's identity. The composite `(SourceKind, SourceId, ActivityTypeKey)` MUST be globally unique across catalog rows; `(SourceKind, SourceId)` MUST be a non-unique lookup index for the reconciler's "what did this source produce?" query and for the stale-removal pass.
- **FR-003**: **Operational reconciliation state** (`SourceVersion`, `ProvisioningHash`, `LastSeenAt`, `LastProvisionedAt`, `LastProvisionedBy`, `IsStale`, `RemovedAt`) MUST live on a sibling entity `ActivityDefinitionReconciliationState` with a 1:0..1 relationship to `ActivityDefinition`. Catalog rows created outside the provisioning path (admin API, tests) MAY have no reconciliation-state row. This split protects the catalog read contract from churning every reconciliation pass (Sipke item 9 / framework §2.9 persistence-only-churn argument).
- **FR-004**: `ActivityDefinition` MUST NOT carry CLR-binding fields on the parent entity. CLR binding is descriptor-side, version-side.
- **FR-005**: `ActivityDefinitionVersion` MUST carry `Version`, `ActivityTypeKey`, `ImplementationKind`, and a polymorphic `IImplementationDescriptor` (concrete subtype determined by `ImplementationKind`). `Version`, `ActivityTypeKey`, and `ImplementationKind` MUST be immutable per existing immutability mechanism.
- **FR-006**: `ImplementationKind` and `SourceKind` MUST be **smart-enum value-records** — sealed records wrapping a `string Value`, with `static readonly` instances declared for the known kinds. Persisted to the database as the string `Value`. Consumed in code as the typed wrapper. Equality is value-based on the wrapped string. Adding a new kind is `new ImplementationKind("X")` (or a `static readonly` declaration in the relevant `.Core`) — no schema change, no enum-numeric reservation. Unit B ships at minimum `ImplementationKind.Clr`, `ImplementationKind.Workflow`, and at least one `SourceKind` matching the current provisioner's source. The set is open.
- **FR-007**: An `IImplementationDescriptor` **interface** MUST be defined as the polymorphic input contract for activity construction. Concrete descriptor types implement `IImplementationDescriptor` and are paired with an `ImplementationKind`. `TypeInformation` (in `Elsa.Primitives`) MUST remain a pure value object; a new `ClrImplementationDescriptor` (in `Elsa.Activities.Design.Core`) MUST implement `IImplementationDescriptor` and wrap `TypeInformation` as the payload for `ImplementationKind.Clr`. At least one non-CLR descriptor (`WorkflowImplementationDescriptor`-style: workflow definition id + version id) MUST be defined and round-trip through the store. **Storage:** `ActivityDefinitionVersion` exposes a `[NotMapped] IImplementationDescriptor ImplementationDescriptor` CLR property — the combined rich projection (descriptor's runtime type IS the kind binding). The persisted form is an **EF Core shadow column** named `ImplementationDescriptor` (string, JSON-serialised descriptor payload), accessed via `EntityEntry.Property("ImplementationDescriptor")`. The loading handler hydrates the rich projection by (a) reading `ImplementationKind`, (b) resolving the matching CLR descriptor type from `IImplementationDescriptorRegistry` (per FR-027), (c) reading the shadow column string, (d) calling `IPayloadSerializer.Deserialize(json, type)` via reflection-constructed generic method invocation. The saving handler serialises the rich projection back to the shadow column via `IPayloadSerializer`. No custom `JsonConverter` required.
- **FR-027**: An `IImplementationDescriptorRegistry` MUST be defined in `Elsa.Activities.Design.Core` following the canonical §2.6.1 Registry + StartUp Task sub-pattern (worked example: Elsa §E3.3). ### Key Entities

**Provenance vs. execution-binding — two orthogonal axes.** Every catalog row answers two independent questions:

| Axis | Question | Fields |
|---|---|---|
| Provenance | *Where did this catalog row come from?* | `SourceKind`, `SourceId` on `ActivityDefinition` (immutable creation provenance); reconciliation-state sibling for the operational tail. |
| Execution binding | *How do we run this activity?* | `ImplementationKind`, `IImplementationDescriptor` on `ActivityDefinitionVersion`. |

They are often correlated (a `SourceKind=Workflow` row typically has `ImplementationKind=Workflow`), but they are not the same axis. A CLR activity discovered by reflection and the same activity declared in a package manifest share an `ImplementationKind=Clr` descriptor but differ on `SourceKind`. The split lets us reason about reconciliation (provenance-axis concern) and execution (binding-axis concern) independently.

- **ActivityDefinition** *(catalog parent — identity layer)*. Stable logical identity `ActivityTypeKey` (immutable, renamed from the previous `UniqueName`); **immutable creation provenance** (`SourceKind`, `SourceId`, `ProvisionedAt`, `ProvisionedBy`); display metadata (`Category`, `DisplayName`, `Description`). No CLR-binding fields. No `IsBrowsable` column — picker visibility is determined by catalog row presence + the reconciliation-state sibling's `RemovedAt` field. Inherits `Id` from `Entity` and `TenantId` from `TenantEntity`. Operational reconciliation fields live on the sibling — see `ActivityDefinitionReconciliationState`.
- **ActivityDefinitionVersion** *(catalog child, append-only)*. Immutable per existing mechanism. Carries `Version`, `ActivityTypeKey`, `DefinitionId`, `ImplementationKind`, `Kind` (Action / Trigger / Job / Task), the existing JSON-backed `InputsSource` / `OutputsSource` / `DesignFacetsSource` columns with their `[NotMapped]` projections (`IEnumerable<InputDefinition>` / `OutputDefinition` / `ActivityDesignFacet`), and a `[NotMapped] IImplementationDescriptor ImplementationDescriptor` rich property combined with an **EF Core shadow column** named `ImplementationDescriptor` (string, JSON payload) — hydrated by the loading handler via `IPayloadSerializer.Deserialize(json, typeFromKind)` and serialised back by the saving handler. The shadow column is configured as immutable via `PropertySaveBehavior.Throw` at model-creating time. Inherits `TenantId` from `TenantEntity`.
- **ActivityDefinitionReconciliationState** *(catalog sibling — operational layer; 1:0..1 with `ActivityDefinition`)*. Carries `SourceVersion` (most-recently-seen source-side version), `ProvisioningHash`, `LastSeenAt`, `LastProvisionedAt`, `LastProvisionedBy`, `IsStale`, `RemovedAt`. Read/written by Unit F's reconciler and audit endpoints. Same DbContext as `ActivityDefinition`; same transaction; FK back to the catalog row. Rows that never went through the provisioning path (admin API, tests) have no reconciliation-state sibling.
- **ImplementationKind** *(smart-enum value-record)*. `public sealed record ImplementationKind(string Value)` with `static readonly` instances for known kinds. Unit B ships `ImplementationKind.Clr` and `ImplementationKind.Workflow`; additional kinds (`JavaScript`, `Remote`, `Script`, `HostMethod`, `PackageManifest`, …) are added as new `static readonly` declarations (or constructed inline by downstream consumers) — no schema change required. Persisted as the wrapped string; equality is value-based.
- **SourceKind** *(smart-enum value-record)*. Same shape as `ImplementationKind` — `public sealed record SourceKind(string Value)` with `static readonly` instances for known sources. Identifies the **type of source** that produced the catalog row (e.g. `SourceKind.ClrDiscovery`, `SourceKind.Workflow`, `SourceKind.Script`, `SourceKind.PackageManifest`, `SourceKind.Remote`, `SourceKind.TenantScript`, `SourceKind.System`). Composed with `SourceId` to form the source-identity composite used by reconciliation.
- **IImplementationDescriptor** *(polymorphic input-contract interface, in `Elsa.Activities.Design.Core`)*. The base interface for all kind-specific descriptors. Implementations carry the binding payload that allows the matching resolver to return a CLR `Type` (and, downstream, allows the factory to construct an `IActivity`). Payloads by kind: `ClrImplementationDescriptor` wraps `TypeInformation` (`TypeName`, `Namespace`, `AssemblyName`, `AssemblyVersion`); `WorkflowImplementationDescriptor` carries workflow definition id + version id; `RemoteImplementationDescriptor` carries connector id + operation id; `ScriptImplementationDescriptor` carries script id + engine + entrypoint. Different payloads; one interface; one factory entry point.
- **ClrImplementationDescriptor** *(seed concrete descriptor, in `Elsa.Activities.Design.Core`)*. Implements `IImplementationDescriptor`, wraps a `TypeInformation` value object as the payload. `TypeInformation` itself stays in `Elsa.Primitives` as a pure value object — the descriptor concept is an Activities-domain construct that *uses* `TypeInformation`, not a property of `TypeInformation` itself.
- **IActivityFactory** *(dispatch + construction entry point)*. Single method: `ValueTask<IActivity> Create(IImplementationDescriptor descriptor, IEnumerable<InputState> inputs, IEnumerable<OutputState> outputs, CancellationToken ct)`. The factory inspects the descriptor's kind, dispatches to the matching `IActivityImplementationResolver` to obtain a CLR `Type`, instantiates the type (via DI / activation), transforms each `InputState` / `OutputState` into a runtime `IExpression`, sets the corresponding `Input` / `Output` properties on the produced `IActivity`, and returns the instance ready for the runtime middleware pipeline. The distinct `InputState` / `OutputState` types in the signature prevent accidental swapping. Unknown-kind lookups fail through a runtime / domain path, not a system path (Elsa §E2.6.1).
- **IActivityImplementationResolver\<TDescriptor\>** *(kind-specific type resolution, `TDescriptor : class, IImplementationDescriptor`)*. Two members: `string Kind { get; }` (matches the discriminator) and `Type Resolve(TDescriptor descriptor)` (returns the CLR `Type` that backs this kind of descriptor). The resolver's *only* job is mapping descriptor → CLR `Type`; instantiation and argument-state population are the factory's job. One implementation per `ImplementationKind`. Contributed via `IDomainEventSender` per framework §2.6.1 (Registry + StartUp Task sub-pattern): a startup task publishes a domain event whose payload is `List<IActivityImplementationResolver>`; features handle the event to add their resolvers; `IActivityFactory` reads the populated registry at construction time. Unit B ships the CLR resolver; non-CLR resolvers plug into the same registry without modifying Unit B.
- **InputDefinition / OutputDefinition / ActivityDesignFacet / ArgumentDefinition** *(sealed records in `Elsa.Activities.Design.Core.Models`)*. Structurally immutable; no separate read-only sibling interface. The records' immutability is the read-contract guarantee. The existing `IArgumentDefinition` interface is retired — consumers reference the `ArgumentDefinition` record directly.
- **ArgumentState / InputState / OutputState** *(filled-in canvas, in `Elsa.Activities.Design.Core.Models`)*. `ArgumentState` is a base `public record` with `string ReferenceKey` and `ArgumentValue Value`. `InputState : ArgumentState` and `OutputState : ArgumentState` are sealed derived records carrying the same shape; the distinct types make the `IActivityFactory.Create(...)` signature type-safe (inputs / outputs cannot be swapped at the call site). `ArgumentState` represents the design-time configured value for an `ArgumentDefinition` — not a runtime value — and is transformed by the factory into a runtime `IExpression` at construction time.
- **ArgumentValue** *(sealed record, in `Elsa.Activities.Design.Core.Models`)*. Carries `object? Value` (the literal value or expression source) and an `ExpressionType` discriminator (smart-enum value-record per the §FR-006 pattern: `ExpressionType.Literal`, `ExpressionType.JavaScript`, `ExpressionType.Liquid`, …). Open discriminator; new expression types can be added without schema change.
- **IActivityDefinitionHasher** *(contract in `Elsa.Activities.Design.Reconciliation.Core`)*. Single method: given an `IActivityDefinition` (and/or `IActivityDefinitionVersion`), return a deterministic string hash representing its content. Consumed by `ActivityVersionReconciler` to populate `ActivityDefinitionReconciliationState.ProvisioningHash` and detect drift between reconciliation passes. Default implementation ships in the `Elsa.Activities.Design.Reconciliation` feature.
- **JSON-file reconciliation source** *(seed feature, hosted in or alongside `Elsa.Activities.Design.Reconciliation`)*. Handles `OnActivityVersionsReconciling`; reads activity definitions from a structured JSON file (e.g. `elsa-core-activities.json`); contributes `IActivityDefinitionVersion` instances with `Definition.SourceKind = SourceKind.Json`, `Definition.SourceId = <assembly name from the JSON entry>`, `Definition.ProvisionedAt = <now or file mtime>`, `Definition.ProvisionedBy = Environment.MachineName`. The end-to-end proof for the new reconciliation flow at Unit B close.
- **TenantEntity** *(new base class in `Elsa.Primitives.Entities`)*. Inherits from `Entity`, adds `TenantId`. `TenantId` is removed from `Entity` itself. Entities that are tenant-scoped declare themselves by inheriting from `TenantEntity` rather than `Entity` — applies in Unit B to the activity-catalog entities and (by the same change) to the workflow-side entities (`WorkflowDefinition`, `WorkflowDefinitionVersion`, `WorkflowDefinitionDraft`) so the codebase remains consistent. Rationale mirrors Sipke item 7's `IsBrowsable` argument: tenancy is a domain concern, not a base-class concern.
- **IActivityDefinition / IActivityDefinitionVersion / IActivityDefinitionReconciliationState** *(stable read contracts, in `Elsa.Activities.Design.Core`)*. Getters-only surface over the three catalog entities; what consumers depend on. `IActivityDefinition` exposes identity + creation provenance + display only; reconciliation state is reached via the separate `IActivityDefinitionReconciliationState` contract so reconciliation churn does not invalidate consumers of the identity read contract. May coexist with mutable command / editing models that are part of the domain contract (per Sipke item 8).

This spec is implemented against the two-layer constitution at `.specify/memory/constitution.md` (Elsa v2.0.0 draft) and `.specify/memory/constitution-framework.md` (framework v2.0.0 draft). Constitution Check gates run at the plan stage; this spec carries the following originating constitutional concerns:

- **FR-024 / SC-008 originate three new constitutional rules.** All three are folded as part of Unit B's amendment cycle within the pre-ratification v2.0.0 (draft) substrate (no version bump required pre-ratification):
   1. **Elsa §E2.x (catalog source-of-truth)** — codifies *"if an activity is visible in the picker, it has a persisted catalog entry; the picker queries the catalog store, not live providers."* Elsa-specific; no framework analogue.
   2. **Framework §2.6.5 (sync contributor pattern — rare exception)** — codifies the narrow case where a provider interface resolved via DI as `IEnumerable<TContributor>` is permitted; demands three criteria (intrinsically sync dispatch site, behaviour-not-data, Registry + StartUp Task inapplicable).    3. **Elsa §E3.9 (sync contributor pattern worked example)** — the canonical Elsa-side worked example: `IEntityModelCreatingHandler` over EF Core's `OnModelCreating`. Elsa-specific; satisfies G16 by keeping the concrete example in the Elsa layer while the synthetic rule lives in the framework layer.
