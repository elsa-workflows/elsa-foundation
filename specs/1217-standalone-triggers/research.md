# Standalone triggers: current source and shared Runtime admission

**Status:** research and proposed implementation design; not production evidence or an approved persisted ABI.  
**Inspected base:** `e0ba87ecfc3b1e774c509ed274b19cd3f34a1124`, 5 November 2026.  
**Feature:** [#3582](https://github.com/elsa-workflows/elsa-foundation/issues/3582). Program-goal state: `none/free-flow`.

## Authority and decisions already made

The [delivery-start record](https://github.com/elsa-workflows/elsa-foundation/issues/3582#issuecomment-6671646417) records owner authorization and the decisions this design must preserve:

- A subscription follows a selected publication slot's serving version. Fresh admission checks its mapping against that version's input contract.
- Durably accepted work retains the exact accepted publication and finishes through trigger pause or target unpublication. Those operations stop fresh admissions. Cancel-pending is a separate explicit operation.
- HTTP has two intentional modes: one workflow owns the response, or one endpoint acknowledges durable acceptance and independently starts several workflows.
- Event and schedule subscribers are independent roots, associations are the same persisted objects from both authoring surfaces, and no dummy trigger activity is required in the target graph.

[ADR 0043](../../docs/adr/0043-publication-slots-define-start-authority.md) is accepted, but the convergence amendment at its top still says **proposed, awaiting owner acceptance**. The accepted sole-slot authority and exclusive HTTP identity rules remain constraints. A new resource cannot grant fresh starts to an unpublished target. Extending exclusive ingress ownership and accepted-delivery authority needs an explicit ADR amendment; this research does not silently ratify the proposed amendment.

The [shared-runtime mapping co-review on #2892](https://github.com/elsa-workflows/elsa-foundation/issues/2892#issuecomment-6670940060) proposes a Runtime-owned standalone ingress source family in the normal persistence/delivery composition. It explicitly excludes a fake publisher workflow, fabricated delivery context, API queue and second pump. That review is advisory source coherence, not adoption of its persisted ABI or evidence that the implementation exists. This feature adopts the same integration direction without depending on the rest of #2892 or implementing its group/phase semantics.

### HTTP, Event and recurring scheduling

[HttpEndpointMiddleware](../../Essentials/src/Activities/Http/Middleware/HttpEndpointMiddleware.cs) supports synchronous inline dispatch and asynchronous dispatch, authorization, size limits, timeout handling and a request-time ambiguity backstop. Current async ingress has no durable external source record. Its response can acknowledge the starts that succeeded while another start was shed. This is not the required durable responsibility for a standalone fan-out cohort.

[WriteHttpResponse](../../Essentials/src/Activities/Http/Activities/WriteHttpResponse.cs) returns a typed durable instruction. [HttpResponseInstructionDelivery](../../Essentials/src/Activities/Http/Services/HttpResponseInstructionDelivery.cs) delivers it after the inline drain, outside activity activation scopes. This separation is reusable without passing a live `HttpContext` into workflow activities. Existing sync delivery falls back to 202 if no committed response was produced; the standalone transport contract must explicitly settle its no-response, suspension, remote-worker and deadline behavior rather than inherit this accidentally.

[HttpEndpointRoutingUniquenessValidator](../../Essentials/src/Workflows/Runtime/Http/Services/HttpEndpointRoutingUniquenessValidator.cs) checks normalized endpoint claims against other authoritative slots. [HttpEndpointRoutesResolver](../../Essentials/src/Workflows/Runtime/Http/Services/HttpEndpointRoutesResolver.cs) combines trigger-binding and waiting-bookmark routes, and fingerprints their stimulus hashes for convergence. A standalone HTTP owner must join the same ownership, request generation and manifest/convergence paths. Adding one HTTP binding per subscriber would create competing endpoint owners and fail the existing guard.

[EventTriggerStimulusProvider](../../Essentials/src/Activities/Primitives/Activities/EventTriggerStimulusProvider.cs) uses named-event broadcast identity. [PublishStimulusIntentAdapter](../../Essentials/src/Activities/Primitives/Services/PublishStimulusIntentAdapter.cs) decodes the canonical persisted event; local events use resume-only semantics. [PublishStimulusExecutor](../../Essentials/src/Activities/Primitives/Services/PublishStimulusExecutor.cs) requires the actual workflow source, then retries capacity shedding. Standalone Event resources should contribute new-start subscriptions to the same original event delivery selection. Saved PublishEvent sources must keep their actual source and original complete cohort. An Event resource must not change broadcast into competing-consumer durable messaging or create new standalone sources on every retry.

[RecurringTriggerScheduleIndexer](../../Essentials/src/Workflows/Runtime/Scheduling/RecurringTriggerScheduleIndexer.cs) derives artifact/node-owned schedules. [RecurringTriggerPumpTask](../../Essentials/src/Workflows/Runtime/Scheduling/RecurringTriggerPumpTask.cs) claims fenced occurrences and routes through exactly the owned embedded binding, retaining failed/shed occurrences. [RecurringTriggerSchedule](../../Essentials/src/Workflows/Runtime/Core/Models/RecurringTriggerSchedule.cs) defines one overdue firing followed by advancement beyond the wake instant, with no replay of all missed intervals. A shared standalone schedule needs one resource-owned occurrence and several independent recipients, not one timer per subscription. [RecurringScheduleCalculator](../../Essentials/src/Workflows/Runtime/Scheduling/RecurringScheduleCalculator.cs) currently calculates Cron in UTC; timezone/DST authoring is an actual extension, not a configuration surface already supported by this calculator.

### Native and genuine BPMN execution are different paths

Native root invocation already supports mapped declared inputs. A native `BpmnProcess` activity or wrapper exercises that path but is not evidence for a genuine direct BPMN model.

[BpmnModelRuntime](../../Essentials/src/Activities/Bpmn/Elsa.Activities.Bpmn/Internal/BpmnModelRuntime.cs) publishes model material and a live `BpmnModel` source reference, and starts via `IBpmnModelRuntime.StartAsync(sourceReferenceId, requestId, inputs, caller)`. Its current model material has an empty input contract. [BpmnDirectExecutionDriver](../../Essentials/src/Activities/Bpmn/Elsa.Activities.Bpmn/Internal/BpmnDirectExecutionDriver.cs) explicitly rejects nonempty start inputs. The current direct publication also does not establish the same workflow activation-slot identity as native publishing. Therefore a generic target consumer must expose actual model eligibility, publication selection and input capability; it cannot cast model material to a native executable or fabricate a slot. Supporting genuine BPMN needs a bounded model-owned adapter and any missing input/slot bridge, with real direct-model qualification. Until that exists the capability must visibly refuse that target, without calling the overall agreed product complete.

## Comparison with a small trigger workflow

Today's useful alternative is an embedded HTTP/Event/Timer/Cron start followed by `DispatchWorkflow` activities. [DispatchWorkflow](../../Essentials/src/Activities/DispatchWorkflow/Runtime/Activities/DispatchWorkflow.cs) already validates declared child inputs, carries a publish-time exact child pin, records child lifecycle, and optionally waits or cancels with the parent. It remains appropriate when an author wants ordering, coordination or a parent business operation.

The first-class resource is justified by the agreed differences: edit/pause an entry point independently, share one source configuration, discover associations in both directions, follow the selected serving slot for new admissions, and start independent roots. Implementing the resource as a hidden workflow would inherit parent/child cancellation, fixed child dependencies and publication machinery that the operator did not author. It would also fabricate publisher provenance for external ingress. Reuse Runtime's delivery mechanisms directly instead.

## Proposed shared Runtime implementation

The following is a proposed implementation shape. API names are illustrative and must be reconciled with concurrent shared-runtime work before contract freeze. No part of this section is a claim that the capability already exists.

### 1. Generalize source identity in the existing outbox family

Introduce a versioned discriminated Runtime delivery source: `WorkflowCheckpoint` retains the actual workflow/checkpoint/intent identity; `StandaloneIngress` names an actual accepted external source. Both carry immutable scope and a source fingerprint. This distinction must exist in serialized wire, physical projections and source opening, not only metadata.

Evolve the common outbox work envelope and durable source context around that union. Preserve the existing workflow intent constructors/wire and their checkpoint-specific invariants. A standalone branch has no workflow publisher, activity or checkpoint ID. Its intent has source-neutral kind/key/payload facts and a typed ingress source. Existing workflow-only readers, cleanup queries and live-drain paths filter the workflow source branch explicitly. No dummy string is stored in `WorkflowExecutionId` to satisfy old constructors. The physical schema gains explicit source kind/ID projections and nullable workflow-owner projections for this branch, with versioned readers/upcasters and migrations for every supported relational provider.

Keep one physical outbox, one claim/retry/completion protocol, the existing exact-kind dispatcher and the existing scoped resumption pump. The new branch is not a separate API-owned queue or polling service. The outbox's legacy public name need not decide the domain vocabulary; source-neutral contracts should describe Runtime delivery, while existing checkpoint-producing callers retain their current semantic wrapper.

### 2. Add a provider-atomic standalone admission contract

A Runtime-owned admission service accepts a prepared ingress request from an authorized provider adapter. The normal selected persistence backend supplies its writer, exact lookup and cancellation capability together with the existing outbox family. Unsupported/split composition refuses before effects; it never falls back to memory or `AddPendingForTestingAsync`.

An admission request identifies tenant/persistence scope, resource and configuration revision, source event/HTTP key or schedule occurrence, the initiating authority, source schema and canonical payload, and the expected association generation. It contains no arbitrary trusted executable pins supplied by a browser. Runtime resolves the exact authoritative target selection and provider-owned source validation.

One physical acceptance commits all of these facts together:

1. Resource/association revision and operational state still permit this fresh admission. For a schedule, the exact fenced occurrence is still owned; for HTTP, the selected route generation still names this exclusive owner.
2. Every selected recipient has its exact active publication/source selection, complete material identity (including model kind/incarnation where relevant), subscription/mapping revision and normalized declared inputs. Invalid and unavailable recipients have explicit outcomes under the selected product policy; none are silently removed from an allegedly complete set.
3. Required target material/dependency roots are protected through the existing root-write lease/fence protocol. Publication eligibility is compared/fenced at the authoritative acceptance boundary, not merely read before a later unrelated insert.
4. A unique immutable source key/fingerprint, complete recipient set, accepted authority/scope and initial recipient delivery responsibility are recorded in the common outbox source. Both source identity and submitted-intent fingerprint include the trusted persistence scope and exact tenant, with explicit null-versus-string framing; resource IDs or source keys reused in a null and named tenant within one partition cannot share acceptance. The source is immediately recoverable by the ordinary processor.

EF performs this through the selected shared Runtime context with an owned transaction, authoritative row revisions and material/reference fences. The in-memory provider follows the same ordering using the existing shared write gate and material/reference gates; it remains process-local and cannot prove restart durability. Trigger resource persistence and slot/reference reads must join that actual atomic boundary or supply an equivalent provider-owned compare/fence operation; an interface composition that cannot do so must refuse activation. Merely placing several `SaveAsync` calls in one API handler is insufficient.

A request timeout or ambiguous commit acknowledgment is resolved by scoped exact source lookup. Repeating the same authorized source identity and immutable request returns the winning receipt; reusing its key with different content returns a conflict. Caller keys locate retained responsibility and never grant target authority. Current access checks still apply before exposing a receipt.

### 3. Freeze recipients and give each independent root a stable identity

Use a versioned, length-framed/digested identity derived from `(scope, source identity, subscription identity)`. Subscription identity is stable across edits; a new association gets a new identity. The accepted source freezes the mapping revision and exact publication. Later retries never rematch today's subscribers, remap against today's payload settings, or follow a replacement serving version.

Do not modify the frozen v1/v2 formats in [KeyedWorkflowStartIdentity](../../Essentials/src/Workflows/Runtime/Core/Models/KeyedWorkflowStartIdentity.cs). Add a distinct derivation or use a clearly source/subscription-scoped occurrence key through an explicitly supported dispatcher contract. Two selected slots can share an artifact without collapsing, and two independent subscriptions remain distinguishable if the product permits them. Redelivery converges on the same execution/command/envelope across processes and target replacement.

Persist per-recipient phase under the owning source as Pending, DispatchCommitted, TargetAccepted or CancelledBeforeDispatch, with retry/final-failure observations separate from that monotonic phase. Pre-admission refused entries remain explicit in the frozen selection. Execution started/completed/faulted/cancelled is a separate observation linked by execution ID. A source completes delivery only when every accepted recipient has physically transferred responsibility or was cancelled before its seal; policy/capability refusal after sealing retains owed work and cannot become a silent success. Retrying a partial cohort may resend the same idempotent command after an ambiguous acknowledgment, but must never execute a successful recipient again.

For saved workflow-origin Event sources, extend the existing complete cohort with a typed standalone-subscription recipient variant. Preserve its source ID, fingerprint and original wait/embedded-start selection; do not create a new external-source row as a surrogate. The per-subscription identity is additional to the embedded per-artifact identity and does not reinterpret legacy cohorts. The shared source validator/retention implementation must understand both recipient variants.

### 4. Make retained ingress authority explicit at target admission

Add a typed accepted-ingress authority branch in normal Runtime start admission. It names the physical source, exact recipient, source/selection fingerprints and immutable `DispatchCommitted` seal; it is data to revalidate, not a bearer capability. The dispatcher/target provider rereads that physical seal and verifies immutable accepted inputs, full material pin, scope/root identity, target provenance and canonical command. This target authority does **not** depend on the source handler's expiring owner/fence: current claims gate source mutations, while an already sealed queued command must remain valid after claim expiry or source handoff. Ordinary start policy and declared input validation still run.

This branch allows the exact already accepted publication to be retired while refusing any newly selected unpublished target. It supplies declared workflow inputs and no fake trigger node. Existing `StimulusDelivery` and retained-child authority retain their current stricter meanings. The new authority must survive canonical command serialization, queue transport and restart with causal fail-closed checks, and target acceptance/receipt logic must converge after ambiguous enqueue acknowledgment.

The existing dispatcher checks its source before actor enqueue, while first workflow state is committed later. That check alone cannot linearize cancel-pending against an in-flight enqueue. The [Runtime contract](contracts/runtime.md) resolves this with a durable `DispatchCommitted` recipient seal before enqueue. Cancel and seal compare the same physical Pending state. Cancellation that wins prevents any seal/enqueue; cancellation that loses reports committed dispatch responsibility, without claiming the target is queued or started. The same source retains the exact sealed command and roots until a physical deterministic target receipt is verified. Crash before enqueue and acknowledgment loss recover through the ordinary source retry; no cross-store queue transaction is claimed.

Initially force every new source/cohort/control/acceptance mutation through a coherent physical boundary in the existing checkpoint/fold composition. Preserve Balanced as the host default and preserve untracked work. No source admission may depend on a coalescing overlay that can disappear after the HTTP acknowledgment.

### 5. Reuse provider adapters and ordinary module discovery

Expose the narrow module extension contracts actually needed: trigger type configuration validation and source/payload description; authorized source submission; and a model-owned target consumer that captures eligibility and accepts exact mapped root starts. Contribute these through normal feature composition and capability discovery. Runtime owns admission, source persistence, delivery claims, retained authority and generic diagnostics; module code owns HTTP/Event/schedule configuration and payload interpretation.

The public submission seam is a producer-bound `IStandaloneTriggerIngress<TSource>` resolved through normal registered module composition. Its detached signal contains only trigger resource identity, source key, declared payload schema and payload. Runtime binds the registered producer/type and obtains scope and source actor from the trusted normal source execution context; the signal cannot supply tenant, grant, material, captured recipients or a fence. Registered source authorization and resource/type/schema matching run before internal admission prepares captures. The separate authoring descriptor supplies configuration/schema metadata and does not grant submission rights. Unsupported composition refuses before effects and conflicting producer/type registrations fail startup. This is ordinary trusted application/module code, with no new secret token/capability product and no generic browser management invoke endpoint. The independent consumer must submit through this public port; internal store/capture constructors are not a substitute.

The existing [durable-source handler contribution](../../Essentials/src/Workflows/Runtime/Core/Extensions/RuntimePostCommitIntentHandlerServiceCollectionExtensions.cs) can host exact-kind delivery once it understands the source-neutral context. Registration already refuses conflicting owners for one kind. Reuse its retry configuration and dispatcher; do not introduce a second handler registry. A generic root-start handler delegates only model-specific acceptance to a consumer adapter, keeping source/cohort validation centrally owned.

Extend `RuntimePostCommitOutboxStoreBackend` and both normal registrations to own the new admission/control capability. Provider capability qualification must verify the actual selected outbox, material, references, resource state and target acceptance stores, including decorators/coalescing. A legacy provider reports unsupported before an operation requiring the guarantee. Public consumer tests must register an external module through published contracts, submit a real source, map declared inputs and recover delivery; tests using internal constructors are insufficient extension evidence.

## Transport-specific application of the proposal

| Family | Source and acceptance | Required integration and remaining design work |
|---|---|---|
| HTTP async fan-out | One exclusive resource-owned route accepts one Runtime source containing the complete selected cohort. A 202 is emitted only after the physical admission receipt is committed; it means retained responsibility, not workflow completion. | Read/authorize/limit/parse before admission. Define request-key policy, invalid input status, unavailable-subscriber policy and no-subscriber behavior. Return a receipt/operator link and explicit recipient outcomes; infrastructure/admission failure cannot become a success acknowledgment. Downstream workflows cannot compete to deliver this exchange's response. |
| HTTP workflow-owned response | Exactly one response owner and exact root target. Reuse committed response instructions and request-owned delivery after accepted root execution where local inline work is supported. | Route ownership is still one resource. Explicitly settle suspension/no instruction, remote dispatch, deadline/disconnect and retry behavior. A retained execution may finish after request loss; its completion is not proof that the client received a response. Do not make a replayed receipt write a second transport response automatically. |
| Timer/Cron | One resource-owned schedule occurrence is admitted once to the shared outbox before its scheduling responsibility is settled. The ordinary outbox delivers several recipients. | Owner decision: when no recipients can be admitted, retain one overdue occurrence and retry with backoff against current targets; do not advance its cursor. Known zero eligible is distinct from unknown/store failure. Once any recipients are accepted, freeze the complete accepted/refused set and recover it without rerunning successful recipients or adding later subscribers. Extend the existing recurring owner/pump, use deterministic occurrence replay for admission/settlement crashes, and fence updates; timezone/missed-firing details remain explicit contracts. |
| Event from committed workflow publication | Keep the original PublishEvent outbox source and add standalone subscription recipients to its original complete cohort. | Preserve pre-effect wait snapshot, local-event resume-only behavior, embedded starts and tenant scope. Subscription edits after acceptance do not rewrite the cohort. |
| Event from external ingress | An authorized Event adapter submits one real standalone source to the same Runtime admission service. | Event remains broadcast. External source identity, payload schema and retry contract are explicit; no durable-message consumer cardinality or broker is introduced. |

HTTP ownership must be checked in both directions: creating/updating/activating a standalone endpoint against embedded owners, and publishing an embedded endpoint against standalone owners. The existing route snapshot lease, manifest and convergence fingerprint need to include the resource owner/revision so a pure mode/options/owner change cannot leave another node serving an obsolete generation. The exact implementation must preserve existing bookmark resume behavior and reject ambiguous response ownership before effects.

For schedule updates, persist stable schedule/resource identity, configuration revision, cursor and fenced ownership. A timezone or expression change must define whether a due old occurrence is retained, replaced or explicitly discarded; that policy cannot be inferred from `CreatedAt`. A successful pause stops fresh admission at its revision boundary and preserves accepted sources. Resume must not silently replay every missed occurrence unless that is the chosen contract. Qualify clock changes, DST, claim expiry, concurrent update and restart against the selected actual persistence provider.

The owner confirmed that an occurrence with zero eligible recipients remains the **one overdue occurrence**, with visible backoff and no cursor advancement. Each pre-admission retry evaluates the current subscription/slot/input/grant state. A complete known-zero evaluation may show its refusal reasons; an unavailable store leaves eligibility unknown and reports infrastructure failure, never an empty-success result. Event/schedule admission is always independent: one refused subscriber does not hold healthy siblings. The first admission with at least one eligible recipient captures the complete evaluated accepted/refused set; later subscribers or repaired refusals are not added to that already accepted occurrence. The source receipt, including an identical replay after acknowledgment loss, is the proof that permits schedule settlement. RequireAll/AcceptAvailable are configurable HTTP policies only.

## Qualification implications and unresolved engineering points

No build, host, fixture or runtime check was executed for this research. Source reading establishes integration points only. The proposed capability needs at least the following causal behavior evidence before delivery claims:

- Real durable admission, response loss and identical-key replay; conflicting key content; no success when commit/provider support is unavailable.
- Publication replacement/unpublication and resource pause races on both sides of the admission boundary; accepted exact pin retained through collection/deletion/restart; fresh unavailable target refused visibly.
- Two subscriptions/slots sharing material without duplicate-key collapse; partial fan-out failure and ambiguous target enqueue recover without another execution for successful recipients.
- Cancel-pending racing a handler, target command admission and first workflow state; UI reports which responsibility won and never implies cancellation of an already running workflow.
- Source claims outliving their leases and another node retrying; exact recipient/fingerprint verification and stale claimant completion isolation.
- Declared mapping/defaults/refusals through normal native roots and genuine supported model roots, with no dummy activity graph or wrapper substituted for model evidence.
- Shared HTTP route conflicts both ways, pure configuration/mode changes across nodes, request-size/auth/input failures, both real response modes and response delivery failure distinct from workflow completion.
- Schedule due/update/pause/resume/clock/timezone/restart races using the selected policy, one occurrence source with several recipients, and no same-literal schedule broadcast.
- Retained schedule occurrence with known zero eligible and with unavailable eligibility store: no cursor advance, distinct diagnostics/backoff, later admission against current targets, then an immutable full accepted/refused cohort with no late additions.
- Event complete original cohort, unchanged embedded starts/waits/local semantics and tenant isolation; no rematching changed associations after partial delivery.
- External module submits a real detached signal through the public producer-bound port without internal capture/store access; resource/type/schema mismatch and unauthorized/unsupported composition refuse before effects; old workflow/outbox wire and real recovery remain valid.

The [Runtime contract](contracts/runtime.md) now proposes the concrete source-neutral CLR/wire shape, public submission port, DispatchCommitted/cancellation boundary and physical target receipt rules.
