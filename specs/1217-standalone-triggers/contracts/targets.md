# Proposed target capture, publication and start contract

**Status**: Proposed implementation contract, version 1; not implementation or acceptance evidence.
**Inspected source**: `e0ba87ecfc3b1e774c509ed274b19cd3f34a1124`.
**Owns**: Native and genuine authored BPMN subscription targets, their publication-slot bridge, realized inputs and ordinary root admission.
**Related**: [Architecture](../architecture.md), [feature #3582](https://github.com/elsa-workflows/elsa-foundation/issues/3582).

## Confirmed product behavior

- A subscription follows the selected logical definition's currently serving slot. An accepted occurrence retains its captured publication, inputs and subscriber set across replacement, pause, unpublication and retry.
- Pause, association removal and resource-grant revocation block new acceptance. Cancel-pending is explicit and can retire only work whose target admission has not won.
- Start authority belongs to the shared resource. Creator/granting-user identity is audit attribution; their later removal or personal permission loss does not disable the automation.
- Async HTTP policy is configured per trigger: `RequireAll` by default, or explicit `AcceptAvailable` with visible partial outcomes. Accepting zero recipients fails. This contract determines target eligibility; the HTTP contract owns the response representation.

The type names and versions below are proposed reservations for implementation review. They must be checked for collisions on the implementation base before committing code. Existing wire values and profiles are unchanged. `DispatchCommitted` below is a durable source-side promise to enqueue one exact command; it is neither queue acceptance nor execution start.

## Minimal public seam and internal ownership

Split target authoring discovery from runtime preparation/reconciliation into two independently dispatched contracts, as required by [framework §2.6.4](../../../.specify/memory/constitution-framework.md). `IStandaloneTriggerTargetDiscovery` serves picker/schema/tooling consumers. `IStandaloneTriggerTargetRuntime` serves admission/delivery consumers. Each has its own keyed registration/dispatch path; neither inherits, resolves or requires the other. They may share detached immutable selector, descriptor and input-contract models in Core. Native and BPMN modules contribute the relevant implementations without introducing another workflow engine. Duplicate keys refuse within each dispatch family; an authoring-only registration does not imply runtime support.

| Contract/operation | Input and result | Side effects |
|---|---|---|
| Authoring `IStandaloneTriggerTargetDiscovery.DescribeAsync` | Trusted scoped selector → authorized published identity/input-schema description, static ordinary-entry constraints and declared HTTP response capability metadata. | Read-only. Does not load/resolve a runtime target adapter, execute a driver or reserve readiness. |
| Runtime `IStandaloneTriggerTargetRuntime.PrepareAsync` | Trusted serving selection + normalized input bag + server authority → exact native/model command preparation and retention requirements, revalidated against actual current material, entry support and runtime capabilities. | No recipient code, actor drain, target queue write or publication change. Requires no Design store, draft ID, picker or authoring tooling. |
| Runtime `IStandaloneTriggerTargetRuntime.ReconcileAsync` | Exact accepted recipient ID/capture → absent, durably queued, started or conflicting target admission, with the authoritative evidence address. | Read-only. An unavailable read remains unavailable, not absent. Requires no authoring discovery registration. |

Discovery can use authorized read models and published metadata without installing the runtime target implementation. Runtime uses the accepted source/material/slot contracts and its own capability checks without depending on Design. Displayed schema/capability metadata is advisory: runtime preparation never treats discovery output as authority or skips fresh physical validation. An unavailable runtime is a visible admission capability failure, not a reason to break schema discovery.

The first-party admission coordinator owns resources, grants, source occurrences, persisted captures, physical admission and retries. Runtime implementations cannot grant publication authority or return a successful admission solely because they invoked recipient code.

These are purpose-specific typed requests/results, not dictionaries containing arbitrary service objects. The host coordinates the physical source seal and ordinary target dispatch after preparation; a module adapter cannot substitute a private queue. Module-facing types contain detached JSON and immutable identities, never `HttpContext`, `IServiceProvider`, delegates, principals or credentials. Native/model dispatch implementations, source readers and persistence participants remain internal unless an independently compiled module requires a narrowly defined contract.

The external management API accepts only a logical target selector and mappings. It never binds a saved capture, execution authority, source lease, publication/reference ID, model incarnation or `WorkflowExecutableStartAuthority` from caller JSON. Internal types that are serializable are data, not bearer capabilities.

## Selector and accepted recipient wire

`StandaloneTriggerTargetSelector` v1 has `adapterKey`, `workflowDefinitionId` and `slotName`. `slotName` is explicit, with the visible default `default`. Tenant and persistence scope are server-owned context. A material hash, numeric latest version, Design draft or test-run source is not a production selector. The adapter key identifies the execution model; it is checked against the selected material/protocol and cannot reinterpret native material as model material or vice versa.

Persist a new `StandaloneTriggerStartCapture` with `formatVersion: 1`, rather than constructing a `StimulusStartRecipient` with a fake embedded trigger binding. Its required fields are:

| Field group | Required facts |
|---|---|
| Source | Source family/address, accepted occurrence ID, content fingerprint, actual persistence scope and tenant. |
| Resource | Trigger ID/revision, subscription ID/revision, resource invocation grant ID/revision and accepted grant evaluation. |
| Logical target | Adapter key, stable workflow definition ID, exact authored version ID, slot ID/name/revision and selected activation/publication ID. |
| Material | Full `WorkflowExecutableIdentity`; physical material incarnation; native/model discriminant; model protocol/profile when model. |
| Provenance | Exact `WorkflowExecutableSourceProvenance` and its authoritative source-reference identity. Production standalone captures never use reference-less legacy authority. |
| Values | Immutable normalized declared inputs, target input-contract fingerprint, mapping revision/fingerprint and captured expression parameter/result evidence. Native variable defaults use a separate server-computed seed field. |
| Execution | Deterministic recipient/start IDs, registered server-owned system authority and root-initiator attribution. |

The native variable seed is derived using the existing `RuntimeVariableDeclarationProjector` from the exact selected executable. It cannot be authored in a subscription or supplied by a producer. This preserves ordinary declared variable defaults without pretending they are workflow inputs. Model captures do not carry native variable seeds.

Source payload and safe source metadata remain separate from declared inputs and authority. Input names are case-sensitive according to the existing declared contract. Presence, explicit null and omitted/default values retain their existing meanings. Persist the target contract and mapped JSON with their versioned fingerprints, not a global serializer's incidental output bytes.

Use a purpose-specific v1 digest built with the existing Runtime identity/fingerprint conventions: a fixed domain string, length-delimited exact strings, ordinally ordered maps and a fixed canonical JSON representation. Freeze that preimage with test vectors. Do not change `ExpressionDefinition.Fingerprint`, native artifact hashes, `RuntimeModelMaterial.ComputeContentHash`, global HTTP JSON settings or `IPayloadSerializer` for this feature.

The capture's logical/source identity is independent of deduplicated material's original producer identity. The source's `ArtifactId` joins its actual retained material. Preserve the complete material pin strictly while separately checking the source/slot/logical-definition relation. Two definitions sharing a material artifact must not collapse into one subscription or be rejected because one stored material row remembers the other producer.

Derive recipient identity from the accepted scoped occurrence and subscription ID. Derive its execution, command and envelope/input IDs deterministically with a new named v1 derivation. A retry uses those same IDs and capture. Do not modify existing `KeyedWorkflowStartIdentity` v1/v2 formats, deduplicate subscriptions by artifact, or add another recipient when the serving version changes.

## Input mapping without a new expression binding kind

Use the existing [`IPortableExpressionEvaluator`](../../../Essentials/src/Expressions/Core/Contracts/IPortableExpressionEvaluator.cs), [`ExpressionDefinition`](../../../Essentials/src/Expressions/Core/Models/ExpressionDefinition.cs) and `binding-pure-v1` capability profile. Portable evaluation already accepts exact immutable parameter values; this feature does not require a new `ExpressionParameterBinding` discriminator.

Trigger-owned mapping wire v1 has one destination input name and one value source: literal JSON, a source-field selector, or a portable expression template plus named trigger-owned parameter selectors. Parameter selectors are only literal JSON or a path into the detached source envelope. Paths use the owning mapping contract's defined JSON-field traversal; missing and explicit-null are distinct results. They are not workflow variable names or executable-node identities.

At admission:

1. Resolve the target's current authoritative contract and mapping revision without invoking the target.
2. Materialize every template parameter from the captured source envelope. Reject unresolved required parameters; do not silently replace missing values with null.
3. Construct an ordinary immutable `ExpressionDefinition` with `LiteralExpressionParameterBinding` parameters. Preserve its authored language, source, result type, evaluator options and existing capability-profile name. Pass the exact immutable values to `ExpressionEvaluationRequest`; require the parameter set to match the definition.
4. Evaluate using the existing portable language handler. No ambient workflow state, target variable/activity outputs, clock service, network or service locator enters this pure evaluation path. If an existing language/profile cannot provide this path, report unsupported; do not route it through a different evaluator silently.
5. Build the destination bag and call `IWorkflowExecutableInputValidator.Validate`. Retain its normalized bag/defaults and the parameter/result evidence used for this evaluation. Reject unknown/duplicate destinations, invalid types and missing required inputs before acceptance.

Save/preflight uses `ValidateKnownInputs` for statically known values and validates that all required nondefaulted destinations have mappings. Preview runs the same realization against sample data and is advisory. Real admission rechecks the actual publication, complete bag and resource grant. Retries use captured results; they do not reevaluate expressions.

Use a trigger-specific tooling adapter/API context. The current workflow expression tooling expects a `WorkflowDraftId`; it cannot be advertised as reusable unchanged for an autonomous trigger. Reuse the editor widgets, portable language catalog and evaluator; supply the declared trigger source/parameter schema through the new context. No change to accepted workflow variable/activity-result binding or serializer semantics is included. A necessary change to a #3052 board contract must be separately proposed through its human agreement process.

## Material-neutral publication-slot bridge

The current [`WorkflowActivationCommand`](../../../Essentials/src/Workflows/Runtime/Core/Models/WorkflowActivationLifecycle.cs) and [`PublicationActivationRequest`](../../../Essentials/src/Workflows/Publishing/Core/Models/PublicationAuthority.cs) require a native `WorkflowExecutable`. Extend them additively with material-neutral request types; retain existing native overloads as adapters into one internal coordinator implementation:

```text
WorkflowMaterialActivationCommand v1
  LogicalDefinitionId, SlotName, ActivationId, ExpectedRevision, Source
  MaterialPin, MaterialIncarnationId, Kind(Native|Model)
  SourceReference, OwnershipIntent

PublicationMaterialActivationRequest v1
  PublicationRecord Candidate
  WorkflowMaterialActivationCommand material request
```

The public material command carries identities, not arbitrary projection callbacks. The Runtime coordinator rereads actual material and routes preparation internally. `LogicalDefinitionId` comes from validated authored source/provenance and determines the ledger key. The full stored material pin remains unchanged. The source reference carries the logical definition/exact authored version and points to the actual artifact. Native callers retain their current logical key and publication behavior.

For a native candidate, use the existing trigger indexer and recurring-schedule decorator. For a direct-model candidate, prepare an **empty** activation in `IWorkflowTriggerBindingStore` and, when composed, `IRecurringTriggerScheduleStore`. Both existing contracts explicitly preserve activation state for empty projections. This records prepared/active/replaced lifecycle without a fake native executable, embedded binding or new serving ledger. The ordinary `IWorkflowActivationSwitch` commits the slot/projection visibility/reference retirement together. Do not move the slot through `IWorkflowActivationAuthority.TryActivateAsync` alone.

Refactor the coordinator's logical key, material pin/lease acquisition, projection preparation, same-artifact checks, abandonment and observer fallback into the common internal path. `EnsureServingAsync`, deactivation, compensation, cancellation-after-commit and startup repair must work when both projection sets are empty. Native slots, native→model and model→native replacement in the same logical slot use the same protected transition; changing execution model does not create a second slot namespace. Readiness refuses a mixed backend or missing physical material/source/root-lease composition.

Extend `IPublicationActivator` with the material request using default refusal for providers that do not support it. Reuse the existing publication journal, completion/recovery and policy resolution. The active slot remains authoritative if a publication journal write lags. Same-artifact no-op returns the **actual** currently active publication/source and does not journal a candidate as active or report its requested authored version as serving. Model support does not alter native no-op semantics.

The BPMN authored-publishing bridge belongs in the existing Interchange layer, which already reads/authenticates `WorkflowDefinitionVersion`. Add a dependency on Publishing.Core there when implementing the material publication bridge; do not make the BPMN runtime depend on Design or HTTP API assemblies. Factor model preparation from `BpmnModelRuntime.PublishCoreAsync` so it can return validated stored material and trusted provenance without independently minting a live Published reference. The bridge then calls the existing Publishing lifecycle through its material request. Existing raw/legacy `IBpmnModelRuntime.PublishAsync` remains available with its documented identity and creates no slot-following authored target by inference.

Add an authored publication operation with slot intent, expected slot revision and expected publication ID. Existing authored publication callers adapt to a default-slot replacement with current preflight; request IDs retain exact-content replay/conflict behavior. The response includes the actual logical definition/version, slot/revision, publication/reference, material pin/incarnation, profile and activation outcome. The normal unpublish/restore path must read model material and use the material-neutral coordinator; no BPMN-only unpublish ledger or source-retirement shortcut is allowed.

## Native root preparation and durable dispatch commitment

Add `WorkflowExecutableStartAuthorityKind.StandaloneTrigger = 4`; existing values 0–3 remain frozen. Its optional `standaloneTrigger` value is omitted when unused and contains a v1 Runtime-owned source/recipient capture address plus fingerprint, not a fabricated outbox binding ID. The dispatcher rereads the actual accepted capture and immutable `DispatchCommitted` seal, validates scope/authority/input equality and checks retained material roots. The complete server capture and physical seal, not caller-supplied fields, grant selection of the saved publication.

The prepared native request uses `PublishedRun`, no native parent, nesting depth zero, null `TriggerNodeId`, empty embedded `TriggerMetadata`, captured declared inputs, server-derived native variable defaults and exact captured source provenance. This enters ordinary Sequence/Flowchart/root behavior. It cannot select a bookmark, embedded node or test-run scope. Source payload may occupy its existing separate reserved stimulus channel; it cannot be merged into `Inputs`.

Factor native `WorkflowStartDispatcher` validation/normal command construction into an internal preparation operation so standalone admission reuses current input validation, start policy, persistence mode, deterministic command/envelope and load-shedding checks. Do not bypass these by manually writing a superficially similar Start work item. Existing `DispatchAsync` continues to use the same preparation and ordinary actor dispatch.

The Runtime source participant commits `DispatchCommitted` with the exact recipient/capture, deterministic execution/command identity and normalized semantic command fingerprint. This compare-and-swap uses the actual source store's owner/fence and competes atomically with cancel-pending. It is an irrevocable, retained responsibility to enqueue that command. No target queue write or inline actor drain occurs before the seal commits. Native and model queues retain their existing physical admission/deduplication boundaries; there is no requirement for a transaction spanning the source and queue.

If cancellation wins, no seal or target command is produced. If sealing wins, cancel-pending reports **dispatch committed** with the intended execution address, even if no queue/state row exists yet. A lost seal response triggers retained seal lookup, not a new command identity. Crashing after the seal and before enqueue leaves the source owed. A subsequent worker recovers the seal and retries the exact normal dispatch until an actual deterministic queue/execution/input receipt proves admission. Neither source completion nor UI `Queued` can be inferred merely from the seal.

Later source delivery-lease expiry does not revoke the seal or invalidate an already queued target command. Creating a seal requires the current source claim/fence; validating a sealed command or replay requires the immutable physical seal, capture, scope and exact fingerprint rather than that expired lease. Source settlement/progress writes still require current delivery ownership. Concurrent post-seal workers can only submit the same intended command; ordinary target identity/deduplication converges them.

The semantic fingerprint includes the target pin, scope, captured authority/provenance, declared/seeded values and deterministic entry/command identities. Queue attempt timestamps and transient diagnostics are not new intended input. The first actual queue admission supplies its ordinary transport metadata; retry preserves its winning admission. Do not weaken a queue's content-conflict check to accommodate differently mapped values.

`Queued` means positive evidence of durable target responsibility, not workflow completion. Native reconciliation checks the deterministic queued command or exact execution state/start authority. A conflicting existing execution, changed inputs or foreign scope refuses. If reads fail, the source remains owed/uncertain. A fresh preparation and ordinary native dispatch still apply the host's current `IWorkflowExecutableStartPolicy`; a post-seal denial remains visibly owed/blocked. An already queued exact command replays without applying the trigger's newly revoked grant or selecting a replacement publication. After successful admission the ordinary actor/scheduler drains the normal command, using request-scoped synchronous drain only for a qualified workflow-owned HTTP response.

## Genuine BPMN: bounded authored input profile

Genuine model runs use `RuntimeModelExecutionState` and `ExecuteModel`; they do not create a native wrapper execution. The supported new target is an authored definition published through the material-neutral slot bridge, with a normal none-start entry. Event-only/ambiguous/unsupported entry requirements are rejected in preflight. Do not forge a `BpmnStartSignal` or embedded trigger metadata.

Keep protocol key `elsa.bpmn`, protocol version 1, Runtime model material format 1 and Runtime model execution-header format 1. Introduce profile **`foundation-inputs-v1`**, which an old driver rejects as unsupported. Its model definition is a new BPMN-owned v1 envelope containing `baseDefinition` and `workerInputMappings`; do not add format 7 to the existing closed `BpmnModelDefinition` union or relax its older constructors.

The initial base definitions are the three shapes the existing authored projection produces: closed human format 1, native service/fault-policy format 3 and claim-required human format 6. Decode their existing structures/profiles through a shared internal representation and retain their present semantic/capability restrictions. Existing raw/retained formats 2/4/5 and all old native/embedded profiles stay unchanged; their broader extension is outside this authored input-entry slice. A closed authored process may use the new slot bridge without changing its legacy material hash/profile. Adding declared inputs selects the new input-capable profile.

`RuntimeModelMaterial.InputContract` contains the authored workflow declarations. `baseDefinition` still carries the process graph/work inventory and exact worker dependency pins. The new envelope's v1 worker mappings are deliberately small: destination worker input → either literal JSON or a case-sensitive declared model input name. They introduce no expression language or mutable BPMN variables. General expression routing, new BPMN conditions, event starts, collaboration or the separate durable messaging product are not prerequisites.

The initial profile supports explicit-null **input values**, including literal worker mappings, but refuses explicit-null **defaults** while declaration presence is still observable, before envelope serialization, hashing or publication effects. Its existing nullable contract format cannot retain that default presence. An authored immutable input declaration with a `defaultValue: null` member is therefore refused as ambiguous; omit the member for no default. This limitation does not reinterpret retained legacy material or change its hashes. Full null-default support needs a separately versioned presence-aware contract. This refusal is an unsupported-profile witness, not successful null-default execution qualification.

Publication validates every mapping against the exact model and worker declared input contracts. Each required worker input has a mapping/default. Reject unknown inputs, duplicate destinations, incompatible literals/name types, unsupported worker contracts and unsupported nested model/service shapes. The existing authored service-binding UI gains this explicit mapping alongside its retained worker pin. It does not silently pass the whole transport payload or all workflow inputs to a worker.

At model start, validate the realized bag with `IWorkflowExecutableInputValidator`, retain it in the new model-owned state frame and invoke the released interpreter's ordinary root Start with its existing capabilities. Do not reinterpret input names as BPMN variables. Human inspection exposes authorized inputs from that committed frame. Before a native service invocation is committed, realize its literal/name mappings from the retained bag, apply the worker validator and commit the normalized worker inputs with the exact native-work origin/outbox intent. Retry of that same attempt reuses them. This provides a concrete model-input consumption witness through an existing supported service task without adding general data-state semantics.

Use model-owned state frame **16** for the new input-capable profile and for new authored slot-bound direct/standalone entries that must copy their accepted provenance. It wraps the existing closed-profile document plus `declaredInputs`, complete accepted start provenance and profile/base-format identifiers. Start provenance identifies an authored direct entry or standalone capture/seal; a direct call cannot assert standalone authority. A closed material profile may therefore keep its existing hash while its new authored entry writes frame 16. Its decoder validates the underlying human/service/claim shape rather than treating every optional property as interchangeable. Frame 16 preserves the existing work/result/claim/cancellation structures of that base shape. All older frame readers remain; raw/legacy/embedded entries not using these new capabilities retain their previous writers/bytes. Reject unknown frames/contradictory base shape. Recheck the reservation against concurrent BPMN work before implementation.

### Provider-protected authored direct admission

The same published business model remains callable directly. Extend authenticated `IBpmnModelRuntime.StartAsync` to recognize slot-bearing authored references and to prepare a server-owned `RuntimeAuthoredModelStartSelection` v1: logical definition/exact authored version, slot ID/name/revision, selected activation/publication, exact source-reference/provenance, full material pin/incarnation, normalized input bag/contract fingerprint, captured direct execution authority and deterministic execution/input/command IDs. Authenticate and authorize the request through existing resource-aware model permissions; this selection is not accepted from client JSON. It contains no trigger, subscription, resource grant, fake publisher execution or common ingress source owner.

The existing [`RuntimeExecutionProtocolRouter`](../../../Essentials/src/Workflows/Runtime/Elsa.Workflows.Runtime/Services/Executions/RuntimeExecutionProtocolRouter.cs) already leases the exact model root/dependency closure before `queue.EnqueueAsync` and checks the selected material. Those leases provide material-retention protection; they do **not** fence a publication slot or source reference against concurrent replacement/unpublication. A live read followed by ordinary enqueue is insufficient for these new slot-bearing references.

Add a bounded target-owned authored-start operation on the internal protocol-router/provider boundary. Its prepared request contains that selection and the actual ordinary `ExecuteModel` scheduler command with its copied direct provenance. Under the router's existing material-root lease callback, the selected Runtime physical participant must compare the expected slot revision/activation and source identity/liveness **while committing the deterministic actual queue row**. It keeps the slot/source protection until queue commit, using concurrency protection shared with activation/unpublish; a read-committed transaction containing only a SELECT and later queue INSERT does not establish this guarantee. The EF implementation uses the actual shared Runtime context/queue/slot/source participants with provider-appropriate locking or an equally strong fence. The in-memory implementation holds the corresponding existing provider locks through the queue write. There is no cross-backend transaction promise.

This participant is a distinct additive capability with default `Unsupported`/`NotSupportedException`; `SupportsClaimTransitions`, model material support or matching backend type names do not imply support. Qualify the actual instances and their physical protection. It must perform the normal model input/profile validation, current start policy, admission/backpressure and queue content checks. No driver/actor drain runs until its queue commit is known to have succeeded. Do not create another direct-start receipt/source table merely to imitate trigger delivery: the deterministic queue command and copied direct provenance are the accepted responsibility, followed by the existing model state/input receipt.

If queue admission wins, its captured direct start is accepted and the existing queued-model retention protects it across later unpublication/replacement; consumption uses the copied provenance without requiring the source to become live again. If unpublication/replacement wins, the expected source/slot comparison refuses the stale request without enqueue. An authored slot-bearing source that loses this comparison never falls back to the raw legacy start path. A tombstoned execution or a queue call that returns without a durable row/retained state cannot be reported as newly admitted.

Request replay checks the exact deterministic pending queue command and retained model state/input receipt before fresh publication eligibility, after authenticating/authorizing the caller. An exact prior accepted start remains the result after unpublication. Same-ID/different pin, scope, provenance, authority or normalized input fingerprint conflicts; unavailable lookup remains uncertainty. Lost enqueue acknowledgment is reconciled against those actual records before another fresh admission attempt. Current publication reads never retarget an accepted replay to a replacement.

Reserve direct model input kind **`start-authored-v1`**, with copied server-owned authored provenance, for this provider-protected path. It is an ordinary root `ExecuteModel` command, dispatched through the existing queue/protocol router and released BPMN root Start semantics. An old protocol registration rejects the new kind even when the material retains a closed legacy profile; this prevents an old host from ignoring new slot-authority metadata. The new driver validates the copied pin/input/provenance and stores it in frame 16. The input-capable profile accepts its declared bag; closed profiles still require an empty bag. Raw legacy `StartAsync` continues using its existing `start` command and published-source behavior. This bounded direct-call change prevents newly slot-published models from working only through the standalone adapter while Run uses stale source authority or rejects the new logical identity/input profile.

### Model start command and receipt

Reserve model command input kind **`start-trigger-v1`** with a v1 payload containing the saved recipient/dispatch seal, normalized declared inputs, captured logical source provenance and capture fingerprint. The ordinary public `StartAsync` transport cannot submit it. Its driver validation rereads the retained physical seal/capture and exact model material/incarnation/authority. It checks captured values before the ordinary root start, then commits model state and `RuntimeModelInputReceipt` through the existing scheduler fence/checkpoint participant. It does not require an expired source delivery lease or the retired publication to become live again.

After the source seal, the model adapter queues this normal `ExecuteModel` command through its existing actor/queue path. Positive queue/state/input receipt evidence advances the source to target-accepted; the source seal alone does not. A receipt or same-fingerprint pending command answers retries; a same-ID/different-fingerprint command conflicts. `RuntimeModelInputReceipt` proves consumption of the input, while queue acceptance only proves responsibility. A terminal model does not receive a second start. Failed/unsupported admission remains visible and cannot be mapped to completed business execution.

### Typed native service input extension

Reserve `RuntimeModelNativeWorkOrigin` **format 2** for input-capable model work. Add immutable normalized `inputs` and the pinned worker input-contract fingerprint, with an additive constructor and version-aware equality. Format 1 retains empty inputs and exactly its old serialization. `IsEquivalentTo`, source/attempt checks, persisted work, cancellations and returned result origin compare the full v2 inputs/fingerprint; an input change is not the same attempt.

Reserve outbox kind **`Elsa.Bpmn.StartNativeWork.v2`** for that v2 origin. The existing delivery handler supports v1 and v2; it passes only the physically committed v2 bag through `WorkflowStartDispatcher` with existing ModelWork authority. `ResolveModelWorkAsync` and the native-work checkpoint boundary verify the supplied bag against the retained model work/source; the ordinary native input validator applies again. No standalone resource grant is borrowed for a child worker: the committed model invocation and retained exact dependency remain its authority. Existing model result/cancel kinds can stay v1 envelopes containing an explicit v2 origin, because old readers already refuse the unsupported origin version; unused old origins remain byte-identical.

## HTTP mode capabilities and partial policy

Native adapter capability reports workflow-owned response only when the composed HTTP bridge can provide the real request lifetime/response context and refuse async response writers. Genuine BPMN adapter v1 reports **`supportsWorkflowOwnedHttpResponse: false`** and supports Event, schedule and async HTTP starts through ordinary model roots. The UI/API refuses an attempted sync model association with a specific capability finding. It must not convert the request to async mode or claim that a native service's response automatically belongs to its model parent. A future model response bridge requires its own concrete design and qualification.

For async HTTP `RequireAll`, any selected enabled subscription failing target/grant/mapping/readiness validation prevents occurrence acceptance and creates no successful recipient acceptance. For explicit `AcceptAvailable`, capture the eligible subset atomically and retain excluded subscriptions as **not accepted**, with safe reasons and the evaluated revision. At least one recipient must be accepted. Excluded targets are not owed deliveries and are not silently admitted on retry after a publication/configuration change. In either policy, a target failure discovered **after** durable acceptance is an owed recipient outcome, recovered against its captured version without rerunning accepted siblings. The source receipt distinguishes those two cases.
