# Source-aware catalog disclosure boundary for #3908

Research snapshot: `4b08750f64eaa9728cbbcece94328d7789a0c48e`, 6 November 2026. The owner approved this boundary at `1bf3d5955a42222a5b62e4b0d463e17c43eedd16` on 6 November 2026 ([receipt](https://github.com/elsa-workflows/elsa-foundation/pull/3923#issuecomment-6675758688)). Exact public API/serialization details remain technical design, and no implementation or passed security qualification is claimed. Spec 1219 retains its 33 requirements. The separate #3917 ownership fix is not in this source snapshot; tenant preservation remains a prerequisite rather than something this proposal implements.

**Recommendation:** keep one activity catalog. Add a small Activities-owned disclosure contract that every metadata projection uses, implemented for source-bound entries by an optional Integrations contribution. Reuse Foundation Identity for the Elsa permission decision and Connections for tenant-scoped credential resolution. Neither currently supplies the missing per-source entitlement. Keep metadata disclosure, source invocation and Runtime delivery authority separate decisions.

## Minimum extension boundary to agree

The names below describe responsibilities, not proposed final C# signatures.

1. **Activities-owned disclosure evaluator and resource.** A public, narrow `.Core` seam asks whether the current trusted authority may disclose an exact catalog resource for a stated purpose: schema/metadata read, construction/options expansion, or authoring/publication use. It returns **allowed**, **denied**, or **unavailable**, with safe reason/recovery codes; cancellation remains distinct. A single scoped coordinator aggregates registered owner contributions, so consumers cannot choose a more permissive evaluator. The coordinator remains independent of Integrations, HTTP, EF and source credentials.
2. **Verified source association.** Each protected entry must resolve to its catalog definition/version, actual owner tenant, provider/schema identity and a provider-owned source resource: stable source identity/incarnation, type/operation/schema identity and any fixed connection binding/incarnation. These are policy inputs, not an authority grant. The trusted publication/provisioning path must validate the association and preserve it through version/publication projections and forks. The source-owned provider resolves it from its registered owner and canonical manifest/source registry; request bodies, caller-added facets, arbitrary `SourceId` strings and assistant content cannot assert that an entry is public or select another tenant. Existing [version contracts:14](https://github.com/elsa-workflows/elsa-foundation/blob/1bf3d5955a42222a5b62e4b0d463e17c43eedd16/Essentials/src/Activities/Design/Core/Contracts/IActivityDefinitionVersion.cs#L14) already carry provider/consumer identity, opaque payload and source provenance, but define no source authorization binding. The concrete recommendation below is new immutable disclosure-requirement metadata, with existing provenance retained as evidence used during admission.
3. **Optional Integrations policy contribution.** The source owner resolves the associated connection/resource and evaluates both the Elsa user's permitted source use and the source account's applicable schema/field/operation capability. One provider key may serve several differently permitted source instances. A required protected owner with no installed contribution, an invalid binding or an unavailable authority cannot fall back to general catalog read permission. Reject duplicate/ambiguous owner registrations at composition time. Known public code-owned entries keep the normal catalog gate and availability behavior; protected source entries require the extra decision.
4. **Conservative initial schema boundary.** Allow or withhold the whole exact operation schema. If some of its field names, choices, defaults, facets or descriptor contents are not disclosable, withhold the entry rather than silently editing its executable contract. A provider may deliberately supply a separate safe, versioned operation/projection. Record/value/option reads still enforce their declared field and record gates. Generic field-by-field schema redaction is a larger follow-on unless a concrete initial provider requires it.

Reuse [IPermissionAuthorizationService and IPermissionResourceHandler:42](https://github.com/elsa-workflows/elsa-foundation/blob/1bf3d5955a42222a5b62e4b0d463e17c43eedd16/Essentials/src/Foundation/Identity/Core/Authorization/AuthorizationContracts.cs#L42) for the Elsa-side permission/resource decision. Its [implementation:428](https://github.com/elsa-workflows/elsa-foundation/blob/1bf3d5955a42222a5b62e4b0d463e17c43eedd16/Essentials/src/Foundation/Identity/Elsa.Foundation.Identity/Authorization/AuthorizationServices.cs#L428) validates normalized principals; resource denials take precedence, and absent resource answers fall back to the permission evaluator (lines 452–474). Therefore a required protected-source owner must be checked explicitly: merely adding an optional resource handler while permitting generic fallback is insufficient. The real source-use permission/resource profile remains a separate integration/workload decision; the generic catalog unit supplies a keyed policy boundary and does not silently change existing connection management/binding policy.

## Recommended retained admission representation

**Agreed boundary; representation details to implement:** introduce one generic `CatalogDisclosureRequirement` value in Activities Design Core, retained on both the exact catalog version and its closed publication snapshot. The name and wire shape require review. It records a requirement to authorize; it never records a permission grant. A reader can parse the outer requirement without loading the source provider or deserializing its descriptor.

| Conceptual member | Proposed rule |
|---|---|
| Representation schema/version | Required and understood by the shared reader. Unknown or malformed representation is unavailable, never public. |
| Classification | Explicit `Public` or `Protected`; omitted/unspecified is unresolved and fails closed. `Public` means source-independent metadata admitted for disclosure behind normal catalog/module permission, not permission to invoke a source. |
| Protected requirements | A nonempty, bounded conjunction of stable policy references. Each has a policy key, policy/binding schema version and opaque canonical resource binding. All must allow. One reference suffices for a normal source operation; conjunction prevents a fork or dependency from replacing an inherited requirement with a weaker new owner. This is not a generic policy-expression language. |
| Resource binding | Stable source/type/operation/schema identity and relevant source/connection incarnation, interpreted only by the keyed policy owner. No credentials, caller claims or saved allow decision. Tenant ownership comes from the trusted persisted owner/context and must agree with any tenant association in the binding; authored tenant text is not authoritative. |

Read behavior is mechanical: `Public` proceeds to existing gates; `Protected` requires every referenced policy owner and supported schema. Missing module/key, unsupported schema or undecidable source access returns unavailable without its private metadata. Explicit denial withholds the resource. Empty protected requirements, missing metadata, conflicting catalog/publication requirements and unknown classification refuse. There is no Core switch on an entity provider or source kind, and no rule that absence of a registered provider means public. A policy key may resemble a provider key, but they have different roles: the retained requirement is the signal to require authorization.

### Admission must force the requirement

The outer metadata is **server-produced**, absent from user-writable authoring DTOs. A trusted host admission registry identifies the actual registered contribution producer/content authority, its supported schemas and its minimum disclosure classification. Code-owned public sources get explicit public admission through their owning composition. Source-bound private contributions get a mandatory protected policy key/binding requirement through their admitted owner. Classification is derived from that registration and validated canonical material, not merely a submitted provider key, source string, facet, `TenantId` or an author-selected `Public` flag. A registration which owns protected content cannot return a weaker public classification for it. A new contribution without a known admission owner is refused; it does not inherit legacy compatibility by omitting metadata. This boundary assumes installed server code and host composition are trusted; arbitrary malicious plugins or database writers are outside the confidentiality claim.

Enforce admission on **both** reconciliation paths: with a source publisher and without one. The existing reconciler can call create/add-version commands directly when no source publisher is installed ([reconciler:139](https://github.com/elsa-workflows/elsa-foundation/blob/1bf3d5955a42222a5b62e4b0d463e17c43eedd16/Essentials/src/Activities/Design/Reconciliation/Elsa.Activities.Design.Reconciliation/Services/ActivityVersionReconciler.cs#L139)). The create/add-version persistence commands currently serialize caller-supplied version material ([store:627](https://github.com/elsa-workflows/elsa-foundation/blob/1bf3d5955a42222a5b62e4b0d463e17c43eedd16/Essentials/src/Activities/Design/Persistence/EntityFrameworkCore/Stores/EfActivityDesignStores.cs#L627)). Those ordinary entry points and the source/Design publication commit boundaries must refuse missing, weakened or inconsistent admission metadata **before any Runtime or Design writes**. The source publisher's already-published shortcut ([snapshot publisher:69](https://github.com/elsa-workflows/elsa-foundation/blob/1bf3d5955a42222a5b62e4b0d463e17c43eedd16/Essentials/src/Workflows/Publishing/Api/Services/SourceOwnedActivityVersionPublisher.cs#L69)) must compare the retained requirement too; an old public publication is not evidence that a newly protected candidate was safely admitted. This recommendation is additive to the separate tenant-ownership fix.

Forks retain an immutable inherited requirement in server-owned authoring/draft metadata, and each newly published version takes its effective requirement from that trusted lineage plus any additional target requirements. The current fork creates a Design-owned target with `ForkedFrom`, `SourceVersionId` and a migrated manifest ([fork handler:91](https://github.com/elsa-workflows/elsa-foundation/blob/1bf3d5955a42222a5b62e4b0d463e17c43eedd16/Essentials/src/Activities/Design/Api/Handlers/ActivityForkHandlers.cs#L91)); provenance alone is therefore insufficient. Include the retained requirement in candidate/receipt material fingerprints and recheck the exact source at apply/commit alongside the existing source/target fingerprints ([store:1087](https://github.com/elsa-workflows/elsa-foundation/blob/1bf3d5955a42222a5b62e4b0d463e17c43eedd16/Essentials/src/Activities/Design/Persistence/EntityFrameworkCore/Stores/EfActivityDesignStores.cs#L1087)). Removing the source link, migrating providers, cloning a draft or changing its authoring authority cannot turn inherited protected material public. If lineage/policy is unavailable, refuse the fork/publication. Declassification is excluded from the initial design; it would need a separately authorized explicit operation, not a migration side effect.

### Concrete schema, compatibility and contract cost

**Scoped pre-GA storage decision:** [the implementation plan](../plan.md) uses fresh ActivitiesDesign format 2.0.0 stores under [ADR 0078's current baseline policy](../../../docs/adr/0078-workflow-executions-are-virtual-actors-and-cluster-membership-is-a-foundation-contract.md#consequences). Existing preview databases are preserved and unsupported by the new format; this unit adds no in-place/rolling upgrader or finalization override. Classification below applies to supported-format unclassified material and trusted current inventories. It does not claim schema-1 import or legacy receipt replay.

- Add the public requirement value to the catalog version read-model/factory/clone boundary and closed publication model; the current factory and `From` explicitly copy fields ([factory:33](https://github.com/elsa-workflows/elsa-foundation/blob/1bf3d5955a42222a5b62e4b0d463e17c43eedd16/Essentials/src/Activities/Design/Persistence/Core/Services/ActivityDefinitionVersionFactory.cs#L33), [entity:115](https://github.com/elsa-workflows/elsa-foundation/blob/1bf3d5955a42222a5b62e4b0d463e17c43eedd16/Essentials/src/Activities/Design/Persistence/Core/Entities/ActivityDefinitionVersion.cs#L115)). Add server-owned inherited requirements to authoring/draft and fork reservation/receipt material. Update both [catalog/publication projections:13](https://github.com/elsa-workflows/elsa-foundation/blob/1bf3d5955a42222a5b62e4b0d463e17c43eedd16/Essentials/src/Workflows/Publishing/Elsa.Workflows.Publishing/Services/ActivityCatalogProjection.cs#L13), atomic material comparisons, equality/duplicate checks and management projection references. Commit validation requires the catalog/publication copies to agree exactly. Public interface/package/API-surface changes require review and versioning; an omitted field cannot default to `Public` for new contributions.
- Persist serialized requirement metadata in Activities Design, with explicit validation and write-once guards for immutable version/publication and inherited lineage. Regenerate the four real provider Initial baselines for this fresh-store preview profile; those are current migration families, for example [SQLite initial:1](https://github.com/elsa-workflows/elsa-foundation/blob/1bf3d5955a42222a5b62e4b0d463e17c43eedd16/Essentials/src/Activities/Design/Persistence/EntityFrameworkCore/Migrations/ActivitiesDesign/Sqlite/20261104061016_Initial.cs#L1). No Runtime event ABI, record store or executable-template schema is selected by this metadata change.
- Keep existing executable behavior/template hashes unchanged. Compare canonical requirement metadata independently in reconciliation/publication/atomic/fork identity checks; a different requirement at an existing immutable version is a conflict, not an input-presentation refresh. Review supported-format classification explicitly; do not silently rehash or republish existing executable artifacts or imply an old-database upgrade.
- Supported-format missing metadata is **unresolved**, not public. Stamp explicit `Public` for positively identified existing code-owned public entries using reviewed owning-package/catalog inventory tied to exact identity/content; stamp protected requirements where a qualified owner can reconstruct them. Unknown custom/source-private rows remain unavailable pending explicit classification. Existing `TenantId=null`, `SourceKind="CLR"`, an unregistered key or an absent facet is never sufficient evidence by itself. This preserves intentional old/global code catalog entries while avoiding a permanent null-means-public bypass for new private entries. The compatibility inventory/mapping and treatment of unresolved deployments are required migration evidence.
- Enable protected contribution publication only on a deployment whose normal catalog/detail/construct/options/assistant/read paths enforce the retained requirement, including old retained contexts. A schema column cannot make an older reader respect it. Mixed-version hosts or consumers that ignore the marker must not coexist with newly published private entries; require coordinated upgrade/capability admission before enabling that provider profile. Otherwise the first old reader remains a disclosure path even though new readers fail closed.
- Runtime-only inspection that exposes copied private schemas must retain enough source-policy association in its owning Runtime/integration contract to guard that disclosure without Design services. That deployment/material decision still needs explicit agreement; the Design marker is not a reason to add Runtime → Design dependencies or a claim that Runtime inspection is already qualified.

The owner agreement covers first-class retained requirements, trusted forced admission, explicit legacy classification and monotonic fork inheritance. The scoped implementation plan resolves member names, serialization and registry registration through normal technical review; it does not reopen this boundary or silently adopt a Runtime/source-use ABI.

## Trusted context, compatibility and failures

**Interactive authority:** use the normalized principal and request tenant selected by the host, plus the existing endpoint/module permission. The current Activities adapter establishes these from the HTTP context ([authorization context:36](https://github.com/elsa-workflows/elsa-foundation/blob/1bf3d5955a42222a5b62e4b0d463e17c43eedd16/Essentials/src/Activities/Design/Api/Services/HttpContextActivityDesignAuthorizationContext.cs#L36)); follow that trust boundary. Catalog consumers must not supply principal/tenant/permission strings as ordinary authoring inputs. An absent request identity is not implicit global access.

**Workload authority:** use an explicit host/Runtime-owned workflow or workload resource authority, not whichever HTTP principal happens to be present, the workflow author's old claims, a task participant or an event payload. [ICurrentSubjectPermissionAuthorizer:56](https://github.com/elsa-workflows/elsa-foundation/blob/1bf3d5955a42222a5b62e4b0d463e17c43eedd16/Essentials/src/Foundation/Identity/Core/Authorization/AuthorizationContracts.cs#L56) can re-evaluate a persisted subject where a selected identity provider supports it; its default is Unsupported and store failures propagate so work can remain owed. This is a reusable option, not proof of an agreed workload identity or permission grant. Shared event admission/delivery must follow the still-unagreed #3912/#3904 current/retained responsibility contract; this proposal selects neither grant lifetime nor ingress/resumption ABI. Fresh external reads/operations require current source authorization regardless.

**Tenant/global compatibility:** retain persistence isolation before resource policy. EF currently returns own-tenant plus intentional global rows ([AccessFilter:1705](https://github.com/elsa-workflows/elsa-foundation/blob/1bf3d5955a42222a5b62e4b0d463e17c43eedd16/Essentials/src/Activities/Design/Persistence/EntityFrameworkCore/Stores/EfActivityDesignStores.cs#L1705)); #3917 must preserve the private owner through publication. A global row is not itself a source-use grant. Keep truly public code-owned globals unchanged. A generic public source-independent operation template can remain global only if its metadata contains no private source schema; its selected connection is checked at options/publication/use. Source-specific private schemas should be tenant-owned and retain source/incarnation identity. Declaring a private source schema global for convenience is not a supported compatibility shortcut. Mixed owner/source associations must refuse rather than retarget.

**Failure policy:** denied resources contribute no private entry/existence/count. Unknown protected owner, unsupported policy, source/connection/identity outage or invalid binding yields unavailable/refusal, never allowed or successful empty capabilities. For the first version, prefer a fixed unavailable outcome for a catalog read whose protected portion cannot be decided, rather than extending the current result into a silently partial catalog; narrower independently requested public resources can still succeed. Preserve original causes for safe operator diagnostics and wrap infrastructure failures at the owning boundary. The existing Core catalog has a fixed cause-free unavailable exception ([contract:31](https://github.com/elsa-workflows/elsa-foundation/blob/1bf3d5955a42222a5b62e4b0d463e17c43eedd16/Essentials/src/Activities/Design/Core/Contracts/IActivityAuthoringCatalog.cs#L31)). Do not list inaccessible source names in that message.

**Caching:** start with no new reusable positive disclosure/source-use authorization cache. Cache immutable metadata independently of grants; a scoped service must not retain a positive resource decision for a whole HTTP request, streaming assistant turn, checkpoint sequence or session. One explicitly bounded read/admission batch may use its freshly computed decision set for that same projection only. Existing assistant deduplication is limited to an explicit `AgentAdmissionPass`: each distinct snapshot/flags is admitted at most once, the pass ends at the next write, provider call or tool execution, and it is never a service field or reused across passes/checkpoints/turns ([AgentDisclosureHistory.cs:192](https://github.com/elsa-workflows/elsa-foundation/blob/1bf3d5955a42222a5b62e4b0d463e17c43eedd16/Extensions/Agent/src/Elsa.Agent/Services/AgentDisclosureHistory.cs#L192)). Source-resource owner admission must run again in each new pass, including several passes within one HTTP stream. Owner-admission awaits and tool discovery may belong to that single pass; they do not extend its lifetime past those boundaries. Any later authorization cache needs a separately agreed bounded-staleness/revocation contract, with authority/tenant/source/incarnation/schema/resource/policy-revision keys. Credential rotation and connection recreation remain different: the resolver exposes `Version` and `IncarnationId` ([resolver:77](https://github.com/elsa-workflows/elsa-foundation/blob/1bf3d5955a42222a5b62e4b0d463e17c43eedd16/Essentials/src/Connections/Elsa.Connections/Services/DefaultConnectionResolver.cs#L77)); neither substitutes for source/schema revision or permits name recreation to retarget old entries.

**Metadata HTTP transport can reuse context-free Connections contracts.** Public [IConnectionResolver:9](https://github.com/elsa-workflows/elsa-foundation/blob/1bf3d5955a42222a5b62e4b0d463e17c43eedd16/Essentials/src/Connections/Core/Contracts/IConnectionResolver.cs#L9) resolves the connection using the trusted tenant and selected connection reference; public [IHttpRequestAuthenticator:9](https://github.com/elsa-workflows/elsa-foundation/blob/1bf3d5955a42222a5b62e4b0d463e17c43eedd16/Essentials/src/Connections/Core/Contracts/IHttpRequestAuthenticator.cs#L9) applies its credentials to an outbound request without an activity execution context. A metadata provider can use those contracts directly after source-use/disclosure authorization, select the registered authenticator for the resolved scheme, and dispose the resolved connection. Missing or ambiguous transport composition must refuse rather than bypass credentials or source policy. Built-in authenticators enforce allowed hosts and HTTPS before applying credentials ([host guard:19](https://github.com/elsa-workflows/elsa-foundation/blob/1bf3d5955a42222a5b62e4b0d463e17c43eedd16/Essentials/src/Connections/Elsa.Connections/Http/HttpRequestAuthenticators.cs#L19), [bearer application:129](https://github.com/elsa-workflows/elsa-foundation/blob/1bf3d5955a42222a5b62e4b0d463e17c43eedd16/Essentials/src/Connections/Elsa.Connections/Http/HttpRequestAuthenticators.cs#L129)); preserve those controls and safe secret logging. Only the workflow-facing [IHttpConnectionApplicator:11](https://github.com/elsa-workflows/elsa-foundation/blob/1bf3d5955a42222a5b62e4b0d463e17c43eedd16/Essentials/src/Activities/Http/Connections/IHttpConnectionApplicator.cs#L11) requires `ActivityExecutionContext`; its [implementation:40](https://github.com/elsa-workflows/elsa-foundation/blob/1bf3d5955a42222a5b62e4b0d463e17c43eedd16/Essentials/src/Connections/Workflows/Services/HttpConnectionApplicator.cs#L40) obtains the execution partition and registers applied secrets with invocation masking (lines 62–64). Do not fabricate an activity execution context for metadata discovery or claim that transport resolution authenticates the Elsa user's right to use that source. That real source-use policy remains a separate agreement and qualification gate; context-free transport reuse does not satisfy it.

Within the approved catalog unit, implementation design must specify: (1) contract owner and narrow optional Integrations boundary; (2) the recommended first-class retained public/protected requirement, forced admission, legacy classification and monotonic fork inheritance; (3) Elsa source-use permission/resource policy distinct from Connections management; (4) exact-entry historical assistant recheck and required evidence/session refusal when it fails or cannot be established; (5) pre-count query/cursor integration, explicit admission-pass lifetime and initial whole-schema/whole-read failure behavior. The separate entity-operation/event units must agree on trusted workload authority and Runtime delivery responsibility; this catalog decision does not grant them or block independent catalog foundation work. No storage backend, new binding language, second catalog, fake publisher or record module is selected.

The first implementation must demonstrate the same allowed/denied/unavailable decisions through every surface above, using two differently permitted sources under one provider, same-tenant denied users, foreign tenants, current and retained assistant context, guessed IDs, options and counts/cursors, revocation, provider removal and outages. Intentional global code-owned entries must retain their behavior. That is a qualification obligation for the agreed design, not evidence already supplied by the global synthetic catalog or narrow typed-input witnesses.

Assistant qualification must include revocation or policy-owner outage after the original catalog disclosure, with derived assistant text and a provider SDK that retains historical transcript state. The next historical admission must fail as required before provider/tool reuse; an optional diagnostic plus a dropped attachment cannot pass. Also revoke/change source authority between write, provider-call or tool-execution boundaries within a single streaming HTTP turn: a positive result from an earlier pass cannot authorize the later pass.

For the admission representation specifically, retain an actual protected entry, remove its provider/policy implementation and reopen: every disclosure path must still recognize its protected requirement and refuse/unavailable without private names or counts. Also prove that a registered protected producer cannot publish `Public`/missing requirements (including through the no-publisher reconciliation path or the duplicate shortcut), that a fork/provider migration cannot strip inherited requirements, and that changing only the requirement at an existing version conflicts even when executable behavior is unchanged. A reviewed legacy public global entry must remain available, while an unresolved legacy custom entry remains withheld. These are causal negative cases for the proposed representation, not passed results.
