1. **[P2] Expose the protocol initialization event from Runtime Core.** `Essentials/src/Workflows/Runtime/Elsa.Workflows.Runtime/Services/Executions/RuntimeExecutionProtocolRegistry.cs:11–13` declares `RuntimeExecutionProtocolsInitializing` as an internal implementation type, although the public `IRuntimeExecutionProtocolContributor` and cross-domain BPMN feature feed this contribution point. Ratified framework §2.6.1 requires domain contribution points to be named events in the domain `.Core`; §2.18.2/§2.23.3 require an extension contract that another feature can consume to be public. External protocol contributions do work through the public contributor port and its single internal aggregator. The issue is the mandatory ownership of the contribution event itself, not failed driver registration: a third-party feature cannot depend on this named event/payload from Core or compile an independent `IEventHandler<RuntimeExecutionProtocolsInitializing>` using it. The approved plan also places this named event in Runtime Core, and explicitly requests no constitutional exception. Move the public sealed event/payload to Core, retain one internal aggregator and Sequential startup publication, and update API tracking/catalog. Existing binary reflection confirms `IsPublic=False`; no owner exception for this placement appears in the cached discussion.

2. **[P2] Wrap nested BPMN JSON failures at the model-runtime boundary.** `Essentials/src/Activities/Bpmn/Elsa.Activities.Bpmn/Internal/BpmnDirectExecutionDriver.cs:362` deserializes the nested process without wrapping `JsonException` (the definition/input deserializers have the same boundary issue). A valid `BpmnModelDefinition` envelope can contain process JSON `{"elements":42}` because its constructor admits an object; publication reaches this line through `BpmnModelRuntime.PublishAsync:53`. The error escapes `IBpmnModelRuntime` as raw `System.Text.Json.JsonException`, rather than `BpmnModelValidationException` with an inner cause/context. Ratified framework §2.23.5 expressly forbids a raw infrastructure exception crossing a feature boundary and requires a documented domain exception. The HTTP renderer at `BpmnHostingApi.cs:113` already handles `JsonException` as400; no unhandled HTTP500 is claimed. Independently, a non-HTTP model-runtime/driver caller receives a serializer-specific failure, bypassing its domain-validation exception handling and losing material/execution context. The required wrapper should preserve the original exception through the existing `innerException` constructor and document the public failure contract. Catch/wrap owned model-definition/input deserialization at the appropriate boundary, preserve the inner exception and relevant material/execution identity, and retain transport JSON parsing separately. A temporary reflection diagnostic reproduced the raw exception against existing Release binaries at `4d77feefd`; `git diff 4d77feefd HEAD --` confirms both affected production files are identical at the reviewed head. Diagnostic source is `/tmp/elsa-2898-review-1/standards-diagnostic/Program.cs`.
