## S1 — P2: Normalize failures at the new model-material boundary

**Primary current line:** `Essentials/src/Workflows/Runtime/Persistence/EntityFrameworkCore/Stores/EfWorkflowExecutableStore.ModelMaterial.cs:22` (new `IWorkflowExecutableStore.FindMaterialAsync`). The same finding also applies to the initial load and outer catch in `SaveModelAsync` at lines 40 and 67–69, and the new `ListMaterialPageAsync` query at lines 87–90.

**Concrete scenario:** A qualified EF model-material provider in persistence scope `tenant-a` receives a non-cancelled operation token, but opening the authoritative store raises `IOException` or an internal `OperationCanceledException`. `FindMaterialAsync` calls `LoadPairAsync` without a boundary catch. The existing artifact query helper wraps provider/InvalidOperationException shapes but explicitly propagates cancellation and does not normalize IOException. The new list method uses the same helper. The new save method's initial `LoadPairAsync` is inside a catch that accepts provider-classified failures only. All six I/O/unrequested-cancellation cases escape as the *identical raw exception instance*, with no scope, artifact or operation context and no contextual domain exception retaining it as InnerException.

This is observable through the **new model-material contract**, rather than an invented consumer: `BpmnModelRuntime.StartAsync` reads the published source's physical material at `Internal/BpmnModelRuntime.cs:103`; model dispatch/recovery also reads it at `Services/Executions/RuntimeExecutionProtocolSelector.cs:62`. Publication uses new `SaveModelAsync` at `BpmnModelRuntime.cs:72`, while model-aware dependency closure and retention use new `ListMaterialPageAsync`. These callers do not establish a catch around the particular material operation before it leaves that public provider boundary. A storage-originated cancellation is consequently indistinguishable from caller cancellation at that boundary. **No separate HTTP response, scheduler deletion, data loss, or real provider outage is claimed.**

**Governing rule:** ratified Framework §2.23.5 explicitly includes `IOException` among infrastructure exceptions that must not cross a feature boundary unwrapped. The wrapping domain exception must retain the original cause and identifying context, and public methods document it. Spec1017's hosting contract and state model separately require contextual infrastructure failures while caller cancellation remains cancellation. The existing default native artifact implementation has the same inherited behavior, but the present finding is limited to the **three newly added model-material operations** and their current real consumers. It does not assert this PR introduced the pre-existing native defect.

**Independent validation:** `/tmp/elsa-2898-c531-followup/review15/standards-material-probe/Program.cs`, `Probe.csproj` and `results.json`. The executable references the actual Workbench product DLLs, not a copied implementation or replacement store. Assembly metadata reports **9d4221e872c7f991e3a46919d8810a97ffee4e83** for the Runtime EF, Runtime Core and Persistence EF DLLs; their SHA-256 values are in the result. The relevant source trees of final F and 9d were independently shown identical. A public `RuntimeSqliteDbContext`, real `EfWorkflowExecutableStore` and `DbConnectionInterceptor.ConnectionOpeningAsync` exercise the real read path. Save receives a valid `RuntimeModelMaterial` with its correct recomputed content hash and fails before any mutation.

**Requested correction:** Give all three new operations a contextual domain boundary for I/O and unrequested storage cancellation, retain the original exception as InnerException, preserve caller-requested cancellation and existing corruption/identity refusal semantics, and document that public failure contract. Cover each operation and both failure forms, alongside provider and caller-cancellation controls. This does not require changing native semantics or the schema/writer formats.
