# Runtime-only partial fork recovery

Source [`58309bd997494bbe7e3f31fd7025c53d004c2a7c`](https://github.com/elsa-workflows/elsa-foundation/commit/58309bd997494bbe7e3f31fd7025c53d004c2a7c) was rebuilt and exercised through the production Workbench's authenticated BPMN HTTP endpoints. The explicit single-node runtime/authentication profile configures no Design or publication services/storage. Workbench discovers both BPMN implementation and API assemblies directly. The profile includes the existing file-system lock provider needed by the Tasks pump.

The process forks to two genuine model human waits. Completing the left branch leaves the right invocation/attempt active at revision 2. The owned process exits, restarts on the same store and returns the identical execution view and surviving work. Replaying the left completion changes neither. Completing the right branch produces exactly one modeled human wait after the join at revision 3; its replay creates no extra work. Completing that wait yields one terminal Completed result at revision 4. Four input receipts/checkpoint markers and zero native workflow/activity/bookmark rows are checked.

[Observations, feature names, SQLite table catalogs and binary versions/hashes](process.json) identify both processes and all pins/incarnations. All three owned database catalogs lack Design/definition tables, and `design.db` is absent. Identity data and configuration are not exported. The consistent closed-host [partial](partial.sqlite.gz) and [completed](completed.sqlite.gz) Runtime snapshots pass integrity/hash checks. [Qualification](qualification.json) records the rebuilt three-test whole host suite and ten composition/discovery/catalog checks, all passing with zero skips.

This adds actual runtime-only partial-fork/join recovery to the initial direct human witness. It does not prove changed-binary or legacy upgrade, clustered placement, timer/broadcast/cancellation/settlement, actual native/ETL work bindings or Studio acceptance.
