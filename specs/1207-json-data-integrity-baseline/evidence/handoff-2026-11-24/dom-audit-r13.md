## Additional actionable findings

### 1. [P2] Standalone trigger read/save normalizes untouched configuration data

`essentials/src/Workflows/Runtime/Api/StandaloneTriggers/TriggerManagement.Configuration.cs:11` parses the stored `StandaloneTrigger.Configuration` JsonElement as a JsonObject; line 15 serializes that object back. This happens even when `ProtectedPaths(trigger)` is empty and no redaction occurred. `TriggerManagement.ReadAsync` calls `ViewAsync`, which calls this helper and returns its configuration in the API read model. Thus a read of an unchanged configuration changes inner whitespace/escape spellings. TriggerConfigurationField explicitly supports json-valued fields; configuration is not restricted to control scalars.

The paired save path at lines 20–29 similarly parses proposed and stored configuration as JsonNode, reinserts protected leaves, and serializes the entire proposed object. `BuildChange` handles SaveConfiguration using this value, validates it and places it into the next aggregate. Even when there are no sensitive fields, or only the trigger name changed, accepted raw configuration is re-emitted before storage. The generic StandaloneTrigger constructor clones the original JsonElement; the normalization comes from these helpers, not its model/store contract.

Reproduction: use the existing `StandaloneTriggerManagementTests.Configuration.cs` ConfigurationFixture with an event type, no sensitive fields and a json field containing `{ "OwnerKey":"Ren\u00e9", "n":1.0, "wide":12345678901234567890123456789012345, "x":null }`. Assert the exact field GetRawText through Management.ReadAsync, then Preview/Apply a SaveConfiguration carrying the same JsonElement and assert the stored aggregate plus returned read. Add a sensitive sibling/path case so protecting a secret does not alter the retained public fragment or preserved secret fragment. Preserve existing protected-path, null and preview/authorization behavior; this finding does not request any policy change.

### 2. [P2] Agent continuity metadata rewrites already accepted result fields

`extensions/Agent/src/Elsa.Agent/Services/AgentNativeControls.cs:79` parses `accepted.Result` into a JsonObject, adds the Conversation control member at line 81 and serializes the whole object at line 82. Every existing result field is therefore rewritten while only an unrelated control member needed adding. With controls disabled the same method returns the original JsonElement directly.

This is a concrete persisted-result-to-workflow-value path, rather than merely a new reporting document: AgentActivity.OnChildCompletedAsync calls the authenticated AgentTurnJournal.ResultAsync, passes its retained AgentTurnResult to Complete, and then PrepareCompletionCheckpointAsync uses acceptedResult as the activity completion result. ResultAsync deserializes the protected accepted journal envelope with the baseline-derived AgentJson profile. Adding Conversation must not normalize an unchanged accepted Article token or nested JSON output field.

Reproduction: adapt the existing continuity-enabled AgentNativeTests fixture with accepted model JSON `{"Article":"Ren\u00e9"}` and assert the Article GetRawText from the accepted receipt and resulting completion remains `"Ren\u00e9"`; also exercise an object-valued output field with inner whitespace, explicit null and a number beyond decimal precision. Compare controls enabled/disabled, assert the reserved Conversation member still has the correct session/revision and keep collision/contract refusals. Changing the outer result's control envelope is legitimate; changing its untouched carried data fields is the defect.
