# Feature Specification: Single Diff-Based Draft Update Command

**Feature Branch**: `003-single-update-command`
**Created**: 2026-06-02
**Status**: Draft
**Input**: User description (Unit 2 — design-domain roadmap): "Replace Unit C's granular Draft-mutation commands with ONE coarse `IUpdate` command that, under the existing per-Draft distributed lock, loads existing Draft state → diffs incoming vs stored → emits one event per detected difference (re-homing the granular Design.Core event types as the events `IUpdate` emits, keeping event-sourcing open for Unit H) → persists. Keep the lifecycle commands. Adjust `DraftMutationPipeline` to the single-command shape. Per-diff events publish on the Unit 1 unified `IEvent` / `IEventHandler<T>` / `IEventPublisher` substrate. The `OnDraftValidating` (Sequential gate) / `OnDraftValidated` (Background outcome) validation pair stays."

---

## Context

Unit C (feature `002-workflow-state-scope`) shipped a **granular CQS command surface** for Draft authoring: one command per mutation kind (add/remove/move activity; add/update/remove activity input; add/update/remove activity output; add/remove connection; declare/update/remove variable; add/update/remove workflow input; add/update/remove workflow output). The current codebase carries **20 granular mutation commands** in `Elsa.Workflows.Design.Persistence.Core.Contracts` (implementations in `Elsa.Workflows.Design.Persistence.EFCore/Commands`), each publishing one of **20 granular mutation events** declared in `Elsa.Workflows.Design.Core/Events`. Three lifecycle events (`OnDraftCreated`, `OnDraftClonedFromVersion`, `OnDraftDiscarded`) bring the Design.Core event total to **23**.

The 2026-06-01 architecture review (agenda Item 3 + the parked phase-2 "Item D" command-granularity discussion) leaned toward **one coarse update command "for now"** rather than the granular surface. Joey's phase-2 call (2026-06-02, registered in [`follow-up-items/2026-06-02_unit_single_update_command.md`](../../../elsa-foundation-project-management/epic1-elsa-refactor-constitution/follow-up-items/2026-06-02_unit_single_update_command.md)) commits to this and reshapes it: a single `IUpdate` command reads the existing Draft state, **diffs** the incoming desired state against it (variables, inputs, outputs, connections, activities, …), and **for each detected difference emits one event** — all inside that one command, under the existing per-Draft distributed lock.

Rationale (Joey): collapsing the granular surface makes the core code base cleaner and simpler "for now." A whole class of questions — how the UI invokes 20 distinct commands, how to batch them, how to order them — becomes irrelevant or non-blocking. It still leaves the door open for event sourcing (the per-diff events ARE the stream, consumed by Unit H), but removes the 20-command surface and the open UI-invocation questions.

This unit **depends on** Unit 1 (feature `001`-addendum — Unified event sending). Unit 1 collapsed the three former in-process pub/sub concepts (`IDomainEvent` / `INotification` / `ILifecycleEvent`) into the single `IEvent` concept published via `IEventPublisher.Publish(IEvent, IEventPublishingStrategy?, …)` in `Elsa.Events.Core` / `Elsa.Events`. The per-diff events `IUpdate` emits publish on that substrate. The existing `DraftMutationPipeline` already runs on it.

The audience for this spec is the architecture group (Joey + Sipke + Frans) and the AI agents implementing against the constitution. Stakeholder framing is architect-grade, not end-user.

## Terminology

### Diff-based update (Joey's working definition, 2026-06-02)

A **diff-based update** is a Draft authoring operation whose input is a **desired end-state** for one or more Draft-content dimensions (the full activity graph, the variable set, the workflow input/output declarations, …) rather than a single discrete mutation instruction. The command computes the **difference** between the incoming desired state and the currently-stored Draft state, and the set of differences it detects becomes the set of events it emits. One difference → one event. The events are the same per-dimension event types the granular commands used to publish individually; the command is the new single producer of all of them.

The diff is the seam that keeps event-sourcing open (Unit H): the ordered sequence of per-diff events across successive `IUpdate` calls IS the Draft's change stream, whether or not a stream subscriber is registered.

### What diff-based update is NOT

- **Not a coarse "replace the whole Draft and emit one `DraftUpdated` event" operation.** The point of the diff is to preserve the *granular per-dimension event surface* (the 20 mutation event types) so event-sourcing, audit, and validation consumers see semantically-typed changes, not an opaque "something changed."
- **Not a lifecycle operation.** Draft creation, clone-from-version, discard, and promote-to-version remain distinct lifecycle commands (see Scope). `IUpdate` only ever mutates an existing Draft's authored content.
- **Not a per-call validation owner.** Validation stays exactly as the Draft mutation flow runs it today: `OnDraftValidating` (Sequential gate, contribution pattern) inside the lock, `OnDraftValidated` (Background outcome) after release.

## Clarifications

### Session 2026-06-03

- Q: After the 20 granular public command contracts are deleted and the diff is semantic per-concept, what happens to the per-action *apply logic* the old commands carried? → A: **It survives as private apply-steps.** The public `IXxxCommand` contracts are deleted (FR-002 unchanged), but each per-action "apply this change to State + produce this typed event" body is **retained as a private internal apply-step** that the diff engine invokes once per detected concept-change. The diff engine stays a thin dispatcher; the 20-fold per-action logic becomes ~20 private apply-steps, not 20 public commands. This preserves the tested per-action logic under framework §2.21.1 (the *objective* — "applying change X produces event Y" — survives; tests migrate to drive the apply-step through `IUpdate`). (Resolves former FR-020 / Open Question 2; folds into FR-002, Key Entities diff engine.)
- Q: Under "full desired state always", how does `IUpdate` handle a desired state computed from a now-stale read (another writer committed between the client's read and the `IUpdate`)? → A: **Last-writer-wins, whole-draft.** `IUpdate` carries **no concurrency/version token**; the submitted desired state always wins wholesale. Any concurrent edit committed between the client's read and its `IUpdate` is silently overwritten — the per-Draft lock serialises the *writes* but does not detect a stale-based payload. Conflict *avoidance* is the workflow designer's responsibility (e.g. single-editor-per-Draft UX). This keeps the "full state always" model simple and leaves the `WorkflowDefinitionDraft` entity shape unchanged (no version column added). (Folds into FR-022, the concurrent-`IUpdate` edge case, Assumptions.)
- Q: What identity key does the semantic diff match on per dimension to decide UPDATE vs REMOVE+ADD (e.g. a rename)? → A: **Stable synthetic ids.** Activities match by `NodeId`; variables, workflow inputs/outputs, activity inputs/outputs, and connections each match by a **stable id that the desired-state payload round-trips**. A rename (or any in-place change to an element whose id is unchanged) is therefore a single **UPDATE** event (e.g. `OnVariableUpdatedInDraft`), not a REMOVE+ADD pair. This yields a cleaner change stream for Unit H (no false remove+add churn on rename) and requires the desired-state payload to carry those ids. (Folds into FR-023, Key Entities diff engine, Assumptions.)

### Session 2026-06-02

- Q: Should `IUpdate` and `DraftMutationPipeline` be **separate** (a thin command delegating to a reusable pipeline), or is the command itself the pipeline? → A: **The `IUpdate` command IS the mutation-pipeline shell.** There is no separate `DraftMutationPipeline` collaborator sitting alongside the command on the mutation path. The command's own implementation performs the canonical sequence: **(1) acquire the per-Draft lock → (2) load + diff/execute the update → (3) Sequential `OnDraftValidating` gate + rewrite the validation sibling → (4) transactional flush → (5) release lock → (6) Background-publish the per-diff mutation events + `OnDraftValidated`.** The existing `DraftMutationPipeline`'s **mutation path (`ExecuteMutation`) is absorbed into / becomes** the `IUpdate` command implementation. (Folds into FR-007, US3, Key Entities.)
- Q: Diff granularity — structural (per field) vs semantic (per domain concept)? → A: **Semantic, per domain concept.** `IUpdate` diffs at the level of the domain concepts the event surface already names (each activity, connection, variable, workflow input/output, and their sub-fields). Each detected concept-level change maps **1:1** to one of the 20 existing event types (e.g. a changed activity-input value → `OnActivityInputUpdatedInDraft`; a removed connection → `OnConnectionRemovedFromDraft`). The diff engine is concept-aware, not a generic field-tree differ. (Resolves former FR-019 / Open Question 1.)
- Q: Does `IUpdate` receive the complete desired Draft state, or a partial per-dimension subset? → A: **The complete desired state, always.** `IUpdate` receives the full desired Draft content; the diff is computed against the whole stored state. Absent elements mean removal; new elements mean add; changed elements mean update. There is no partial/patch mode — that would reintroduce the "which dimensions am I updating" scoping ambiguity this unit set out to eliminate. (Resolves an input-shape ambiguity flagged at clarify.)
- Q: Is designer layout (positions/sizes — the `OnActivityMovedInDraft` event, stored in the separate `WorkflowDefinitionDraftLayout` sibling, NOT in `WorkflowDefinitionState`) inside `IUpdate`'s scope? → A: **Yes — `IUpdate` covers layout too.** The desired-state input `IUpdate` receives also carries the desired layout; the command diffs the `WorkflowDefinitionDraftLayout` sibling alongside `WorkflowDefinitionState` and emits `OnActivityMovedInDraft` for each layout difference. `IUpdate` is the single entry point for all Draft content **and** layout. The §E2.9 in-State/out-of-State boundary is unaffected — layout stays in its sibling entity, never folded into `WorkflowDefinitionState`; `IUpdate` simply writes both. (Resolves the move-event producer gap.)
- Q: Now that the mutation pipeline is absorbed into `IUpdate`, how do the lifecycle commands (create/clone/discard/promote) obtain the lock/validate scaffolding — and are they in Unit 2's scope? → A: **The lifecycle commands are OUT of Unit 2's scope; they are dealt with separately.** Unit 2 absorbs only the *mutation* path into `IUpdate` and deletes the 20 granular mutation commands. The lifecycle commands keep functioning as Unit C shipped them. Ownership of their separate work: **`IPromoteDraftToVersionCommand` → Unit D** (PERSONAL_TODO roadmap item 6 — already owns the promote implementation alongside field allocation + multi-draft cardinality). **`ICreateDraftCommand` / `ICloneDraftFromVersionCommand` / `IDiscardDraftCommand`** already exist (shipped in Unit C, currently using `DraftMutationPipeline.ExecuteCreation`); their topology-alignment to the absorbed-shell shape (and the disposition of any residual `ExecuteCreation` path) is a **direct follow-up to this spec** — registered at [`follow-up-items/2026-06-03_followup_lifecycle_command_shells.md`](../../../elsa-foundation-project-management/epic1-elsa-refactor-constitution/follow-up-items/2026-06-03_followup_lifecycle_command_shells.md). Unit 2 MUST NOT break create/clone/discard; if leaving the residual `ExecuteCreation` path in place is the least-invasive way to keep them green, that is acceptable and the follow-up reworks it. (Folds into FR-003, FR-007, US3.)

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Collapse the granular command surface into one diff-based `IUpdate` (Priority: P1)

The 20 granular Draft-mutation commands are replaced by a single `IUpdate` command (provisional name) that accepts a desired Draft content state, diffs it against the stored Draft inside the existing per-Draft distributed lock, emits one per-diff event per detected difference on the Unit 1 `IEventPublisher` substrate, and persists. The 4 lifecycle commands (`ICreateDraftCommand`, `ICloneDraftFromVersionCommand`, `IDiscardDraftCommand`, `IPromoteDraftToVersionCommand`) are untouched. The `OnDraftValidating` / `OnDraftValidated` validation pair is untouched.

**Why this priority**: This is the load-bearing deliverable of Unit 2. It is the simplification Joey committed to and the substrate every later design-domain unit builds on. Stories 2 and 3 (event re-homing, pipeline reshape) are the mechanical consequences of this collapse and make no sense without it.

**Independent Test**: A single call to `IUpdate` with a desired state that differs from the stored Draft in several dimensions (e.g. one added activity, one removed connection, one renamed variable) results in exactly the corresponding per-diff events being published and the Draft's persisted `State` reflecting the desired state, all under one lock acquisition. The 20 granular command contracts no longer exist on the public surface.

**Acceptance Scenarios**:

1. **Given** a Draft with stored State S0 and an incoming desired State S1 that adds one activity, removes one connection, and updates one variable, **When** `IUpdate` executes, **Then** exactly three per-diff events are published (`OnActivityAddedToDraft`, `OnConnectionRemovedFromDraft`, `OnVariableUpdatedInDraft`), the persisted State equals S1, and only one `workflow-draft:{DraftId}` lock was acquired for the whole operation.
2. **Given** an incoming desired State identical to the stored State (no differences), **When** `IUpdate` executes, **Then** zero per-diff events are published, the validation pair still runs (per the unchanged pipeline), and persistence is a no-op-equivalent (State unchanged).
3. **Given** the post-collapse codebase, **When** the `Elsa.Workflows.Design.Persistence.Core.Contracts` surface is inspected, **Then** the 20 granular mutation command contracts (`IAddActivityToDraftCommand`, `IRemoveConnectionFromDraftCommand`, … the full set) are gone and a single `IUpdate` (or its committed final name) replaces them, while the 4 lifecycle command contracts remain.

### User Story 2 — Re-home the granular mutation events as `IUpdate`'s per-diff emissions (Priority: P2)

The 20 granular mutation event types in `Elsa.Workflows.Design.Core/Events` are preserved as **event types** and become the events `IUpdate` emits, one per detected difference. The 3 lifecycle events (`OnDraftCreated`, `OnDraftClonedFromVersion`, `OnDraftDiscarded`) stay bound to their retained lifecycle commands. The `EVENTS.md` catalog (renamed from `DOMAIN_EVENTS.md` on 2026-05-29) and its parity test (Unit C FR-030 / FR-031) are updated so the documented publication site of each mutation event is `IUpdate` rather than the deleted granular command.

**Why this priority**: Re-homing keeps the granular event surface — and therefore event-sourcing (Unit H), audit, and per-dimension validation consumers — intact across the command collapse. Without it, the simplification would either drop the typed event surface (closing the event-sourcing door this unit is explicitly told to keep open) or leave the catalog describing publication sites that no longer exist.

**Independent Test**: After the collapse, all 20 mutation event types still exist in `Elsa.Workflows.Design.Core/Events`; a diff that touches each dimension causes the matching event to be published by `IUpdate`; the catalog-parity test passes with every mutation event's documented publication site naming `IUpdate`.

**Acceptance Scenarios**:

1. **Given** the 20 mutation event types existed pre-collapse with per-command publication sites, **When** Unit 2 lands, **Then** all 20 types still exist unchanged in shape, every one is reachable as a `IUpdate` per-diff emission, and none is deleted.
2. **Given** `EVENTS.md` (the catalog, renamed from `DOMAIN_EVENTS.md` 2026-05-29) documented each mutation event's publication site as a granular command, **When** Unit 2 lands, **Then** each mutation event's documented publication site is updated to `IUpdate` and the parity test (FR-031) passes.
3. **Given** the 3 lifecycle events, **When** Unit 2 lands, **Then** they remain bound to `ICreateDraftCommand` / `ICloneDraftFromVersionCommand` / `IDiscardDraftCommand` respectively and are NOT emitted by `IUpdate`.

### User Story 3 — Absorb the mutation pipeline into the `IUpdate` command shell (Priority: P2)

Today the Draft mutation flow lives in `DraftMutationPipeline.ExecuteMutation`, which takes a `mutateDelegate` closure that mutates State and returns **one** `IEvent`, and the granular commands are thin callers of it. Unit 2 **collapses that indirection**: the `IUpdate` command's own implementation IS the shell. Its body performs the canonical sequence directly — acquire the per-Draft lock → load + diff (producing **a set** of per-diff events) → Sequential `OnDraftValidating` gate → rewrite the validation sibling → transactional flush → release lock → Background-publish the per-diff events + `OnDraftValidated`. There is no separate `DraftMutationPipeline` collaborator retained alongside the command. The Sequential-gate / Background-outcome validation structure and the lock/transaction ordering are preserved exactly; only the topology (command-is-the-shell) and the "one event per mutation → N per-diff events per update" assumption change.

**Why this priority**: The mutation shell is the single point of entry to Draft state changes and the home of the lock + validation + ordering guarantees. Absorbing it into the command removes the closure indirection Unit C introduced (a thin command wrapping a pipeline) while keeping every guarantee. It must accommodate a set of events from one command without losing the cause-before-effect ordering (`OnDraftValidated` after the mutation events) or the single-transaction persistence of State + validation sibling.

**Independent Test**: An `IUpdate` call producing N per-diff events runs with exactly one lock acquisition, one transactional flush of State + validation sibling, the Sequential `OnDraftValidating` gate running once against the post-diff state, and the N mutation events + one `OnDraftValidated` published Background after lock release in cause-before-effect order — all inside the command's own implementation, with no `DraftMutationPipeline` type remaining as a separate collaborator.

**Acceptance Scenarios**:

1. **Given** the `IUpdate` command shell, **When** an update produces N per-diff events, **Then** all N publish Background after lock release and before/around the single `OnDraftValidated`, preserving cause-before-effect order (mutation events as cause, validation outcome as consequence).
2. **Given** the `IUpdate` command shell, **When** any update executes, **Then** `OnDraftValidating` is published exactly once (Sequential) against the post-diff Draft state, the validation sibling is rewritten wholesale from the collected errors, and State + sibling flush in one transaction inside the lock.
3. **Given** the absorption, **When** Unit 2 lands, **Then** no separate `DraftMutationPipeline` type remains as a collaborator of the command; the lock/validate/persist/publish logic lives in (or is privately owned by) the `IUpdate` implementation. How the lifecycle commands obtain the same lock/validate scaffolding is settled per the Clarifications session (see below).

### Edge Cases

- **Incoming desired state introduces an entity with a NodeId / reference key that does not yet exist (add) AND removes another that does (remove) in the same call.** The diff yields both an add event and a remove event; both publish; both apply. The diff is **semantic (per domain concept)** per the 2026-06-02 Clarifications session, so each concept-level change maps 1:1 to one event type. The exact *ordering* among the per-diff events within one `IUpdate` (e.g. whether removes precede adds) is a plan-stage detail, not a blocking clarification — the cause-before-effect guarantee that matters constitutionally is mutation-events-before-`OnDraftValidated` (FR-006), which holds regardless of intra-update ordering.
- **Incoming desired state is byte-identical to stored state.** Zero diffs → zero mutation events. The validation gate still runs (the pipeline always validates), so a Draft that was already invalid stays invalid and a re-validation pass can still update the sibling. This is intentional: validation is a property of state, not of mutation.
- **A single field changes on an existing activity (e.g. one input value).** Per the 2026-06-02 Clarifications session (semantic, per domain concept), this surfaces as the concept-named event — a changed activity-input value → `OnActivityInputUpdatedInDraft` — not a coarser opaque "property changed" event. The diff engine is concept-aware, mapping each detected concept-level change 1:1 to one of the 20 existing event types.
- **An element is renamed (e.g. a variable's name changes) but its identity is otherwise stable.** Because the diff matches on **stable synthetic ids** (FR-023), the element is recognised as the same one across desired vs stored, so a rename surfaces as a single UPDATE event (`OnVariableUpdatedInDraft`) — NOT a REMOVE of the old name plus an ADD of the new. A REMOVE+ADD only occurs when the *id* differs (genuinely a different element).
- **Two concurrent `IUpdate` calls target the same Draft.** The *writes* are serialised by the per-Draft lock (Unit C FR-027): the second waits, then diffs against the first's committed result. But concurrency is **last-writer-wins, whole-draft** (FR-022): if the second call's desired state was computed from a read taken *before* the first call committed, the second payload lacks the first's additions, so the diff legitimately emits REMOVE events that undo the first writer's work — and that overwrite is intentional, not a fault. `IUpdate` carries no version token to detect the stale read; conflict *avoidance* (e.g. single-editor-per-Draft UX) is the designer's responsibility, out of Unit 2's scope.
- **A per-diff event handler throws (e.g. a flaky event-sourcing subscriber).** Mutation events publish Background; per Unit 1 the Background strategy catches and logs, so a throwing subscriber never breaks `IUpdate`. The Sequential `OnDraftValidating` gate is the only synchronous publish and is owned by trusted in-process validators.
- **The desired state would, if applied, leave the Draft invalid.** The diff still applies and the mutation events still fire (the user's authoring intent IS the transition, per the existing pipeline rationale); the validation sibling records the errors; promotion (`IPromoteDraftToVersionCommand`) remains gated on an empty error set (Unit C FR-024). Invalid intermediate states are a normal authoring condition, not a command failure.

(No deletion arises, so no §2.21.1 architect-approval gate is triggered.) Additionally, the single diff engine introduces **net-new behaviours that no individual granular command exercised**, each of which MUST be tested in its own right: (a) **no-op** — desired == stored emits zero mutation events while the validation pair still runs (SC-009); (b) **multi-dimension diff in one `Execute`** — several changes across activities/connections/variables/inputs/outputs/layout yield exactly the corresponding set of events in deterministic order (Scenario 1); (c) **last-writer-wins overwrite** (SC-014); (d) **rename = single UPDATE** vs **id-change = REMOVE+ADD** (SC-015); (e) **connection change = REMOVE+ADD** (connections have no update event); (f) **activity removal cascades to connection prune**; (g) **cause-before-effect ordering** — per-diff events precede `OnDraftValidated`. No test is silently dropped.

- **FR-017**: The diff-based design MUST keep event-sourcing open for Unit H. The ordered sequence of per-diff events across successive `IUpdate` calls IS the Draft change stream; with no stream subscriber registered the events publish and are no-op'd (closed mode); with a Unit H subscriber registered they are persisted to the future stream (open mode). - **FR-018**: A Unit 2 follow-up file MUST exist/stay maintained at [`follow-up-items/2026-06-02_unit_single_update_command.md`](../../../elsa-foundation-project-management/epic1-elsa-refactor-constitution/follow-up-items/2026-06-02_unit_single_update_command.md) per meta-repo `CLAUDE.md` §5, and `PERSONAL_TODO.md` MUST reflect Unit 2's status as it progresses.
- **FR-022**: `IUpdate` MUST use **last-writer-wins, whole-draft** concurrency semantics. The command MUST NOT carry or check a concurrency/version token: the submitted desired state always wins wholesale, and a desired state computed from a now-stale read is applied as-is (silently overwriting any edit committed between the client's read and the `IUpdate`). The per-Draft lock (FR-009) serialises *writes* only; it does not detect a stale-based payload. The `WorkflowDefinitionDraft` entity gains no version column. Conflict *avoidance* is out of scope for Unit 2 (a workflow-designer UX concern, e.g. single-editor-per-Draft).
- **FR-023**: The semantic diff MUST match elements on **stable synthetic ids** to decide UPDATE vs REMOVE+ADD per dimension: activities by `NodeId`; variables, workflow inputs/outputs, activity-level inputs/outputs, and connections each by a stable id carried (round-tripped) in the desired-state payload. An in-place change to an element whose id is unchanged (including a rename) MUST surface as a single UPDATE event (e.g. `OnVariableUpdatedInDraft`), never a REMOVE+ADD pair. An element whose id is absent from the desired state is a REMOVE; an element whose id is absent from the stored state is an ADD. The desired-state input shape (FR-001) MUST therefore expose those ids; the concrete carrier type is a plan-stage detail.

### Open / Unresolved Requirements *(flagged for `/speckit.clarify`)*

- **FR-019** *(RESOLVED 2026-06-02 — semantic)*: Diff granularity is **semantic, per domain concept**. `IUpdate` diffs at the level of the domain concepts the event surface already names (each activity, connection, variable, workflow input/output, and their sub-fields); each detected concept-level change maps **1:1** to one of the 20 existing event types. The diff engine is concept-aware, not a generic field-tree differ. (Was Open Question 1.)
- **FR-020** *(RESOLVED 2026-06-03 — survive as private apply-steps)*: The 20 granular commands' **public contracts vanish** (FR-002) but their per-action **apply logic survives internally as the diff engine's private apply-steps**. FR-002's removal is therefore a **public-surface-only removal**: the diff engine is a thin dispatcher that, for each detected concept-change, invokes the matching private apply-step (which mutates State and produces the typed event). The per-action bodies are migrated, not deleted; their tests' objectives are preserved per framework §2.21.1 by re-pointing them through `IUpdate`. (Was Open Question 2.)
- **FR-021** *(RESOLVED 2026-06-03 — plan phase, [research.md](./research.md) R7)*: The command is named **`IUpdateDraftCommand`** (impl `UpdateDraftCommand`, method `Execute(UpdateDraftRequest, CancellationToken)`) — chosen over the provisional bare `IUpdate` for consistency with the retained lifecycle command family (`ICreateDraftCommand`, `ICloneDraftFromVersionCommand`, `IDiscardDraftCommand`, `IPromoteDraftToVersionCommand`). The **per-diff events keep their existing names verbatim** (`OnActivityAddedToDraft`, …); re-homing them onto the unified `IEvent` substrate changes only their *producer*, not their identity — renaming would break the catalog-parity test and event-sourcing consumers for no benefit. (Was Open Question 3.)

### Key Entities

- **`IUpdate`** (new command contract, `Elsa.Workflows.Design.Persistence.Core.Contracts`; provisional name): the single Draft-content mutation command. Input: a desired Draft content state. Behaviour: load stored Draft → diff → emit one event per difference → validate → persist, under the per-Draft lock. Replaces the 20 granular mutation commands. Final name per Open Question 3.
- **Diff engine** (new, internal to the `IUpdate` implementation in `Elsa.Workflows.Design.Persistence.EFCore`): computes the difference between desired and stored Draft content across all content dimensions **and the layout sibling**, and maps each difference to one of the 20 mutation event types. Granularity is **semantic, per domain concept** (resolved — FR-019): concept-aware, mapping each concept-level change 1:1 to a typed event (including `OnActivityMovedInDraft` from the layout diff, FR-001a). Internal shape (resolved — FR-020): the engine is a **thin dispatcher** over ~20 **private apply-steps** — the demoted per-action logic of the deleted granular commands — invoking the matching apply-step once per detected concept-change. Element matching uses **stable synthetic ids** (FR-023): same-id → UPDATE (incl. rename), id-absent-from-desired → REMOVE, id-absent-from-stored → ADD. Concurrency is **last-writer-wins, whole-draft** (FR-022) — the engine diffs the submitted desired state against current stored state with no version check.
- **The 20 granular mutation event types** (existing, `Elsa.Workflows.Design.Core/Events`): `OnActivityAddedToDraft`, `OnActivityRemovedFromDraft`, `OnActivityMovedInDraft`, `OnActivityInputAddedToDraft`, `OnActivityInputUpdatedInDraft`, `OnActivityInputRemovedFromDraft`, `OnActivityOutputAddedToDraft`, `OnActivityOutputUpdatedInDraft`, `OnActivityOutputRemovedFromDraft`, `OnConnectionAddedToDraft`, `OnConnectionRemovedFromDraft`, `OnVariableDeclaredInDraft`, `OnVariableUpdatedInDraft`, `OnVariableRemovedFromDraft`, `OnWorkflowInputAddedToDraft`, `OnWorkflowInputUpdatedInDraft`, `OnWorkflowInputRemovedFromDraft`, `OnWorkflowOutputAddedToDraft`, `OnWorkflowOutputUpdatedInDraft`, `OnWorkflowOutputRemovedFromDraft`. Preserved as types; re-homed to `IUpdate` as the producer. Each is an `IEvent` (Unit 1 substrate).
- **The 3 lifecycle event types** (existing, `Elsa.Workflows.Design.Core/Events`): `OnDraftCreated`, `OnDraftClonedFromVersion`, `OnDraftDiscarded`. Stay bound to the retained lifecycle commands; NOT emitted by `IUpdate`.
- **`DraftMutationPipeline`** (existing, `Elsa.Workflows.Design.Persistence.EFCore/Services`): the lock + validate + persist + publish pipeline. **Absorbed into the `IUpdate` command implementation** (per the 2026-06-02 clarification): the command IS the shell. After Unit 2 there is no standalone `DraftMutationPipeline` collaborator on the mutation path; its `ExecuteMutation` logic lives inside `IUpdate`, reshaped from one-event-per-mutation to N-events-per-update. The lock/validation/ordering guarantees are preserved. (Disposition of the current `ExecuteCreation` lifecycle-creation path is settled per the Clarifications session.)
- **`OnDraftValidating`** (existing, `Elsa.Workflows.Design.Validations.Core/Events`): the Sequential validation gate. Fires once per `IUpdate` against the post-diff state; aggregates `IDraftValidator` contributions via the single `ExecuteValidations` handler. Unchanged.
- **`OnDraftValidated`** (existing, `Elsa.Workflows.Design.Validations.Core/Events`): the Background validation-outcome event. Fires after lock release, after the per-diff mutation events. Unchanged.
- **The 4 lifecycle commands** (existing, `Elsa.Workflows.Design.Persistence.Core.Contracts`): `ICreateDraftCommand`, `ICloneDraftFromVersionCommand`, `IDiscardDraftCommand`, `IPromoteDraftToVersionCommand`. Untouched by Unit 2.
