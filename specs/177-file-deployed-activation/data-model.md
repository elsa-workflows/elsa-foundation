# Data model: File-deployed activation and recovery

The [v1 contract](contracts/activation-v1.md) governs the safe handoff and outcome states. These are conceptual records; C# type names and transport are implementation choices. The [file bridge model](../176-composition-file-bridge/data-model.md) remains canonical for import, review and candidate-file generation.

| Entity | Fields and relationships | Authority, validation and lifetime |
|---|---|---|
| `CandidateHandoff` | Opaque candidate ID, selected host identity, configured default shell, environment, accepted composition/catalog pin, safe logical file roles, unresolved findings, creation time. It refers to one generated candidate directory. | Created after a fresh all-file check and explicit bridge review. The shareable projection contains no raw source bytes, physical paths, connection values, private change tokens or unkeyed content hash. Candidate ID is stable for this artifact, not a claim that another generated artifact with equal bytes shares the ID. |
| `PrivateCandidateVerification` | Candidate ID and a private content check over every included file, plus local source association and review decision. | Trusted local/deployment context only, not portable. Recheck all files at handoff and before external deployment. If the private record is absent in a later process, re-review instead of trusting a naked ID. |
| `DeploymentObservation` | Deployer identity, release/artifact identity, selected host/environment, expected-current identity, actual-current identity, observation time, and evidence that a complete immutable switch occurred. | Supplied by the external deployment owner. It can prove what was switched under that owner's guarantee; it cannot alone prove what the host consumed on restart or reload. Missing or mismatched evidence yields `deployment-unverified`. |
| `ProcessStartObservation` | Process identity, selected environment, start/ready time and safe source/override identity when a future trusted host contract can supply it. | Startup-bound changes require a new process from the retained artifact. Current Workbench has no source/override receipt; its generation number cannot identify a process or candidate by itself. |
| `ReloadObservation` | Selected shell, attempted time, transport result, per-shell success/error, reported new generation, and readback of active generation. | Host-produced, authorized observation. The raw CShells blueprint and provider exceptions are never relayed into a shareable result. A timeout/error can leave the result uncertain until readback. |
| `ReadinessObservation` | Configured default shell, active generation, ready/unavailable status, time and process identity when available from a trusted source. | Workbench's current readiness applies only to the default shell and does not itself supply process identity. The observed generation must match the same process's reload/readback generation for a ready claim. It says nothing about connection affinity or migration rollback. |
| `CandidateMatch` | `verified`, `mismatch`, or `unverified`, with safe evidence provenance. | `verified` requires trusted deployed-artifact, process-start source/override, applied-package and generation correlation, not a later directory comparison or successful reload. The current host has no such claim; its first honest value is `unverified`. |
| `ActivationOutcome` | Opaque operation ID, candidate/deployment/restart-or-reload/readiness identities, stage, candidate match, safe refusal/uncertainty code, and previous/new process/generation observations. | Each stage can be observed separately. Never collapse a post-deployment failure into pre-change refusal, or return a successful candidate-match claim from transport success or a generation count alone. No raw source, secret, management key or vendor exception escapes. |
| `RecoveryDecision` | New repair or source-rollback choice, expected observed deployment/generation, reviewed new candidate or previous release identity. | A new operation after readback; the old review token is not replayed. Source rollback does not undo database migrations or data changes. |

## State transitions

`reviewed candidate → candidate handoff → external deployment observation → process restart or eligible shell reload attempted → active process/generation observation → readiness observation → candidate-match assessment`. `CandidateMatch=verified` is unreachable with the current host evidence alone. At any stage, refusal/timeout can produce `candidate-only`, `deployment-changed-not-active`, or `uncertain`; readback may resolve uncertainty without repeating the deployment or activation. A recovery decision starts a new operation against observed current state.

For the first implementation slice, only candidate handoff and private drift verification are ready to code. Host-observed activation and recovery are specified here but require the generation-bound attestation gate in [research.md](research.md) before they can honestly produce a verified candidate match.
