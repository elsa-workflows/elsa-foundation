# Called BPMN coded-error recovery through EF

This is a bounded **T045 increment**, not closure of T045 or T029. Four cases run real published executable records through Foundation's DispatchWorkflow activity, a separately dispatched BPMN child root, its control producer, durable outbox, normal bookmark resume, caller inbox and released BPMN 0.5.0 interpreter over SQLite. Both Durable and Balanced modes cover an authored `ORDER` error caught by the caller's `ORDER` boundary and an `OTHER` error that remains unhandled. The [machine receipt](called-coded-error-ef-recovery.json) binds current source, binaries, normal runs and restored behavioral controls.

The executable builders supply the same pin, input contract, consumer declaration and scoped resume map that compilation emits; they do not run the public authoring compiler or HTTP import API. The concrete call key is the production `Elsa.DispatchWorkflow` identity. This evidence qualifies actual runtime/EF transport across providers; actual source-built Workbench/Studio and compilation remain separate gates.

## Three provider generations

1. Publish the actual child and pinned caller into the normal executable/source stores, then start the published caller in their default persistence partition. The child executes a BPMN error end event; its real root becomes Faulted with `bpmn.error` classification and the authored code. Its original ActivityReturnedFault incident remains blocking. The normal terminal producer creates ordinal zero, terminal, empty-notification control carrying the authored error separately from the safe generic Faulted diagnostic. A controlled dispatcher outage **before normal caller delivery** records retryable result one. Exact source identity is computed from the carried commit/intent and positively read back with identical immutable intent. The caller's dispatch leaf remains Suspended and workflow Running. Persisted mode and exact child pin are asserted before disposing the original provider.
2. Advance the test clock past retry availability and open a different provider on the same database. Unchanged child documents/incident and immutable source are checked before recovery. Normal recovery resumes the real DispatchWorkflow leaf with outcome Faulted and no local leaf fault; its exact control inbox consumes the authored terminal batch. For ORDER, the caller's error handler runs and the caller completes without incidents. For OTHER, the handler never runs and the caller faults with the original authored classification. The child workflow remains Faulted with its original blocking incident in both cases. Before acknowledging delivery, a forwarding observer independently reads the concrete committed calling leaf's consumed exact inbox and the source still Delivering with a positive fence and its prior result count one. It then throws a controlled after-effect timeout, recording retryable result two. This is actual caller control checkpoint commit before ACK, not a fabricated receipt or a process-kill claim.
3. Dispose that provider, advance past availability and open a third one. The full frozen caller activity/incident documents and child activity/incident documents are equal before retry. Normal recovery settles the same immutable source as Delivered, result three. The same complete documents remain equal afterward, physical caller bookmarks stay empty and neither workflow has poison. This terminal duplicate retry does not claim that the BPMN adapter evaluates control a second time; the normal resume executor recognizes consumed/terminal work.

The caller's inbox is positively terminal-consumed with cursor one, no pending batch, the exact dispatch/child/root/consumer address and acceptance of the original transport. The original processed-parent completion receipt is nonempty. Snapshot equality covers complete activity and incident documents; physical bookmark absence is checked separately. Child Faulted workflow status, exact child pin and child persisted mode are asserted on every child-fact read; caller terminal status, exact caller pin and mode are asserted before/after final retry and retained in that named projection. These fields are checked explicitly, but this is not whole-workflow byte identity or a positive physical bookmark-generation witness.

Final focused **4/0/0**; complete Runtime EF **1,682/0/0**. Two deliberately broken caller-adapter variants compile and fail behaviorally in both modes, with exact production source restoration before final normal verification:

| Mutation | Failures / companion passes | Actual phase |
|---|---:|---|
| Force every called authored error to ORDER | 2 / 2 | OTHER incorrectly completes the actual caller after recovered delivery instead of faulting. |
| Drop the called authored ErrorCode before the library callback | 4 / 0 | ORDER incorrectly faults the actual caller; OTHER still faults but loses its propagated authored classification. Both failures occur after recovered caller delivery. |

The two companion passes are the unchanged ORDER controls under the forced-match mutation. These mutations exercise the real caller adapter after source creation and provider restart; they are not satisfied by an assertion about a constructed control envelope alone.

Initial unqualified runs remain recorded: one compile-only fixture property typo; four registration failures when persistence-mode wrappers were applied before selecting EF; four null-cut failures and their diagnostic rerun when the call node used a CLR FullName. The latter correctly triggered the production boundary's `caller invocation differs` refusal before terminal delivery. The final fixture uses the canonical published activity key, retains the CLR descriptor and leaves that boundary guard unchanged. No production source, package pins, old capture or authoring fingerprint changed to make the test pass.
