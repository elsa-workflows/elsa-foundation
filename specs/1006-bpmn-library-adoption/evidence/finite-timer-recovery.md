# Finite recurring timer prerequisite

This is a bounded prerequisite fix inside #2735/#3338. T045 remains open. The [public-host recovery increment](opted-called-workbench-recovery.md) is already delivered at `9a179f481`; the next concurrent-call host attempt exposed a pending notification with no delivery attempt. That concurrent run is failed and unqualified. The timer correction below has its own deterministic source evidence; a rebuilt standard host must still repeat the concurrent cases.

The owned normal host's actual notification row was Pending, immediately available, eligible, revision one and never claimed. The source was produced by the selected actual child after a normal public Event resumed it; its sibling remained waiting. The normal Tasks and WorkflowsRuntimeResumption features were enabled, with a one-second sweep interval. Read-only managed diagnostics found the resumption timer's configured wait still one second but its native timer unarmed, uncanceled and idle. Other recurring timers remained armed. Its lifetime token was not canceled, no resumption async stack remained active, and its consecutive-failure count was zero. The [bounded observations](finite-timer/diagnostic-scope.json) retain these facts and explicitly limit their interpretation. The exact elapsed value of the live event was not captured.

Source inspection found a reproducible sentinel collision. `ScheduledTaskExecution.Callback` subtracts elapsed monotonic time from a finite wait, then passed that remainder to `NextArm`. A callback exactly one millisecond late computes `-1ms`, which is also `Timeout.InfiniteTimeSpan`. `NextArm` treated it as a configured infinite wait. The callback consequently disabled its one-shot timer and returned before both the action and the normal finally-based next-run scheduling. This mechanism is consistent with the observed idle finite timer; the heap does not independently prove that exact live timing event occurred.

The fix distinguishes configured infinity before calculating a finite remainder. Only a positive finite remainder can rearm; zero and every negative remainder execute the normal action and finally path. Existing rounding and long-wait chunking remain in `NextArm`, and action-fault logging and disposal paths are unchanged. An optional `TimeProvider` on the internal timer class defaults to `TimeProvider.System`, preserving the prior monotonic clock. It supplies deterministic elapsed timestamps in the tests while `System.Threading.Timer` remains the actual callback mechanism. There is no new public contract or dependency.

Three new tests exercise real timer callbacks:

- Two finite callbacks each observe exactly 101ms elapsed for a configured 100ms wait. Both must execute, positively proving the first execution rearms the next run.
- A configured infinite wait remains idle after a large monotonic-clock advance.
- Two real callbacks fire while the controlled clock is still before the original finite deadline and do not run the action. Advancing that clock past the deadline then executes it.

With the clock seam and original callback branch, the finite late and early-then-late tests fail at their intended action timeouts; configured infinity passes: **two failures, one pass**. With the fix, the complete Tasks test project passes **71 tests, zero failures/skips**. Existing positive rounding, long-wait, cron, adaptive backoff, action failure and lifecycle coverage also runs. [Red](finite-timer/red-results.json) and [green](finite-timer/green-results.json) retain all test names, outcomes and counts, original TRX hashes and exact source hashes. The [small reversal patch](finite-timer/restore-old-finite-callback.patch) reproduces the original branch with the same test seam. Apply that zero-context patch with `git apply --unidiff-zero` only in a controlled negative variant. It is a negative variant, not production code to apply during ordinary execution.
