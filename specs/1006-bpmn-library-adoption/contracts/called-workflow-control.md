# Called-workflow control boundary design

Status: implementation plan refinement reviewed for FR-014 by independent correctness, standards and acceptance lenses. Findings corrected: mandatory empty terminal barriers, retained-root/current-overlay lookup, exact source outbox identity and atomic inbox contributions on every continuation branch. Source changes await task review. This is inside the existing switch PR, with ordinary DispatchWorkflow policy unchanged.

## Typed control data

Add a small BPMN-independent control model in Workflows.Runtime.Core. One immutable version-1 batch identifies its consumer key/version, originating child workflow/root invocation, source work item and a root-local monotonically increasing batch ordinal; it carries an ordered finite list of authored notifications and an optional authored terminal failure code. Identifiers/codes are nonblank bounded strings; notification count and serialized payload bytes have explicit finite limits and validation. It carries no exception text, CLR fault type, incident object, authority choice or arbitrary diagnostic dictionary. Runtime transports the opaque consumer classification; only the consumer interprets it.

A structural continuation may stage one such batch separately from private semantic state. The existing structural-state projector places the batch on an additive typed ActivityExecutionState property in the same checkpoint as the continuation. It replaces the previous batch projection rather than accumulating a second semantic history. Its next ordinal comes from the last committed root projection, so retries of one checkpoint retain the same identity/ordinal. An absent field is the legacy/default representation. The batch is not itself proof of dispatch authority. Its transport envelope carries the exact source commit ID, intent ID and computed outbox item ID; source work identity alone cannot locate an authoritative outbox record.

DispatchWorkflowResult gains a separate optional typed control property while preserving its existing constructor and deserialization of old payloads. Fixed safe DiagnosticMetadata remains unchanged, including its allowlist and original incident IDs. The ordinary DispatchWorkflow activity still completes with Completed/Faulted/Cancelled/DispatchFailed outcomes. It does not fabricate a local activity fault when its child workflow faults.

## Capability and identity

A structural consumer declares a generic consumer key/version, compiled into its pinned executable metadata. The BPMN adapter opts in only when scheduling released Call Activity work, recording the key/version in the exact child's scheduling provenance. DispatchWorkflow admits that capability only in wait mode and only when its committed direct parent's pinned executable declares the matching consumer. It copies the admitted capability into the authoritative WorkflowDispatchRecord; fire-and-forget and ordinary dispatch receive none. No new authoring input or BPMN-specific shared-runtime branch is added.

ChildStartExecutor passes the committed dispatch ID as a lookup hint in the child's start metadata. A scoped generic boundary service implemented by the DispatchWorkflow package resolves that hint against IWorkflowDispatchStore and validates all of: deterministic dispatch/child/caller identity; wait mode and admitted capability; exact child executable and committed workflow parent; root invocation/node belonging to that child executable with no activity parent; committed caller and its direct parent/consumer metadata; tenant/partition/test-scope consistency. A parent workflow ID, incoming notification metadata or arbitrary root alone grants no capability. Pending is allowed only during a coherent admitted child start, since synchronous execution may precede MarkStarted; it does not waive the committed record. A missing old capability returns unavailable and preserves prior dispatch behavior.

Capability describes the exact retained boundary even after cancellation. Actual delivery independently acks a terminal target or retired call without executing the consumer. This prevents late delivery from faulting the called process merely because its caller was interrupted. Corrupt/conflicting identity fails closed, with original durable state retained.

BpmnProcessRuntime uses this service before setting HasEnclosingScope for a called root. Same-workflow nested processes keep their existing committed activity-parent notification path. An unrelated root still has no parent-notification authority. The BPMN adapter puts authored error classification and outward library signals in the generic batch; shared runtime never reads BPMN error categories or matches escalation codes.

## Checkpoint and transport

A DispatchWorkflow checkpoint enricher consumes only changed root control projections with a validated boundary. Every nonterminal source batch generates a deterministic durable post-commit intent in the same child checkpoint, keyed by dispatch/root/source-work identity. It owns one generic control-delivery payload addressed to the committed caller's structural parent and names the exact DispatchWorkflow invocation as its logical notifying child; the called root remains provenance. The payload includes the caller's pinned executable and cannot name an unrelated target.

Every opted-in called-root terminal outcome emits a fresh terminal ordinal, even when it has no new notification or authored failure code. This empty terminal barrier is required after previous nonterminal control and is also the first ordinal for a call with no prior control; reusing the last nonterminal projection would be incorrect. Terminal control stays in WorkflowDispatchCompletionEnricher's existing single parent-resume intent/result. It must not emit a separate notification row for a terminal batch. The terminal enricher loads the exact retained committed root invocation and overlays current activity-state changes, rather than requiring the root to be present in a later workflow-terminal checkpoint. Blocking-incident workflow fault observation can occur after the root fault is already committed and include only nonterminal ancestors. It validates the root against the dispatch executable and keeps all ordered terminal notifications plus optional authored failure in that one result. A root terminal continuation checkpoint never emits a separate nonterminal intent, even when workflow terminalization follows in a later commit. If the producer already staged a fresh terminal batch in the root checkpoint, the workflow terminalizer uses it exactly. Otherwise (ordinary exception/cancellation or a terminal path with no staged batch), the terminal enricher creates the mandatory empty barrier from the last committed ordinal, records that terminal projection on the exact root in this same checkpoint, and uses its stable workflow-terminal commit source. It never guesses authored error classification from an exception. An already committed equivalent resume intent remains replay authority. Ordinary diagnostics and the called workflow's actual fault/incident stay intact.

When the normal DispatchWorkflow resume completes the leaf, its checkpoint enricher validates the typed result against the retained dispatch and projects the control batch onto the completed activity's typed control field. Ordinary result/outputs/outcome remain as before. The existing parent-completion callback sees one completed child and one whole optional control batch; a declared consumer handles the batch once, while an ordinary child/default consumer follows its existing completion path. This is a completed-child control outcome, not the same-workflow fault-and-incident protocol. It grants no RequestChildFaultAbsorption permission.

A generic child-control notification command/handler delivers a nonterminal batch through the existing StructuralCallbackEvaluation commit machinery. A replacement authorizer owned by DispatchWorkflow validates the exact committed boundary before consumer execution. The consumer opt-in interface is in the existing Core boundary; the callback context carries exact local child identity, ordered control batch and terminal/nonterminal status. No generic library dependency or consumer-name switch appears in runtime.

Ordering and replay use a generic control inbox on the exact calling child ActivityExecutionState, committed through the existing checkpoint authority with the parent decision. The inbox is scoped to dispatch/root/consumer and holds the next expected ordinal plus pending out-of-order batches. It is not a second store or semantic-state authority. A delivery first validates its immutable source intent/result and exact identity. A matching earlier ordinal is acknowledged as a consumed duplicate; a future ordinal is durably buffered without a consumer callback. Only the contiguous prefix from the next expected ordinal is supplied to the consumer, in one callback, and its cursor/pending removal commits with all resulting parent state/work. Conflicting identities or content at an occupied ordinal refuse, rather than overwrite. Terminal completion enters that same inbox; it cannot overtake an owed earlier nonterminal batch. The existing processed parent-completion receipt records that the terminal delivery was durably accepted into this inbox, including when it must wait for a missing earlier batch. A later nonterminal delivery can then release the contiguous prefix including the buffered terminal batch.

The source root's monotonic projection and deterministic intent identity establish one immutable batch per ordinal. Transport includes exact source commit/intent/outbox IDs. Both nonterminal delivery and terminal-result admission use IPostCommitOutboxLookupStore.FindAsync on that exact item, verify its computed identity and persisted payload/ordinal/target/result equivalence, and retain the row while accepted retries need it. There is no scan or inference from the latest root projection. Validation checks source outbox authority, rather than trusting a caller-supplied old ordinal or a latest-only watermark. An initial first ordinal other than zero cannot silently reset the stream. No missing batch is skipped and no finite retry exhaustion is treated as successful semantic delivery. The existing outbox remains responsible for owed delivery; permanent failures remain visible for recovery. Retained cursor/pending data must survive provider restart and cannot be cleaned while its target invocation or accepted retries need it. No throughput or unbounded-stream storage claim is made.

The generic handler's use of StructuralCallbackEvaluation needs an internal additional-child-state contribution, so the calling child's inbox projection commits atomically with the target parent's state and all schedules/cancellations. The ordinary completion handler already commits processed-child state and extends that same projection. The contribution must reach Defer, Complete, intentional Fault and Cancel checkpoint branches, including incident/cancellation services, not just the deferred/completed helpers. Neither path saves the inbox independently before or after the parent decision. An out-of-order acceptance that invokes no consumer still commits its inbox contribution and acknowledges only after that checkpoint. Tests must prove crash/replay on both buffered and consumed paths.

The completed-child path reuses the existing durable parent-completion receipt for acceptance into the same inbox. One callback folds the contiguous ordered batches, their signals and any terminal classification locally before applying commands, without intermediate pruning. BPMN routes a typed called failure through the released OnWorkFaulted classification even though the DispatchWorkflow leaf itself completed normally; it never claims that leaf's local incident was absorbed. Catching a called error can complete the caller while the child workflow's actual incident remains truthful. Nonterminal signals use the exact still-active call work handle/token; interrupting cancellation uses the existing dispatch subtree-cancellation policy to reach only its child workflow.

## Required proof and compatibility

Before acceptance, actual host witnesses cover coded-error match/mismatch, both escalation forms during running work, both forms with terminal delivery, signal-plus-terminal-failure precedence, two concurrent calls at one binding, exact cancellation propagation, restart and duplicate delivery. Dedicated EF controls cover parent commit before acknowledgement, split/concurrent claims and staged terminal batch recovery. Terminal-success and ordinary-terminal-fault witnesses with no new control deliver the fresh empty terminal barrier before an earlier escalation, restart with the gap buffered, and prove no early caller advancement before ordered eventual consumption. Ordinary fault does not invent an authored failure classification. A deliberate split-terminal-batch mutation must fail. Missing/foreign/root capability, conflicting dispatch/caller/root and unsupported batch versions refuse safely.

Legacy DispatchWorkflowResult and dispatch records lacking control fields remain readable and retain ordinary defaults. Existing ordinary Faulted-outcome and safe-diagnostic tests remain green. Frozen BPMN authoring descriptors stay byte-identical. No generic exception metadata is promoted to authored control. The new capability and callbacks are intentional public API deltas tracked separately from authoring compatibility.

Specs 100's ordinary result/diagnostic policy and 126's local-parent protocol remain defaults. Reviewed spec1006 FR-014 extends only explicit opted-in waited control delivery; it does not retroactively claim that cross-workflow roots were covered by the old local-parent protocol. No new owner choice is required for preserving these defaults. Production #2898/#2907, arbitrary operator alteration and running binary rollback remain outside this proof.
