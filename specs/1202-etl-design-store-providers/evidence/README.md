## Bite-proofs

[`bite-proofs.json`](bite-proofs.json) has ten entries, and all bite. One, recorded at `bdb89368c` (review round 4), covers a draft update retrying the deadlock it loses to a publication on SQL Server. One, recorded at `45c609432` (review round 3), covers a failed draft create leaving nothing tracked. One, recorded at `ae9f03105` (review round 2), covers a failed publication clearing the change tracker before a rollback that may throw. Two, recorded at `6337c6bef` (review round 1), cover a draft update reporting its own revision and a failed publication clearing the change tracker. Five, recorded at `84b61a306`, cover (the `design-publish-retry` entry names the full `PublishRetry` declaration, since `UpdateRetry` later shared its initializer; two of them name `Key_and_hash_columns_use_the_engines_binary_collation`, which round 1 renamed to `Key_columns_use_the_engines_binary_collation`):
- the registration selecting the PostgreSQL context;
- the binary collation in the SQL Server, PostgreSQL and MySQL models: without it the model disagrees with the committed migrations, so the model-agreement test fails (and on SQL Server and PostgreSQL the migrate step in each test's setup refuses the database). The recorded column collation comes from the migrations, so `Key_columns_use_the_engines_binary_collation` guards the migrations, not the model;
- the publication retry: with a single attempt, the concurrent-publication contract fails on all three server engines, so the races are real there.

**Not bite-proven:**
- **The publication's transient-conflict filter on `catch (DbUpdateException)`.** Removing it survives: `A_publication_that_runs_out_of_attempts_leaves_nothing_for_a_later_save_to_publish` does reach that catch with a transient `DbUpdateException`, but without the filter the fallback rolls back (which succeeds on SQLite), clears the tracker and rethrows, so the outcome is the same. The case the filter exists for is a bare transient `DbUpdateException` whose explicit rollback could throw and hide it; on SQLite (busy or locked) and MySQL that clause is reachable, while on SQL Server and PostgreSQL the default execution strategies raise a transient save failure as an `InvalidOperationException` around the `DbUpdateException`, which the catch-all clears and rethrows without an explicit rollback. No test stages a throwing rollback on that path.
- **The catalog without `EF.Functions.Collate`.** Hash keys sort alike under every collation, so no paging case can tell; the collation itself is bite-proven above.
- **Provider selection for SQL Server, MySQL and SQLite**: only the PostgreSQL entry is mutated; the other three are tested by the same registration test per engine (and SQLite by the host tests).
- **The SQLite context's ordinal comparers**: untested; they declare no collation, so they are not in the model snapshot.
- **The MySQL `utf8mb4` character-set annotation**: tested through model agreement, not bite-proven.
- **The read retry** (`EtlDesignReadRetry`, round 5): on SQL Server a read-committed store or catalog read, or an update's re-read after its statement committed, can be the victim SQL Server picks in a deadlock between two publications, which surfaced a raw `SqlException` 1205 (and, for the re-read, a committed save reported as failed whose retry then returned `Conflict`). A review-round scratch repro staging that three-way cycle failed 15 of 40 runs on SQL Server before the fix (0 on PostgreSQL and MySQL) and passed 10 of 10 after it. It is not in the suite: SQL Server, not the test, picks the victim, so a committed test could not fail deterministically.
- **The draft update retry's exhaustion** (rethrowing the last conflict after 16 attempts): untested; only the SQL Server deadlock it retries is bite-proven.
- **The per-attempt `ChangeTracker.Clear()` at the start of each publication attempt**: untested; the races use one context per writer, and a failed attempt is already cleared by the catch-all.
- **The update result's format version, schema version and timestamp**: only its revision is bite-proven; its pipeline and hash are checked through the returned pipeline and the codec's hash check, but the interleave test uses one format and schema version for both writers.
- **Tooling**: the shared generator's exclusion of `Extensions/Etl` and `Extensions/Rules`, and the ETL script's refusal of SQLite and rewrite of the migration to internal, were exercised by running the scripts, not by tests.
- **Wrapping**: a publication or draft update that runs out of attempts rethrows the provider failure unchanged; ETL has no persistence exception type, as before this slice. Follow-up: #3758.

## Actual Workbench journey

[`design_store_workbench_journey.py`](design_store_workbench_journey.py) starts, for each server engine, its own database container and its own Workbench on ephemeral loopback ports, with the ETL design store on that engine and the runtime on SQLite. It creates two definitions whose ids differ only by case, validates and publishes one, runs the published version from a native Flowchart over a JSON Lines file, stops the host, starts a new one on the same database and reads the draft, the publication and the catalog back.

All 18 checks (six per engine) pass; the summary is [`workbench-journey-summary.json`](workbench-journey-summary.json), recorded at `bdb89368c` with a clean tree, after rounds 1–4's store fixes. Earlier runs at `9432455c1`, `ae9f03105` and `45c609432` passed the same checks. Container secrets are generated per run.

## Limits

- The ETL **runtime** store remains SQLite-only; its registration still refuses other engines. It needs narrower keys, provider-specific check constraints, ordinal collation and retried transitions, and is the next slice.
- Studio is unchanged by this slice.
- An update's result carries this writer's revision and content but the draft's current `lastPublishedVersion`, which a later writer's publication may have advanced; when that writer also advanced the revision, any validate or publish against this one conflicts; when it only published this revision, the reported value is current. No decision depends on it.
