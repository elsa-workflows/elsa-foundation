# Standalone durable jobs: research and reuse

**Research date:** 5 November 2026. **Assembled:** 6 November 2026. **Canonical request:** [#3586](https://github.com/elsa-workflows/elsa-foundation/issues/3586).

**Status:** Research evidence. On 6 November, [ADR0096](../../docs/adr/0096-jobs-owns-durable-handler-invocations.md) records the owner's explicit scoped Jobs-domain adoption after independent design review. Implementation uses the Elsa-owned default recommended below. No third-party dependency is selected; no runtime/provider or product qualification is established by this research. Elsa source findings remain pinned to [`e0ba87ecfc3b1e774c509ed274b19cd3f34a1124`](https://github.com/elsa-workflows/elsa-foundation/commit/e0ba87ecfc3b1e774c509ed274b19cd3f34a1124).

## Selected product constraints

The owner selected standalone .NET handlers with optional native/BPMN integrations in the initial release; no workflow graph or unrelated authoring stack is required. Queue, workflow-instance, workflow-definition and job-type pauses compose durably across nodes and restart. Work remains durably acceptable while paused, unrelated work on the same queue stays eligible, held work consumes no execution capacity, and running attempts finish. Workflow-instance/definition pauses also hold result-driven continuation; queue/type pauses gate attempts only. Completed physical results remain retained. See the [owner authorization and initial decision record](https://github.com/elsa-workflows/elsa-foundation/issues/3586#issuecomment-6671631992) and [program record](../../docs/program-goals/standalone-jobs.md).

The owner subsequently selected a **durable start-permission cutoff**: an attempt starts when its permission commits in the store. A pre-pause grant may enter its handler after pause acknowledgement; operations must show that Starting/Running handoff. Pause is not process suspension. The owner also selected **one catch-up occurrence by default after pause or outage**, with optional explicit replay-all. This policy concerns schedule slots that have not become accepted jobs: every already-accepted `JobId` remains recoverable and is not coalesced away. These selections constrain the design; they are not existing runtime guarantees.

## Actual Elsa reuse findings

| Existing facility | Source evidence | Consequence for #3586 |
|---|---|---|
| Workflow scheduler-work queue | [`IWorkflowSchedulerWorkQueue`][workflow-queue] is keyed by workflow execution and requires strict FIFO. A hidden, leased or delayed head holds back later work in that execution. [`EfSchedulerWorkQueueStore`][ef-workflow-queue] provides bounded pages and fenced transitions. | Retain this queue's model-owned ordering. It is not a selective named-job queue where a held job can be skipped while unrelated work proceeds. Reuse provider techniques, not incompatible semantics. |
| Package location of queue/claim support | [`Elsa.Workflows.Runtime`][workflow-package] references Activity Runtime Core, Workflow Runtime Core, Attention, Events and Tasks. [`Workflow Runtime Core`][workflow-core-package] itself references Activity Runtime Core, Expressions, Primitives and Serialization. | Referencing the workflow runtime solely to reuse one generic helper would pull workflow-specific package weight into standalone jobs. A bounded shared extraction needs real consumers and review; do not require that runtime in the standalone handler/client contract. These are source reference findings, not a measured restored/published package closure. |
| Generic fenced claim renewal | [`FencedClaimLease<TClaim>`][fenced-claim] renews owner/fence before a side effect and optionally during it. Its three existing consumers are the [post-commit outbox processor][outbox-consumer], [durable timer pump][timer-consumer] and [recurring-trigger pump][recurring-consumer]. | This is actual reusable behavior with several consumers, not a hypothetical universal scheduler. `RunAsync` only renews before dispatch; `RunRenewingAsync` needs renewal I/O isolated from the body's `DbContext`. Neither alone supplies all-scope pause/start atomicity, distributed permits, fenced job-result persistence or exactly-once external effects. |
| Host tasks | [`TaskStateManager`][task-state] holds process-local task/execution lists. [`TaskExecutor`][task-executor] explicitly gives `SingleNodeTask` no failover, fencing or persisted record that a task ran. | Reuse hosting, lifecycle and bounded sweep/backoff support where suitable. `Elsa.Tasks` is host infrastructure, not proof of this durable job product. |
| Existing recurrence | The [recurring pump][recurring-consumer] claims a persisted occurrence, uses a stable occurrence key and settles its cursor after routing. It routes an owner-matched workflow start and advances beyond now rather than replaying every elapsed slot. | Reuse recurrence arithmetic and identity principles with #3582; do not force standalone jobs through workflow trigger bindings. Explicitly implement the selected job catch-up/replay policy and preserve accepted identities. The workflow pump's existing behavior is not automatic job-policy adoption. |
| ETL terminal result and delivery responsibility | [`EfEtlRuntimeStore`][etl-store] creates a terminal result and outbox in the same terminal transaction, validates result/delivery identities and fences delivery acknowledgement. [`EtlNativeResultDelivery`][etl-delivery] checks the exact tenant, partition, execution, artifact/hash, activity, bookmark, registration and provider. | Reuse this proof pattern for ordinary model adapters: retain the job result, deliver idempotently, and retire responsibility only after durable model consumption or proven parent-terminal handling. Do not copy ETL-owned state or make ETL a job prerequisite. |

The [ETL delivery tests][etl-delivery-tests] specifically reject `Dispatched`, `Deferred`, `Duplicate` and `NotFound` mailbox statuses as sufficient acknowledgement; a matching consumed receipt and absent bookmark prove consumption. These tests exercise an existing adapter seam, with some receipt state seeded by fixtures; they are not standalone-job, real native/BPMN or multi-process qualification. [ADR 0088][adr88] likewise separates model state/semantics from shared durable mechanics and anticipates a worker host gating new claims.

The recommended persistence direction is therefore job-owned records and transitions using the established [EF infrastructure][ef-infrastructure], with one start/lease/result authority. Shared primitives may move to an appropriately small existing home under review. This finding does not admit a new generic lifecycle/store facade or prove that current EF providers already implement the required job admission transaction.

## Capability comparison

| Capability | Hangfire | Quartz.NET 4.x | TickerQ 5.x |
|---|---|---|---|
| Deployment | Separate producer/server processes; optional dashboard | Standalone scheduler or hosted service; optional API/dashboard | Registered/source-generated functions and independent workers; optional dashboard |
| Schedules | Immediate, delayed and recurring jobs | Immediate/one-off, delayed, cron and other trigger families; misfire policies | One-time tickers, cron definitions and occurrence history; late/catch-up policies |
| Durable recovery | Store-specific transaction/invisibility recovery; execution can repeat | Persistent-store clustering; interrupted firing recovery requires opt-in | Conditional acquisition, renewable leases and generation-fenced results in capable durable providers |
| Retry | Automatic retries, increasing delays and manual retry | Persisted trigger retry policies; fixed/exponential/explicit | Configured retry intervals and separate stale-restart policy |
| Concurrency | Worker count per server; optional distributed throttlers are best effort | Per-job-key non-overlap; node/cluster execution-group ceilings | Global and per-function limits local to a host; ordinary cron overlap local |
| Operations | State/history, failures, retry/delete/trigger; application authorization | API/dashboard, histories, outcomes/progress and cluster views | Dashboard, input/result/progress/history, manual actions and cluster discovery |
| Required pause | Four-scope durable admission not established by core | Persisted group/trigger pause exists; independent overlapping reasons need more than these flags | Dashboard host stop and cron disable do not establish four-scope durable attempt admission |

### Hangfire

[Enqueue](https://docs.hangfire.io/en/latest/background-methods/calling-methods-in-background.html) persists serialized work before returning. The [released worker](https://github.com/HangfireIO/Hangfire/blob/v1.8.25/src/Hangfire.Core/Server/Worker.cs#L145) explicitly allows requeue even after physical execution. Recovery timing is store/version dependent. [Recurring definitions](https://docs.hangfire.io/en/latest/background-methods/performing-recurrent-tasks.html) create ordinary background jobs; [delayed scheduling](https://docs.hangfire.io/en/latest/background-methods/calling-methods-with-delay.html) is polled. [Retries](https://docs.hangfire.io/en/latest/background-processing/dealing-with-exceptions.html) default to ten before a manually retryable failure.

[Identity](https://docs.hangfire.io/en/latest/background-methods/index.html) serializes .NET type/method metadata and arguments, not ambient tenant/user context. The [success state](https://github.com/HangfireIO/Hangfire/blob/v1.8.25/src/Hangfire.Core/States/SucceededState.cs) serializes return values but can substitute a serialization-error string; Elsa still needs stable handler/version and useful result contracts. [Cancellation](https://docs.hangfire.io/en/latest/background-methods/using-cancellation-tokens.html) is cooperative and storage-polled. [Queues](https://docs.hangfire.io/en/latest/background-processing/configuring-queues.html) have provider-dependent ordering and [worker counts](https://docs.hangfire.io/en/latest/background-processing/configuring-degree-of-parallelism.html) are per server.

[Ace throttlers](https://docs.hangfire.io/en/latest/background-processing/throttling.html) can defer jobs while releasing workers, but are private-feed, provider-limited and explicitly best effort. Connection-based `DisableConcurrentExecution` does not prevent every duplicate physical execution. No checked core control establishes all four independent pause reasons and their transactional start cutoff. [Console hosting](https://docs.hangfire.io/en/latest/background-processing/processing-jobs-in-console-app.html) can omit web quickstart dependencies. [Dashboard authorization](https://docs.hangfire.io/en/latest/configuration/using-dashboard.html) must protect sensitive serialized arguments; it does not supply Elsa tenant boundaries. [Core terms](https://www.hangfire.io/licenses.html) are LGPLv3-or-later or commercial; advanced packages have separate terms.

### Quartz.NET

[Clustering](https://www.quartz-scheduler.net/documentation/quartz-4.x/tutorial/advanced-enterprise-features.html) shares a persistent store; recovering interrupted work requires requesting recovery and can repeat effects. [Retry policies](https://www.quartz-scheduler.net/documentation/quartz-4.x/how-tos/retrying-failed-jobs.html) persist retry state. [Execution groups](https://www.quartz-scheduler.net/documentation/quartz-4.x/tutorial/execution-groups.html) distinguish node limits from cluster ceilings using the fired-trigger ledger/locking. Per-node configuration still needs deployment agreement; one group tag is not simultaneous queue, handler and workflow quotas.

Group pause persists across nodes/restarts and can cover future additions to exactly named groups. However, [released source](https://github.com/quartznet/quartznet/blob/v4.7.2/src/Quartz/Impl/AdoJobStore/AdoJobStoreBase.PauseResume.cs#L585) explicitly allows an individual resume to resume triggers within a still-paused group until a later store reapplies it. `ResumeTrigger` checks paused/blocked/overlap state, not four independent reasons. This cannot directly implement #3586's all-scopes conjunction. Standby/start controls one scheduler process and is not a replacement for persisted deployment pause. A firing already committed before pause must also be treated according to the selected permission cutoff.

[Outcomes/history](https://www.quartz-scheduler.net/documentation/quartz-4.x/how-tos/job-outcomes.html) retain status/summary/metrics; arbitrary non-report `context.Result` values are ignored by that history. Retained typed business output needs its own contract. [Multi-tenancy](https://www.quartz-scheduler.net/documentation/quartz-4.x/multi-tenancy.html) authorizes schedulers; groups inside a scheduler are not a tenant authorization boundary. [License](https://www.quartz-scheduler.net/license.html): Apache 2.0.

### TickerQ

[Reliability](https://tickerq.net/docs/5.x/guides/reliability) documents atomic acquisition, renewable leases, generation-fenced terminal writes and explicit recovery capabilities. EF Core, MongoDB and Redis support recovery; in-memory does not. Retry, stale restart and cooperative timeout are separate policies. A handler ignoring cancellation remains owned and consumes capacity until exit; no hard in-process timeout is supplied. Execution can repeat. Persisted overdue work differs from cron slots never created while offline: default run-on-availability and bounded latest-slot catch-up do not mean replay of every missed slot.

[Scheduler settings](https://tickerq.net/docs/5.x/guides/scheduler) explicitly make global/function limits and ordinary cron overlap host local. [Cross-node cancellation](https://tickerq.net/docs/5.x/dashboard/clustering) uses owner/generation-targeted short-lived store commands; acceptance does not prove the remote handler stopped. [Released dashboard source](https://github.com/Arcenox-co/TickerQ/blob/v10.5.1/src/TickerQ.Dashboard/wwwroot/src/components/cron/SchedulerHostCard.tsx) says stop/start applies to its serving host. The [scheduler implementation](https://github.com/Arcenox-co/TickerQ/blob/0927caa8047b850a8b4b42548cc244fb47b9ba7e/src/TickerQ/Src/BackgroundServices/TickerQSchedulerBackgroundService.cs#L463) freezes process-local scheduling and drains; it does not create durable cluster pause. The [released provider interface](https://github.com/Arcenox-co/TickerQ/blob/v10.5.1/src/TickerQ.Utilities/Interfaces/ITickerPersistenceProvider.cs) exposes several scheduled/immediate/on-demand/recovery paths that an admission integration would all need to cover.

[Typed output](https://tickerq.net/docs/5.x/guides/requests-results) publishes only with acknowledged successful completion; failed, cancelled and stale attempts do not publish results. [Current 5.x licensing](https://tickerq.net/docs/5.x/getting-started/licensing) is source-available with conditional Community/evaluation/commercial entitlement and a certificate installed on every replica. Historical permissive artifacts retain their historical terms, not automatic access to current fixes/features. This is a material dependency choice for Elsa customers.

## Recommendation and proof still required

Recommend an **Elsa-owned default job domain**, using existing EF/hosting infrastructure and reviewed small shared primitives. Native and BPMN adapters consume its retained result through their own progression contracts. This avoids installing a second scheduler/store/retry authority to emulate the four-scope start invariant. None of the researched providers directly proves that complete contract. The implementation now selects this recommendation after independent design review and scoped owner adoption of the Jobs domain in ADR0096. It is not runtime/provider qualification.

Quartz is the strongest optional schedule-producer candidate if existing Elsa scheduling cannot support the reviewed recurrence policy. Hangfire/TickerQ integrations can serve customers with those installations, subject to version/provider/license qualification. A producer adapter should submit a stable occurrence identity to one durable admission authority. A provider that owns execution must prove the complete lifecycle contract; a pre-handler pause query or dashboard stop button is insufficient.

Implementation qualification must show atomic permission grant against every applicable pause and deployment-wide permit, all dispatch/retry/recovery paths using that gate, fenced ownership/result transitions, and retained results independently of model continuation. It must exercise the selected catch-up policy without dropping accepted identities, cross-node pause/start races, overlapping reasons, restart/handover, unrelated same-queue progress, cancellations/timeouts and duplicate delivery. Actual packaged standalone/native/BPMN consumers, real provider processes and tenant-authorized API/Studio journeys remain required; none was exercised by this research.

## Selection, inference and evidence

- **Selected:** The product constraints and later owner choices above, recorded on #3586 and its specification. Delivery authorization permits the work; it is not architect consensus or constitution ratification.
- **Inferred/recommended:** Elsa-owned default, optional producer/adapters, bounded extraction of reused mechanics and the proposed package/persistence shape. ADR0096 now records the scoped owner domain adoption; the runtime/default choice is reviewed engineering design, with provider/product proof still pending.
- **Observed evidence:** Source contracts/implementations at the pinned Elsa commit and linked third-party releases/source/docs as inspected on 5 November. Reading an implementation or existing test does not demonstrate the new product's provider, deployment or acceptance guarantees.
