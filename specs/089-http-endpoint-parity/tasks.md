## Verified design facts (from the planning exploration — do not re-derive)

- `StimulusRouter.RouteAsync` already implements `StartAndResume` with snapshot-before-start self-resume protection ([StimulusRouter.cs:73-97](../../src/Elsa/Workflows/Runtime/Services/StimulusRouter.cs)); the resume path already carries `StimulusDispatchRequest.Input` end-to-end to the `[ResumeTarget]` invocation (`resumePayload.Input`, `WorkflowResumeBookmarkSchedulerWorkHandler.cs:232`).
- `InvokeResumeMethodAsync` binds a resume method with zero params, ONE `IActivityExecutionContext`, or ONE `JsonElement` — never both (`WorkflowResumeBookmarkSchedulerWorkHandler.cs:364-403`). The context shape today has NO resume-input accessor — that is the D5 gap (T002).
- An activity that calls `context.CreateBookmark(...)` suspends: the invoke handler enqueues bookmark-creation work and skips the completion checkpoint (`WorkflowInvokeActivitySchedulerWorkHandler.cs:319-326`); N bookmarks per execution are supported with distinct `BookmarkId`s (throws on duplicates, line 593). Follow `Delay.cs` for the `ActivityBookmarkRequest` + `[ResumeTarget]` shape.
- Bookmark expiry is enforced in the LOOKUP layer, not the raw index (`GlobalBookmarkStimulusLookup.cs:46`, `BookmarkStimulusLookup.cs:45`; `IBookmarkStimulusIndex` deliberately does not filter). Any new consumer must go through an expiry-aware surface.
- Bookmark consumption atomicity = per-execution actor mailbox + re-read-then-delete folded into the `BookmarkConsumed` checkpoint — two concurrent resumes: exactly one wins (existing semantics, no new work).
- `WorkflowExecutionStartDispatchRequest` carries only `artifactId` — the matched trigger binding's node id is dropped at dispatch, so an executing activity cannot know whether it triggered this run (gap → T003).
- The publish compiler stamps `executionType` from the activity TYPE's shape onto every node, and `WorkflowTriggerBindingExtractor` binds EVERY Trigger-shaped node and THROWS if a trigger node yields zero descriptors — so today a mid-flow HttpEndpoint would wrongly become a start trigger (gap → T006). Route entries are template-only (`HttpRouteData.Route`); `RouteTable` supports both incremental `Add`/`Remove` and atomic full `Refresh`.
- Bookmark rows (`BookmarkState`) already carry a `Metadata` string map (`RuntimeCreateBookmarkCommandPayload.Metadata` flows into it) — the route template and endpoint options ride there, reusing the `HttpEndpointRouting` vocabulary.
- There is NO bookmark-lifecycle observer seam today (trigger indexing has `IWorkflowTriggerIndexObserver`; bookmarks have nothing) — gap → T005.
- `GroundworkBookmarkStateStore` implements the bookmark store — the new type-scoped query must land there AND in `InMemoryBookmarkStateStore`. Groundwork rule: a new/changed index set must NOT bump `SchemaVersion` — backfill keys on the index-set change (Condition-7); enhance Groundwork itself if a capability is missing, never design around it.

## Design decisions (this pass — implement as specified, note deviations in task notes)

- **D-D1 (start vs mid-flow, elsa-core parity)**: `HttpEndpoint` gains a literal-at-publish input `CanStartWorkflow` (bool, **default true** — preserves all A–C behavior; deviation from elsa-core's default-false is deliberate, documented). Publish-time: `CanStartWorkflow=false` nodes produce NO trigger bindings. Run-time: the activity completes with the stimulus input ONLY when it is the node that triggered this run (`TriggerNodeId` == own node id, T003); in every other case — mid-flow node, direct-run, another node's trigger — it suspends with bookmarks. EXCEPTION preserving A's direct-run path: a `CanStartWorkflow=true` node executing with NO trigger-node identity on the run (direct run) keeps the authored-route fallback and completes. A `CanStartWorkflow=false` node ALWAYS suspends (US4's independent test starts the workflow directly and must suspend at the mid-flow endpoint).
- **D-D2 (one bookmark per method)**: mid-flow suspension creates one bookmark per supported method — `bookmarkId = "http-endpoint:{activityExecutionId}:{method}"`, `stimulusType = HttpEndpointRouting.StimulusType`, `stimulusHash = HttpEndpointStimulus.Hash(template, method)`, `expiresAt = null`, `metadata` = `http:template` + `http:method` + the endpoint options metadata (same `HttpEndpointStimulusOptions.ToMetadata()` payload as trigger bindings). Per-method hashes are mandatory (the per-execution lookup returns Ambiguous on ≥2 matches for one hash).
- **D-D3 (resume-input through the context, research D5 preferred fix)**: the resume method takes `IActivityExecutionContext`; the resume input is exposed via a new carrier-side accessor (T002) so the activity keeps `Set`/outputs access. The `JsonElement`-parameter fallback is NOT used.
- **D-D4 (route-table freshness)**: `HttpEndpointRoutesResolver` unions trigger-binding templates with waiting (non-expired) HttpEndpoint bookmark templates; a new bookmark-lifecycle observer seam (T005) triggers a full re-projection `Refresh` on bookmark created/consumed, mirroring `RouteTableTriggerIndexObserver`. Observer failures on the RUN path are logged, never fault the workflow (contrast: the trigger-index observer fails the PUBLISH — different blast radius, both documented). Startup task already calls the resolver, so restart is covered. A stale route (expired/consumed bookmark not yet refreshed) deterministically 404s at dispatch — acceptable per spec edge cases.
- **D-D5 (middleware options for resume-only matches)**: when no trigger claimant exists for the matched (template, method), endpoint options (authorize/policy/timeout/size limit) come from the waiting bookmark's metadata via an expiry-aware lookup. When both a claimant and bookmarks exist, the claimant's options win (single deterministic source; documented). The 409 ambiguity guard stays trigger-claimant-only — bookmark resumes are instance-scoped and cannot be ambiguous across definitions.
- **D-D6 (response shape)**: 202 body becomes `{ "started": [...], "resumed": [...] }` (resumed = dispatched resumes' workflow execution ids, mirroring `DispatchStimulusResponse.From`); the no-match 404 branch requires `StartedCount == 0 && ResumedCount == 0`.
- **D-D7 (resume input validation)**: the resume target applies the same validation discipline as the start path (strict Path/Method, JsonException-safe); on missing/malformed resume input it falls back to the authored-route model (consistent with start; the input is produced by our own middleware, so this is a defensive path, not an API).
