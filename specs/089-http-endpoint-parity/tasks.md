## Verified design facts (from the planning exploration — do not re-derive)

- The spec-069 chain is fully implemented and verified: `WorkflowExecutionCommandDispatchOptions.AmbientServices` (`WorkflowExecutionActorModels.cs:84-98`) → actor `EnqueueAsync` holds the mailbox and calls `_commandProcessor.ProcessAsync(envelope, options, ct)` (`InProcessWorkflowExecutionActorProvider.cs:181,193`) → `WorkflowSchedulerCommandRouter` attaches `options.AmbientServices` to the drain request and **awaits `DrainAsync` INLINE** (`WorkflowSchedulerCommandRouter.cs:65-68`) → `RuntimeSchedulerDrainRequest.AmbientServices` → drainer → `RuntimeExecutionPipelineDispatcher` stages `Workspace.AmbientServices` (`:49,70`) → the invoke handler builds the activity context WITH the ambient provider (`WorkflowInvokeActivitySchedulerWorkHandler.cs:77-88`, `HandleWithServicesAsync`), else a fresh scope. **`context.GetRequiredService<T>()` therefore resolves from ambient services when staged** — PROVEN by `ComposedRuntimeActivityExecutionTests.InProcessAgent_UsesDispatchAmbientServicesForActivityExecutionContext` (the canonical E2E template). No new context accessor is needed.
- **Neither dispatcher forwards options today**: `WorkflowStartDispatcher.cs:119` and `BookmarkResumeDispatcher.cs:142` call the single-arg `agent.EnqueueAsync(envelope, ct)`. `StimulusDispatchRequest` (`StimulusRoutingModels.cs:27-102`) has no options field; every existing field is durable-safe and defensively cloned/snapshotted — a new options field must be a plain live reference, NOT cloned, and MUST be excluded from `BuildDispatchMetadata()` (metadata flows into the durable envelope).
- Envelope purity already has a reflection contract test: `RuntimeAgentProviderContractTests.CommandEnvelope_DoesNotCarryRequestAffineServices` (`:119-126`) — extend, don't duplicate. Drain-side carry test pattern: `RuntimeSchedulerCommandDrainDispatchTests.ProcessAsync_CarriesDispatchAmbientServicesIntoDrainRequest`.
- **Non-local = dispatch status, not a flag**: `ForwardingWorkflowExecutionActor.EnqueueAsync(envelope, options, ct)` DROPS options (delegates to the single-arg overload) and returns `Deferred` — ambient services never cross the transport by construction. The middleware needs no explicit locality check: no live write happened ⇒ degrade to 202.
- **The dispatch result does NOT expose completed-vs-suspended**; the middleware detects "workflow wrote the live response" itself, after the inline drain returns (same async flow, so the write already happened).
- **`IHttpContextAccessor` TRAP**: the inline drain runs on the caller's async flow, so the AsyncLocal-backed accessor resolves the live `HttpContext` even for ASYNC-mode dispatches and even from a fresh internal scope. It MUST NOT be the live-write discriminator — the discriminator is an ambient-scope-only holder (E-D2).
- Timeout machinery (C-era) already propagates: the middleware's linked CTS token flows `RouteAsync → dispatchers → EnqueueAsync → mailbox wait → drain loop` (`WorkflowSchedulerDrainer.cs:84` ThrowIfCancellationRequested); OCE maps to 408 via the fault seam. A bookmark suspend returns normally (Quiesced) — NOT a timeout.
- `WriteHttpResponse` (`src/Elsa/Activities/Http/Activities/WriteHttpResponse.cs`) is a sync `void Execute` recording `HttpResponseInstruction` via `SetWorkflowOutput` — the artifact contract is explicitly designed for E to layer delivery on top without changing it.
- `IHttpContentFactory` set (Text/Json/Xml/FormUrlEncoded, `HttpFeature.cs:83-86`, scoped, no selector abstraction) currently has **zero production consumers**; `CreateHttpContent` returns `HttpContent` (pre-encoded `RawStringContent : ByteArrayContent`) — usable for a live write via `CopyToAsync(Response.Body)` + header copy.
- `ResponseMode` does not exist anywhere yet. Insertion points (post-#603 options round-trip owner + post-D merge fixes): `HttpEndpoint` literal input → `HttpEndpointTriggerStimulusProvider` (`ReadLiteralBool` pattern `:115-123`) → `HttpEndpointStimulusOptions` (`ToMetadata`/`FromMetadata`/`MergeForResume`) → `MergedHttpEndpointOptions` (+`FromClaimant`/`None`) → `HttpEndpointRouting` metadata key. Bookmark metadata rides automatically via `HttpEndpointStimulus.Describe` folding `options.ToMetadata()` — scenario 5.5 gets the resumed endpoint's mode for free.
- Middleware sync branch points (post-D shape): options resolved at `HttpEndpointMiddleware.cs:141` (`MergedHttpEndpointOptions`); dispatch block `:202-230` (linked-CTS + `RouteAsync`); 404 `:234-238`; the 202 writer `:240-255` is the reusable degrade path.
- Test templates: `WriteHttpResponseExecutionTests.SingleResponseOutput` (durable artifact assertion), `HttpEndpointMiddlewareTests` + `RecordingStimulusRouter`, `HttpEndpointHostFixture` (in-process agent drains synchronously before the response returns — sync tests assert immediately; fixture needs a Sequence helper composing HttpEndpoint → WriteHttpResponse; `LiteralBinding` helper `:483-491` for the new literal).

## Design decisions (this pass — implement as specified, note deviations in task notes)

- **E-D1 (ResponseMode vocabulary)**: `enum ResponseMode { Async = 0, Sync }` in `Elsa.Http.Core`; metadata key `http:responseMode` (`HttpEndpointRouting.ResponseModeMetadataKey`), omit-when-Async (round-trip identity); NON-identity (never enters the hash — two endpoints differing only in mode share a routing key, documented). Literal-at-publish input on `HttpEndpoint`, default Async (FR-018: Async preserves today's contract bit-for-bit); non-literal fails the publish like the other options.
- **E-D2 (live-write discriminator — the IHttpContextAccessor trap)**: a new scoped holder, e.g. `SyncHttpResponseSink` (in `Elsa.Activities.Http`; scoped registration on the feature; members: `HttpContext? HttpContext`, `bool ResponseWritten`, populate/mark methods). The middleware populates the REQUEST scope's instance ONLY for sync-mode dispatches and passes `context.RequestServices` as `AmbientServices`. `WriteHttpResponse` resolves the holder via `context.GetService` — ambient (request) scope ⇒ populated instance ⇒ live write; fresh internal scope (async mode, durable resume, non-HTTP start) ⇒ empty instance ⇒ artifact-only. NEVER use `IHttpContextAccessor` for this (AsyncLocal leaks the context into async-mode inline drains).
- **E-D3 (WriteHttpResponse behavior, FR-020)**: always records the durable `HttpResponseInstruction` exactly as today. Additionally, when the holder exposes an `HttpContext` AND `Response.HasStarted == false`: write status + headers, and the body via the `IHttpContentFactory` set matched on ContentType (`CreateHttpContent` → `CopyToAsync(Response.Body)`); absent/unmatched content type with a non-empty body ⇒ plain `WriteAsync` with the raw body and the authored ContentType (or `text/plain` when absent) — documented. Set `holder.ResponseWritten = true` after a successful write. `Response.HasStarted == true` (double WriteHttpResponse in one run) ⇒ skip the live write, artifact still recorded. Missing HTTP context ⇒ artifact-only, NO fault (spec assumption, softer than elsa-core).
- **E-D4 (dispatch-options passthrough, FR-019/FR-021)**: `StimulusDispatchRequest` gains optional `DispatchOptions` (`WorkflowExecutionCommandDispatchOptions?`, live reference, excluded from metadata/cloning); `IWorkflowStartDispatcher`/`IBookmarkResumeDispatcher` + impls gain an optional options parameter threaded to `agent.EnqueueAsync(envelope, options ?? Default, ct)`; `StimulusRouter` forwards to BOTH starts and resumes (one request scope serves all outcomes of one HTTP request — scenario 5.5's resume gets fresh ambient context because each resuming request dispatches with its own scope). HARD INVARIANT (spec-069 FR-001 / spec-089 FR-021, tested): ambient services never serialize into `WorkflowExecutionCommandEnvelope` or any persisted state; the forwarding actor's options-drop is pinned as the never-cross-process guarantee.
- **E-D5 (middleware sync branch + degrade, FR-019/FR-022)**: when merged options `ResponseMode == Sync`: populate the holder, dispatch with ambient services, and after `RouteAsync` returns — if `holder.ResponseWritten || Response.HasStarted` ⇒ return (the workflow authored the response); else ⇒ the EXISTING 202 writer (degrade: suspend-before-response, no WriteHttpResponse, or non-local `Deferred` — one code path covers all three, no locality inspection needed). Async mode: bit-identical to today (no holder populate, no ambient services). Timeout (408) and fault mapping (400/500) unchanged — they already wrap the dispatch and now bound the sync wait (SC-003: no request hangs past its timeout).
- **E-D6 (ResponseMode merge rules)**: claimant-present ⇒ claimant's mode (D-D5 claimant-wins, consistent); resume-only ⇒ **Sync if ANY matching waiting bookmark requests Sync** (the response is per-request; a sync-authored waiting endpoint gets its same-exchange reply even when an async sibling shares the identity — rationale documented in `MergeForResume`).
