# Contract: Internal Seams Touched (089)

Changes to module-internal contracts; each is catalogued in the owning module's EXTENSION_POINTS.md in the PR that lands it.

## A — start-input + host wiring

- `IStimulusRouter` (behavioral): start path forwards `StimulusDispatchRequest.Input` on the first-class `WorkflowExecutionStartDispatchRequest.StimulusInput` field → `WorkflowExecutionStartCommandPayload.StimulusInput` → `RuntimeCheckpointCommandPayload.SeedStimulusInput` → reserved durable channel (`RuntimeMetadataKeys.StimulusInputName`) → `IExecutionExpressionState.StimulusInput`. Never the workflow-inputs bag (collision/spoof-proof by construction; revised from the original seed-input-key design during the spec-089 code review).
- `ActivitiesHttpFeature : IMiddlewareShellFeature` (implemented on the existing feature, not a separate class): mounts `HttpEndpointMiddleware`. **Ordering (review V8 — RESOLVED by CShells 0.0.29-preview.145, cshells PR #124):** `IMiddlewareShellFeature` now has an `int Order` (default 0) and CShells applies middleware features via `OrderBy(f => f.Feature.Order)`. `ActivitiesHttpFeature` leaves the default; sub-unit C sets an explicit order if auth-sensitive middleware joins the shell pipeline.
- Transport guard: `HttpEndpointOptions.MaxRequestBodyBytes` (default 1 MiB, streaming-enforced, 413) bounds the body because the stimulus payload becomes durable state on the started instance; per-endpoint authored limits remain sub-unit C. Empty/root `BasePath` disables the middleware (never a host-wide catch-all); base-path matching is segment-bounded.
- Platform limitations (review V16 — RESOLVED by cshells PR #124): shell containers are guaranteed an `IMiddlewareFactory` (the feature's TryAdd workaround was removed when adopting preview.145), and per-shell dynamic pipelines mean shells activated after startup get their middleware too.

## B — routing (as-built)

- `TriggerStimulusDescriptor` +`Metadata: IReadOnlyDictionary<string,string>` (optional, ordinal snapshot). `WorkflowTriggerBindingExtractor` copies it verbatim into `WorkflowTriggerBinding.Metadata`; `WorkflowTriggerBinding.BuildId` now keys on (artifactId, nodeId, **stimulusHash**) so sibling descriptors on one node get distinct deterministic ids.
- `IActivityTriggerStimulusProvider.Describe` returns **zero-or-more** descriptors (`IReadOnlyCollection`; empty = not mine). HTTP emits one per (template, method); Timer/Cron/Event return single-element collections.
- Shared vocabulary `Elsa.Http.Core.HttpEndpointRouting` (StimulusType `HttpEndpoint`, metadata keys `http:template`/`http:method`) sits below both `Elsa.Activities.Http` (writer) and `Elsa.Workflows.Runtime.Http` (reader) — no cross-module edge.
- `IHttpEndpointRoutesResolver` reshaped to `ResolveRoutesAsync()` over `IWorkflowTriggerBindingStore.ListByStimulusTypeAsync` (new store member; no new index, no schema bump). Templates are stored **endpoint-relative, unprefixed** — the base path is exclusively `HttpEndpointMiddleware`'s concern, so the resolver takes no options dependency and the two BasePath settings cannot diverge.
- Freshness: new `IWorkflowTriggerIndexObserver` seam (TryAddEnumerable) invoked by `WorkflowTriggerIndexer.IndexAsync` after delete-and-resave; observer failure fails the publish. `RouteTableTriggerIndexObserver` does a full re-projection refresh; `UpdateRouteTableStartupTask` covers shell start. Both catalogued in the owning EXTENSION_POINTS.md files.
- DependsOn closure (review B2): `ActivitiesHttp` depends on **`WorkflowsRuntimeHttp`** (not just `Http`). `WorkflowsRuntimeHttp` contributes the route-table populators (`UpdateRouteTableStartupTask`, `RouteTableTriggerIndexObserver`, `IHttpEndpointRoutesResolver`); enabling the endpoint activity alone without them would compose an empty route table so every endpoint 404s. No cycle — `WorkflowsRuntimeHttp` depends only on `Http` + `WorkflowsRuntimeTriggers`, never back on `ActivitiesHttp`.
- Route-table swap (review B6): `RouteTable.Refresh` builds a complete new dictionary off to the side and publishes it in a single `IMemoryCache.Set` (atomic swap), so a concurrent reader observes either the old table or the fully-built new one — never the empty/partial intermediate the previous `Clear()`+`Add` loop exposed (transient 404s during any publish). Build-time duplicate routes still throw `InvalidOperationException`, but abort the swap and leave the live table intact. Incremental `Add`/`Remove` keep mutating the live dictionary.
- Middleware: first deterministic route-table match wins for overlapping templates (elsa-core parity); ambiguity (= same (template, method) hash claimed by >1 `DefinitionId`) → `409` before any dispatch.
- BREAKING (pre-release): unauthored `SupportedMethods` defaults to `GET`; non-literal `SupportedMethods` fails the publish like a non-literal `Path`.
- Strict string-only literals (review B12): both `Path` and every `SupportedMethods` array element must be authored as JSON **strings**. A non-string literal (number/bool/object) fails the publish with the same `ArgumentException` as a non-literal binding — it is no longer silently `ToString()`-coerced into a garbage route path or HTTP method. (Extraction shares one `RequireJsonString` helper — DRY finding V15.)

## C — parsing/auth/faults (as-built)

- Policy contracts moved DOWN to `Elsa.Http.Core` (`IHttpEndpointAuthorizationHandler`, `IHttpEndpointFaultHandler`, contexts, `HttpBadRequestException`) so the middleware consumes them without a cross-module edge; implementations stay in `Elsa.Workflows.Runtime.Http`. `AuthorizeHttpEndpointContext` slimmed to `(HttpContext, Policy)` — authorization runs before any instance exists, so the Runtime `Workflow` resource member is gone.
- `IHttpRequestBodyParser` (contract `Elsa.Http.Core`, impl `Elsa.Http`, TryAdd): content-type dispatch to wire-safe `JsonElement?` (json/+json parsed, text/* string element, unknown/invalid/empty → null, never throws). The response-side `IHttpContentParser` set was deliberately NOT force-fit (HttpResponseMessage/ReturnType/converter shape) and is regression-pinned untouched.
- Endpoint options are NON-IDENTITY claimant-binding metadata written by the provider (`http:authorize` omit-when-false, `http:policy` raw, `http:requestTimeout` invariant `"c"`, `http:requestSizeLimit` invariant long) and parsed by the middleware from the (single-definition) claimants the B ambiguity guard already fetched.
- Middleware enforcement order: authorize (fail closed — 401 when the handler is missing/denies, before the body is read) → per-endpoint size-limited body read (413) → parse (`ParsedContent` on the wire model + activity output) → dispatch under a linked-CTS per-endpoint timeout with faults mapped via `IHttpEndpointFaultHandler` (timeout→408, `HttpBadRequestException`→400, other→500; inline fallback mapping when the policy feature is absent).
- `AuthenticationBasedHttpEndpointAuthorizationHandler` hardened: prefers an authenticated `User`, else `AuthenticateAsync` against the shell-scoped default scheme, fails closed on any failure/throw. Investigation result: root `UseAuthentication` runs after `MapShells`' scope swap and resolves per-shell schemes, so `User` IS populated in the shell branch; `IMiddlewareShellFeature.Order` stays default (auth is not a shell middleware feature — nothing in-branch to order against).

## D — mid-flow resume (as-built)

- **Resume-input carrier channel (T002, research D5 fix):** `RuntimeExecutionExpressionCarrierState` gains `ResumeInput` (`JsonElement?`); `RuntimeExecutionExpressionCarrier.Create` takes an optional `resumeInput` (clones), so invoke/parent-completion call sites stay null and only `WorkflowResumeBookmarkSchedulerWorkHandler` passes `resumePayload.Input` — a live per-invocation value, never durable state. Surfaced on `IExecutionExpressionState.ResumeInput` + `SimpleActivityExecutionContext`, mirroring `StimulusInput`. Both existing resume-method shapes (zero-param / one `JsonElement`) stay supported; the `JsonElement`-parameter fallback is unused.
- **Trigger-node identity channel (T003):** `StimulusRouter.StartMatchingTriggersAsync` reads the matched `binding.ExecutableNodeId` → new optional `WorkflowExecutionStartDispatchRequest.TriggerNodeId` → `WorkflowExecutionStartCommandPayload.TriggerNodeId` → `RuntimeCheckpointCommandPayload.SeedTriggerNodeId` → seeded on a reserved durable channel (`RuntimeMetadataKeys.TriggerNodeId`, value-id prefix `trigger:`) → projection → `IExecutionExpressionState.TriggerNodeId` (string?, null on direct/resume-only runs). Never the workflow-inputs bag (collision/spoof-proof by construction — same discipline as §A `StimulusInput`).
- **Provider contract (T006):** `IActivityTriggerStimulusProvider.Describe` now returns `ActivityTriggerStimulusResult` (`NotRecognized` | `Recognized([...])`, new type in `Runtime.Core/Models`) instead of a bare descriptor collection. The extractor throws its zero-descriptor guard ONLY when NO provider recognizes a trigger node, so a `Recognized([])` (declared non-start) yields no bindings without failing the publish. Timer/Cron/Event providers updated mechanically. `HttpEndpointTriggerStimulusProvider` returns `Recognized([])` when it reads `CanStartWorkflow=false`.
- **`CanStartWorkflow` + D-D1 (T006/T007):** `HttpEndpoint` gains a literal-at-publish `CanStartWorkflow` (bool, **default true** — deliberate deviation from elsa-core's default-false, preserves all A–C behavior; non-identity, never enters the stimulus hash; non-literal fails the publish). Run-time branch (D-D1): completes on the start path (`TriggerNodeId` == own node) or a start-capable direct run (no trigger identity); every other case (foreign trigger node, mid-flow node, or `CanStartWorkflow=false` on any run) suspends.
- **Bookmark metadata parity (D-D2):** mid-flow suspension creates one bookmark per method via `HttpEndpointStimulus.Describe` — `bookmarkId = "http-endpoint:{activityExecutionId}:{method}"`, shared `HttpEndpointRouting.StimulusType`, per-method `HttpEndpointStimulus.Hash(template, method)`, `expiresAt = null`, and the SAME `HttpEndpointStimulusOptions.ToMetadata()` payload (template + method + options) the trigger provider stamps on bindings — so the middleware reads options off a resume-only match exactly as off a binding.
- **Type-scoped bookmark query + metadata lookup (T004):** `IBookmarkStimulusIndex.ListByStimulusTypeAsync(stimulusType, ct)` on both stores (hash-agnostic type scan; Groundwork does a clause-free full scan narrowed by type in code — byte-identical to the sibling `GroundworkWorkflowTriggerBindingStore.ListByStimulusTypeAsync`, NO new index, NO `SchemaVersion` bump). `IGlobalBookmarkStimulusLookup.FindWaitingByTypeAsync(GlobalBookmarkStimulusTypeLookupRequest, ct)` returns the non-expired `Matches` snapshots (incl. `Metadata`) for a type regardless of hash — expiry filtered in the lookup layer (raw index stays unfiltered), no correlation scoping (mid-flow resumes are instance-scoped).
- **Bookmark lifecycle observer seam (T005):** new `IBookmarkLifecycleObserver` (`OnBookmarkCreatedAsync`/`OnBookmarkConsumedAsync`, both `BookmarkState`) in `Runtime.Core/Contracts`, fanned in by a shared `BookmarkLifecycleNotifier` (TryAddEnumerable observers, TryAddSingleton notifier). **Failure policy (opposite of `IWorkflowTriggerIndexObserver`):** fires on the RUN path — the notifier catches+logs every observer throw and NEVER faults the run (a stale route simply 404s until the next refresh). Consumed fires from `BookmarkConsumptionCheckpointService.CommitAsync` (commits + notifies inline). **Created fires from TWO commit sites** because CreateBookmark dispatches through the ADR-0029 activity pipeline: the direct `WorkflowCreateBookmarkSchedulerWorkHandler.HandleAsync` notifies after its inline commit (unit/direct path), and — the fix — `RuntimeActivityCheckpointMiddleware` (the pipeline Checkpoint slot, the real drain path) notifies after committing a staged `BookmarkCreated` checkpoint. Without the middleware notification the mid-flow route never appears and the endpoint can never be resumed (bug found + fixed by the T012 integration tests).
- **Route-table union + observer (D-D4, T009/T010):** `HttpEndpointRoutesResolver` unions distinct trigger-binding `http:template` values with waiting non-expired HttpEndpoint bookmark templates (via `FindWaitingByTypeAsync`, expiry-aware — not the raw index), ordinal-deduped, endpoint-relative. `RouteTableBookmarkObserver : IBookmarkLifecycleObserver` (`Runtime.Http`) re-projects the WHOLE route table (`resolver.ResolveRoutesAsync` → `routeTable.Refresh`) on created/consumed where `StimulusType == HttpEndpointRouting.StimulusType` — a full union, so a consumed bookmark's template survives if another instance still awaits it; non-HTTP types return before opening a scope. Mirrors `RouteTableTriggerIndexObserver`'s singleton + fresh-scope + full-refresh exactly. Startup task covers restart.
- **Options from bookmark (D-D5, T011):** when NO trigger claimant exists for the matched (template, method), `HttpEndpointMiddleware` reads endpoint options (authorize/policy/timeout/size limit) from a waiting bookmark's metadata via `FindWaitingByTypeAsync` filtered to the stimulus hash. Claimant wins when both exist. Enforcement order (authorize → size limit → parse → timeout+faults) unchanged and now applies to resume-only matches. The 409 ambiguity guard stays claimant-only (bookmark resumes are instance-scoped, cannot be ambiguous across definitions).
- **Response shape (D-D6, T011):** middleware dispatch mode `StartOnly → StartAndResume` (self-resume protection via the router's snapshot-before-start, unchanged). 202 body becomes `{ "started": [...], "resumed": [...] }` (resumed = `Resumes` where `Status == Dispatched`); the no-match 404 branch requires `StartedCount == 0 && ResumedCount == 0`.
- **Resume input validation (D-D7):** the `[ResumeTarget]` `OnRequestReceived` (context-shaped) reads `ResumeInput`, deserializes/validates via a private helper shared with the start path (DRY), and falls back to the authored-route model on a missing/malformed payload (the input is produced by our own middleware — a defensive path, not an API).
- **Resume durable-output fix (T008):** the resume handler now durably persists a resume target's `CaptureOnSuccessfulCompletion` outputs (refactored `ActivityOutputPublisher.BuildDurableOutputChanges` keyed on activity-execution/node ids, folded into the consumption checkpoint) — behavior-preserving for existing resume targets (`Delay`'s no-op unaffected); required for the resumed `HttpEndpoint`'s Result/RouteData/ParsedContent to land.

## E — sync responses (spec-069 seam)

- `StimulusDispatchRequest` + start/resume dispatch requests gain an optional non-durable dispatch-options passthrough carrying `WorkflowExecutionCommandDispatchOptions.AmbientServices` to the actor enqueue. INVARIANT (spec-069 FR-001, tested): ambient services never serialize into `WorkflowExecutionCommandEnvelope` or any persisted state.
- `WriteHttpResponse` (behavioral): when ambient services expose `HttpContext`, writes the live response via `IHttpContentFactory`; always records `HttpResponseInstruction`.
