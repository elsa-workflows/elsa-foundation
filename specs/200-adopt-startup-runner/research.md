# Research: Shared Startup Runner Adoption

Source baseline: qualified Foundation observer candidate `af83b06bb2b4dcd84b1269cc39575ff68033cbbf`; qualified runner package `.173` source `f5bfc0db5ef9440dd777c2dd0d97fbf817f22e2f`. Documentation-only CShells main `c596ca2b0c6cd3deb069db4071adc132c954731d` has unchanged product source. This is preparation, not implementation acceptance.

## R1 — Three host adapters

**Decision**: Keep existing hosted-service phase ownership; use the opt-in shared runner inside each adapter.
**Rationale**: Foundation defaults on and awaits serial attempts before listening, then retries failed targets independently. Workbench eager defaults off and performs a serial one-shot pass; default warmup returns immediately, waits for ApplicationStarted and performs discovery then one activation with its own telemetry.
**Alternatives**: A shared hosted service or combined eager/warmup state would erase phase/policy distinctions. Reusing the execution primitive alone avoids that.

## R2 — Successful custom-shell generation

**Decision**: Require additive `ReturnedGeneration` diagnostics upstream through CShells #167; keep `VerifiedGeneration`'s built-in-only meaning unchanged.
**Rationale**: Current success accepts a custom shell under the registry stable-return/current-reference contract but exposes no descriptor identity. Workbench currently records the returned descriptor generation. Reading GetActive afterward can race to a later generation. A safe integer from the accepted return avoids extra activation calls or shell/provider retention.
**Alternatives**: Widening VerifiedGeneration changes documented null-custom semantics; a host registry decorator merely recaptures upstream data and adds unnecessary wiring. Readiness capability is a distinct decision.
**Prerequisite satisfied for preview design**: [#167](https://github.com/valence-works/cshells/issues/167#issuecomment-6073687376) is closed after PR168 merged as `f5bfc0d` and preview `0.0.30-preview.173` passed the ten-package public archive audit and fresh-cache consumer qualification on actual .NET 8/9/10 runtimes: 30 scenario groups, 132 assertions and six loaded DLL comparisons. [PR169](https://github.com/valence-works/cshells/pull/169) records that acceptance. This qualifies the additive diagnostics API; final released-package adoption remains required.

## R3 — Foundation fatal exceptions

**Decision direction**: Keep Foundation's existing fatal set and separate initial/background propagation. The set is OutOfMemoryException, StackOverflowException, AccessViolationException, AppDomainUnloadedException and BadImageFormatException. Supplied-token cancellation remains cancellation; an uncancelled OperationCanceledException is an ordinary retryable Foundation failure. Workbench retains its own log-and-continue/failed-warmup boundary for other exceptions, including that fatal set.
**Rationale**: The runner catches activation exceptions as structured failures. Initial attempt observer may capture ExceptionDispatchInfo and cancel its owned run before the post-observer cancellation check; StartAsync then rethrows the captured fatal before any later target/retry. A background fatal must stop only that target through retry policy; other recovery continues. StopAsync must join all owned work before propagating fatal faults, and a bounded wait may expire first.
**Verified baseline**: The [six-group copied-service experiment](https://github.com/elsa-workflows/elsa-foundation/issues/2509#issuecomment-6073646728) compiled five byte-identical files from `af83b06` on net10 and passed with zero cleanup failures. Initial fatal exceptions retain identity and skip later targets; uncancelled OperationCanceledException retries while supplied-token cancellation propagates. Already-faulted ordered joins select the first configured fatal (A); a live first StopAsync with actual completion order B,A,C selects B; a subsequent StopAsync selects A. Caller-bounded shutdown cancels while work ignores cancellation and later joins after release. Root pre/post source hashes and independent audit are retained. This is an out-of-tree baseline experiment, not rebuilt-host acceptance.
**Selected compatibility clarification**: Retain fatal identities per target, join the owned runner, then rethrow the first configured target's original fatal. Retain/log every captured fatal. This deliberately replaces scheduler-dependent concurrent-fatal selection; it does not claim exact legacy `Task.WhenAll` timing. No per-target completion-marker machinery or upstream completion API is required. Capture fatal state before fallible logging; observer exceptions are isolated, so throwing from an observer or retry policy cannot propagate the host fatal. Background fatal policy returns Stop for that target only.
**Selected cancellation boundary**: Pass a host-owned lifetime token to the runner. Forward the caller's startup token only while `StartAsync` remains pending, and dispose that registration before successful return. Cancellation during the still-pending initial-pass handoff may abort the run; after return, only host shutdown owns cancellation. The [copied-service/public-package comparison](https://github.com/elsa-workflows/elsa-foundation/issues/2509#issuecomment-6073903414) passed three controlled cases on .NET 10.0.8: legacy retries after late caller cancellation, the directly linked runner self-stops before any explicit Stop, and an unlinked-token runner control retries. Two loaded DLLs match the audited public `.173` archives. This proves why direct token forwarding is unsuitable, not that the adapter is implemented.
**Owned join**: Keep one retained shutdown task. It requests/awaits host cancellation, joins the runner even if cancellation callbacks fail, then applies the explicit fatal selection. Each caller bounds its wait without cancelling or abandoning that task. Preserve independent shutdown errors; a sole fatal is rethrown as its original instance. Initial fatal remains a separate captured failure rethrown by StartAsync after owned cleanup and does not become background history.
**Required implementation proof**: Test serial cancellation/fatal skip, cancellation in the handoff and after StartAsync return, multiple background fatals, unaffected recovery, cancellation-callback failure, and bounded then subsequent shutdown joins. No adapter test or rebuilt-host acceptance is claimed by these research experiments.
**Alternatives**: Global cancel changes unaffected-target recovery; silently swallowing fatal exceptions changes startup/shutdown behavior. A new generic fatal-runner option is unnecessary if host policy can preserve these semantics through existing callbacks.

## R4 — Failure projection and existing readiness compatibility

**Selected projection**: An unsuccessful callback's one-based AttemptNumber equals cumulative failed attempts for that target/run: prior owned success is terminal, and cancellation ends the run before any later callback. Use that callback number directly; do not read an asynchronously assigned run handle or trigger Snapshot's external reconciliation from the observer. Store only a per-run, per-target failure base alongside the current diagnostic row. The first eligible failure after reset sets base to AttemptNumber minus one; public Attempts is AttemptNumber minus base. Active notification or owned success clears row/base; the existing raw-Active write-time guard suppresses late failures. Readiness continues to consult the live registry, independently of terminal runner history.
**Selected policy handoff**: Calculate the existing reset-sensitive delay once with the failure projection; retain only one immutable attempt-number/action/delay decision per configured target/run for the runner policy. No duplicate count increment, jitter calculation, timer or retry loop. Public LastFailedAt plus that selected delay remains the existing advisory deadline. The independently reviewed observer-to-policy order records essential projection/decision state before fallible logging, even when external satisfaction makes the runner skip its later policy callback. Expected classification failures need a safe ordinary outcome, without retaining the original exception or recalculating jitter in a policy fallback.
**Selected external-completion boundary**: Adopt the runner's terminal SatisfiedExternally result as completion of startup recovery, just like an owned activation success. Legacy recovery could retain a timer until its next scheduled activation observed success; the runner may complete earlier when another path has already settled the shell. A later deactivation remains live not-ready state and does not restart the completed boot run. Do not add an Elsa timer to recreate the legacy extra probe. Recorded intervals/deadlines describe the last decision; operator copy must not promise future work for a terminal run. Tests must cover external completion before the old deadline, later deactivation and a failed callback whose policy is skipped. This is an explicit scheduling clarification, not exact legacy parity or a custom-registry readiness choice.
**Classification**: NotCurrent is a safe activation reason, not an invented exception or EF refusal, and uses the ordinary retry policy. Clarify the public FailureType documentation accordingly. Existing external request activation, later deactivation and late-failure assertions remain mandatory; registries omitting lifecycle notifications retain only the existing dynamic-hide behavior while Active.
**Independently reviewed no-notification correction**: The legacy raw-Active guard suppresses a failed callback's write; it does not delete an earlier row. Keep that row if no lifecycle reset was observed. Compute the suppressed callback's delay using the retained count plus one, then rebase its diagnostic offset to callback AttemptNumber minus the retained row's Attempts, so the ignored failure does not inflate the next visible count. Repeat that rebase for each suppressed callback. With no prior row, retain no row/base and let the next eligible callback establish its first-failure base. A real Active lifecycle notification still clears row/base. Source review confirms the formula; implementation must test the notified and omitted-notification branches separately without inferring a persistent reset.
**Alternatives**: A copied retry loop/tracker counter duplicates upstream ownership. Treating terminal startup success as current readiness breaks reload semantics. Silently choosing fail-closed or raw-Active custom readiness is outside this unit.

## R5 — Owned shutdown and test boundaries

**Decision**: Delegate scheduling cancellation/join to the retained run; caller wait cancellation must not abandon its underlying work. Keep the Workbench pre-start wait/discovery and their cancellation owned by its existing service.
**Rationale**: IShellActivationRun.StopAsync promises tracked work survives a bounded wait. Initial/background fatal tests must include cancellation-ignoring activations and a subsequent successful join.
**Validation**: Preserve full existing adapter assertions, exercise real runner DI with controlled clocks/gates, add exact-return custom generation races and eager/warmup overlap, and run rebuilt process recovery. Mutation proof must fail a behavioral assertion after compilation and restore source exactly.

## Research disposition

R1–R5 have selected directions with explicit R3/R4 compatibility clarifications and independent source review of the observer-to-policy handoff. Root and independent requirements/Phase1 reviews are complete. The plan is reviewed; no tasks/implementation acceptance is claimed, and no Foundation implementation source was changed or built. The copied-service and cancellation-lifetime experiments have run; neither satisfies the final runner/host gate. Final stable release/pin/lock/host gates remain separate from any future preview check.
