## Context

`WorkflowDefinitionState` is persisted as the `StateSource` shadow JSON on `WorkflowDefinitionVersion` (immutable) and `WorkflowDefinitionDraft` (mutable) inside the `Workflows.Design` sub-domain. It is the canonical authored document of a workflow.

Sipke's 2026-05-26 entity-design review (item 2) flagged a god-object risk: as the entity-design Units B–G crystallize, `WorkflowDefinitionState` will be the natural dumping ground for any workflow-related concern unless its scope is pinned now. This feature pins it.

Constitutional substrate: Elsa v2.0.0 (draft) + framework v2.0.0 (draft), folded 2026-05-27 in Unit A. Unit C is parallel-safe with Units B (activity catalog identity) and D (parent vs version field allocation).

The audience for this spec is the architecture group (Joey + Sipke + Frans) and the AI agents implementing against the constitution. Stakeholder framing is architect-grade, not end-user.

## Terminology

### Reconciliation (Joey's working definition, 2026-05-28)

**Reconciliation** is the mechanism by which the environment is kept up to date with activity definitions and workflow definitions from **trusted external sources** — git repositories, blob stores, file systems, package manifests, tenant-managed sources, etc.

The mechanism runs continuously (on triggers: startup, scheduled passes, source-change events, manual sync). On each pass, it pulls from each configured trusted source and applies entries via the Model X policy codified in FR-016 (lookup by `(id, version)`; if absent, create with immutable provenance; if present with matching hash, skip-or-throw per duplicate-handling config; if present with mismatched hash, **throw**).

**A reconciliation pass doubles as a source-validity check.** When a previously-persisted `(id, version)` shows up on a later pass with a *different* content hash, the hash mismatch is **diagnostic signal that the source is broken** — same logical identity must mean same content. Model X surfaces this by throwing loudly at the reconciliation site rather than silently tolerating drift; the operator gets immediate, actionable awareness. "The source is broken" is *useful knowledge*, not a problem the system is supposed to paper over.

**What reconciliation is NOT** (under Joey's adopted Model X):

- **Not a mirror that tracks source-side deletions.** Versions in the persisted store are never deleted (per [`follow-up-items/2026-05-08_entity_design.md`](../../../elsa-foundation-project-management/epic1-elsa-refactor-constitution/follow-up-items/2026-05-08_entity_design.md) Q3 stance); a source disappearance is informational only at the operator layer (logging / telemetry) and is not propagated into entity state.
- **Not a continuous drift-tracking system.** There is no `LastSeenAt` heartbeat, no `IsStale` flag, no `RemovedAt` flip on the entity. Reconciliation is transactional at entry-creation time only; per-pass state lives in logs, not in the domain.
- **Not a mutation channel into existing versions.** A version is immutable once persisted; reconciliation only ever creates new entries, skips matched-hash ones, or throws on mismatched-hash conflicts.

**Status.** This is Joey's working definition adopted 2026-05-28. Sipke's earlier framing (`2026-05-26_ENTITY_DESIGN_RESPONSE_SIPKE.md` item 6) treated reconciliation as a continuous drift-tracker with `LastSeenAt` / `IsStale` / `RemovedAt`. Alignment on the canonical definition is queued for the 2026-06-01 architecture review meeting (agenda Item 1 — Definition of Reconciliation; the Model X mechanism in Item 2 follows from the definition).

Version-tied rows are immutable (enforced consistently with the Version's `[Immutable]` regime); Draft-tied rows remain mutable. Re-laying out an already-promoted Version requires minting a new Version. Designer layout is treated as part of authoring, not as a mutable side-channel.
- Q: Unit B coupling — does Unit C wait for, or proceed independently of, Unit B's catalog-side `ActivityVersionId`? → A: Independent. Unit C declares `ActivityNode.ActivityVersionId : string` now; the value written into it follows Unit B's emerging format convention (per Joey 2026-05-28: stable). No constitutional coupling between units; small mechanical handshake on the string content. No shared contract type is introduced as part of Unit C.
- Q: Dual-parent FK shape on the new design-metadata entity — one entity with two nullable FKs (XOR), two distinct entity types, or a TPH/TPT hierarchy? → A: Two distinct entity types — `WorkflowDefinitionVersionLayout` (immutable, FK to `WorkflowDefinitionVersion`) and `WorkflowDefinitionDraftLayout` (mutable, FK to `WorkflowDefinitionDraft`), sharing the read contract `IWorkflowDefinitionLayout` in `Elsa.Workflows.Design.Core`. Each entity carries its own `[Immutable]` regime mirroring its parent; no XOR invariant or discriminator column is introduced.
- Q: Entity naming — does "DesignMetaData" collide enough with the existing `WorkflowMetadata` to rename? → A: Yes — rename to `WorkflowDefinitionVersionLayout` / `WorkflowDefinitionDraftLayout` (read contract `IWorkflowDefinitionLayout`). Matches Sipke item 2's exact wording ("designer layout, when it is genuinely part of authoring"); commits the scope explicitly to layout (positions/sizes/canvas state); future non-layout designer concerns become separate sibling entities under their own clearer names rather than expanding a catch-all "MetaData" entity.
- Q: Additional scope — what happens to today's `WorkflowMetadata` value object on `WorkflowDefinition`? → A: Delete it entirely. Per Joey 2026-05-28: it is legacy, none of its properties (`Provider`, `Materializer`, `MaterializerContext`, `IsSystem`, `ToolVersion`, `CustomProperties`) are needed. The `MetaData` reference is removed from `WorkflowDefinition`; the `IsSystem` shadow-column lift in `WorkflowDefinitionSavingHandler` is removed; the value-object type itself is deleted. Future Version-level metadata (per Sipke item 10) is Unit D's territory and may introduce a fresh shape with fresh semantics; Unit C does not pre-empt that decision, it only removes the legacy.
- Q: Event-sourcing for Drafts — does Unit C ship a `WorkflowDraftEvent` stream, or defer to a follow-on unit? → A: **Architectural slot in Unit C; full implementation deferred** ("Option B+"). The Draft entity stays as a materialized mutable snapshot in all modes. Event-stream persistence is an **opt-in feature** that can be enabled or disabled per deployment — not everyone wants it. The Draft entity must be shaped to support both: closed by default (no event observer registered, no persistence), open when the feature is wired in (a subscriber writes events to a stream). The seam is **domain events that fire on Draft mutations** (per framework §2.6.1). The dual-layer split (Sipke item 11) applies: UI/session undo+redo MAY remain client-side for low-latency editing; the server-side stream serves the audit / rollback / comparison / cross-session-recovery / collaboration use cases, including the "dropdown of recent edits, click to revert" UX. Layout events fold into the same Draft event stream (single stream, single replay). Version and other entities are NOT event-sourced. The concrete `WorkflowDraftEvent` entity, EF mapping, stream-persistence feature, replay APIs, `WorkflowDraftRevision` checkpoint mechanism, and revert-to-revision UX integration are deferred to a follow-on unit.
- Q: Event types and granular mutation commands — declare in `*.Design.Core`, fully implement, or defer? → A: **Declare the event types in `*.Design.Core` AND adopt granular CQS mutation commands as the canonical Draft authoring surface — independent of event-sourcing on/off.** Per Joey 2026-05-28: granular per-action commands (add/update/delete activity; add/update/delete connection; declare/update/remove variable; etc.) are architecturally better than the "save the whole state object" pattern even without event-sourcing — they avoid complex pre/post-diff comparison to derive what changed. With event-sourcing enabled, each command's event publication is the natural seam for the stream subscriber. Without event-sourcing, the commands still work as a clean per-action API. A UI builder that prefers "push the whole object" MAY layer its own coarse-grained feature on top, but the canonical Unit C surface is granular. Event type records pin to Sipke item 11's named list (`OnDraftCreated`, `OnActivityAddedToDraft`, `OnActivityRemovedFromDraft`, `OnActivityPropertyChangedInDraft`, `OnActivityMovedInDraft`, `OnConnectionAddedToDraft`, `OnConnectionRemovedFromDraft`, `OnVariableDeclaredInDraft`, `OnInputChangedInDraft`); workflow-level metadata events (`MetadataChanged`) are deferred to Unit D since the metadata fields themselves are Unit D's allocation.
- Q: Validation error storage — sibling entity, inline on Draft, or computed-on-read? → A: **Sibling entity** — `WorkflowDefinitionDraftValidation`, FK to `WorkflowDefinitionDraft`, no Version-side counterpart (by the no-errors-required-for-promotion rule). Errors are simple data (not immutable individuals with `IsSolved` tracking — that framing was considered and rejected as the wrong abstraction). On each Draft mutation, validators rebuild the full error set; the prior set is replaced wholesale. Errors are **grouped by `(Path, Type)` scope**: `Path` points at where the error is (NodeId, optionally extended with an input/output ref), `Type` is the validation category (`General` / `Input/Output` / etc.). The UI uses `(Path, Type)` to group related errors together (e.g., the two missing required inputs of an HttpSendRequest activity render as a single grouped item). Multiple errors may share the same `(Path, Type)` scope.
- Q: Validator subscription pattern — granular subscription, coarse `OnDraftMutated` event, or hybrid? → A: **Coarse event, named `OnDraftValidating`** (not `OnDraftMutated` — "mutated" is too wide; "validating" precisely names the validators' phase). Fires after every granular Draft mutation (the FR-018 events). Validators subscribe to `OnDraftValidating` and contribute errors via a method, not by mutating a raw collection (see the new "domain events expose intent-revealing methods" sub-pattern below). Granular FR-018 events stay as the event-sourcing-stream surface. Two-layer surface — granular = "what happened" (stream), coarse = "validate the post-mutation state" (validators + any future generic per-mutation consumer).
- Q: Domain events — should they expose raw collections or intent-revealing methods? → A: **Intent-revealing methods, not raw collections.** Adopted as a framework §2.6.1 sub-rule (provisional, pending the 2026-06-01 review). Domain events MUST expose method-based contribution APIs (e.g. `AddVersion(IActivityDefinitionVersion)` on `OnActivityVersionsReconciling`; `AddValidationError(ValidationError)` on `OnDraftValidating`). The backing collection MUST be private; the read accessor is a **public `IReadOnlyList<T>`** property — non-mutating by type, so public visibility is safe and `InternalsVisibleTo` is NOT used as default (per Joey 2026-05-28: "read-only means items inside can also not be replaced or mutated; all good"). Events MUST be `sealed class` (not `record`). Rationale: tighter encapsulation, self-documenting contracts (method names reveal allowed contributions), no accidental cross-handler manipulation. **Smell heuristic** (per Joey 2026-05-28): *too wide a variety of methods on a single domain event indicates two distinct events that should be split.* Cascade: retroactively refactor `OnActivityVersionsReconciling` in this branch (Unit B's reconciliation pattern) to match — same reasoning as the Model X cascade: don't leave two patterns in the codebase.
- Q: Does the Draft → Version promotion command also take the `workflow-draft:{DraftId}` lock? → A: **Yes, the same lock with the same key.** Promotion is a state-affecting operation that reads the Draft + reads the validation sibling + creates a Version + may update Draft lifecycle state — all of which must observe a consistent Draft. Sharing the lock with mutation commands serializes them on the same Draft. **Architectural consequence (per Joey 2026-05-28):** mutations arriving *after* a promotion are not part of the promoted Version — they exist on the Draft only and would have to be promoted to a new (higher) Version to be included. This is exactly the Version-immutability rule at work; the lock makes it concrete.
- Q: Catalog completeness — enforce by parity test or rely on review discipline? → A: **Parity test ships in Unit C.** A reflection-based test scans the `Elsa.Workflows.Design.Core` assembly for all `IDomainEvent` types and parses `DOMAIN_EVENTS.md`'s event headings; it asserts bidirectional parity (every event has a catalog entry; every entry maps to a real event). Failing the test fails the build. Sets the precedent for §2.22.1: future domains adopting the rule inherit the same parity-test pattern. Constitutional intent (catalog as a discoverable, reliable index) becomes structurally enforced, not aspirationally maintained.
- Q: Exception semantics inside the locked mutation pipeline — if an FR-018 granular event handler or an `OnDraftValidating` validator throws, what does the publisher see and what persists? → A: **Subscriber MUST NEVER break the publisher.** Cross-domain coupling exists at the contract level (the event's shape); cross-domain *failure coupling* is forbidden. The framework's default domain-event pipeline ships an exception-shielding middleware that wraps each per-handler invocation in `try/catch`, logs the exception with diagnostic context (handler type + event type), and continues to the next handler. The dispatch always completes; the publisher proceeds as if every handler succeeded; handler failures are observable only through the middleware's logs / telemetry. This applies uniformly to FR-018 granular events AND to the `OnDraftValidating` event — validators are not special internal subscribers (a cross-domain feature like `Elsa.Http` may ship a validator that subscribes to Draft mutation events and only acts when the activity in the payload is an `HttpActivity`; that handler's exception is shielded like any other subscriber). Constitutional cascade: framework §2.6.1's "Visibility" bullet is rewritten under this rule + a default-with-escape-hatch framing (an engineer composing a custom pipeline MAY swap the exception-shielding middleware for aggregate-throw / fail-fast / retry / dead-letter semantics; the rule is a default, not a closed mandate). Code cascade landed in `Elsa.Mediator` (Phase-6): new `DomainEventHandlerIteratorMiddleware` + `DomainEventExceptionShieldingMiddleware`; refactored `DomainEventHandlerInvokerMiddleware`; default pipeline composes `Iterator → ExceptionShielding → Invoker`. Status: provisional pending 2026-06-01 review (agenda Item 4b).
- Q: Granular event-surface completeness — Sipke item 11's list gives activities + connections full add/remove/update symmetry but only `OnVariableDeclaredInDraft` and `OnInputChangedInDraft` for the definition-bag concerns (variables, workflow inputs, workflow outputs). Is that intentional or a gap? → A: **Fill the gap with symmetric CRUD per definition-bag, and rename workflow-input/output events to be explicit (`WorkflowInput` / `WorkflowOutput`, not bare `Input` / `Output`).** Per Joey 2026-05-28: at design time, workflow inputs and workflow outputs are workflow-definition-level *declarations* — they are NOT the same concept as per-activity inputs/outputs; the workflow-level fields only get bound *as* activity-shaped inputs/outputs at compile time when the workflow is composed as an activity inside another workflow. Explicit naming avoids the ambiguity in Sipke item 11's `OnInputChangedInDraft` and prevents conflation with `OnActivityPropertyChangedInDraft` (which covers per-activity properties). Concretely: replace `OnInputChangedInDraft` with three explicit events (`OnWorkflowInputAddedToDraft`, `OnWorkflowInputUpdatedInDraft`, `OnWorkflowInputRemovedFromDraft`); add the equivalent trio for workflow outputs; extend variables from declaration-only to full add/update/remove. FR-018 grows from 9 → 16 mutation events; FR-019 grows correspondingly. The §2.6.1 smell heuristic ("too wide a variety of methods on a single domain event indicates two distinct events that should be split") is satisfied — one event per (collection, operation) pair, not one event covering all operations on a collection.
- Q: Should the scope-policy test (FR-004 / SC-003 / US1 Acceptance Scenario 2) ship in Unit C, or rely on review discipline against the constitutional rule? → A: **Rely on review discipline for now; defer automated enforcement to a future *Code Analysers* epic.** Per Joey 2026-05-28: the constitution is being made deliberately sound precisely to avoid needing ad-hoc per-unit guard tests; once all the patterns settle and the platform reaches a steady state, a dedicated *Code Analysers* epic can approach compile-/build-time enforcement as a unified bundle (whole-platform static analysis, not per-rule micro-validators). Creating ad-hoc validators per constitutional rule now would produce mess; the constitution + documentation header + PR review carry the rule until the dedicated epic opens. Cascade: FR-004 + SC-003 + US1 Acceptance Scenario 2 + Edge Case wording all updated to reflect review-discipline-only enforcement. The catalog-parity test (FR-031) is kept because documentation drift on the events catalog is uniquely structural — the catalog IS the discovery surface for cross-domain consumers, and a stale catalog is an immediate consumer-impact problem from day one (different category from the State scope policy, which evolves slowly and is reviewer-tractable). Registered as future-epic candidate in `follow-up-items/2026-05-28_future_epic_code_analysers.md`.
- Q: Activity-domain naming + design/runtime composition — when a model-owning domain (HTTP, Email, Slack, …) contributes activities, do they live at `Elsa.Activities.Design.<Domain>` / `Elsa.Activities.Runtime.<Domain>`, at `Elsa.<Domain>.Activities.Design` / `Elsa.<Domain>.Activities.Runtime`, or somewhere else — and where do activity-specific validators land? → A: **Three-segment HTTP-owns-prefix.** Per framework §2.2 (model-owning domain wins prefix; HTTP owns HttpRequest, headers, etc.), the pattern is `Elsa.<Model>.Activities.<Phase>` — for HTTP: `Elsa.Http.Activities.Design` + `Elsa.Http.Activities.Runtime`. Activity-specific validators co-locate inside `Elsa.<Model>.Activities.Design` (consistent with session-2 Q3's "validators live with their activity feature" rule). The design-time module subscribes to `OnDraftValidating` from `Elsa.Workflows.Design.Validations.Core` (cross-`.Core` reference per §2.1). §E2.2 hard rule preserved — Runtime modules never reference Design modules at the implementation level (separate packages). §2.20 Rule 1 preserved — no empty `Elsa.Http.Activities` umbrella unless real shared code emerges between Design and Runtime. Constitutional cascade: new §E3.10 worked example folds into Elsa constitution as additive guidance — three-segment secondary-domain naming with phase split. No new framework rule; §2.2 + §2.20 + §E2.2 already cover it. Status: provisional pending 2026-06-01 review (agenda Item 6).
- Q: `InputDefinition` / `OutputDefinition` have no `IsRequired` flag — how does the FR-033 required-vs-optional validator get its source of truth? → A: **Add `bool IsRequired { get; init; } = false;` to `InputDefinition` and `OutputDefinition` in `Elsa.Activities.Design.Core/Models` as part of Unit C.** Defaults to `false` for backward compatibility — framework §2.21.1 preserved (existing test subjects/objectives unchanged). Per code check: `WorkflowDefinitionState.Inputs` / `Outputs` use the *same* `InputDefinition` / `OutputDefinition` records as activity-level inputs/outputs. The activity-node validator reads `InputDefinition.IsRequired` from catalog metadata. `OutputDefinition.IsRequired` describes a result the activity contract guarantees to produce; it does **not** require an author to add an output capture to every placed node (clarified by issue #1058). Workflow-level input/output requirements remain downstream semantics because the authored state carries declarations, not invocation bindings. Touches Unit B's `Elsa.Activities.Design.Core` surface but the change is purely additive — one constructor parameter per record + EF column for activity-side persistence.
- Q: Validator registration audience — does Unit C ship any validators, and where do activity-type-specific validators live? → A: **Unit C ships a `Validations` sub-domain under `Elsa.Workflows.Design` with two modules** (no secondary-domain split per consumer; refined from an earlier draft of this answer). Structure: (1) `Elsa.Workflows.Design.Validations.Core` owns `ValidationError`, `IWorkflowDefinitionDraftValidation` (read contract for the persisted error sibling), and the `OnDraftValidating` event — these were previously sketched in `Elsa.Workflows.Design.Core` (FR-022, FR-025); they relocate here. (2) `Elsa.Workflows.Design.Validations` ships **all baseline validators** applicable regardless of activity type — graph integrity (orphan activity with no connection, missing/duplicate start activity), duplicate variable name (case-insensitive), activity input/output required-vs-optional metadata check, **and the variable-expression resolver** (if `expression.Type == Variable`, the named variable MUST exist in the workflow definition). Per Joey 2026-05-28: expression resolution is **too inherent to workflow authoring** to factor into a `Validations.Expressions` secondary-domain module — it folds into the baseline. The feature references `Elsa.Workflows.Design.Validations.Core` + `Elsa.Expressions.Core` (cross-`.Core` per §2.1). The baseline list is intentionally **open-ended**: additions land as universal cases surface. (3) **Activity-specific validators ship inside their activity feature** — e.g., `Elsa.Http` ships `IDomainEventHandler<OnDraftValidating>` implementations that recognise their own activities and contribute errors (HttpEndpoint authorization-policy lookup; URL string-input validation; the real recurring-bug case Joey cited). No `Elsa.<Activity>.Validations` sub-module per activity is required — the handler is a small body of work co-located with the activity itself; the activity feature already references `Elsa.Workflows.Design.Validations.Core` to subscribe. If a given activity grows a substantial validator surface later, refactor-cost (§2.16) governs the extraction. No new constitutional rule is needed; the structure leans on existing §2.6.1 cross-feature subscription via domain events.
- Q: Reconciliation policy under Unit B's cascade — does the workflow design side need an operational/reconciliation-state sibling, mutable provenance fields, and per-pass tracking (Sipke item 6's full model), or is it a stricter immutable-only model? → A: **Model X** — strict immutable-only reconciliation. Per Joey 2026-05-28: a version is immutable, full stop; reconciliation is exactly one-shot at creation time. Lookup by `(id, version)`; if found and hash differs → throw (real version-mismatch conflict, not a duplicate); if found and hash matches → skip or throw per duplicate-handling configuration; if not found → create with all provenance fields immutable. No per-pass mutating fields (no `LastSeenAt`, no `IsStale`, no `RemovedAt`) live on the entity. Source disappearance is intentionally not tracked at the entity layer; versions are never deleted. This applies to **both** Workflow design (Unit C scope) and Activity reconciliation (Unit B's already-landed reconciliation-state sibling needs an alignment-check against this model). Model X is Joey's adopted working position; Sipke's pushback room is the 2026-06-01 architecture review meeting. The constitutional codification of Model X (in §E2.X or a sibling §E2.Y) is provisional until that meeting.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Codify the scope and protect it with a test (Priority: P1)

The architecture group ratifies *what `WorkflowDefinitionState` is for* and *what it is not for*, **and** ratifies the Unit C reconciliation policy (Model X — immutable provenance, skip-or-throw with hash safety net, no per-pass mutating fields, no operational reconciliation sibling). Both rules are recorded in the Elsa constitution; the `WorkflowDefinitionState` record carries a documentation header pointing at the scope rule; the in-State / out-of-State boundary is enforced by **review discipline** (PR review against the constitutional rule) for now — automated compile-/build-time enforcement is explicitly deferred to a future *Code Analysers* epic that approaches the whole platform's static analysis as a bundle (per session-3 clarification). The Model X sub-section is queued for explicit ratification at the 2026-06-01 review meeting.

**Why this priority**: The constitutional codification is the load-bearing deliverable of Unit C. Without it, Units D/E/F/G have no shared substrate for "what stays in State vs. what splits off." Stories 2 and 3 deliver structural support but make no sense without the rule they support.

**Independent Test**: Land the constitution amendment + add the documentation header on the `WorkflowDefinitionState` record. Verify against today's State that the existing members (`Variables`, `ActivityConnections`, `Activities`, `Inputs`, `Outputs`, `WorkflowActivityOptions`, `StrategyOptions`) are clean against the policy by review (per FR-005). Future violations are caught at PR review time, not by an automated test in Unit C.

**Acceptance Scenarios**:

1. **Given** the Elsa constitution at v2.0.0 (draft), **When** Unit C's amendment is folded, **Then** a new §E2.X exists that codifies the in-State / out-of-State scope and ratifies the architectural triplet (`WorkflowDefinitionState` ↔ read models/projections ↔ `WorkflowExecutable`), with cross-references from §E2.2 (Design ↔ Runtime split) and §E2.6 (artifact-only runtime).
2. **Given** the codified scope, **When** the `WorkflowDefinitionState` record is read by any future contributor, **Then** they find a documentation header that quotes the in-State / out-of-State boundary and points at the constitution §E2.X.

### User Story 2 — Extract designer layout into a sibling entity (Priority: P2)

Designer layout (positions, sizes, canvas metadata) is removed from any path that could land inside `WorkflowDefinitionState`, and is owned by two normalized sibling entities — `WorkflowDefinitionVersionLayout` (FK to Version, immutable) and `WorkflowDefinitionDraftLayout` (FK to Draft, mutable) — each holding a normalized list of design-metadata records keyed by NodeId. A unified getter-only read contract `IWorkflowDefinitionLayout` lives in `Elsa.Workflows.Design.Core`; both entities live in `Elsa.Workflows.Design.Persistence.Core`; EF Core mappings live in the existing EFCore project.

**Why this priority**: Designer layout is the single largest concrete chunk of "could-be-creep" content Sipke called out as conditional ("when genuinely part of authoring"). Joey's 2026-05-19 pre-meeting position (entity-design follow-up Section D, Q4) and today's confirmation lock the sibling-entity approach. Without this, Story 1's policy is correct in the abstract but immediately violated the moment designer layout is implemented.

**Independent Test**: Independently from Story 1, designer layout can be authored against the sibling entity, persisted, retrieved, and rendered by the designer — without `WorkflowDefinitionState` itself growing any layout-typed members. The sibling entity's normalized list of metadata records keyed by NodeId can be inspected for any given activity node without traversing `WorkflowDefinitionState`.

**Acceptance Scenarios**:

1. **Given** a `WorkflowDefinitionVersion` is persisted, **When** a designer client writes layout metadata for its placed activity nodes, **Then** the metadata lands in a `WorkflowDefinitionVersionLayout` row FK'd to that Version (or, for Drafts, a `WorkflowDefinitionDraftLayout` row FK'd to the Draft), holding a normalized list of design-metadata records each keyed by a NodeId belonging to the parent's activity graph.
2. **Given** the sibling entity is in place, **When** a runtime or projection consumer loads only `WorkflowDefinitionState`, **Then** no design-metadata records are reachable through it (the runtime and read-side consumers stay layout-oblivious).
3. **Given** the read contract `IWorkflowDefinitionLayout` lives in `*.Design.Core`, **When** a design-time consumer references only `*.Design.Core`, **Then** it can read design metadata via the contract without depending on `*.Persistence.Core`.

### User Story 3 — Unify NodeId terminology and collapse the catalog reference (Priority: P2)

`ActivityNode.ReferenceKey` is renamed to `NodeId`, and `ActivityPortConnection.ActivityReferenceKey` is renamed to a NodeId-named property (final name `NodeId` or `ActivityNodeId` settled at plan stage), so the join key used by connections, by the new `WorkflowDefinitionDesignMetaData`, and by any future per-node sibling is consistently named. Separately, today's `(activityDefinitionId : string, version : int)` pair carried on `ActivityNode` is collapsed into a single `ActivityVersionId : string` — the stable catalog reference owned by Unit B.

Argument-level `ReferenceKey` (on `ArgumentDefinition`, `InputDefinition`, `OutputDefinition`) and `VariableDefinition.ReferenceKey` are different semantics and stay untouched.

### Edge Cases

- **A design-metadata record references a NodeId that no longer exists in `WorkflowDefinitionState`.** Orphaned records are tolerated transiently during edits on the Draft-side entity; eventual cleanup is a draft-save-side concern. The Version-side entity is immutable, so this case does not arise post-promotion. The runtime/projection side is never affected because it does not load design metadata.
- **A design-metadata row exists but its parent `WorkflowDefinitionVersion`/`WorkflowDefinitionDraft` was deleted.** Treated as orphan; cleanup is owned by the persistence-side cascade configuration on each of the two entities, not by `WorkflowDefinitionState`.
- **A future contributor tries to nest layout-style fields back into `ActivityNode` (e.g. position, size).** Caught at PR review against the constitutional scope rule (Elsa §E2.X) and the documentation header on `WorkflowDefinitionState`; rejected at PR time, not at runtime. Automated compile-/build-time enforcement is deferred to a future *Code Analysers* epic per session-3 clarification.
- **A consumer that today reads `(activityDefinitionId, version)` from `ActivityNode` must keep working through the collapse.** Covered by framework §2.21.1: the existing tests' subjects/objectives are preserved across the rename; consumer-side mapping changes accordingly.
- **A property newly proposed for `WorkflowDefinitionState` whose category is genuinely ambiguous between "authored content" and "projection / catalog / build metadata".** Surfaces as an architecture-meeting escalation; resolution is constitutional (amend §E2.X), not silent.

A validator that throws *past* its own boundary is a bug; the dispatcher's shielding catches it (so dispatch completes), but that validator's error contributions for the current pass are lost. Workflow-level required inputs/outputs are declarations without invocation bindings and remain a downstream semantic.

Walks all catalog-backed activities (root + nested); resolves each node's `ActivityVersionId` against the catalog (`IActivityDefinitionLookup`); emits `ValidationError(Path: "{NodeId}", Type: "Graph/UnknownActivityVersion")` when the version does not resolve. Engine-intrinsic nodes (`ActivityNode.Intrinsic != null`) are excluded because they deliberately have no persisted catalog row and are validated by intrinsic-specific validation/compilation. Other catalog-consulting validators skip the unresolvable node rather than fault — this validator owns the report. Intended consequence, ratified with the amendment: a draft referencing catalog activities from an uninstalled package carries a visible validation error (and cannot promote per FR-024) until the package is reinstalled.

The validator requires `Elsa.Expressions.Core` for expression-type knowledge; this dependency is acceptable because the feature itself depends on `Elsa.Expressions.Core` per FR-032 (expressions are inherent to workflow authoring).
