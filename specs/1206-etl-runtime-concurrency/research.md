# Research: runtime concurrency

Source inspected: #3803 at `ece0e0b6f383ac082fca5366a3d4396264e733f9`; existing EF retry/classifier and the design-store implementation. This is a continuation of qualified schema work, not a new persistence design.

- **Decision: reuse `EfWriteRetry`, one budget per public store operation.** Its default budget is 16. Use `IsSaveConflict(Concurrency | UniqueKey)` for wrapped save races plus `IsTransientWriteConflict` for failures during queries. Pass the context so a surviving caller transaction cannot be silently bypassed. Remove the old two-attempt claim loop; retries must not multiply.
- **Decision: keep capture outside retries.** `AcceptBatchAsync` snapshots at most two effects; `AdmitConnectorAsync` serializes bounded shard pins. Capture these once, then call private single-attempt bodies. The current snapshot tests are retained and gain conflict-between-capture-and-retry controls.
- **Decision: database units own their transactions.** Refuse existing caller/ambient/enlisted transactions before clearing tracking or issuing SQL. Dispose failed attempt transactions before retry and clear abandoned tracking. Re-read clock, terminal state, fences and budgets inside every attempt. Inspection calls an unretried private connector-run read within its own transaction.
- **Decision: normalize the runtime failure boundary.** A small public `EtlStoreException` in Core.Runtime is catchable through the three existing public store contracts. It retains operation, nullable scope/run identifiers and original cause. Retry sees original provider exceptions; wrapping occurs once afterward. Preserve cancellation, validation/corruption and direct `SchemaWriteRefusedException`. Design-store cleanup stays #3758.
- **Rejected: a store decorator or new execution port.** The existing partial store and a private helper cover the demonstrated requirement without changing replacement registration or optional connector capabilities. No physical file/HTTP/SQL/RabbitMQ operation enters the retry boundary.
- **Proof strategy:** real contexts on the same server database rendezvous at their first save after both read; the gate acts once per participant so retries cannot wait on it again. Identical admission must return Applied+Replay; changed immutable content Applied+Conflict. Record a native classified conflict and remove/restore retry to demonstrate the guard. SQLite begin-immediate gates cannot stand in for server contention.
- **Correctness workload:** four independent writers over a finite set of 32 runs with at least two partitions, checking all accepted/outstanding counters, unique terminal/outbox identities and stale fences. This is a bounded correctness soak, with no throughput or latency assertion.

- **Planning-review correction: multi-save preparation.** `CommitConnectorPreparationAsync` has three saves. A classified injected conflict after a successful first save must roll back the whole transaction, reconstruct one complete graph on retry, and leave no partial persisted/tracked graph at exhaustion. Real engines supply the database/transaction; injected failures are labeled separately from native contention.
- **Planning-review correction: continuous compaction.** `CompactConnectorHttpHistoryAsync` executes set-based updates/deletes before `SaveChangesAsync`; it must not use the finite first-save rendezvous. A separate command interceptor stages a failure after a real compaction write, before lease persistence. Verify rollback/retry preserves request predecessors, retained batch/page identities, exact compacted accounting and one current lease; exhaustion restores the prior history. This qualifies an existing transition, not a new continuous capability.
