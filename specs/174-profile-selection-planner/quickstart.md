# Validation guide: pinned selection planner

Status: local implementation validation for #1986. PR and post-merge evidence must be recorded separately against their exact heads.

## Local prerequisites

- .NET 10 SDK and restored repository packages.
- The public `Elsa.Modularity.Planning` library and its tests.
- No host, database, package feed, or secrets are required; supplying any of them would violate the pure-planner test boundary.

## Focused checks

Run the planning test project in Release. The test suite must assert the exact sorted feature-ID sets for Embedded (12), Authoring (16), Worker (14), and Custom (17) using the documented *planning fixtures*. Run each with reordered definition/member declarations and formatting changes. Compare complete selection/removal reasons, not only counts.

Run the contract's negative vectors: overlapping profile/group/addition/removal; required removed edge; manifest-only optional companion; unknown ID; absent package; unreadable manifest; known incompatible package; loaded empty descriptor versus manifest edge; changed catalog version and rationale. Verify that no missing dependency is auto-added and no test claims a runnable host.

Canonicalization checks must use two independent UTF-8 expected-digest vectors, including non-ASCII display/rationale text, generated by an ECMAScript RFC 8785-compatible implementation. Formatting, object-key order and set-member order preserve the digest. Duplicate JSON keys, lone surrogate input, duplicate member IDs, unknown schema version and same ID/version with changed content refuse with specific codes. A tampered digest must fail before expansion.

Re-resolution checks hold the accepted document byte-for-byte, compare old and candidate exact sets/reasons/package locks, and mark unknown settings/resource impact unverified. A persistence summary must contain only redacted resource references and source/status; if absent, provider/connection/schema/migration/layout are all unchecked. A side-effect sentinel should fail if any file write, package fetch, database call or host activation is attempted; the public planner should have no such dependency to invoke.

## Repository gates

```bash
dotnet test tests/essentials/Modularity/Planning/Tests/Elsa.Modularity.Planning.Tests.csproj -c Release
dotnet test tests/essentials/Architecture/Elsa.Architecture.Tests.csproj -c Release
dotnet run --project tools/maps/Elsa.Maps.Generator -- check
dotnet run --project tools/maps/Elsa.Maps.Generator -- solution-filters-check
git diff --check
```

If map check is red because the added project changes generated facts, run `dotnet run --project tools/maps/Elsa.Maps.Generator -- all`, review generated findings, and stage every changed map path including `docs/maps/manifest.json`. Run the checks sequentially to avoid competing writes to the generator's build output. Finish with exact-head PR CI and exact post-merge main CI/Maps.

## Limits of this evidence

These tests prove deterministic selection planning against supplied snapshots. They do not prove that Embedded/Authoring/Worker can activate in a rebuilt host, that a package is loadable or available in a feed, that migrations are safe, or that a web builder is usable. Those are later gates under #1961–#1964.
