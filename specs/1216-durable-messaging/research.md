## Baseline refresh corrections

The initial scan used `b7fc0ec330ad55a2062b5badbf7697705852201b`. Relevant changes through the inspected baseline are included above and add these implementation constraints:

- [`RuntimePostCommitOutboxClaimedQuery`](../../Essentials/src/Workflows/Runtime/Core/Models/RuntimePostCommitOutbox.cs) now accepts `DeliveredByClaimSince` and ordinal `ExcludedDeliveredOutboxItemIds`. [`IRuntimePostCommitOutboxClaimStore.ListClaimedAsync`](../../Essentials/src/Workflows/Runtime/Core/Contracts/IRuntimePostCommitOutboxClaimStore.cs) returns unsettled rows first and qualifying claim-delivered rows afterward. Exclusions apply before the limit and do not hide held rows. EF adds `ClaimDeliveredAtUtcTicks` and migrations for SQLite, PostgreSQL, SQL Server and MySQL; older null projections are tolerated and omitted from the completed-delivery listing.
- [`RuntimeCoalescingSession`](../../Essentials/src/Workflows/Runtime/Elsa.Workflows.Runtime/Services/Coalescing/RuntimeCoalescingSession.cs) records `QueueSeededAt`. [`WorkflowDrainOrchestrator`](../../Essentials/src/Workflows/Runtime/Elsa.Workflows.Runtime/Services/Scheduler/WorkflowDrainOrchestrator.cs) detects continuations a peer delivered after that snapshot and restarts the segment from durable state. Preserve that handoff and the delivered-ID exclusions; otherwise an overlay can report quiescence while durable work remains queued.
- [`WorkflowCancellationPlanner`](../../Essentials/src/Workflows/Runtime/Elsa.Workflows.Runtime/Services/ActivityExecutions/WorkflowCancellationPlanner.cs) cancels only `Scheduled`, `Running`, `Waiting` and `Suspended` activities. Superseded source lineage and its bookmarks can remain. Raw bookmark existence is therefore insufficient eligibility; retain exact activity-generation and nonterminal owning-execution checks.
- [`GetRuntimePersistenceMode`](../../Essentials/src/Workflows/Runtime/Api/Endpoints/PersistenceMode/Get/Endpoint.cs) exposes `GET runtime/workflows/persistence-mode` with `WorkflowRuntimeRead`. It is an existing integration/Studio inspection seam, not message durability qualification.

The refresh did not land standalone message ingress, buffering, per-definition arbitration, independent message deduplication or active-key admission.

## Proposed integration boundary

**Proposal, not an accepted architecture or implemented contract:** place message acceptance and per-definition recipient selection in the shared runtime persistence boundary. Reuse existing scheduler, mailbox, checkpoint, post-commit delivery, publication/start policy and exact-recipient mechanisms for execution. Preserve the immutable Event cohort protocol and Event broadcast semantics.

The proposed message-owned records would distinguish durable acceptance, outstanding eligibility, one immutable selected recipient per logical definition, delivery progress, and terminal outcome. They must preserve the original accepted message's other definition deliveries when one definition succeeds or a producer retries. An accepted message's producer identity must remain recognizable for the independent deduplication window even when its payload buffer or recipient execution has ended.

Use native/model adapters only where an owning model has genuine recipient contracts. They must return authoritative tenant/model/logical-definition identity and exact subscription/admission evidence; an adapter must not create a competing execution store or broker. Notifications can prompt reconciliation, while persisted obligations and recovery scans cover lost notifications, restarts and partial multi-definition progress.

Shared standalone ingress is being discussed in [#2892 comment 6670940060](https://github.com/elsa-workflows/elsa-foundation/issues/2892#issuecomment-6670940060). It is a live proposal, not a landed capability or dependency that can be assumed present. Coordinate shared-runtime changes with the active owner of [#3820](https://github.com/elsa-workflows/elsa-foundation/issues/3820); this inventory does not authorize taking over that work or resuming unrelated programs.

## Design and qualification risks

1. **Acceptance uncertainty:** define the durable acknowledgement boundary, duplicate acknowledgement and retry-safe producer identity. An interrupted response may follow a successful commit. Immediate-only unmatched submission needs an explicit result rather than an implied buffered acceptance.
2. **Selection and recovery:** persist a per-definition winner before effects, or prove an equivalent atomic protocol. A crash, stale worker, lost acknowledgement or changed publication must complete the same selection without admitting a second start/wait recipient. Treat temporary unavailability separately from permanent failure; do not reselect merely because a selected recipient cannot be read.
3. **Key admission:** enforce same-key message-start exclusion across workers and versions using durable authority, including the interval before the execution header exists. Release requires the owning native/model terminal contract; incidents, cancellation races and pending model settlement need explicit rules. Other start mechanisms retain their own policy.
4. **Late eligibility:** decide which late waits and newly published definitions can receive buffered messages, how long matching remains open after another definition succeeds, and what publication replacement changes before versus after selection. Expiry must not leave ambiguous in-progress obligations.
5. **Boundaries:** derive tenant/access scope from authenticated authority, distinguish logical definition from artifact/version and subscription, and preserve test-run isolation. Payload, correlation, failure details and secret references require the normal authorized access rules.
6. **Retention:** separate payload buffering, producer-ID recognition, delivery receipts and execution/material roots. Bound storage and admission pressure. Cleanup must not delete an outstanding recipient's recovery authority or make a duplicate appear newly accepted within its window.
7. **Payload and ordering:** specify compatibility failures, competing waits, start/wait priority and deterministic fairness. Existing Event payload acceptance and correlation behavior do not settle these message decisions.
8. **Provider claims:** in-memory mechanisms are not restart durability. EF implementation alone does not qualify every relational provider or multi-node mode. Exercise the actual selected provider, schema, host composition, workers, crash/restart and acknowledgement-loss paths before making those claims.

## Subsequent source-audit findings, 6 November

- Material declarations must come from hash-covered behavior. [`WorkflowExecutableHasher`](../../Essentials/src/Workflows/Runtime/Elsa.Workflows.Runtime/Services/Executables/WorkflowExecutableHasher.cs) omits native node metadata from both node hash renderings, while actual input bindings/descriptor payloads participate. A metadata-only Message-name annotation could change eligibility without changing artifact identity. Native providers must read literal/hash-covered inputs; metadata can only be a checked derived hint. Direct BPMN owns its versioned hashed model bindings; existing signal formats are not Message declarations.
- Direct BPMN material IDs are synthetic/content-derived. The contained provenance change uses explicit `BpmnModel.Authored.v1` source attribution for canonical authored DefinitionId while preserving material pins/hashes; legacy `BpmnModel` retains absent logical provenance. Runtime/catalog/embedding recognition must share the exact owned matcher. This is separate from actual Message start/wait/interest integration.
- Sender cancellation can use one retained Message sender control rather than enumerating every source. [`EfWorkflowExecutionStateStore`](../../Essentials/src/Workflows/Runtime/Persistence/EntityFrameworkCore/Stores/EfWorkflowExecutionStateStore.cs) supplies a revision-neutral transactional write-lock pattern. New finalization must acquire/recheck its control and canonical source inside the owned transaction; the existing completion implementation's pretransaction reads are not sufficient for this participant. Cancellation retries do not make arbitrary source-induced sender revision increments harmless. Reserve native outcome/continuation capacity in the initial suspension checkpoint so later refusal can always retain its proof.
- Relevant backend/BPMN test projects require [verified archived-fixture hydration](../1017-direct-bpmn-hosting/evidence/README.md) through `python3 tools/bpmn/restore_evidence.py`, as CI does. Restoration validates original archive/member hashes; it is test setup, not upgraded-host qualification.

These findings refine the engineering mapping. Executed component checks and their actual source snapshots belong in `evidence/`; the baseline inventory above does not qualify the first-release product.
