## Common mechanism and distinct family policy

| Source family | Canonical immutable source and selection policy | Owner retained |
|---|---|---|
| Native post-commit Event | Actual `RuntimePostCommitOutboxItem`/intent and its existing publisher authority; existing immutable exact cohort remains final, including empty. No duplicate ingress row. | Existing Event/stimulus/outbox owners. |
| Standalone `StimulusIngress` | One real Runtime standalone source with complete pre-effect exact start/wait cohort plus C2 consumer manifest. Its owner preserves original legacy ambiguity, exact tracked admissions, per-recipient dispositions and owed seal batches. | #3820/#3840 owns C2 policy, delivery-group/input/control mechanics and qualification. |
| Standalone `BusinessMessage` | One real Runtime standalone source whose immutable header is the accepted message/policy/complete logical-definition cohort. Exact per-definition winners are selected later for buffered messages; immediate-only selects/reserves or records Unmatched during acceptance. | #3583 owns interests, producer deduplication, per-definition arbitration/admission/recovery and operator behavior. |

Share canonical source identity/content verification, provider transactions, fenced work claims/CAS/replay, atomic progress/follow-up creation and the normal delivery processor. Do not impose `StimulusIngress`'s fixed exact cohort/seal policy on `BusinessMessage`, or reopen Event cohorts to implement buffering. Kernel dispatch uses registered family/version, never StateMachine/BPMN type-name tests.

`MessageAcceptance` is a typed projection of the **BusinessMessage source's immutable header**, not another acceptance-authority row. The same `MessageId` is that source ID. Per-definition records, reservations, dedup addresses and receipt/history indexes are source-owned participants/projections; none can independently authorize acceptance. Selected per-definition child deliveries are work/capability records addressed under that source, not fresh accepted-message sources. A native send's original outbox source and the accepted business source are two real causes connected by a sticky outcome, not two competing message ledgers.

`IRuntimeMessageSourceTransactions` is the BusinessMessage family capability on the **same selected source backend**, not an independently selectable store. `AcceptAsync` is standalone application acceptance only; native send handlers MUST NOT call it or any other mutating acceptance method. Public commands contain proposals, not authority; the provider rereads trusted scope, canonical source, permissions/owner captures and exact physical conditions. No public delegate/SQL/JSON mutation escape hatch enters `CommitAsync`.

Planner execution is effect-free: `PrepareAsync` may read canonical candidates but cannot reserve, accept, enqueue target commands or call actors. Only the provider commit installs exact child/winner/reservations and derives dispatch work. For a persisted Dispatch child, `HandleAsync` rereads that committed exact target/current source capability and may invoke only its normal target owner. `RuntimeDeliveryAttempt` contains transport diagnostics and candidate proof references, never authoritative Delivered. `PrepareCompletionAsync` proposes settlement; provider completion rereads canonical evidence. These distinct registered work roles cannot fall through to each other.

## Closed plans and required evidence

Use a versioned closed union with known sealed variants and a private-protected base constructor; unregistered subclasses, unknown versions and generic mutation JSON refuse. Target checkpoints accept only variants matching their actual native/model transition. Canonical payload JSON is data, not an executable mutation plan.

| Variant | Required fields and provider-derived writes/results |
|---|---|
| `MessageAcceptPlan` | Canonical request fingerprint/lifetime intent; trusted scope/producer authority capture; expected producer-address/interest/capacity revisions; complete proposed cohort/digest; immediate-only candidates when applicable. Provider revalidates all pages/policy/authority and derives one source, dedup binding and pending/selected/Unmatched rows/work. No acceptance from a partial cohort. |
| `MessageSelectPlan` | Source/header fingerprint, definition-delivery revision, complete candidate-set/wait-set revision, exact proposed candidate registration/publication capture, capability and reservation/admission epochs. Provider serializes wait-first arbitration and absence of ready waits for a start, installs one winner + exclusive reservation/admission + deterministic dispatch child. A loser remains unselected. |
| `MessageDispatchAcknowledgementPlan` | Committed child/winner/capability/target identities and candidate target-admission checkpoint/receipt reference. Provider reads that canonical proof, deriving Accepted/owed-reconciliation or still-owed retry; a handler's transport success cannot produce Delivered. It never selects another recipient. |
| `MessageConsumptionPlan` | Exact selected capability/reservation/admission condition and native consumed-wait/activity decision or model input/decision identity. The target checkpoint creates proof atomically with progression; later source settlement must read that proof. Only canonical semantic consumption derives Delivered. |
| `MessageClosePlan` | Old winner/capability/reservation epochs; authorized operation identity; target generation and canonical unconsumed-state evidence. Joint CAS closes source capability and reservation with a retained tombstone. Consumed proof wins; unresolved admission/consumption cannot close or free the wait. |
| `MessageReleasePlan` | Exact admission epoch/target, source capability and native terminal/model settlement checkpoint or proved pre-admission refusal plus closed-start capability. Provider rereads owner evidence and releases only that epoch, retaining release/retirement proof and deriving pending-discovery work. Absence is not evidence. |
| `NativeMessageFinalizePlan` | Exact physical native source/intent fingerprint; proposed MessageAcceptPlan or sanitized definitive rejection evidence; exact sender/private wait capture; stable source-outcome operation ID. Existing native claim completion revalidates sender cancellation/resolution and derives sticky Accepted/Rejected plus callback, or replay-settles existing Cancelled without callback. No persisted acceptance precedes that completion transaction. |
| `NativeMessageSenderCancellationPlan` | Exact sender/control identity and cancellation checkpoint/operation proof. The sender-fenced checkpoint seals one retained NativeSenderControl; it does not enumerate sources or capture their revisions. New finalization under a revision-neutral control lock derives Cancelled; callbacks retire using that proof. Existing Accepted remains immutable, and cancellation neither steals nor requires source transport claims. |
| `MessageSenderCallbackPlan` | Canonical sticky SourceOutcome identity/fingerprint, exact private wait/continuation generation and target consumed-result or authoritative sender-retirement reference. Provider derives callback settlement/continued debt; rejection faults through the ordinary target checkpoint. No receipt is fabricated for Rejected. |
| `TrackedSourceSealPlan` | Proposed common envelope names actual source/manifest fingerprint, retained disposition-proof references and deterministic seal-batch identity. This document only reserves the typed successful-finalization slot, without defining its group/control mutations. |

Source-claim plans use the actual source claim. Sender cancellation and target consumption are checkpoint-only participants under their owning sender/target fence; they cannot be submitted as a fabricated claimed RuntimeSourceCommit.

Initial work, callback/dispatch/reconcile/seal work and outcome projections are derived by the owning participant from the validated variant and canonical state. Callers cannot supply unrelated source/target work or assert a terminal business result.

## Physical representation and existing processor

- Add one `RuntimeIngressSourceEntity` for standalone immutable header plus source revision/operation proof, and `RuntimeDeliveryWorkEntity` for independently claimable source-owned work. Work references the actual source address; it does not duplicate source payload/cohort/authority. An indexed message receipt view is a projection of the source. Native outbox adaptation reads its existing row rather than copying it into `RuntimeIngressSourceEntity`.
- Add Message participant entities for definition deliveries, producer addresses, exact wait reservations, active-key admission and interest roots/epoch/capacity. Internal `EfRuntimeDeliverySourceStaging.ReadCurrentAsync/StageCreateAsync/StageWorkCompletionAsync` and `EfRuntimeMessageParticipantStaging.StageAcceptanceAsync/StageSelectionAsync/StageNativeOutcomeAsync` share `RuntimeDbContext`; source operations are exposed by the selected `EfRuntimePostCommitOutboxStore` backend, splitting implementation into internal helpers/partial files. These helpers stage only; the existing transaction owner commits. No second transaction owner is registered.
- `RuntimeCoreServiceCollectionExtensions` registers the in-memory family facets on its existing checkpoint/outbox state. EF aggregate registration replaces them as one owned family. Extend `RuntimePostCommitOutboxStoreBackend`'s descriptor ownership/snapshot checks and Runtime aggregate composition validation for these facets. Reject later foreign replacements, mixed access scopes and missing participant support.
- Extend `RuntimePostCommitOutboxProcessor` with internal `ProcessStandaloneAsync`/`OpenDeliveryContextAsync`, resolving family handlers and committing their plans through the selected source store. It stays under existing `IRuntimePostCommitOutboxProcessor.ProcessAsync` and `RuntimeResumptionService`; bounded source-family fairness prevents either lane starving legacy continuations. No Message/StateMachine hosted pump, fake `RuntimePostCommitIntent`, controller-owned queue or direct actor call replaces that path.
- The **only native delivery-finalization atomic entry is existing `IRuntimePostCommitOutboxClaimCompletionStore.CompleteClaimAsync`**, with optional versioned `RuntimePostCommitSourceFinalization? SuccessfulFinalization` on `RuntimePostCommitOutboxClaimCompletion`. No `CompleteSourceAsync` or handler-side acceptance commit remains. EF/in-memory implementations stage this typed participant with the actual claim result and existing dispatch projection/failure follow-up; unsupported participants refuse before any write. C2 seal and Message finalization use distinct owned variants, never fake dispatch failures. Sender cancellation is separately authorized by its physical cancellation checkpoint, not by a stolen source transport claim.
- Standalone completion commits work acknowledgement + family progress + durable child dispatch/callback/seal work in one operation. Source/work transport completion never means every business recipient consumed or that the source has no remaining domain obligations. Follow-ups have deterministic IDs; each acquires its own current claim and rereads retained original evidence.

## Native send outcome and sender handoff

`NativeMessageSendHandler.PrepareCompletionAsync` performs read/replay/planning only: it reads the actual source/current scope, canonical intent and sender/private wait, then returns `NativeMessageFinalizePlan` or the exact replay plan referencing its existing sticky outcome. `ReadNativeOutcomeAsync` is read-only. There is no `ResolveNativeSendAsync` write path. Create-only `NativeMessageSourceOutcome(SourceAddress, IntentFingerprint, Accepted|Rejected|Cancelled, ReceiptOrReasonOrCancellationProof, SenderContinuation)` resides on the native source/approved participant; it wins before producer dedup/default/capacity checks. Different source content conflicts; no ID/expired dedup cannot fresh-accept it.

`RuntimePostCommitIntentHandlerContribution` adds `requiresSuccessfulFinalization` through a new overload while preserving old constructors. It requires the completion-aware sibling handler/dispatcher; invoking old intent-only/bare context dispatch for such a kind refuses rather than discarding a return value. `RuntimePostCommitIntentDispatcher.PrepareDispatchAsync` invokes this handler or returns LegacyHandled after old dispatch. `ProcessClaimedItemAsync` carries the preparation through its claim-lease result into `RecordSuccessAsync`/`RecordDeliveryResultAsync`, which attaches SuccessfulFinalization to the existing CompleteClaimAsync request. It cannot call standalone AcceptAsync first.

That **one provider transaction** validates current persisted native claim/fence/expiry and canonical source, resolves existing SourceOutcome, rechecks producer/dedup/complete-interest/capacity and commits BusinessMessage acceptance if new + sticky Accepted/Rejected + owed callback work + native claim result. A definitive Rejected is a successfully settled transport with a business rejection callback, not a transport retry or fictitious receipt. Producer duplicates bind the original BusinessMessage source. Temporary/unknown failures manufacture no terminal outcome. An existing Cancelled outcome is replay-settled under the current claim without inbox acceptance or callback; the retained cancellation tombstone remains authoritative. Existing bare handlers and null-finalization requests keep their old paths.

Q4 adds `NativeMessageSenderCancellationPlan` through the shared [`WorkflowCancellationPlanner`](../../../Essentials/src/Workflows/Runtime/Elsa.Workflows.Runtime/Services/ActivityExecutions/WorkflowCancellationPlanner.cs) to both [`WorkflowCancelSchedulerWorkHandler`](../../../Essentials/src/Workflows/Runtime/Elsa.Workflows.Runtime/Services/WorkHandlers/WorkflowCancelSchedulerWorkHandler.cs) and [`CancelWorkflowAlterationHandler`](../../../Essentials/src/Workflows/Runtime/Elsa.Workflows.Runtime/Services/Alterations/Handlers/CancelWorkflowAlterationHandler.cs). Its exact sender/control and cancellation checkpoint/operation identity seals one retained NativeSenderControl under the sender execution fence. No source list, per-source resolution revisions or transport claim is required. Message-specific cancellation cost is constant in retained sends; existing activity enumeration remains.

The first send checkpoint provisions the control and reserves retained outcome/continuation capacity with the actual intent/private wait. New finalization acquires a revision-neutral control write lock and rereads canonical source/control state inside its owned transaction before acceptance. The [existing EF workflow write lock](../../../Essentials/src/Workflows/Runtime/Persistence/EntityFrameworkCore/Stores/EfWorkflowExecutionStateStore.cs) is a pattern; a Message-owned retained control preserves proof beyond workflow deletion. Do not increment sender revisions on every acceptance: the existing cancellation checkpoint retry policy does not make that induced contention harmless. Keep sender-control/capacity/source/target lock order consistent across all paths.

Cancellation-first seals the control. A current source claimant derives and settles immutable Cancelled without a receipt, fresh dedup allocation or callback; tombstones remain retained. Acceptance-first preserves its source outcome/message/recipient obligations. Callback admission uses the same control and exact wait proof to consume or retire responsibility. Before the suspension checkpoint, cancellation discards staging. Missing state, an in-memory token or requested cancellation cannot determine the winner; reconcile lost commit acknowledgements from durable control/outcome evidence.

Keep CompleteClaimAsync's existing enum return. A Persisted result does not expose a prepared receipt as committed: the processor must reread `ReadNativeOutcomeAsync` for the exact source/operation and return that canonical record in an additive optional `RuntimePostCommitOutboxProcessedItem.SourceOutcome`; callbacks read the same record. On lost commit acknowledgement, reconcile source+operation/outcome in a fresh owned scope before recording failure or redriving. If unreadable, preserve uncertainty/debt; never infer noncommit or accept afresh. Stale claims cannot finalize a new outcome. Equivalent committed outcome replays without repeating policy/selection; current authorization governs disclosure.

`SendMessage` stages intent + invocation-private wait in its ordinary suspension checkpoint. A source handler never accepts during uncommitted `ExecuteAsync`. Callback work uses an additive guarded Message path on `IBookmarkResumeDispatcher`, emitting DeliverMessage 22/Wait with exact `ExpectedRecipient` and the immutable source-outcome condition. Accepted completes with receipt; Rejected consumes that private wait and faults the send invocation through its normal checkpoint owner. Transport acknowledgement alone does not retire the callback. Retain canonical consumed-result or authoritative sender-retirement evidence; missing execution/activity is uncertainty. Persist responsibility before returning from the source handler; do not synchronously wait for its own callback drain/acknowledgement while holding the sender's mailbox/claim.

## Checkpoint, recipient capability and material boundary

`RuntimeMessageCheckpointChanges` is a versioned typed set of interest-root transitions, target admission/consumption proofs, source outcomes/sender continuation settlement and exact admission release evidence. `ExpectedMessageRecipient` carries source/work address, immutable selected-delivery identity, source-capability epoch and exact wait-reservation or start-admission epoch/target. The authoritative provider compares it at target admission **and** semantic consumption with ordinary execution/bookmark/model conditions. It contains no transport-key-as-authority shortcut.

- Add optional `RuntimeMessageRecipientCondition? ExpectedMessageRecipient` to the reusable native resume/model/checkpoint records, forwarding the validated exact condition into the checkpoint. Message target admission and sender callbacks travel as outer DeliverMessage 22, not ordinary Start 0/ResumeBookmark 1/ExecuteModel 21 carrying an optional flag. The guarded handler uses a closed Start/Wait/Model body; optional fields are internal propagation, not an old-reader fence. Add `WorkflowExecutableStartAuthorityKind.MessageDelivery` with `WorkflowExecutableMessageDeliveryAuthority` containing the source/definition-delivery/capability/admission addresses and exact publication/material target. Normal start policy still runs; initial native/model start checkpoint validates the admission condition. Preserve old keyed-start derivations/null fingerprints; C2 commands retain their own path.
- Update `RuntimeCheckpointCommitValidator` shape checks; `RuntimeCheckpointCommitFingerprint` wraps only nonempty semantic participants with a version. Absent/null fields serialize exactly as before and preserve old fingerprints. Refreshable attempt fences/revisions are conditions, not new semantic operation identity; immutable selected addresses/outcomes participate in the decision fingerprint. Reuse of operation ID with changed semantic content conflicts.
- `EfRuntimeCheckpointCommitStore` stages Message conditions/participants in its existing owned transaction beside exact bookmark deletion or `EfModelCheckpointStaging` model decision/input receipt, before its immutable marker. `StageMessageRecipientAsync` CAS-touches canonical source capability/reservation and target rows even when semantic content is unchanged. In-memory native participation validates then mutates under its existing gate; current in-memory model checkpoints remain unsupported.
- Forward capability/shape checks through `CoalescingRuntimeCheckpointCommitStore`, persistence policy and fold handling. Any source/recipient reservation, admission, consumption, closure/outcome or interest lifecycle mutation initially flushes the coherent physical boundary before acknowledgement/effect. Balanced remains default; untracked work is unchanged. No buffered marker or separate participant `SaveChanges` substitutes for physical acceptance.
- Selection retains exact executable/material incarnation, actual publication/source provenance or active-execution ownership and payload roots. Pending cohorts retain discoverability; an interest root grants neither start authority nor access. Native/model source capability closure and target checkpoint must serialize. Closed tombstones survive delayed envelopes and source/target deletion; a stale command cannot consume a re-reserved still-live wait or start after key release.
- Retain acceptance/consumption/closure/release and native SourceOutcome proof independently of payload buffering and producer dedup. Cleanup uses actual material/reference/execution boundaries and sticky retirement evidence. API standalone source rows never require a fictional native publisher root.

## Claims, uncertainty, provider and adoption checks

Claims use the existing fenced-claim primitive: renew immediately before dispatch on the owning scoped context, never parallel EF renewal on that same context. A long operation may outlive visibility; every effect/target admission/commit revalidates canonical source and semantic capability. Stale completion writes nothing. A successor replays the same work/operation and exact selected target, not a new match set. Source transactions reconcile lost commit acknowledgements by retained operation/source evidence in a fresh owned scope; cancellation after a commit may still leave accepted work. API retry needs the original producer ID/content, while native retry uses its immutable SourceOutcome address.

An equivalent already-committed semantic operation returns its canonical retained proof before evaluating obsolete recipient predicates, as exact checkpoint replay does today; it never reconsumes a wait or reselects. This replay does not authorize a new mutation under a stale current transport claim. Conflicting operation content refuses even when the target/claim has since retired.

EF uses Runtime's existing revision-CAS/unique-index/owned-transaction dialect and canonical projection validation.
