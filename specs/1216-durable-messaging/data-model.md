# Durable messaging data model

**Status:** Candidate engineering design; no persisted ABI, implementation or provider qualification is established here.
**Scope:** [spec 1216](spec.md), [delivery contract](contracts/delivery-design.md) and [acceptance matrix](acceptance-matrix.md). Q1–Q4 are accepted product decisions; the records below propose their implementation.
**Baseline:** `e0ba87ecfc3b1e774c509ed274b19cd3f34a1124`. Existing terms follow the [Elsa glossary](../../docs/glossary/elsa.md).

## Ownership and identity

All records belong to the selected Runtime persistence family. EF uses its existing `RuntimeDbContext`, connection, schema/migrations and transaction owners. In-memory development state uses `InMemoryRuntimeCheckpointStoreState` and its existing write gate. New domain contracts do not select another broker, execution store, delivery authority or pump.

Preserve existing opaque server identifiers as exact ordinal UTF-16, including their original framing boundaries. Submitted message names, business keys and producer IDs use the specified strict UTF-8 bounds. A material receiver address preserves the owning node/model identifier, bounded to 1024 UTF-16 code units; it is neither a subscription capability nor a substitute logical definition identity.

| Address | Candidate identity rule |
|---|---|
| `MessageScope` | Actual PersistenceScope and authoritative tenant, with a distinct finite TestScope only for isolated test work. Retain run-kind/partition in captured authority and validate them; worker placement or execution protocol cannot split a production definition/admission lane. Default partition derives from PersistenceScope; unsupported foreign partition mappings refuse. Test/private sends cannot escape to production. |
| `LogicalDefinition` | Scope + tenant + stable definition namespace + stable definition ID. Ordinary authored native/BPMN versions use namespace `WorkflowDefinition` and their canonical authored `DefinitionId`. Exclude model/protocol, version, artifact, activation slot and execution. |
| Standalone model definition | An explicitly owner-assigned stable ID in its genuinely distinct definition namespace. A protocol or material hash is not that namespace/ID. Embedded models and native workers use their owner's declared logical definition. |
| `MessageId` | Opaque server-assigned accepted identity, independent of producer ID and target execution. |
| Producer address | Scope + tenant + authorized stable producer namespace + exact producer message ID. Name/key are fingerprinted content, not deduplication namespace escape routes. |
| Definition delivery | `MessageId` + `LogicalDefinition`; one persisted record/winner across all versions and models of that definition. |
| Start admission lane | `LogicalDefinition` + exact business key; exclude message name, individual message ID and execution protocol. |
| One-shot subscription | Owner kind + exact execution/subscription identity and physical registration generation. Native captures include bookmark/activity/node/resume target; model captures include protocol/material incarnation and model-owned generation. |

Direct BPMN currently synthesizes `PinnedExecutable.DefinitionId` from material hash. Add canonical logical provenance through `BpmnModelPublicationProvenance`, its authored projection, source reference and execution capture; preserve existing executable identity/hash formats. Existing direct sources without proved stable provenance cannot silently infer historical message membership. Native-to-BPMN publication of one authored definition must retain one definition-delivery/admission address.

## Candidate records

Every mutable row carries a physical `Revision`; immutable logical content and its versioned fingerprint are validated on reread. Provider projections accelerate lookup but never override canonical content or scope.

| Record | Required retained fields and transitions |
|---|---|
| `MessageAcceptance` | Format/fingerprint version; `MessageId`; scope/tenant; trusted producer/acceptance authority; exact name/key; portable payload/reference and declared contract; sender lifetime intent; immutable effective policy; trusted `AcceptedAt`; complete ordered logical-definition cohort, `CohortDigest`, captured interest epoch; original receipt. Acceptance content/cohort never changes. |
| `MessagePolicySnapshot` | Buffered or immediate-only mode; resolved finite buffer/dedup durations/deadlines and limit/configuration version; protection/retention policy references. Preserve omitted lifetime intent separately from the resolved default. Duplicate submission never recalculates/slides deadlines. Numeric defaults/bounds belong to the API/configuration contract. |
| `MessageDeduplication` | Unique producer address; address generation; accepted `MessageId`; versioned semantic-content fingerprint; original receipt reference; `DeduplicateUntil`. Expiry permits a new generation/acceptance, never overwrite/delete the old accepted message or its deliveries. |
| `MessageDefinitionDelivery` | Unique definition-delivery address/cohort; status Pending, Selected, Delivered, Expired, Unmatched, Failed or Abandoned; immutable winner, source/target capability epochs and admission/consumption proof. Selected attempt state distinguishes ready, retry scheduled, unavailable and intervention required. Failed/Abandoned are closed terminal outcomes; a selected winner never returns to pending/reselection. |
| `MessageRecipientReservation` | Unique one-shot subscription address; reservation epoch; owning definition delivery; expected source-capability epoch and exact target capture; state reserved/consumed/closed; consumption or proved-unconsumed close evidence. Retain the last epoch/tombstone when reusable. A new message may reserve a still-live wait only after authoritative closure of the prior unconsumed capability. |
| `MessageStartAdmission` | Unique start lane; monotonically increasing admission epoch; owner definition delivery; deterministic target identity; exact publication/material/start-authority capture; reserved/admitted/released state; terminal/refusal/release evidence. Reserve before an execution header exists. Never release from lease expiry or an absent lookup. |
| `MessageInterestRoot` | Scope/tenant/logical definition; root owner kind/id; exact publication activation/source or active execution/material incarnation; finite declared names and declaration version/digest; physical revision; prepared/serving/closed lifecycle and retained close evidence. This discovery root grants no independent start/resume authority. |
| `MessageScopeControl` | Coherent interest epoch and bounded capacity/accounting revisions. Root activation/closure and acceptance compare/touch the same applicable epoch. Independently account outstanding work/payload, live dedup, retained native-source replay bindings and terminal receipt metadata. Capacity reservation and proved retirement release use conditional revisions. Never hold this coordination boundary across workflow dispatch or execution. |
| `NativeSenderControl` | One retained control per actual sender execution/scope/incarnation, with immutable tenant/run/test/authority binding; Open or CancellationSealed plus exact cancellation checkpoint/operation proof. The first send checkpoint provisions it. Finalization and callbacks acquire its revision-neutral transactional lock; cancellation seals it under the sender fence without enumerating sources or stealing claims. Retain until all linked source/callback replay is retired. |
| `NativeSendOutcome` | Create-only full source identity/scope/fingerprint → immutable Accepted(receipt), Rejected(safe permanent reason) or Cancelled(authoritative sender cancellation proof), with sender invocation/private wait/version. Acceptance commits with inbox acceptance; rejection/cancellation records no fictitious inbox receipt. Retention follows possible source replay, never producer dedup expiry. |
| `MessageSenderContinuation` | Original source/outcome; exact private wait/generation and callback operation ID; accepted receipt or rejection; pending/accepted/consumed/closed proof. Success completes the send after acceptance; rejection consumes its private wait and faults that invocation at the owning checkpoint. Neither waits for business delivery. |
| `MessagePayloadRetention` | Actual payload location/encoding, confidentiality/disclosure metadata, owed-reference count or equivalent root proof, buffer/delivery/evidence deadlines and deletion proof. Auditable terminal metadata can outlive payload retention. |

Use ordinal exact name/key/ID comparison and length-delimited versioned identity digests. Narrow SQL indexes use bounded hashes/order projections with full canonical equality verification. Persist sanitized reason codes rather than sensitive values in identifiers, URLs, logs or exception text.

## Invariants

- **I1 — Accepted means committed:** acceptance, immutable policy/content/cohort, dedup binding when supplied, capacity reservation and initial Runtime work either all commit or none do. A partial/unavailable interest read never produces an empty/partial accepted cohort.
- **I2 — Historical scope:** a definition belongs only if an authorized declared-name interest existed at acceptance. Membership cannot expand later. Late waits/replacement versions inside that cohort still require current owning authority.
- **I3 — Winner:** each definition delivery transitions from unselected to one exact start-or-wait winner at most once. A retry dispatches that winner only.
- **I4 — One-shot exclusion:** different messages cannot reserve one generation simultaneously. A losing buffered message installs no winner and stays pending; immediate-only instead completes bounded admission reconsideration/unmatched with no later discovery obligation.
- **I5 — Active-run exclusion:** one occupied admission epoch per logical-definition/key, across versions/models/workers. Other start mechanisms do not acquire this lane.
- **I6 — Distinct fences:** transport claim fence, delivery-capability epoch, wait-reservation epoch, bookmark generation and start-admission epoch are separate facts. Renewing/reclaiming transport never grants new semantic selection or releases a key.
- **I7 — Consumption proof:** queue/actor acknowledgement does not establish semantic receipt. Target checkpoints compare the exact selected source capability/reservation and retain target admission/consumption evidence atomically with native/model progression.
- **I8 — Independent windows:** buffer expiry closes new selection, not selected obligations; dedup expiry releases only producer-ID recognition. Neither deletes the other's outstanding proof. Duplicate acknowledgement preserves every original delivery.
- **I9 — Native send identity:** a committed source resolves to its immutable Accepted, Rejected or Cancelled outcome on every retry, without producer ID and beyond dedup expiry. Changed source content conflicts. A rejected/cancelled source cannot accept after policy changes; a genuine new invocation is a new source.
- **I10 — Closed means fenced:** final failure/abandonment closes delayed target admission/consumption durably. Proved consumption cannot become abandonment; uncertain consumption cannot be treated as unconsumed.
- **I11 — Sender cancellation:** cancellation and acceptance serialize through the retained sender control inside their actual transactions. Cancellation-first seals that control and prevents acceptance by every stale source claim; current claim replay derives the source’s immutable Cancelled outcome; acceptance-first preserves the accepted message and recipient obligations. Callback retirement needs authoritative sender cancellation proof. A cancellation request, absence or lost acknowledgement cannot decide the race.

## Transactions and provider participation

| Boundary | Required joint writes/checks |
|---|---|
| **T1 Interest publication** | Prepare material-derived declaration; activate/replace/deactivate its publication root with the actual activation slot/projections and interest epoch. Extend existing activation switch ownership; a swallowed observer notification cannot establish membership. |
| **T2 Active execution interest** | Create active-material root at initial authoritative native/model checkpoint; close at authoritative terminal lifecycle. Old active material remains eligible after unpublish/replacement. Exclude test-run/private roots from production discovery. |
| **T3 Buffered API acceptance** | Validate trusted scope/producer/permissions and durable representability; resolve dedup identity; read all bounded cohort pages against a coherent interest epoch; reserve capacity; insert acceptance + every definition delivery + independent dedup identity + Runtime discovery work. Replay resolves the original committed acceptance. |
| **T4 Immediate-only acceptance** | T3 plus complete acceptance-time candidate selection/reservation for every cohort member, or durable per-definition `Unmatched`. No unselected future-discovery obligation survives. An unavailable authority read refuses before commit; uncertain commit rereads the original selection and never rescans new listeners. |
| **T5 Buffered selection** | Revalidate source/cohort/deadline/current authority; serialize wait-first arbitration; acquire exclusive exact wait reservation or free start admission; CAS pending definition delivery to its immutable winner; retain material/source roots and enqueue ordinary Runtime dispatch work. A stale candidate/reservation loser rolls back without selecting it. |
| **T6 Native target admission/consumption** | Existing execution fence + exact bookmark/activity/execution generation + selected message capability/reservation expectation; atomically record admission/consumption with their actual native checkpoint changes. Validate again at each distinct semantic boundary. Do not accept a caller-authored DTO as source authority. |
| **T7 Model target admission/consumption** | Existing model fence/revision/material incarnation + owner subscription generation + selected capability/reservation; model decision, `RuntimeModelInputReceipt`, message proof and outbox changes share one checkpoint transaction. |
| **T8 Terminal/release** | Native completed/faulted/cancelled transition or model-confirmed terminal settlement records exact target/admission epoch evidence and durable release work. Conditional release cannot clear a successor epoch. Pre-admission refusal also closes every old start capability before release. |
| **T9 Close/reuse wait** | Prove old selected delivery unconsumed; close its target capability; retain closed tombstone; conditionally release matching reservation epoch in the actual target/source boundary. A newer reservation rejects delayed commands from every prior owner/epoch. Unknown outcome retains reservation. |
| **T10 Send checkpoint** | Stage send content/identity and exact private receipt wait, provision the sender control and reserve its retained outcome/continuation capacity in the sender invocation's suspension checkpoint. No external message acceptance occurs during uncommitted activity execution. Fault/reset discards transient staged intent. |
| **T11 Resolve native send** | Validate canonical source/current claim/authority; resolve original immutable outcome first. Inside the owned transaction, lock and reread the retained sender control before new acceptance. Otherwise apply T3/T4 and commit Accepted plus continuation, or record definitive Rejected plus rejection continuation. A cancellation checkpoint seals that same sender control with authoritative cancellation proof. A current claimant derives Cancelled without new acceptance/callback when sealed. Existing Accepted remains immutable; callbacks use the control proof to retire their sender continuation. Temporary/unknown failures retain unresolved source work. Producer dedup does not replace source identity. |
| **T12 Sender outcome** | Resume exact private wait through its owner, guarded by immutable SourceOutcome. Accepted completes with receipt; Rejected consumes the wait and faults that send invocation atomically. Retain callback until consumption or authoritative sender retirement; absence is uncertainty. |
| **T13 Cleanup** | Conditional independent buffer/dedup/audit cleanup plus actual source/execution/material retention checks. Persist closed/released/consumed tombstones before payload or root deletion can remove needed recovery evidence. |

## Interest declarations and snapshot consistency

Extract declarations from immutable runtime material, never from mutable Design records. The candidate initial wire declares a fixed name per receive/start or an explicit finite owner-declared name set; a runtime-chosen name must belong to that set before subscription registration. Unbounded dynamic names do not enroll every message. Business keys remain runtime values.

A root is a real serving publication or retained nonterminal execution. Closing one publication does not close an active execution root or erase an accepted definition delivery. A retired root is not start authority. Each root update and complete cohort capture participates in the applicable interest epoch; use a bounded coherent snapshot/conditional epoch transaction, retrying an invalidated capture before acknowledgement. Finish every page before acceptance. Quota limits bound cohort size so atomic immediate-only selection remains finite; reject excess before consuming a producer ID.

## Authored send integration

Use the invocation-keyed suspension/staging pattern in [`DispatchWorkflow`](../../Essentials/src/Activities/DispatchWorkflow/Runtime/Activities/DispatchWorkflow.cs) and its staging buffer. Extend `WorkflowInvokeActivitySchedulerWorkHandler` to reset/drain typed Message staging on clean suspension and reset on fault/cancellation. The existing required-source contribution can carry a real native send through `IRuntimePostCommitDurableSourceIntentHandler` without adopting Event recipient-cohort semantics.

The callback uses `BookmarkResumeDispatchRequest.ExpectedRecipient` and an authoritative accepted-record guard like [`UserTaskResumeGuard`](../../Essentials/src/Workflows/Runtime/Elsa.Workflows.Runtime/UserTasks/UserTaskResumeGuard.cs). Reuse User Tasks' exact recipient/result reconciliation, not `CreateUserTask.StageAsync` as a precommit acceptance precedent. Acceptance receipt completion does not wait for recipient workflows. Source-binding proof remains after either producer window closes; source retirement/compaction must retain a tombstone sufficient to prevent source replay from accepting anew.

Q4 cancellation participates in the actual cancellation checkpoint, rather than an observer or handler-local token check. Extend the shared `WorkflowCancellationPlanner` and both scheduler Cancel and CancelWorkflow alteration checkpoints with a typed `NativeMessageSenderCancellationPlan`: exact sender/control identity and cancellation checkpoint/operation proof, checked under the sender execution fence. It seals one control, without enumerating retained source history, capturing each source revision or requiring a transport claim. Existing activity cancellation enumeration remains unchanged.

The first send suspension checkpoint provisions the control and reserves one retained native outcome/continuation proof slot per committed send. Capacity refusal occurs before creating the durable source/private wait. Later Accepted, Rejected or Cancelled resolution uses that reserved slot and cannot be stranded because a rejection needs fresh capacity. Retire capacity only with actual source/callback replay-retirement proof.

Finalization opens the owned transaction, acquires a revision-neutral write lock on the control and rereads canonical source/control state there. Preserve an existing immutable SourceOutcome first; Open may create Accepted/Rejected, while CancellationSealed derives Cancelled without accepting or creating a callback. Do not increment sender workflow/control revisions for every finalization: ordinary cancellation must not fail from source-induced revision churn. The existing EF revision-neutral workflow lock is a pattern; the Message control retains proof after workflow deletion. Use one consistent lock order for sender-control, capacity and source/target participants across suspension, cancellation, finalization and callbacks.

Cancellation-first seals the control; a valid claimant later materializes and settles Cancelled while retaining its tombstone. Acceptance-first keeps its message/recipient obligations. Callback admission also reads/locks the control and either consumes the exact private wait or retires continuation responsibility using the cancellation proof. Missing sender state, a requested cancellation and lost acknowledgement remain uncertainty. Before the initial checkpoint, cancellation discards transient staging.

## Physical constraints and retention proofs

- EF record helpers use canonical content, scope/hash/order projections and `Revision` CAS, following existing Runtime schema families. Own the transaction with a clean context; reject ambient/caller-owned transactions where the joint boundary cannot be proved. On conflict/unknown commit, rollback and reread a canonical winner/marker before effects.
- The selected backend exclusively owns source/inbox/checkpoint contracts. Registration rollback snapshots include new participants; context/scope identity checks reject foreign replacements and split providers. No cross-database transaction fallback or process-local lock may stand in for durability.
- Use a shared authoritative provider clock domain for accepted deadlines and boundary comparisons, with reviewed backward-time/skew handling. Store accepted policy/deadlines once. Transport visibility and semantic retention remain separate clocks.
- Retain exact delivery-capability, reservation/admission generation and consumption/closure/release evidence through all possible delayed commands, manual retries, execution deletion and recovery scans. Deletion tombstones must establish retirement; absence never proves it. A transport claim timeout cannot erase any such proof.
- Protected payloads use the real encoding/disclosure/retention boundary. Receipt/history can retain bounded sanitized metadata after payload deletion; disclose expired/unavailable payload state truthfully. A hash is not permission to expose a sensitive key.
- Provider support is evidence-based: native/model, physical/coalescing and every advertised SQLite/PostgreSQL/SQL Server/MySQL topology require real commit-uncertainty/concurrency/restart tests. The in-memory development path is explicitly non-durable. See the acceptance matrix; all qualification remains **NOT RUN**.
