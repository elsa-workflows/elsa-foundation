# Durable messaging acceptance matrix

**Canonical request:** [#3583](https://github.com/elsa-workflows/elsa-foundation/issues/3583)
**Date:** 2026-11-06
**Qualification status:** **NOT RUN**. This is a before-code acceptance plan, not implementation, provider qualification or UX approval evidence.

Owner-selected first-release capabilities remain required. Resolve outstanding product contracts in the [specification](spec.md) before converting their design-dependent assertions into final checks. An unresolved contract, unsupported provider, skipped journey or green fixture must not silently narrow the feature. Source observations are in the [gap inventory](research.md); proposed engineering contracts are separate from accepted requirements.

**Product decision status:** Q1–Q3 are accepted on 5 November 2026: success acknowledges durable acceptance through a stable receipt, with delivery separately observable; a new logical definition introduced after acceptance cannot consume that historical message, while later waits and eligible replacement versions of an already eligible definition retain their opportunity; a ready matching wait takes precedence over a matching published start. Wait arbitration uses matching address/order before payload compatibility, so an incompatible selected winner cannot be bypassed for another recipient. Q4, accepted on 6 November, stops an unaccepted send when sender cancellation wins the durable race and preserves every already accepted message/recipient obligation. Concrete engineering contracts still require review; these decisions are not implementation or executed evidence.

| Operator | Find a message by receipt, name or business key; identify which definition is pending, delivered, expired or failed; follow its chosen run; perform only authorized recovery without replaying successful definitions. | Workflow Definitions/Connections collection composition; User Tasks collection/detail navigation and accepted-but-pending feedback. |
| Restricted reader | Inspect only authorized metadata and delivery outcomes; denied payloads, tenants and recovery actions remain unavailable in both UI and direct API calls. | Current principal/tenant checks and separate runtime payload-resolution authorization. |

Use the existing Studio shell and a domain-owned contribution, following [module UI guidance](../../Studio/docs/module-ui.md), [Slots and Contributions](../../Studio/docs/adr/0001-use-slots-and-contributions-for-studio-extensibility.md) and [Studio UX acceptance](../../docs/contributing/studio-ux-acceptance.md). A new shell, dashboard or manual Studio send console is not necessary to prove these goals. API submission, authored send/receive and operator diagnosis are required journeys.

The proposed collection shows receipt identity, message name, business key, acceptance time, effective buffer expiry and a truthful aggregate such as “2 delivered · 1 pending.” Detail separates acceptance, independent lifetime deadlines, per-definition recipient/progress/history, chosen run links and authorized payload access. Delivery must not imply recipient-run completion or consumption by every definition. Labels and recovery actions remain subject to the reviewed contract.

## Camunda reference notes

Research retrieved on 5 November 2026; current unversioned pages identify themselves as Camunda **8.10** and mark 8.11 unreleased. These are informed references, not an Elsa parity commitment.

- [Messages](https://docs.camunda.io/docs/components/concepts/messages/): name/key subscriptions snapshot values when opened and close with their element/scope. Positive TTL buffers; zero disables buffering; a newly opened subscription takes the earliest matching buffered message. Cardinality is one subscription per BPMN process ID across versions/instances, with independent delivery to different process definitions. Competing subscriptions are explicitly nondeterministic. Optional ID uniqueness checks name/key/ID only while the original remains buffered; an ID may be reused after discard. The synchronous response's preference for a newly created instance key is not a general deterministic start/wait arbitration guarantee.
- [Message events](https://docs.camunda.io/docs/components/modeler/bpmn/message-events/): deployment replaces previous-version start subscriptions; messages published before deployment do not start that process. Active message-started instances block another start for the same nonempty key across versions; buffered messages can start the latest version after completion/termination. Empty keys bypass that exclusion. Catch subscriptions open on activation. Throw events create worker jobs rather than directly correlating engine messages.
- [Publish message API](https://docs.camunda.io/docs/apis-tools/orchestration-cluster-api-rest/specifications/publish-message/): supports buffering, does not wait for correlation, requires `MESSAGE:CREATE` when authorization is enabled and documents backpressure/retry. Publication success must not be presented as recipient completion.
- [Correlate message API](https://docs.camunda.io/docs/apis-tools/orchestration-cluster-api-rest/specifications/correlate-message/): immediate correlation without buffering; returns one instance key even if multiple definitions receive. Documents unmatched `404` and subscription-dependent create/update-instance permission. These response and permission choices are references; Elsa must define its own acceptance/uncertainty contract.

Elsa's owner-selected independent deduplication window after delivery/recipient completion extends beyond Camunda's buffered-ID check. Buffer-by-default configuration, shared API/activity semantics, per-definition operator outcomes and crash-safe selected-recipient recovery require Elsa's own reviewed guarantees. The selected business key corresponds conceptually to correlation key; Camunda 8.10's additional `businessId` field is a separate feature and is not implicitly adopted. Elsa has accepted durable receipt/separate delivery, exclusion of brand-new historical consumers and ready-wait precedence. Engineering contracts for fairness, empty keys, dedup namespace/content conflicts, immediate-only selection, expiry/recovery, terminal release and the actual support declaration still need explicit review.
