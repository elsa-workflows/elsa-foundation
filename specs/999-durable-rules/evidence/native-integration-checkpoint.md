# Native Rules compiler and composite checkpoint

This checkpoint extends the [hosting checkpoint](native-hosting-checkpoint.md). It adds a real registered compiler case and a separate persisted native Sequence/Flowchart case. T027–T032 remain open: these cases do not yet prove the compiler-produced artifact executing through a persisted publication handler, Workbench REST or a package host. Upgrade/rollback acceptance is also open.

## Production corrections discovered by integration

1. The native executable hasher produces `sha256:<digest>`. Rules incorrectly required a raw 64-character digest in both its retained destination and private-state reader. Those boundaries now preserve the external identity exactly under the shared nonempty valid-Unicode/256-UTF-8-byte identifier bound. The prefix participates in the invocation fingerprint and exact native destination comparison. Rules-owned artifact, invocation and stimulus hashes still use strict lowercase hexadecimal SHA-256 validation. The internal validation helper is shared through same-domain internal access, without a new public helper API.
2. The CLR contract for `RunRules` declares a `RuleTerminalResult` result descriptor with no descriptor schema version. Native completion persists that contract descriptor. The delivery inspector incorrectly expected descriptor schema version 1, so a genuinely completed Rules activity could not acknowledge delivery. The inspector now compares the exact CLR descriptor, while retaining full canonical terminal-content comparison, final consumed attempt/receipt checks, contract fingerprint and store-side proof revalidation. The incoming `RunRulesCompletion` trigger descriptor still uses schema version 1; `RuleTerminalResult.ResultSchemaVersion` is separately validated as version 1. Neither version is substituted for the activity result descriptor.

## Evidence boundaries

- `RulesCompiledPublicationTests` uses real SQLite activity/workflow design catalogs, normal CLR assembly scanning and reconciliation, runtime type registration, and the registered workflow compiler plus Rules enrichment. The compiler receives an authored in-memory Sequence containing `RunRules` followed by `WriteLine`. Assertions cover ordered children, literal inputs, canonical Rules artifact bytes/hash, implementation pin and compiler-generated scoped resume target. The catalog scope is explicitly global because the reconciled CLR entries are global. The implementation identity is synthetic. This is not the persisted workflow publish handler or REST authoring path, and this executable has not yet been run through the persisted runtime.
- `RulesPersistedNativeFlowchartTests` independently assembles a Sequence containing a parallel Flowchart with Rules and a waiting Event, followed by a counter activity. It uses real native and Rules SQLite stores, migrations, normal Rules features, registered metadata enrichment, native start dispatch, partition-specific post-commit intent sweeps, the finite evaluator and real terminal delivery/proof/acknowledgement. It verifies the native hasher identity survives harness publication unchanged. Rules completes while the Event remains suspended, the join/final remain incomplete and the parent remains running. Releasing the Event completes the join, following activity and workflow, with the counter exactly one. The implementation identity is synthetic and the graph is prebuilt; harness publication saves executable/source-reference records but bypasses the full compiler/publication handler. Workers are stepped explicitly, so this is durable runtime-composition evidence, not distributed or package-host evidence.
- Focused identity tests prove exact prefix preservation, different fingerprints for stripped versus original identities, exact-address rejection, successful retained completion proof and UTF-8 limits. A descriptor regression obtains the real CLR contract type, accepts its unversioned descriptor, and rejects an invented descriptor version 1. Existing canonical-content mismatch and receipt/attempt tests remain active.

## Review and validation

The integrated tests exposed the two production defects above. Earlier attempts also caught fixture-only issues: missing imports/project path/required arguments, missing Primitives clock and durable paging configuration, tenant/partition mismatch, default-scope sweeps, an omitted Event input, and typed Event provider metadata. These were corrected without bypassing native or design persistence checks. Source review additionally found that harness publication normalizes CLR descriptor consumer keys; the prebuilt graph now uses that normal form before hashing and verifies the stored graph against the retained hash.

Independent read-only review confirmed external-identity ownership and the distinction between activity result, trigger and domain payload schema versions. The compiler fixture review found no false-green issue within its explicitly limited claim. Root reviewed the integrated source and ran all builds and tests serially.

Two isolated removal controls restore the old raw-hash requirement and the old result-descriptor version requirement respectively. The first fails on the real native hash; the second fails the persisted composite at delivery acknowledgement even though the native Rules activity is completed. Each source file is restored byte-for-byte before intact validation. These are focused regression controls; they do not complete T032's REST/package proof-before-acknowledgement requirement.

The restored complete Rules suite passed **269 tests**, and architecture passed **585 tests**, with zero failures/skips. Restore, map generation, generated solution-filter validation and diff checks passed. Generated findings show zero runtime-to-design signals, unlinked catalogs or missing catalogs; generated documentation remains ignored and unstaged. Three bounded review rounds ended clean within this checkpoint scope. Existing package/analyzer and generator-hint warnings remain visible and unsuppressed.

Exact commands, outcomes and log hashes are recorded in the [receipt](native-integration-receipt.json). External effects remain at least once. The next acceptance step is to execute the actual compiler-produced artifact through the persisted native runtime, then cover the remaining cancellation/refusal/unavailability and publication/REST/package cases before closing the native tasks.
