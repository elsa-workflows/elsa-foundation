# Studio acceptance: workflow and activity testing

**Feature records:** [#3588](https://github.com/elsa-workflows/elsa-foundation/issues/3588) and [#3892](https://github.com/elsa-workflows/elsa-foundation/issues/3892).
**Status:** Design acceptance record; no journey or visual acceptance has been executed for this feature.
**Inspected baseline:** `29601557f5a28a885598061fbd48fc2e31007d37`.
**Owner choices:** Test the current explicitly captured candidate after compatibility validation; provide a Studio Tests library with portable export/import. Workflow and selected-activity targets share saved cases, suites, setup, execution and verdict semantics.

## User goal and reference

A workflow author can select an activity occurrence in the designer, supply its required context, execute it without running predecessors or unrelated successors, and turn that setup into a saved asserted case. The author can also create full-workflow cases with multiple events/actions and controlled time, group both target kinds in suites, reopen and revise them, inspect their history and run the same cases from CI. A test engineer can choose a named test-system integration explicitly and distinguish execution behavior from whether assertions passed.

Use [Workflow Definitions](../../Studio/src/essentials/Elsa.Studio.Workflows/Client/src/workflow-editor/pages.tsx) and [Connections](../../Extensions/Connections/studio/Elsa.Studio.Connections/Client/src/ConnectionsPage.tsx) as collection references. Follow [module UI guidance](../../Studio/docs/module-ui.md) and [design tokens](../../Studio/docs/design-tokens.md) for page structure, tables, forms, statuses, notifications and controls. Reuse the existing [workflow setup panel](../../Studio/src/essentials/Elsa.Studio.Workflows/Client/src/workflow-editor/WorkflowTestDrivePanel.tsx), [wait controls](../../Studio/src/essentials/Elsa.Studio.Workflows/Client/src/workflow-editor/WorkflowTestRunControls.tsx), [runtime panel](../../Studio/src/essentials/Elsa.Studio.Workflows/Client/src/workflow-editor/editorPanels.tsx) and [Activity Definition Test Run dialog](../../Studio/src/essentials/Elsa.Studio.Workflows/Client/src/ActivityDefinitionTestRunDialog.tsx) where their behavior fits the common contract. These references do not establish acceptance of the new feature.

## Shared experience

### Entry points and target identity

- Add **Tests** under Workflows using the existing [module registration](../../Studio/src/essentials/Elsa.Studio.Workflows/Client/src/module.tsx). Its library has Cases, Suites and Results views with clear search/filter/count semantics. Create and Import use separate forms or dialogs, preserving the collection's scroll position and focus on return.
- Add a **Tests** section to the [activity inspector](../../Studio/src/essentials/Elsa.Studio.Workflows/Client/src/workflow-editor/InspectorPanel.tsx). An explicitly selected occurrence offers **Test activity** and its related saved cases. It opens the same workbench as the library. The workflow Test Run setup offers the corresponding whole-workflow entry and **Save as test case**.
- Use `selectedActivity` from [WorkflowDesignerPanelContext](../../Studio/src/essentials/Elsa.Studio.Workflows/Client/src/workflow-editor/editorTypes.ts). Its `inspectedActivity` scope-owner fallback is not a selection. With no explicit selection, show “Select an activity to test” and no occurrence run action. An explicitly selected composite remains a legitimate target when supported.
- The workbench header names the definition, activity label and containing scope when applicable. **Current candidate** is the default run source. Capture it explicitly, validate the saved case against it and show whether it is ready, stale or incompatible before execution. Changes after capture require Refresh candidate and another validation; they never alter a running test.
- Changing designer selection, renaming an activity or reopening another workflow does not retarget the open setup or saved case. A removed/incompatible occurrence offers **Rebind target**, which identifies the proposed occurrence and affected setup/assertions before saving a new case revision. Never guess a replacement by label, position or activity type.
- Results retain immutable candidate, case revision and required dependency identities. Show useful labels and revision information first; make exact identifiers, dependency manifest and captured content available through Technical details. Old results remain associated with their original content when the current candidate changes.

### Authoring and execution

Use one workbench for workflow targets, selected occurrences and standalone reusable Activity Definitions. Organize it into Target, Setup, Steps, Assertions and Results sections, keeping the primary action for the active task clear. The first manual run may require only Target and Setup; saving a case does not create a second product or reinterpret the setup.

Setup exposes declared inputs and the supported surrounding context: scoped variables, explicit expression bindings/prior outputs, fixtures and connection selection. Preserve absent, explicit null and value where the contract distinguishes them. Identify missing or unsupported context beside the relevant field before dispatch. A supplied prior output is fixture data, not evidence that its producer ran. No predecessor is executed to discover a missing value.

Dependency setup distinguishes **Controlled** from **Integration**. Controlled mode lists configured substitutes and supported boundaries; an unsupported/unconfigured boundary blocks execution with a reason. Integration mode identifies the chosen test environment and real connections explicitly. A mixed setup identifies each real and substituted dependency. Neither mode silently falls back to real I/O. Fixtures and substitutes are scoped to the test run. Secret values never enter downloadable case files, screenshots or result details; portable files carry references requiring destination mapping.

Steps use the modules' supported events/user actions and time operations with a clear ordered editor. Show the intended wait/target and data, allow reordering deliberately and explain incompatible or missing module support. Controlled time displays its initial instant and explicit advancement; real time is a separate stated configuration. Do not present global clock changes or unsupported time control as a working option. An asynchronous step shows whether it is dispatching, waiting for settlement or settled; delivery acceptance is not settlement.

Assertions cover outputs/outcomes, expected faults or waits, relevant paths and dependency interactions including non-invocation. Results show the expected value, observed value and useful failure location for each assertion. An expected business fault/rejection can pass; a completed execution can fail its assertions. Observed values may be offered as draft assertions, but the author must choose them before they become expectations.

Manual exploration with no assertions displays **No verdict** alongside the actual execution state. It never displays Passed merely because dispatch or execution completed. **Save as test case** preserves the target and setup, then makes the absence of assertions clear. A saved asserted run that cannot establish the required evidence is Incomplete; missing assertions are not silently invented.

Save as case also offers the supported manual event/action deliveries and time advances in observed order for author confirmation. Translate runtime wait identities to stable model-owned authored selectors; ambiguous translation requires an explicit selection. Qualify a waiting selected composite → manual resume → save steps/assertions → reload → automatic headless replay. Copying old runtime wait IDs or omitting the actions that produced the asserted result is invalid.

Pending/invalid unapplied code-editor JSON blocks capture until explicit Apply or Reset, without losing the buffer. With autosave disabled, change an applied configured input, test it and read the stored business draft: the result must use the unsaved new value while the stored draft remains unchanged. This falsifies persisted-draft fallback and hidden saves.

The Results view separates Execution status from Test verdict. Preserve Passed, Failed, Skipped, Cancelled, Unavailable and Incomplete with their distinct reasons, plus No verdict for unasserted exploration. A skipped member remains visible in suite totals and machine reports. An unsupported target is Unavailable, not Skipped or Passed. Timeout, expiry, interrupted settlement and lost evidence cannot produce a passing verdict. Cancellation requested remains pending until acknowledged; cleanup failure or unknown terminal state is visible. Report export and CI exit status use the same verdicts.

### Saving, suites and portability

Save returns a durable case revision. Reopen restores the complete setup, ordered steps and assertions. Editing creates the next revision; running captures one exact revision. Unsaved edits and conflicts remain visible, and abandoning an edit returns focus without changing the saved case.

Suites name exact case revisions for a run and may mix workflow and activity targets. Each member has its own result; suite counts expose all verdicts. A later case edit does not rewrite a prior suite result. Library filtering and opening results preserve the author's place and use real server pagination/counts where applicable.

Export downloads a versioned, inspectable case or suite package. Import validates it before saving, shows target/dependency mappings and unresolved references, and requires a deliberate identity/collision decision. Import never starts execution or publishes a definition. The packaged headless runner consumes that same saved/exported case model and accepts the explicit candidate and required test-system mappings without opening Studio. Result files identify the same candidate, case revision and dependencies as Studio.

### Permissions and capability states

Backend capabilities and permissions determine available actions. Reading cases/results, changing cases/suites and running/cancelling have distinct requirements defined by the common testing contract. Denied access, unavailable capability, empty data and request failure have different UI states. Direct URLs and API calls enforce the same boundary; hiding an action is not authorization.

The current [publishing permission catalog](../../Essentials/src/Workflows/Publishing/Api/Authorization/WorkflowPublishingPermissions.cs) requires `workflows/publishing:manage` for ordinary workflow/activity Test Run endpoints, including their reads. [Runtime evidence permissions](../../Essentials/src/Workflows/Runtime/Api/Authorization/WorkflowRuntimePermissions.cs) remain applicable when opening runtime details. Do not imply that publishing read access alone authorizes existing test operations. A new testing permission must be cataloged and enforced by its owner rather than weakening existing endpoints implicitly.

A pinned/read-only designer view does not itself decide testing authority. Keep test/history controls outside a fieldset disabled solely for draft editing; derive their actions from test permissions and target capabilities. A reader may inspect permitted history without editing the workflow. Loss of session, tenant or backend identity clears protected results and prevents actions using the former identity. Reauthentication requires fresh validation of the current scope.

## Target support matrix

This table defines required user-visible behavior, not evidence that a target is already implemented. The implementation's server capability response is authoritative for an installed host; unavailable rows remain visible and explain recovery.

| Target | Expected semantics | Unavailable or invalid setup behavior |
|---|---|---|
| Whole native workflow | Execute the captured candidate using its normal root/start semantics and supported test steps. | Identify invalid candidate/start, missing context or unsupported boundary; no dispatch. |
| Selected native leaf | Execute that exact configured occurrence with explicit supplied context. Predecessors, siblings and unrelated successor branches do not run. | Name the missing context or unsupported execution boundary; never replace the occurrence with a newly constructed standalone activity. |
| Selected native composite | Execute its normal owned work, routing and waits through its model; retain the composite as the result target. | Explain unsupported model/context behavior rather than flattening children or bypassing its semantics. |
| Native leaf/composite in nested scopes | Retain exact occurrence identity and supported ancestor variable/scope context. Supply required context explicitly. | Show the relevant scope and missing/unsupported requirement; never run the containing workflow to obtain it. |
| Reusable Activity Definition occurrence | Execute its configured call-site occurrence against the exact required reusable dependency identity, including configured inputs and normal owned work. | Identify missing/incompatible dependency or context. The standalone definition test is not a substitute for the call-site test. |
| Standalone reusable Activity Definition | Use the same case/setup/assertion/result model with its exact definition revision and contract. | Show contract/dependency incompatibility and preserve the previous result. |
| BPMN-bound target | Discover and execute only through BPMN model-owned targeting, routing and scope semantics. | State which model boundary cannot support the requested isolated target. Never invoke a generic native activity path to bypass BPMN. |
| Extension-owned activity/event/action/time boundary | Discover its declared support and use registered model/step/dependency behavior shared with headless execution. | Name the missing, ambiguous or incompatible module/contract. No browser-click substitute or unsafe generic injection. |
| Removed, replaced or incompatible target | Preserve the saved target and historical results; offer deliberate rebind and a new case revision. | Show stale/incompatible identity before any execution; no automatic match by name/type/location. |

## Observable states

| Surface | States that must remain distinguishable |
|---|---|
| Tests library | Loading; empty with permitted create/import; populated; filtered no matches; paged results; refresh failure with retained stale rows; initial failure with Retry; denied; missing capability. |
| Designer entry | No explicit selection; supported occurrence; supported composite; nested occurrence; reusable occurrence; unavailable model/module; read-only design with permitted testing; denied testing. |
| Candidate and case | Capturing/validating; ready; current candidate changed; missing/removed target; incompatible dependency/context; deliberate rebind; unsaved edit; saved revision; concurrent edit conflict. |
| Setup and steps | Valid absent/null/value; field validation; missing scope/prior output; controlled substitute ready/missing; explicit real test system; unsupported time/event/action; fixture validation; dirty form cancellation and focus restoration. |
| Run and result | Dispatching; accepted; running; active wait; step settlement; expected fault/wait; passed; failed; skipped; unavailable; incomplete; no verdict; cancellation requested/confirmed; timeout; expiry; interruption; cleanup failure; lost observation and reconnect. |
| History and portability | Empty history; multiple immutable results; prior candidate/case revision; export pending/success/failure; import validation/mapping/collision/error/success; inaccessible/expired evidence. |
| Access and layout | Reader, author and runner rights; lost session/tenant/backend change; keyboard operation/focus; desktop/narrow; light/dark; long labels, identifiers and assertion values. |

Use normal labels and primary/secondary action hierarchy, wrap useful values and expose technical identifiers through disclosures. Narrow layouts must keep target, verdict, failure reason and run/cancel action usable without document-level horizontal scrolling. New dialogs trap focus, support Escape when safe and return focus to their opener. Preserve entered data on recoverable validation/transport failure.

## Smallest composed journeys

All journeys below are required. Group variants within a journey to avoid duplicate fixtures; do not replace normal host behavior with intercepted API responses. Use owned disposable composed hosts and harmless owned test systems. Never use production credentials, publish production starts or mutate existing production instances.

|---|---|---|

Save chosen assertions as a case, leave/reload, reopen, edit/save and rerun against the current captured candidate. The explicit real integration in UX-04 uses a test-owned endpoint and ordinary real transport, not an intercepted Studio response. The matching ordinary execution in UX-06 belongs to the disposable acceptance host; it is not a production instance. Record that evidence classification explicitly. A fixture DOM test alone does not qualify these journeys.

## Execution and independent acceptance

Follow [Studio UX acceptance](../../docs/contributing/studio-ux-acceptance.md). Extend the existing [acceptance journeys](../../Studio/tests/acceptance/journeys.spec.ts) and [owned-host runner](../../tools/ux-acceptance/run.py) with the feature's journey/capture inventory; its current fixed inventory must not silently omit these tests. The [acceptance configuration](../../Studio/tests/acceptance/playwright.config.ts) supplies desktop/narrow and light/dark projects, trace retention and zero retries. Use focused backend/integration tests for lifecycle, isolation, dependency and report semantics alongside real UI journeys. Honor build slots and run only the projects needed by the change.

Final evidence must identify the committed source SHA and PR head, contain successful execution of every intended journey/variant, and retain downloadable screenshots, accessibility snapshots, traces, runtime/report records and headless artifacts. Failed, skipped, unavailable or not-run proof remains visible; a deliberately failing regression is a successful control only when the journey explicitly verifies its expected failed verdict. Never use that distinction to hide an unintended failure.

An independent reviewer must open the current-head screenshots and inspect the complete affected experience against the references, including save/reopen/rebind transitions, verdict clarity, primary actions, spacing, keyboard/focus, narrow layouts and recovery. Supply the running owned host when recorded evidence cannot answer an interaction. Record the existing UX acceptance receipt on the PR with Passed, Failed or Incomplete, reviewed/tested SHAs, observed states, downloadable Actions artifact links, reviewer identity, findings/retests and any unverified states. An author's machine report is not independent visual acceptance. Merge and resulting-main qualification remain delivery gates outside this design record.
