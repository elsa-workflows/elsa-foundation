## Selected occurrence and surrounding context

[`WorkflowStartSchedulerWorkHandler`](../../Essentials/src/Workflows/Runtime/Elsa.Workflows.Runtime/Services/WorkHandlers/WorkflowStartSchedulerWorkHandler.cs) unconditionally selects `executable.RootActivity` for a normal workflow start. [`WorkflowExecutionStartDispatchRequest.TriggerNodeId`](../../Essentials/src/Workflows/Runtime/Core/Models/WorkflowExecutionStartDispatch.cs) is the reserved matched-trigger channel, propagated to structural activities for legitimate start routing. It is not a supported general selected-node start API. [`IStructuralStartEntryProvider`](../../Essentials/src/Workflows/Runtime/Core/Contracts/IStructuralStartEntryProvider.cs) validates legal composite start paths, rather than permitting arbitrary skips.

The reviewed design selects an explicit validated test-only admission/termination boundary in the normal runtime while retaining the full captured artifact. The bounded probe below supports its primitive feasibility. Preserve exact candidate/target identity, normal binding/composite work and dependency identity while excluding surrounding graph execution. A derived harness was considered and rejected for this design: copying the node and replacing bindings with literals would lose the configured occurrence's semantics, and a source mapping alone would not restore its lexical/capture ownership.

[`RuntimeActivityInputSnapshotMaterializer`](../../Essentials/src/Workflows/Runtime/Elsa.Workflows.Runtime/Services/Values/RuntimeActivityInputSnapshotMaterializer.cs) materializes bindings using committed durable values, invocation ancestry and causal activity history. [`RuntimeContainerScopeService`](../../Essentials/src/Workflows/Runtime/Elsa.Workflows.Runtime/Services/Values/RuntimeContainerScopeService.cs) requires the canonical root variable frame, traverses actual parent invocations, observes lexical shadowing/iteration frames and respects closed reusable boundaries. [`RuntimeInputBindingResolutionContext`](../../Essentials/src/Workflows/Runtime/Core/Models/RuntimeInputBindingResolutionContext.cs) distinguishes workflow members, scope-addressed variables, visible expression variables, causal history and executable contracts. Moving a nested node to a root does not recreate those facts.

An important control is required: [`CausalActivityResultResolver`](../../Essentials/src/Workflows/Runtime/Elsa.Workflows.Runtime/Services/Values/CausalActivityResultResolver.cs) throws unavailable for absent required producers, but returns no result for an optional producer (`IsOptional`). [`RuntimeInputBindingResolver.ResolveActivityResult`](../../Essentials/src/Workflows/Runtime/Elsa.Workflows.Runtime/Resolvers/RuntimeInputBindingResolver.cs) then materializes typed explicit-null for that optional absence. Missing workflow request/variable bindings also throw. Test setup must distinguish an explicitly supplied null fixture from a missing prior-output fixture, including optional production bindings, before execution. Normal runtime faults alone do not enforce the stricter explicit-test-context requirement. Preserve ordinary production optional/null/causal semantics.

Fixture declarations must carry scope and producer/member identity, not only a flattened display name. Inputs, expression parameters, previous outputs, connections and fixture effects remain distinct setup concepts. Dynamic expressions and third-party consumers require declared capabilities: static scanning alone cannot prove every possible dependency or side effect. A missing supported context should produce a structured unavailable reason before admission; unexpected runtime dependencies must fail closed without real-I/O fallback.

## Controlled time and effects

[`Delay`](../../Essentials/src/Activities/Scheduling/Activities/Delay.cs) computes deadlines using constructor-injected `TimeProvider`, persists a timer through `IDurableTimerScheduler` and suspends through its typed registration. [`DurableTimerPumpTask`](../../Essentials/src/Workflows/Runtime/Scheduling/DurableTimerPumpTask.cs) claims and fires timers against the host clock. [`BpmnDurationTimer`](../../Essentials/src/Activities/Bpmn/Elsa.Activities.Bpmn/Internal/BpmnDurationTimer.cs) has a separate model-owned durable source/delivery path. [`IRuntimeActivityExecutionContext`](../../Essentials/src/Workflows/Runtime/Core/Contracts/IRuntimeActivityExecutionContext.cs) also exposes delayed child scheduling through post-commit outbox availability. A test clock that controls only Delay is incomplete for scenarios that use other admitted time boundaries.

The same host `TimeProvider` controls leases, outbox claim validity, test expiry and infrastructure deadlines. Controlled business time must not replace the global clock or advance those infrastructure lifetimes. Scope retention, wall timeout and cancellation remain wall-clock concerns. A per-test business clock, owned timer delivery and module-owned time capability need proof across asynchronous operation scopes, child dispatch and restart. An unsupported time boundary must be reported explicitly; no silent real-time waiting.

Expression behavior already has deliberate purity rules. [`JintPortableJavaScriptEvaluator`](../../Essentials/src/Expressions/JavaScript/Jint/Services/JintPortableJavaScriptEvaluator.cs) strips ambient `Date`, `Temporal`, `Intl`, random and other ambient capabilities in the binding-pure profile. [`PortableLiquidExpressionHandler`](../../Essentials/src/Expressions/Liquid/Services/PortableLiquidExpressionHandler.cs) supplies fixed epoch/UTC and rejects time/time-zone filters. Do not claim JavaScript/Liquid wall time is a free supported test clock extension or relax expression purity as a testing shortcut. Supported time values should cross declared expression parameters/capabilities.

[`SendHttpRequest`](../../Essentials/src/Activities/Http/Activities/SendHttpRequest.cs) uses a named `IHttpClientFactory` client and `IHttpConnectionApplicator`; these are practical module boundaries for substitute responses, invocation ledgers and explicit test-system connections. They do not cover arbitrary scripts, file/process access, database clients or third-party I/O. An explicit real integration profile must capture chosen test-system identity and admitted effect capability without exporting credentials. Configured substitutes must retain invocation order/count/argument matching and unexpected-call evidence, including proof of non-invocation after settlement.

[`ClrActivityActivator`](../../Essentials/src/Activities/Primitives/Elsa.Activities.Primitives/Activation/ClrActivityActivator.cs) creates a fresh partition-bound child DI scope for each attempt using `ActivatorUtilities`. Changing a parent request's service provider does not by itself prove substitutions reach that child scope, replay, resumed work or detached dispatch. A legitimate scoped test context/effect provider must be propagated deliberately and concurrency-tested; process-global mutable overrides are unsuitable.

## Saved cases, current candidate and reports

[`InMemoryWorkflowTestRunStore`](../../Essentials/src/Workflows/Publishing/Api/Services/InMemoryWorkflowTestRunStore.cs) holds transient run/draft records and lazily expires them using wall time. Durable activity draft receipts are operation receipts, not saved cases or historical assertion reports. No common durable case/suite library, revision model, regression verdict/report model or packaged scenario runner was established by this research. These need actual implementation and Studio/headless equivalence acceptance.

The owner's current-candidate choice means running an existing case against the deliberately selected current captured content after validation, not silently pinning every future rerun to the original candidate. Every result still records exact candidate content, exact case revision, target identity and required dependency/configuration identities. Deleted/incompatible targets require explicit rebinding; ordinal position or display-name matching must not retarget them. Content-addressed executable identity and source reference are separate facts; retain enough captured authoring/source information to validate occurrence identity, inspect the tested setup and diagnose later changes. Export/import must preserve supported versioned case semantics and report unavailable module/fixture/test-system requirements, while keeping secrets external.

The common runner should expose execution progress separately from assertions and final verdict. Expected fault/wait/business rejection can pass; completed execution can fail. Dispatch acceptance, empty assertion lists, missing evidence, interrupted runs and cleanup still owed cannot become passed by aggregation. Machine-readable output and process exit status must preserve failed, skipped, cancelled, unavailable and incomplete states. A headless host invokes the same backend runner/contracts as Studio, without browser click automation or a second engine.

## Bounded runtime spikes before implementation commitments

Each spike should produce a small executable witness using owned temporary host/store material, a concrete supported/unavailable matrix and a proposed contract diff. Witnesses prove only their named cases. None authorizes production changes or reduces agreed acceptance.

1. **Selected native entry and completion.** Exercise one nested leaf and one selected composite from an exact captured candidate using the normal scheduler/activation/checkpoint path. Instrument predecessors, sibling branches and successors; none outside the selected subtree may run. Demonstrate selected composite owned work and normal fault/wait behavior. Compare a test-start seam with a source-mapped harness and select the smaller correct contract; reject either if it needs an alternate interpreter.
2. **Explicit surrounding context.** Exercise root/nested shadowed variables, a loop iteration value, workflow request, pure expression, prior output projection and a closed reusable boundary. Demonstrate explicit null versus missing output, wrong producer/scope/type, unavailable external value and stale target. No fixture may create fabricated predecessor success. Produce exact preflight diagnostics and identify which dynamic/module contexts require a contribution.
3. **Business clock versus wall lifetime.** Run a Delay plus supported follow-up event, advance virtual time and prove no wall wait. Concurrently observe an ordinary execution and another controlled case: neither clock/timer may change. Exercise delayed child work and model timers separately; verify timeout, lease, scope expiry and cancellation still use wall lifetime. Document each unsupported boundary visibly.
4. **Effects and explicit real integration.** Run the same HTTP target with a configured substitute and against an owned local test service through an explicit integration setup. Retain request/response/connection identity and interaction counts; inject an unexpected/missing substitute and prove no outbound fallback. Include non-invocation after asynchronous settlement, concurrent cases and resumed activity attempts.
5. **Wait selection, retry and settlement.** Save a scenario with two same-name waits, stable target/step selection and repeated delivery ID. Prove exact-one wait delivery, retry convergence after consumption, delivery pending versus committed consumption and bounded wait-for-quiescence. Include a fault with intended pass assertions and a completed run with intentionally failing assertions.
6. **Cancellation and lifetime cleanup.** Cancel before admission, during a wait and during asynchronous/detached work; race another step and expiry. Prove admission fences, actual root terminal status, downstream cleanup responsibility and eventual settlement. Preserve cancelled/interrupted/incomplete evidence and test missing cleanup capability rather than returning early success.
7. **BPMN model ownership.** Qualify native process composite and bound task separately from direct human, native-service, duration-timer, native-event and claims profiles. Include `RunBpmn` crossing and at least one unsupported target reason. Demonstrate exact model pin/incarnation, model-owned actions, test-scope propagation, model/native ingress exclusion and cleanup. Do not weaken physical model/outbox proof to make the witness pass.
8. **Durability and library portability.** Persist/save/reopen/edit/rerun one activity and one workflow case/suite; restart the owned host during an accepted run. Import an exported case into a separate owned store and validate missing modules/fixtures/test-system references, conflicting revisions and deliberate rebinding. Preserve original history and do not expose secrets.
9. **One execution contract in Studio and CI.** Execute identical captured candidate/case revisions through backend API and packaged headless path, then compare verdict/assertion/evidence identities. Include deliberate regression, unavailable capability, skipped/cancelled/incomplete controls and meaningful exit statuses. Composed Studio save/run/reload, visual inspection and independent UX acceptance remain separate required proof.

Post-spike design must retain the complete requested critical path: manual selected occurrence testing and save-as-case; workflow/activity cases and suites; assertions, fixtures, supported actions/time/effects; history and import/export; a shared packaged headless runner; legitimate extension points; composed-host and CI evidence; review/merge and resulting-main qualification. A partial witness or first milestone is not delivery of both feature records.

## Executed research probe: parentless native scheduling and capture ownership

On 5 November, an owned external probe referenced the normal current-source activity execution harness and Sequence projects at `29601557f5a28a885598061fbd48fc2e31007d37`. Source/report/output are retained locally in `/private/tmp/elsa-testing-1215-runtime-probe-20261105/{Program.cs,README.md,result.json}`; these ephemeral paths are research reproducibility pointers, not shared delivery evidence. Final commands were:

```sh
dotnet build /private/tmp/elsa-testing-1215-runtime-probe-20261105/RuntimeProbe.csproj --no-restore -m:1 --verbosity quiet
dotnet /private/tmp/elsa-testing-1215-runtime-probe-20261105/bin/Debug/net10.0/RuntimeProbe.dll
```

Both exited 0; the focused build reported three existing HTTP package-pruning warnings and no errors. The probe used owned in-memory stores, a hand-built full runtime artifact with a Sequence and three children, and a typed literal Echo activity. Selected execution used a normal WorkflowStarted checkpoint followed by an explicit ScheduleActivity mailbox command; no activity ancestor/predecessor state was seeded and no alternate interpreter or production source change was introduced.

| Control | Observed result |
|---|---|
| Ordinary full graph | Completed; container, predecessor, selected and successor executed; selected returned 42. |
| Parentless selected literal primitive | Completed; only selected executed and returned 42; original container root/all four nodes and the complete serialized stored artifact remained unchanged; TestRun/scope identity survived. |
| Ordinary full graph with configured closed graph capture | Completed; selected capture succeeded with its enclosing closed-boundary invocation present. |
| Same configured capture with only selected executing | Faulted with the precise missing-nearest-closed-scope-owner diagnostic; only selected executed; complete stored artifact unchanged. |

This supports feasibility of the ordinary parentless scheduling/completion primitive and establishes a concrete capture-ownership gap: a read/input overlay alone cannot preserve this configured nested capture. The closed Sequence is a runtime fixture, not a compiler-generated reusable definition. The probe does not implement or qualify supported test-start admission, caller authorization, candidate compiler/manifest capture, lexical/prior-output fixtures, actual reusable publication, time/effects, persistence/restart, cancellation, Studio or packaged CI. It does not fulfill the nine research obligations above. Initial probe setup failures (macOS `/tmp` symlink path resolution, local compile/type-registration mistakes) were corrected locally and are described in its README; none was treated as a product defect. Machine load was high, so no timing conclusion is drawn.
