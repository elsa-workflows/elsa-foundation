## Architecture decision still required

OD16 chooses normal workflow/activity authoring and publication ownership. It does not choose the internal interpreter/hosting mechanism.

Compare a native composite implementation, an internal model-hosting fit and a simpler sufficient alternative against the same acceptance matrix. Prefer the smallest fit that supports the accepted behavior. Reuse existing activity, scheduler, delivery, identity, correlation, publication and persistence authorities; identify genuinely StateMachine-owned semantic state separately.

Before freezing placement, propose and qualify a bounded witness:

1. Select a transition whose action durably waits.
2. Admit a new machine-addressed event under an explicit bound and distinguish admission from evaluation.
3. Restart an owned host/store and recover the selected phase plus retained input.
4. Finish selected work, evaluate the retained event under the declared order and retain its handled/unhandled outcome.
5. Deliver an obsolete timer/task completion and prove it cannot act on a new state visit.
6. Identify the exact existing contracts used and any reviewed shared extension required. Do not substitute a competing scheduler or independently acknowledged delivery authority to make the witness pass.

The witness has not been implemented or executed. Its technical plan and any architecture-affecting changes require the applicable agreement first.

### P2 — Complete selection and phase rules

The proposed initial profile uses one explicit destination per transition, or no destination for an action without exit. Simultaneous regional reactions use compatible transitions, not a new multi-target/fork syntax. Stable authored identities and explicit transition order remain separate from diagram layout.

1. Evaluate candidates against one committed configuration and the normal visible-value context. Work from active children toward ancestor fallbacks and retain the first eligible same-source rule in authored order. If an eligible descendant handles this input, exclude its matching ancestor fallback independently of exit-set overlap, including when both reactions act without exit. A false child condition permits fallback; a guard error is a fault, not false eligibility. It must retain enough selection/input context for supported recovery and must not silently consume the input as unhandled.
2. Compute proposed exit/entry boundaries before selecting a compatible set from candidates left after hierarchy fallback exclusion. Candidates conflict if their exit sets overlap, or one would exit the source visit on which another reaction depends. The latter covers an action without exit competing with another region's whole-container exit. Visit remaining candidates in explicit authored order, retaining a candidate only when compatible with every retained candidate. Do not resurrect an excluded ancestor fallback or reconsider a later same-source rule because its first eligible candidate lost an unrelated-region conflict. Propose one explicit total transition order, filtered per source, rather than a new implicit region/layout priority. Its serialized representation and validation still need design.
3. For ordinary transitions between separate descendants, retain the shared containing state and exit the active configuration below it that the transition replaces. Explicit self-re-entry exits the source and its active descendants. A compound-parent preserving transition keeps that parent visit but replaces its active descendants; a re-entering one replaces the parent visit too. A parallel-parent transition to a descendant follows OD49. Direct cross-region edges remain invalid. Enter the explicit destination path, then recursively enter required initial children and all regions, using explicit targets where present. This proposed boundary algorithm needs hierarchy/region fixtures before acceptance.
4. Persist the selected set and applicable phases before executing their authored work. Child exits precede parent exits, all selected exits precede actions, actions precede entries, and parent entries precede child entries. Independent same-phase work may progress while a sibling waits. Record individual work completion so normal retry does not repeat completed work. A later business input cannot change the selected set halfway through execution.
5. A valid input is evaluated once for its selected set, not replayed after a state change. Proposed disposition for a completed losing activity trigger is to consume that completion and re-arm only its own trigger after the selected work settles if the same source visit remains active; never queue it to trigger a later state visit. False-guard and successful action-without-exit rearming retain their accepted rules. Repeated composite work can repeat effects.
6. After a reaction, exhaust automatic transitions, then process still-applicable completion opportunities, rechecking automatic paths after each reaction. Completion opportunities follow OD48 and are consumed durably even when ineligible. Discard an opportunity whose owning visit ended; do not retarget it. The exact identity and committed consumption representation remain an integration item.
7. Propose a configured positive progress bound shared by automatic/completion progress and immediately completing rearm cycles. Carry its causal scope through new work IDs, durable phases and restart, so fresh scheduler work cannot reset the protection. A genuine new external cause can begin another bounded progression only when the machine is allowed to evaluate it; queued arrivals do not clear a blocking incident. The concrete scope/reset rule, limit, diagnostic and supported normal recovery actions must be specified and tested before approval.

State-visit values use existing variable-frame/binding/secret policies. This proposal does not extend a closed frame's lifetime or let transition work read disposed locals by reference. The implementation design must show the normal scope/frame ownership and permitted captured outputs for entry, exit, trigger and action work; a semantic visit record alone does not prove ordinary activity bindings.

### P3 — Concrete admission and recovery contract to prove

Propose the following policies; the configuration owners, concrete limits and representations remain part of M0 agreement:

- Count accepted, unsettled business inputs, including selected/in-flight input, against pending capacity C. Check retained identity before full/terminal rejection so a valid duplicate can return its receipt without another admission. Rejected attempts reserve no accepted-event identity or position; a later retry can attempt admission again.
- Keep accepted unsettled identities and payloads until final disposition. They cannot expire because phase work or recovery waits longer than a receipt window. Propose a settled-receipt retention window R beginning at committed final disposition. A bounded receipt budget counts both unsettled reservations and retained settled receipts: admission reserves that slot together with pending capacity, settling releases pending capacity but keeps the receipt slot until permitted expiry. Do not evict promised receipts to admit another event; refuse new distinct admission when either budget is exhausted. Capture the effective retention policy so configuration changes cannot shorten an already promised window. C/R/budget are named configuration obligations, not invented production defaults.
- Compare logical event contents through the existing runtime serialization/fingerprinting authority, including fields that affect eligibility and excluding transport-only retry metadata. Name the exact authority or propose a reviewed extension; do not invent local JSON equivalence. Retained same-ID/same-content retries return the existing admission order and current outcome; conflicting content is rejected. Outside the declared retained guarantee, no deduplication proof is promised; unsettled accepted events are never in that expired category.
- Report accepted only after durable admission is established, including any required flush in a coalescing mode. Transport enqueue, staged state and an in-memory response are not sufficient evidence. A definite pre-commit refusal is not accepted. An ambiguous commit result must remain unknown until the same identity is resolved through authoritative retained state; it must not be mislabeled rejected or blindly admitted again. A host unable to provide durable acceptance must expose that unavailability.
- Allocate admission order, capacity and receipt/state change atomically under existing execution authority. Pending phases and recovery may admit inputs without evaluating them. Resuming/retrying the failed child keeps the selected set, completed phases and sibling results; it does not dequeue/select the original input again.
- When invocation completion/cancellation wins before selection, apply OD37. When cancellation interrupts already-selected work, record an interrupted disposition with actual phase/effect evidence, not an unselected not-processed or successful handled outcome. Final selection/phase completion and subsequent internal progress need separate causal evidence so an automatic-cycle incident cannot make already-performed input effects disappear.
- Retention/deduplication is admission evidence, not exactly-once participant effects. Current-subject authorization, tenant/partition scope, value withholding and inspection permissions remain authoritative for admission, retry and receipt access.

Expose valid state/region/transition creation and mutation through keyboard-accessible outline/inspector actions; raw serialization is not the semantic editing path for supported content. Keep read-only/source-owned content non-mutating, preserve unsupported content, and show actionable validation without silently rewriting it. View-state storage follows its existing owner.

Use the normal execution view and exact pinned version. Link semantic phase/selection facts to ordinary activity occurrences and incidents. Show queued/awaiting-recovery separately from unhandled, interrupted, stale and terminal-not-processed outcomes; do not infer causal order solely from timestamps. Preserve current content while replacement evidence loads, with explicit unavailable/withheld states under normal policies. Actual narrow-width, keyboard, root/nested, save/reload and read-only journeys remain required qualification, not a design mockup pass.

### P5 — Proposed first saga witness topology

Use one inline authored definition, with an outer native compensation scope retaining its journal while a nested control Flowchart runs the lifecycle machine. The first witness deliberately creates no external participant effects inside that control subtree.

| Outer scope step | Forward work | Compensation |
|---|---|---|
| Reserve A | Controlled external participant reservation | Release A with its own occurrence/result/operation key |
| Reserve B | Another controlled reservation | Release B with its own occurrence/result/operation key |
| Lifecycle control | Flowchart containing StateMachine; approved final routes to Confirm, withdrawal/deadline final routes to Compensate | Explicit no-effect handler for this control-only step, proposed as an ordinary empty Sequence |

The [Sequence source](https://github.com/elsa-workflows/elsa-foundation/blob/9eaed8b3302f7cdaaa8366315adfbc37b181d92a/Essentials/src/Activities/Sequence/Activities/Sequence.cs) completes when it has no child. That supports the proposed no-effect handler shape, but its complete publication/runtime composition still needs a witness. The handler is explicit because Compensate stops the running control step and native compensation treats that started step as uncertain. This is not an exception to uncertainty rules, nor a handler to reuse if participant effects are later added inside that subtree.

On the positive path, Confirm keeps the reservations and the scope completes normally. On withdrawal/deadline, the machine first completes through its ordinary mapped outcome; the Flowchart then explicitly requests compensation. The existing scope owns the control-step disposition and releases B then A. This avoids requiring a state-local completed scope to retain a global journal or requiring Compensate to cancel a still-running StateMachine in the initial witness.

Prove restart while the machine waits after several state changes, then explicit recovery, handler retry/intervention and restart during recovery. Also cancel the workflow while the machine waits and prove that no compensation starts. Keep reusable-activity boundary refusal and actual fault visibility explicit: an internal StateMachine phase fault that awaits normal recovery must not be assumed to have reached the outer scope. Scopes inside per-state work with later hand-over, participant effects inside the machine, and cross-reusable-boundary recovery are not proved by this narrow topology. The exact topology remains proposed until M0 agreement.

### Parent-to-descendant modes are chosen; full boundaries remain open

The [SCXML transition reference](https://www.w3.org/TR/scxml/#transition) distinguishes whether a transition targeting a descendant exits its source state. OD41 explicitly chooses both parent-visit preservation and re-entry for a compound parent with one active child targeting a descendant, extending OD15's earlier same-state distinction. OD49 initially requires explicit whole-parent re-entry for parallel-parent-to-descendant transitions, following the target in its region and initial states in others. These choices do not select an Elsa schema, default or implementation. Full boundary calculation, validation and source/Studio proof remain open, and OD39 still excludes direct cross-region edges initially.

### Concurrent durable activity work is an explicit adaptation

The [SCXML parallel-state reference](https://www.w3.org/TR/scxml/#parallel) describes simultaneously active regions with defined serial processing of executable content. OD28 deliberately allows independent ordinary Elsa activity work to progress concurrently within each phase, retaining hierarchy dependencies and selected-set phase barriers. This is an adaptation for the accepted durable-activity composition model, not SCXML execution conformance. Qualification must cover concurrent work, existing shared-value policies and the absence of a guaranteed independent-branch completion order rather than borrowing the reference's serial-processing assumptions.

### Automatic-cycle protection is not proved by drain limits

OD19 requires automatic progress before queued business-event evaluation and protection against an indefinitely running automatic cycle. The existing [drain options](https://github.com/elsa-workflows/elsa-foundation/blob/9eaed8b3302f7cdaaa8366315adfbc37b181d92a/Essentials/src/Workflows/Runtime/Core/Models/WorkflowDrainOrchestratorOptions.cs) and [drain orchestrator](https://github.com/elsa-workflows/elsa-foundation/blob/9eaed8b3302f7cdaaa8366315adfbc37b181d92a/Essentials/src/Workflows/Runtime/Elsa.Workflows.Runtime/Services/Scheduler/WorkflowDrainOrchestrator.cs) bound generic execution for their own purposes: the no-progress count is reset by newly dispatched work IDs, the total-cycle limit is optional, and each drain creates its own cycle budget.

Consequently, those source counters alone do not prove a semantic bound for a StateMachine automatic cycle that keeps producing work or spans durable continuations/restarts. The M0 plan must identify the protection boundary, lifetime, diagnostic and recovery contract, reuse suitable runtime controls and prove the accepted bound. This is an unproved integration requirement, not a reported defect in the generic drain contract.

OD32 extends the internal-progress ordering to completion reactions; OD33 requires detected excessive automatic/completion progress to stop, retain committed progress and expose an actionable incident requiring normal recovery without automatic repetition. These accepted outcomes do not establish the concrete detection limit/lifetime or a sufficient incident/recovery integration. The source-grounded technical design must specify and prove those details without creating competing runtime authorities.

### Existing owners remain authoritative

OD23 requires recovery at the failed activity boundary while preserving earlier completed phases. The [structural reschedule opt-in](https://github.com/elsa-workflows/elsa-foundation/blob/9eaed8b3302f7cdaaa8366315adfbc37b181d92a/Essentials/src/Workflows/Runtime/Core/Contracts/IRuntimeStructuralActivity.cs), `IRuntimeAcceptsRescheduledFaultedChild`, governs `RescheduleActivity/1` under its eligibility rules; it is not a prerequisite checked by `RetryFaultedActivity/1`. The [operator retry handler](https://github.com/elsa-workflows/elsa-foundation/blob/9eaed8b3302f7cdaaa8366315adfbc37b181d92a/Essentials/src/Workflows/Runtime/Elsa.Workflows.Runtime/Services/Alterations/Handlers/RetryFaultedActivityAlterationHandler.cs) instead validates its own fault/intervention/parent eligibility and retains scheduling provenance and operation keys for the successor. The first development witness confirms that guard retry succeeds with and without the reschedule marker, disproving the earlier proposed negative control. This is a bounded native fixture observation, not qualification of StateMachine recovery.
