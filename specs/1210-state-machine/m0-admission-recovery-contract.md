# M0 machine-addressed admission and recovery contract

> Historical M0 research/proposal, recovered from 6 November. See [current status](README.md); revalidate runtime mechanisms against the 12 November kernel direction before implementation.

**Revision:** A1/r2. The [scoped delegated policy decision](https://github.com/elsa-workflows/elsa-foundation/issues/3815#issuecomment-6670586138) agrees its listed behavioral direction against exact published `191d2e777` and frozen manifest `e7cc5ebd44dbb1bd67cda628ff542801cbea5deef8f9e8bf5097d691f4addda7`: exact addresses/current authorization, versioned semantic identity, coherent pending/receipt reservations without eviction, physical acceptance/unknown outcomes, selection/recovery and terminal/supersession dispositions, and promised retention. Numeric defaults, helper/API/schema representation, clock/storage topology, concrete shared mechanism and native placement are not approved by that decision. The remaining technical choices below remain subject to implementation review and qualification; Q2 is not closed. The [later direct owner instruction](https://github.com/elsa-workflows/elsa-foundation/issues/3815#issuecomment-6670672472) authorizes resolving those choices and completing the full feature through its normal gates, not claiming an unrun proof or another person's agreement.

## Address, semantic contents and current authority

An admission targets one exact persistence/tenant/partition scope, workflow execution, native machine invocation and pinned executable/receiver protocol. A state name, correlation value, definition ID, operation key or latest invocation is not an address. The sender's event ID is an opaque ordinal string within that invocation; do not trim, case-fold or normalize a valid ID. The input contract declares validation and encoded-size limits before admission. Retries and receipt lookup still require current authorization for that exact target; possession of an event ID or receipt is not authority.

Persist a versioned semantic-content fingerprint separately from command/envelope IDs and causal trigger-group identity. The semantic envelope contains the declared business-event kind, presence and contents of its payload, and every declared author-visible attribute. An absent payload differs from explicit null. Retry timestamps, transport IDs, observer metadata and current authorization credentials are not semantic attributes. Receiver identity/material are validated independently and cannot change during retry. Unknown fields cannot affect guards while being omitted from fingerprinting: the declared contract must either reject them or retain them as semantic contents.

The existing [runtime fingerprint authority](https://github.com/elsa-workflows/elsa-foundation/blob/9eaed8b3302f7cdaaa8366315adfbc37b181d92a/Essentials/src/Workflows/Runtime/Core/Models/RuntimeCheckpointCommitFingerprint.cs) already defines canonical object ordering and exact numeric normalization for intents and model inputs. Propose a versioned invocation-input operation in that owner, with an explicitly bounded semantic envelope; do not hash a fabricated model command or copy the private canonicalizer into StateMachine. Preserve all historical intent/model/checkpoint fingerprints. The new envelope must reject duplicate JSON object property names before admission and specify its normal string/number/presence encoding. Qualify reordered properties, equivalent numeric spellings, array order, string distinctions, absent/null and nested duplicate-property refusal. Persist the effective fingerprint version with the receipt; an upgrade cannot reinterpret an already accepted ID.

No production envelope/helper is delivered by this proposal. Its exact representation and value/secret-policy treatment require shared-owner review. Semantic payload retention uses normal durable-value storage and access policies; it does not duplicate resolved secrets into receipts or diagnostics.

## Bounded admission and receipt reservation

The effective machine policy declares positive pending-event capacity **C**, positive receipt-slot capacity **B ≥ C**, settled-receipt retention **R**, and finite identity/semantic-envelope size limits. These are required configuration obligations, not accepted numeric defaults. One receipt slot reserves the bounded identity, fingerprint, order, policy and outcome metadata required for its promised lifetime. Runtime resource/tenant limits remain authoritative. Configuration validation must reject an incoherent policy before feature admission.

Count every accepted but not finally disposed business event against C, including an event currently evaluating or driving a selected transition set. Waiting for durable phase work, a guard fault, regional recovery or a loop incident does not release that reservation. Settling the input releases its pending reservation but retains its receipt slot. B counts unsettled reservations plus unexpired settled receipts, so a long receipt window cannot make retention unbounded or force early eviction. If only B is exhausted, return a distinct receipt-capacity result; both capacity results refuse immediately without waiting for capacity. Neither evicts an accepted event or a promised receipt.

Under the target's existing execution writer, evaluate admission in this order:

1. Establish current scope/authorization, supported coherent physical boundary and exact receiver address. Validate and fingerprint the declared semantic envelope without activating unrelated authored activity inputs.
2. Resolve a retained event ID before considering full or terminal rejection. Same ID/content returns its existing order and current outcome without consuming capacity or scheduling another evaluation. Same ID/different semantic content returns conflict, even when the receiver is terminal. A lookup/read failure is unavailable/unknown, not evidence that the ID is new.
3. For a new ID, reject a terminal/retired invocation. For an active invocation, reject immediately if C or B would be exceeded or the admission ordinal is exhausted. Do not consume the ID or ordinal on refusal; a later retry can attempt admission again.
4. Atomically allocate the next positive invocation-local ordinal, reserve C and B, retain the content/fingerprint/effective receipt promise, append the canonical input and create or preserve an owed evaluation wake-up. Commit all required value-reference ownership in that same coherent boundary. Never wrap/reuse an exhausted ordinal.
5. Report accepted only after the physical commit is authoritative. Coalesced staged state, a transport acknowledgment or scheduler enqueue alone is insufficient. If commit success is ambiguous, report an unresolved result with the same event identity for lookup/retry; do not label it rejected or allocate a fresh semantic identity.

Concurrent distinct admissions receive their observable order from the committed allocation; concurrent identical retries obtain one reservation. An admission which loses a revision race re-reads authoritative state and applies the same reducer rather than treating the race as capacity or conflict. Cancellation of the HTTP request cannot roll back an already committed admission or justify a false rejection response.

The pure admission operation may progress while ordinary work is pending or recovery blocks chart evaluation. It cannot drive guards, transition selection, phase work, variable mutation or automatic progress. If the normal execution/physical dependency is unavailable, refuse or leave the result unresolved honestly; do not bypass the existing writer. Acceptance while recovery is blocked must not reactivate a secret-bound Entry just to reach the receipt reducer.

## Evaluation, disposition and recovery

The canonical business queue is evaluated in committed ordinal order after the agreed automatic/completion progress settles. Distinct timer/activity-trigger competition retains its separate contract. A business input and an activity-trigger completion derived from it have different identities; receipt lookup neither makes an activity ready nor replays a consumed input.

| Semantic input state | Required committed evidence and allowed next steps |
|---|---|
| Queued | Accepted order/content and capacity reservations retained. May be selected for evaluation, or finalized as not processed when the invocation ends or retires. |
| Evaluating | Exact input, committed configuration/visit identities and selection/recovery context retained. A guard error blocks evaluation with a normal actionable incident; it is not false eligibility or unhandled. |
| Selected | Exact selected transition set, consumed occurrences and complete phase plan retained before authored effects. Required Exit/Action/Entry work may wait or recover without selecting/dequeuing the business input again. |
| Handled | All required selected-set work succeeded and its resulting configuration was committed. Final input outcome records selected identities and completed work; later automatic/completion incidents are linked subsequent progress, not reversal of this outcome. |
| Unhandled | Evaluation completed with no eligible transition. Final disposition releases C and never revives after values/configuration change. |
| Not processed | Invocation completion/cancellation/retirement won before a transition set was selected. Final reason distinguishes completion, cancellation and retirement/supersession with exact evidence; retain any interrupted eligibility-evaluation evidence rather than implying the input was never examined. |
| Interrupted | Invocation cancellation/retirement ended a selected input before its required work succeeded. Record the actual phase boundary, completed siblings and known external-effect uncertainty. It is neither successful handled nor unselected-not-processed. |

The transition from Queued into Evaluating and selection context must be durable before guard work can fault or its result can be lost. Selection and the committed phase plan obey C1's semantic checkpoint rather than a separate lease or selection ledger. An evaluating input whose guards all return false becomes Unhandled atomically with its reservation release. Cancellation before selection follows the existing P3 proposal's Not processed policy, retaining the recorded evaluation boundary; it cannot claim an unhandled evaluation succeeded.

Recovery follows normal eligible child-activity/incident protocols. Successful earlier phases and independent sibling work remain successful; still-running work follows Elsa's normal incident policy. Retrying an ordinary child may use a successor activation, but the semantic phase operation retains its committed identity and cannot be scheduled twice by a duplicate acknowledgment. Business receipts never retarget a successor machine invocation. Expected guard/phase faults must leave the coordinating receiver active through an eligible ordinary child boundary; faulting the receiver and reopening its closed frames is not an implementation of continued bounded acceptance.

Loop exhaustion preserves committed progress and the selected/final input evidence. Queue admission cannot clear the loop incident. A supported recovery operation must have explicit eligibility and audit evidence before further evaluation; an automatic timer/retry of the same blocked cycle is not recovery. Concrete guard-child, phase-successor and loop-recovery topology remains a native-placement proof obligation, not a new recovery API approved here.

## Terminal races and retention

Admission, evaluation selection and terminal lifecycle changes serialize through the same execution authority. If admission wins before terminality, its accepted receipt exists and terminalization must finalize its input according to the table. If terminality wins, a new ID is rejected; retained duplicates/conflicts still resolve without activating the receiver. The terminal checkpoint must durably reconcile all accepted pending inputs, capacity counts, final reasons and cleanup/wake-up responsibilities. For bounded C, no input may disappear between terminal state and receipt settlement. If the selected physical boundary cannot make that terminal projection coherent, the host is not qualified for this capability.

Eligible receiver/ancestor supersession is also a lifecycle boundary, not a cancellation alias. The normal [successor staging](https://github.com/elsa-workflows/elsa-foundation/blob/9eaed8b3302f7cdaaa8366315adfbc37b181d92a/Essentials/src/Workflows/Runtime/Elsa.Workflows.Runtime/Services/Alterations/ActivitySuccessorStaging.cs) records Superseded and exact successor lineage. Its atomic alteration participant must settle the old receiver's unselected inputs as Not processed with an explicit superseded/retired reason, and selected work as Interrupted, retaining actual work/lineage evidence and receipt promises on the old address. The successor gets no copied input queue, receipts or receiver control state. Shared checkpoint validation must refuse supersession if it cannot stage that projection coherently; it must not silently strand reservations or rely on a future callback from the ended owner. This applies to receivers retired within a superseded ancestor subtree too. Ordinary eligible child retry under a continuing receiver still transfers its logical phase obligation rather than terminalizing that receiver's business queue.

Capture each accepted receipt's effective retention promise. Unsettled receipts/payload responsibilities do not expire while work or recovery remains pending. R begins at that receipt's committed final disposition using the normal trusted persistence/time authority. Policy changes cannot shorten a previously promised R or invalidate a pending identity. Settling frees C, while a receipt slot frees only after its promised window and all normal source/transport/value obligations are discharged. A clock/read failure cannot silently authorize expiry.

Workflow/activity deletion and material/value collection must honor the receipt and unfinished-work retention roots. Terminal lookup does not depend on rebuilding a closed variable frame, resolving the original secret inputs or finding the latest definition. Pin only the existing evidence/material/value roots actually required by the declared promise, and release them through their normal owner; do not retain every activity PrivateState indefinitely. Exact store/query/collector placement remains part of the shared contract review.

After the retained guarantee ends, an active invocation may accept the same ID as a new admission with a new ordinal; no deduplication is promised for the expired receipt. A terminal invocation still rejects new admissions. A missing record outside retention must not be described as proof that the event was never accepted. No event or receipt automatically moves to another invocation, republished version or replacement execution.

## Qualification and agreement gate

The next agreed work unit must prove the actual ordinary admission path, physical receipt query and supported recovery topology, with no private API queue, temporary flag or fixture-owned receipt store:

1. C and B boundaries, selected input counted, immediate distinct refusals, and simultaneous admissions/retries around the last slot and ordinal exhaustion.
2. Semantic fingerprint compatibility controls above, exact target/version mismatch, same ID in two machine invocations, changed retry credentials under current authorization and unauthorized lookup/admission.
3. Physical admission commit versus response, coalescing flush, process death/ambiguous completion, request cancellation, duplicate retry and cold retained receipt lookup.
4. Ordinary durable phase wait and failed child/guard/loop recovery while bounded admission continues; unavailable secret resolution for unrelated authored work cannot be an admission dependency.
5. Queue order across restart; unhandled non-revival; false guard versus guard fault; recovery preserving selection/completed phases/regional siblings; duplicate/stale child acknowledgments and successor controls.
6. Admission/selection/completion/cancellation/supersession races, unselected Not processed (with any interrupted evaluation evidence) versus selected Interrupted, ancestor retirement, old-address retained lookup and a clean successor queue; handled input followed by a separate internal-progress incident.
7. Retention across long recovery, later policy changes, terminal receipt lookup, attempted deletion/collection before expiry, safe expiry with remaining transport/value obligations, full B without eviction and post-retention same-ID behavior.
8. Source-bound legacy native/model/BPMN, selected EF/provider and reusable/secret/withholding compatibility at each new checkpoint shape, plus actual Studio projections of every distinct outcome.

Independent review and the applicable scoped design/spec agreement must precede implementation. C1/shared-owner integration, concrete defaults, physical representation, native placement, Q1/Q3 and Studio/saga qualification remain open. Passing bounded N9/N10 probes does not satisfy these admission/recovery cases.
