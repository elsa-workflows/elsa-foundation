## Bite-proofs

[`bite-proofs.json`](bite-proofs.json) has 47 entries, and all bite. Three, recorded at `1ac5c8e19` (review round 7), cover the limit regex's connection-limit and channel-limit alternatives and the release of a held connection when the broker unblocks it; they supersede the round 3 and 4 entries for those limits, which mutated earlier wording. In the batch run the connection-limit mutation once passed; run alone, and three more times, it failed, and that run is the one recorded. Four, recorded at `3e7a85bf0` (review round 6), cover the limit match stripping quoted names before matching, a timed-out or blocked confirm being transient, holding one blocked connection per target, and the broker's blocked notice ending a confirm. Three, recorded at `d9fafbd3c` (review round 5), cover the limit match ignoring quoted virtual host and user names, releasing an abandoned connection in the background, and the persisted effect mechanism 2. Four, recorded at `189c40061` (review round 4), cover the driver treating a channel-limit 530 as transient, the bound on each confirm, and the worker's length re-checks of the exchange and routing key. Five, recorded at `154fbb248` (review round 3), cover the writer refusing a body that is not an array of objects (both checks), the writer's run header, the binding refusing an invalid AMQP URI, and the driver treating a connection-limit 530 as transient. Four, recorded at `069d41663` (review round 2), cover the host, port and allowed exchanges in the pinned handle and the routing key's length. Six, recorded at `5fc2122e4` (review round 1), cover dispatch skipping a route the owed batch already records, the missing-publisher refusal, the handle excluding the AMQP URI, two current revisions being ambiguous, the writer failing an unroutable batch, and the driver treating an unreachable broker as transient. The other 18, recorded at `78f18b250`, cover the compiler's main-route, exchange and routing-key rules and the exchange's length; the worker's error-route and name re-checks; the binding's allowed exchange and the virtual host and user in its handle; the writer's negative acknowledgement and transient yields and its per-record message id; dispatch recording only after every confirm; the store's `.amqp` publication key; and, on the real broker, the driver's 404 rejection, return-as-unroutable mapping, mandatory flag and persistent delivery mode.

**Not bite-proven or not tested:**
- **The decision to hold a blocked connection.** With it disabled (recorded at `4a32719c9`), the alarm test still passes: the broker then lists no more than two blocked connections in that test, so the count does not separate the two. The lookup that makes later publications yield while one is held is bite-proven (round 6), and the hold's release on unblock (round 7).
- **The confirm bound and the round-trip bound.** Since round 6 the broker's `connection.blocked` notice ends a publication under an alarm long before either bound, so no current test reaches them; the round 4 entry for the confirm bound mutated a test that round 6 replaced and is superseded.
- **The driver's refusal classifications, tested but not bite-proven:** failed authentication (`AuthenticationFailureException`, also inside `BrokerUnreachableException`) and a 530 that is not a limit, both exercised on the real broker; the classifier's default arm, for an exception type nothing else names, is untested.
- **Server-side inspection of a RabbitMQ run** (the inspector's and runtime API's `rabbitMq` effect state) is proven only by the Workbench journey's `inspectionShowsTheRabbitMqRoute` check, not by a .NET test or a bite-proof.
- **Releasing an abandoned connection in the background** when a publication ends unanswered without a blocked notice (a failure, a bound reached, or the caller's cancellation): the round 5 entry mutated earlier code, and since blocked connections are held, no test reaches this path with an unresponsive broker.
- **Untested guards:** the driver's release of a held blocked connection when it shuts down, and its re-check, right after taking the hold, of an unblock or shutdown that arrived first (a race review round 7 reproduced on a real broker by delaying the client's reads; no test can order the broker's notices); the driver's transient reading of a 530 that reports a limit the broker could not query; the binding's refusal of a blank AMQP URI; the driver's disabled automatic recovery, which keeps a recovered connection from confirming part of a batch; and the compiler's size budget for the exchange and routing key.
- **The default ports** come from the client's connection factory; the target test pins them, but no guard of ours chooses them.
- **Guards tested but not bite-proven:** the default-exchange routing, the content type and headers set by the driver, the binding's revision check (shared with the SQL bindings' pattern), the cross-catalog ambiguity check in `HostConnectorBindings` (untested for RabbitMQ), and the Studio controls.
- **Untested:** the driver's classification of failed authentication through `BrokerUnreachableException`'s inner exception on broker versions other than 4.1, and of reply codes 403 and 406; refused credentials, a missing exchange (404) and both kinds of 530 are exercised.
- **The store refusing a confirmed route's record.** Dispatch yields on `BudgetExceeded` or `Conflict` and fails with `etl.rabbitmq-delivery-refused` on any other refusal, the mapping SQL delivery uses; no test makes the store refuse.
- **A broker restart during a publication** is not a committed test. Review round 8 probed it against RabbitMQ 4.1: a killed broker surfaced as `AlreadyClosedException` (code 0) and a stopped one as 320 `CONNECTION_FORCED`, both classified transient.

## Actual Workbench journey

[`rabbitmq_workbench_journey.py`](rabbitmq_workbench_journey.py) starts its own RabbitMQ 4.1 container (the management API only declares the topology and reads the queue) and its own Workbench on ephemeral loopback ports. Two JSON Lines → RabbitMQ definitions run from native Flowcharts:
- **delivered:** four records reach the queue bound to `etl.people` by `people.loaded`, through the Done port, each persistent JSON with the message id `{effectId}:0` and the run's id in its headers;
- **unroutable:** a routing key no queue matches settles the run as a business error with `etl.rabbitmq-unroutable`, through the BusinessError port, and nothing reaches the queue.

All eight checks pass. The summary is [`workbench-journey-summary.json`](workbench-journey-summary.json), recorded at `1ac5c8e19` with a clean tree. Earlier runs at `78f18b250`, `bea009757`, `189c40061`, `d9fafbd3c` and `3e7a85bf0` passed the same checks. The unroutable run keeps one outstanding record after it settles; a SQL run settled by a rejected delivery does the same, so the journey checks accounting on the delivered run only, and the defect is #3724.

## Limits

These are stated in the ETL README:
- **At least once.** A replayed batch is published again in full; consumers deduplicate by message id.
- **Ordering.** Messages of one batch keep their order; batches of different partitions interleave, and a replayed batch can arrive after later ones.
- **Main route only**, and the runtime never declares topology.
