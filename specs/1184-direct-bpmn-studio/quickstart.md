# Validation guide

Use configured build-slot wrapper and check load before trusting timing failures. Own fresh separate Design/Runtime stores; stop only owned child hosts.

## Pre-change witness

[Pre-claim evidence](evidence/preclaim/README.md) includes the verified archive, exact source and portable collector. Save/reopen/promote and direct wait/restart/complete control passed. Candidate metadata **failed XML retention**. This does not prove the new publisher, claims or direct Studio.

## Actual human journey

1. Record exact owned host source/products. Through Studio import/open/configure a supported human process, save/reopen/promote, publish direct; prove binding/identity/layout export/reimport.
2. Start/inspect human wait. Verify direct model rows and no invented native workflow/activity/bookmark.
3. Stop host, capture whole consistent stores, restart. Fresh browser discovers the same wait through normal navigation, no scripted ID.
4. Complete exact work; restart/repeat the same operation. Verify one terminal result, retained replay and unchanged pin/Authority. Capture resulting P1 checkpoints before changing the claim writer.

For an isolated current-source pair, build Workbench, Studio Web and `tools/bpmn/DeliveryRecoveryRead` in Release after building the Studio frontend. Run `tools/bpmn/run_owned_studio_upgrade.py --family direct-human` with their assembly paths and a new output directory. This mode starts fresh separate stores and selects direct hosting/publication; original/layout modes still restore their frozen captures. All business writes come from the browser. The controller only performs readiness/login/read observations, provider backups and control of its own children.

In that output directory, `command.json` accepts `{"action":"checkpoint","label":"human-wait"}`, `{"action":"restart","label":"restarted-wait"}` and `{"action":"finish"}`. Use distinct labels for subsequent cuts/restarts. Each cut retains both whole stores and typed model/input observations; an existing label is refused. This harness capability is not proof that the journey passed.

## Actual ETL journey

1. Use the pipeline selector and normal closed RunEtl service workflow publication, then bind/publish supported direct service process.
2. Cause the finite HTTP/file dependency failure after external effects. Follow BPMN incident → native worker → ETL partitions in UI.
3. Retain original failure/stores, restart, inspect held incident/budget/pins.
4. Restore identical dependency and retry exact incident in Studio. Replay same request after uncertainty; require one distinct replacement attempt and one successful parent continuation.
5. Inspect original history, physical destination bytes/counts and declared at-least-once effects. A newer pipeline publication cannot change pins.

## Claim/interruption journey

Race two authorized subjects for one claim-required item; one owner completes. Restart/recover same claim, refuse foreign/stale completion. Test both completion versus timer/cancel orders and retained retry/cancel replay; no resurrection, truthful settlement. Admission-off recovers accepted work but refuses new admission. Old reader refuses actual new frame/material; upgraded host continues actual old stores/replay.
