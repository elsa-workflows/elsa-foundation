# Research: Local composition file bridge

The [source-boundary investigation](../../docs/reports/runtime-composition/import-export-boundary.md) and [proposed v1 contract](contracts/file-bridge-v1.md) define the file-only migration use case. This research resolves implementation choices for [#2013](https://github.com/elsa-workflows/elsa-foundation/issues/2013). The specification remains Draft; these are planning decisions, not claims that a converter exists.

| Decision | Evidence and reason | Alternative deferred |
|---|---|---|
| Use a reusable, pure bridge seam beside the selection planner; keep disk and prompts in CLI | `AuthoredComposition` has opaque settings/resources and a strict v1 top level. `SelectionPlanner.Plan` already owns exact selection and dependency findings. A future web builder needs the same preview/patch semantics without invoking a console. | A CLI-only conversion engine would invite a second builder interpretation. Extending `SelectionPlanner` with host-file I/O would mix two boundaries. |
| Read raw selected JSON layers and retain provenance before deriving effective values | [Workbench startup](../../src/apps/Elsa.Workbench/Program.cs) loads base `shells.json`, then the selected shell overlay, then environment variables and command-line arguments. Raw JSON keeps false, zero, null, empty, and source layer identities; flattened `IConfiguration` does not preserve all of these. The preview says “effective across selected files,” not “effective running host.” | Treating the host's merged configuration as import evidence would lose provenance and overclaim parity with process overrides. |
| Use the pinned Workbench source as compatibility evidence and a synthetic two-shell fixture for contract behavior | Current Workbench has one `default` shell, 81 base object-map feature entries, and seven Production entries; it has no `tenant-b`, `primary` resource, or fixture A/B. The synthetic fixture proves sibling-shell, named-resource, and unknown-node preservation that Workbench cannot. | Presenting the synthetic fixture as observed Workbench state would be misleading. An available separate CShells checkout is not proof of the pinned `0.0.30-preview.159` package's array semantics. The pinned-package proof below narrows array state and overlay behavior; cross-shape layer changes refuse in v1. |
| Classify portable settings by exact reviewed field paths, deny by default | The selection catalog carries feature groups/profiles, not a setting safety schema. `SecretSettingMask` masks descriptor-declared settings in management responses, but does not classify arbitrary imported JSON. An optional local [setting review file](contracts/setting-review-v1.md) names exact feature/field paths, expected JSON types, and safety decisions without carrying source values. Only its explicitly classified fields can enter portable intent after the operator reviews and accepts the preview. Every other path remains local and masked. | A generic “copy all settings” option would export credentials. A bare `--portable-setting` flag would let an unknown canary through without a reviewable classification artifact. Package/descriptor loading would cross the offline boundary. |
| Allow only existing logical persistence references in portable intent | The local host retains `ConnectionStrings`, provider, and `ConnectionName`; only reviewed resource names and bindings enter `resources`. Existing referenced names must be defined in the selected local resource tree. Reachability and provider compatibility remain unchecked. | Inline physical values and automatic pooling guesses would undermine the central-resource design and disclose secrets. |
| Freeze every copied supported file and recheck before acceptance/publication | The output includes unselected sibling overlay files for preservation. A content change in any copied file invalidates review, even if that file was not used to compute the selected shell. Tokens stay private in memory; no sidecar or source bytes enter authored v1. | File timestamps alone are insufficient; keeping a persistent source bundle or sidecar broadens secret and recovery scope. |
| Publish only after an interactive review of one preview or diff | `composition import` writes one fresh authored file after a TTY decision. `composition generate` reopens local sources, computes a redacted candidate diff, and writes a fresh directory after a separate TTY decision. Noninteractive use without a review transport refuses in v1. | `--yes` or an unattended default would turn the source scan into implicit acceptance. A web transport and in-place apply belong to later work. |
| Copy then patch only reviewed paths; stage privately and rename atomically | The bridge checks duplicate keys/IDs, unsafe paths, and source changes; the CLI keeps copied bytes for untouched files and changes only accepted JSON paths. It prepares output beside a nonexisting destination, verifies it, rechecks source, then publishes by same-volume rename. On refusal it removes staging and leaves source/destination untouched. | Reusing `FeatureManagementService.SaveAsync` edits only a feature slice and cannot preserve/revise this whole file bundle. |

The actual Workbench appsettings files carry separate logging, connection, and migration-policy nodes. Production has a `//_migrate` JSON property. All are preservation data, not bridge policy. Any discrepancy discovered while testing the pinned CShells package is a reason to narrow supported source shapes and revise the Draft contract before implementation, not to silently approximate host behavior.

## Pinned CShells feature-shape proof (#2017)

Foundation pins `CShells` `0.0.30-preview.159` in `Directory.Packages.props`. The focused tests in `tests/essentials/Architecture/WorkbenchConfigurationTests.cs` compose synthetic base and selected overlay JSON through that package's public `ConfigurationShellBlueprint`, using the same `IConfiguration` layering Workbench supplies. Run them with:

```bash
dotnet test tests/essentials/Architecture/Elsa.Architecture.Tests.csproj -c Release --no-restore --filter FullyQualifiedName~Pinned_cshells_package
```

| Input | Observed composed view | Bridge consequence |
|---|---|---|
| Object-map `A` with settings, `B: false`; overlay changes `A.Flag` | A enabled, B disabled; overlay Flag wins while base Limit remains | Explicit disable is supported in object-map syntax; setting provenance requires raw layers. |
| Base object-map `A: false`; overlay `A: {"Flag":true}` | A stays disabled; the base scalar value survives beside overlay children | Refuse scalar/object changes for one feature across layers rather than claiming the overlay re-enables it. A scalar `true` overlay over an object resets prior settings. |
| Array `[{"Name":"A","Enabled":false}]` | A remains enabled; `Enabled` is flattened as a setting | Array syntax has no explicit disabled-state encoding in this package. Refuse an authored removal targeting an array instead of inventing a translation. |
| Base array `["A","B"]`; overlay `["C"]` | Effective enabled array is C, B | The overlay replaces numeric index 0, not feature ID A; untouched base index 1 survives. Duplicate effective IDs must refuse. |
| Object-map base with array overlay | Composition rejects mixed numeric and named `Features` children | Keep cross-shape overlay refusal in v1. |
| Case-equivalent array entries `A`, `a` | Composition rejects duplicate configured names | Reject duplicates in raw layers and after effective layering. |
| Raw false, zero, null, empty string/object/array setting leaves | Raw JSON distinguishes all six kinds. Composition exposes false/zero as strings, retains empty string and empty array as empty values, and drops null and empty object leaves. | Read raw JSON before flattening; preserve untouched source nodes and types instead of reconstructing files from `ShellSettings`. |
| Object-map `A: null` versus `A: {}` | Both compose as enabled A with no settings | Keep the raw distinction even though runtime composition collapses it. |

These tests prove the pinned package's file-layer behavior, not process environment or command-line overrides, package inventory, a running host, or database readiness. The Draft [specification](spec.md), [v1 contract](contracts/file-bridge-v1.md), and [task graph](tasks.md) now reflect the array-state and numeric-index limits before a converter implementation issue is opened.
