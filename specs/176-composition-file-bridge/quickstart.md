# Validation quickstart: Local composition file bridge

This is a planned acceptance run for the first implementation story; `composition import` and `composition generate` do not yet exist. Use the [two-shell fixture](contracts/file-bridge-v1.md#two-shell-acceptance-fixture), a valid pinned catalog containing A/B, and the [setting review input](contracts/setting-review-v1.md) that classifies only `A:/Flag` and `A:/Limit`. Put sentinel values in the local connection string and unclassified `A.Future` string field. Use a disposable host directory and two fresh output paths.

1. In a terminal, run `dotnet elsa composition import --host-dir <fixture> --shell default --environment Production --catalog <catalog> --setting-review <review> --output <new-authored.json>`. Verify the preview says A enabled, B explicitly disabled, Flag=true from Production, Limit=0 from base, Future.x present/null but unclassified, and logical resource `primary`. It must mark package inventory, process overrides, provider reachability, and runtime host state unchecked. Decline once and confirm no output; rerun and explicitly accept.
2. Inspect the authored JSON with the strict existing reader or `composition plan`. It must have the supplied catalog pin, null profile, empty groups/locks, `add:[A]`, `remove:[B]`, accepted A, reviewed Flag/Limit, and logical resource references only. Neither sentinel may occur in the authored file, plan, stdout, or stderr.
3. Change only authored A.Limit from 0 to 1. Run `dotnet elsa composition generate --host-dir <fixture> --shell default --environment Production --catalog <catalog> --composition <edited-authored.json> --setting-review <review> --output-dir <new-candidate>`. Inspect the redacted diff and approve it. Parsed JSON comparison should show only base A.Limit changed. Tenant-b, disabled B, A.Future, CustomRoot, unrelated overlay annotation, and appsettings nodes remain semantically identical; untouched sibling files remain byte-identical where possible. Original source files remain byte-identical.
4. Exercise refusals: run without a terminal, name a missing overlay, introduce duplicate/case-equivalent IDs, use an unclassified authored setting, change any copied file after preview, and pre-create the destination. Each case must return its [stable refusal class](contracts/file-bridge-v1.md#failure-and-publication-boundary), disclose neither sentinel, and leave no published partial output. A changed *unselected* copied overlay must also invalidate the snapshot.
5. Run a separate source-layout check against a disposable copy of `src/apps/Elsa.Workbench` JSON. It proves preservation of the actual single-shell object-map files, Production overlay, and root appsettings nodes. Do not claim that this sample proves tenant-b, named-resource, array-shape, or running-host behavior; those have separate fixture/package checks.

For implementation verification, run `dotnet test tests/essentials/Modularity/Planning/Tests/Elsa.Modularity.Planning.Tests.csproj` and `dotnet test tests/essentials/Cli/Tests/Elsa.Cli.Tests.csproj`, the architecture guard, `dotnet run --project tools/maps/Elsa.Maps.Generator -- check`, and `git diff --check`. The focused CLI test should invoke the real process and scan both streams for canaries. EF container suites are not relevant to this file-only change unless implementation crosses into EF. The main-branch broad CI policy is independent of this focused PR proof.
