# Validation quickstart: Local composition file bridge

`composition import` is the first implementation checkpoint. `composition generate` remains planned; this checkpoint does not claim a source-preserving round trip. Use the [two-shell fixture](contracts/file-bridge-v1.md#two-shell-acceptance-fixture), a valid pinned catalog containing A/B, and the [setting review input](contracts/setting-review-v1.md) that classifies only `A:/Flag` and `A:/Limit`. The fixture puts sentinel values in the local connection string and unclassified `A.Future` string field. Use a disposable host directory and a fresh output path.

1. In a terminal, run `dotnet elsa composition import --host-dir <fixture> --shell default --environment Production --catalog <catalog> --setting-review <review> --output <new-authored.json>`. Verify the preview says A enabled, B explicitly disabled, Flag=true from Production, Limit=0 from base, Future.x present/null but unclassified, and logical resource `primary`. It must mark package inventory, process overrides, provider reachability, and runtime host state unchecked. Decline once and confirm no output; rerun and explicitly accept.
2. Inspect the authored JSON with the strict existing reader or `composition plan`. It must have the supplied catalog pin, null profile, empty groups/locks, `add:[A]`, `remove:[B]`, accepted A, reviewed Flag/Limit, and logical resource references only. Neither sentinel may occur in the authored file, plan, stdout, or stderr.
3. Exercise import refusals: run without a terminal, name a missing overlay, introduce duplicate/case-equivalent IDs, change a selected or unselected copied file after preview, and pre-create the destination. Each case must return its [stable refusal class](contracts/file-bridge-v1.md#failure-and-publication-boundary), disclose neither sentinel, and leave no published partial output. The filesystem and source-reader tests cover source mutation that is difficult to time through an interactive CLI.
4. Run a separate source-layout check against a disposable copy of `src/apps/Elsa.Workbench` JSON. It proves the actual single-shell object-map files and Production overlay can be read without host activation or copying unreviewed values. It does not prove tenant-b, named-resource, array-shape, or running-host behavior; those have separate fixture/package checks.

For the later generation story, change only authored A.Limit from 0 to 1 and run `composition generate` against a second fresh output directory. Compare parsed JSON to show only base A.Limit changed. Tenant-b, disabled B, A.Future, CustomRoot, unrelated overlay annotation, and appsettings nodes should remain semantically identical; untouched sibling files should remain byte-identical where possible. Original source files must remain byte-identical. This step is not a gate for the import checkpoint.

For implementation verification, run `dotnet test tests/essentials/Modularity/Planning/Tests/Elsa.Modularity.Planning.Tests.csproj` and `dotnet test tests/essentials/Cli/Tests/Elsa.Cli.Tests.csproj`, the architecture guard, `dotnet run --project tools/maps/Elsa.Maps.Generator -- check`, and `git diff --check`. The focused CLI test invokes the real process and scans both streams for canaries. This file-only bridge has no EF behavior to prove; the repository's broad main-branch CI policy is a separate gate.
