# Validation quickstart: Local composition file bridge

`composition import` and `composition generate` form the file-only round trip. Use the [two-shell fixture](contracts/file-bridge-v1.md#two-shell-acceptance-fixture), a valid pinned catalog, and the [setting review input](contracts/setting-review-v1.md) that classifies only `A:/Flag` and `A:/Limit`. The fixture puts sentinel values in the local connection string and unclassified `A.Future` string field. Use a disposable host directory and fresh output paths.

1. In a terminal, run `dotnet elsa composition import --host-dir <fixture> --shell default --environment Production --catalog <catalog> --setting-review <review> --output <new-authored.json>`. Verify the preview says A enabled, B explicitly disabled, Flag=true from Production, Limit=0 from base, Future.x present/null but unclassified, and logical resource `primary`. It must mark package inventory, process overrides, provider reachability, and runtime host state unchecked. Decline once and confirm no output; rerun and explicitly accept.
2. Inspect the authored JSON with the strict existing reader or `composition plan`. It must have the supplied catalog pin, null profile, empty groups/locks, `add:[A]`, `remove:[B]`, accepted A, reviewed Flag/Limit, and logical resource references only. Neither sentinel may occur in the authored file, plan, stdout, or stderr.
3. Exercise import refusals: run without a terminal, name a missing overlay, introduce duplicate/case-equivalent IDs, change a selected or unselected copied file after preview, and pre-create the destination. Each case must return its [stable refusal class](contracts/file-bridge-v1.md#failure-and-publication-boundary), disclose neither sentinel, and leave no published partial output. The filesystem and source-reader tests cover source mutation that is difficult to time through an interactive CLI.
4. Run a separate source-layout check against a disposable copy of `src/apps/Elsa.Workbench` JSON. It proves the actual single-shell object-map files and Production overlay can be read without host activation or copying unreviewed values. It does not prove tenant-b, named-resource, array-shape, or running-host behavior; those have separate fixture/package checks.

5. Change only authored A.Limit from 0 to 1, then run `dotnet elsa composition generate --host-dir <fixture> --shell default --environment Production --catalog <catalog> --composition <accepted-authored.json> --setting-review <review> --output-dir <new-candidate-directory>`. Review the redacted `/Limit` diff and type `generate` to publish. The CLI does not print either sentinel or the physical connection value. Decline or run without a terminal to confirm neither publishes a directory.
6. Compare parsed JSON to show only base A.Limit changed. Tenant-b, disabled B, A.Future, CustomRoot, unrelated overlay annotation, and appsettings nodes remain semantically identical; untouched sibling files remain byte-identical. Original source files remain byte-identical. Existing logical default and feature-binding references can be changed only to names already defined in the selected local resource definitions and only when their physical source paths already exist. Unsupported activation edits or newly authored paths refuse rather than silently disappearing.
7. Pre-create the destination, alter any selected or unselected copied file after the snapshot, and cancel during publication. Each refusal must preserve the source and leave no partial candidate. The filesystem publisher tests exercise the timed recheck and cleanup; the real-process generation tests cover approval, refusal, preservation, and both output streams.

For implementation verification, run `dotnet test tests/essentials/Modularity/Planning/Tests/Elsa.Modularity.Planning.Tests.csproj` and `dotnet test tests/essentials/Cli/Tests/Elsa.Cli.Tests.csproj`, the architecture guard, `dotnet run --project tools/maps/Elsa.Maps.Generator -- check`, and `git diff --check`. The focused CLI tests invoke the real process and scan both streams for canaries. A disposable Workbench-file generation sample checks existing-file preservation without activating a host. This file-only bridge has no EF behavior to prove; the repository's broad main-branch CI policy is a separate gate.
