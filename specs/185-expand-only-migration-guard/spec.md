# Feature Specification: Expand-Only Migration Guard

**Feature Branch**: `claude/2093-specs-b7-b9`
**Created**: 2026-09-27
**Status**: Draft
**Input**: Workstream B8, [issue #2104](https://github.com/elsa-workflows/elsa-foundation/issues/2104), of the
cluster-safe schema rollout program [#2093](https://github.com/elsa-workflows/elsa-foundation/issues/2093). A migration
added after [#1976](https://github.com/elsa-workflows/elsa-foundation/issues/1976) freezes the 4.0 baselines may only
add: nullable columns, tables and indexes. The build fails when such a migration drops, renames or retypes anything,
unless an explicit, reviewed opt-out names its reason. That is what keeps hosts still on the previous version working
against the migrated schema during a rolling upgrade: phase 1, "Expand", of the rollout #2093 describes.

Decisions of record: [ADR 0078](../../docs/adr/0078-workflow-executions-are-virtual-actors-and-cluster-membership-is-a-foundation-contract.md)
("The first consumers", "The schema version gate": "While a version awaits finalization, migrations are expand-only:
nothing is dropped, renamed or retyped until no finalized version still reads it"; Consequences, on the #1976 freeze)
and [ADR 0077](../../docs/adr/0077-a-module-upgrades-in-place-only-when-its-persisted-schema-is-unchanged.md) ("How
this composes with runtime module installation": "An additive migration leaves the older version working"). Both are
accepted through B0 ([#2096](https://github.com/elsa-workflows/elsa-foundation/issues/2096), PR #2118). The owner's
decision Q3 on #2093 (2026-09-27) binds this spec: B8 stays a migration guard, and content-shape changes are enforced by
spec 180's round-trip fixture, not here. The module declaration it reads is
[ADR 0076](../../docs/adr/0076-persistence-tooling-runs-inside-the-host-closure.md)'s D2 (`[EfModule]`).

Companion specs: [spec 180](../180-schema-upcaster-chain/spec.md) (B4) relies on this guard for the rule that a new
column is nullable, so a predecessor's writes leave it unset ("Writing the predecessor format"), and owns the matching
rule for JSON content (FR-022, FR-027). [Spec 181](../181-schema-finalization-gate/spec.md) (B5) assumes it
(Assumptions). [Spec 186](../186-post-finalization-backfill/spec.md) (B9) is where rows are upgraded after
finalization, which is why a migration here never rewrites data.

## Terms

Spec 180's Terms apply, notably EF module. In addition:

- **Baseline**: the migrations of one EF module, for one provider context, that #1976 freezes when 4.0 ships as a
  stable release: each module's `Initial`, and for Secrets the historical chain it already keeps.
- **Freeze manifest**: the committed record #1976 adds of shipped migration ids and content hashes. This spec reads
  from it which migrations make up each baseline (RQ-001).
- **Post-freeze migration**: a migration of a first-party EF module that is not part of its module and provider's
  baseline (FR-002).
- **Pre-existing table**: a table the migration under inspection does not create.
- **Violation**: one migration operation that is not on the allowed list (FR-007 to FR-010), named in the canonical
  form of FR-011.
- **Opt-out**: a reviewed declaration on one migration that permits exactly the violations it lists (FR-012).
- **Contracting migration**: the second half of a change split across two versions (spec 180, FR-027): a migration
  that removes what a later version no longer reads. It always needs an opt-out.

## Current state

- **Thirteen EF modules, four provider contexts each.** `EfModuleCatalog.Discover` finds 13 `[EfModule]` declarations
  in eleven assemblies across `src/essentials` and `src/extensions`, and `EfModuleDescriptorTests` pins them. Each
  module has one `Initial` migration per provider, regenerated by `tools/ef/generate-module-migrations.sh` whenever its
  model changes. Secrets alone keeps a chain of two or three migrations per provider.
- **Migrations compile into each module's assembly and are provider-free.** The generator's post-processing step
  rewrites the few provider-package calls EF emits, so a migration's operations can be built with EF Core Relational
  alone.
- **The operations are already inspected in tests.** `OrdinalCollationMigrationTests` builds each migration through the
  provider context's `IMigrationsAssembly.CreateMigration` and reads its `UpOperations`, against a placeholder
  connection that is never opened. Nothing inspects which kinds of operation a migration contains.
- **#1976 has not happened.** No baseline is frozen and no freeze manifest exists. Until it happens every model change
  rewrites `Initial` under a new id, and ADR 0078 says no upgrade path, this guard included, applies to a real
  database before then.

The inventory, with paths, counts and the EF Core operation types the classification covers, is in
[research.md](./research.md).

## The invariant and how it holds

**Invariant.** Applying a post-freeze migration of a first-party EF module never breaks a read or a write that a host on
the previous release makes, unless a reviewed opt-out on that migration names the exact operations that may, and why.

It holds through four mechanisms, each tested separately (Success Criteria):

1. **Operations, not source text, are inspected** (FR-004). The guard classifies what EF will execute, the same list
   `dotnet elsa persistence script` and `apply` turn into SQL, so a helper method or a reformatted file cannot hide a
   drop.
2. **The allowed list is closed** (FR-006). Anything not on it is a violation, including an operation type the guard
   has never seen and raw SQL. A new kind of operation fails the build until someone decides where it belongs.
3. **An opt-out must match exactly** (FR-013). It permits the violations it lists and no others, and a listed
   violation that does not occur fails too, so an opt-out never becomes a blanket permission.
4. **The scan cannot pass by examining nothing** (FR-003, FR-018 to FR-020). It reports what it examined, and its floors fail
   when an independent enumeration finds a module, a provider context or a migration it skipped, or when the freeze
   manifest is missing.

Why "additive" is the rule, per operation, is in "Why each operation is classified as it is" below.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - An additive change passes (Priority: P1)

After 4.0, a module author adds a nullable projection column, a new table and a non-unique index to a module. They
generate the incremental migration for each provider. The guard classifies every operation as allowed, and the build
passes.

**Why this priority**: Expand-only is the normal path for every schema change after 4.0. If the guard got in its way,
authors would learn to reach for the opt-out.

**Independent Test**: A fixture migration with an `AddColumn` that is nullable, a `CreateTable` with its own keys, and
a `CreateIndex` that is not unique, classified by the guard.

**Acceptance Scenarios**:

1. **Given** a post-freeze migration whose operations are all on the allowed list, **When** the guard runs, **Then** it
   passes and reports the migration among those it examined.
2. **Given** a migration that creates a table together with its foreign keys, unique constraints and indexes, **When**
   the guard runs, **Then** those constraints pass, because no older host writes the new table.

---

### User Story 2 - A destructive change fails the build and says what to do instead (Priority: P1)

An author renames a column in the model and generates the migration. The guard fails the build, naming the module, the
provider, the migration and the violation, and explains the remedy: add the new column beside the old one now, and
remove the old one in a later contracting migration, with an opt-out, once no finalized version reads it.

**Why this priority**: This is #2104's purpose. A rename applied during a rolling upgrade breaks every host still on the
previous version, and ADR 0078's gate cannot help once the schema itself has moved.

**Independent Test**: Fixture migrations with a drop, a rename and a retype, each classified by the guard. This is
#2104's acceptance.

**Acceptance Scenarios**:

1. **Given** a post-freeze migration that drops a column, **When** the guard runs, **Then** the build fails with
   `DropColumn <table>.<column>` named.
2. **Given** one that renames a column, **When** the guard runs, **Then** it fails with `RenameColumn` named.
3. **Given** one that changes a column's type, **When** the guard runs, **Then** it fails with `AlterColumn` named.
4. **Given** any of these, **When** the failure is reported, **Then** its message gives the two-version remedy and
   names the opt-out as the way to land a contracting migration deliberately.

---

### User Story 3 - A reviewed opt-out lands a contracting migration, and nothing more (Priority: P2)

A later release removes the old column, which no finalized version has read since the previous release. The author
adds an opt-out to each provider's migration, listing `DropColumn <table>.<column>`, giving the reason, and naming the
pull request where the change was reviewed. The guard passes and prints the opt-out in its output. A second, unlisted
drop in the same migration would still fail.

**Why this priority**: Contracting is the legitimate second half of every non-additive change (spec 180, FR-027). It
must be possible, and it must be deliberate and visible.

**Independent Test**: Fixture migrations with a matching opt-out, an opt-out missing one violation, an opt-out listing
one that does not occur, and an opt-out on a migration with no violations.

**Acceptance Scenarios**:

1. **Given** an opt-out whose list equals the migration's violations, **When** the guard runs, **Then** it passes and
   prints the module, provider, migration id, reason and review reference.
2. **Given** a migration with a violation the opt-out does not list, **When** the guard runs, **Then** it fails naming
   the unlisted violation.
3. **Given** an opt-out listing a violation the migration does not contain, **When** the guard runs, **Then** it fails
   naming the stale entry.
4. **Given** an opt-out on a migration with no violations, **When** the guard runs, **Then** it fails.

---

### User Story 4 - The scan cannot pass by examining nothing (Priority: P1)

Someone moves a module's migrations to a folder the scan does not know, or the freeze manifest goes missing in a
reorganization. The guard fails, naming what it expected to find and did not, instead of passing over an empty set.

**Why this priority**: A guard that silently scanned zero migrations looks exactly like a green one. #2104 asks for the
real scan to assert what it examined.

**Independent Test**: Run the real scan with one module's assembly withheld, and again with the manifest path pointing
nowhere.

**Acceptance Scenarios**:

1. **Given** the real scan, **When** it finishes, **Then** it reports the number of EF modules, provider contexts,
   baseline migrations, post-freeze migrations, operations examined and opt-outs honoured.
2. **Given** an EF module declared in source that the scan did not examine, **When** the floors are checked, **Then**
   the guard fails naming the module.
3. **Given** the freeze manifest is missing, **When** the real scan runs, **Then** it fails naming the path it expected,
   and never treats every migration as pre-freeze.

---

### Edge Cases

- **A new EF module after 4.0.** Its first migration has no baseline, so it is post-freeze. It only creates tables, so
  it passes with no opt-out.
- **Different operations per provider.** Each provider's migration is classified on its own, and each carries its own
  opt-out when one is needed (FR-014).
- **A data fix in a migration.** `migrationBuilder.Sql(...)` or `UpdateData` on an existing table is a violation.
  Upgrading rows belongs to spec 186's backfill, which runs after finalization and through the family's upcasters.
- **A widening that is safe on every engine**, such as a longer `varchar`. It is still an `AlterColumn` and needs an
  opt-out. The guard does not judge which alterations each of four engines can apply without breaking an older host
  (Decisions).
- **Seed data for a new table.** `InsertData` into a table the same migration creates passes.
- **A unique index on a new nullable column.** It is a violation: SQL Server treats NULLs as equal in a unique index, so
  the second older-host insert, which leaves the column null, fails.
- **`Down` operations.** They are not examined. Nothing downgrades a database: `dotnet elsa persistence` has no
  downgrade command, and a rollback past finalization restores a backup (spec 181, FR-003).
- **A migration EF cannot build without a provider.** The generator keeps migrations provider-free. If one is not, the
  guard fails for that migration, naming it, rather than skipping it.
- **A third-party EF module.** It is not first-party, so this guard does not run over it. Its author can call the same
  classifier from their own tests (Out of Scope).

## Requirements *(mandatory)*

### Functional Requirements

**Scope**

- **FR-001**: The guard MUST examine every migration of every provider context of every first-party EF module: every
  `[EfModule]` declaration in `src/essentials`, `src/extensions` and `src/apps` (ADR 0076, D2). A provider context the
  declaration marks unsupported is skipped and reported as skipped.
- **FR-002**: A migration is post-freeze when it is not part of its EF module's baseline for its provider context, as
  the freeze manifest records it (RQ-001). A module or provider context with no baseline recorded has no pre-freeze
  migrations: every migration it has is post-freeze.
- **FR-003**: The real scan MUST fail when the freeze manifest is missing or unreadable, naming the path it expected.
  It MUST NOT treat a missing manifest as "nothing is post-freeze". The classifier and its fixture tests (FR-021) do
  not need the manifest, so they can land before #1976; the real scan is enabled in the change that freezes the
  baselines, or after it.

**Inspection**

- **FR-004**: The guard MUST classify EF migration operations, not source text. For each migration it builds the
  migration through its provider context's `IMigrationsAssembly.CreateMigration`, with that provider's name, and reads
  `UpOperations`, as `OrdinalCollationMigrationTests` does. It opens no database.
- **FR-005**: `Down` operations MUST NOT be examined.
- **FR-006**: Classification MUST be per operation, against a closed allowed list. An operation not on the list is a
  violation, whether its type is known to the guard or not.

**The allowed list**

- **FR-007**: On a table the same migration creates, these MUST be allowed: `CreateTableOperation` with its columns,
  primary key, foreign keys, unique constraints and check constraints; `CreateIndexOperation`, unique or not;
  `AddForeignKeyOperation`, `AddPrimaryKeyOperation`, `AddUniqueConstraintOperation` and
  `AddCheckConstraintOperation`; and `InsertDataOperation`.
- **FR-008**: On a pre-existing table, these MUST be allowed: `AddColumnOperation` when the column is nullable and not
  computed; and `CreateIndexOperation` when the index is not unique.
- **FR-009**: Anywhere, these MUST be allowed: `EnsureSchemaOperation` and `CreateSequenceOperation`.
- **FR-010**: Every other operation MUST be a violation. That includes, and the guard's message names each
  explicitly: every drop (table, column, index, foreign key, primary key, unique constraint, check constraint, schema,
  sequence); every rename (table, column, index, sequence); `AlterColumnOperation` of any kind — type, nullability,
  length, default, collation or computed expression; `AlterTableOperation`, `AlterDatabaseOperation`,
  `AlterSequenceOperation` and `RestartSequenceOperation`; `SqlOperation`; `UpdateDataOperation` and
  `DeleteDataOperation`; `InsertDataOperation` into a pre-existing table; an `AddColumnOperation` that is not nullable,
  or is computed; a unique `CreateIndexOperation` on a pre-existing table; and a foreign key, primary key, unique
  constraint or check constraint added to a pre-existing table.
- **FR-011**: Each violation MUST be named in one canonical form, `<OperationName> <table>[.<column, index or
  constraint>]`, with the operation's type name without its `Operation` suffix and without a schema, because a schema
  belongs to a deployment and not to a migration. For example `DropColumn elsa_example.Legacy`.

**Opt-out**

- **FR-012**: An opt-out MUST be an attribute on the migration class, readable as assembly metadata without running
  the migration, carrying: a reason, which MUST NOT be blank; a review reference, a GitHub issue or pull request in
  `#NNNN` form, where the change was reviewed; and the exact list of violations it permits, in FR-011's form. The
  attribute type lives in `Elsa.Persistence.EntityFramework` beside `[EfModule]`, so a third-party module can use it
  too. Its name is the plan's to confirm; this spec calls it the opt-out.
- **FR-013**: A migration with an opt-out MUST pass only when its violations equal the opt-out's list. A violation the
  list lacks fails, naming it. A listed violation that does not occur fails, naming the stale entry. An opt-out on a
  migration with no violations fails.
- **FR-014**: An opt-out MUST cover only the migration class it is on. Each provider's migration of one change carries
  its own.
- **FR-015**: Every opt-out the guard honours MUST appear in its output with the module, provider, migration id,
  reason and review reference, so each one is visible in the CI log of every run, not only in the pull request that
  added it.

**Failure**

- **FR-016**: A violation MUST fail the build through a test in the CI suite. The message MUST name the module, the
  provider, the migration id and every violation, and give the remedy: split the change across two versions (ADR
  0078's 2026-09-27 amendment; spec 180, FR-027) by adding alongside now and removing later in a contracting
  migration with an opt-out, once no finalized version still reads what it removes.
- **FR-017**: A migration the guard cannot build (FR-004) MUST fail the guard, naming it. It is never skipped.

**What the scan examined**

- **FR-018**: The real scan MUST report the number of EF modules, provider contexts examined and skipped, baseline
  migrations, post-freeze migrations, operations classified and opt-outs honoured.
- **FR-019**: The set of EF modules the scan examined MUST equal each of two independent enumerations, and the guard
  fails naming any difference: the `[assembly: EfModule(...)]` declarations found by scanning the source of all three
  roots of FR-001, and the modules the freeze manifest names.
- **FR-020**: For every module, every supported provider context MUST have a baseline in the manifest, and the number
  of post-freeze migrations the scan classified MUST equal the number of migrations the provider context contains
  minus its baseline. Either mismatch fails.

**Fixtures**

- **FR-021**: Fixture migrations, in a synthetic module in the test project as `SyntheticEfModules` already provides
  for other module graphs, MUST prove detection of a drop, a rename and a retype (#2104's acceptance), and also of a
  non-nullable `AddColumn`, a unique index on a pre-existing table, an `SqlOperation` and an operation type the guard
  does not know. An expand-only fixture MUST pass, and so MUST a fixture that creates a table with its constraints.
  The four opt-out cases of User Story 3 MUST each be a fixture.
- **FR-022**: The fixtures MUST run through the same classifier as the real scan, so a passing fixture proves the real
  scan's logic and not a copy of it.

### Requirement on #1976

- **RQ-001**: The freeze manifest MUST record, for each EF module and provider context, which migrations make up its
  baseline, separately from migrations shipped after it. A list of shipped ids and hashes alone does not tell a
  baseline from a later migration once later ones ship, and FR-002 needs that distinction.

### Key Entities

- **Baseline**: per EF module and provider context, the frozen migrations #1976 records.
- **Post-freeze migration**: any other migration of a first-party EF module.
- **Violation**: an operation outside the allowed list, in canonical form.
- **Opt-out**: reason, review reference and the exact violations permitted, on one migration class.

## Why each operation is classified as it is

The test for every operation is the one ADR 0077 states: does a host on the previous release keep working against the
migrated schema? That host's model does not know anything the migration adds, and EF Core never writes a column its
model does not know.

- **A new table** is invisible to the older host, so anything on it is safe, including its constraints and seed data.
- **A nullable, non-computed column** on an existing table is left null by every older insert and update, which is what
  spec 180 means by "unset". A non-nullable column refuses the older host's inserts unless it has a default, and even
  with a default it no longer means "unset". A computed column is an expression the guard cannot judge.
- **A non-unique index** changes no result. **A unique index or a new constraint** on an existing table can refuse an
  older host's insert. On SQL Server even a unique index on a brand-new nullable column does, because it treats NULLs
  as equal.
- **Drops and renames** break every older read or write of what they remove or rename.
- **Every `AlterColumn`** is a violation, including ones that are safe on some engines. Which alterations are safe
  differs per engine and per direction, SQLite rebuilds the table for most of them, and the guard does not carry four
  engines' rules. An author with a genuinely safe alteration writes the opt-out and says why.
- **Raw SQL and data operations** on existing tables are opaque or change what older hosts read. Upgrading rows is the
  backfill's job (spec 186), after finalization.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Each fixture violation of FR-021 fails the guard with its canonical name, and each passing fixture
  passes.
- **SC-002**: The four opt-out fixtures of User Story 3 give pass, fail, fail and fail.
- **SC-003**: The real scan's report lists all 13 current EF modules and every supported provider context, and fails
  when any one is withheld.
- **SC-004**: With the freeze manifest absent, the real scan fails; it never reports success over zero migrations.
- **SC-005**: A post-freeze migration generated from an additive model change passes on all four providers with no
  opt-out.

## Assumptions

- Migrations stay provider-free after generation, as `tools/ef/generate-module-migrations.sh`'s post-processing makes
  them today, so building their operations needs EF Core Relational alone.
- #1976 freezes every first-party module's baseline at the 4.0 stable release and gives the generator a mode that adds
  incremental migrations (#1976, "What the freeze involves").
- Content changes inside a stored JSON document produce no migration at all. Spec 180's FR-022 round-trip fixture is
  what enforces the two-version split for them (Decisions, Q3 on #2093).

## Dependencies

- **#1976**, for the baselines and the freeze manifest, with RQ-001. The real scan is enabled with or after it
  (FR-003).
- The migrations test project (`tests/essentials/Persistence/EntityFrameworkCore/Migrations/Tests`), whose
  `ModuleContextCatalog`, `OrdinalCollationMigrationTests` and `SyntheticEfModules` already provide the module
  contexts, the operation-reading path and synthetic module fixtures ([research.md](./research.md)).

## Out of Scope

- Content-shape changes to stored JSON: spec 180, FR-022 and FR-027.
- Upgrading rows: spec 186.
- The #1976 guard against editing, renaming or deleting a shipped migration, which is #1976's own.
- Refusing, at apply time, a contracting migration that arrives before it is safe (Open questions, Q26).
- Running the guard over third-party EF modules. The classifier and the opt-out attribute are public, so an author can
  run the same check from their own tests.

## Open questions

- **Q26 — Refusing an early contracting migration at apply time.** The guard decides what may merge. It cannot stop a
  host from applying a contracting migration under `AutoMigrate` while an older host still reads what it removes: the
  first upgraded pod migrates, and the older pods break. The opt-out's reason is where an author records why the
  removal is safe, but nothing checks it when the migration is applied. The opt-out could also name the schema family
  and version whose finalization makes the removal safe, and `EfModuleMigrator` could refuse to apply the migration
  before the finalization record reaches it. **Recommendation: keep B8 to the build guard, as #2104 scopes it, and file
  the apply-time refusal as a follow-up before the first contracting migration ships.** No contracting migration can
  exist until a release after 4.0 has split a change across two versions.

## Decisions

Recorded 2026-09-27, when this spec was drafted. The first is the owner's, on #2093; the rest are this draft's own,
and merging the spec approves them.

- **B8 guards migrations only.** Decided by the owner as Q3 on #2093: content-shape changes are split across two
  versions and enforced by spec 180's round-trip fixture, so this guard has no JSON check.
- **EF migration operations, not source text.** Operations are what EF executes. A source scan would be defeated by a
  helper method, and the repository already builds operations this way in tests.
- **A closed allowed list.** An open list of forbidden operations would pass whatever a future EF version adds. The
  closed list fails it until someone classifies it.
- **Only nullable, non-computed columns; no unique index or new constraint on an existing table.** Spec 180 depends on
  a new column being null when an older host writes the row. A default does not give that, and a unique index or
  constraint can refuse the older host outright.
- **Every `AlterColumn` is a violation.** The guard does not carry per-engine rules about which alterations an older
  host survives. Safe ones are rare and go through the opt-out, where a reviewer sees the reason.
- **The opt-out is an attribute that must match exactly.** It sits on the migration it permits, is frozen with it by
  #1976's content hash, and is readable as metadata. Exact matching keeps it from permitting a second destructive
  operation added in the same pull request. A central register file was considered and not chosen: it would sit apart
  from the migration and would not serve a third-party module.
- **A missing freeze manifest fails the real scan.** The alternative, treating everything as pre-freeze, is the
  failure that looks like success. The classifier and fixtures can still land before #1976.
