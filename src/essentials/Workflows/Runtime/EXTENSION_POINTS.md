# Extension points — Workflows.Runtime domain

The canonical per-domain catalog (framework §2.22.1), anchored at the
`Elsa.Workflows.Runtime` composition root. Contracts remain in `Elsa.Workflows.Runtime.Core`;
provider/default implementations may live in sibling runtime projects. Runtime execution
contracts are Design-free and operate on runtime-owned executable artifacts and execution state.

> **ADR 0033 split.** Since the contracts/engine split, `Elsa.Workflows.Runtime.Core` holds only the
> contracts, models, constants, pipeline contract surface (middleware attribute/bases/placeholders,
> `RuntimePipelinePlanBuilder`), and validators. Unless an entry states otherwise, every **default
> implementation** named in this catalog now lives in this `Elsa.Workflows.Runtime` implementation
> package (moved types keep their
> `Elsa.Workflows.Runtime.Core.*` namespaces). Replacing a default still works the same way: register
> your implementation against the `.Core` contract; the engine package's registrations all use
> `TryAdd*`.

## Documented ADR 0033 deviations hosted at the composition root

Two contract-shaped surfaces live in the engine package rather than `.Core`, deliberately:

- **`IRuntimeCoalescingSessionAccessor` + `IRuntimeCoalescingDrainScopeFactory`** (namespace
  `Elsa.Workflows.Runtime.Contracts`) expose the concrete `RuntimeCoalescingSession` engine
  working state. Their only consumers are the opt-in coalescing composition in Runtime.Api and its
  tests.
- **`ActivityRuntimePipelineBuilder` + `WorkflowRuntimePipelineBuilder`** (namespace
  `Elsa.Workflows.Runtime.Builders`) bake concrete engine middleware and the concrete
  `RuntimeCheckpointCommitter` into their default plans. The declarative slot machinery remains in
  `.Core`, so third-party middleware authors do not need the engine package at compile time.

## Semantic guard

The ADR 0033 `RuntimeCoreEngineShapeGuardTests` architecture guard prevents concrete engine-role
types (`*Service`, `*Handler`, `*Dispatcher`, `*Drainer`, `*Orchestrator`, `*Materializer`,
`*Committer`, `*Scheduler`, `*Router`, `*Pipeline`, `*Session`, `*Scanner`, `*Processor`, and
`InMemory*`) from moving back into the `.Core` assembly.

## Persistence access and scope contracts

Provider-neutral persistence access and scope selection are runtime-domain contracts because they
are consumed by the runtime `I*Store` surface as well as design, publishing, identity, and
provider adapters. They live in `Elsa.Workflows.Runtime.Core.Contracts` and
`Elsa.Workflows.Runtime.Core.Models`; no contract in this layer depends on EF Core or another
storage provider.

### `IPersistenceAccessContextAccessor` / `IPersistenceAccessContextBinder`

The scoped accessor exposes the immutable `PersistenceAccessContext` selected for the current
request or operation. A transported/background operation binds one context exactly once through
the paired binder. Hosts replacing the accessor must replace both contracts with the same scoped
state holder and must preserve fail-closed scope and privilege validation.

### `IPersistenceOperationScopeFactory` / `IPersistenceScopeSource` / `IPersistenceScopeRunner`

These host-lifetime bridges create fresh async DI scopes, supply a finite duplicate-free
`PersistenceScope` snapshot, and run one ordinary operation per partition. The default
`AddPersistenceCore` registration is implemented by Runtime.Core and remains provider-neutral;
providers only replace the contracts when they own an equivalent boundary.

### `AddPersistenceCore`

`AddPersistenceCore(IServiceCollection, string defaultScope = PersistenceScope.DefaultValue)`
registers the scoped default access context and singleton scope bridges with `TryAdd*`. It does
not select a database provider or grant privileged, global, or cross-scope access. Provider
adapters validate and translate the selected context at their own persistence boundary.

## Overridable replacement contracts

### `IWorkflowDispatchStore` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Replacement (one provider owns first-class workflow-dispatch lifecycle records).
- **Signature:** save/find plus list by parent workflow execution ID.
- **Usage:** `RuntimeCheckpointStateChangeSet.WorkflowDispatches` is applied atomically with activity state and post-commit outbox work. The built-in in-memory and EF Core providers project it through their workflow-dispatch stores.
- **Safety:** operational records contain safe input descriptors, never raw child input values. Raw values exist only in the protected child-start intent payload required for delivery.

### `IWorkflowDispatchQueryStore` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Additive query capability over the configured `IWorkflowDispatchStore`.
- **Signature:** `QueryAsync(WorkflowDispatchQuery query, ...)`, notably by child workflow execution ID.
- **Usage:** `WorkflowDispatchCheckpointEnricher` uses it to mirror a child's terminal checkpoint onto every dispatch waiting on that child, which is what queues the parent-resume intent. `CheckpointRuleViolationWorkflowFaulter` also requires it before faulting a refused first commit into existence: without the projection the synthesized child would be a terminal execution nothing acts on, and the durable child-evidence rule would read it as a delivered start.
- **Safety:** a store that does not adopt it still checkpoints, but projects no terminal dispatch, so a waited child's parent is resumed by neither route. Both built-in providers implement it.
- **Default implementations:** `InMemoryWorkflowDispatchStore` and the EF module's scoped `EfWorkflowDispatchStore`.

### `IWorkflowDispatchAdmissionStore` / `IWorkflowDispatchCancellationStore` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Additive provider capabilities over the configured `IWorkflowDispatchStore`.
- **Signature:** `TryAdmitAsync(dispatchId, admittedAt, ...)` conditionally advances Pending to Started; `ApplyCancellationAsync(request, ...)` resolves a replay-stable parent cancellation request against current admission state.
- **Usage:** DispatchWorkflow linearizes external child start against parent cancellation. Cancellation requests are carried in `RuntimeCheckpointStateChangeSet.WorkflowDispatchCancellations` and resolved in the same provider transaction as the parent Cancelled state and child-cancel outbox item.
- **Safety:** cancellation wins by producing a Cancelled-before-admission marker that suppresses later start; admission wins by preserving Started and adding cancellation-requested responsibility. Terminal state never regresses. DispatchWorkflow readiness fails when either capability is absent.
- **Default implementations:** `InMemoryWorkflowDispatchStore` and the EF module's scoped `EfWorkflowDispatchStore`.

### `IWorkflowTestScopeStore` / `IWorkflowTestScopeAdmissionStore` / `IWorkflowTestScopeCleanupStore` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Single-provider replacement family for finite test-run scope lifecycle, admission fencing, and detached cleanup.
- **Usage:** a test-run root carries one immutable scope snapshot through checkpoints and DispatchWorkflow descendants. Root/new-child checkpoint admission validates Open state; direct cleanup applies only to fire-and-forget dispatches, while waited children retain the production parent-cancellation contract.
- **Safety:** the guarded provider claim rejects conflicting durable providers in either composition order. Provider transactions serialize scope close against detached child admission and commit a Started child's cancellation marker with its deterministic cancel outbox responsibility. A cleanup that finds that cancel item already recorded converges when the item carries the same responsibility (`WorkflowDispatchLifecycle.EnsureTestScopeCancellationResponsibility`), whatever its delivery progress, and keeps the item unchanged; it must not re-save it as pending (spec 102 FR-014). A different responsibility under the same identity is a conflict.
- **Defaults:** `InMemoryWorkflowTestScopeStore`; the EF Core module replaces the complete family.

### `IWorkflowExecutionStateStore` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Replacement (one provider owns retained workflow-execution state and its executable-retention projection).
- **Signature:** in addition to save/find/list, `ListPinnedExecutableArtifactIdsAsync(...)` returns the distinct artifact IDs pinned by every retained execution status, and `DeleteAsync(workflowExecutionId, ...)` removes an execution. **No retention policy calls it yet:** Elsa does not currently delete workflow executions, so runtime history is kept indefinitely. Workflow-execution retention is planned in [#1770](https://github.com/elsa-workflows/elsa-foundation/issues/1770).
- **Usage:** workflow-execution records are durable executable-retention roots. Completion or fault does not release an artifact; only deletion of the retained execution does. Providers must answer the distinct-root query without materializing every full workflow-execution document and must keep the projection consistent with save/delete.
- **Default implementation:** `InMemoryWorkflowExecutionStateStore`; durable persistence providers such as the opt-in `RuntimeWorkflowExecutionEntityFrameworkCoreFeature` replace it. EF providers retain an authoritative lossless document plus indexed history, alteration-capture, authority and pinned-artifact projections; `IWorkflowRuntimeAttentionQuery` remains a separate cross-store contract.

### `IWorkflowHealthQuery` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Optional provider capability implemented by the selected workflow-execution state store.
- **Signature:** `SupportsIncidentStore(IIncidentStateStore)` and `QueryHealthPageAsync(WorkflowExecutionStatePageQuery, IncidentHealth, CancellationToken)`.
- **Usage:** `SupportsIncidentStore` must witness that the selected incident store shares the provider's actual persistence scope; a provider must return false for an unrelated incident backend so the API uses the selected-store fallback. Apply current Active, Blocking or None incident health in the same persistence scope before counting and keyset paging. Cursors must bind to health, ordinary filters and scope. The API uses these pages as candidates and still applies request inspection authorization; only its explicit allow-all development adapter can return the provider page directly. Providers without the capability retain bounded candidate traversal and authorization-safe health filtering.
- **Default implementation:** `EfWorkflowExecutionStateStore`, using existing incident status and workflow identity projections without fault/value content or a schema change.

### `IWorkflowExecutableReferenceGarbageCollector` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Replacement (one collector owns physical executable-artifact reclamation for a runtime composition).
- **Signature:** `SweepAsync(CancellationToken cancellationToken = default)`.
- **Usage:** an artifact is eligible only when it is outside creation/staging grace and absent from the transitive dependency closure of both root sets: live source references and retained workflow executions. Root writers acquire provider-backed leases for the full validated closure before committing either root. The collector first acquires a conditional deletion guard, then recomputes closure reachability, and only that matching guard may delete; leases and guards use provider CAS so the check/delete boundary is safe across hosts. Root-query, graph-integrity, or guard failures retain the artifact for a later sweep.
- **Default implementation:** `WorkflowExecutableReferenceGarbageCollector`; registered by the Runtime composition root. The opt-in `WorkflowsRuntimeReferenceGarbageCollection` feature schedules it and exposes cadence/grace policy.

### `IWorkflowExecutableRootWriteLeaseManager` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Replacement (one coordinator scopes the provider-backed lease required to establish an executable-retention root).
- **Signature:** `ExecuteAsync(rootIdentity, leaseId, write, ...)` runs the durable write while acquiring, renewing, and finally releasing sorted leases for the exact root and dependency closure. The original artifact-ID overload remains for source compatibility and single-artifact writes.
- **Usage:** canonical publication, test-run, and workflow-execution checkpoint writers execute their durable root write through this coordinator. Persistence providers implement the underlying lease/guard transitions on `IWorkflowExecutableStore`; custom root writers must use the identity overload and provide closure-wide behavior. Lease loss cancels the write and is surfaced rather than silently reporting an unprotected root. Third-party implementations that rely on the default identity-overload fallback remain compatible but fence only the root until they override it.
- **Lease identity** *(#2274)*: a lease id names one execution. A store hands an unexpired lease with the same id to every acquirer, token included, and the first to release it ends it for all of them, so writes that may run at once must pass distinct ids. The activation coordinator passes `activation:{activationId}:{nonce}`, with a fresh nonce per call, because concurrent calls for one activation share its id. Each call's lease therefore fences the artifact closure from reference garbage collection, which is refused while any live lease exists whatever its id, from before that call's root write until it releases the lease itself, and its renewals succeed whoever else finishes first. A lease whose holder dies is never renewed or released, and no later call takes it over, so it fences the closure until it expires, `RootWriteLeaseDuration` (one minute by default) after it was acquired or last renewed.
- **Default implementation:** `WorkflowExecutableRootWriteLeaseManager`.

### `IWorkflowActivationCoordinator` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Replacement (one coordinator owns the activation lifecycle of every slot in a runtime composition).
- **Signature:** `ActivateAsync(WorkflowActivationCommand, ...)`, `DeactivateAsync(WorkflowDeactivationCommand, ...)`, `EnsureServingAsync(workflowDefinitionId, slotName, ...)`.
- **Usage:** mints the activation's source reference, prepares its trigger bindings and recurring schedules, moves the slot through `IWorkflowActivationSwitch`, and notifies `IWorkflowTriggerIndexObserver`s; Publishing and the artifact reconciler both activate through it. What a refusal, a failure, a cancellation or a stopped process leaves behind is documented once, on `IWorkflowActivationSwitch` and in ADR 0043. `DeactivateAsync` also turns off every other activation the projection stores list as serving the slot (`ListServingActivationIdsAsync(slotId)`), then retires their references, logging and leaving live one it cannot retire. `EnsureServingAsync` writes nothing when the slot's activation serves, and `ActivateAsync` makes the same check first.
- **Upgrade from a version before [#2230](https://github.com/elsa-workflows/elsa-foundation/issues/2230):** such a version could stop between its slot transition and its projection switches, leaving the slot naming an activation prepared in every projection store, or switched on in some and prepared in the others, while the one it replaced still serves. The first same-artifact activation, publish or `EnsureServingAsync` that meets the slot (Publishing's shell-start pass is one) repairs it through `IWorkflowActivationSwitch.TryRepairAsync`, tells the trigger observers as an activation does (a failure to tell them is logged and the repair stands), and logs a warning. A slot whose activation is missing or replaced in some store, which only a fault or a manual change leaves, fails every activation, check and publish with an error naming the remedy. Publishing owns the slot: unpublish it, then publish again. Another source owns it, such as the artifact reconciler, which activates and never deactivates, so removing the artifact from the mounted set does not clear it: no command clears it yet, so delete the slot, and the activation's projections and source reference, from the runtime's store, and the next pass activates the artifact again. A replaced activation whose source reference that version never retired is not repaired: it serves nothing and only keeps its artifact from garbage collection; retire it as under Operator recovery.
- **Operator recovery:** a reference that deactivation cannot retire stays live and keeps its artifact from garbage collection; once the store is healthy, retire it with `IWorkflowExecutableSourceReferenceStore.RetireAsync("activation-ref:{activationId}", now, "activation-replaced")`. Retiring it does not affect serving.
- **Concurrent calls for one activation** *(#2251, #2274)*: calls that activate the same artifact through the same source, such as two nodes reconciling one mounted set, share its activation id, source reference and projections; each holds a root-write lease of its own (see Lease identity under `IWorkflowExecutableRootWriteLeaseManager`). The switch's discard rules decide what each leaves. The artifact reconciler stays a `[SingleNodeTask]` for the three loud-but-wrong cases the Reconciliation README's "Why the passes take turns" lists.
- **Default implementation:** `WorkflowActivationCoordinator`.

### `IWorkflowActivationSwitch` *(Core — `Elsa.Workflows.Runtime.Core`, #2230)*
- **Kind:** Replacement owned by a persistence backend (one switch commits the slot authority and the projection stores of the backend that owns them).
- **Signature:** `TryActivateAsync(WorkflowActivationSlotRequest, ...)`, `TryRevertAsync(WorkflowActivationRevert, ...)`, `TryDeactivateAsync(WorkflowDeactivationSlotRequest, alsoServing, ...)`, `TryDiscardAsync(WorkflowExecutableSourceReference, ...)`, `TryRepairAsync(WorkflowActivationSlot, alsoServing, ...)`.
- **Usage:** each operation is one commit; the interface's documentation and ADR 0043 describe the guarantee, cancellation, revert, discard and repair. Only `IWorkflowActivationCoordinator` calls it. `WorkflowActivationSwitchRules` holds the reference rules and the retry bound both shipped switches apply.
- **Composition:** a switch is composed with the slot authority and the projection stores of its own backend and refuses any other when constructed. `WorkflowActivationSwitchCompositionValidator` constructs it once while the shell prepares, so a mixed composition, such as one EF participant selected through its own extension beside the in-memory switch, or a custom store, fails shell start rather than its first activation. A composition without the trigger serving spine never activates and is not checked.
- **Default implementation:** `InMemoryWorkflowActivationSwitch`, registered by `AddWorkflowActivationDefaults`, which the Runtime core and Publishing's engine fallback call. It holds the in-memory authority's lock and each in-memory projection store's lock together, and moves references by compare-and-swap in an order that never leaves an activation serving with a retired reference. `EfWorkflowActivationSwitch` replaces it in `AddRuntimeEntityFrameworkCore`: one `RuntimeDbContext` transaction whose rows carry their revisions as concurrency tokens.

### `IWorkflowExecutableInputValidator` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Replacement (one validator owns declared workflow-input contract enforcement).
- **Signature:** validates complete realized input bags or only statically known publication inputs and returns safe findings plus normalized inputs.
- **Usage:** DispatchWorkflow Design validates knowable literal bindings before publication; Runtime validates the realized bag against the exact pinned child before staging responsibility. Supported literal defaults are materialized during normalization, unknown type aliases fail closed, and findings never retain rejected raw values.
- **Default implementation:** `WorkflowExecutableInputValidator`.

### `IWorkflowExecutableStartPolicy` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Replacement (exactly one policy decides whether an otherwise-authorized future executable start may materialize).
- **Signature:** evaluates immutable executable, authority, and typed runtime context and returns an allow or classifiable deny decision.
- **Usage:** evaluated after retained/live authority, input, and dispatch-depth validation and before actor lookup. A denial creates no workflow execution state and does not mutate the executable. Multiple policy registrations fail composition deterministically.
- **Default implementation:** `AllowWorkflowExecutableStartPolicy`.

### `WorkflowExecutableDependencyGraph` *(Runtime implementation service)*
- **Kind:** Shared integrity service used by publication validation, closure leasing, and garbage collection.
- **Usage:** resolves deterministic de-duplicated closures by full artifact ID/hash identity. Missing artifacts, hash mismatches, conflicting identities, and exact-identity cycles are classified failures; same-definition different-artifact edges remain legal.

### `IRuntimeCheckpointPersistencePolicy` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Replacement (one policy decides how checkpoints flush in a runtime composition).
- **Signature:** `DecideAsync(RuntimeCheckpoint checkpoint, CancellationToken cancellationToken = default)`.
- **Usage:** separates checkpoint semantics from persistence timing. The checkpoint name says what changed; the policy decides immediate, deferred, or skipped flush.
- **Default implementation:** `ImmediateRuntimeCheckpointPersistencePolicy` *(intra-domain default)*.
- **Alternative implementation:** `CoalescingRuntimeCheckpointPersistencePolicy` *(opt-in, W9/E3-6/RT-10)* — burst-coalescing folding of intra-drain checkpoints into one flush at quiescence; enable with `services.AddCoalescingRuntimeCheckpointPersistence()` (see the Coalescing checkpoint persistence section below).

### `IRuntimeCheckpointWriter` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Replacement (one writer owns persistence of checkpoint envelopes for a runtime composition).
- **Signature:** `WriteAsync(RuntimeCheckpointCommit commit, RuntimeCheckpointPersistenceDecision decision, CancellationToken cancellationToken = default)`.
- **Usage:** implemented by runtime persistence providers to commit the checkpoint boundary and its atomic state-change envelope.
- **Default implementation:** `InMemoryRuntimeCheckpointWriter` *(single-node in-memory default for the current runtime slice; durable providers replace this)*.

### `IRuntimeCheckpointCommitEnricher` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Contributor (zero or more deterministic enrichment phases run before checkpoint fingerprinting and persistence).
- **Signature:** `Order` plus `EnrichAsync(RuntimeCheckpointCommit commit, CancellationToken cancellationToken = default)`.
- **Registration and ordering:** register contributors as `IEnumerable<IRuntimeCheckpointCommitEnricher>`. Lower `Order` values run first; equal values retain registration order. Existing contributors that do not override `Order` remain in the default phase (`0`). Later phases may depend only on state established by documented earlier phases.
- **Default implementations and dependents:** `WorkflowDispatchCheckpointEnricher` projects generic child terminal lifecycle in phase `0`; DispatchWorkflow parent cancellation runs in phase `50`; terminal result/resume enrichment runs in phase `100`. Replacements must be replay-deterministic and must fail closed on conflicting state.

### `IRuntimePostCommitIntentDispatcher` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Replacement (one dispatcher owns delivery of committed outbound runtime intents for a composition).
- **Signature:** `DispatchAsync(RuntimePostCommitIntent intent, CancellationToken cancellationToken = default)`.
- **Default implementation:** `RuntimePostCommitIntentDispatcher`, an ordinal keyed aggregate over contributed `IRuntimePostCommitIntentHandler` registrations.
- **Usage:** the outbox processor invokes this replacement contract after checkpoint commit. The default aggregate selects exactly one contributed handler by the persisted intent kind; hosts may still replace the aggregate as a unit.

### `IRuntimePostCommitIntentHandler` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Contributor (one handler owns one stable post-commit intent kind).
- **Signature:** `HandleAsync(RuntimePostCommitIntent intent, CancellationToken cancellationToken = default)`.
- **Registration:** call `services.AddRuntimePostCommitIntentHandler<THandler>(intentKind)`. The registration argument is the sole kind authority; handlers expose no second kind property that could disagree. The built-in scheduler delivery registers `RuntimeSchedulerPostCommitIntentDispatcher` for `RuntimePostCommitIntentKinds.EnqueueSchedulerWork` through this same surface, with its bounded retry policy (`RuntimeSchedulerPostCommitIntentDispatcher.RetryPolicy`, see the per-kind table under `IRuntimePostCommitOutboxStore`).
- **Composition rules:** kinds use ordinal comparison. Repeating the same `(intent kind, handler type)` is idempotent. Different handler types claiming one kind fail deterministically with the kind and sorted handler identities; the aggregate defensively repeats that validation when composed.
- **Lifetime and boundary:** the extension registers handlers as scoped defaults, and the aggregate resolves the selected handler from the active outbox-delivery scope. The global resumption sweep processes every deliverable intent kind outside workflow execution actor mailboxes. The per-execution `WorkflowDrainOrchestrator` remains intentionally filtered to scheduler work only.
- **Failure behavior:** handler exceptions and unsupported kinds flow through `RuntimePostCommitOutboxProcessor`; the existing outbox retry policy selects the persisted failed/final state. Neither case is silently acknowledged as delivered.

### `IRuntimePostCommitOutboxStore` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Replacement (one provider owns durable post-commit outbox state for a runtime composition).
- **Signature:** `SavePendingAsync(RuntimePostCommitOutboxItem item, ...)`, `GetDeliverableAsync(RuntimePostCommitOutboxQuery query, ...)`, `RecordDeliveryResultAsync(RuntimePostCommitOutboxDeliveryResult result, ...)`.
- **Usage:** stores delivery state for post-commit intents so providers can preserve record, commit, deliver, and mark-delivered ordering.
- **Default implementation:** `InMemoryRuntimePostCommitOutboxStore` *(single-node in-memory default for the current runtime slice; durable providers replace this)*.
- **Claim capability (`IRuntimePostCommitOutboxClaimStore`):** a provider that claims also renews. `RenewClaimAsync` extends a claim's visibility only while its owner and fencing token still hold the item, as a compare-and-set against concurrent claimers, and returns `null` when they do not. `RuntimePostCommitOutboxProcessor` renews each claimed item immediately before dispatching it, through the shared `FencedClaimLease` rule (#2195), so an item whose claim lapsed during a long batch and was re-claimed by a peer is skipped, not dispatched again. A claimed completion refused as stale is logged (`RuntimePostCommitClaimLost`) and the item reported as superseded; neither ends the batch. Renewal is not repeated during a dispatch, because intent handlers share the store's persistence context, so a single dispatch that outlives the visibility timeout can still be repeated by a peer. Every shipped intent kind converges under that repeat, by the mechanism in the table below. `RuntimePostCommitOutboxClaimTransitions.Renew` is the shared transition the in-memory, coalescing and EF stores apply. The processor dispatches a claimed batch's `EnqueueSchedulerWork` continuations before every other kind, each part in claim order (#2225): a continuation only enqueues, while another kind can need an execution's mailbox (a `PublishStimulus` start or resume, a DispatchWorkflow parent resume through `BookmarkResumeDispatcher`), and a live drain waiting for its own continuation holds that mailbox. Each item is still renewed immediately before its own dispatch. The claim's visibility timeout is `RuntimePostCommitOutboxProcessing.ClaimVisibilityTimeout` (one minute). A claim store also lists the items whose delivery is taken on and unsettled: `ListClaimedAsync(RuntimePostCommitOutboxClaimedQuery)` returns one execution's items of one intent kind that are `Delivering`, whoever owns the claim and whether or not it has lapsed, or `FailedRetryable`, earliest `RuntimePostCommitOutboxClaimTransitions.ClaimableAt` first, and writes nothing. `FailedFinal` items are not listed. The drain orchestrator reads it before it reports quiescence (#2225, see `IWorkflowDrainOrchestrator`), so a provider that leaves such an item out lets a drain return before its own next step has run. The coalescing decorator always answers from the durable store, because only the drain that owns a session ever claims an overlay item.
- **Why a repeated dispatch converges, per intent kind.** A contributed handler for a new kind must name its own mechanism before it relies on the outbox.

  | Intent kind | Handler | What makes a repeated dispatch converge |
  |---|---|---|
  | `EnqueueSchedulerWork` | `RuntimeSchedulerPostCommitIntentDispatcher` | The work item's `WorkItemId`: enqueue is create-only by `(WorkflowExecutionId, WorkItemId)`, so a repeat while the item is queued keeps the first, and the drainer runs nothing for a terminal execution. **Not fully idempotent once the item was drained:** a repeat then enqueues it again and convergence rests on its handler. `ScheduleActivity`, `StartActivity`, `InvokeActivity`, `CreateBookmark`, `NotifyParentActivity` and parent completion return early once their activity execution has moved on; `CompleteActivity` has no such guard and re-enqueues its deterministic follow-ups, so a repeat that arrives after its whole chain was drained re-runs that chain's checkpoint, whose replay conflicts with the committed one (a fresh `OccurredAt`) and poisons the item. A repeat that late needs a dispatch that outlived its claim and a peer that drained the whole chain before redelivering; the same window already exists for redelivery after a crash between dispatch and completion. Tracked in elsa-workflows/elsa-foundation#2232. **Retried, bounded (#2225):** the kind registers `RuntimeSchedulerPostCommitIntentDispatcher.RetryPolicy`, four attempts one second apart, the shape and numbers of a `PublishStimulus` send and of a DispatchWorkflow child start at its defaults; only the last failed attempt is `FailedFinal`. A retry repeats a failed attempt, and the enqueue is one create-only write, so an attempt that failed before that write committed queued nothing and its retry cannot repeat drained work. The exception is a write that committed but whose acknowledgement was lost: its retry dedupes while the item is still queued, and falls in the window above once it was drained. |
  | DispatchWorkflow `StartChild` | `ChildStartExecutor` | The deterministic child execution id (`WorkflowDispatchIdentity`). The start dispatcher answers `Duplicate` when the child already exists, the start envelope id is fixed by the dispatch, and the start work handler refuses a Start for an execution that already has state. |
  | DispatchWorkflow `ResumeParent` | `ParentResumeExecutor` | The parent's wait bookmark is consumed once. A repeat finds it consumed, or the parent terminal, and returns; a resume that reaches the mailbox after the bookmark was consumed is a no-op in the resume handler. |
  | DispatchWorkflow `CancelChild` | `ChildCancelExecutor` | Cancel is idempotent: a terminal dispatch or a terminal child returns at once, the cancel envelope id is fixed by the dispatch, and the drainer runs nothing for a terminal execution. |
  | `PublishStimulus`, keyed (always, from `PublishEvent`) | `PublishStimulusExecutor` | The derived execution id (`KeyedWorkflowStartIdentity`, from the intent's idempotency key and the matched artifact) for starts; the consumed-once bookmark for resumes. |
  | `PublishStimulus`, unkeyed | `PublishStimulusExecutor` | None for starts: at-least-once, and a repeat may start a second instance. `PublishEvent` never stages an unkeyed intent, so only a hand-built one reaches this row. |

### `IPostCommitFailureProjector` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Optional replacement contract. Exactly one active owning feature may recognize and safely project its own effective-final intent failures; feature registration rejects an existing replacement with a clear diagnostic.
- **Signature:** `ProjectAsync(RuntimePostCommitOutboxItem item, RuntimePostCommitOutboxDeliveryResult finalResult, ...)` returns an optional dispatch/follow-up aggregate.
- **Usage and safety:** the outbox processor invokes it only at effective final failure, then passes its result to the fenced claim-completion store. The projection must validate the canonical intent/dispatch identity and may expose only fixed diagnostics and stable identifiers; it cannot persist independently of the claimed outbox completion.
- **Known cross-domain replacement:** `Elsa.Activities.DispatchWorkflow.Runtime.WorkflowDispatchDeliveryFailureProjector`, selected by `ActivitiesDispatchWorkflowRuntime`; registration rejects a second replacement instead of silently choosing one.

### `IWorkflowDispatchRedriveStore` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Additive atomic provider capability for separately authorized delivery recovery.
- **Signature:** `RedriveAsync(WorkflowDispatchRedriveRequest request, ...)` returns a safe disposition and lifecycle summary.
- **Usage and safety:** only a fire-and-forget, delivery-caused `DispatchFailed` record linked to its exact `FailedFinal` start item can be reopened. The provider advances generation and fencing while reusing the original dispatch, child, intent, payload, retry policy, and idempotency identities. Wait dispatches and ordinary terminal states remain closed, and ordinary `IWorkflowDispatchStore.SaveAsync` still rejects `DispatchFailed -> Pending`.
- **Default and replacements:** `InMemoryRuntimeCheckpointCommitStore` supplies the process-local atomic implementation. Durable providers must bind this capability to the same physical dispatch/outbox transaction owner they use for fenced completion.

### `IWorkflowDispatchRetentionCollector` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Host-invoked sweep. Registered by the Runtime composition root; **not scheduled by any pump**.
- **Signature:** `SweepAsync(...)` returns candidate, deleted, retained and uncertain counts for one bounded pass: at most one page per terminal status.
- **Usage and safety:** deletes a terminal dispatch record only when both its parent and child workflow executions are absent, checked twice, then removed through a snapshot-fenced `IWorkflowDispatchDeleteStore.TryDeleteAsync` so it cannot race a redrive. Any read failure retains the record. It never cascades. Cursor positions are kept per persistence partition, so a host running one sweep per scope does not carry one scope's position into the next.
- **Current effect:** **it deletes nothing today.** Elsa does not yet delete workflow executions, so no dispatch record ever has both linked executions absent. It is the dispatch half of the workflow-execution retention planned in [#1770](https://github.com/elsa-workflows/elsa-foundation/issues/1770).
- **Known gap before scheduling it:** a `DispatchFailed` record has no child execution, so it becomes eligible as soon as its parent is gone, while a redrive, which does not depend on the parent, may still be wanted. #1770 must settle a rule for records awaiting redrive before this is wired to a pump.

### `IRuntimeResumptionService` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Replacement (one service owns a single system-wide resumption sweep pass for a runtime composition).
- **Signature:** `SweepAsync(RuntimeResumptionSweepRequest request, CancellationToken cancellationToken = default)`.
- **Usage:** one sweep pass re-delivers stranded post-commit outbox items system-wide (`ProcessAsync(workflowExecutionId: null, intentKind: null)`) across all contributed kinds, unions durable scheduler-queue backlog (`IWorkflowSchedulerWorkQueue.ListClaimableWorkflowExecutionIdsAsync`) with `IRuntimeRecoveryScanner` candidates, and re-drives each discovered execution by enqueueing a `RunSchedulerWork` envelope through the actor mailbox — preserving single-writer discipline. Backlog discovery lists only executions whose work is claimable now and walks the backlog from a position kept between sweeps (`RuntimeResumptionDiscoveryStateStore`). Every candidate, backlog, recovery-scanner or sourced, is re-driven only when the drainer's `IWorkflowSchedulerPauseGate` would let its next queued item advance (re-driving a held one only left another `RunSchedulerWork` row behind the paused head); a held recovery or sourced candidate still counts as dealt with, a held terminal execution is still purged and reaped, and the next pass after a hold is lifted re-drives it. When the gate cannot be consulted the execution is not re-driven, since its drain would consult the same gate; a recovery candidate then keeps the scan cursor in place, and the sweep logs one aggregated warning (event `RuntimeResumptionPauseCheckFailed`). So neither hidden work, paused work, nor a fixed set of executions can hold the window (#2188). Next items are read with `IWorkflowSchedulerWorkQueue.ListNextWorkItemsAsync`, one request per page. The service requires the pause gate and the discovery state store. A queue without claimable discovery keeps the earlier first-page listing and the sweep warns once per queue type per host (event `RuntimeResumptionFirstPageBacklogDiscovery`). The request bounds each sweep (`MaxExecutionsPerSweep`; the recovery scanner keeps half of it, at least one slot, the backlog the rest, either side may use what the other leaves, and a cap of one alternates) and skips executions the caller is backing off (`ExcludedWorkflowExecutionIds`). Re-drive failures surface on the result and do not abort the sweep; callers own logging and backoff. It is not registered by the runtime API feature — only the `WorkflowsRuntimeResumption` shell feature registers it and drives it from a recurring pump.
- **Default implementation:** `RuntimeResumptionService` *(registered by the feature-gated `Elsa.Workflows.Runtime.Resumption` package)*. It also re-drives the candidates every registered `IRuntimeRecoveryCandidateSource` supplies, beside the backlog, and settles those it dealt with.

### `IWorkflowTriggerBindingStore` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Replacement (one provider owns the durable trigger-binding index for a runtime composition).
- **Signature:** `SaveAsync(...)`, `ListByStimulusAsync(WorkflowTriggerBindingPageQuery, ...)`, `ListByStimulusTypeAsync(stimulusType, ...)`, `ListByArtifactAsync(artifactId, ...)`, `DeleteByArtifactAsync(artifactId, ...)`, `ListActiveStimulusHashesAsync(stimulusType, ...)` *(#2190)*; the activation-scoped `PrepareActivationAsync`, `ActivateAsync`, `DeleteByActivationAsync`, `ListByActivationAsync`, `FindActivationStateAsync(activationId, ...)` and `ListServingActivationIdsAsync(slotId, ...)` *(#2193)*.
- **Usage:** stores `WorkflowTriggerBinding` documents mapping a stimulus identity to a start-trigger inside a published artifact. `ListByStimulusAsync` is the finite, continuation-bearing cross-artifact lookup over active bindings with an exact stimulus type/hash; `ListAllByStimulusAsync` traverses those bounded pages for business operations that must fan out to every match. `ListByStimulusTypeAsync` is a type-scoped full scan (no hash) used to rebuild a per-shell projection over one stimulus family (e.g. the HTTP route table); `by-artifact` scoping supports republish replacement. `ListActiveStimulusHashesAsync` reduces the `ListByStimulusTypeAsync` population to its distinct stimulus hashes, so a node can notice that another node changed the projection's source without re-reading every binding (the HTTP route-table convergence check). A store answers it without materializing bindings: `EfWorkflowTriggerBindingStore` projects the hashes from the covering index `IX_elsa_runtime_trigger_binding_route_convergence` (on MySQL, which cannot hold that index, with one row lookup per active binding of the type), with the exact-identity lookup key in the `DISTINCT` so a case-insensitive collation cannot fold two hashes together.
- **Activation scope:** `ActivateAsync(activationId, replacedActivationId)` must be idempotent in every order: once the candidate serves and its replaced activation is switched off, a further call is a no-op success, whoever made the switch. That holds for calls that overlap, not only for calls in sequence: two calls can switch the same activation at once ([#2265](https://github.com/elsa-workflows/elsa-foundation/issues/2265)). A store that reads a projection in more than one statement must not take a switch another call committed between them for a corrupt projection or for a replaced activation that no longer serves. The EF stores read each projection state again once they have read its rows, and decide only when no state moved. Every write that changes whether a row serves, or the projection's immutable content, moves the state in the transaction that writes the rows (preparing, switching and deleting a projection create, move or delete its state), so rows read while it stood still belong to it. A state is compared by its revision and its projection fingerprint, because a projection deleted and prepared again restarts at the creation revision: one prepared again with other content reads as moved, and its rows are never taken for the first one's. Writes that move no state change nothing a projection check compares and move their row's own revision: the recurring-schedule store's occurrence claims, renewals, settlements and releases and its single-schedule delete, and the trigger-binding store's `SaveAsync`, which serves the artifact-scoped index. A switch whose write loses to another's revision, or that the provider chose as a deadlock victim, reads again in a new transaction and finds the switch made. A store's own `ActivateAsync` retries within `EfWriteRetry`'s default attempt budget, and `IWorkflowActivationSwitch` within `WorkflowActivationSwitchRules.MaximumAttempts`, after which either fails with "changed concurrently; retry the operation", or with "encountered a transient write conflict; retry the operation" when its last attempt was a deadlock victim. The trigger-binding store's `FindActivationStateAsync` reads again under the same budget and then fails with "changed concurrently; retry the operation"; it reports rows that disagree with their state as corrupt (`InvalidDataException`) only when the state stood still while they were read. Check the candidate before the replaced activation. While the candidate is not yet serving, every store, the in-memory ones included, must refuse a replaced activation that no longer serves, so a switch never leaves two activations serving one slot. The activation lifecycle switches these projections through `IWorkflowActivationSwitch`, in the commit that moves the slot (#2230); a store whose backend ships a switch stages the same rules inside that commit. A candidate that serves beside a replaced activation that still serves is refused too. `PrepareActivationAsync` must refuse an activation whose projection serves or has served and is still stored, so a retry after a compensation that could not delete it fails loudly instead of reusing a projection that reads as `Replaced`. `FindActivationStateAsync` reports `Missing`, `Prepared` (never served), `Active`, or `Replaced` (served, then switched off by its replacement) for one activation, and must answer for an activation with no bindings. The EF stores derive `Replaced` from the projection state's revision through `ActivationProjectionStateLifecycle`: a state is created at `CreationRevision`, only `ActivateAsync` advances it, and the revision, also the row's concurrency token, never moves back. `ListServingActivationIdsAsync` lists the activations with an active binding minted for a slot, whatever their references say; the EF store reads the scope's active bindings to answer it, since no index covers the slot, and only deactivation and the repair of a slot left half done call it. `FindActivationStateAsync` and `ListServingActivationIdsAsync` have no default implementation.
- **Default implementation:** `InMemoryWorkflowTriggerBindingStore` *(single-node in-memory default; `EfWorkflowTriggerBindingStore` replaces it for durable storage over the `workflowTriggerBinding` document kind)*.

### `IStimulusRouter` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Replacement (one routing spine turns an external stimulus into starts and/or resumes).
- **Signature:** `RouteAsync(StimulusDispatchRequest request, CancellationToken cancellationToken = default)`.
- **Usage:** the E3-1/E3-5 spine. Snapshots the cross-execution resume set before starting new instances, starts matching published triggers, and resumes each waiting instance through the actor mailbox. Stimulus payload and trigger-node identity travel on reserved durable channels and are delivered through typed invocation/trigger contracts; they never enter the author workflow-input bag or an ambient expression context. Optional matched bindings and dispatch options are forwarded across both fan-out paths.
- **Start-once for keyed requests (#2195):** a request that carries an `idempotencyKey` starts each matching workflow as a keyed start (`KeyedWorkflowStartIdentity`, key `{idempotencyKey}:start:{artifactId}`), so a redelivery on any node, before or after a restart, names the same workflow execution and is reported as `SkippedDuplicate`. A recurring-trigger occurrence of a publication slot is routed with `StimulusStartKeyScope.Occurrence` (#2198): its key already names the trigger across publications, so its start is keyed without the artifact (`KeyedWorkflowStartIdentity.ForOccurrence`, start key `{occurrenceKey}:start`), and the start dispatcher answers an existing execution of that occurrence as the duplicate whichever artifact it is pinned to. Such a request must be `StartOnly`, carry its key and pre-match its binding, and the router refuses it when more than one binding matches, rather than letting the second silently never start. This is durable: it rests on the start dispatcher reading execution state, not on process memory. It replaced the in-memory `IStimulusStartDeduplicator`, which recorded a key before the start was dispatched and so turned the retry of a failed start into a silent skip. A request without a key is still plainly at-least-once and **may double-start**.
- **Behaviour change for reused keys:** because the dedupe is durable, reusing an idempotency key on `POST /runtime/workflows/stimuli` for the same artifact yields `SkippedDuplicate` **permanently**, across restarts and on every node, not only for the lifetime of one process. A caller that wants a second start must send a new key. A recurring-trigger occurrence (key built by `RecurringTriggerSchedule.BuildOccurrenceKey`) is likewise started at most once, durably, however often that occurrence is fired; the recurring-trigger pump relies on this, since it fires each occurrence at least once (#2198).
- **Frozen identity formats:** keyed start ids are `wfexec:start:{version}:{digest}`, `command:start:{version}:{digest}` and `envelope:start:{version}:{digest}`, where the digest is the lowercase hex SHA-256 of the values `"elsa.workflow-start"`, the version and the start key, each value's UTF-8 bytes prefixed by its 4-byte big-endian length. Version `v1` (`KeyedWorkflowStartIdentity.For`) has the start key `{idempotencyKey}:start:{artifactId}`. Version `v2` (`KeyedWorkflowStartIdentity.ForOccurrence`, #2198), used only for a recurring occurrence of a publication slot, has the start key `{occurrenceKey}:start`, where the occurrence key is `recurring:{slotId}:{executableNodeId}:{stimulusHash}:{occurrenceTicks}` with each id escaped (`%` as `%25`, `:` as `%3A`); a recurring schedule without a slot keeps `recurring:{scheduleId}:{occurrenceTicks}` under `v1`. These ids are persisted and a redelivery is recognized only by deriving the same id again, so the derivations and the occurrence key are frozen: changing one silently starts every redelivered occurrence a second time. A change is a new version beside `v1` and `v2`; `KeyedWorkflowStartIdentityTests` pins the literals of both and of the occurrence key.
- **Default implementation:** `StimulusRouter`.

### `IRuntimeSecretResolver` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Replacement (framework §2.6.2), declared by `[RuntimeSecretResolverReplacementContract]`: at most one resolver per container. The runtime owns the contract, so it references no secrets module. The runtime registers no resolver. A second registration is detected at startup: `ActivitiesRuntimeFeature` (`Elsa.Activities.Runtime`) registers a shell initializer that fails shell activation with `MultipleRuntimeSecretResolversException` when the composed services hold more than one, whichever order they were registered in, so a second one never wins by registration order. Activation consumes the single optional resolver. The feature that registers one (the Secrets bridge, slice 4) also refuses one registered before it, as an early diagnostic.
- **Signature:** `ResolveAsync(RuntimeSecretResolutionRequest request, CancellationToken cancellationToken)` returns `RuntimeSecretResolution`. The request carries `TenantId` and a `RuntimeSecretReference` (name, optional type name and scope). The result is `RuntimeSecretResolution.Success(value)` or `RuntimeSecretResolution.Failure(failureCode, isRetryable)`; a failure code is a code name of ASCII letters and digits, never the store's error text. `RuntimeSecretResolution` is a class rather than a record, and its `ToString()` prints only the outcome (`Succeeded`, or the failure code and retry classification), never the value.
- **Usage:** `ActivityActivator` (`Elsa.Activities.Runtime`), through `ActivitySecretInputResolver`, calls it when a hydrating activation meets a withheld `SecretReference` input, on every such activation: invoke, bookmark resume, structural parent evaluation and the re-materialized child-completion activation. The tenant is the execution partition read at activation (`IWorkflowExecutionPartitionAccessor`), which is the scope the instance's own rows are stored under; on the background drain path, where the scheduler work handlers get no ambient services, that is the host's persistence scope (spec 188 research R2); no binding, payload, setting or default selects it, and a global or across-scope context is refused before any call. When the instance records a tenant, it must match that partition, or activation refuses with `TenantMismatch` and the resolver is never called. A snapshot without a withheld secret calls nothing and reads neither the partition nor the instance. The resolved text is converted with the conversion plan the withheld envelope carries, hydrated into the activity, and never written back to state; nothing is cached, so a rotated secret takes effect at the next activation. A resolver returns a failure for every domain outcome and throws only `OperationCanceledException` when the caller cancels; whatever it throws or reports after the activation was canceled is treated as the cancellation, and anything it throws while the activation's token is live (a cancellation-typed exception from its own timeout included) or a null result is dropped and reported as `ResolverFailed` (permanent), so its message never reaches a fault. Classifying a failure is the resolver's obligation: activation copies `IsRetryable` into the fault unchanged, and only `StoreUnavailable` may be retryable.
- **Typed failures:** `RuntimeSecretResolutionException` *(`Elsa.Workflows.Runtime.Core.Exceptions`)* faults the activity with the message `Secret '<name>' could not be resolved (<code>).`, carrying no value, and implements `IRuntimeFaultClassification`. Its code is the resolver's failure code, `TenantMismatch`, `ResolverFailed` when the resolver throws, or `ConversionFailed` when the resolved text cannot be converted with the pinned plan (or the envelope carries none). `RuntimeSecretResolverNotFoundException` means the host composes no resolver: `ActivityActivationFailureHandler` classifies it as activation-failure kind `MissingSecretResolver`, so the activity waits with an `ArtifactActivationFailed` incident (recovery `CorrectDeploymentAndResume`) instead of faulting (constitution §E2.6.1). `MultipleRuntimeSecretResolversException` is the startup diagnostic for a host that composes more than one resolver: it fails shell activation and names every registration (implementation type, registered instance's type, or "a factory registration") and nothing else. It is never thrown at activation and is not an activation failure.
- **Default implementation:** none in the runtime.
- **Known implementations:** `SecretValueRuntimeResolver` *(cross-domain, `Elsa.Secrets.Workflows`, feature `SecretsWorkflows`)*, over the Secrets module's `ISecretValueResolver`. Its registration throws, naming both, when another `IRuntimeSecretResolver` is already registered; one registered after it fails shell activation as above. See [`Elsa.Secrets.Workflows/README.md`](../../Secrets/Workflows/README.md).

### `IRuntimeAdmissionLoadSignal` / `IRuntimeAdmissionController` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Replacement pair for dispatch admission control (RB1, #1235): the load signal owns the in-flight measurement and its reservation, the controller owns the admit-or-shed decision and the adaptive limit.
- **Signature:** `TryOpenCharge(double limit, out long observedLoad)` is one atomic compare-and-reserve on the gated path; `OpenCharge()` opens a charge unconditionally, for the paths the controller has already decided are not subject to the limit; `RecordDispatch()` weights the ambient charge one unit per scheduler dispatch. `IRuntimeAdmissionController.TryAdmit()` returns an admitted decision carrying the charge and a completion callback, or a shed carrying observed load, limit, and retry-after.
- **Usage:** the default scheduler command router gates externally arriving live work through a router-internal deny-list predicate (change which kinds are gated by replacing the scoped router via `IWorkflowExecutionCommandExecutor`, not through a seam of its own). Recovery and control-plane commands (`RunSchedulerWork`, `Cancel`, `PauseWorkflowExecution`, `UnpauseWorkflowExecution`) bypass admission: the sweep carries its own bound (`RuntimeResumptionOptions.MaxExecutionsPerSweep`) and refusing an operator's cancel at capacity would remove the tool for ending the overload. `AlterWorkflow` **is** gated (#1325): the gate sits above the alteration hand-off, so an alteration is now a **sheddable, counted-as-one** command and a dispatch nested inside it takes the ambient-charge path. It is counted as one and no more — an alteration holds the seed unit every admitted command pays for as long as its actor call runs, but performs no scheduler dispatches of its own (the product's only `RecordDispatch()` call site is in `WorkflowSchedulerDrainer`, which the alteration branch never reaches), so it accrues none of the per-dispatch units a `Start` does, flat regardless of plan size, and the scheduler work it commits is charged to whoever drains it next, which is never the alteration: the drain loop is per-execution and runs until the queue is dry, so under the exempt `RunSchedulerWork` that work stays uncounted, while under a subsequently admitted live command (a `ResumeBookmark`, `Checkpoint`, `CompleteActivity`) its dispatches are charged to *that* command. Because it dispatches nothing, its completion is also excluded from the adaptive sample (`ChargedUnits <= 1`), so its sub-millisecond exits cannot collapse the latency baseline. It is the one gated kind besides `Start` whose refusal writes nothing: parking an `AlterWorkflow` work item would hand it to `NoopWorkflowSchedulerWorkHandler`, which matches every kind except `InvokeActivity`/`GeneratedEvent`/`ResumeBookmark` and silently drops it (`ContinueVolatileWait`, `DeliverSignal`, and — in the core composition, whose handler comes from `ActivitiesRuntimeFeature` — `NotifyParentActivity` share that handler-less property and have no faulting fallback either; latent as router envelopes only because nothing constructs them as such). The outright refusal is safe because the alteration pump (`WorkflowAlterationOrchestrationPumpTask`, registered by `AddWorkflowRuntime` itself rather than by any opt-in feature, though as an `IRecurringTask` it runs only where the Tasks domain schedules it — and it is also the only producer of `AlterWorkflow` envelopes, so a host that does not run it cannot reach the refusal) re-claims the job once its lease lapses: a full `WorkflowAlterationOrchestrationOptions.JobLeaseDuration`, **1 minute by default**, against a `RetryAfter` in seconds. Parking on shed is conditional on a re-driver being composed (**#1320**): the router reads the injected `IEnumerable<IWorkflowDispatchDurabilityEvidence>` once when it is constructed — once per dispatched command, since it is scoped — and parks only when some evidence names `WorkflowDispatchDurabilityComponents.Resumption`, which in the product only `WorkflowsRuntimeResumptionFeature` contributes and `AddWorkflowRuntime` does not. Without it every gated kind takes the start-shaped refusal — shed, nothing written, and (because the agent consumes the idempotency key off `ShedWorkQueued` rather than off the kind) the key left intact so the caller's retry is honest — instead of promising a delivery no sweep would perform. The check is on the component *name*, not on its durability level, so a process-local re-driver would count too; an absent enumerable reads as "no re-driver", which is the conservative direction for a router composed by hand. What the evidence establishes is that the sweep is **registered**, not that it runs — the same caveat the alteration pump carries above, since `RuntimeResumptionPumpTask` is likewise an `IRecurringTask` and runs only where the Tasks domain schedules it: a host calling `WorkflowsRuntimeResumptionFeature.ConfigureServices` directly with no Tasks host contributes the evidence, parks, and never sweeps, which is #1320 again in a composition this rule reads as safe (a shell-composed host does not, that feature declaring `DependsOn = { "Tasks" }`). The refusal itself is reached by hand-composed and in-memory hosts — those composing `AddWorkflowRuntime` / `WorkflowsRuntimeApi` and no resumption feature — and not by a shell composing the durable runtime-store persistence features, since all nine of those declare `DependsOn = { "WorkflowsRuntimeResumption" }` (the distributed-placement feature does not, but it leaves the scheduler queue in-memory, so such a shell does reach the refusal). On a host composing no alteration executor at all, an `AlterWorkflow` arriving at capacity is refused before the router's "alterations are not composed" throw; that masks a composition error behind a retryable refusal only in principle, since one registration composes both that executor and the pump that is the only producer of `AlterWorkflow` envelopes. The default signal meters **dispatches, not commands** — an External-leaf run pays ~56 dispatches where a fusable run pays ~5, so a command-count limit would under-report exactly the shape production traffic has.
- **Safety:** a replacement signal must keep compare-and-reserve atomic; a separate read followed by a reserve lets N simultaneous callers all observe the same below-limit load and all pass, which is the burst the limiter exists to stop. `InFlightDispatches` must also remain a cheap, always-safe read: the controller reads it on the exempt paths (admission disabled, ambient charge), so the property may not throw or block. A replacement charge must also **seed at one unit** on admission and add one per `RecordDispatch()`: the controller reads `ChargedUnits <= 1` as "this command dispatched nothing" and excludes that completion from the adaptive sample (#1325), so a charge seeding at zero makes every single-dispatch command report one and silently drops those completions from the sample, biasing it toward heavier commands. Adaptation keeps running on everything that dispatched twice or more, which is why the miscalibration surfaces as drift rather than as an error. The adaptive controller and the `StaticLimit` operator override share one code path (the override clamps the adaptive range to a single value), so a replacement must not fork them.
- **Default implementations:** `DispatchRuntimeAdmissionLoadSignal` and `RuntimeAdmissionController`, both `TryAdd`-registered singletons.

### `IWorkflowDrainOrchestrator` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Replacement (one coordinator owns command-triggered workflow execution drain orchestration for a runtime composition).
- **Signature:** `DrainAsync(WorkflowExecutionCommandEnvelope envelope, RuntimeSchedulerDrainRequest request, CancellationToken cancellationToken = default)`.
- **Usage:** bridges the accepted command boundary to scheduler draining after scheduler work is recorded and the drain policy requests immediate advancement. The default coordinator drains scheduler work, processes deliverable `RuntimePostCommitIntentKinds.EnqueueSchedulerWork` outbox items for the same workflow execution, and repeats scheduler draining until scheduler-intent delivery quiesces, a pause/fault stops scheduler draining, or the bounded cycle guard is reached. While ownership is active it renews the lease at one-third of the acquired lease duration. For scoped persistence, each renewal resolves the configured ownership service in a fresh `IPersistenceOperationScopeFactory` scope bound to the command envelope's partition; the foreground scope remains responsible for acquisition, checkpoint work, and release. Each renewal scope is disposed before the next cadence, and cleanup stops and awaits renewal before releasing with a non-cancelable token. A rejected or failed heartbeat cancels the drain and surfaces `RuntimeExecutionOwnershipLostException`. Checkpoint commit remains the durability boundary: commits record post-commit work, and the coordinator only delivers it after the commit path succeeds. `WorkflowDrainOrchestratorOptions` names the cycle and outbox batch limits; cycle-cap exhaustion throws `DrainCycleLimitExceededException`.
- **Quiescence means the drain's own continuations are delivered and drained (#2225).** The resumption sweep claims across every execution, so it can take a continuation between the drain's commit and its delivery step; the step then delivers nothing, or reports the item superseded. Before the coordinator reports `Quiesced` it therefore asks the outbox store which of the execution's `EnqueueSchedulerWork` items another deliverer holds or has failed (`IRuntimePostCommitOutboxClaimStore.ListClaimedAsync`). It waits for those deliveries to finish, polling with backoff from 10 ms to a 500 ms cap and never past the earliest claim's lapse; it claims a lapsed item itself through the durable claim path and delivers it; and it then drains the work the other deliverer queued, since it still holds the execution's lease. A delivery the other deliverer completed before the drain's read leaves only queued work, so after a scheduler drain that ran items and stopped neither on a terminal status nor at its work-item budget the coordinator also checks the execution's queue. The waiting is bounded by `WorkflowDrainOrchestratorOptions.ContinuationClaimWaitLimit`, one deadline per drain request that starts at the first wait (default `RuntimePostCommitOutboxProcessing.ClaimVisibilityTimeout` plus `ContinuationClaimWaitMargin`, 90 seconds). When the deadline passes, or the other deliverer's attempt failed (`FailedRetryable` listed, or an awaited item that ended failed), the drain stops with `OutboxDeliveryFailed`, as for a failed delivery of its own, so the command answers `AcceptedButFaulted` rather than `Accepted`; the durable item stays with its claimant and then the sweep. `EnqueueSchedulerWork` retries (`RuntimeSchedulerPostCommitIntentDispatcher.RetryPolicy`, four attempts one second apart), so every failed attempt but the last is `FailedRetryable` and listed: a transient failure on another deliverer ends the drain with `OutboxDeliveryFailed` whenever it happened, and the sweep delivers the retry once its delay has passed. The drain does not wait for that retry. A failure of the drain's own delivery in an earlier cycle ends it only while the item is still undelivered: if the claim-free retry in a later cycle delivered it, the drain quiesces. One case stays open: a continuation whose attempts were all made, and all failed, by other deliverers before the drain's first read is `FailedFinal`, is not listed, and the drain still reports `Quiesced`. The attempts are at least the retry delay apart, so that takes a drain whose first read comes more than three retry delays after the commit that recorded the continuation, with another deliverer re-attempting the item as each delay passes; one sweeper re-attempts it at most once per pass. Listing terminal failures would fault every later drain of the execution, and skip incident resolution, for good; telling this drain's failure from an older one needs a clock comparison or a read at the start of every drain. Cancelling the drain's token, or losing its lease, ends the wait with the drain's usual cancellation. The outbox claim store, the outbox lookup store and the scheduler work queue are required constructor parameters, so no composition can build a drain that skips this check.
- **Default implementation:** `WorkflowDrainOrchestrator`.

### `IDurableTimerStore` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Replacement (one store owns durable timers for a runtime composition).
- **Signature:** `SaveAsync(DurableTimer timer, ...)`, `FindAsync(string workflowExecutionId, string timerId, ...)`, `DeleteAsync(string workflowExecutionId, string timerId, ...)`, `ListDueAsync(DateTimeOffset now, int limit, ...)`.
- **Usage:** persists `DurableTimer` records (a due-time-indexed document kind, `durableTimer`) keyed by `(WorkflowExecutionId, TimerId)`. `SaveAsync` is a deterministic upsert so a pre-commit crash re-executing the owning activity re-writes the same timer rather than duplicating it. `ListDueAsync` returns timers with `DueTime <= now`, ordered by `(DueTime, TimerId)`, capped at `limit`; the durable timer pump (`DurableTimerPumpTask`) drains this and fires each due timer through `IBookmarkResumeDispatcher`. With claim transitions, the pump fires each claimed timer under the shared `FencedClaimLease` rule (#2195): the claim is renewed immediately before the fire and kept renewed while it runs, and a timer whose claim was lost, before, during, or at its completion or release, is logged and skipped without ending the sweep. The pump owns idempotency: it deletes a timer on `Dispatched`/`Duplicate` (the resume is durably enqueued into `IWorkflowSchedulerWorkQueue` before the dispatcher returns — see `WorkflowSchedulerCommandRouter.ProcessAsync` — so deletion cannot lose the resume), and treats a past-grace `NotFound` as an already-consumed bookmark.
- **Default implementation:** `InMemoryDurableTimerStore` *(single-node in-memory default; Delay works but is **not** restart-durable without a durable store)*. `EfDurableTimerStore` *(durable `IDocumentStore`-backed bridge; swapped in by `AddRuntimeEntityFrameworkCore`)*.
- **Follow-ups (W8):**
  - **Native due-time range index.** `MaxTimersPerTick` bounds the *dispatch* burst, not the *load*; a native range index on `DueTime` is the scale follow-up.
  - **Timer/Cron start triggers** (recurring schedules that *start* a workflow) ship via a **dedicated recurring-trigger schedule store + pump** (see `IRecurringTriggerScheduleStore` / `IRecurringTriggerScheduleProvider` below and the `WorkflowsRuntimeRecurringTriggers` feature), **not** the `durableTimer` store. Rationale: the durable-timer pump resumes an *existing* execution (it has a `WorkflowExecutionId`); a start trigger has none, so it needs the trigger/stimulus router (W7) to *start* a workflow. The `durableTimer` kind therefore remains resume-only.
  - **Atomic timer registration (Option B).** Delay registers its timer activity-side, strictly before the bookmark (so "bookmark committed, timer missing" is structurally excluded). A fully atomic timer==bookmark lifecycle via a post-commit `RegisterDurableTimer` intent (`IRuntimePostCommitIntentDispatcher`) is the alternative if orphaned timers ever prove noisy.

### `IRecurringTriggerScheduleStore` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Replacement (one store owns recurring-start schedules for a runtime composition).
- **Signature:** `SaveAsync(RecurringTriggerSchedule schedule, ...)`, `FindAsync(string scheduleId, ...)`, `DeleteByArtifactAsync(string artifactId, ...)`, `DeleteAsync(string scheduleId, ...)`; activation-scoped projection: `PrepareActivationAsync`, `ListByActivationPageAsync`, `ListByArtifactPageAsync`, `ActivateAsync(string activationId, string? replacedActivationId, ...)`, `DeleteByActivationAsync`, `FindActivationStateAsync(activationId, ...)` and `ListServingActivationIdsAsync(slotId, ...)` *(#2193)*, with the same activation-scope obligations as `IWorkflowTriggerBindingStore`; occurrence claims (#2198): `ClaimDueAsync(RecurringTriggerOccurrenceClaimRequest request, ...)`, `RenewClaimAsync(RecurringTriggerOccurrenceClaim claim, DateTimeOffset now, TimeSpan visibilityTimeout, ...)`, `SettleClaimAsync(RecurringTriggerOccurrenceClaim claim, DateTimeOffset nextOccurrence, ...)`, `ReleaseClaimAsync(RecurringTriggerOccurrenceClaim claim, DateTimeOffset visibleAt, ...)`. The due listing (`ListDueAsync`) and the plain cursor compare-and-swap (`TryAdvanceAsync`) are gone: the pump reads due occurrences only by claiming them, and an advance that is not a settled claim is what lost occurrences.
- **Usage:** persists `RecurringTriggerSchedule` records for Timer/Cron **start** triggers — the recurring-start counterpart to `IDurableTimerStore` (which is resume-only). `SaveAsync` is an idempotent upsert keyed by `ScheduleId`. Workflow activation (`WorkflowActivationCoordinator`: `IWorkflowTriggerIndexer.PrepareActivationAsync`, which prepares the schedules through `RecurringTriggerScheduleIndexer`, then `ActivateAsync`) is the production republish path; legacy artifact-scoped indexing replaces an artifact's schedules via `DeleteByArtifactAsync` + re-save, and `RecurringTriggerScheduleIndexer` then carries over a cursor whose occurrence is already due. The recurring-trigger pump (`RecurringTriggerPumpTask`, `WorkflowsRuntimeRecurringTriggers` feature) fires the trigger stimulus through `IStimulusRouter`.
- **Delivery guarantee — at least once per occurrence, one start (#2198):** the pump records each due occurrence as in flight before it routes it: `ClaimDueAsync` takes a fenced claim (owner, fencing token, row revision) with a visibility lease of `RecurringTriggerPumpOptions.ClaimVisibilityTimeout` and leaves the cursor on the occurrence. The claim is renewed immediately before the route under the shared `FencedClaimLease` rule (not during it: the router's start dispatch shares the store's unit of work), and the cursor moves past the occurrence only through `SettleClaimAsync` once the route returned — or, for a Cron with no later occurrence, by deleting the schedule once its last occurrence was routed. A node that dies after claiming leaves the claim to lapse and a peer fires the occurrence again; a route that throws, or finds no binding owned by the schedule, is released with `ReleaseClaimAsync` and a geometric backoff, so it is retried rather than skipped. Every claim transition is a compare-and-set on owner, token and revision and on the stored schedule still being the one claimed, so any other change to the row (a peer's re-claim, a deactivation, a republish, a delete) makes the claim stale; a stale settlement or release is logged and skipped without ending the sweep. Fencing tokens increase with every claim of a schedule and are not reissued when a schedule is deleted and saved again later (the EF store counts a recreated schedule's tokens on from its creation instant; the in-memory store draws them from one store-wide sequence). Repeats are harmless because the pump routes each fire with the occurrence key `RecurringTriggerSchedule.BuildOccurrenceKey`, so the router starts it as a keyed start and a fire of the same occurrence repeated on any node, after a restart, or by the publication that replaced it converges on the execution the first fire started. **Republish:** `ActivateAsync` replaces the replaced activation's schedules in one write, and each activated schedule takes over the cursor of the replaced schedule of the same trigger (slot, trigger node, stimulus) when that cursor is earlier than its own and no later than the instant of the activation, read from the store's `TimeProvider` (`RecurringTriggerSchedule.TakeOverFrom`), so republishing does not skip a due occurrence; a claim in flight on the replaced schedule is stale from that write on. **Missed-occurrence policy:** settling advances the cursor to the first occurrence strictly after the sweep's now, so after downtime, or while a failing occurrence is retried, a schedule fires its due occurrence once and the elapsed backlog is never replayed. **Rolling deploys:** the claims and the start-once dedupe hold only among nodes at #2198 or later (keyed starts need #2195 or later); a node from before #2198 advances before it routes and keys its starts per artifact, so an occurrence may start twice while old and new nodes both run the pump (`docs/runtime-durable-timers.md`, *Rolling deploys*). **Replacement stores** must implement the claim transitions; the interface gives them no default body, so the pump has no at-most-once fallback. The EF store keeps the claim in its own operational columns beside the content document, so the schema family's content version is unchanged.
- **Default implementation:** `InMemoryRecurringTriggerScheduleStore` *(single-node in-memory default; start triggers work but are **not** restart-durable without a durable store)*. `EfRecurringTriggerScheduleStore` *(durable EF Core row store: one row per schedule, its content document beside relational lookup and ordering columns and the occurrence-claim columns, plus a projection-state row per activation; swapped in by `AddRuntimeEntityFrameworkCore`)*.

### `IIncidentStrategy` / `IIncidentResolutionAction` *(Core contracts; Runtime defaults)*

- **Kind:** Additive, versioned strategy extension. A published executable pins one exact
  `IncidentStrategyReference` (`Alias`, `Version`); Runtime never re-reads Design options or the host's current
  default while executing it.
- **Register:** call Runtime's `services.AddIncidentStrategy<TStrategy>(descriptor)`, or annotate the concrete strategy with
  `[IncidentStrategy(alias, version, ...)]` and call `AddIncidentStrategy<TStrategy>()`. Strategy implementations
  are scoped. Alias comparison is ordinal case-insensitive, version comparison is exact, duplicate identities
  fail, and custom aliases must be dotted. Discovery reads descriptors without constructing strategies.
- **Decision model:** `ResolveAsync(IncidentStrategyContext, CancellationToken)` receives immutable, policy-safe
  snapshots and returns one executable `IIncidentResolutionAction`. Actions execute against a guarded
  `IncidentResolutionActionContext`; they may transition only the target incident, request workflow faulting,
  add bounded outcome metadata, and request separately registered strategy-safe post-commit intents. They cannot
  mutate activities, retry/suspend/complete workflows, absorb/suppress structural faults, or access checkpoints.
  Incident metadata is projected through an explicit correlation/classification allowlist; exception messages,
  stack traces, payloads, variables, and private runtime state are excluded. Strategy-owned outcome and intent
  metadata is limited to 32 nonblank, control-character-free string pairs (128-character keys and 1024-character
  values).
- **Built-ins:** Runtime always registers `Fault/1` and `ContinueWithIncidents/1`. `Fault` keeps the incident
  blocking and faults the workflow. `ContinueWithIncidents` opens the incident while preserving the faulted
  activity and lets independent scheduled work finish.
- **Failure/replay:** null decisions, strategy failures, action failures, and invalid custom action kinds discard
  that action's staging and apply a fresh runtime-owned `FaultWorkflow` decision. All outcomes and permitted
  intents commit in one ordered end-of-drain checkpoint; a durable outcome prevents reevaluation. A missing pinned
  implementation before start records `WaitForIntervention` with `MissingStrategyImplementation`, leaves the run
  pending, and schedules no retry.
- **Safe intents:** register a third-party kind with `AddIncidentStrategySafeIntent(...)`. Runtime-control,
  scheduler, dispatch, stimulus, and retry kinds are rejected. Runtime derives intent identity, idempotency,
  timestamp, and workflow/activity correlation.

- **Default implementation:** `WorkflowSchedulerDrainer` *(contract-only drain boundary for the current runtime slice)*.

### `IWorkflowSchedulerPauseGate` *(Core — `Elsa.Workflows.Runtime.Core`)*

- **Usage:** maps supported scheduler command kinds to `RuntimePauseDecisionRequest` values and delegates to `IRuntimePauseDecisionProvider`. The default drainer peeks the next queued item, consults this gate, and stops without dequeuing when the decision blocks advancement.
- **Default implementation:** `WorkflowSchedulerPauseGate` *(maps `StartActivity`/`InvokeActivity` to `BeforeActivityExecutionStart` and `GeneratedEvent` to `BeforeGeneratorEmission`)*.

### `IWorkflowSchedulerDrainPolicy` *(Core — `Elsa.Workflows.Runtime.Core`)*

- **Usage:** command processing records scheduler work first, then asks this policy whether to drain. Returning `null` defers draining.

### `IWorkflowSchedulerDrainObserver` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Contributor (observers consume coordinated drain results produced by workflow execution draining).
- **Signature:** `OnDrainedAsync(WorkflowExecutionCommandEnvelope envelope, RuntimeSchedulerDrainResult result, CancellationToken cancellationToken = default)`.
- **Usage:** modules can project one command-triggered coordinated drain outcome into diagnostics or future checkpoint/outbox behavior without making history continuation state.   system incidents, resolves eligible ordinary activity-fault incidents once causal work is quiescent, and only

### `IWorkflowSchedulerWorkHandler` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Contributor (handlers consume drained scheduler work items).
- **Signature:** `Name`, `CanHandle(RuntimeSchedulerWorkItem workItem)`, `HandleAsync(RuntimeSchedulerWorkItem workItem, CancellationToken cancellationToken = default)`.
- **Usage:** modules can handle specific scheduler command kinds without replacing the drainer. The drainer evaluates ordinary handlers before fallback handlers.
- **Default implementations:** `WorkflowStartSchedulerWorkHandler` *(turns `Start` work into `ScheduleActivity` work for executable start nodes)*, `WorkflowScheduleActivitySchedulerWorkHandler` *(records `Scheduled` `ActivityExecutionState` and queues `StartActivity` work for one executable node)*, `WorkflowStartActivitySchedulerWorkHandler` *(transitions scheduled activity state to `Running` and queues `InvokeActivity` work)*, `WorkflowCompleteActivitySchedulerWorkHandler` *(drains deterministic activity completion work)*, `WorkflowCheckpointSchedulerWorkHandler` *(commits named checkpoint scheduler work through `RuntimeCheckpointCommitter`)*, `MissingActivityInvocationSchedulerWorkHandler` *(fallback that faults `InvokeActivity` when no provider is composed)*, `MissingBookmarkResumeSchedulerWorkHandler` *(fallback that faults `ResumeBookmark` when no bookmark resume provider is composed)*, `MissingGeneratedEventSchedulerWorkHandler` *(fallback that faults `GeneratedEvent` when no generated-event provider is composed)*, and `NoopWorkflowSchedulerWorkHandler` *(fallback that acknowledges drained work that has no required provider-specific handler)*.

`RuntimeSchedulerWorkHandlerBase<TPayload>` (project `Elsa.Workflows.Runtime`, same namespace) is the
optional dispatch scaffold for payload-typed handlers that also implement `IRuntimePipelineWorkHandler`:
it deserializes the payload once (throwing validation errors before any scope is created) and runs the
handler body against the pipeline's ambient services or a fresh scope. The fresh scope is bound to the
partition the dispatcher staged (`RuntimePipelineWorkspace.PersistenceScope`), so the body works in the
partition the work item belongs to; direct no-pipeline dispatch knows no partition and its scope carries
the host's persistence scope. A derivation supplies `Name`,
`CanHandle`, `DeserializePayload`, and `HandleWithServicesAsync`. Shipped derivations:
`WorkflowInvokeActivitySchedulerWorkHandler`, `WorkflowParentActivityCompletionSchedulerWorkHandler`,
`WorkflowNotifyParentActivitySchedulerWorkHandler` *(all cross-domain — `Elsa.Activities.Runtime`)*.
A handler that must not run in the drain's ambient services (the resume handler) implements the
interfaces directly: it always creates its own scope and takes only the staged partition from the workspace.

### `IFallbackWorkflowSchedulerWorkHandler` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Contributor marker (handlers consume drained scheduler work items only after ordinary handlers decline them).
- **Signature:** inherits `IWorkflowSchedulerWorkHandler`.
- **Usage:** modules can register catch-all scheduler work handlers without becoming priority handlers. The default drainer evaluates these handlers after ordinary `IWorkflowSchedulerWorkHandler` registrations.
- **Default implementation:** `NoopWorkflowSchedulerWorkHandler`.

### `IWorkflowExecutableStore` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Replacement (one store owns runtime executable artifact lookup for a runtime composition).
- **Signature:** `SaveAsync(WorkflowExecutable executable, ...)`, unconditional `DeleteAsync(string artifactId, ...)`, guarded `DeleteAsync(WorkflowExecutableDeletionGuard, now, ...)`, root-write lease acquire/renew/release, deletion-guard begin/cancel, `FindAsync(string artifactId, ...)`, and `ListAsync(...)`.
- **Usage:** stores and retrieves runtime-owned immutable `WorkflowExecutable` artifacts by content-addressed artifact ID. Publishing writes artifacts through this contract; runtime start, resume, and scheduler paths read them without loading Design-owned workflow state. Mutable source-reference publication, retirement, scope, and expiry checks remain outside this store and authoritative.
- **Default implementation:** `InMemoryWorkflowExecutableStore` *(single-process default)*. The EF Core module supplies `EfWorkflowExecutableStore` as a keyed backend; SQLite reference features select a bounded `CachingWorkflowExecutableStore`, while PostgreSQL/distributed and legacy direct registrations preserve direct reads by default. The cache coalesces same-ID misses, retains only positive provider results, invalidates on save/unconditional delete and successful guarded delete, and never populates from `ListAsync`. Root-write lease and deletion-guard transitions pass through to the provider unchanged; custom providers can replace the keyed backend without a concrete dependency.
- **EF Core implementation:** `EfWorkflowExecutableStore` *(opt-in `WorkflowsRuntimeArtifactsEntityFrameworkCorePersistence`; provider contexts and entities are owned by the Runtime persistence leaf)*.
- **Durable-provider controls:** `CacheWorkflowExecutables` defaults to `true` for SQLite and `false` for PostgreSQL/distributed features; `WorkflowExecutableCacheCapacity` defaults to `256` positive artifacts per shell/provider. Disable caching to restore direct durable reads. Telemetry reports bounded hit/miss, eviction reason, and provider-load outcome/duration dimensions without workflow or artifact IDs. Cache state and mutation invalidation are process-local; PostgreSQL hosts must explicitly opt in with an accepted immutable-retention/invalidation policy.

### `WorkflowExecutableStoreDecorator` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Derivation base (pass-through decorator scaffold over `IWorkflowExecutableStore`).
- **Signature:** every `IWorkflowExecutableStore` member as a `virtual` forward to the wrapped store, exposed through the protected `Inner` property.
- **Usage:** derive and override only the operations the decorator intercepts; everything else forwards unchanged. `CachingWorkflowExecutableStore` (read caching + mutation invalidation) and `InvalidatingWorkflowExecutableStore` (mutation invalidation with direct reads) are the shipped derivations.

### `IExecutableActivityTemplateStore` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Replacement (one store owns immutable, content-addressed executable templates for reusable activity versions).
- **Signature:** find by template id or behavior hash, list, save, and delete unreferenced templates.
- **Usage:** Publishing compiles provider-neutral activity versions into `ExecutableActivityTemplate` artifacts. Workflow artifacts pin exact template identities and closed dependency sets; Runtime loads only these artifacts and never falls back to Design state. Equal canonical behavior can share a template even when source version labels differ.
- **Default implementation:** `InMemoryExecutableActivityTemplateStore`; the EF Core module replaces it for durable hosts.
- **EF Core implementation:** `EfExecutableActivityTemplateStore` *(opt-in `WorkflowsRuntimeArtifactsEntityFrameworkCorePersistence`; provider contexts and entities are owned by the Runtime persistence leaf)*.

### `IWorkflowExecutableSourceReferenceStore` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Replacement (one store owns source/version/publication references to content-addressed workflow and activity artifacts).
- **Signature:** find/list by source reference or artifact, save, retire/restore, delete, and discover unreferenced artifacts. `TryDeleteDoomedAsync(snapshot, now, ...)` is the compare-and-delete the garbage collector uses: it removes a reference only while the stored row still matches the snapshot and is still retired or expired, so a reference restored after the sweep's listing survives. There is no unconditional hard delete on the contract, and implementations must provide it.
- **Usage:** keeps mutable lifecycle, retention, expiry, and layout sidecars outside immutable behavior artifacts. Source-owned CLR reconciliation creates a distinct source reference per definition version even when versions share one template hash. Runtime start pins the exact referenced artifact; garbage collection follows live references.
- **Default implementation:** `InMemoryWorkflowExecutableSourceReferenceStore`; the EF Core module replaces it for durable hosts.
- **EF Core implementation:** `EfWorkflowExecutableSourceReferenceStore` *(opt-in `WorkflowsRuntimeArtifactsEntityFrameworkCorePersistence`; provider contexts and entities are owned by the Runtime persistence leaf)*.

### `IActivityExecutionHierarchyStore` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Replacement read/write surface for checkpoint-committed activity execution hierarchy and composite-boundary layout.
- **Signature:** write `ActivityExecutionHierarchyRecord`; read cursor-paged descendants, boundary metadata, pinned execution layout, and previous/next attempt navigation by workflow/activity execution identity.
- **Usage:** preserves one workflow execution while making reusable composite boundaries navigable. Inspection clients can click through a graph activity into its full descendant execution graph and complete pinned structural layout, including authored nodes that did not execute, without loading authored Design documents. Boundary lifecycle remains separate from descendant aggregate state. Records are checkpoint-gated and use ordinary activity execution identities/scopes; there is no special “custom activity” scope and no child workflow identity.
- **Default implementation:** `RuntimeInMemoryActivityExecutionHierarchyStore`; the EF Core module replaces it for durable hosts. Opaque page cursors are encoded by `IActivityExecutionHierarchyCursorCodec`.
- **EF Core implementation:** `EfActivityExecutionHierarchyStore` *(opt-in `WorkflowsRuntimeActivityExecutionEntityFrameworkCorePersistence`;)*.

Cursor failures carry the cursor class, boundary/query/access binding results, and a recoverable restart action. Authorization-profile changes invalidate issued cursors but do not alter committed hierarchy history.

`ExecuteWorkflow` remains a separate explicit operation for starting another workflow. It does not use the reusable activity template/hierarchy boundary to disguise a child workflow as an activity.

### `IRuntimePipelineWorkHandler` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Contributor opt-in (a migrated scheduler work handler's context-aware overload).
- **Signature:** `HandleAsync(RuntimeSchedulerWorkItem workItem, IRuntimePipelineContext pipelineContext, CancellationToken)`.
- **Usage:** ADR 0029 Move 2 slot-invoked handler model. A scheduler work handler additionally implements this interface to run inside the pipeline's `Invoke` slot with the per-dispatch context threaded **explicitly** (no ambient/AsyncLocal accessor). The handler either **stages** its assembled `RuntimeCheckpointCommit`(s) on `IRuntimePipelineContext.Workspace` for the `Checkpoint` slot to commit **in order, one committer call per staged entry** (never folded — folding is the coalescing decorators' job), or, for the nested-invoke handlers whose commits must go through a dynamically-resolved provider, commits **inline** in the `Invoke` slot and stages nothing. - **Known implementations (shipped):** workflow `Cancel` + `Checkpoint`; activity `CreateBookmark`, `ScheduleActivity`, `StartActivity` (stage), and the nested-invoke `InvokeActivity` + `ParentActivityCompletion` (inline-commit, stage nothing).

### `IWorkflowDispatchDurabilityEvidence` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Contributor (one contribution per durability boundary a host composes).
- **Signature:** `string Component { get; }` and `WorkflowDispatchDurabilityLevel Level { get; }`. Component names are the constants on `WorkflowDispatchDurabilityComponents`; `Required` lists the five a durable host must cover.
- **Register:** `services.TryAddEnumerable(ServiceDescriptor.Singleton|Scoped<IWorkflowDispatchDurabilityEvidence, TEvidence>())`. `TryAddEnumerable` de-duplicates by **implementation type**, so each boundary needs its own distinct type rather than one type registered repeatedly. Either lifetime is fine — but a *consumer* must be scoped, since some contributions are (see below).
- **Usage:** two consumers, and they are not the same kind of consumer. `WorkflowDispatchReadinessAssessor` aggregates the whole set into a `WorkflowDispatchReadinessReport` — pure reporting. `WorkflowSchedulerCommandRouter` reads it as a **write decision** (#1320): it parks a shed command's work item only when some contribution names `WorkflowDispatchDurabilityComponents.Resumption`, and otherwise refuses outright, writing nothing. The match is on the component *name* and not on `Level`, so a process-local re-driver counts. Two consequences for implementers: a leaf that supplies its own re-driver without contributing that component silently turns parking off for every gated kind on that host; and the contribution proves the re-driver is **registered**, not that it runs, since `RuntimeResumptionPumpTask` is an `IRecurringTask`. The refusal rule itself is documented in the `IRuntimeAdmissionLoadSignal` / `IRuntimeAdmissionController` entry above.
- **Known implementations (shipped):** four process-local defaults registered unconditionally by `AddWorkflowRuntime` — `ProcessLocalCheckpointEvidence`, `ProcessLocalDispatchStoreEvidence`, `ProcessLocalOutboxEvidence`, `ProcessLocalSchedulerEvidence` *(intra-domain — default)*; `DurableResumptionEvidence` from `WorkflowsRuntimeResumptionFeature`, the only contributor of the `resumption` component anywhere in the product *(intra-domain)*; `ProcessLocalDistributionEvidence` from `WorkflowsRuntimeDistributedFeature` *(intra-domain)*; the **scoped** `Ef*DurabilityEvidence` types the Runtime EF Core module contributes *(intra-domain)*; and the scoped distribution durability evidence from `Elsa.Workflows.Runtime.Distributed.Persistence.EntityFrameworkCore` *(intra-domain — that project is domain `Elsa.Workflows`, same as this contract)*. `WorkflowDispatchDurabilityEvidence` (Core, `Models/WorkflowDispatchReadiness.cs`) is a shipped public record implementing the interface; nothing registers it, and it exists so a caller or test can express a contribution without declaring a type.

### `AddWorkflowRuntime(IServiceCollection)` *(engine — `Elsa.Workflows.Runtime`)*

Registers the full hosting-agnostic runtime (stores, scheduler queue/drainer, checkpoint committer, pipelines + built-in middleware, dispatcher, ownership fencing, post-commit outbox) so a worker or test harness can compose and drive a drain **without** the API feature. `WorkflowsRuntimeApiFeature` composes it and adds only the API/endpoint concerns. ### `ResumeTargetAttribute` *(Core — `Elsa.Activities.Runtime.Core`)*
- **Kind:** Declaration surface (activity author contract).
- **Signature:** `[ResumeTarget("stable-resume-target-id")]` on an activity handler method.
- **Usage:** declares the stable resume target ID that compile/publish can place into `WorkflowExecutable.ResumeTargets`. Durable bookmarks store the ID, not the C# method name.
- **Not a runtime callback store** — handler method names and delegates are implementation details and are not persisted in `BookmarkState`.
- **Compiler indexing (W8, node-scoped since the BPMN Phase-2 catch-events prerequisite):** `WorkflowExecutableCompiler` reflects `[ResumeTarget]` methods off each node's resolved activity type and indexes them into `WorkflowExecutable.ResumeTargets`. The map key is **node-scoped** (`{executableNodeId}:{attributeId}`, with the attribute id preserved as `LocalResumeTargetId`) — the same rescoped shape the activity-template placer emits — so multiple instances of the same resume-target activity coexist in one workflow (two `Delay`s, or several synthesized BPMN timer catch events). Activities keep registering trigger registrations by their local attribute id; the resume resolver's `(ExecutableNodeId, LocalResumeTargetId)` fallback binds them, and durable bookmarks store the node-scoped id.

### `IRuntimeStructuralActivity` *(Core — `Elsa.Workflows.Runtime.Core`)*
- **Kind:** Engine-only structural activity protocol; not a DI contributor or ordinary activity-author callback surface.
- **Signature:** `ExecuteStructureAsync(IRuntimeActivityExecutionContext context)` returns `ValueTask<RuntimeStructuralContinuation>`.
- **Usage:** lets a composite schedule and coordinate executable children without placing child scheduling or continuation methods on the minimal `IActivity` contract. The initial runtime invocation uses this method instead of `IActivity.ExecuteAsync`. `IRuntimeActivityChildCompletionHandler` and `IRuntimeActivityChildFaultHandler` provide the corresponding parent re-evaluation callbacks.
- **Decision model:** every structural entry point returns one immutable `RuntimeStructuralContinuation`: `Complete(outcome)`, `Defer`, `Faulted(ActivityFault)`, or `Cancel(reason)`. A terminal decision cannot schedule children in the same evaluation. Initial execution may defer only after scheduling at least one child; a child callback may defer while awaiting existing children or after scheduling the next child.
- **Child-subtree cancellation (spec 112):** a child callback may stage `RequestChildSubtreeCancellation(childActivityExecutionId, reason)` against a live direct child. `ActivitySubtreeCancellationPlanner` traverses the subtree, terminalizes cancellable members to `Cancelled`/`ParentCancelled`, captures an `ActivityScopeCleanupRequest` (bookmarks, durable timers, queued scheduler work), and suppresses the subtree's non-terminal incidents; the parent-evaluation handler folds it all into the same checkpoint commit as the continuation (honored with `Defer`/`Complete`; terminal targets skip as a legal race; structural misuse faults the evaluation). The same planner backs the `CancelActivityScope` scheduler command.
- **Child-fault absorption (spec 115):** a child-fault callback may stage `RequestChildFaultAbsorption(incidentId, reason)` naming the evaluation's incident. The incident resolves with an `AbsorbFault` outcome sourced from `StructuralFaultAbsorption`, and the faulted child's leftover subtree is reclaimed via the same planner (`Cancelled`/`FaultAbsorbed` descendants, cleanup capture, other incidents suppressed) in the continuation's commit. Absorption is a runtime-internal structural operation; public strategy actions cannot request it.
- **Trigger identity (spec 089 D / 117 D4):** `IRuntimeActivityExecutionContext` exposes the committed, spoof-proof start identity — `TriggerNodeId` (the matched binding's executable node id) and `TriggerMetadata` (the binding's free-form `string→string` map, carried verbatim from `WorkflowTriggerBinding.Metadata`). Both are seeded onto reserved durable channels at the workflow-started checkpoint (never the `input:*` namespace) and projected back by `RuntimeInputBindingStateProjection`. A structural trigger activity (e.g. `BpmnProcess`) compares `TriggerNodeId` to its own node id to detect a trigger delivery and reads per-descriptor routing facets from `TriggerMetadata` (e.g. the BPMN start element id under `"bpmn.startElementId"`). The stimulus router forwards `binding.Metadata` through the start dispatch; the recurring-trigger pump's `StartOnly` path rides the same router code, so timer-start metadata flows for free.
- **Live child activities (spec 119 D4; spec 121):** a structural activity that also implements the opt-in marker `IRuntimeLiveChildActivityConsumer` receives its parent's direct, non-terminal child executions on `IRuntimeActivityExecutionContext.GetLiveChildActivities()` (each `RuntimeLiveChildActivity` = activity-execution id + executable node id + status + **iteration id**), populated **only** during a child-completion/child-fault evaluation and loaded from committed state via `IActivityExecutionStateStore.ListAllByParentAsync` (read-only, spoof-proof). Non-consumer parents pay nothing; the collection is empty for initial/resume evaluations. This is the lookup that lets a first-catch-wins racer (the BPMN event-based gateway) resolve a losing sibling's node id to its live child activity-execution id before staging that subtree's `RequestChildSubtreeCancellation`. `IterationId` (spec 121, populated from the child's `ActivityExecutionState.IterationId`) disambiguates N concurrent same-node children of a multi-instance host, so a consumer keys the lookup by `(executable node id, iteration id)` rather than node id alone; it is `null` for ordinary single-run children.
- **Scoped-variable read (spec 123 D1):** a structural activity that implements the opt-in marker `IRuntimeScopedVariableReader` may read its enclosing container-scoped variable values through `IRuntimeActivityExecutionContext.TryReadScopedVariableValue(name, out ValueEnvelope? envelope)`, populated by the runtime on the invoke, child-completion/child-fault, and bookmark-resume paths (all three handlers, marker-gated). The projection is built from committed frame state via `RuntimeContainerScopeService.ProjectScopedVariablesForReaderAsync` (which reuses `BuildVisibleFramesAsync` with `includeOwnContainer: true` + `ProjectVisibleVariableEnvelopes`, the same name→key resolution the leaf input-binding path uses), so there is one variable-value truth and no re-implemented envelope-unwrap. Resolution is by name across the activity's own visible chain only — own iteration → own container → ancestors → the workflow root frame — innermost scope winning for a shadowed name; it is read-only, spoof-proof (the ancestor walk is the ownership guard), and exposes committed values only (a concurrent-branch write becomes visible only once committed, on a later evaluation's basis). A non-marker activity, or a name that resolves to no visible declared variable, reads `false` with a `null` envelope — it never throws on an unpopulated seam. `BpmnProcess` uses it to read a collection-mode multi-instance host's collection variable once at loop start (spec 123 D2). The `VariableScope` type and the `variableScope: null` handler arguments are untouched (still unwired).
- **Input re-materialization (issue #977):** a structural activity that implements the opt-in marker `IRuntimeRematerializeInputsOnChildCompletion` has its input snapshot re-materialized from live committed variable frames before every child-completion/child-fault evaluation (`RuntimeActivityInputSnapshotMaterializer`, the same materialization the start handler pins the entry snapshot with, so frame visibility is identical to entry — ancestors + root, not the own container). The fresh snapshot is **transient**: the pinned `ActivityExecutionState.InputSnapshot` committed at activation stays immutable (ADR 0045 §3's invocation record is unchanged), and the re-read is a pure function of committed frame state, so redelivery converges. Non-marker composites reuse the pinned snapshot byte-for-byte; the notification and bookmark-resume evaluations never re-materialize. `While` is the sole implementer — its loop condition must observe a body's committed `Set` of the condition variable to terminate.
- **Known implementations (shipped):** `Sequence`, `Flowchart`, `Parallel`, `If`, `Switch`, `For`, `ForEach`, `While` (also an `IRuntimeRematerializeInputsOnChildCompletion`, issue #977), `Do`, and `BpmnProcess` (also a `[TriggerActivity]`, spec 117, an `IRuntimeLiveChildActivityConsumer`, spec 119, and an `IRuntimeScopedVariableReader`, spec 123).

## Coalescing checkpoint persistence *(opt-in — W9 / E3-6 / RT-10)*

The burst-coalescing persistence policy is an **opt-in** durability/throughput trade, enabled with
`services.AddCoalescingRuntimeCheckpointPersistence()` (in `Elsa.Workflows.Runtime.Api.Coalescing`). It is
**not** registered by default: the default runtime keeps `ImmediateRuntimeCheckpointPersistencePolicy` and
the contracts/decorators below are absent, so the default path is byte-identical. When enabled, it swaps the
policy to `CoalescingRuntimeCheckpointPersistencePolicy` and layers ambient-session decorators over the
checkpoint commit store, scheduler queue, post-commit outbox, and state stores (including a durable-baseline
read memo over the inspection store — spec 131). See
[`docs/runtime-durable-resumption.md`](../../../../docs/runtime-durable-resumption.md#coalescing-checkpoint-persistence--the-deferred-flush-window-e3-6--rt-10)
and the [benchmark results](../../../../docs/reports/elsa-4-architecture-review-2026-07/w9-checkpoint-coalescing-benchmark.md).

> **Documented ADR 0033 deviation.** The two coalescing interfaces below moved to the
> `Elsa.Workflows.Runtime` engine package instead of staying in `.Core` with the other contracts:
> both expose the concrete `RuntimeCoalescingSession` (engine working state) on their signatures, so
> they cannot stand ahead of the engine, and their only consumers are the opt-in coalescing
> composition in `Runtime.Api` plus its tests. Their namespace, `Elsa.Workflows.Runtime.Contracts`,
> follows that package. This canonical catalog covers both the contracts and engine-hosted deviations.

### `IRuntimeCoalescingSessionAccessor` *(engine — `Elsa.Workflows.Runtime`)*
- **Kind:** Replacement (one ambient accessor exposes the active coalescing session to the decorators).
- **Signature:** `RuntimeCoalescingSession? Current { get; }`, `IDisposable Push(RuntimeCoalescingSession? session)`.
- **Usage:** an `AsyncLocal` push/pop stack that makes the current drain segment's in-memory working set ambient to the coalescing store/queue/outbox decorators, mirroring the existing ambient ownership-scope resolution. Only registered by the opt-in extension.
- **Default implementation:** `AsyncLocalRuntimeCoalescingSessionAccessor` *(opt-in only)*.

### `IRuntimeCoalescingDrainScopeFactory` *(engine — `Elsa.Workflows.Runtime`)*
- **Kind:** Replacement (one factory opens the per-drain coalescing scope and performs the quiescence flush).
- **Signature:** `IRuntimeCoalescingDrainScope Begin(string workflowExecutionId, int? maxSegmentCheckpoints = null)`; scope exposes `RuntimeCoalescingSession Session` and `ValueTask FlushAtQuiescenceAsync(CancellationToken)`. The optional cap overrides the host-configured `MaxSegmentCheckpoints` for that run (ADR 0032 R5 per-workflow authored cadence).
- **Usage:** `WorkflowDrainOrchestrator` opens a scope around a drain when the factory is registered (greediest resolvable ctor), buffers intra-drain checkpoints in the session, and flushes one folded atomic commit at quiescence through `RuntimeCheckpointCommitter.CommitAsync` (so W5 ownership fencing still gates it). Per execution, the orchestrator first consults `IRuntimeCheckpointCadenceResolver` (per-run stamp > authored-on-executable cadence > host default) and skips the scope entirely for an authored-Immediate run. Only registered by the opt-in extension.
- **Default implementation:** `RuntimeCoalescingDrainScopeFactory` *(opt-in only)*.

### `IRuntimeLiveDrainDeliveryAccessor` *(engine — `Elsa.Workflows.Runtime`)*
- **Kind:** Replacement (one ambient accessor marks the live drain that owns an execution's post-commit intent delivery — WU-2, spec 105-runtime-live-drain-delivery).
- **Signature:** `RuntimeLiveDrainDeliveryScope? Current { get; }`, `IDisposable Push(RuntimeLiveDrainDeliveryScope? scope)`.
- **Usage:** an `AsyncLocal` push/pop stack, mirroring `IRuntimeCoalescingSessionAccessor`. `WorkflowDrainOrchestrator.DrainCoreAsync` pushes a scope on the Immediate (no coalescing scope factory) branch, bounded by the RT-2 single-writer lease. While the scope is ambient, `RuntimePostCommitOutboxProcessor` delivers `EnqueueSchedulerWork` intents for the owning execution in-memory — idempotent `EnqueueAsync` plus a direct `Pending -> Delivered` mark via the existing non-claim recording contract — skipping the durable claim round-trip. It never engages while a coalescing session is active (the overlay is authoritative) and leaves other intent kinds, other executions, and unmarked callers (recovery sweep, v1 stores) on the durable claim path. The scope is not exclusive: the sweep can still take the owning execution's continuation (#1798). The drain then treats it as its own until it is delivered and drained (#2225, see `IWorkflowDrainOrchestrator`). Registered by default because Immediate is the default cost model.
- **Default implementation:** `AsyncLocalRuntimeLiveDrainDeliveryAccessor`.

## Runtime alteration contracts

| Contract | Ownership and use |
|---|---|
| `IWorkflowAlterationStore` | Single-owner durable plan/target/job storage. Its claim, seal, terminal, and paging operations preserve fenced at-least-once execution. |
| `IWorkflowAlterationPayloadProtector` | Protects deferred envelope JSON with plan/tenant/request associated data. Durable hosts replace the development-only key material with a restart-stable retained key ring. |
| `IWorkflowAlterationRegistry` | Singleton descriptor-only catalog. It returns stable kind/version/display metadata and never resolves handler instances. |
| `IWorkflowAlterationPreflightHandler` | Scoped, trusted custom contribution registered through `AddWorkflowAlterationHandler<T>`. It validates its own payload and may only update projection/staging state. |
| `IWorkflowAlterationProjectedState` | Per-job mutable in-memory view shared in envelope order. A handler can expose its staged logical state to later handlers without persistence. |
| `IWorkflowAlterationStagingWorkspace` | Per-job collector for deterministic checkpoint-bound changes. Duplicate change keys fail preflight. |
| `IWorkflowAlterationRuntimeCheckpointStagedChange` | Handler-owned change that applies through the Runtime alteration checkpoint builder after all preflights pass. |
| `IWorkflowAlterationCheckpointWriter` | Single-owner atomic checkpoint collaborator. It persists terminal job evidence with workflow/activity/bookmark/value/scheduler/outbox changes and supports acknowledgement reconciliation. |
| `IWorkflowAlterationHandlerResolver` | Scoped exact `(kind, schemaVersion)` resolver. Hosts do not replace it to choose a handler dynamically or infer a latest version. |

Custom handlers are trusted code. They must use only stable envelope identity, must not serialize or log payloads,
must return bounded safe failures, and must make their changes replay-safe under the deterministic job checkpoint.
They must not use the alteration path to bypass activity ownership, authorization sealed at submission, workflow actor
serialization, or Runtime's persistence/checkpoint boundary.

The public envelope and persisted plan use only `kind`, `schemaVersion`, and protected JSON. Do not persist a CLR
type name, assembly-qualified type, service key, or executable payload schema type as an alteration identity.
