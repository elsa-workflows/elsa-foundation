# DispatchWorkflow runtime

This module owns the Foundation-native `DispatchWorkflow` activity and its child-start post-commit handler. Enable the `ActivitiesDispatchWorkflowRuntime` shell feature; it has a hard dependency on `WorkflowsRuntimeResumption` so cross-execution child starts are delivered by the global pump, outside workflow actor mailboxes.

#676 supports fire-and-forget dispatch against the exact live Published source pinned into the parent executable. The parent completion checkpoint atomically records the `Dispatched` result, deterministic child ID, Pending dispatch record, and start intent.

#677 makes that pin deterministic and retained. Publication validates the child artifact's versioned workflow-input contract and records an exact child artifact ID/hash dependency bound to the dispatch node. Runtime validates realized dynamic inputs before checkpoint staging, materializes supported literal defaults, and starts the retained child through immutable parent-artifact/node authority even after the child's source is replaced or unpublished. Typed runtime context such as tenant and authority never comes from the workflow input bag.

Cross-workflow dispatch increments durable `DispatchNestingDepth` exactly once. Root starts and legacy payloads begin at zero; the default maximum child depth is 32 and hosts can configure a positive alternative through `DispatchWorkflowRuntimeFeature.MaxNestingDepth`. Delivery and replay preserve the staged depth and recheck the configured limit before materialization.

The in-memory provider proves asynchronous semantics and replay convergence within one process. It is not process-crash durable. The EF Core runtime module persists executable dependency metadata, closure-wide artifact lease fencing, dispatch lifecycle state, and post-commit delivery evidence.

The runtime feature registers the default allow start policy. Hosts may replace `IWorkflowExecutableStartPolicy` with exactly one implementation to deny future child materialization using immutable executable/authority context. Policy denial does not rewrite the artifact or affect already-materialized execution state.

#678 persists dispatch records, retained executable dependencies, and post-commit outbox state through the runtime checkpoint transaction. The provider-backed stores preserve deterministic identities, fenced claim completion, and authenticated inspection across process restart.

#679 adds successful `WaitForCompletion=true` execution. The parent wait checkpoint atomically records its non-expiring bookmark, suspended activity, Pending dispatch record, child ID output, and child-start intent. A successful child terminal checkpoint records the Completed dispatch projection and one deterministic parent-resume intent carrying the child's committed output values (see Outputs below). Resume delivery is performed by the global post-commit pump and retries with positive backoff until bookmark consumption is durably observable; duplicate delivery before or after consumption converges without a second logical completion. Unbounded retries emit payload-free structured warnings for operational alerting.

#680 completes waited child fault/cancellation propagation and parent-cancellation delivery. Terminal child evidence is projected through the same deterministic resume route, while cancel commands retain their original dispatch/child/idempotency identities and converge across duplicate or restarted delivery.

#681 adds host-configured finite child-start retry, fixed safe delivery classification, provider-atomic exhausted-delivery projection, and separately authorized detached redrive. The Runtime domain owns the replacement seam and fenced completion/redrive contracts; this feature supplies the single `WorkflowDispatchDeliveryFailureProjector` replacement and the child-specific policy. A visible deterministic child always wins over a stale failure. Wait exhaustion produces one safe, permanently non-redrivable `DispatchFailed` resume; fire-and-forget exhaustion exposes only allowlisted incident/dead-letter metadata and can reopen the same dispatch/outbox identity through the tenant-scoped manage endpoint.

#1799 also stops a refused first commit from stranding a waited parent on the forwarded path. A start forwarded through distributed placement is acknowledged before the child runs, so the owning node's refusal never reaches the parent's dispatch. The runtime now faults such a child into existence from its start command, which gives its dispatch the child's own `Faulted` outcome through the ordinary enrichers, so the parent resumes with a child outcome rather than a delivery failure. A rule that refuses the child's content refuses that commit too, and the start then fails to `DispatchFailed` as before.

#1799 stops a `Duplicate` dispatch result from counting as a delivered start on its own. `Duplicate` has two producers that mean opposite things: the start dispatcher answers it after reading the child's durable state, which is proof the child exists, while an agent answers it out of a process-local, bounded idempotency cache, which proves only that the key was seen there. A start whose refusal could not be recorded consumes its key before the refusal is reported, so claim expiry redelivers into the second kind, carrying none of it. The two are now told apart by whether a child can be seen: one that reached a child stays delivered, and one with no child to show for it is a failed delivery that retries, because the answer comes from a cache that keeps answering the same way while the evidence is read again on every attempt. Its own delivery budget then dead-letters it into `DispatchFailed`, which is how the parent gets an answer.

## Outputs

Spec 1245 gives the activity three outputs: `ChildWorkflowExecutionId`, `Status` and `Output`. There is no `Result` output.

- `Status` is the outcome the dispatch selected: `Dispatched`, `Completed`, `Faulted`, `Cancelled` or `DispatchFailed`. Several outcomes can lead to the same node, and `Status` says which one ran.
- `Output` holds the completed child's named outputs as one JSON object (name to value), holding the committed values unchanged. No diagnostics capture setting truncates or redacts them.
  - It is `{}` after a faulted, cancelled or failed child, so no child data crosses (spec 100), and a member read gives `undefined`.
  - It is absent on `Dispatched`, so a capture leaves its variable unchanged.
  - Outputs that are sensitive, require encryption, or carry a redaction mode or a retention policy, and outputs not stored inline, are left out. That loss is declared on the `Output` contract (ADR 0046 V6). Each run that leaves one out reports the `dispatch.child-output-withheld` warning, whose `outputs` detail lists the names in ordinal order and never a value.
- The terminal status, the allow-listed fault and cancellation diagnostics, and the child-control transport stay in the stored activity result as `Terminal`. It is not an output, but the whole-result read still reaches it.

TestRun behavior and distributed two-node delivery remain owned by #682 and #683 respectively.

See [EXTENSION_POINTS.md](EXTENSION_POINTS.md) and the feature specifications under `specs/096-dispatch-workflow-fire-and-forget/` through `specs/101-dispatch-delivery-recovery/`.

## BulkDispatchWorkflows

Spec 1242 (`specs/1242-bulk-dispatch-workflows/`) adds `BulkDispatchWorkflows` (runtime type `Elsa.BulkDispatchWorkflows`): start one child workflow per item, optionally wait for all of them, and run a branch per child that ends.

- **Shape.** One input, `Items`, and three single slots. `Dispatch` holds one authored `DispatchWorkflow`, which says everything about the child: the target (pinned at publish like any dispatch), `Inputs` and `CorrelationId` (which read `variables.currentItem` and `variables.currentIndex`), `WaitForCompletion` and `CancelChildOnParentCancellation`. `ChildCompleted` and `ChildFaulted` are optional. Publish refuses an empty `Dispatch` slot, or one that holds anything else, with `BulkDispatch/DispatchSlot`.
- **Passes.** For each item the activity runs the `Dispatch` node once, under its own iteration id and with an iteration scope holding `currentItem` and `currentIndex`. Each run is an ordinary `DispatchWorkflow` execution, so dispatch identity, pinning, resume, cancellation, audit and recovery are unchanged. `Completed` runs `ChildCompleted` for that item; `Faulted`, `Cancelled` and `DispatchFailed` run `ChildFaulted`; `Dispatched` (the node did not wait) ends the pass. The activity completes with `Done` when every pass has ended, and at once for null or empty `Items`. A value that is not a collection faults it, as `ForEach` does.
- **Window and cap.** At most 16 passes are open at once; the next item's pass starts as one ends, in item order. A fire-and-forget pass ends straight away, so the window refills at once. More than 1,000 items fault the activity with `BulkDispatchCapExceeded` before anything is dispatched. Neither number is an author input (tuning: #5980; the cap is shared with the parallel ForEach in #5875). For more items, batch them: a sequential `ForEach` over batches, with one bulk dispatch per batch.
- **Faults.** The activity handles no child fault itself, so the workflow's incident strategy decides, for the `Dispatch` execution and for anything in a slot. Under the default Fault strategy the workflow faults. `ChildFaulted` is for children that ended badly, not for a fault of the `Dispatch` node itself (an undeclared child input, the nesting depth, an expression error).
- **ContinueWithIncidents.** The incident stays open and the other passes go on. The faulted pass keeps its place in the window, so 16 open incidents stall the activity. The activity keeps waiting for the faulted child, as `Sequence` does, so an operator ends the pass with `RescheduleActivity` of the faulted activity. `RetryFaultedActivity` is refused there (`NoBlockingIncident`), because the strategy opens the incident instead of waiting for intervention. When a slot holds a `Flowchart` or another composite that handles its own child faults, the fault is reported as the slot's direct child, so that is the activity to reschedule.
- **`DispatchFailed`.** It reaches `ChildFaulted` only when the `Dispatch` node waits. A fire-and-forget child that fails to start is not seen by the bulk activity.
- **Concurrent writes.** Passes run concurrently, so a variable write from `Dispatch` (an output capture) or from a slot gets publish warning `ValueFlow/ConcurrentWrite`, and a shared counter or list can lose updates. Record per-child results in the child workflow, or read them after the bulk activity. A result binding between two different children of the bulk node cannot tell which item's run it reads, so publish refuses it (`ValueFlow/EarlierProducerRun` or `ValueFlow/UnavailableProducer`). Bindings inside one slot keep their own rules.
