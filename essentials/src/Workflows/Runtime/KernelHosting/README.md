# Workflow kernel hosting

The `WorkflowsRuntimeKernelHosting` feature serves the Foundation host's default shell on the built-in Actor Foundation. Add `Elsa.Workflows.Runtime.KernelHosting`, `Elsa.Workflows.Runtime.KernelHost` and `Elsa.Workflows.Runtime.KernelApi` as package roots in the deployment's Nuplane feed, then add `WorkflowsRuntimeKernelHosting` to the default shell. The feature catalog discovers shell features from package roots. Keep the existing design, publication, executable and trigger binding features enabled. The package depends on the shell's workflow runtime API, workflow HTTP activities and Jint engine. The Foundation host loads it from the feed.

Set `Provider` to `SQLite` or `PostgreSQL`. Set `SqlitePath` to an absolute path on a local volume for SQLite. Set `PostgresConnectionString` through deployment configuration for PostgreSQL. Use a dedicated database for either provider. The opt-in serves one tenant and one process. Set `Tenant` to the shell's authoring and runtime persistence tenant. Startup restores that tenant's publications and reads pinned artifacts in the same scope. Restart the host to enable, update, or remove the kernel feature. A refused live replacement leaves the active generation serving.

The existing workflow HTTP options supply the route mount, timeout and maximum request size. The synchronous timeout starts when a route matches and covers the request body, actor reply and response delivery. Published Native and Flowchart workflows can start through their HTTP routes and dispatch to a published child definition, with or without waiting for completion. The normal run list reads the kernel, and the run history endpoint pages and catches up to retained activity starts and outcomes. Publication refuses schedule starts and mid-flow HTTP waits.
