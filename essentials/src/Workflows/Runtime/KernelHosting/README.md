# Workflow kernel hosting

The `WorkflowsRuntimeKernelHosting` feature serves the Foundation host's default shell on the built-in Actor Foundation. Add `Elsa.Workflows.Runtime.KernelHosting`, `Elsa.Workflows.Runtime.KernelHost` and `Elsa.Workflows.Runtime.KernelApi` as package roots in the deployment's Nuplane feed, then add `WorkflowsRuntimeKernelHosting` to the default shell. The feature catalog discovers shell features from package roots. Keep the existing design, publication, executable and trigger binding features enabled. The shell needs the workflow runtime API, workflow HTTP activities and Jint engine. Use `Elsa.Activities.Http` and, for Studio, `Elsa.Activities.Design.Api` from the same package publication as KernelHosting. Include the HTTP package in the deployment's roots so the catalog can discover `ActivitiesHttp` and its HTTP settings export. The Foundation host loads it from the feed.

Set `Provider` to `SQLite` or `PostgreSQL`. Set `SqlitePath` to an absolute path on a local volume for SQLite. Set `PostgresConnectionString` through deployment configuration for PostgreSQL. Use a dedicated database for either provider. The opt-in serves one tenant and one process. Set `Tenant` to the shell's authoring and runtime persistence tenant. Startup restores that tenant's publications and reads pinned artifacts in the same scope. Restart the host to enable, update, or remove the kernel feature. A refused live replacement leaves the active generation serving.

The existing workflow HTTP options supply the route mount, timeout and maximum request size. The synchronous timeout starts when a route matches and covers the request body, actor reply and response delivery. Published Native and Flowchart workflows can start through their HTTP routes, resume through committed mid-flow waits, and dispatch to published child definitions. A wait uses a literal route template with values supplied by the running workflow. A request with no matching wait publishes nothing. The normal run list reads the kernel, and the run history endpoint pages and catches up to retained activity starts and outcomes. Publication still refuses schedule starts.

Automatic deletion is off by default. Set `FinishedRetentionSeconds`, `CancelledRetentionSeconds` or `FaultedRetentionSeconds` to opt in for a terminal status. Use the same policy on PostgreSQL hosts that share a tenant. When the shell starts, it counts already-ended runs that become eligible. A workflow runtime manager in the same tenant can read `GET /runtime/workflows/retention` for the count, effective windows, proposed windows and confirmation. The count is an upper bound because the owner may protect individual runs. A manager without a tenant claim can use the endpoint for the default tenant when authorized there. With more than 100 newly eligible runs, the proposed shortening waits for confirmation. Set `RetentionConfirmation` to the quoted receipt and restart the host to apply the reviewed change. The store records the applied revision and requires a fresh count on activation. If the affected cohort grows beyond the approved count, retrieve a new receipt.

The sweep reads one projected page at a time and sends an exact terminal selection. The owner checks the configured window and the terminal mark again before deleting the run. Unresolved Parks are excluded.

## Ephemeral Execute qualification

Private protocol 125 exercises Ephemeral published Execute through the installed owner. The stock package keeps Ephemeral Execute unavailable. The requester uses the exact published executable in the shell's bound tenant. If the run needs durable storage, the owner pins that published material and settles the first durable turn before returning its readable run ID.

The private response reports `Volatile` after a write-free completion, `Committed` after first durability, `Refused` for a definitive refusal, or `Unavailable` when the local owner could not queue the start. `Unknown` means the requester stopped waiting or ownership was lost after queueing. A commit may still have won, so this response carries no retry hint. Only `Committed` includes a run ID.

If the first turn faults before sealing model state, the owner can commit a Park with the exact original input. An operator's selected Recover retries that uncommitted turn. The store verifies the input against the root's creation fingerprint. The details API reports `Ephemeral` for these committed runs and for ordinary promotions, with boundary-level inspection.

After a volatile checkpoint exists, incident recovery currently covers one unconsumed local self input with no other pending effects. Recovery with several outstanding local inputs and promotion across an unsettled volatile job remain outside the qualified scope. Run private protocol 125 with owners built from the same revision when exercising initial-fault recovery.
